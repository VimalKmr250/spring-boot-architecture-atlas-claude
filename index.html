Start at the boundary, not the beans

Before any layering decision, draw who talks to the system and what it depends on. Every integration on this diagram becomes a failure mode, a timeout budget and an on-call page later.

The move that pays for itselfClassify every external dependency as in the request path or not on day one. Everything not in the path goes through an event and an outbox — that single rule keeps checkout availability at 99.95% while five downstream systems average 99.5%.

The default recommendation

Start as a modular monolith with genuinely enforced boundaries. It gives you the one thing microservices cannot: cheap boundary changes. Getting a boundary wrong is normal; getting it wrong across a network costs a quarter.

Extract a service when you can name the reason

  • Scaling: one module needs 20× the instances of the rest.
  • SLA: checkout must stay up while reporting is being redeployed.
  • Team: a team with its own release cadence is blocked by the train.
  • Compliance: PCI or PII scope you want physically isolated.

"It felt too big" is not on this list.

You will ship your org chart — plan for it

A modular monolith is a compile-time distributed system

One process, one deployable, one transaction manager — but modules that only see each other through published interfaces and events. Every microservice discipline except the network.

Three packages per module, and only one is public

Java gives you public (the whole world) and package-private (this one package). There is nothing in between — so a modular monolith has to invent "module-private" by convention, and then enforce it with tooling.

The gap this works around

Package-private does not nest. order.internal.domain.Order cannot be package-private and still visible to order.internal.app — those are different packages to the compiler. So every class in a module with any internal structure must be public, and therefore callable from every other module.

The three-package layout restores the missing level: the boundary is declared by position in the package tree, and the build enforces that position.

The test for whether api is cleanCould you serialise everything in it to JSON and put it behind HTTP tomorrow, without touching a single field? If yes, the package is honest. That is not hypothetical — it is exactly what happens the day the module is extracted.

Interfaces and records only in api

No @Entity, no Hibernate proxies, no JPA collection types, no Jackson annotations carrying database column names. And nothing in api may reference internal — one field of type Order and the whole boundary is gone.

web belongs in internal

Surprising, but right: no module calls your controller in-process. The HTTP contract is a different contract from the in-process one, and merging them is how a Spring @RequestBody record ends up passed between modules.

OrderRepository is not in spi

It is a port the module implements for itself, in internal/jpa. It lives with the domain that declares it. spi is only for what someone else must provide — the next slide.

api offers; spi requires — and both arrows point inward

This is the part that gets misread. The two packages are not "public" and "also public" — they are opposite ends of the same property: the module depends on nobody, in either direction.

Reach for spi when one of these is true

  • The provider may change. Tax is in-house today, a third-party engine next year.
  • It would otherwise create a cycle. order needs something from fulfilment, which already calls order.api.
  • The module must be extractable blind. When order becomes a service, its spi implementations become HTTP clients and nothing inside order changes.
And when not toOtherwise call the other module's api directly. Every spi port is one more hop between a reader and the real implementation. Most modules should have an empty spi package — a codebase where every cross-module call is inverted is one where nobody can answer "what actually happens when I place an order?" without a debugger.

A boundary nobody can break by accident

Rules in a wiki decay. Rules in the test suite do not. These four tests, running in CI, are the difference between a modular monolith and a monolith with optimistic folder names.

src/test/java/.../architecture/ModuleBoundaryTest.java
@AnalyzeClasses(packages = "com.retailco.shop", importOptions = DoNotIncludeTests.class)
class ModuleBoundaryTest {

    /** 1. Nobody reaches into another module's internals. */
    @ArchTest
    static final ArchRule internals_are_private = SlicesRuleDefinition.slices()
            .matching("com.retailco.shop.(*)..")
            .namingSlices("module $1")
            .should().notDependOnEachOther()
            .ignoreDependency(alwaysTrue(), resideInAPackage("..shop.(*).api.."))
            .ignoreDependency(alwaysTrue(), resideInAPackage("..shop.shared.."));

    /** 2. No module cycles — the rule that keeps extraction possible. */
    @ArchTest
    static final ArchRule no_cycles = SlicesRuleDefinition.slices()
            .matching("com.retailco.shop.(*)..")
            .should().beFreeOfCycles();

    /** 3. The domain stays framework-free: it must survive a Spring upgrade untouched. */
    @ArchTest
    static final ArchRule domain_is_pure = noClasses()
            .that().resideInAPackage("..internal.domain..")
            .should().dependOnClassesThat().resideInAnyPackage(
                    "org.springframework..", "jakarta.persistence..", "com.fasterxml.jackson..");

    /** 4. Controllers never touch repositories — the layering most teams silently lose. */
    @ArchTest
    static final ArchRule web_goes_through_application = noClasses()
            .that().resideInAPackage("..internal.web..")
            .should().dependOnClassesThat().resideInAnyPackage("..internal.jpa..", "..internal.domain..repository..");
}

What it does not do

  • It will not invent boundaries — you still do the domain work.
  • It does not stop cross-schema SQL; that needs a database-level rule or a migration review.
  • Adopting it on a tangled codebase means a long list of violations on day one. Baseline them, then ratchet down.

Pair it with the ArchUnit rules on the previous slide — Modulith owns module-to-module, ArchUnit owns inside-the-module.

Call an API, or publish an event?

This is the single most consequential line-level decision in the codebase. Get it wrong in one direction and modules cannot be extracted; wrong in the other and nobody can follow the flow.

The decision ruleAsk: "if this step fails, should the user's action fail?" Yes → synchronous call, same transaction (taking payment). No → event (sending the confirmation email, updating the loyalty balance, reindexing search). Teams that apply only this one rule consistently end up with a system that can be pulled apart later.

The in-process event that survives a crash

A plain ApplicationEventPublisher event is lost if the JVM dies between commit and listener. Spring Modulith's event publication registry writes the event into your database inside the same transaction — the transactional outbox, without the boilerplate.

order/internal/app/PlaceOrderUseCase.java
@Transactional
public OrderId place(PlaceOrderCommand cmd) {
    var order = Order.place(cmd.customerId(), cmd.lines(), pricing.quote(cmd));
    repository.save(order);

    // written to event_publication in THIS transaction
    events.publishEvent(new OrderPlaced(
            order.id().value(), order.customerId().value(),
            order.total(), Instant.now()));

    return order.id();            // commit → listeners fire
}
inventory/internal/OrderPlacedListener.java
@Component
class OrderPlacedListener {

    // runs AFTER commit, in a NEW transaction
    @ApplicationModuleListener
    void on(OrderPlaced event) {
        inventory.reserve(event.orderId(), event.lines());
    }
    // success  → row deleted from event_publication
    // throws   → row keeps completion_date = null
    //            and is retried on restart / by the republish job
}

@ApplicationModuleListener

Is just @Async + @Transactional(REQUIRES_NEW) + @TransactionalEventListener(AFTER_COMMIT) in one annotation — the three you would otherwise forget one of.

Incomplete-publication job

spring.modulith.republish-outstanding-events-on-restart=true replays anything stuck. Alert on the age of the oldest incomplete row — it is your best early-warning metric.

Externalising later

Add @Externalized("order.placed::#{#this.orderId}") and the same event goes to Kafka with the key you name. Nothing in the producing code changes.

Ordering caveatThe registry guarantees at-least-once, not ordering and not exactly-once. Listeners must be idempotent — reserve inventory keyed on orderId, not by incrementing a counter.

Extraction, when the evidence arrives

A module built this way is extracted in days, not a quarter, because the seam already exists. The order of operations matters more than the tooling.

The trapExtracting a module whose tables are still joined from three other modules. You will end up with a "service" that shares a database — all the latency of distribution, none of the autonomy. Split the data first, run for a month, then split the process.

Strangling a legacy system, concretely

"Strangler fig" is quoted constantly and implemented rarely. The whole pattern is one component — a router at the edge — plus the discipline to migrate by capability rather than by table.

Pick the first capability carefully

High enough value to justify the router, low enough risk to survive being wrong, and with data you can genuinely separate. A read-only reporting view is a common, sensible first cut.

Branch by abstraction, inside the code

When the seam is a class rather than an HTTP route: introduce an interface, implement it twice, switch with a flag, delete the old one. Same shape as the router, no infrastructure at all.

Budget for the double-run

Running both systems, reconciling them and fixing the differences is real work that appears in no estimate. Plan for it explicitly or the migration stalls at 70% and stays there.

The anti-corruption layer is not optional here

Their model is thirty years old, uses CUST-STAT-CD with eleven values, and encodes business rules in the ordering of a COBOL copybook. Translate it at the boundary into your language, in exactly one class.

Without that layer, CUST-STAT-CD appears in your domain, your API, your database and your frontend — and the legacy system's model becomes your model permanently, including after it is retired.

Design for their maintenance windowIf the ERP is down 02:00–04:00 nightly, that is an architectural constraint, not an operational detail. Queue the work, make the queue durable, and make your UI honest ("submitted — confirmation within 2 hours") rather than pretending the call is synchronous and timing out.
Reconciliation is a featureAny integration that is not a single transaction will drift — a message dropped, a file half-processed, a record rejected silently. Build a daily reconciliation job and a report of differences from the start. Every team that adds it after the first incident wishes they had had it before.

Four layers, one direction of dependency

Ports and adapters, named in Spring terms. The rule is a single arrow direction: everything points inward at the domain, and the domain points at nothing.

Pragmatic dialA pure domain costs a mapping layer. For a CRUD-ish module (catalog admin), skip it: @Entity straight to the controller is fine and honest. Spend purity where the rules live — order, pricing, payment.
Test signalIf your domain test needs @SpringBootTest, the layering has already failed. Domain tests are new Order(...) and JUnit, nothing else.

The aggregate: where invariants actually live

An anaemic Order with getters and setters pushes every rule into a service, where it gets duplicated. Put the rules on the object that owns the data, and make illegal states unrepresentable.

order/internal/domain/Order.java — the consistency boundary
public final class Order {

    private final OrderId id;
    private final CustomerId customerId;
    private final List<OrderLine> lines;
    private OrderStatus status;
    private Money total;
    private long version;                    // optimistic lock, see the concurrency slide

    /** Factory carries the creation rules; no public constructor, no setters. */
    public static Order place(CustomerId customer, List<OrderLine> lines, Money quotedTotal) {
        if (lines.isEmpty())                 throw new EmptyOrderException();
        if (lines.size() > MAX_LINES)        throw new OrderTooLargeException(lines.size());
        if (!quotedTotal.equals(sum(lines))) throw new PriceMismatchException();
        return new Order(OrderId.generate(), customer, List.copyOf(lines), PLACED, quotedTotal);
    }

    /** State transitions are methods, and each guards its own precondition. */
    public void markPaid(PaymentReference ref) {
        if (status != PLACED) throw new IllegalTransition(status, PAID);
        this.status = PAID;
        this.paymentRef = ref;
    }

    public void cancel(CancellationReason reason) {
        if (status == SHIPPED || status == DELIVERED)
            throw new OrderAlreadyShipped(id);   // the rule the business actually cares about
        this.status = CANCELLED;
    }

    public Money total() { return total; }                       // no getters that leak mutability
    public List<OrderLine> lines() { return List.copyOf(lines); }
}

Aggregate = transaction boundary

One aggregate, one transaction, one optimistic lock. If two aggregates must change atomically, you have drawn the boundary wrong — or you need a saga.

Reference other aggregates by ID

CustomerId, not Customer. An object graph that spans aggregates is the N+1 generator and the reason nothing can be extracted later.

Value objects earn their keep

Money with a currency prevents the class of bug that BigDecimal plus a comment does not. Same for OrderId vs UUID.

The application service does four things, and no more

Load, invoke the domain, save, publish. Orchestration lives here; rules do not. When a use case grows an if about business meaning, that if belongs on the aggregate.

Transactions: the four things that bite

@Transactional looks like a keyword and behaves like a proxy. Almost every production transaction bug is one of these four.

1 · Self-invocation does nothing

@Service
class OrderService {
    public void importAll(List<Row> rows) {
        rows.forEach(this::importOne);   // ← proxy bypassed
    }
    @Transactional public void importOne(Row r) { ... }  // NOT transactional here
}

Fix: move importOne to another bean, or inject TransactionTemplate. Spring 7 logs a warning for this case; older versions failed silently for years.

2 · Rollback rules surprise people

By default Spring rolls back on RuntimeException and Error — not on checked exceptions. A checked PaymentDeclinedException commits the half-written order.

@Transactional(rollbackFor = Exception.class)

…or simply make domain exceptions unchecked, which is the convention worth adopting wholesale.

3 · The transaction is not the message boundary

Committing the order and publishing to Kafka are two systems. There is no distributed transaction here that you want. Use the outbox: write the event to your database in the same transaction, relay it after.

"Send then commit" loses events on rollback; "commit then send" loses them on crash. Only the outbox survives both.

4 · REQUIRES_NEW is a second connection

It suspends the current transaction and takes another connection from the pool. Nest it inside a loop and you deadlock your own pool. Legitimate uses: audit rows that must survive a rollback, and @ApplicationModuleListener.

Default postureOne transaction per use case, opened in the application service, never in the controller and never in the repository. Read paths get readOnly = true — it lets Hibernate skip dirty-checking and lets the driver route to a replica.

Two customers, one last unit of stock

Concurrency bugs are invisible in test and inevitable at scale. Two mechanisms cover almost everything: optimistic locking for state you own, idempotency keys for operations you cannot afford to repeat.

Optimistic locking — cheap, correct, retryable
@Entity
class InventoryItemEntity {
    @Id UUID sku;
    int available;
    @Version long version;          // Hibernate adds ... WHERE version = ?

Idempotency key — the only safe way to retry a payment
@PostMapping("/orders")

        @RequestHeader("Idempotency-Key") @NotBlank String key,
        @Valid @RequestBody PlaceOrderRequest req) {

    return idempotency.execute(key, req.fingerprint(), () -> orders.place(req.toCommand()));
}

// execute(): INSERT INTO idempotency_key(key, fingerprint, status) VALUES (?,?, 'IN_PROGRESS')
//   unique violation + same fingerprint  → return the stored response (200/201, same body)
//   unique violation + diff. fingerprint → 422, the client reused a key for a different request
//   success                              → store response body + status against the key, TTL 24h

Why not pessimistic locks

SELECT ... FOR UPDATE is correct but serialises the hot row. Fine for a rarely-contended ledger; fatal for a flash-sale SKU. Optimistic + retry lets the uncontended 99% run free.

Retry only what is safe

Retrying a non-idempotent POST is how customers get charged twice. The rule: no retry without an idempotency key, at every layer — client, gateway, and your own @Retryable.

"Exactly once" does not exist

Over a network you get at-most-once or at-least-once. Exactly-once effects are achieved by making at-least-once delivery hit an idempotent handler. Say it that way in a review and in an interview.

The compatibility rules that avoid versions entirely

  • Additive only: new optional fields, never a removed or renamed one.
  • Never repurpose a field. status gaining a new enum value breaks every client with an exhaustive switch — add statusV2 or document the open set from day one.
  • Tolerant reader on every consumer: ignore unknown fields (FAIL_ON_UNKNOWN_PROPERTIES=false).

The event backbone, drawn as it really is

"We use Kafka" says nothing. What matters is the topic list, who owns each one, what the key is, and where poisoned messages go.

Topic naming carries ownership

<domain>.<entity>.<event>.v<n>. The version in the name means a breaking schema change is a new topic and a dual-publish window, not a coordinated big-bang deploy.

Events, not commands, on the bus

OrderPlaced (fact, past tense, many consumers) not SendEmail (instruction, one consumer). Facts let you add consumers without touching the producer — the whole point.

Thin or fat?

Thin events (ids only) force a call back and couple you to producer availability. Fat events (a snapshot of what changed) are the enterprise default: bigger payload, independent consumers.

The consumer that survives a bad Tuesday

Four properties make a Kafka consumer operable: bounded retry, a dead-letter path, idempotency, and manual offset commit. Missing any one of them produces an incident that ends with "we replayed the whole topic".

@Component
class OrderPlacedConsumer {

    @KafkaListener(topics = "orders.placed.v1", groupId = "inventory",
                   concurrency = "6")
    @Transactional
    public void handle(@Payload OrderPlaced event,
                       @Header(RECEIVED_KEY) String key,
                       Acknowledgment ack) {

        // idempotency: the natural business key, not an offset
        if (reservations.existsByOrderId(event.orderId())) {
            ack.acknowledge();                 // already done — a duplicate, not an error
            return;
        }
        inventory.reserve(event.orderId(), event.lines());
        ack.acknowledge();                     // commit offset only after the work committed
    }
}

@Configuration
class KafkaErrorConfig {
    @Bean DefaultErrorHandler errorHandler(KafkaTemplate<?, ?> template) {
        var recoverer = new DeadLetterPublishingRecoverer(template,
                (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));

        var handler = new DefaultErrorHandler(recoverer,
                new ExponentialBackOffWithMaxRetries(3));   // 3 tries, then DLT — never infinite
        handler.addNotRetryableExceptions(
                DeserializationException.class,             // a poison pill never gets better
                IllegalArgumentException.class);
        return handler;
    }
}
The silent killerDefault enable.auto.commit=true commits offsets on a timer, regardless of whether your handler succeeded. A crash mid-batch loses messages that Kafka believes were processed. Set ack-mode: MANUAL_IMMEDIATE and commit yourself.
Infinite retry = stopped partitionA message that can never succeed, retried forever, blocks its partition and every message behind it. Bound the retries, publish to the DLT, alert, move on. Ordering is preserved for everything that can proceed.
Consumer lag is your real SLIAlert on kafka_consumergroup_lag and on DLT depth, not on CPU. Lag rising steadily means consumers cannot keep up — scale to the partition count, then increase partitions. Lag flat but non-zero at a fixed number usually means one stuck partition.

The outbox: the only honest way to write and publish

You cannot atomically commit to PostgreSQL and produce to Kafka. So don't try — commit the intent to publish alongside the data, and let a separate process do the publishing.

Polling relay

SELECT ... WHERE sent_at IS NULL ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 100, publish, mark. Simple, no extra infrastructure, adds polling latency (typically 200 ms–1 s). Spring Modulith's registry is exactly this.

CDC (Debezium)

Reads the write-ahead log, so no polling, no load on the table, ordering guaranteed by the log, latency in milliseconds. Costs a Kafka Connect cluster and replication-slot operations. Worth it above roughly a few thousand events/sec.

A saga is a transaction you cannot roll back

Checkout touches payment, inventory and fulfilment. Two-phase commit across them is unavailable, slow and locks everything. Instead: a sequence of local transactions, each with a compensating action.

Orchestration default for enterprise

A OrderSaga state machine owns the sequence, persists its state, and issues the next command. You can query "where is order 88421 stuck". Costs a central component that knows all the steps.

Choreography

Each service reacts to events with no coordinator. Lower coupling, but the flow exists only in people's heads and in traces — debugging a stuck order means reading five services' logs. Fine for 2–3 steps, painful at six.

Non-negotiables for either stylePersist the saga state (order_saga table with a status and a step). Make every step idempotent and keyed. Put a timeout on every step — a saga with no timeout has orders that sit in AWAITING_PAYMENT for eleven days and nobody notices until finance asks.

Why order_summary exists

It is a denormalised table maintained by event listeners — it already contains the customer's display name and the line count, so the order-history screen is one index scan instead of three joins across two schemas that the boundaries forbid anyway.

Cost: eventual consistency of a second or two, and a rebuild job. Benefit: the p99 on your most-hit screen drops by an order of magnitude and stops depending on other modules.

Make rebuild a first-class featureEvery projection needs a documented, tested "replay from scratch" path. You will need it — after a bug, after a schema change, and the first time someone asks for a field you did not project.
Where the line isUse a read model when the query is hot, cross-module, or awkward. Do not project everything: each projection is a second source of truth that can drift, and drift is discovered by customers.

Event sourcing: store the decisions, derive the state

Instead of a row that holds where the order is now, an append-only log of everything that happened to it. Current state is a fold over that log. The question is never "is it elegant" — it is whether the audit trail is a requirement or a nice-to-have.

Justified when

  • The audit trail is the requirement — ledgers, trading, regulated workflows where "prove what you knew and when" is a legal question.
  • Temporal queries are a real business need, not a hypothetical.
  • The domain is genuinely event-shaped and experts already talk in events.
  • You need to retro-actively fix a bug by replaying with corrected logic.

Not justified when

  • "It would be good to have history" — an audit table or a domain-event log is a tenth of the cost.
  • The team has not run it before and the domain is still moving.
  • Ad-hoc querying matters: analysts cannot query an event stream.
  • You mainly wanted decoupling — that is the outbox, and you can have it today.

What it actually costs to run

Four mechanisms you must build and operate. None is hard on its own; together they are the reason this is a considered architectural commitment rather than a storage choice.

The four things you must build

Snapshots
Replaying 40,000 events per load is not viable. Snapshot every N events and replay only the tail.
Projections
Nobody queries the event store. Every read model is built by a projector, which must be restartable, idempotent, and monitored for lag.
Schema evolution
You can never delete an event type. Version them, and keep upcasters that convert v1 payloads to v3 — forever.
Replay tooling
Rebuilding a projection from scratch must be a routine, tested operation, not a heroic weekend.
The mistake that ends projectsPutting the current time or a call to another service inside the aggregate's decision logic. Replay then produces different events than the original run, and the log stops being a faithful record. Decisions must be a pure function of (state, command, data carried on the command).
The pragmatic middleNormal state storage, plus a durable, immutable domain-event log written in the same transaction (the outbox). You get the audit trail, the integration events and the ability to rebuild read models — without upcasters, snapshots or a team that must think in streams. For most enterprise domains this is the right trade.

Keep search and reporting off the transactional database

Two workloads destroy OLTP performance: full-text search with filters, and analysts running unbounded joins. Both have an obvious home, and both get there through events.

Routing rule worth writing downAfter a write, pin that user's reads to the primary for a short window (a sticky flag in the session or a Redis key keyed on user id). It is five lines of code and removes an entire category of support ticket.

Design-first vs code-first

Code-first (annotations → spec) is faster and what most Spring teams do; the risk is a spec that documents whatever the code happened to do.

Design-first (spec → stubs) is right when an external party or another team consumes the API and the contract must be agreed before either side builds. Use it for partner APIs, code-first internally.

Contract tests for the async sideOpenAPI covers HTTP. Kafka events need the same treatment: register Avro/JSON schemas, set compatibility to BACKWARD, and let the registry reject an incompatible producer at deploy time.

Where the token lives decides your threat model

Micro-frontends: usually the wrong answer

They solve an organisational problem — independent deployment by separate teams — at a real technical cost. If you do not have that organisational problem, you are buying the cost for nothing.

The cost, stated honestly

  • Shared dependency versions become a negotiation (two Angular majors on one page, or a shell that pins everyone).
  • Bundle size grows: duplicated vendor code across remotes.
  • Cross-app state and routing need a contract nobody owns.
  • Design consistency requires a real design system, funded and staffed.
  • A slow remote degrades a page it does not own; you now need loading and error boundaries per fragment.

When it genuinely pays

  • Four or more teams shipping to one screen surface on different cadences.
  • A legacy app being strangled page by page — the most defensible case by far.
  • Acquisitions: two stacks that must appear as one product next quarter.

Note that all three are org or history problems, not UI problems.

Delivery: the parts users actually feel

Enterprise frontends are rarely slow because of framework choice. They are slow because of bundle discipline, waterfalls and cache headers — all of which are architecture decisions, not tuning.

Security: the filter chain, then the method, then the row

Three layers, each catching what the one above cannot. Authorisation at only one of them is how data leaks between customers.

Layer 1 · the filter chain — who are you, broadly what may you reach

The layer most teams skip. A bug in a repository method that forgets WHERE customer_id = ? returns other customers' orders with a perfectly valid token.

Audit is a featureWho changed what, when, from where — with the trace id. Append-only, its own schema, read-only role for auditors. Retrofitting it after an incident or an audit finding is far more expensive than adding it in week two.

Layering — later wins, and the jar is the weakest

Feature flags belong here too

Flags decouple deploy from release: ship the new pricing engine dark, enable it for internal users, then 1%, then all. They are also your fastest rollback — faster than any redeploy.

Add an expiry date to every flag and a ticket to remove it. A four-year-old flag with three stale branches behind it is technical debt with a UI.

The pipeline

  1. Build + unit + arch tests — under 5 minutes or people stop watching.
  2. Integration — Testcontainers, module tests.
  3. Contract gates — OpenAPI breaking-change check, schema registry compatibility.
  4. Security — dependency scan (CVE), SAST, image scan, license check.

Sizing the runtime with arithmetic, not vibes

Connection pools and thread pools are where capacity planning meets reality. Both are answerable with one formula, and both are almost always set by copy-paste instead.

Little's law, applied to a connection pool

Concurrency needed = throughput × time each request holds a connection.

Target
600 orders/min = 10 orders/s
DB time
~40 ms of database work per order (not total request time)
Needed
10 × 0.04 = 0.4 connections average
Peak ×5
~2 connections; set the pool to 10–20 for headroom and bursts

The usual instinct — "set it to 100, to be safe" — makes things worse: PostgreSQL context-switches between 100 backends, latency rises, and each request holds its connection longer, which needs more connections. Pools are queues; oversizing moves the queue somewhere less observable.

Sanity check: total connections across all pods must stay well under the database's max_connections. 40 pods × 20 = 800 is how a healthy service takes down a shared cluster.

Virtual threads (Java 21+, on by default in Boot 4 when enabled)

spring.threads.virtual.enabled: true
  • Helps: IO-bound request handling — thousands of concurrent requests blocked on HTTP or JDBC, without a thread per request.
  • Does not help: CPU-bound work, or throughput limited by the database. It removes a thread ceiling; it does not create capacity downstream.
  • Watch: pooled resources are still the real limit — 10 000 virtual threads contending for 20 connections just queues elsewhere. And pinning on synchronized blocks is largely resolved in modern JDKs, but legacy libraries can still pin.

A modular monolith is not one server. It is one artifact deployed many times — and you can already scale, isolate and protect parts of it before extracting anything.

Production hygiene checklist

  • Liveness and readiness probes distinct; readiness fails while warming.
  • preStop sleep + graceful shutdown (server.shutdown=graceful) so in-flight requests finish.
  • Requests and limits set; -XX:MaxRAMPercentage=75 so the JVM respects the container.
  • PodDisruptionBudget, so a node drain does not take the whole service.
  • HPA on a metric that reflects load (RPS or queue depth), not only CPU.
  • Anti-affinity across zones; at least three replicas for anything customer-facing.
Sequencing a release with a migrationMigrate first (expand-only, backwards compatible), then roll the pods. Never run migrations from an init container on every pod — one pod runs them, as a Job, with a lock. Flyway takes the lock for you; the mistake is running the Job concurrently with itself.

Multi-region: three topologies, one hard question

The hard question is never compute — it is where writes happen. Everything else follows from that answer, and picking it is one of the few decisions that is genuinely irreversible.

Things that quietly break when you go multi-regionAuto-increment ids collide — switch to UUIDv7 or region-prefixed sequences. Kafka does not replicate itself; you need MirrorMaker and a consumer-offset story. Caches are per-region and diverge. Scheduled jobs fire twice. Every one of these is discovered after the decision, so raise them during it.

The conversation to have with the business

Not "what RTO do you want" — the answer is always zero. Instead: "one hour of downtime costs roughly £X in lost orders and £Y in remediation. Going from a 4-hour RTO to a 15-minute RTO costs £Z a year. Which do you want?"

Do not forget the dependenciesYour service failing over is pointless if the identity provider, the secret store or the payment gateway is single-region. DR is a property of the whole path, and the weakest link sets the real RTO.

Cost is an architectural constraint, not a finance problem

Architecture decisions set the cost curve years before anyone looks at the bill. Being able to express a design in cost per unit of business value is one of the clearest seniority signals there is.

Worked example: cost per 1,000 orders

Volume
1.2M orders/month, peak 40× on sale days
Compute
12 web + 6 worker pods, 2 vCPU / 4 GiB each
Database
primary + replica, provisioned for peak
Kafka
3 brokers, 7-day retention
Egress
the line everyone forgets until the invoice

Divide the monthly total by 1,200 and you have cost per 1,000 orders. Now every proposal has a comparable number: does this cache pay for itself? Does that extra service? Does multi-region?

It also exposes the real bill-driver, which in most enterprise systems is the database provisioned for peak and idle the rest of the month — not the application tier everyone spends time tuning.

Decisions with long cost tails

  • Provisioning for peak. A 40× sale peak sized statically means paying 40× all year. Autoscaling, queueing and load shedding are cost decisions as much as resilience ones.
  • Chatty synchronous calls. Each internal hop costs compute, network and latency budget on every request, forever.
  • Retention. Seven days of Kafka versus thirty is a straight multiple. So is log retention, which is frequently the largest observability line.
  • Cross-AZ and cross-region traffic. Priced per gigabyte, invisible in design reviews, and often the biggest surprise on a first multi-region bill.
  • One service per team, by policy. Each one carries a fixed floor of compute, monitoring and pipeline cost regardless of its traffic.
Capacity planning, minimallyCurrent peak throughput × expected growth × a safety factor, checked against the measured limit from a load test. Re-run quarterly. That is enough to avoid both the surprise outage and the 60%-idle cluster.

Data residency, PII and retention as architecture

In a regulated enterprise these constraints arrive as requirements, not preferences, and each one is far cheaper designed in than retrofitted. All four below are architectural, not operational.

Know where personal data is

A data inventory per module: which fields are personal, what the lawful basis is, how long it is kept, who it is shared with. Without it you cannot answer a regulator, a deletion request, or "does this new report leak anything".

Practical version: annotate the fields. @Pii(category = CONTACT) on the entity, and a test that fails if a @Pii field appears in a log format or an unencrypted export.

Residency shapes the topology

"EU customer data stays in the EU" decides your region strategy, your backup locations, your analytics pipeline and which SaaS vendors you may use. It also rules out a single global database — which is exactly the kind of constraint that must land in level 1 of the decision hierarchy, not level 6.

Deletion must be designed

A deletion request has to reach: the OLTP row, every read model, the search index, the cache, the warehouse, the backups, and the event log. The last two are the hard ones — an immutable event log and a right to erasure are in direct tension.

The usual resolution is crypto-shredding: store personal fields encrypted with a per-subject key, and delete the key. The events remain; their personal content becomes unreadable.

Minimise, then separate

  • Do not collect what you do not need; do not copy it into three services because it was convenient.
  • Pseudonymise in analytics — the warehouse rarely needs a real name.
  • Keep the PCI or PII surface in as few components as possible; that is one of the four legitimate reasons to extract a service.
  • Retention policies enforced by a job, not by a wiki page.
The one that catches everybodyLogs and heap dumps. A team designs beautiful field-level encryption, then logs the whole request body at DEBUG during an incident, and ships a copy to a log aggregator in another jurisdiction with 90-day retention. Privacy controls must cover the diagnostic path, because that is the path people use under pressure.

How to introduce them into an existing codebase

  1. Baseline, do not block. Record today's violations in a file; fail the build only on new ones.

  3. Add one per repeated review comment. If a reviewer catches the same mistake twice, that is a missing fitness function, not a missing reviewer.

The reframing worth carryingArchitecture is not the diagram — it is the set of properties you are defending. A property nobody measures is a preference. A property with a failing build behind it is a constraint, and constraints are what actually survive delivery pressure.
Good interview material"How do you stop a modular monolith degrading?" answered with three named, executable checks and a ratcheting strategy is a much stronger answer than "code reviews and discipline" — because the interviewer has watched discipline lose to a deadline before.

Governance that speeds teams up

Enterprise architecture functions fail in one of two ways: a review board everyone routes around, or no standards at all and forty incompatible services. The way out is to make the compliant path the easy path.

The bottleneck model

  • Every design goes to a weekly board; the queue is three weeks.
  • Standards are a 90-page document nobody has read.
  • Compliance is checked by a human, late, at a gate.
  • Architects are separate from delivery and have not run anything in production for years.

Result: teams either wait and resent it, or ship first and seek forgiveness. Both damage the architecture, and the board sees neither.

The paved road model

  • A service template that already has observability, security, CI, health checks and the error model wired in — a new service starts compliant.
  • Shared starters the platform team owns, so a change to the logging standard is a version bump.
  • Fitness functions enforce the rules in the pipeline, not in a meeting.
  • ADRs for anything off the road, reviewed asynchronously in the PR.
  • Architects embedded in delivery, writing some of the code.

Leaving the paved road stays possible — it just requires writing down why.

What a review is actually forNot approving designs — catching the level 1–4 decisions from the hierarchy slide, and spotting the same problem being solved separately by three teams. Review the decisions that are expensive to reverse; let teams own the rest. A board that debates library choices has no time left for the boundary that will cost a quarter.
Measure the function, not the artefactsLead time for a new service to reach production. Number of teams on the current template version. Percentage of services meeting the observability baseline. Those tell you whether governance is working. "Number of designs reviewed" tells you only how busy the board was.
Where this leaves the atlasEverything in this deck is one of three things: a decision (recorded in an ADR), a property (defended by a fitness function), or a default (encoded in the template). Anything that is none of the three is an opinion, and opinions do not survive contact with a delivery deadline.

Write the decision down while you still remember why

An ADR takes twenty minutes and answers the question every new engineer asks in month two: "why is it like this?" — which is otherwise answered by guessing, and then by an unnecessary rewrite.

ADR-014 · Keep the modular monolith; do not split payment yet

What makes an ADR useful

  • The context is dated and numeric. "6 engineers, 240 ms" ages visibly; "the team is small" does not.
  • The rejected options are listed, with why. Otherwise someone re-proposes them in a year.
  • Consequences include the negatives. An ADR with only upsides was written to win an argument, not to record one.
  • A revisit trigger. This is the line that turns a decision into a living one.
Where they liveIn the repo, under docs/adr/, in the PR that implements them. A decision record in a wiki nobody opens is a decision record nobody reads.
Worth recordingAnything in levels 1–4 of the decision hierarchy, any library that becomes load-bearing, any deliberate deviation from your own standard, and every "we tried X and it did not work".

What Spring Boot actually is

Boot is not a framework. It is three things layered on top of Spring Framework: an opinionated dependency set, a conditional configuration engine, and an embedded runtime. Knowing which layer a behaviour comes from is what makes problems diagnosable.

Boot adds no runtime model

There is no "Boot container". It is the same ApplicationContext Spring has always had — Boot just populates it for you and starts a server in main() instead of deploying a WAR.

Opinionated, not locked

Every auto-configured bean backs off the moment you declare your own. That is the single design rule the whole thing rests on — the next three slides are how it works.

Boot 4 finer modules

Boot 4 splits the framework and its own jars into smaller modules. Nothing changes conceptually, but it is the most common upgrade surprise — imports move.

Four ways to take control back

In escalating order of force. Reach for the weakest one that works — each step up moves you further from the defaults that Boot upgrades will keep maintaining for you.

1 · Set a property weakest, best

spring.jpa.open-in-view: false
spring.datasource.hikari.maximum-pool-size: 20
server.shutdown: graceful

Covers the large majority of real cases. Nothing to maintain, survives every upgrade.

2 · Declare your own bean

@Bean
ObjectMapper objectMapper() { ... }     // auto-config backs off

Works because of @ConditionalOnMissingBean. The trap: you now own all of Boot's defaults for that bean, which for ObjectMapper means you silently lose the module registrations Boot had configured.

3 · Customise instead of replace usually right

@Bean
Jackson2ObjectMapperBuilderCustomizer dates() {
    return b -> b.simpleDateFormat("yyyy-MM-dd");
}

Boot exposes a *Customizer for most things it builds. You change one setting and keep every default — almost always what you actually wanted in case 2.

4 · Exclude the auto-configuration

@SpringBootApplication(exclude = SecurityAutoConfiguration.class)

The blunt instrument. Legitimate for a batch app that must not start a web server, or when an in-house starter conflicts. Excluding SecurityAutoConfiguration to "make the 401 go away" is how unauthenticated endpoints reach production.

Shutdown order, and the one that bites

  1. SIGTERM arrives; ContextClosedEvent is published.
  2. Web connector stops accepting new requests; in-flight ones finish.
  3. SmartLifecycle.stop() runs in reverse phase order — Kafka listener containers stop here.
  4. Singletons destroyed in reverse dependency order; @PreDestroy then DisposableBean.

The bite: a Kafka consumer that has read a batch but not committed offsets when the JVM is killed will reprocess it on the next pod. That is normal and correct — and it is why every consumer must be idempotent.

Failure analysersWhen startup fails, Boot's FailureAnalyzers turn a 400-line stack trace into a readable block — "Web server failed to start. Port 8080 was already in use." You can register your own for in-house starters, and it is one of the highest-goodwill things a platform team can ship.
Don't do work in a constructorA bean constructor that calls a database or an HTTP endpoint makes startup depend on that system being up. Boot will fail to start, the pod will crash-loop, and a dependency's blip becomes your outage. Constructors wire; ApplicationReadyEvent works.

The bean lifecycle, and where your proxy appears

Nine steps between "definition" and "usable bean". The one worth memorising is step 7 — it is where @Transactional, @Cacheable, @Async and @PreAuthorize all physically come into existence.

Scopes

singleton (default, one per context) · prototype (new every injection; no destroy callback ever runs) · request / session (web, injected as a scoped proxy) · application. A prototype injected into a singleton is created once — use ObjectProvider if you need a fresh one per call.

Circular dependencies

Constructor injection on both sides cannot be resolved and fails at startup — correctly, since it is a design smell. Boot 2.6+ disables the field-injection workaround by default. Fix the design, or use @Lazy on one side only as a stopgap.

Proxy type

JDK dynamic proxy when the bean implements an interface, CGLIB subclass otherwise (Boot forces CGLIB by default). CGLIB cannot proxy final classes or final/private methods — the annotation is silently ignored, which is the worst failure mode there is.

One HTTP request, hop by hop

Where your code can intervene, and — more usefully — which stage an exception was thrown in, because that determines whether your @ControllerAdvice will ever see it.

Customising the security error bodyBecause the security chain sits outside the advice, you shape its responses with authenticationEntryPoint (401) and accessDeniedHandler (403) on the filter chain itself. Doing that is what makes every error in your API one consistent shape — see the ProblemDetail slide in the architecture deck.

The persistence context: open, dirty, flush, commit

Most JPA surprises — "I never called save() and it updated anyway", "my change vanished", "LazyInitializationException" — are this lifecycle, not a mapping problem.

Flush happens three times

Before a query that would read stale data, on flush(), and at commit. So an INSERT can appear far from the save() that caused it — which is why constraint-violation stack traces often point at an unrelated line.

Detached is where lazies die

After commit, a lazy association on a detached entity throws LazyInitializationException. Map to a DTO inside the transaction. open-in-view hides this by keeping the context open for the whole request — set it to false and fix the real cause.

Entity states

Transient (new, no id) → Managed (tracked) → Detached (context closed) → Removed. save() on a detached entity does a merge, which issues a SELECT first — a quiet source of double queries in bulk loops.

How to read a dependency problem

  1. mvn dependency:tree / gradle dependencies — find where the version came from.

@Bean

                       ItemReader<PaymentRecord> reader,
                       ItemProcessor<PaymentRecord, Reconciliation> processor,
                       ItemWriter<Reconciliation> writer) {

proxyBeanMethods — the one people never set

By default, @Configuration is CGLIB-proxied so that calling orderService() from another @Bean method returns the singleton rather than a new object. Convenient, but it costs a proxy per config class at startup.

If your @Bean methods never call each other — which is the norm when you take dependencies as method parameters — set proxyBeanMethods = false. Every Boot auto-configuration class does. Measurably faster startup, and it is what native-image compilation wants.

@Repository is not decorativeWithout it, a unique-constraint violation surfaces as a Hibernate ConstraintViolationException; with it, as Spring's DataIntegrityViolationException. Scanning@SpringBootApplication scans its own package and below. That is why the main class belongs at the root package — a class in a sibling package is silently never registered, and the symptom is a confusing "no qualifying bean" at startup.

@Enumerated(ORDINAL) is the default

And it stores 0, 1, 2. Insert a new enum constant in the middle a year later and every historical row silently changes meaning. Always STRING. This is the single most damaging JPA default.

@Column defaults you should set

equals/hashCode

Do not use Lombok's @Data on an entity — it generates them over all fields including lazy associations, which triggers loads and breaks Set semantics before the id is assigned. Use the business key, or the id with a stable hashCode.

UUID: the version matters

Random UUIDv4 primary keys fragment a B-tree index, because every insert lands in a random leaf page. On a large, insert-heavy table that costs real write throughput and index bloat.

Time-ordered UUIDs (v7) insert sequentially and largely remove the problem while keeping client-side generation. Hibernate 6.2+ supports them via @UuidGenerator(style = TIME).

@IdClass vs @EmbeddedId@IdClass repeats every key field on the entity and in a separate class, so the two drift. @EmbeddedId keeps one definition and gives you a type you can pass around. Use @IdClass only when mapping a legacy schema whose queries you cannot change.
Natural vs surrogateUse a surrogate key even when a natural one exists. Order numbers get reformatted, customer references get reissued, and "this will never change" is a statement about the current business process, not about the data.

Relationships: owning side, cascade, orphans

Four annotations, and about six ways each to get it subtly wrong. The owning side is the concept everything else hangs off: the side without mappedBy owns the foreign key, and only changes to the owning side are written.

The parent — order owns its lines
@Entity
class OrderJpaEntity {

    @OneToMany(mappedBy = "order",              // ← inverse side: line owns the FK
               cascade = CascadeType.ALL,       // persist/merge/remove flow to lines
               orphanRemoval = true,            // removing from the list DELETEs the row
               fetch = FetchType.LAZY)          // default for *ToMany — keep it
    private List<OrderLineEntity> lines = new ArrayList<>();

    // ALWAYS maintain both sides — the object graph is not self-healing
    void addLine(OrderLineEntity line) {
        lines.add(line);
        line.setOrder(this);
    }
    void removeLine(OrderLineEntity line) {
        lines.remove(line);
        line.setOrder(null);
    }

    @ManyToOne(fetch = FetchType.LAZY)          // EAGER is the default here — override it
    @JoinColumn(name = "customer_id", nullable = false)
    private CustomerEntity customer;

    @ManyToMany
    @JoinTable(name = "order_promotion",
               joinColumns = @JoinColumn(name = "order_id"),
               inverseJoinColumns = @JoinColumn(name = "promotion_id"))
    private Set<PromotionEntity> promotions = new HashSet<>();

Cascade the aggregate, never across aggregatesCascadeType.ALL from Order to OrderLine is right — lines have no life without the order. CascadeType.ALL from Order to Customer means deleting an order deletes the customer. REMOVE is the dangerous one; PERSIST and MERGE are usually what people actually wanted.
@ManyToOne is EAGER by defaultThe spec default, and it is wrong for almost every enterprise entity. Every @ManyToOne without fetch = LAZY adds a join or an extra select to every single load of that entity — and they compound: five eager parents on one entity means loading one row touches six tables.
@ManyToMany: prefer the join entityThe moment the relationship needs an attribute — when the promotion was applied, who applied it — @ManyToMany has to be rewritten as two @OneToManys to an explicit join entity. That request always comes. Also: use Set, not List, or Hibernate deletes and reinserts the whole join table on every change.

Resource server, client, and what JWT validation really does

@Bean JwtAuthenticationConverter jwtConverter() {
    var scopes = new JwtGrantedAuthoritiesConverter();
    scopes.setAuthorityPrefix("SCOPE_");
    var converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {

        List<String> roles = jwt.getClaimAsStringList("realm_roles");

What validation actually checks

  1. Signature against a key fetched from the JWKS endpoint (cached, refreshed on unknown kid).
  2. Issuer matches issuer-uri.
  3. Expiry and nbf, with a small clock skew allowance.
  4. Audience — only if you configure it.

Point 4 is the one that gets skipped. Without it, a valid token issued for the marketing API is accepted by the payments API, because both trust the same issuer. It is one line of YAML and it closes a real lateral-movement path.

JWTs cannot be revokedA stolen token is valid until it expires. So: keep access tokens short (5–15 minutes), keep refresh server-side (the BFF pattern), and for genuinely sensitive operations check a revocation list or use opaque tokens with introspection — which trades a network call per request for real revocation.
Opaque tokensspring.security.oauth2.resourceserver.opaquetoken introspects each token against the IdP. Slower and it couples request handling to IdP availability, but you get instant revocation and no claims leaking into a token anyone can decode. Many banks mandate it for external-facing APIs.

AOP: the mechanism behind every annotation that "just works"

@Transactional, @Cacheable, @PreAuthorize are all aspects Spring ships. Writing one yourself is the fastest way to stop treating them as magic — and occasionally the right answer for a genuine cross-cutting concern.

An audit aspect — one concern, applied everywhere, defined once
@Aspect
@Component
@Order(20)                                   // lower runs first; @Transactional is Ordered.LOWEST
class AuditAspect {

    // A named pointcut — reusable, and the place to put the expression
    @Pointcut("@annotation(com.retailco.shop.shared.Audited)")
    void audited() { }

    @Pointcut("within(com.retailco.shop..internal.app..*)")
    void inApplicationLayer() { }

    @Around("audited() && inApplicationLayer()")
    Object record(ProceedingJoinPoint pjp) throws Throwable {
        var sig  = (MethodSignature) pjp.getSignature();
        var user = SecurityContextHolder.getContext().getAuthentication().getName();
        long t0  = System.nanoTime();
        try {
            Object result = pjp.proceed();                       // ← call the real method
            audit.success(sig.getName(), user, pjp.getArgs(), Duration.ofNanos(System.nanoTime() - t0));
            return result;
        } catch (Throwable ex) {
            audit.failure(sig.getName(), user, ex);
            throw ex;                                            // NEVER swallow
        }
    }
}
The five advice types
@Before          // runs first; cannot change args or prevent the call
@AfterReturning  // on success; can read (not replace) the return value
@AfterThrowing   // on exception; for logging, not for handling
@After           // finally — always runs
@Around          // the only one that can skip the call, retry it, or change the result

@annotation(X)

Prefer an annotation over a wildcardexecution(* com.retailco..*Service.*(..)) silently stops matching the day someone renames a class or moves a package — and nothing fails, the aspect just stops running. @Audited on the method is visible in the code, greppable, and survives refactoring.

The audit case — the one real use of REQUIRES_NEW
@Service
class OrderService {
    @Transactional                                   // REQUIRED
    void place(PlaceOrderCommand cmd) {
        audit.record("place attempted", cmd);        // must survive a rollback
        var order = Order.place(...);                // may throw → outer rolls back
        orders.save(order);
    }
}

@Service

    @Transactional(propagation = REQUIRES_NEW)       // its own connection, its own commit
    void record(String what, Object payload) { ... }
}
REQUIRES_NEW in a loop is a self-inflicted deadlockIt takes a second connection while holding the first. A pool of 20 with a loop calling a REQUIRES_NEW method exhausts itself at 20 concurrent callers, each holding one connection and waiting for another that will never come free. The symptom is a hang, not an error.
rollback-only is contagiousIf an inner REQUIRED method throws and you catch the exception in the caller, the transaction is already marked rollback-only. Your caller finishes happily, then commit throws UnexpectedRollbackException — which looks like it came from nowhere. If you intend to recover from an inner failure, that inner call needs REQUIRES_NEW.

Isolation: three anomalies, four levels, and what your database really does

The JPA/JDBC constants are a portable abstraction over engines that behave quite differently. Knowing your engine's actual behaviour matters more than knowing the constant names.

LevelDirty readNon-repeatablePhantom
READ_UNCOMMITTEDpossiblepossiblepossible
READ_COMMITTEDnopossiblepossible
REPEATABLE_READnonopossible*
SERIALIZABLEnonono

* PostgreSQL's REPEATABLE READ is snapshot isolation and does prevent phantoms; MySQL InnoDB prevents them with gap locks. The standard permits them — the engines exceed it.

The three anomalies, in one sentence each

Dirty read
You read a row another transaction wrote but has not committed — and it then rolls back. You acted on data that never existed.
Non-repeatable read
You read the same row twice in one transaction and get different values, because someone committed between them.
Phantom read
You run the same WHERE twice and get a different set of rows, because someone inserted one that matches.
Setting it, on the rare occasion you need to
@Transactional(isolation = Isolation.REPEATABLE_READ, timeout = 5)
BalanceReport reconcile(AccountId id) { ... }
// timeout is in SECONDS and is worth setting on anything long-running —
// it bounds how long a transaction can hold its locks and its connection.
Practical guidanceStay on the database default — READ_COMMITTED on PostgreSQL and Oracle, REPEATABLE_READ on MySQL — and handle concurrency with optimistic locking instead. It is cheaper, it scales, and it fails loudly rather than blocking.
SERIALIZABLE is not free correctnessOn PostgreSQL it uses predicate locking and will abort transactions with a serialization failure under contention — so your code must be prepared to retry the whole unit of work. Turning it on without a retry strategy converts a correctness problem into an availability problem.
The interview follow-up"How would you prevent two customers buying the last item?" — the strong answer is not an isolation level. It is @Version optimistic locking with a bounded retry, plus a reservation with a TTL, as on the concurrency slide of the architecture deck.

@JsonIgnore is not security

It stops a field being serialised — it does not stop it being deserialised unless you also block that. A client can still POST {"role":"ADMIN"} into a field you thought was hidden. Use access = READ_ONLY, or better, a separate request DTO that simply has no such field.

Be a tolerant reader

Custom repository behaviour, without abandoning Spring Data

Three extension points, in the order you should reach for them. Most teams jump straight to injecting EntityManager into a service, which puts persistence code in the application layer.

1 · A fragment — custom code on one repository
interface OrderRepositoryCustom {
    List<OrderJpaEntity> search(OrderSearch filter, Pageable page);
}

class OrderRepositoryCustomImpl implements OrderRepositoryCustom {   // "Impl" suffix is required
    @PersistenceContext private EntityManager em;

    public List<OrderJpaEntity> search(OrderSearch f, Pageable page) {
        var cb = em.getCriteriaBuilder();
        var q  = cb.createQuery(OrderJpaEntity.class);
        var root = q.from(OrderJpaEntity.class);
        var predicates = new ArrayList<Predicate>();
        if (f.status() != null)     predicates.add(cb.equal(root.get("status"), f.status()));
        if (f.customerId() != null) predicates.add(cb.equal(root.get("customerId"), f.customerId()));
        q.where(cb.and(predicates.toArray(Predicate[]::new)));
        return em.createQuery(q)
                 .setFirstResult((int) page.getOffset())
                 .setMaxResults(page.getPageSize())
                 .getResultList();
    }
}

interface OrderJpaRepository extends JpaRepository<OrderJpaEntity, UUID>,
                                     OrderRepositoryCustom { }   // ← composed in
2 · Specifications — composable, for filter-heavy screens
class OrderSpecs {
    static Specification<OrderJpaEntity> hasStatus(OrderStatus s) {
        return (root, q, cb) -> s == null ? null : cb.equal(root.get("status"), s);
    }
    static Specification<OrderJpaEntity> placedAfter(Instant t) {
        return (root, q, cb) -> t == null ? null : cb.greaterThan(root.get("placedAt"), t);
    }
}
// null predicates are ignored, so optional filters compose cleanly:

class DateRangeValidator implements ConstraintValidator<ValidDateRange, OrderPayload> {
    public boolean isValid(OrderPayload p, ConstraintValidatorContext ctx) {
        if (p.placedAt() == null || p.deliverBy() == null) return true;   // let @NotNull say it
        boolean ok = p.deliverBy().isAfter(p.placedAt());
        if (!ok) {
            ctx.disableDefaultConstraintViolation();
            ctx.buildConstraintViolationWithTemplate(ctx.getDefaultConstraintMessageTemplate())
               .addPropertyNode("deliverBy")        // attach the error to a FIELD,
               .addConstraintViolation();           // so the UI can highlight it
        }
        return ok;
    }
}
Two details worth copyingReturn true on null and let @NotNull report it — otherwise one missing field produces two confusing errors. Attach the violation to a property node, or the frontend gets a class-level error it cannot map to an input.
Where groups stop being the answerThree or more groups on one record means you are modelling several operations in one type. Separate CreateOrderRequest and UpdateOrderRequest records are simpler, and each documents exactly one operation's contract.

The date and time rules that avoid incidents

  • Store and transmit instants in UTC. Instant or timestamptz, never a naive local timestamp.
  • Convert to a zone only for display, and carry the user's zone explicitly rather than relying on the server's default.
  • LocalDate for business dates — an invoice due date is a date, not an instant, and forcing it to one shifts it by a day for half your users.
  • Never Date or Calendar in new code; both are mutable and carry a hidden zone.
  • Set the JVM zone explicitly (-Duser.timezone=UTC) so behaviour does not change between your laptop and the cluster.
The enum parameter trapAn unknown enum value in a request parameter produces a 400 whose message names your Java class and its constants — an internal detail leaking to the client. Register a converter that maps unknown values to a domain exception and returns a ProblemDetail listing the accepted values instead.

In-process events: the decoupling that costs nothing

Spring's event publisher is the cheapest way to keep modules from importing each other. The subtleties are all about when the listener runs relative to your transaction.

Publishing and listening
@Service
class PlaceOrderUseCase {
    private final ApplicationEventPublisher events;

    @Transactional
    void place(PlaceOrderCommand cmd) {
        var order = Order.place(...);
        orders.save(order);
        events.publishEvent(new OrderPlaced(order.id(), order.total()));
    }
}

@Component
class Listeners {

    @EventListener                       // SYNCHRONOUS, same thread, same transaction.
    void immediate(OrderPlaced e) { }    // a throw here rolls back the publisher!

    @TransactionalEventListener(phase = AFTER_COMMIT)   // the one you almost always want
    void afterCommit(OrderPlaced e) { search.index(e); }

    @TransactionalEventListener(phase = AFTER_ROLLBACK)
    void afterRollback(OrderPlaced e) { metrics.counter("order.failed").increment(); }

    @EventListener(condition = "#event.total.amount > 1000")   // SpEL filter
    @Async("eventExecutor")                                    // own thread + own tx
    void highValue(OrderPlaced event) { fraud.review(event); }

    @EventListener @Order(1)             // ordering between listeners of the same event
    void first(OrderPlaced e) { }
}
The AFTER_COMMIT trapBy default an AFTER_COMMIT listener runs outside any transaction — so a save() inside it silently does nothing on some setups, or fails with "no transaction in progress". If the listener writes, it needs @Transactional(propagation = REQUIRES_NEW), which is exactly what Spring Modulith's @ApplicationModuleListener bundles for you.
Plain events are not durableA JVM crash between commit and listener loses the event with no trace. For anything that must not be lost — an outbound integration, a customer email, a ledger entry — use the event publication registry or a transactional outbox, as on the architecture deck's events slide.
Generic events@EventListener void on(Created<Order> e) works, but type erasure means Spring needs help: have the event implement ResolvableTypeProvider, or use distinct event types. Distinct types are usually clearer anyway.

Health checks that mean something

Boot auto-registers indicators for every datasource, Redis, Kafka and disk. The ones you write yourself are for dependencies Boot cannot know about — and they need timeouts, or the health check becomes the outage.

A custom indicator — with the two things people forget
@Component("paymentGateway")
class PaymentGatewayHealth implements HealthIndicator {

    private final PaymentGatewayClient client;
    private final CircuitBreaker breaker;

    @Override public Health health() {
        if (breaker.getState() == OPEN) {
            return Health.status("DEGRADED")            // custom status, not DOWN
                    .withDetail("reason", "circuit open")
                    .build();

        try {
            var latency = client.ping(Duration.ofMillis(500));   // 1. ALWAYS bound it
            return Health.up().withDetail("latencyMs", latency.toMillis()).build();
        } catch (Exception ex) {

            //                                       2. class name, not the message —
            //                                          messages leak hostnames and SQL
        }
    }
}

The question every indicator must answer

"If this is DOWN, should Kubernetes stop sending traffic to this pod?"

For the primary database: yes. For the payment gateway: no — every pod would fail readiness simultaneously, the whole service would leave the load balancer, and customers would get a connection error instead of "payments are temporarily unavailable, your basket is saved".

Third-party dependencies belong on a dashboard and in an alert, not in readiness.

Health checks are called constantlyEvery few seconds, by every pod, plus your load balancer and your monitoring. Micrometer: four instrument types, one cardinality rule

Boot instruments HTTP, JDBC, Hikari, Kafka and the JVM automatically. What you add is business measurement — and the failure mode of adding it carelessly is taking down your monitoring stack.

The instruments, and when each is right
@Service
class OrderMetrics {
    private final Counter placed;
    private final Timer   checkout;
    private final DistributionSummary basketSize;

    OrderMetrics(MeterRegistry registry, OrderRepository orders) {
        // COUNTER — monotonically increasing events
        placed = Counter.builder("orders.placed")
                .description("Orders successfully placed")
                .tag("channel", "web")
                .register(registry);

        // TIMER — duration + count + percentiles
        checkout = Timer.builder("orders.checkout.duration")
                .publishPercentiles(0.5, 0.95, 0.99)
                .publishPercentileHistogram()      // enables server-side aggregation
                .register(registry);

        // GAUGE — a value sampled now. Holds a weak reference: keep the object alive.
        Gauge.builder("orders.pending", orders, OrderRepository::countPending)
                .register(registry);

        // DISTRIBUTION SUMMARY — non-time distributions
        basketSize = DistributionSummary.builder("orders.basket.lines").register(registry);
    }

    void recordPlaced(Order o, Duration took) {
        placed.increment();
        checkout.record(took);
        basketSize.record(o.lines().size());
    }
}

Cardinality is the way monitoring diesEvery distinct combination of tag values is a separate time series. A tag of orderId on a service doing 1.2M orders a month creates 1.2M series a month — Prometheus falls over, and the bill if you are on a hosted product is memorable. What to log, what never to log

Logging discipline is a security control as much as an operational one. In a regulated environment the second column below is audit findings, not style preferences.

Log this

  • Every inbound request once: method, templated path, status, duration, trace id.
  • Every outbound call: target, status, duration, retry count.
  • State transitions: order PLACED → PAID, with the ids involved.
  • Every decision a human may later query: why a payment was declined, why a rule rejected an order.
  • Errors, once, at the boundary that handles them — with the stack trace.
  • Startup config summary: which profile, which endpoints, which feature flags.

Never log this

  • Passwords, tokens, API keys, Authorization headers — including in a "full request dump".
  • Full card numbers (PCI), CVV ever, full bank account numbers.
  • Personal data beyond what the purpose needs — names, addresses, emails in bulk.
  • Whole request or response bodies in production. Log field names, not values.
  • Anything at DEBUG that you would not accept at INFO — someone will raise the level during an incident.

JVM memory in a container: heap is not the whole story

The most common container OOM kill is not a heap problem — the heap is fine, and the process is killed for memory the JVM never counted as heap.

Set the percentage, not the megabytes

-XX:MaxRAMPercentage=75 adapts when someone changes the container limit. A hardcoded -Xmx1500m in a container later resized to 1 GiB is an instant crash loop.

Leave real headroom

25% of the limit for non-heap is a reasonable starting point; services with heavy Netty or Kafka use need more. Set container requests == limits for predictable scheduling.

Virtual threads change the maths

Platform threads cost ~1 MB of stack each, so 400 of them is 400 MB. Virtual threads are heap-allocated and tiny — which removes this particular ceiling but moves the pressure onto the heap.

Choosing and reading a garbage collector

Modern collectors are good enough that tuning flags is rarely the answer — choosing the right one and then fixing allocation almost always is.

The container CPU trapThe JVM picks its collector and thread-pool sizes from available processors. A limit of 500m CPU makes availableProcessors() report 1, which selects SerialGC and sizes the common ForkJoinPool to one thread. Read the symptom before touching a flag

Frequent young GCs
Normal and cheap. High allocation rate — look only if pauses hurt.
Old gen grows after full GC
A leak. Heap dump, not a flag.
Long full GCs
Heap too small for the live set, or a leak. Raising -Xmx buys time, not a fix.
Humongous allocations (G1)
Objects > half a region — usually a huge list or byte array. Page the query instead.
GC fine, latency bad
Not a GC problem. Go to the profiling slide.
The fix is usually allocation, not the collectorAn endpoint loading 50,000 entities to return 20 rows is a GC problem caused by a query problem. Paginate, project, stream — and the GC graph flattens without a single flag. Change collectors only once the allocation rate is defensible.

The leaks that actually happen in Spring apps

Unbounded cache
A ConcurrentHashMap used as a cache with no eviction. Use Caffeine with a maximumSize — always.
ThreadLocal on a pooled thread
Set and never removed. The thread lives forever, so the value does too. Always remove() in a finally.
Listeners never unregistered
Anything registering itself at startup that outlives its owner.
Session-scoped state
Large objects in an HTTP session with a long timeout, times concurrent users.
Accumulating collections
A List field on a singleton that only ever grows — an audit buffer, a "recent items" list.
Not a leak
A rising heap that drops after a full GC is just G1 being lazy. Only growth after a full GC counts.

A load test that tells you something true

Most load tests measure the test harness, or a cold JVM, or a database with no data in it. Four things separate a number you can plan with from one you cannot.

The four that matter

  1. Realistic data volume. A query against 1,000 rows tells you nothing about 40 million. Seed production-shaped data — same distribution, same skew, same index sizes.
  2. Realistic mix. Hammering one endpoint measures that endpoint. Real traffic is ~80% reads, ~15% writes, and one nightly batch competing for the same connections.
  3. Warm up, then measure. The first 30–60 seconds are JIT compilation and cold caches. Discard them or you are benchmarking the interpreter.
  4. Model think time. A closed-loop test with zero delay creates a pattern no user produces and hides queueing effects. Use an open model with an arrival rate.

Four tests, four questions

Load
Does it meet the SLO at expected peak?
Stress
Where does it break, and how — shedding load gracefully, or falling over?
Soak
8–24 hours. Leaks, connection exhaustion and log-disk growth only appear here.
Spike
0 → peak in 30 seconds. Does autoscaling react in time, or does the cold pool starve?
Watch the dependencies, not just your serviceThe bottleneck is almost never your application tier. Instrument the database (connections, slow queries, lock waits, CPU), cache hit ratio, and consumer lag during the run. A test that only reports response times tells you "it got slow" and nothing about why.
One number worth derivingState the cost per 1,000 orders at the achieved throughput. It converts a technical result into the language the people funding capacity use, and it is the number that justifies a caching project.
Where it belongsA nightly load test on a scaled-down environment, tracked over time, catches a regression the week it is introduced. A one-off test two weeks before go-live describes a system that no longer exists by launch.

Production readiness, as a checklist

What a Spring Boot service should have before it takes customer traffic. Useful as a go-live gate, and as the outline of an answer when an interviewer asks what "production ready" means to you.

Config & build

  • One artifact promoted across environments; no rebuild per environment.
  • No secrets in the image, the repo or application.yaml.
  • @ConfigurationProperties with validation — bad config fails the boot.
  • Dependency, image and license scans in the pipeline.
  • Version and git commit exposed at /info.

Runtime

  • MaxRAMPercentage set; requests == limits; at least 2 CPUs.
  • Graceful shutdown plus a preStop delay.
  • Liveness and readiness distinct; no third-party dependency in liveness.
  • Connection pool sized from throughput × hold time, checked against the cluster total.
  • Timeouts on every outbound client. No exceptions.

Observability

  • Trace id end to end, including across Kafka.
  • Structured JSON logs; MDC cleared on every thread.
  • RED metrics per endpoint plus the handful of business counters.
  • SLOs with burn-rate alerts; a runbook per alert.
  • Alerts on consumer lag and dead-letter depth.

Resilience & data

  • Idempotency keys on every mutating public endpoint.
  • Retries only where idempotent; breakers with a defined fallback.
  • Outbox for events that must not be lost; consumers idempotent with a DLT.
  • Expand/contract migrations; a rollback rehearsed, not assumed.
  • Backups restored at least once — an untested backup is a hope.
The two nobody does until it hurtsRestore a backup. Most teams have never tried, and discover at the worst moment that the restore takes nine hours or silently omits a schema. Kill a pod in production, deliberately, during business hours. If that is frightening, the graceful-shutdown and retry story is not real yet — and you would rather find out on a Tuesday afternoon than at 2am.

Interview prep · backend / architecture rounds

What the architecture round is actually testing

Not whether you know the patterns — the interviewer assumes you do. They are testing whether you reason about trade-offs under constraints, and whether you have operated what you designed. Most candidates who fail know more patterns than the ones who pass.

What earns points

  • Asking about scale, consistency needs and team size before proposing anything.
  • Naming the trade-off out loud: "this costs us X, and I'd accept that because Y".
  • Volunteering the failure mode of your own design before being asked.
  • Distinguishing what you have run in production from what you have read about.
  • Changing your answer when given new constraints — that reads as engineering, not weakness.

What loses points

  • Jumping to microservices and Kafka in the first sixty seconds.
  • Listing technologies instead of describing behaviour.
  • Claiming "exactly-once" or "no downtime" without qualifying it.
  • No numbers anywhere — no latency, no volume, no pool size.
  • Defending the first idea after the interviewer adds a constraint that breaks it.
The line that reframes a whole interview"Before I design this — what's the read/write ratio, and how stale can the data be for each screen?" Almost nobody asks it, and it is the question that determines most of the architecture.

Six steps for any design question

Say the step names out loud as you go. It makes your reasoning legible and stops you spiralling on one part.

1 · Clarify (3–5 min)

Functional scope — what is explicitly out. Scale: DAU, peak RPS, data volume, growth. Consistency needs per operation. Latency budget. Team size and timeline. Write the numbers where you both can see them.

2 · Contract first

The 4–6 API operations, and the core entities with their key fields. This anchors everything after it and costs two minutes.

3 · Boxes and arrows

Client → edge → API → services/modules → data. Say which arrows are synchronous and which are events, and why, as you draw them.

4 · Data model and storage

Which store for which data and why. Partition/shard key. Indexes for the top three queries. Where the read model is, if any.

5 · Scale the bottleneck

Name the bottleneck first — usually the database or a single hot partition — then fix that: caching, read replicas, async offload, partitioning. Do not scale everything.

6 · Failure and operations

What happens when each dependency is down. Idempotency and retries. Monitoring and the SLO. This is the section most candidates run out of time for — budget for it deliberately.

Time disciplineIn a 45-minute round: 5 clarify, 5 contract, 10 high-level, 10 deep-dive on whatever they steer you to, 10 failure and scale, 5 spare. If you are still on step 3 at minute 25, summarise and move.

Architecture and modularity

Q1

Monolith or microservices for a new enterprise product?

30-second answerModular monolith first, with genuinely enforced boundaries, and extract services on named evidence. Microservices buy independent deployment and scaling, and charge you distributed transactions, network failure handling and an operations platform. Early on, the domain boundaries are still wrong — and fixing a wrong boundary inside one deployable is a refactor, while fixing it across a network is a quarter.

Go deeper: Name the four extraction triggers — divergent scaling, divergent SLA, a team blocked by the release train, and a compliance boundary you want physically separate. Then say what "enforced" means concretely: ArchUnit slice rules, Spring Modulith verification, a database role per module so a cross-schema join fails with a permission error. If they push ("we're 200 engineers"), agree immediately — at that size the coordination cost inverts the answer, and saying so shows the reasoning was about constraints, not preference.

Q2

How do you decide where a module boundary goes?

30-second answerBy language and by change. A boundary belongs where the meaning of a word changes — "order" means something different to fulfilment than to finance — and where things change together for the same business reason. High cohesion inside, low coupling across, and one owning team.

Go deeper: Mention event storming as the practical technique: get domain experts in a room, map the events in time order, and the clusters that emerge are candidate contexts. Test a proposed boundary by asking whether a typical change touches one module or four. Then the honest part — you will get some wrong, which is precisely the argument for keeping them cheap to move.

Q3

What actually stops a modular monolith from becoming a big ball of mud?

30-second answerExecutable rules, not documentation. Three of them: package structure where only api is importable, ArchUnit/Modulith tests failing the build on a violation, and a database role per module so the data boundary is enforced by PostgreSQL rather than by reviewers.

Go deeper: Add the human layer — one owning team per module via CODEOWNERS, and a rule that any boundary exception needs an ADR. Then the failure story: teams that write the rules in a wiki see drift inside a quarter, because a rule that is not a build failure is a suggestion under deadline pressure.

Q4

Walk me through extracting one module into a service.

30-second answerData first, then process. Confirm no other module touches its tables; split the schema and run that way for weeks. Then keep the interface and swap the in-process implementation for an HTTP adapter behind a feature flag, with the old path still there. Cut traffic over, watch, then delete the module. Nothing in the calling code changes at any point.

Go deeper: Call out what changes the moment it is remote: the call can now time out, so callers need timeouts, retries with idempotency, and a fallback; the transaction that used to span both is now a saga with compensation; and you have lost the ability to join. Say explicitly that extracting a module whose tables are still shared produces a distributed monolith — all the latency, none of the autonomy.

Q5

Layered, hexagonal, or clean architecture — which and why?

30-second answerThey are the same idea at different volumes: dependencies point inward, the domain depends on nothing. I use ports and adapters inside each module — domain and application at the core, web/JPA/Kafka as adapters — and I apply it proportionally: full purity where the business rules are, plain JPA-to-controller for CRUD lookup tables.

Go deeper: The concrete payoff is testing — domain tests with no Spring context run in microseconds, so people actually write them. The concrete cost is a mapping layer. Volunteering that you would skip it for a catalog-admin screen is what separates someone who has applied this from someone who has read about it; dogmatic uniform layering is why teams abandon the approach entirely.

Q6

Where do business rules go?

30-second answerOn the aggregate that owns the data the rule constrains. The application service only orchestrates — load, call the domain, save, publish. If a rule sits in a service, it gets duplicated the second a second entry point appears.

Go deeper: Distinguish three kinds: shape validation (Bean Validation on the request record), invariants (enforced in the aggregate's constructor and state-transition methods, so an invalid object cannot exist), and cross-aggregate policies (a domain service, or a saga when it spans modules). The anaemic-domain anti-pattern is worth naming explicitly: entities with only getters and a 900-line service class.

Q7

How do you handle a shared concept like Customer across modules?

30-second answerEach context keeps its own view of it. Ordering needs a customer id and a shipping address; marketing needs preferences; finance needs billing terms. One canonical Customer class shared by everyone becomes a god object that no team can change. Reference across contexts by id, and duplicate the few fields you need.

Go deeper: This is where "duplication is not always a smell" belongs — the inventory module storing a product name is a context's own view, not a normalisation failure. Mention keeping the copies fresh via events, and that the alternative, a foreign key across contexts, is the thing that makes extraction impossible later.

Q8

Design a system where one module needs 20× the capacity of the rest.

30-second answerFirst, check whether you need a new service at all — the same artifact deployed with different profiles gives you independent scaling of web, worker and batch today. If the hot module is genuinely CPU- or memory-shaped differently, that is one of the four extraction triggers, so extract it, with its own data.

Go deeper: The profile trick is a strong signal you have operated this: one jar, three deployments, Kafka listeners gated by @Profile("worker"), no ingress on the workers. It gets you most of the isolation benefit with none of the distribution cost, and it is reversible in an afternoon.

Data and consistency

Q9

How do you keep data consistent across services without 2PC?

30-second answerSaga: a sequence of local transactions, each with a compensating action. Reserve stock, authorise payment, capture, ship — and if authorisation fails, release the stock. Compensation is not a rollback; it is a new business fact with its own audit trail. Order the irreversible steps last.

Go deeper: Contrast orchestration (a saga state machine you can query — "where is order 88421 stuck") with choreography (lower coupling, but the flow exists only in traces). For enterprise work, orchestration is the default past three steps. Then the operational requirements: persist saga state, make every step idempotent, and put a timeout on every step — a saga without timeouts produces orders sitting in AWAITING_PAYMENT for eleven days.

Q10

How do you write to the database and publish to Kafka atomically?

30-second answerYou don't — you use the transactional outbox. Write the event into an outbox table in the same local transaction as the data, and let a separate relay publish it and mark it sent. Crash anywhere and the row is still there, so it gets published again. That gives at-least-once, which is why every consumer is idempotent.

Go deeper: Name both failure modes of the naive approach: send-then-commit publishes an event for an order that rolls back; commit-then-send loses the event on a crash. Then the two relay options — a polling relay (FOR UPDATE SKIP LOCKED, simple, ~200 ms–1 s latency) versus Debezium CDC reading the WAL (millisecond latency, ordering from the log, costs a Connect cluster). Bonus: Spring Modulith's event publication registry is exactly this pattern, built in.

Q11

Two customers order the last item at the same moment. What happens?

30-second answerOptimistic locking with a version column. The update is WHERE sku = ? AND version = ?; the loser gets zero rows updated, an OptimisticLockingFailureException, and a bounded retry on fresh state — where it sees stock is zero and gets a clean "out of stock". No locks held across the request.

Go deeper: Explain why not pessimistic: SELECT FOR UPDATE is correct but serialises the hot row, which is fatal for a flash-sale SKU while being fine for a rarely-contended ledger. Mention the reservation model for real e-commerce — reserve with a TTL at checkout, confirm on payment, release on expiry — so you are not holding stock indefinitely for abandoned carts.

Q12

Can you guarantee exactly-once processing?

30-second answerNot over a network — you get at-most-once or at-least-once. What you can achieve is exactly-once effects: at-least-once delivery into an idempotent handler. Deduplicate on a business key, not on an offset.

Go deeper: Show the concrete handler: check whether a reservation already exists for that orderId, and if so acknowledge and return — a duplicate is not an error. Mention Kafka's transactional producer and read_committed as exactly-once within Kafka, and be clear that it does not extend to your database or a third-party API. Getting this distinction right is one of the strongest signals in a mid-to-senior interview.

Q13

How do you change a database schema with zero downtime?

30-second answerExpand and contract, across three releases. Add the new nullable column; dual-write and backfill in batches; switch reads; then drop the old column once no running version references it. During a rolling deploy old and new pods share one schema, so every migration must be compatible with the previous release.

Go deeper: Add the operational details — CREATE INDEX CONCURRENTLY on large tables, a lock_timeout so blocked DDL fails fast instead of queueing every query behind it, batched backfills, and migrations as immutable append-only files with Flyway validation on. Answer the rollback question before they ask it: you roll forward, and expand/contract is what makes the deployment rollback-safe even though the schema is not.

Q14

The order history page is slow. Walk me through fixing it.

30-second answerMeasure first — is it the database, the serialization, or the network? Then in order of cost: check for an N+1, add the covering index, replace offset pagination with a keyset cursor, project a denormalised read model maintained by events, and only then cache. Each step is cheaper than the next one.

Go deeper: Be concrete: 501 queries in the trace means N+1 — fix with @EntityGraph and assert the query count in a test so it cannot come back. OFFSET 100000 makes Postgres walk 100k rows — switch to WHERE (placed_at, id) < (?, ?) ORDER BY ... LIMIT 20. Caching last is deliberate: caching a bad query hides the problem until the cache misses at peak.

Q15

When would you use CQRS or event sourcing?

30-second answerCQRS-lite — a separate read path with projections instead of aggregates — almost always pays for itself, and costs one class. Full event sourcing is justified when the audit trail is the requirement (ledgers, regulated workflows) or when you genuinely need to reconstruct past state. Otherwise it buys a large amount of complexity for a temporal query nobody asked for.

Go deeper: Name the real costs of event sourcing: schema evolution of events you can never delete, snapshotting for long streams, the difficulty of ad-hoc queries, and a steep onboarding curve for every new engineer. Then the middle ground you would actually ship: normal state storage plus a durable domain-event log, which gives most of the audit value at a fraction of the cost.

Integration, messaging and resilience

Q16

A downstream service is slow. How do you stop it taking you down?

30-second answerFour layers in order. Timeout first — without a bounded call, nothing else can work. Then bounded retries with exponential backoff and jitter, only on idempotent operations. Then a circuit breaker so you stop calling a dead system. Then a bulkhead capping concurrency to that dependency, so it cannot consume every thread you have.

Go deeper: Explain why jitter matters — without it every client retries at the same millisecond and keeps the recovering dependency down. Explain retry amplification: three services each retrying three times turns one request into twenty-seven, exactly when the dependency is struggling. And say that every breaker state needs a defined fallback: a cached value, a queued write, or an honest 503 with Retry-After.

Q17

Synchronous call or event — how do you choose?

30-second answerOne question: if this step fails, should the user's action fail? Yes — synchronous, in the same transaction (taking payment). No — publish an event (confirmation email, loyalty points, search reindex). That single rule keeps checkout availability high while five downstream systems average far less.

Go deeper: Name the cost of the event path honestly — the order now exists in a state where payment has not happened yet, and both the domain model and the UI have to admit that state. Then availability multiplication: five synchronous dependencies at 99.9% each give you 99.5% before you have written a line of your own code.

Q18

How do you guarantee event ordering?

30-second answerOnly within a partition, and only by keying on the entity. All events for one order go to one partition because the key is the order id, so they arrive in order for that order. There is no global ordering across partitions, and you should not design as if there were.

Go deeper: Mention the consequences: partition count caps consumer parallelism, and a hot key creates a hot partition. If a consumer needs to tolerate out-of-order arrival anyway, carry a version or timestamp in the event and ignore anything older than what you have already applied — which is more robust than depending on ordering at all.

Q19

A consumer hits a message it can never process. What happens?

30-second answerBounded retries — three, with backoff — then publish to a dead-letter topic, alert, and move on. Infinite retry blocks the partition and everything behind it. Non-retryable exceptions like deserialization failures skip the retries entirely, because a poison pill never gets better.

Go deeper: Add the two operational pieces: a documented replay path from the DLT after the bug is fixed, and alerting on DLT depth greater than zero plus consumer lag — those two are your real SLIs for the async side, not CPU. Also mention manual offset commit: the default auto-commit acknowledges on a timer regardless of whether your handler succeeded.

Q20

How do you make an API safe to retry?

30-second answerAn Idempotency-Key header the client generates per logical operation. Insert it with a unique constraint before doing the work; on a duplicate key with the same request fingerprint, return the stored response; with a different fingerprint, return 422 because the client reused a key for a different request.

Go deeper: Mention storing the response body and status against the key with a TTL, so the retry gets an identical answer rather than a second order. Then the layering rule: no retry anywhere — client, gateway, or @Retryable — without idempotency. Gateways should retry GETs only. Retrying a POST without a key is how customers get charged twice.

Q21

How do you debug a request that crossed four components and a queue?

30-second answerOne trace id, propagated end to end — including through the Kafka message headers, which is the hop teams forget. Every log line carries it, every span carries it, and the customer's error page shows it. Support quotes the id, you get the whole journey in one query.

Go deeper: In Spring terms: Micrometer Tracing with W3C traceparent, OTLP export, and observation-enabled: true on both the Kafka template and the listener container. Mention structured JSON logs with the correlation pattern, sampling at 10% with errors always sampled, and the cardinality rule — never tag a metric with an order id, that belongs in logs and traces.

Spring and Java specifics

Q22

Why doesn't @Transactional work when I call the method from the same class?

30-second answerBecause it is implemented with a proxy. An internal this.method() call never goes through the proxy, so the advice never runs. Fix by moving the method to another bean, or by using TransactionTemplate explicitly. Spring 7 now logs a warning for this — for years it failed silently.

Go deeper: Same mechanism explains why @Cacheable, @Async and @Retryable also do nothing on self-invocation, and why final or private methods cannot be advised with CGLIB proxies. This question is really testing whether you know Spring is a proxy container rather than magic.

Q23

What rolls a Spring transaction back?

30-second answerBy default, RuntimeException and Error — not checked exceptions. So a checked PaymentDeclinedException commits the half-written order. Either set rollbackFor = Exception.class, or adopt the convention that all domain exceptions are unchecked, which is what I would do.

Go deeper: Cover propagation while you are there: REQUIRED joins the caller's transaction (the default), REQUIRES_NEW suspends it and takes a second connection from the pool — nest that in a loop and you deadlock your own pool. Legitimate uses are audit rows that must survive a rollback, and post-commit event listeners.

Q24

What is an N+1 and how would you catch it before production?

30-second answerOne query for a list, then one per row for a lazy association — 501 queries for 500 orders. Fix with @EntityGraph or join fetch. Catch it by asserting the query count on the hot endpoints in an integration test, so a regression six months later fails the build rather than a dashboard.

Go deeper: Mention open-in-view: false — the default is true and it hides N+1s behind a request-scoped session until production load exposes them. Then the adjacent traps: two join fetches on collections give a cartesian explosion, and pagination combined with join fetch makes Hibernate log "applying in memory" and then run out of heap.

Q25

How do you size a connection pool?

30-second answerLittle's law: concurrency = throughput × hold time. Ten orders a second, 40 ms of database work each, is 0.4 connections on average; times five for peak is about two, so set it to 10–20 for headroom. Then check the total across all pods against the database's max_connections.

Go deeper: Explain why bigger is worse: PostgreSQL context-switches between hundreds of backends, latency rises, each request holds its connection longer, which needs more connections. Pools are queues, and oversizing just moves the queue somewhere less observable. Forty pods at 20 each is 800 connections, which is how a healthy service takes down a shared cluster.

Q26

Do virtual threads change your architecture?

30-second answerThey remove the thread-per-request ceiling for IO-bound work, so you can handle far more concurrent blocked requests without going reactive. They do not create capacity downstream — if your throughput is limited by the database or a third party, ten thousand virtual threads queue on twenty connections instead of on a thread pool.

Go deeper: In Boot it is spring.threads.virtual.enabled: true. Note that pinning on synchronized blocks is largely resolved in modern JDKs but legacy libraries can still pin, and that the honest framing is: virtual threads make the simple blocking programming model scale, which removes most of the reason to adopt WebFlux.

Q27

How do you test a Spring Boot application properly?

30-second answerMatch the test to the layer. Domain rules in plain JUnit with no context, microseconds. Slices — @WebMvcTest, @DataJpaTest — for serialization, validation and SQL. Testcontainers with the real PostgreSQL and Kafka for integration. A handful of end-to-end journeys, no more. Plus architecture tests, which are tests like any other.

Go deeper: Say explicitly that H2 is not your database — it passes SQL that production rejects and skips the constraints and locking behaviour that matter. Mention @ServiceConnection and container reuse to keep the suite fast, and that three reliable E2E tests beat forty flaky ones, because a suite people re-run "because it's probably flaky" has stopped being a gate.

Q28

What's new in Spring Boot 4 that matters architecturally?

30-second answerFour things I would actually use: first-class API versioning on server and client; declarative HTTP interface clients via @ImportHttpServices; resilience in the core framework — @Retryable and @ConcurrencyLimit without an extra library; and null safety through JSpecify with @NullMarked packages. Java 17 is still the baseline, 25 recommended.

Go deeper: Add the migration realities: the framework is split into finer modules, which is the most common upgrade surprise; Jackson 3 changes defaults (ISO-8601 dates, unchecked exceptions); and Spring Data AOT generates repository queries at build time for a meaningful startup improvement. 4.1 added gRPC support and SSRF mitigation on the HTTP clients. Knowing the version cadence — a major or minor every six months — is a cheap credibility signal.

API design and frontend

Q29

How do you version an API?

30-second answerAvoid needing to. Additive changes only, never repurpose a field, and tolerant readers on every consumer. When a breaking change is unavoidable, expand and contract across releases — and if you must cut a version, pick one scheme across the whole organisation rather than three.

Go deeper: Compare path versioning (obvious in logs, gateways and curl — what most enterprises pick) with header or media-type versioning (cleaner REST, and what Spring 7 optimises for with @GetMapping(version = "2")). Then the part people forget: deprecation needs teeth — Deprecation and Sunset headers plus a metric tagged by client and version, or v1 lives forever.

Q30

Where should the access token live in a browser app?

30-second answerNot in the browser. Use the BFF pattern: the browser holds an httpOnly, SameSite session cookie, the BFF holds the tokens and attaches the bearer server-side. Token theft via injected script leaves the threat model entirely. The cost is a stateful hop and CSRF defence.

Go deeper: Both options use OIDC authorization code with PKCE — the only difference is storage, which is why retrofitting the BFF later is an interceptor change rather than a re-architecture. localStorage is defensible for internal tools with low-value data; say so, because the interviewer is checking whether you weigh risk or recite rules.

Q31

How do you keep the frontend and backend contracts in sync?

30-second answerGenerate, never hand-write. The build publishes an OpenAPI document from the controllers; the frontend regenerates its typed client from it on every build, and the generated folder is gitignored so it cannot drift. Renaming a field in Java then breaks the frontend compile in CI, before merge.

Go deeper: Add the breaking-change gate — oasdiff against main turns "is this breaking?" from a judgement call into a build result. Mention that the async side needs the same treatment: Avro or JSON schemas in a registry with BACKWARD compatibility, so an incompatible producer is rejected at deploy time.

Q32

Would you use micro-frontends?

30-second answerUsually no. They solve an organisational problem — independent deployment by separate teams — at a real technical cost in shared dependencies, bundle size and cross-app state. The default is one app with enforced feature boundaries and lazy routes, which is the frontend's modular monolith.

Go deeper: Name the three cases where they genuinely pay: four or more teams on one screen surface, strangling a legacy app page by page (the most defensible), and post-acquisition integration. All three are org or history problems, not UI problems — which is the point worth making.

Two whiteboard scripts

Rehearse these out loud. Not to recite — to have the shape of the answer available so your attention goes to the interviewer's constraints instead of to structure.

W1

"Design an order management system for a large retailer"

Clarify (say these out loud): Order volume and peak — say 1.2M/month, peaking at 40× on a sale day. Read/write ratio: order reads outnumber writes ~20:1. Consistency: stock at checkout must be strongly consistent; stock shown while browsing may be 30 s stale. Latency budget for place-order: 1.5 s p99. Team: 40 engineers, five teams.

Contract: POST /orders (idempotency key), GET /orders/{id}, GET /orders?customer&status (cursor paged), POST /orders/{id}/cancel. Entities: Order (id, customer, lines, status, total, version), OrderLine, Payment, Reservation.

Shape: Modular monolith with eight modules, one artifact, three deployments. "I'd start here rather than microservices because the boundaries are still being learned, and at five teams the coordination cost doesn't yet justify the distribution cost. Here's what would make me split…"

The flow: place order → reserve stock (sync, must fail the order) → authorise payment (sync) → commit → OrderPlaced via outbox → fulfilment, notification, search index, loyalty (all async). Draw the sync hops in one colour and the async in another, and say why each is which.

Data: PostgreSQL, schema per module, no cross-schema joins. order_summary read model for history, maintained by events. Redis for the price cache and rate limits. OpenSearch for search, fed by events. Partition the orders table by month once it passes tens of millions of rows.

Scale the bottleneck: "The bottleneck at 40× is the orders write path and the inventory hot rows." Queue the non-critical work; optimistic locking plus reservation TTL on inventory; scale workers separately from web; pre-warm and raise the cache TTL for the sale window; shed load at the gateway before the database gets there.

Failure and ops: Payment gateway down → circuit breaker, order accepted as PAYMENT_PENDING with a retry job, customer told honestly. WMS down → events queue, fulfilment lags, nothing lost. Kafka down → outbox rows accumulate, the database still serves checkout. SLO 99.9% on place-order with burn-rate alerts; trace id end to end; DLT depth and consumer lag alerted.

W2

"We have a five-year-old monolith with 400 tables. Modernise it."

First, refuse the rewrite. "A big-bang rewrite of a system with five years of encoded business rules has a well-known failure rate. I'd strangle it instead — and the first six weeks are measurement, not code."

Measure: which endpoints carry traffic, which tables are written by more than one area, where the change requests actually land, and what the current failure modes are. Most of the 400 tables are cold; the architecture problem is in maybe forty of them.

Stabilise: add tracing and structured logs, characterisation tests on the highest-traffic flows, a CI pipeline that people trust, and timeouts on every outbound call. You cannot safely change a system you cannot observe.

Modularise in place: draw the boundaries, move packages to match, add ArchUnit rules with today's violations baselined, then ratchet down every sprint. This is unglamorous and it is where most of the value is — it delivers the decoupling without the distribution risk.

Split the data: schema per module, one role per module, cross-schema joins replaced by API calls or read models. Run this way for a while. "If I can't split the data, I definitely can't split the service."

Then extract, one module, on evidence: pick the one with a named trigger — usually the one with a different scaling profile or a compliance boundary. Interface stays, adapter swaps, feature flag, cut over, delete. Measure whether it helped before doing a second one.

Close with the business framing: "Each phase ships value on its own — the tracing pays for itself in incident time, the modularisation in change lead time. Nothing here requires a two-year programme with no deliverable until the end." That sentence is often what the question was really probing.

Five stories to have ready

Behavioural and technical rounds both dig for these. Sixty to ninety seconds each: situation, what you decided, what it cost, what you would do differently.

A production incident you handled

What broke, how you found it, what you changed permanently afterwards. The last part is what they are listening for — a fix without a systemic change reads as firefighting.

A design decision you got wrong

Pick a real one with a real cost, and describe the signal that told you. Candidates who cannot name one read as either inexperienced or unreflective.

A performance problem you diagnosed

Lead with how you measured, not what you guessed. "The trace showed 501 queries" beats "I suspected an N+1" every time.

A disagreement about architecture

How you framed the trade-off, what evidence changed the discussion, and what happened when the decision went against you. Grace here matters more than being right.

Something you simplified or deleted

Removing a service, a cache, or a flag. Senior engineers are measured on what they removed as much as what they built, and almost nobody prepares this one.

Tailoring

If the role is domain-heavy — payments, supply chain, trading — pick stories where the domain rules drove the design. It reads as someone who engages with the business, not only the stack.
