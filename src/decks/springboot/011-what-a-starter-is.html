A starter is a POM with no code in it

That is the entire trick. spring-boot-starter-data-jpa contains zero classes — it is a dependency list plus a curated set of versions. The behaviour comes from the auto-configuration in the jars it drags in.

What spring-boot-starter-data-jpa actually contains
<dependencies>
  <dependency>spring-boot-starter</dependency>          <!-- core + logging + yaml -->
  <dependency>spring-boot-starter-jdbc</dependency>      <!-- HikariCP + JdbcTemplate -->
  <dependency>hibernate-core</dependency>
  <dependency>spring-data-jpa</dependency>
  <dependency>spring-aspects</dependency>
</dependencies>
<!-- no src/main/java at all -->
The BOM is the other half — and the more valuable one (Maven)
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.5.0</version>
</parent>
<!-- now: no <version> on any managed dependency, ever.
     Boot has tested this exact combination of ~400 library versions
     against each other. Overriding one is how you find out which
     three others it was holding hands with. -->
The same thing in Gradle — what the rest of this atlas assumes
plugins {
    id("org.springframework.boot") version "3.5.0"
    id("io.spring.dependency-management") version "1.1.7"  // applies the BOM
}
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")  // no version
}
ext["kafka.version"] = "3.9.1"   // the ONLY safe way to move one library

How to read a dependency problem

  1. mvn dependency:tree / gradle dependencies — find where the version came from.
  2. Override Boot's version only through the property Boot defines (<hibernate.version>, ext["kafka.version"]), never by pinning the artifact directly — that way the whole family moves together.
  3. If you must exclude something, check nothing else on the tree needed it.
The enterprise smellA pom.xml with thirty explicit <version> tags means someone is fighting the BOM. Each one is a CVE-patching job that no longer happens automatically, and a compatibility matrix nobody maintains. Getting a team back onto managed versions is usually a one-day win worth taking.
Boot 4 module splitBoot 4 breaks its own jars into finer modules, so a class you imported from spring-boot-autoconfigure may now live elsewhere. The starters still work unchanged — it is direct dependencies on internal jars that break.
