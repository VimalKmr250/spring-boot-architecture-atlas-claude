Validation groups and cross-field rules

Two things plain constraints cannot express: "this field is required only when creating, not updating", and "the end date must be after the start date".

Groups — different rules for different operations
interface OnCreate { }
interface OnUpdate { }

record OrderPayload(
    @Null(groups = OnCreate.class)        // must be absent when creating
    @NotNull(groups = OnUpdate.class)     // must be present when updating
    UUID id,

    @NotEmpty(groups = { OnCreate.class, OnUpdate.class })
    List<LineRequest> lines,

    @NotBlank(groups = OnCreate.class)    // set once, never changed
    String currency
) { }

@PostMapping
OrderView create(@Validated(OnCreate.class) @RequestBody OrderPayload body) { ... }

@PutMapping("/{id}")
OrderView update(@Validated(OnUpdate.class) @RequestBody OrderPayload body) { ... }
// NOTE: @Valid cannot carry groups — only Spring's @Validated can.
Cross-field — the constraint goes on the class
@Target(TYPE) @Retention(RUNTIME)
@Constraint(validatedBy = DateRangeValidator.class)
public @interface ValidDateRange {
    String message() default "deliverBy must be after placedAt";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

class DateRangeValidator implements ConstraintValidator<ValidDateRange, OrderPayload> {
    public boolean isValid(OrderPayload p, ConstraintValidatorContext ctx) {
        if (p.placedAt() == null || p.deliverBy() == null) return true;   // let @NotNull say it
        boolean ok = p.deliverBy().isAfter(p.placedAt());
        if (!ok) {
            ctx.disableDefaultConstraintViolation();
            ctx.buildConstraintViolationWithTemplate(ctx.getDefaultConstraintMessageTemplate())
               .addPropertyNode("deliverBy")        // attach the error to a FIELD,
               .addConstraintViolation();           // so the UI can highlight it
        }
        return ok;
    }
}
Two details worth copyingReturn true on null and let @NotNull report it — otherwise one missing field produces two confusing errors. Attach the violation to a property node, or the frontend gets a class-level error it cannot map to an input.
Where groups stop being the answerThree or more groups on one record means you are modelling several operations in one type. Separate CreateOrderRequest and UpdateOrderRequest records are simpler, and each documents exactly one operation's contract.
