All seven propagation modes, and the two you should use

Propagation answers one question: when a transactional method is called from inside an existing transaction, what happens? Most teams only ever need REQUIRED and REQUIRES_NEW — but the others appear in interviews and in inherited code.

PropagationCalled with no transactionCalled inside oneUse for
REQUIRED defaultStarts oneJoins itAlmost everything. One transaction per use case
REQUIRES_NEWStarts oneSuspends the outer, starts an independent one on a second connectionAudit rows that must survive the caller's rollback; post-commit listeners
SUPPORTSRuns without oneJoins itReads that are fine either way. Rarely worth specifying
NOT_SUPPORTEDRuns without oneSuspends it, runs withoutA long report inside a transactional flow, to release the connection early
MANDATORYThrowsJoins itEnforcing "this may only be called as part of a larger unit of work"
NEVERRunsThrowsGuarding a method that must not hold a transaction
NESTEDStarts oneSavepoint inside the outer — rolls back to the savepoint onlyPartial rollback. JDBC only, not supported by all setups. Rare
The audit case — the one real use of REQUIRES_NEW
@Service
class OrderService {
    @Transactional                                   // REQUIRED
    void place(PlaceOrderCommand cmd) {
        audit.record("place attempted", cmd);        // must survive a rollback
        var order = Order.place(...);                // may throw → outer rolls back
        orders.save(order);
    }
}

@Service
class AuditService {
    @Transactional(propagation = REQUIRES_NEW)       // its own connection, its own commit
    void record(String what, Object payload) { ... }
}
REQUIRES_NEW in a loop is a self-inflicted deadlockIt takes a second connection while holding the first. A pool of 20 with a loop calling a REQUIRES_NEW method exhausts itself at 20 concurrent callers, each holding one connection and waiting for another that will never come free. The symptom is a hang, not an error.
rollback-only is contagiousIf an inner REQUIRED method throws and you catch the exception in the caller, the transaction is already marked rollback-only. Your caller finishes happily, then commit throws UnexpectedRollbackException — which looks like it came from nowhere. If you intend to recover from an inner failure, that inner call needs REQUIRES_NEW.
