Spring Data derived queries: the keyword reference

The method-name parser is genuinely useful up to about three conditions. Past that it produces names nobody can read, and a @Query is both shorter and clearer.

Readable, and the point where it stops being readable
// Fine

boolean existsByCustomerIdAndStatus(UUID customerId, OrderStatus status);
long countByPlacedAtAfter(Instant since);

// Not fine — write a @Query
List<OrderJpaEntity>
  findByCustomerIdAndStatusInAndPlacedAtBetweenAndTotalMinorGreaterThanOrderByPlacedAtDesc(
      UUID customerId, Collection<OrderStatus> statuses,
      Instant from, Instant to, long min);
deleteBy… is a loop, not a DELETESpring Data loads every matching entity and deletes them one by one, so lifecycle callbacks and cascades fire. That is sometimes what you want; on 200,000 rows it is an outage. For a bulk delete use @Modifying @Query("delete from …") and accept that callbacks will not run.
Ambiguous property namesfindByCustomerAddressCity could mean customer.address.city or a property called customerAddress. Disambiguate with underscores — findByCustomer_Address_City — rather than hoping the resolver guesses right, because it fails at startup with a message that does not name the real problem.
