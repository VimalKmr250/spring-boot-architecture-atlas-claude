Entity and column mapping

The annotations on nearly every entity, with the defaults that are wrong often enough to be worth overriding deliberately.

OrderJpaEntity.java — the mapping layer, not the domain model
@Entity
@Table(name = "orders", schema = "order_mgmt",
       indexes = @Index(name = "idx_orders_customer_placed",
                        columnList = "customer_id, placed_at DESC"),
       uniqueConstraints = @UniqueConstraint(columnNames = { "idempotency_key" }))
public class OrderJpaEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @Column(name = "customer_id", nullable = false, updatable = false)
    private UUID customerId;

    @Column(name = "total_minor", nullable = false)
    private long totalMinor;                    // money as minor units, never double

    @Column(length = 3, nullable = false, columnDefinition = "char(3)")
    private String currency;

    @Enumerated(EnumType.STRING)                // NEVER ORDINAL — see the warning
    @Column(nullable = false, length = 32)
    private OrderStatus status;

    private Instant placedAt;                   // java.time — no @Temporal needed on Hibernate 6

    @Embedded                                   // flattens into the same table
    private AddressEmbeddable shipTo;

    @Column(name = "raw_payload", columnDefinition = "text")
    private String rawPayload;                  // NOT @Lob — see the warning below

    @Transient                                  // never persisted
    private transient boolean recalculated;

    @Version                                    // optimistic locking
    private long version;

    protected OrderJpaEntity() { }              // JPA needs a no-arg constructor
}

@Enumerated(ORDINAL) is the default

And it stores 0, 1, 2. Insert a new enum constant in the middle a year later and every historical row silently changes meaning. Always STRING. This is the single most damaging JPA default.

@Column defaults you should set

nullable is true by default and only affects schema generation — the real constraint must be in your Flyway migration. updatable = false on immutable columns is genuinely enforced by Hibernate and catches bugs.

equals/hashCode

Do not use Lombok's @Data on an entity — it generates them over all fields including lazy associations, which triggers loads and breaks Set semantics before the id is assigned. Use the business key, or the id with a stable hashCode.

@Lob on a String, on PostgreSQLEverywhere else @Lob String means "a big text column". On PostgreSQL the JDBC driver maps it to a large object: the column stores an oid and the bytes live in pg_largeobject. The consequences are all unpleasant — SELECT raw_payload in psql returns a number, a plain DELETE orphans the object so the table never shrinks until you run vacuumlo, and reads need an open transaction so you get "Large Objects may not be used in auto-commit mode". Use columnDefinition = "text" (or @JdbcTypeCode(SqlTypes.LONGVARCHAR)) and let Postgres TOAST it, which it does automatically past ~2 kB. Reserve real LOBs for genuine streaming of hundreds of megabytes.
The mapping entity is not the domain modelIn the architecture deck's layering, Order (domain, no annotations) and OrderJpaEntity (this class) are different types with a mapper between them. For a CRUD-shaped module that separation is overhead worth skipping; for the module where the rules live, it is what keeps Hibernate out of your business logic.
