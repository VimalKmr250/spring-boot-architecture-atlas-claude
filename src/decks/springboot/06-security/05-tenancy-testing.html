Row-level scoping, multi-tenancy, and testing all of it

The third authorisation layer, and the annotations that let you prove any of it works. A security rule with no test is a security rule that will be deleted by a refactor.

Scoping applied centrally, not per query
// Hibernate filter enabled once per request — every query gets the predicate
@Entity
@FilterDef(name = "tenant", parameters = @ParamDef(name = "tenantId", type = String.class))
@Filter(name = "tenant", condition = "tenant_id = :tenantId")
class OrderJpaEntity { ... }

@Component
class TenantFilterActivator {
    @PersistenceContext EntityManager em;
    void activate(String tenantId) {
        em.unwrap(Session.class).enableFilter("tenant").setParameter("tenantId", tenantId);
    }
}

Testing security
@WebMvcTest(OrderController.class)
class OrderControllerSecurityTest {

    @Test @WithMockUser(roles = "OPS")
    void opsCanCancelAnyOrder() throws Exception { ... }

    @Test @WithAnonymousUser
    void anonymousGets401() throws Exception {
        mvc.perform(post("/api/orders")).andExpect(status().isUnauthorized());
    }

    @Test
    void customerCannotSeeAnotherCustomersOrder() throws Exception {
        mvc.perform(get("/api/orders/{id}", otherOrderId)
                .with(jwt().jwt(j -> j.subject("customer-2"))))
           .andExpect(status().isNotFound());     // 404, not 403 — do not confirm existence
    }
}

Multi-tenancy: pick deliberatelyShared schema + tenant column — cheapest, needs RLS discipline, and one forgotten WHERE is a cross-tenant leak. Schema per tenant — good isolation, but migrations across 500 schemas get slow and a failure halfway leaves you inconsistent. Database per tenant — strongest, viable with tens of tenants, and what regulated customers pay for.
404 or 403 for someone else's order?404. A 403 confirms the resource exists, which is an information leak — an attacker can enumerate order ids and learn your volume. Return 403 only when the user can legitimately know the resource exists but may not perform this action on it.
Write the negative testsThe tests that matter are the ones asserting someone is refused. Positive-only security tests pass just as happily against a filter chain that permits everything — which is exactly what an accidental permitAll() looks like.
