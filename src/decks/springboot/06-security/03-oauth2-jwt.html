Resource server, client, and what JWT validation really does

Two starters that sound similar and do opposite things: one accepts tokens, the other obtains them. Enterprise services usually need both.

Resource server — validating an incoming token
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: https://id.retailco.com/realms/shop   # discovers JWKS + issuer automatically
  audiences: [ order-api ]                          # REJECT tokens minted for another service
// scopes → authorities, plus roles from a custom claim
@Bean JwtAuthenticationConverter jwtConverter() {
    var scopes = new JwtGrantedAuthoritiesConverter();
    scopes.setAuthorityPrefix("SCOPE_");
    var converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {
        var authorities = new ArrayList<GrantedAuthority>(scopes.convert(jwt));
        List<String> roles = jwt.getClaimAsStringList("realm_roles");
        if (roles != null) roles.forEach(r ->
            authorities.add(new SimpleGrantedAuthority("ROLE_" + r)));
        return authorities;
    });
    return converter;
}
Client — obtaining a token to call someone else
spring.security.oauth2.client:
  registration.wms:
    client-id: order-platform
    client-secret: ${WMS_CLIENT_SECRET}
    authorization-grant-type: client_credentials     # service-to-service
    scope: [ shipments.write ]
  provider.wms.token-uri: https://id.retailco.com/realms/shop/protocol/openid-connect/token

What validation actually checks

  1. Signature against a key fetched from the JWKS endpoint (cached, refreshed on unknown kid).
  2. Issuer matches issuer-uri.
  3. Expiry and nbf, with a small clock skew allowance.
  4. Audience — only if you configure it.

Point 4 is the one that gets skipped. Without it, a valid token issued for the marketing API is accepted by the payments API, because both trust the same issuer. It is one line of YAML and it closes a real lateral-movement path.

JWTs cannot be revokedA stolen token is valid until it expires. So: keep access tokens short (5–15 minutes), keep refresh server-side (the BFF pattern), and for genuinely sensitive operations check a revocation list or use opaque tokens with introspection — which trades a network call per request for real revocation.
Opaque tokensspring.security.oauth2.resourceserver.opaquetoken introspects each token against the IdP. Slower and it couples request handling to IdP availability, but you get instant revocation and no claims leaking into a token anyone can decode. Many banks mandate it for external-facing APIs.
