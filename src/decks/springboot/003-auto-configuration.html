Auto-configuration, mechanically

Three annotations, one file of class names, and a pile of conditions. No reflection tricks, nothing hidden — you can read the whole chain yourself, and you should once.

ShopApplication.java — one annotation, three jobs
@SpringBootApplication      // = the three below, combined
public class ShopApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShopApplication.class, args);
    }
}

// @SpringBootApplication expands to:
@SpringBootConfiguration    // a @Configuration, marked as THE primary one
@EnableAutoConfiguration    // pull in auto-config classes
@ComponentScan              // scan this package and below

A real auto-configuration class, trimmed
@AutoConfiguration(before = { HibernateJpaAutoConfiguration.class })
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(DataSource.class)   // ← backs off if YOU declared one
    @ConditionalOnProperty(name = "spring.datasource.type",
                           havingValue = "com.zaxxer.hikari.HikariDataSource",
                           matchIfMissing = true)
    HikariDataSource dataSource(DataSourceProperties properties) { ... }
}
The order of events1. @EnableAutoConfiguration reads every AutoConfiguration.imports on the classpath. 2. Each class's conditions are evaluated. 3. Surviving classes are ordered by before/after. 4. Their @Bean methods run — but only after your own @Configuration classes are registered, which is why @ConditionalOnMissingBean can see your beans.
Legacy detail worth knowingBefore Boot 2.7 this list lived in META-INF/spring.factories under an EnableAutoConfiguration key. Boot 2.7 introduced the .imports file and read both; Boot 3.0 removed the spring.factories route entirely. An old in-house starter that never migrated contributes nothing — with no error, because other spring.factories keys still work, so the file looks fine. If a starter mysteriously stopped applying on the 2.x→3.x upgrade, this is why.
