The conditions that decide what exists

These are the whole of Boot's "opinion". Nine annotations; you will write three of them yourself the first time you build an internal starter.

AnnotationFires whenTypical use
@ConditionalOnClassA class is on the classpathConfigure Hibernate only if Hibernate was added
@ConditionalOnMissingClassA class is absentFall back when an optional library is not present
@ConditionalOnBeanA bean of that type already existsAdd a JpaTransactionManager only if a DataSource exists
@ConditionalOnMissingBeanNo such bean is definedThe back-off rule. On nearly every auto-configured @Bean
@ConditionalOnPropertyA property has a value (or is absent, with matchIfMissing)Feature toggles in your own starter
@ConditionalOnWebApplicationIt is a servlet or reactive web appSkip MVC config in a batch job
@ConditionalOnResourceA file exists on the classpathLoad config only when a mapping file is shipped
@ConditionalOnExpressionA SpEL expression is trueCompound conditions — use sparingly, it is unreadable
@ProfileAn active profile matchesEnvironment-shaped beans (worker vs web)

Read this report before guessing"Why is my DataSource the wrong one?" and "why did my custom ObjectMapper not take effect?" are both answered in full by that output, in about thirty seconds. It is the single most under-used diagnostic in Spring Boot.

Actuator's /actuator/conditions endpoint gives the same report as JSON on a running application — useful when the problem only reproduces in an environment you cannot restart with --debug.
