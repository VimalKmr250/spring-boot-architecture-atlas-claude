Jackson: the annotations that shape your API's JSON

Your wire contract is decided here. Every one of these is a public-API decision, so they belong on DTOs — never on entities, where they couple your database schema to your consumers.

The set you actually use
@JsonInclude(JsonInclude.Include.NON_NULL)          // omit nulls — class or field level
record OrderView(

    @JsonProperty("order_id")                       // rename on the wire
    UUID id,

    @JsonFormat(shape = STRING, pattern = "yyyy-MM-dd'T'HH:mm:ssXXX")
    Instant placedAt,

    @JsonFormat(shape = JsonFormat.Shape.STRING)    // BigDecimal as a string —
    BigDecimal total,                               // stops JS clients losing precision

    @JsonAlias({ "customerId", "customer_id" })     // accept both on the way IN
    UUID customerId,

    @JsonIgnore                                     // never serialised
    String internalNote,

    @JsonProperty(access = READ_ONLY)               // serialised out, ignored on input
    OrderStatus status,

    @JsonProperty(access = WRITE_ONLY)              // accepted in, never echoed back
    String idempotencyKey,

    // @JsonUnwrapped flattens a nested object into the parent — but it does
    // NOT work on a record component: Jackson cannot unwrap into a creator
    // parameter, so writing works and reading fails. Flatten it by hand.
    long amountMinor,
    String currency
) { }

// Deserialisation entry points
@JsonCreator                                        // explicit constructor for non-records
@JsonAnySetter                                      // catch-all for unmapped fields
@JsonNaming(SnakeCaseStrategy.class)                // rename the whole class at once

@JsonIgnore is not security

It stops a field being serialised — it does not stop it being deserialised unless you also block that. A client can still POST {"role":"ADMIN"} into a field you thought was hidden. Use access = READ_ONLY, or better, a separate request DTO that simply has no such field.

Money as a string

JSON numbers become IEEE doubles in JavaScript. 99999999.99 survives; a long enough decimal does not. Serialise money as a string, or as minor units in a long. Financial clients will ask you for this eventually — ship it first.

Be a tolerant reader

FAIL_ON_UNKNOWN_PROPERTIES=false (Boot's default) is what lets a producer add a field without breaking you. Turning it on to "catch typos" makes every additive upstream change a production incident.
