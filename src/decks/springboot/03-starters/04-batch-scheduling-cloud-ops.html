Batch, scheduling, and the cloud/ops set

Batch is the half of enterprise Java that architecture decks usually ignore and that runs the business overnight.

Batch & scheduling

-batch
Jobs, steps, chunk-oriented processing, restartability, and the BATCH_* metadata tables that make a failed job resumable from the last commit point. For end-of-day reconciliation, statement generation, bulk file loads.
-quartz
Clustered, persistent scheduling. Use when the schedule must survive restarts and must fire exactly once across a fleet.
@Scheduled
Built into the core — no starter. Fine for a single instance; on N pods it fires N times unless you add a lock (ShedLock, or a database advisory lock).
The classic bug@Scheduled on a service running 6 replicas sends six reminder emails to every customer. Every team meets this once. Design for it: either Quartz clustered, ShedLock, or a dedicated single-replica batch deployment — the third option is the one from the deployment-topology slide.

Cloud & ops

-oauth2-resource-server
Validate incoming JWTs. What your API uses.
-oauth2-client
Obtain tokens to call others — client-credentials for service-to-service.
cloud-config-client
Externalised config with refresh. Weigh against ConfigMaps + a restart, which is simpler and usually enough.
cloud-openfeign
Declarative HTTP clients. Boot 4 Spring's own @ImportHttpServices covers most of this natively now.
resilience4j-spring-boot3
Circuit breaker, bulkhead, rate limiter with Actuator endpoints. Boot 4 core @Retryable and @ConcurrencyLimit cover the common cases.
vault-config
Secrets, and — the part that matters — dynamically issued, short-lived database credentials.
-cache
@Cacheable plus a provider (Caffeine local, Redis shared).
A Spring Batch step — chunked, restartable, and the reason batch exists
@Bean
Step reconcilePayments(JobRepository repo, PlatformTransactionManager tx,
                       ItemReader<PaymentRecord> reader,
                       ItemProcessor<PaymentRecord, Reconciliation> processor,
                       ItemWriter<Reconciliation> writer) {
    return new StepBuilder("reconcilePayments", repo)
            .<PaymentRecord, Reconciliation>chunk(500, tx)   // commit every 500 items
            .reader(reader).processor(processor).writer(writer)
            .faultTolerant()
              .skipLimit(50).skip(MalformedRecordException.class)   // tolerate bad rows
              .retryLimit(3).retry(TransientDatabaseException.class)
            .build();
}
// Crash at item 12,300 of 500,000? Restart resumes from the last committed chunk,
// because the BATCH_STEP_EXECUTION table recorded it. That is the whole value.
