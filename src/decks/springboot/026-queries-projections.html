Queries: derived, JPQL, native, dynamic — and when to leave JPA

Four query mechanisms in Spring Data, in increasing order of power and decreasing order of readability. Knowing when to stop using JPA entirely is part of using it well.

The four mechanisms
interface OrderJpaRepository extends JpaRepository<OrderJpaEntity, UUID>,
                                     JpaSpecificationExecutor<OrderJpaEntity> {

    // 1. Derived — parsed from the method name. Great up to ~3 conditions.
    List<OrderJpaEntity> findByCustomerIdAndStatusOrderByPlacedAtDesc(UUID id, OrderStatus s);
    boolean existsByIdempotencyKey(String key);
    long countByStatus(OrderStatus status);

    // 2. JPQL — portable, type-checked against the entity model at startup
    @Query("select o from OrderJpaEntity o where o.placedAt > :since and o.totalMinor > :min")
    List<OrderJpaEntity> recentLargeOrders(@Param("since") Instant since, @Param("min") long min);

    // 3. Native — when you need database features JPQL has no words for
    @Query(value = """
            select date_trunc('day', placed_at) as day, count(*) as orders
              from order_mgmt.orders
             where placed_at >= :since
             group by 1 order by 1
            """, nativeQuery = true)
    List<DailyCount> dailyCounts(@Param("since") Instant since);

    // 4. Modifying — bulk operations that bypass the persistence context
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("update OrderJpaEntity o set o.status = :to where o.status = :from and o.placedAt < :cut")
    int expireStale(@Param("from") OrderStatus from, @Param("to") OrderStatus to,
                    @Param("cut") Instant cut);
}
Projections — do not load an entity you will not change
// Interface projection: Spring Data generates the select list for you
interface OrderCard {
    UUID getId();
    Instant getPlacedAt();
    long getTotalMinor();
    @Value("#{target.customer.displayName}") String getCustomerName();  // careful: loads it
}
List<OrderCard> findByStatus(OrderStatus status);

// Class/record projection: explicit and obvious
record OrderSummary(UUID id, Instant placedAt, long totalMinor) { }

// Or skip JPA: JdbcClient straight to a record, no entity, no persistence context
jdbc.sql("select id, placed_at, total_minor from order_mgmt.orders where customer_id = ?")
    .param(customerId).query(OrderSummary.class).list();
@Modifying bypasses everythingA bulk update runs SQL directly: no dirty checking, no @Version increment, no entity listeners, no cache eviction. Entities already in the persistence context keep the old values — which is exactly what clearAutomatically and flushAutomatically are for. Bulk operations also skip auditing, so updatedBy silently stops being true.
When to leave JPASpecifications / Criteria for search screens with a dozen optional filters — verbose but composable. jOOQ when the SQL is genuinely complex and you want it type-checked. JdbcClient for every read that does not need an entity, which in a typical service is most of them. Using JPA for writes and something simpler for reads is CQRS-lite and needs no framework.
