Wiring and externalised configuration

Constructor injection is the only form worth using. Everything else on this slide exists to disambiguate, defer or configure it.

Injection
@Service
class PlaceOrderUseCase {
    private final OrderRepository orders;          // final = immutable, testable
    private final PaymentGateway payments;

    // No @Autowired needed — a single constructor is autowired since Spring 4.3
    PlaceOrderUseCase(OrderRepository orders, PaymentGateway payments) { ... }
}

@Qualifier("primaryGateway")      // pick between several beans of a type
@Primary                          // the default choice when ambiguous
@Lazy                             // create on first use — a circular-dep stopgap
@Scope("prototype")               // new instance per lookup
ObjectProvider<Foo> provider;     // optional / lazy / multiple, without @Lazy tricks
@Order(10)                        // ordering within an injected List<Handler>
Configuration binding
@Value("${shop.order.max-lines:100}")   // single value + default. Avoid at scale.
private int maxLines;

// Prefer this: typed, validated at startup, documented, IDE-completable
@ConfigurationProperties("shop.order")
@Validated
public record OrderProperties(
        @Min(1) @Max(500) int maxLines,
        @NotNull Duration reservationTtl,
        @NotBlank String currency) { }

@EnableConfigurationProperties(OrderProperties.class)   // or @ConfigurationPropertiesScan
Never field injection@Autowired private OrderRepository repo; hides dependencies from the constructor, makes the class untestable without Spring, permits circular dependencies that should have failed, and cannot be final. If a class has eight constructor parameters that is a signal, not a reason to switch to fields.

Why @ConfigurationProperties beats @Value

  • Validated at startup, not on first read — a typo fails the boot, not a 3am payment.
  • Relaxed binding: max-lines, maxLines, MAX_LINES all bind, so an env var Just Works.
  • Type conversion for Duration, DataSize, List, nested records.
  • With spring-boot-configuration-processor, your properties get IDE autocomplete and docs.

Records get constructor binding with no @ConstructorBinding needed since Boot 3.

Profiles@Profile("worker") on a bean, application-worker.yaml for its config, SPRING_PROFILES_ACTIVE=prod,worker at runtime. This is the mechanism behind "one artifact, three deployments" in the architecture deck. Keep profiles about role (web/worker/batch), not about environment secrets.
