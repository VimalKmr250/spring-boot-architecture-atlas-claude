Stereotypes and configuration

All the stereotypes are @Component underneath. The differences that actually matter are exception translation on @Repository and proxying on @Configuration.

Stereotypes
@Component        // generic managed bean — the base for all of these
@Service          // semantic only; marks application/domain logic
@Repository       // + translates JDBC/Hibernate exceptions into Spring's
                  //   DataAccessException hierarchy. Not cosmetic.
@Controller       // returns view names
@RestController   // = @Controller + @ResponseBody on every method
@Configuration    // bean definitions live here; see proxyBeanMethods below
@ControllerAdvice // cross-controller @ExceptionHandler / @ModelAttribute
Configuration and bean registration
@Configuration(proxyBeanMethods = false)   // set this on your own configs
class OrderConfig {

    @Bean                                   // method name = bean name
    OrderService orderService(OrderRepository repo) { ... }

    @Bean(initMethod = "start", destroyMethod = "close")
    ReportGenerator reports() { ... }
}

@Import(SharedInfraConfig.class)      // pull in another @Configuration explicitly
@ComponentScan(basePackages = "com.retailco.shop",
               excludeFilters = @Filter(type = ASSIGNABLE_TYPE, classes = LegacyJob.class))

proxyBeanMethods — the one people never set

By default, @Configuration is CGLIB-proxied so that calling orderService() from another @Bean method returns the singleton rather than a new object. Convenient, but it costs a proxy per config class at startup.

If your @Bean methods never call each other — which is the norm when you take dependencies as method parameters — set proxyBeanMethods = false. Every Boot auto-configuration class does. Measurably faster startup, and it is what native-image compilation wants.

@Repository is not decorativeWithout it, a unique-constraint violation surfaces as a Hibernate ConstraintViolationException; with it, as Spring's DataIntegrityViolationException. Your catch blocks and your @Retryable rules are written against the second one. Spring Data repositories get this automatically; hand-written DAOs do not.
Scanning@SpringBootApplication scans its own package and below. That is why the main class belongs at the root package — a class in a sibling package is silently never registered, and the symptom is a confusing "no qualifying bean" at startup.
