Finding a leak from a heap dump

A leak in Java is an object still reachable but no longer needed. The heap dump tells you which one; the reference chain tells you why.

Capture, then analyse offline
# Live histogram first — often enough on its own
jcmd <pid> GC.class_histogram | head -30

# Full dump (pauses the JVM; take it from a pod already out of rotation)
jcmd <pid> GC.heap_dump /dumps/heap.hprof
# or let it happen automatically:
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps

# Eclipse MAT: Leak Suspects -> dominator tree ->
# "path to GC roots, excluding weak/soft references" — that path IS the bug.
A heap dump is customer dataIt contains every string in memory: names, addresses, tokens, possibly card data. Treat it as production data — restricted storage, access logged, deleted afterwards. Copying one to a laptop is a data-handling incident in most banks.

The leaks that actually happen in Spring apps

Unbounded cache
A ConcurrentHashMap used as a cache with no eviction. Use Caffeine with a maximumSize — always.
ThreadLocal on a pooled thread
Set and never removed. The thread lives forever, so the value does too. Always remove() in a finally.
Listeners never unregistered
Anything registering itself at startup that outlives its owner.
Session-scoped state
Large objects in an HTTP session with a long timeout, times concurrent users.
Accumulating collections
A List field on a singleton that only ever grows — an audit buffer, a "recent items" list.
Not a leak
A rising heap that drops after a full GC is just G1 being lazy. Only growth after a full GC counts.
The graph that identifies a leak with no tooling at allPlot jvm_memory_used_bytes{area="heap"} over a week with deploys marked. A healthy service shows a sawtooth with a flat baseline. A leak shows a sawtooth whose troughs rise steadily until the pod restarts — and a restart cadence matching your deploy frequency is how leaks stay hidden for years.
