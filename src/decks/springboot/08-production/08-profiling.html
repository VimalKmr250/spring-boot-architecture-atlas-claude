"The endpoint is slow" — the ordered method

Six steps, cheapest first. Most incidents are solved by step 2 or 3; starting at step 1 rather than guessing is what separates a 20-minute diagnosis from a two-day one.

#StepToolWhat it rules in or out
1Slow for everyone, or at p99 only?The RED dashboardA fat tail means contention, GC or one bad tenant — not the code path itself
2Where does the time go across services?A trace of one slow requestPoints at the hop. Usually a downstream call or the database
3How many queries, and how long?Trace spans, datasource-proxy, pg_stat_statementsN+1, a missing index, or far too many rows returned
4Is it waiting on a pool?Hikari metrics: pending, usage, acquireConnection starvation — the time is queueing, not working
5What are the threads doing right now?/actuator/threaddump, three snapshots 10 s apartA lock, a blocking call, or a fully occupied thread pool
6Where is CPU actually spent?async-profiler / JFR flame graphThe genuinely CPU-bound case — the rarest outcome in enterprise services
Java Flight Recorder — safe to run in production
# Start a recording on a running pod, ~1% overhead
jcmd <pid> JFR.start name=slow duration=120s filename=/dumps/slow.jfr settings=profile
jcmd <pid> JFR.dump  name=slow filename=/dumps/slow.jfr
# Open in JDK Mission Control: hot methods, allocation, locks, JDBC, GC.

# Or always-on, so the evidence already exists when the incident starts:
-XX:StartFlightRecording=disk=true,maxsize=200M,maxage=6h,dumponexit=true
The three-thread-dump trickTake three dumps ten seconds apart. Threads stuck on the same stack frame in all three are your problem — a lock, a socket read with no timeout, or a pool wait. Costs nothing, needs no extra tooling, and solves a surprising share of production hangs.
Measure before and after, the same way"It feels faster" is not a result. Capture p50/p95/p99 and throughput from the same dashboard under comparable load. Optimisations that help p50 and hurt p99 are common — caching often does exactly that.
Where the time usually isIn rough order: N+1 queries · a missing index · an unbounded result set · a downstream call with no timeout · connection-pool starvation · serialising a huge response. CPU-bound application code is near the bottom of that list.
