Performance: budget the latency, stream the wait, and scale with virtual threads

An LLM call spends seconds waiting on the network, so an AI service is I/O-bound with long request times. On classic platform threads, 200 concurrent conversations exhaust Tomcat's default pool. Java 21 virtual threads make blocking calls cheap again, so the simple call() style scales without rewriting into reactive code. Latency itself is managed by budgeting each stage, streaming, and doing less.

application.yml
spring:
  threads:
    virtual:
      enabled: true          # Tomcat and @Async run requests on virtual threads
  mvc:
    async:
      request-timeout: 120s  # long streamed answers
server:
  tomcat:
    max-connections: 10000
BottleneckFix
Threads blocked on model callsVirtual threads; or streaming with Flux
Provider rate limits (requests and tokens per minute)Concurrency cap per instance, a queue, more quota or regions, provisioned throughput
Long promptsTrim history and context; prompt caching for the stable prefix
Long answersAsk for brevity; cap output; stream
Sequential calls in a workflowRun independent calls in parallel; merge steps that do not need separate calls
Repeated workCache embeddings, retrieval results and frequent answers
Batch jobs competing with usersSeparate quotas or deployments; provider batch APIs
Scale out, not upThe service is stateless and the work is waiting, so horizontal scaling is easy; the real limit is your provider quota. Load-test with a stubbed or mocked model endpoint to find your own limits, then with the real provider at low volume to measure its latency distribution.
Say it in the interview"The model dominates latency, so I stream for perceived speed, budget every stage, keep prompts and answers short, and use virtual threads so blocking calls don't exhaust the thread pool. Throughput is bounded by provider quota, so I cap concurrency and plan quota like capacity."
