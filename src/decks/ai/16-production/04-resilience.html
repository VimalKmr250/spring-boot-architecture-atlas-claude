Resilience: bounded retries, real timeouts, a fallback, and a concurrency cap

Model providers rate-limit, time out and have outages like any remote dependency, and a single call can take tens of seconds. Know which retry layer applies to your provider, make the worst-case wait shorter than your users' patience, cap concurrent calls under your quota, and decide what happens when the model is unavailable: a second provider, a cached answer, or an honest message.

        max-interval: 4s
Check the defaultsWith Spring AI's defaults, ten attempts wait 2 + 10 + 50 + 6 × 180 seconds between them: about 19 minutes of backoff alone, holding the request thread. Fine for a nightly batch, unacceptable behind a chat box. Set retries per workload, and do not stack your own retries on top of the provider's without counting the total.
ResilientAnswerService.java
package com.acme.ai.ops;

import com.openai.errors.InternalServerException;
import com.openai.errors.OpenAIIoException;
import com.openai.errors.RateLimitException;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.retry.TransientAiException;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Configuration;
import org.springframework.resilience.annotation.ConcurrencyLimit;
import org.springframework.resilience.annotation.EnableResilientMethods;
import org.springframework.stereotype.Service;

@Configuration
@EnableResilientMethods
class ResilienceConfig {}

@Service
class ResilientAnswerService {

    private static final Logger log = LoggerFactory.getLogger(ResilientAnswerService.class);

    private final ChatClient primary;
    private final ChatClient fallback;

    ResilientAnswerService(@Qualifier("primaryChatClient") ChatClient primary,
                           @Qualifier("fallbackChatClient") ChatClient fallback) {
        this.primary = primary;
        this.fallback = fallback;
    }

    /** At most 20 calls in flight from this instance: stays under the provider quota. */
    @ConcurrencyLimit(20)
    public String answer(String question) {
        try {
            return primary.prompt().user(question).call().content();
        } catch (RuntimeException e) {
            if (!isTransient(e)) {
                throw e;                     // a bad request will fail on any provider
            }
            log.warn("primary model unavailable ({}), using fallback", e.getClass().getSimpleName());
            return fallback.prompt().user(question).call().content();
        }
    }

    static boolean isTransient(Throwable e) {
        return e instanceof RateLimitException
                || e instanceof InternalServerException
                || e instanceof OpenAIIoException
                || e instanceof TransientAiException;
    }
}

Fallback options

Same model through another region or provider; a smaller model; a cached answer for common questions; or a clear "the assistant is busy, here is the help page". Decide per feature, and test the fallback path regularly.

Rate limits are capacity

Providers limit requests and tokens per minute. A concurrency cap and a queue protect you from 429 storms; provisioned throughput or a second region buys headroom for peaks.

Circuit breakers

When the primary is failing, stop sending it traffic for a while instead of paying the timeout on every request. Resilience4j's circuit breaker around answer() is the usual choice.
