A chat is a list of messages you resend on every call

Chat models take a list of messages, each with a role. The model remembers nothing between calls, so to continue a conversation your application sends the whole relevant history again. Understanding that one fact explains chat memory, context limits and most of the token bill.

RoleWho writes itSpring AI type
systemYou. Persona, rules, output format. Highest priority.SystemMessage
userThe end user, or your code on their behalf. Untrusted.UserMessage
assistantThe model. Text, or requests to call tools.AssistantMessage
toolYour code: the result of a tool the model asked for.ToolResponseMessage
Sending history by hand (excerpt) · memory advisors do this for you
List<Message> history = List.of(
        new UserMessage("Where is order 1042?"),
        new AssistantMessage("It ships tomorrow from the Pune warehouse."));

String reply = chatClient.prompt()
        .system("You are Acme's support assistant. Be brief.")
        .messages(history)                       // earlier turns
        .user("Can I still change the address?") // this turn
        .call()
        .content();

History is a cost decision

Resending 40 turns costs 40 turns of tokens on every call. Keep a window of recent messages, summarise older ones, or retrieve only relevant turns. See memory strategies.

The system message is not a security boundary

It has priority, but a determined user message can still talk the model out of it. Enforce rules in code: authorisation on tools, validation of outputs, filters on retrieval.

Stateless is good news

Because the model holds no session, any instance of your service can serve any turn. Keep the history in a shared store (JDBC, Redis) and your chat service scales like any stateless API.
