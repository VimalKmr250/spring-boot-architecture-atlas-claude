Eight ways an LLM feature fails, and the fix for each

Every one of these has caused a production incident somewhere. An interviewer who asks "what could go wrong?" wants this list, and wants each failure matched to a concrete control in your code, not a hope that a better model will fix it.

FailureWhat it looks likeControlIn Spring AI
HallucinationA confident, plausible, invented refund policy or API methodGround answers in retrieved sources, require citations, allow "I don't know"RAG advisors, evaluators

Cost and latency blow-upsA tool loop runs 40 times; a 5-second answer becomes 50Budgets, limits, timeouts, streaming, smaller modelsspring.ai.tools.limits.*, retry and timeout settings
The general ruleNever let the model be the only thing standing between a user and a consequence. The model proposes; deterministic code validates, authorises and executes. That separation is the difference between a demo and a system you can put in front of customers.
Say it in the interview"I assume the model will be wrong some of the time, so I design for detection and containment: grounded answers with citations, typed outputs I validate, tools that enforce authorisation themselves, budgets on every loop, and an evaluation set that runs in CI."
