Sampling options decide how the next token is picked

The model produces a probability for every possible next token; the sampler picks one. Sampling options reshape that choice. They are the first knobs you reach for, and the ones most often set by superstition. Set them per task, write down why, and check the model supports them.

OptionWhat it doesTypical setting
temperatureScales the probabilities. Low values make the top token dominate; high values flatten the curve and add variety.0–0.2 extraction, classification · 0.3–0.5 summaries, Q&A · 0.7–1.0 brainstorming
topPSamples only from the smallest set of tokens whose probabilities add up to p.Leave at default; change temperature or top-p, not both
topKSamples only from the k most likely tokens. Not every provider supports it.Default
maxTokensHard cap on output tokens. The answer is cut off mid-sentence when hit.Always set it: it bounds cost and latency
stopSequencesStops generation when one of these strings appears.Delimiters in few-shot formats
frequencyPenalty · presencePenaltyDiscourage repeating tokens already used.Rarely needed with modern models
Portable options: a model that samples (ollama profile, Claude Haiku 4.5…) · excerpt
String label = chatClient.prompt()
        .system("Classify the review as POSITIVE, NEGATIVE or MIXED. Reply with the label only.")
        .user(review)
        .options(ChatOptions.builder()
                .temperature(0.0)        // same input, (almost) same label
                .maxTokens(10))          // a label, not an essay
        .call()
        .content();

Reasoning models are differentModels that "think" before answering reject a custom temperature or topP: OpenAI's gpt-5 and o-series families, and Anthropic's current Opus and Sonnet models, which use an effort setting instead. OpenAI's reasoning models also expect max_completion_tokens, which Spring AI sends from maxCompletionTokens; the portable maxTokens is sent as max_tokens. Portable options are the intersection of what providers support, so check the model card before relying on them.
Temperature 0 is not deterministicIt makes the most likely token win, but batching and floating-point effects on the provider's GPUs still change outputs now and then. Never write a test that expects an exact string from a real model. Use structured output and assertions on fields instead.

Defaults in config, overrides in code

Put the common case in application.yml. Override per request only where a use case needs something else, such as a classifier at temperature 0. Options set on the request win over the defaults.

Interview trap

"How do you stop hallucinations?" — "Set temperature to 0" is the wrong answer. Low temperature makes the model consistently pick its most likely continuation, which can be consistently wrong. Grounding, citations and validation reduce hallucination; temperature only reduces variety.
