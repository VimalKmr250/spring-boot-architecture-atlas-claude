Choose a model per task, on your data, against a budget

There is no best model, only the cheapest one that passes your evaluation for a given task. A classifier that runs a million times a day and a contract reviewer that runs fifty times a day should not use the same model. Because Spring AI hides the provider behind one API, switching is a configuration change, so the decision can follow evidence instead of fashion.

What to compare

Quality
pass rate on your evaluation set, not public leaderboards
Latency
time to first token (streaming UX) and tokens per second (total time)
Cost
input and output price × your measured token counts
Context
window size, and how well it recalls from long inputs
Features
tool calling, native structured output, vision, audio, prompt caching
Governance
data retention, training on your data (should be "no"), region, certifications
The pattern that saves the most moneyRoute by task. A small model handles the high-volume, well-defined calls (classify, extract, route); a frontier model handles the few calls that need deep reasoning. In Spring AI that is two ChatClient beans built from two models: see multiple models.
Pin the versionAliases such as "latest" move under you, and a model update can change answers your tests depend on. In production, pin a dated model id in configuration and re-run your evaluation set before you move to a new one. The samples in this tab use short aliases only to stay readable.
