Five common use cases, and the building blocks each one needs

Most LLM features in enterprise applications are one of a handful of shapes. Recognising the shape tells you which building blocks you need, which model tier is enough, and which risk to design against first. The next five slides build each one with Spring AI.

Use caseBuilding blocksModel tierFirst risk to design forMeasure
Support chatbotMemory, RAG, tools, streaming, escalationSmall to mid; frontier for hard casesInvented policies; actions for the wrong customerResolution rate, escalation rate, CSAT

Code generation and reviewStructured output, repository context, CI checksFrontier or code-specialisedInsecure or non-compiling code acceptedAcceptance rate, build pass rate, defects
Sentiment and classificationEnums, batching, embeddings or small modelSmallest that passesSilent drift in label qualityAccuracy on a labelled sample, per class

Start where the data is clean

Summarisation and classification over existing text need no tools, no memory and no customer exposure: ideal first projects that build the team's evaluation and operations habits.

Customer-facing comes later

A support chatbot touches every risk at once. Ship it after you can measure retrieval quality, enforce tool permissions and escalate reliably.

Every use case needs a baseline

Before the model: what does keyword search, a rules engine or the current manual process achieve? The LLM feature has to beat it on your metric, not on a demo.
