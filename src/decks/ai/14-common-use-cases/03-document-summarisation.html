Summarisation: stuff it when it fits, map-reduce when it does not

If a document fits comfortably in the context window, one call with a structured output is simplest and sees the whole text. For documents too long for the window, or when you want a cheap model and parallelism, use map-reduce: summarise each part independently, then combine the partial summaries. Either way, ask for a typed summary with the fields your readers need, not "a summary".

DocumentSummarizer.java
package com.acme.ai.usecases.summary;

import java.util.List;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.document.Document;
import org.springframework.ai.transformer.splitter.TokenTextSplitter;
import org.springframework.stereotype.Service;

@Service
class DocumentSummarizer {

    record Summary(String title, String overview, List<String> keyPoints,
                   List<String> obligations, List<String> openQuestions) {}

    private static final int STUFF_LIMIT_TOKENS = 60_000;

    private static final String MAP = """
            Summarise this part of a longer document in at most 8 bullet points.
            Keep names, numbers, dates and obligations exactly as written.
            Do not add anything that is not in the text.""";

    private static final String REDUCE = """
            Combine these partial summaries of one document into a single summary.
            Remove duplicates; keep every obligation, date and amount.""";

    private final ChatClient chatClient;
    private final TokenTextSplitter splitter = TokenTextSplitter.builder()
            .withChunkSize(STUFF_LIMIT_TOKENS / 4)
            .withMaxNumChunks(200)
            .build();

    DocumentSummarizer(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    Summary summarize(String text) {
        List<Document> parts = splitter.split(new Document(text));
        if (parts.size() <= 4) {                                  // fits: one call, whole text
            return chatClient.prompt().system(REDUCE).user(text).call().entity(Summary.class);
        }
        List<String> partials;
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {   // map, in parallel
            List<Future<String>> futures = parts.stream()
                    .map(p -> pool.submit(() -> chatClient.prompt()
                            .system(MAP).user(p.getText()).call().content()))
                    .toList();
            partials = futures.stream().map(DocumentSummarizer::join).toList();
        }
        return chatClient.prompt()                                  // reduce
                .system(REDUCE)
                .user(String.join("\n\n---\n\n", partials))
                .call()
                .entity(Summary.class);
    }

    private static String join(Future<String> f) {
        try {
            return f.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } catch (ExecutionException e) {
            throw new IllegalStateException(e.getCause());
        }
    }
}
StrategyProsCons
Stuff (one call)Sees everything; simplest; cross-references surviveLong inputs cost more and recall drops in the middle
Map-reduceAny length; parallel; cheap model for the map stepLoses links between parts; one extra step
Refine (sequential)Each step sees the running summarySlow: no parallelism; early mistakes propagate
Summaries are read by people who will not check the sourceAsk for exact figures and dates, forbid additions, and keep the structure fixed so readers know where to look. For contracts or medical text, show which section each key point came from.
Evaluate coverage, not proseFor a sample of documents, list the facts a summary must contain, then score how many each summary includes and whether it adds anything unsupported. A fact-checking evaluator with the source as context automates the second half.
Watch the billSummarising every inbound PDF with a frontier model adds up quickly. Route by length and importance: a small model for routine documents, the large one for contracts over a threshold value.
