Three questions on state, adaptation and money

These questions check that you know the model is stateless, that you can tell a knowledge problem from a behaviour problem, and that you think about cost before the invoice arrives.

Q19

The model is stateless. How does chat memory work in Spring AI?

30-second answerMemory means resending relevant history on every call. MessageChatMemoryAdvisor loads the conversation's messages from ChatMemory before the call and saves the new user message and answer after it. MessageWindowChatMemory keeps the last 20 messages by default, and a ChatMemoryRepository stores them: in memory by default, or JDBC, Redis, Cassandra, MongoDB or Neo4j. The conversation id is passed per request with ChatMemory.CONVERSATION_ID.

Go deeper: In 2.0 the id is mandatory; without it the call fails with "conversationId cannot be null". Issue ids on the server and check ownership on every request. History is a cost and privacy decision: size the window, summarise older turns with a small model for long sessions, redact before storing, and expire conversations on a retention schedule. The memory advisor sits outside the tool loop, so one turn is stored as a question and a final answer.

Q20

When would you fine-tune instead of using RAG?

30-second answerRAG for knowledge, fine-tuning for behaviour. If the model lacks facts, especially facts that change or need per-user access control and citations, RAG is the answer; fine-tuning does not reliably teach facts and goes stale. I fine-tune when I need a consistent format, style or narrow skill that a long few-shot prompt only just achieves at high volume, or to distil a large model into a cheaper one for one task, and only after an evaluation shows prompting is not enough.

Go deeper: Name the methods: supervised fine-tuning, LoRA and QLoRA adapters for open-weight models, preference tuning, distillation; hosted tuning APIs versus self-hosted. The cost is mostly data: hundreds to thousands of curated, consented, redacted examples with a held-out set. Operate the tuned model like a release: versioned, compared with the prompted baseline, rolled out by config, re-checked when a new base model ships.

Q21

How do you keep LLM costs under control?

30-second answerMeasure first: token usage per feature and per model. Then send fewer tokens (smaller history window, fewer and better chunks, capped output), use cheaper tokens (route classification and extraction to a small model), and reuse work (provider prompt caching with a stable prefix, a semantic cache for repeated questions, batch APIs for offline jobs). Finally bound the worst case with tool-call limits, timeouts and a per-user token budget.

Go deeper: Input tokens usually dominate because system prompt, context and history are resent every turn. Judge cost per resolved task, not per call: a cheap model that needs three attempts is not cheaper. A budget advisor can refuse a request before the model call; on Spring AI 2.0, the final response's usage already sums every call in the tool loop.
