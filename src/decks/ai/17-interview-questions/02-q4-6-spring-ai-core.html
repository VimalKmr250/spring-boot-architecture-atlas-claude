Three questions on the Spring AI programming model

Interviewers check that you know the main types, where the extension points are, and how the framework stays portable. Concrete class names and one gotcha per answer show real use.

Q4

What is the difference between ChatClient and ChatModel?

30-second answerChatModel is the provider-neutral interface for one round trip: a Prompt in, a ChatResponse out, one implementation per provider. ChatClient is the fluent API built on it: defaults, templates, advisors such as memory and RAG, the tool-calling loop, and structured output with .entity(). I inject the auto-configured ChatClient.Builder, build one client per use case, and drop to ChatModel only when writing framework code.

Go deeper: In Spring AI 2.0 the difference grew: the tool loop moved out of each ChatModel into ToolCallingAdvisor, auto-registered by ChatClient, so calling ChatModel directly now returns raw tool requests. Also mention the builder is a prototype bean and mutable: when building several clients from one builder, call clone(), or they share defaults.

Q5

What is an advisor? Give examples and explain why order matters.

30-second answerAn advisor is an interceptor around the model call, like a servlet filter: it can change the request, the response, or stop the call. Memory, RAG, the tool loop, structured-output validation, logging and safeguards are all advisors. They run in getOrder() order: memory at HIGHEST+200, tool calling at HIGHEST+300, most others at 0. A redaction advisor must sit before memory, or raw personal data gets stored.

Go deeper: Advisors after the tool advisor run on every tool round trip, so a RAG advisor at order 0 retrieves again for each tool call, while memory runs once per turn. Advisors share a context map, which is how per-request values such as the conversation id or a filter expression reach them. A custom advisor usually implements BaseAdvisor (before/after) so it works for both call() and stream().

Q6

How is Spring AI portable across providers, and how do you use two models in one app?

30-second answerEach provider has a starter that auto-configures its ChatModel and EmbeddingModel behind the common interfaces, so business code written against ChatClient does not change; switching is a dependency plus properties, with spring.ai.model.chat choosing the provider when several starters are present. For two models, I disable the auto-configured builder and declare one ChatClient bean per model, injected by qualifier.

Go deeper: Portability covers the common options; provider features such as reasoning effort or prompt caching use provider option classes, so keep those in configuration or a small adapter. When building clients by hand, pass the ObservationRegistry to ChatClient.builder(model, registry, null, null) or you lose metrics and traces. An internal LLM gateway that speaks the OpenAI API is just another base-url.
