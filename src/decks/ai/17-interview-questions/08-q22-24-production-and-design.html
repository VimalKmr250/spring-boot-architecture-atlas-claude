Q22

How do you test and monitor an LLM feature in production?

30-second answerThree layers of tests: unit tests with a stub ChatModel that returns canned replies and records prompts, so prompts, parsing, branches and tool logic are deterministic; integration tests with Testcontainers for Ollama and pgvector; and evaluation suites against the real model with thresholds. In production, Spring AI's Micrometer observations give token, latency and error metrics and traces per call and tool; I add per-feature tags and quality signals such as thumbs-down and escalation rates.

Go deeper: Keep prompt and completion content out of logs and spans by default; Spring AI does. Alert on p95 latency, error types (429 versus 5xx versus timeouts), tokens per request trending up, and quality signals, because a quality regression has no stack trace. Sample conversations for human review each week, and turn failures into new golden-set cases.

Q23

Design an internal knowledge assistant over Confluence and SharePoint with document-level permissions.

30-second answerConnectors ingest pages and their permissions on change events plus a nightly reconciliation; chunks go to pgvector with source, URL, last-modified and ACL groups. On a question, the service reads the employee's groups from the SSO token, builds a filter (everyone, or one of their groups), runs RAG with that filter, and returns an answer with citations. Unanswered and down-voted questions go to content owners.

Go deeper: The risky part is permissions: copied ACLs go stale, so sync on permission-change events, delete vectors of removed pages, and write a test proving one group cannot retrieve another's documents. Map fine-grained permissions to a manageable set of access groups to keep filters fast. Measure retrieval recall on a golden set, show "last updated" with citations, and keep the assistant read-only.

Q24

How would you upgrade a Spring AI 1.x application to 2.0?

30-second answerFirst move to Spring Boot 4 and Jackson 3, since 2.0 requires them. Then work through the breaking changes: .options() takes a builder; memory needs a conversation id on every request; ToolCallAdvisor became ToolCallingAdvisor and ChatModel no longer runs tools; tools must be attached explicitly; MCP annotations moved packages; property keys lost their .options. segment; the JDBC memory table needs a sequence_id column. The tests and evaluation set prove behaviour did not change.

Go deeper: Old property keys still bind but are deprecated, so fix them while the IDE flags them. Check retry behaviour after the upgrade: OpenAI and Anthropic now use their official SDKs' retries and timeouts rather than spring.ai.retry. Upgrade in a branch with the stub-model unit tests and container tests green, then compare evaluation scores before and after on the same models.
