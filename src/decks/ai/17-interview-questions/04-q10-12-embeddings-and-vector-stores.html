Three questions on vectors, indexes and their trade-offs

Expect a concept question, an infrastructure question and a "what goes wrong over time" question. Numbers (dimensions, storage, recall) make the answers credible.

Q10

What are embeddings, and how is similarity measured?

30-second answerAn embedding model maps text to a fixed-length vector, for example 1,536 floats, so that texts with similar meaning are close together. Similarity is usually cosine similarity, the angle between vectors; for normalised vectors dot product gives the same ranking. In Spring AI, EmbeddingModel.embed() returns the vector, and a VectorStore embeds and searches for you.

Go deeper: Embeddings capture topic and paraphrase but are weak on exact identifiers and negation, which is why hybrid keyword plus vector search exists. Scores are not probabilities and thresholds are model-specific, so tune them on labelled data. Many features need only embeddings: deduplication, semantic search, classification by nearest examples, recommendations.

Q11

How do you choose a vector store and an index type?

30-second answerI start with what the team already operates: pgvector if we run PostgreSQL, Elasticsearch or OpenSearch if we have a search cluster and need hybrid search. A dedicated engine such as Qdrant or Milvus comes in at hundreds of millions of vectors or very high query rates. For the index, HNSW is the default: excellent recall at low latency, more memory; IVF builds faster with less memory but needs re-clustering.

Go deeper: ANN indexes trade recall for speed; tune ef_search and measure recall against exact search on sample queries. Selective metadata filters can starve ANN results, so test filters at realistic selectivity. Storage estimate: one million chunks × 1,536 dimensions × 4 bytes is about 6 GB raw, plus index overhead. Because Spring AI abstracts VectorStore, a move is a re-index, not a rewrite.

Q12

What happens when you change the embedding model?

30-second answerEvery stored vector must be recomputed, because vectors from different models live in different spaces and cannot be compared; the dimension may change too, which means a new column or index. So I keep the source text, store the model name with each vector, and run the migration as a background job: build a new index next to the old one, compare retrieval quality on the evaluation set, then switch queries over.

Go deeper: Budget it: re-embedding a million 400-token chunks is 400M tokens. Profiles that use different embedding models, such as OpenAI in production and Ollama locally, must not share a table. The same discipline applies to chunking changes: anything that changes what is embedded requires re-ingestion.
