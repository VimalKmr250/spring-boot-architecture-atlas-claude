Three memory strategies, chosen by conversation length and what must be remembered

A sliding window is simple and right for most chats. Long-running conversations need something more: a running summary that keeps the facts that matter, or retrieval of only the past turns relevant to the current question. Whichever you choose, memory is stored personal data, with the obligations that come with it.

Summarising older turns with a cheap model (excerpt)
List<Message> history = chatMemory.get(id);
if (history.size() > 16) {
    List<Message> older = history.subList(0, history.size() - 6);
    List<Message> recent = List.copyOf(history.subList(history.size() - 6, history.size()));

    String summary = fastChatClient.prompt()
            .system("""
                    Summarise this support conversation in at most 6 bullet points.
                    Keep order ids, amounts, dates and anything we promised.""")
            .messages(older)
            .user("Summarise the conversation above.")
            .call()
            .content();

    chatMemory.clear(id);
    chatMemory.add(id, new UserMessage("Summary of our earlier conversation:\n" + summary));
    chatMemory.add(id, recent);
}

Memory is personal dataDecide retention up front and enforce it with a job. Support "delete this conversation" with chatMemory.clear(id). Redact card numbers and secrets before they are stored by ordering a redaction advisor ahead of memory. Keep each tenant's conversations in a separate partition or table, and include memory in your data-subject access and erasure processes.
Say it in the interview"The model is stateless, so memory is a cost and privacy decision. I default to a window of recent messages in a shared store, keyed by a server-issued conversation id with an ownership check. For long sessions I summarise older turns with a small model, and conversations expire on a retention schedule."
