The model asks for a tool; your code decides whether and how to run it

Tool calling (also called function calling) lets a model use live data and take actions. You describe tools with a name, a description and a JSON schema for the arguments. The model can reply with a request to call one instead of text. Your application runs the tool, sends the result back, and the model continues. The model never executes anything itself, and that is the property your security rests on.

Two model calls, at least

Every tool use costs a round trip: the request that produced the tool call, and the request that carries the result. Each resends the conversation and tool definitions, so a chatty tool loop multiplies latency and tokens. Prefer tools that return everything needed in one call.

The description is the interface

The model chooses tools from their names and descriptions alone. "Gets order" is ambiguous; "Returns status, carrier and estimated delivery date of one of the current customer's orders" tells it when to call and what it will get.

1.x where the loop lives

In 1.x each ChatModel ran tools internally. In 2.0 the loop is ToolCallingAdvisor, auto-registered by ChatClient, so it is ordered, observable and replaceable like any advisor, and ChatModel.call() returns the raw tool request.
