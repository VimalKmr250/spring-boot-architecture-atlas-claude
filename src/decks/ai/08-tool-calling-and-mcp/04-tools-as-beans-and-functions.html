Functions as tools, and choosing the tool set per user

When a tool wraps an existing service, a FunctionToolCallback bean is often cleaner than annotating that service. Either way, in Spring AI 2.0 a model can only call tools you attach to the request or client: there is no global registry it can reach by name. That makes per-user tool sets, built from the user's roles, the natural place to enforce least privilege.

InventoryToolConfig.java
package com.acme.ai.tools.beans;

import java.util.ArrayList;
import java.util.List;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.tool.ToolCallback;
import org.springframework.ai.tool.annotation.ToolParam;
import org.springframework.ai.tool.function.FunctionToolCallback;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.core.Authentication;
import org.springframework.stereotype.Service;

@Configuration
class InventoryToolConfig {

    record StockQuery(
            @ToolParam(description = "Product SKU, for example LMP-01") String sku,
            @ToolParam(description = "Warehouse code; omit for all warehouses",
                       required = false) String warehouse) {}

    record StockLevel(String sku, int available) {}

    record AdjustStock(@ToolParam(description = "Product SKU") String sku,
                       @ToolParam(description = "Units to add (negative to remove)") int delta) {}

    interface Inventory {
        StockLevel level(String sku, String warehouse);
        StockLevel adjust(String sku, int delta);
    }

    @Bean
    ToolCallback stockLevelTool(Inventory inventory) {
        return FunctionToolCallback
                .builder("stockLevel", (StockQuery q) -> inventory.level(q.sku(), q.warehouse()))
                .description("Current available stock of one product")
                .inputType(StockQuery.class)
                .build();
    }

    @Bean
    ToolCallback adjustStockTool(Inventory inventory) {
        return FunctionToolCallback
                .builder("adjustStock", (AdjustStock a) -> inventory.adjust(a.sku(), a.delta()))
                .description("Corrects the stock count of one product after a manual recount")
                .inputType(AdjustStock.class)
                .build();
    }
}

@Service
class StoreOpsAssistant {

    private final ChatClient chatClient;
    private final ToolCallback stockLevel;
    private final ToolCallback adjustStock;

    StoreOpsAssistant(ChatClient.Builder builder,
                      @Qualifier("stockLevelTool") ToolCallback stockLevel,
                      @Qualifier("adjustStockTool") ToolCallback adjustStock) {
        this.chatClient = builder.defaultSystem("You help Acme store staff with stock questions.").build();
        this.stockLevel = stockLevel;
        this.adjustStock = adjustStock;
    }

    String ask(String question, Authentication user) {
        List<ToolCallback> tools = new ArrayList<>(List.of(stockLevel));    // everyone can read
        boolean manager = user.getAuthorities().stream()
                .anyMatch(a -> a.getAuthority().equals("ROLE_STORE_MANAGER"));
        if (manager) {
            tools.add(adjustStock);                                         // only managers can write
        }
        return chatClient.prompt().user(question).tools(tools.toArray()).call().content();
    }
}

Way to declare a toolUse when
@Tool methods + .tools(object)Tools written for the assistant, several per class
FunctionToolCallback beanWrapping an existing service without touching it
MethodToolCallbackProviderExposing a bean's @Tool methods as a ToolCallbackProvider
MCP tool callbacksTools that live in another service: MCP
1.x no more tools by name2.0 removed toolNames(...), defaultToolNames(...) and the resolver that looked tools up among all beans. Attach tools explicitly with tools(...) or defaultTools(...), which accept @Tool objects, ToolCallbacks and providers; the toolCallbacks(...) variants are deprecated for removal in 2.0. A global fallback can be re-enabled with spring.ai.tools.resolution.fallback.enabled=true, but it widens what a fooled model can call; leave it off.
Read tools and write toolsSeparate them, as here. Read tools can be broadly available; write tools go only to roles that may perform the action anyway, and should be idempotent, audited, and in many cases create a request a person confirms.
