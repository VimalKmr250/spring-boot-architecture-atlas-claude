Design every tool as if an attacker were choosing the arguments

Through prompt injection, sometimes one is. A tool is an API endpoint whose caller is a language model influenced by whatever text it has read. Apply the same controls you would to a public endpoint, plus two that are specific to AI: the model must never choose whose data it touches, and actions with consequences need a confirmation step outside the model.

A write tool that proposes instead of acting (excerpt)
@Tool(description = """
        Proposes a refund for one of the current customer's orders.
        The customer must confirm it in the app before anything is paid.""")
RefundProposal proposeRefund(@ToolParam(description = "Order id") String orderId,
                             @ToolParam(description = "Reason in the customer's words") String reason,
                             ToolContext ctx) {
    String customerId = (String) ctx.getContext().get("customerId");
    Order order = orders.requireOwned(orderId, customerId);            // authorisation
    RefundProposal proposal = refunds.propose(order, reason);          // idempotent per order
    audit.record(customerId, "proposeRefund", orderId, proposal.id()); // who, what, when
    return proposal;   // the model tells the user to confirm; the UI calls the real refund API
}
The rule of thumbIf you would not expose the tool as a public REST endpoint with the same parameters and the user's token, do not expose it to a model.
Observability built inSpring AI records an execute_tool <name> span for every tool call. Arguments and results are not recorded unless you set spring.ai.tools.observations.include-content=true; leave it off where tools handle personal data.
Say it in the interview"Tools run with the user's identity, never one the model supplies. Read tools are broad, write tools are narrow, and anything with money or messages creates a pending action that a human confirms. Every call is audited and limited."
