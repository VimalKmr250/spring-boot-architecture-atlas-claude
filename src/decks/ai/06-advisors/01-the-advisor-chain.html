Advisors wrap the model call like servlet filters, in order

An advisor sees the request on the way in and the response on the way out, and can change either, or stop the call entirely. Spring AI sorts advisors by getOrder(), lowest first, and always ends the chain with an advisor that calls the ChatModel. Memory, RAG, the tool loop, output validation and logging are all advisors. Knowing their order explains most surprising behaviour.

Memory outside the tool loop

Memory runs once per user turn: it loads history before the loop and saves the final exchange after it. Advisors ordered after ToolCallingAdvisor, such as RAG and logging, run on every tool round trip, so a three-tool answer retrieves three times. Order an advisor before the tool advisor if it should run once.

Guards go first

SafeGuardAdvisor defaults to order 0, so memory has already stored the message it is about to block. Give it, and any redaction advisor, an order below HIGHEST_PRECEDENCE + 200 so nothing sensitive reaches memory, retrieval or logs.

Advisors share a context map

Each request carries a context() map that advisors read and write: the conversation id for memory, retrieved documents for citations, your own flags. Set values per call with .advisors(a -> a.param(key, value)).
