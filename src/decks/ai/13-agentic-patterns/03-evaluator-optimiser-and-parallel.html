Let one call critique another, and run independent calls at the same time

The evaluator–optimiser pattern pairs a generator with a reviewer that checks the draft against explicit criteria and returns structured feedback; the generator revises until the review passes or a round limit is hit. Parallelisation sends independent calls at once, so ten section summaries take as long as the slowest one. Java 21's virtual threads make the parallel part ordinary blocking code.

ProductCopyStudio.java
package com.acme.ai.agents;

import java.util.List;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.stereotype.Service;

@Service
class ProductCopyStudio {

    record Review(boolean approved, List<String> issues) {}

    record Result(String copy, int rounds, boolean approved) {}

    private static final int MAX_ROUNDS = 3;

    private final ChatClient writer;
    private final ChatClient reviewer;

    ProductCopyStudio(ChatClient.Builder builder) {
        this.writer = builder.clone()
                .defaultSystem("You write product descriptions for Acme Retail. 60–90 words.")
                .build();
        this.reviewer = builder.clone()
                .defaultSystem("""
                        You review product copy. Approve only if ALL hold:
                        1. Every claim is supported by the product facts.
                        2. No superlatives ("best", "revolutionary").
                        3. 60–90 words, mentions the warranty.
                        List each failed rule as an issue.""")
                .build();
    }

    /** Evaluator–optimiser: draft, review, revise; bounded. */
    Result write(String productFacts) {
        String copy = writer.prompt().user("Product facts:\n" + productFacts).call().content();
        for (int round = 1; round <= MAX_ROUNDS; round++) {
            Review review = reviewer.prompt()
                    .user("Facts:\n" + productFacts + "\n\nCopy:\n" + copy)
                    .call()
                    .entity(Review.class);
            if (review.approved()) {
                return new Result(copy, round, true);
            }
            copy = writer.prompt()
                    .user("Product facts:\n" + productFacts + "\n\nRevise this copy:\n" + copy
                            + "\n\nFix these issues:\n- " + String.join("\n- ", review.issues()))
                    .call()
                    .content();
        }
        return new Result(copy, MAX_ROUNDS, false);    // a person finishes it
    }

    /** Parallelisation: one virtual thread per product, results in input order. */
    List<Result> writeAll(List<String> productFacts) throws InterruptedException {
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            List<Future<Result>> futures = productFacts.stream()
                    .map(facts -> pool.submit(() -> write(facts)))
                    .toList();
            return futures.stream().map(ProductCopyStudio::join).toList();
        }
    }

    private static Result join(Future<Result> future) {
        try {
            return future.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } catch (ExecutionException e) {
            throw new IllegalStateException(e.getCause());
        }
    }
}
Make the criteria checkable"Is it good?" produces vague reviews. Numbered rules with yes/no outcomes produce issues the writer can act on, and give you a pass rate to track. Rules a program can check, such as word count, should be checked in code instead.
Bound everythingA round limit, a fallback to a person, and a provider rate limit in mind: 50 products × up to 7 calls each is 350 calls in a burst. Cap concurrency (a Semaphore, or Spring's @ConcurrencyLimit) to stay under your quota.
