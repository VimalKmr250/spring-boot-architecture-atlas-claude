Build an agent only when the path is unknowable, and fence it in when you do

An agent trades predictability for flexibility. That trade is worth it for investigation-style tasks: diagnosing why an order is stuck across five systems, researching a supplier, triaging an incident. It is a poor trade for anything you can already describe as steps. When you do build one, the controls matter more than the prompt.

Four questions before building an agent

Complexity
Is the task multi-step and impossible to specify in advance? If you can write the flowchart, write a workflow.
Value
Does the outcome justify several times the cost and latency of a workflow?
Capability
Has a model shown, on your evaluation tasks, that it can do this reliably?
Cost of error
Can mistakes be caught before they reach a customer or a ledger: review, tests, dry-runs, rollback?

A "no" to any of them means a simpler design: a workflow, a single call, or plain code.

A safe first agent

An internal "why is this order stuck?" investigator: read-only tools over order, payment, warehouse and carrier systems, used by support staff who read its findings before acting. High value, contained risk.

A risky first agent

A customer-facing agent that can issue refunds and change addresses autonomously. Same technology, far higher cost of error; build the workflow version first.

Say it in the interview"I start with workflows because they are testable. I reach for an agent only for genuinely open-ended tasks, and then I bound it: tool and token limits, read-only by default, human approval for side effects, tracing, and an evaluation suite."
