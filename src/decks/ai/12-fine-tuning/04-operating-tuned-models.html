A tuned model is a release artefact: evaluate it, version it, and plan its replacement

A fine-tuning job produces a new model that your application depends on, built from a dataset that will age. Treat it like a build output: compare it with the base model on the same held-out set, promote it through environments, keep the old version ready for rollback, and know when you will retrain or retire it.

Before promoting a tuned model

  • Beats the base model with your best prompt on the held-out set, by a margin worth the extra cost and pipeline.
  • No regression on general prompts and on safety checks (refusals, toxicity, leakage of training examples).
  • Latency and price per call measured; tuned models are often priced higher per token, or need your own GPUs.
  • Model id, dataset version, base model and evaluation scores recorded together in a model registry or release notes.
  • Rollout behind configuration: a property switches between versions, so rollback is a config change.

A common, sensible outcome

Many teams build the dataset and evaluation set, compare a tuned small model with a prompted large one, and keep the prompted one because the difference does not justify the pipeline. The evaluation set is still the most valuable thing they built.

Where tuning clearly wins

High-volume, narrow, stable tasks: routing, extraction in a fixed format, house-style rewriting. Distilling such a task into a small model can cut cost and latency several-fold.
