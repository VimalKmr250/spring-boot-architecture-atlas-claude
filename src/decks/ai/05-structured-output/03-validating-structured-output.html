Validate twice: the schema with the model, the business rules in code

Two kinds of wrong output reach you. Malformed: not JSON, a missing field, a label outside the enum. Well-formed but wrong: urgency 7 on a 1–3 scale, a summary of 2,000 words. Spring AI's StructuredOutputValidationAdvisor checks the reply against the JSON schema and asks the model again with the errors. Bean Validation on the record checks the rest, and anything still invalid goes to a person instead of downstream.

ValidatedRouter.java
package com.acme.ai.structured;

import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validator;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;
import java.util.Set;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.client.advisor.StructuredOutputValidationAdvisor;
import org.springframework.stereotype.Service;

@Service
class ValidatedRouter {

    enum Queue { DELIVERY, ORDER_CHANGE, BILLING, RETURNS, PRODUCT_QUESTION, OTHER }

    record Routing(@NotNull Queue queue,
                   @Min(1) @Max(3) int urgency,
                   @NotBlank @Size(max = 200) String summary) {}

    sealed interface Outcome permits Routed, NeedsHuman {}
    record Routed(Routing routing) implements Outcome {}
    record NeedsHuman(String reason) implements Outcome {}

    private final ChatClient chatClient;
    private final Validator validator;

    ValidatedRouter(ChatClient.Builder builder, Validator validator) {
        this.chatClient = builder
                .defaultSystem("""
                        Route Acme support tickets.
                        urgency: 1 = low, 2 = time-sensitive, 3 = money lost or customer upset.
                        summary: one sentence, at most 200 characters.""")
                .defaultAdvisors(StructuredOutputValidationAdvisor.builder()
                        .outputType(Routing.class)     // schema derived from the record
                        .maxRepeatAttempts(2)          // re-ask with the errors, twice at most
                        .build())
                .build();
        this.validator = validator;
    }

    Outcome route(String ticket) {
        Routing routing;
        try {
            routing = chatClient.prompt().user(ticket).call().entity(Routing.class);
        } catch (RuntimeException e) {    // still unparseable, or the provider failed
            return new NeedsHuman("unusable model output: " + e.getMessage());
        }
        Set<ConstraintViolation<Routing>> violations = validator.validate(routing);
        if (!violations.isEmpty()) {
            ConstraintViolation<Routing> first = violations.iterator().next();
            return new NeedsHuman(first.getPropertyPath() + " " + first.getMessage());
        }
        return new Routed(routing);
    }
}
LayerCatchesCost
Native structured outputShape errors, before they happenNone; not every provider or schema
StructuredOutputValidationAdvisor (or .entity(T.class, s -> s.validateSchema()))Shape errors, by re-asking with the validation messageOne extra call per failure (default 3 attempts)
Bean Validation on the recordRanges, lengths, required fields, patternsMicroseconds
Business checksTotals that do not add up, unknown SKUs, dates in the futureA lookup or a sum
Human review queueEverything that still fails, plus a random samplePeople's time; measure the rate

Make the failure path a first-class resultReturning a sealed Outcome instead of throwing forces every caller to handle "needs a human". Track the share of NeedsHuman outcomes as a metric: when it rises after a prompt or model change, you know before your users do.
Enums are your best friendFor classification, an enum gives the model a closed list, gives the schema an enum constraint, and gives your code an exhaustive switch. Add an OTHER value so the model never has to force a ticket into the wrong queue.
