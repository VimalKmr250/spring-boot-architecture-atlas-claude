Generic types need a type reference; strict schemas need the provider's help

Java erases generics at runtime, so List<LineItem>.class does not exist. Pass a ParameterizedTypeReference instead, or wrap the list in a record. And by default the schema is only a polite request in the prompt: with useProviderStructuredOutput() Spring AI hands it to the provider's native JSON-schema mode, where the model's decoding is constrained to valid output.

InvoiceExtractor.java
package com.acme.ai.structured;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.util.List;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.converter.ListOutputConverter;
import org.springframework.core.ParameterizedTypeReference;
import org.springframework.stereotype.Service;

@Service
class InvoiceExtractor {

    record LineItem(String sku, String description, int quantity, BigDecimal unitPrice) {}

    record Invoice(String supplier, String invoiceNumber, LocalDate issued,
                   String currency, List<LineItem> lines, BigDecimal total) {}

    private final ChatClient chatClient;

    InvoiceExtractor(ChatClient.Builder builder) {
        this.chatClient = builder
                .defaultSystem("""
                        Extract data exactly as written in the document.
                        Use ISO dates (yyyy-MM-dd) and ISO 4217 currency codes.
                        Use null for anything that is not present.""")
                .build();
    }

    /** A record that contains a list: the simplest shape. */
    Invoice invoice(String text) {
        return chatClient.prompt()
                .user(text)
                .call()
                .entity(Invoice.class, spec -> spec.useProviderStructuredOutput());
    }

    /** A top-level generic type needs a ParameterizedTypeReference. */
    List<LineItem> lineItems(String text) {
        return chatClient.prompt()
                .user(text)
                .call()
                .entity(new ParameterizedTypeReference<List<LineItem>>() {});
    }

    /** Just strings: a comma-separated list is cheaper than JSON. */
    List<String> keywords(String text) {
        return chatClient.prompt()
                .user(u -> u.text("Five search keywords for: {text}").param("text", text))
                .call()
                .entity(new ListOutputConverter());
    }
}
Format instructions (default)Native (useProviderStructuredOutput)
HowSchema appended to the prompt as textSchema sent as the provider's response format
GuaranteeUsually valid; can break on long or odd inputsOutput constrained to the schema by the provider
ProvidersAny chat modelThose whose options support an output schema: OpenAI, Anthropic, Ollama, among others
Schema limitsNone beyond the model's understandingProviders restrict keywords (some formats, recursion); test complex types
TokensSchema text costs input tokens each callOften cheaper; some providers cache compiled schemas
Valid JSON is not correct dataNative mode guarantees the shape. It does not stop the model from putting the wrong number in a valid field, inventing a SKU, or summing the total incorrectly. Validate business rules in code: see validation.
Design the record for the modelFlat beats deep. Clear field names beat abbreviations. Enums beat free strings. A nullable field with "null if not present" beats a required one the model must invent. A record designed this way is also easier to evaluate.
Money and datesAsk for BigDecimal amounts and ISO dates, and say which currency and format. Then recompute the total from the lines in code and compare: an extraction that does not add up goes to review.
