Switch providers with a starter; run several models with explicit beans

Code written against ChatClient does not change when the provider does. Swapping is a dependency plus properties. Running two models side by side, a cheap one for routing and a strong one for reasoning, takes one more step: turn off the auto-configured builder and declare a ChatClient bean per model.

ChatClientConfig.java · a fast model and a deep one
package com.acme.ai.models;

import io.micrometer.observation.ObservationRegistry;
import org.springframework.ai.anthropic.AnthropicChatModel;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.openai.OpenAiChatModel;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.stereotype.Service;

@Configuration
class ChatClientConfig {

    /** Cheap and quick: routing, classification, short answers. */
    @Bean
    @Primary
    ChatClient fastChatClient(OpenAiChatModel model, ObservationRegistry registry) {
        return ChatClient.builder(model, registry, null, null)
                .defaultSystem("Be brief and precise.")
                .build();
    }

    /** Stronger and slower: long documents, multi-step reasoning. */
    @Bean
    ChatClient deepChatClient(AnthropicChatModel model, ObservationRegistry registry) {
        return ChatClient.builder(model, registry, null, null)
                .defaultSystem("Think carefully. Cite the parts of the input you used.")
                .build();
    }
}

@Service
class ContractReviewService {

    private final ChatClient deep;

    ContractReviewService(@Qualifier("deepChatClient") ChatClient deep) {
        this.deep = deep;
    }

    String review(String contract) {
        return deep.prompt().user(contract).call().content();
    }
}
application.yml · two chat providers in one app
spring:
  ai:
    chat:
      client:
        enabled: false          # no auto-configured ChatClient.Builder
    model:
      embedding: openai         # chat left unset: both ChatModels are created
    openai:
      api-key: ${OPENAI_API_KEY}
      chat:
        model: gpt-5-mini
    anthropic:
      api-key: ${ANTHROPIC_API_KEY}
      chat:
        model: claude-sonnet-5-5
Why the builder is switched offThe auto-configured ChatClient.Builder injects a single ChatModel. With two ChatModel beans, startup fails with "expected single matching bean". Disable it and build each client yourself.
Keep the metricsChatClient.builder(model) without an ObservationRegistry produces no metrics or traces. Pass the registry, as above, so hand-built clients are observed exactly like auto-configured ones.

Portable code, provider-tuned options

Business code uses ChatClient and portable options. Provider-specific settings (reasoning effort, prompt caching, Bedrock guardrails) live in configuration or in a small adapter, so a switch touches one place.

Gateways count as providers

Many enterprises route every call through an internal LLM gateway for keys, quotas and audit. If it speaks the OpenAI API, point spring.ai.openai.base-url at it and nothing else changes.

Fallback across providers

With two clients, a fallback is ordinary code: catch the outage from the primary and retry the request on the secondary. See resilience for the full pattern.
