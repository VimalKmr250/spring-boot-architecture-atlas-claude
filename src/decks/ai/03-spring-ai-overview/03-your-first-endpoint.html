A REST endpoint that asks a model, in one class

Inject the auto-configured ChatClient.Builder, set the defaults this use case needs, build once, and call it per request. The builder is a prototype bean, so each injection point gets its own and defaults never leak between features. The built ChatClient is immutable and thread-safe.

AskController.java
package com.acme.ai.first;

import jakarta.validation.Valid;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/ask")
class AskController {

    record Question(@NotBlank @Size(max = 2_000) String text) {}

    record Answer(String text) {}

    private final ChatClient chatClient;

    AskController(ChatClient.Builder builder) {
        this.chatClient = builder
                .defaultSystem("""
                        You are the assistant for Acme Retail's customers.
                        Answer in at most three sentences.
                        If you are not sure, say so instead of guessing.""")
                .build();
    }

    @PostMapping
    Answer ask(@Valid @RequestBody Question question) {
        String text = chatClient.prompt()
                .user(question.text())
                .call()
                .content();
        return new Answer(text);
    }
}

       -d '{"text":"Can I return a sofa after 30 days?"}'

returned after that is usually not accepted. I'm not certain
about exceptions for large items; please check the returns
page or contact support."}
Notice the honest hedgeThe model does not know Acme's policy. The system prompt told it to admit uncertainty, so it hedged instead of inventing a rule. Making it actually know the policy is the job of RAG.

Validate input like any API

@Size(max = 2_000) is a cost control as well as a sanity check: every character you accept is a token you pay for, and a 2 MB paste would fill the context window.

One client per use case

Build separate ChatClients for support, summarisation and classification, each with its own system prompt, options and advisors. Sharing one "god client" mixes concerns the way a shared god service does.

Errors are your API's errors

Timeouts, rate limits and provider outages surface as exceptions from call(). Map them in your @RestControllerAdvice to a 503 with a retry hint; never return the provider's raw error to the client.
