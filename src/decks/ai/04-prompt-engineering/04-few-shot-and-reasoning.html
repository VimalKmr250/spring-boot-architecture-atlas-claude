Show the model two or three answers, and give it room to think

Examples are the most reliable way to pin down a format or a judgement call that is hard to describe in rules. Send them as earlier conversation turns, so the model sees exactly what a good answer looks like. For decisions with several factors, ask a non-reasoning model to write its reasoning before its answer; reasoning models already do that internally.

TicketRouter.java · few-shot as message pairs
package com.acme.ai.fewshot;

import java.util.List;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.messages.AssistantMessage;
import org.springframework.ai.chat.messages.Message;
import org.springframework.ai.chat.messages.UserMessage;
import org.springframework.stereotype.Service;

@Service
class TicketRouter {

    /** Varied on purpose: different queues, urgencies and writing styles. */
    private static final List<Message> EXAMPLES = List.of(
            new UserMessage("Parcel says delivered but it's not here. Third time this month!!"),
            new AssistantMessage("DELIVERY | HIGH"),
            new UserMessage("hi, can I change the colour on order 5521 before it ships?"),
            new AssistantMessage("ORDER_CHANGE | MEDIUM"),
            new UserMessage("Your site charged my card twice for one order."),
            new AssistantMessage("BILLING | HIGH"),
            new UserMessage("Do you sell gift cards?"),
            new AssistantMessage("PRODUCT_QUESTION | LOW"));

    private final ChatClient chatClient;

    TicketRouter(ChatClient.Builder builder) {
        this.chatClient = builder
                .defaultSystem("""
                        Route the support ticket. Reply with QUEUE | URGENCY only.
                        Queues: DELIVERY, ORDER_CHANGE, BILLING, RETURNS, PRODUCT_QUESTION, OTHER.
                        Urgency: HIGH if money is lost or the customer is already upset,
                        MEDIUM if it is time-sensitive, otherwise LOW.""")
                .build();
    }

    String route(String ticket) {
        return chatClient.prompt()
                .messages(EXAMPLES)      // the examples go before the real ticket
                .user(ticket)
                .call()
                .content();
    }
}

Good examples

Two to five, covering the edge cases, varied in length and style, and correct. The model copies their patterns, mistakes included. If every example is HIGH, expect HIGH.

When to stop adding them

Each example is input tokens on every call. If you need dozens to get the behaviour right, that is the signal to consider fine-tuning.

Reasoning models are differentWith gpt-5, o-series or Claude's adaptive thinking, the model reasons before answering on its own, and the provider bills those hidden tokens. Asking it to "think step by step" in the output only adds cost. Tune the effort setting instead, and keep a reasoning field only when you want an explanation to log or show a reviewer.
