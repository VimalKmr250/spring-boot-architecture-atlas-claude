Any text the model reads can try to give it orders

A model cannot reliably tell your instructions from instructions hidden in the data it reads. Direct injection comes from the user ("ignore your rules"). Indirect injection hides in content the model processes on someone's behalf: a review, a PDF, a web page, an email, a tool result. There is no prompt that fixes this. You contain it with layers, so that a fooled model still cannot do damage.

Layer ② in code: the tool decides, not the model (excerpt)
@Tool(description = "Cancel one of the current customer's orders")
String cancelOrder(@ToolParam(description = "Order id") String orderId,
                   ToolContext ctx) {
    // The customer id comes from the authenticated session, never from the model.
    String customerId = (String) ctx.getContext().get("customerId");
    Order order = orders.findById(orderId)
            .filter(o -> o.customerId().equals(customerId))   // ownership check
            .orElseThrow(() -> new IllegalArgumentException("No such order"));
    return orders.requestCancellation(order);   // creates a pending request a human can see
}

Least privilege

Give each client only the tools its use case needs. A summariser that reads supplier PDFs should have no tool that can send email, so an injected "send this" has nothing to call.

Confirm side effects

For refunds, cancellations and outbound messages, the tool creates a pending action and a person (or the user, in the UI) confirms it.

Check the output

Structured output with enums and ranges, HTML escaping, and a filter for links or image URLs to unknown domains, which are a common way to leak data.

Filters help a little

SafeGuardAdvisor blocks requests containing listed phrases; a moderation model catches abuse. Both are easy to evade, so they are a layer, not the defence.
