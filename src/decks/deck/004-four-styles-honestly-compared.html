The four styles that actually ship

Everything else is a variation. The question is never "which is best" — it is which failure you would rather have: a tangled codebase, or a distributed system you cannot debug.

StyleBoundaries enforced byWins whenBreaks when
Layered monolithConvention only< 8 engineers, one domain, speed beats structureTwo teams edit the same service class daily
Modular monolithCompiler + ArchUnit + Modulith10–60 engineers, one domain, one release trainModules need genuinely different scaling or SLAs
Service-basedNetwork, shared databaseYou need independent scaling before independent dataThe shared schema becomes the coupling everyone fights
MicroservicesNetwork + private data storeMany teams, divergent SLAs, real autonomy neededDomain is still moving, or you lack platform engineering

The default recommendation

Start as a modular monolith with genuinely enforced boundaries. It gives you the one thing microservices cannot: cheap boundary changes. Getting a boundary wrong is normal; getting it wrong across a network costs a quarter.

Extract a service when you can name the reason

  • Scaling: one module needs 20× the instances of the rest.
  • SLA: checkout must stay up while reporting is being redeployed.
  • Team: a team with its own release cadence is blocked by the train.
  • Compliance: PCI or PII scope you want physically isolated.

"It felt too big" is not on this list.
