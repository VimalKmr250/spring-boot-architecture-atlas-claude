One build, one artifact, four environments

The artifact that reaches production is the one that was tested — byte for byte. Anything rebuilt per environment reintroduces the class of bug this rule exists to eliminate.

settings.gradle.kts — modules as Gradle projects, when you want hard walls
rootProject.name = "shop"
include("modules:order", "modules:payment", "modules:inventory",
        "modules:catalog", "modules:shared", "app")

// modules/order/build.gradle.kts
dependencies {
    api(project(":modules:shared"))
    implementation(project(":modules:payment"))   // sees payment's api only
    // a compile error is now impossible to merge, not just discouraged
}

Trade-off: Gradle modules give compiler-enforced boundaries and faster incremental builds, at the cost of more build files and slower IDE indexing. One source set plus ArchUnit is lighter and usually enough; escalate to Gradle modules when the rules keep getting suppressed.

The pipeline

  1. Build + unit + arch tests — under 5 minutes or people stop watching.
  2. Integration — Testcontainers, module tests.
  3. Contract gates — OpenAPI breaking-change check, schema registry compatibility.
  4. Security — dependency scan (CVE), SAST, image scan, license check.
  5. Package once — bootBuildImage, tagged with the commit sha.
  6. Promote the same digest: dev → test → staging → prod.
  7. Deploy rolling or canary; migrate before, expand/contract always.
Deploy ≠ releaseDeploying the artifact and enabling the behaviour are separate events. Deploy continuously; release with a flag. This is what makes a Tuesday-afternoon deploy boring, which is the actual goal.
