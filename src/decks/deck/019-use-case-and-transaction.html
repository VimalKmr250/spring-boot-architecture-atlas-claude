The application service does four things, and no more

Load, invoke the domain, save, publish. Orchestration lives here; rules do not. When a use case grows an if about business meaning, that if belongs on the aggregate.

order/internal/app/PlaceOrderUseCase.java
@Service
@Transactional                                  // the ONE transaction boundary
class PlaceOrderUseCase implements OrderService {

    private final OrderRepository orders;       // port
    private final PricingPort pricing;          // port → pricing module api
    private final ApplicationEventPublisher events;

    @Override
    public OrderId place(PlaceOrderCommand cmd) {
        var quote = pricing.quote(cmd.lines(), cmd.customerId());   // 1. gather
        var order = Order.place(cmd.customerId(), cmd.lines(), quote.total()); // 2. domain decides
        orders.save(order);                                          // 3. persist
        events.publishEvent(OrderPlaced.from(order));                // 4. announce
        return order.id();
    }
}
Do not do this hereif (customer.isVip() && total.gt(500)) discount = ... — that is a pricing rule sitting in an orchestration class, invisible to the domain model and impossible to unit-test without Spring.
Keep the transaction shortNever call an external HTTP API inside @Transactional. A 3-second gateway timeout becomes a 3-second database connection held, and a pool of 20 becomes an outage at 7 concurrent checkouts.
Read paths skip all thisQueries do not need aggregates. @Transactional(readOnly = true) + a JdbcClient projection straight to a record is faster, simpler and perfectly legitimate. CQRS-lite, no framework required.
