The five JPA failures that reach production

Every one of these passes code review and every one of them is found by a load test or an incident. Know the symptom, not just the name.

TrapHow it shows upFix
N+1 selectEndpoint fine with 10 rows, 4 s with 500. 501 queries in the trace.@EntityGraph / join fetch; assert query count in tests with datasource-proxy
LazyInitializationExceptionWorks in the service, 500s in the controller or serializerMap to a DTO inside the transaction. Never open-in-view — set it to false explicitly
Cartesian explosionTwo join fetch on collections returns 10k rows for one orderFetch one collection per query, or use @BatchSize / two queries
Unbounded findAll()Heap dump at 3am when a customer has 40k ordersEvery repository method takes a Pageable or a hard limit. No exceptions
Paging + join fetchLog warning "applying in memory", then OOMPage over IDs, then fetch the entities for that page
application.yaml — the settings that prevent three of the above
spring:
  jpa:
    open-in-view: false            # default is true and it hides N+1s until production
    properties:
      hibernate.jdbc.batch_size: 50
      hibernate.order_inserts: true
      hibernate.order_updates: true
      hibernate.query.fail_on_pagination_over_collection_fetch: true
  datasource:
    hikari:
      maximum-pool-size: 20        # sized, not guessed — see the runtime slide
      leak-detection-threshold: 20000
Make it a test, not a habitAssert the query count on your three hottest endpoints: 
@Test void orderDetail_isOneQuery() {
    var before = queries.count();
    mvc.perform(get("/orders/{id}", id));
    assertThat(queries.count() - before).isLessThanOrEqualTo(2);
}

An N+1 introduced six months later then fails the build instead of the Black Friday dashboard.
