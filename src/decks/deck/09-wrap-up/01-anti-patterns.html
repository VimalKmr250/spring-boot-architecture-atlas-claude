Twelve anti-patterns, and what each one actually costs

Every one of these is common, defensible in the moment, and expensive later. Recognising them by their symptom is more useful than knowing their names.

Anti-patternWhat you seeWhat it costs
Distributed monolithServices that must be deployed together; a change touches four reposMicroservice cost, monolith coupling — the worst square of the grid
Shared database across servicesTwo services, one schema, nobody may change a columnThe schema becomes the coupling; autonomy is zero
Anaemic domainEntities with only getters; 900-line OrderServiceRules duplicated across services and silently diverging
Chatty sync callsOne page render = 14 internal HTTP callsLatency multiplies, availability multiplies down
Retry without idempotencyA retry annotation on a POSTDuplicate charges, duplicate orders, a finance reconciliation project
God gatewayBusiness rules in gateway YAMLUntested, unversioned logic that cannot run locally
Entity as API contract@Entity returned from a controllerSchema changes break clients; lazy-loading errors in serialization
Everything asyncEvents for things the user is waiting onUnreadable flows, and a UI that must explain eight intermediate states
Library sprawlThree JSON libraries, two HTTP clients, two mappersCVE surface, onboarding cost, inconsistent behaviour at boundaries
Config in the artifactEnvironment-specific values baked into the jarRebuild per environment; the tested artifact is not the shipped one
Dogmatic layeringSix mapper classes to read one lookup tableTeam abandons the architecture wholesale because the tax is uniform
Architecture as a documentA wiki page; no test enforces any of itDrift within one quarter, and nobody can tell you when it happened
The pattern behind the patternsNine of these twelve are failures to make the rule executable. Whenever you write down an architectural rule, ask in the same breath: what test, lint, database grant or CI gate makes it true tomorrow?
