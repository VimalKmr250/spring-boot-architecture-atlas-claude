Generate the client; never hand-write a DTO twice

Hand-maintained TypeScript interfaces drift from the Java records within one sprint, and the drift is discovered by a customer. Make the OpenAPI document the single source and generate both sides from it.

Backend: contract published by the build
# springdoc renders it from the controllers at build time,
# then it is committed and diffed in the PR
- task: generateOpenApiDocs        # gradle
  outputFileName: openapi.yaml

# CI gate: fail the build on a breaking change
- run: oasdiff breaking main/openapi.yaml openapi.yaml --fail-on ERR
Frontend: client regenerated on every build
- run: npx @openapitools/openapi-generator-cli generate \
        -i ../api/openapi.yaml -g typescript-angular \
        -o src/app/api --additional-properties=useSingleRequestParameter=true
# src/app/api is .gitignore'd and rebuilt — it cannot drift

What this buys you

  • Renaming a field in Java breaks the frontend compile, in CI, before merge.
  • The oasdiff gate turns "is this a breaking change?" from a judgement call into a build result.
  • New endpoints appear in the frontend with types and no ticket.

Design-first vs code-first

Code-first (annotations → spec) is faster and what most Spring teams do; the risk is a spec that documents whatever the code happened to do.

Design-first (spec → stubs) is right when an external party or another team consumes the API and the contract must be agreed before either side builds. Use it for partner APIs, code-first internally.

Contract tests for the async sideOpenAPI covers HTTP. Kafka events need the same treatment: register Avro/JSON schemas, set compatibility to BACKWARD, and let the registry reject an incompatible producer at deploy time.
