Delivery: the parts users actually feel

Enterprise frontends are rarely slow because of framework choice. They are slow because of bundle discipline, waterfalls and cache headers — all of which are architecture decisions, not tuning.

Caching strategy, in two lines of config

/index.html        Cache-Control: no-cache          # always revalidated
/*.[contenthash].js Cache-Control: public, max-age=31536000, immutable

Hashed assets are immutable and cached for a year; the tiny HTML entry point is revalidated on every load. A deploy is then instantly live with zero stale-bundle incidents.

Kill the waterfall

The classic enterprise pattern — load shell, then call /me, then call /permissions, then call the page data — costs four sequential round trips before anything renders. On a 200 ms RTT that is 800 ms of blank screen.

Fix: the BFF returns bootstrap data with the first request, and route resolvers fire in parallel.

Budgets, enforced in CI

"budgets": [
  { "type": "initial", "maximumError": "500kb" },
  { "type": "anyComponentStyle", "maximumError": "8kb" }
]

A budget that fails the build is the only thing that stops gradual bundle creep. Add a Lighthouse CI check on the three routes that matter.

What to measure

LCP
largest content painted — target < 2.5 s at p75, on real user data
INP
responsiveness to interaction — < 200 ms; where heavy tables fail
CLS
layout shift — reserve space for images and async content
TTFB
your BFF's p95; the part your backend actually controls

Collect from real users (RUM), not only from lab runs on a developer laptop.

Accessibility is not a phaseIn enterprise procurement it is a contractual requirement (WCAG 2.2 AA, VPAT). Retrofitting it into a finished component library costs several times what building it in does: keyboard paths, focus management on route change, labelled controls, live regions for async results, and contrast that survives your dark theme.
