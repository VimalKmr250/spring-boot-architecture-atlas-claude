Spring Modulith: the boundary, documented and tested

Spring Modulith (2.x, current on Boot 4) makes the module a first-class concept: it derives the module graph from your package structure, verifies it, generates documentation, and gives per-module integration tests.

order/package-info.java — declaring the module and its exports
@ApplicationModule(
    displayName = "Order Management",
    allowedDependencies = { "payment :: api", "inventory :: api", "shared" }
)
package com.retailco.shop.order;

// order/api/package-info.java
@NamedInterface("api")
package com.retailco.shop.order.api;
ModularityTest.java — verification + docs in four lines
class ModularityTest {
    static final ApplicationModules modules =
            ApplicationModules.of(ShopApplication.class);

    @Test void verifiesModuleStructure() {
        modules.verify();          // fails the build on an illegal dependency
    }

    @Test void writesDocumentation() {
        new Documenter(modules)
            .writeModulesAsPlantUml()      // C4 component diagram, per module
            .writeIndividualModulesAsPlantUml()
            .writeModuleCanvases();        // exports, events, dependencies, beans
    }
}

Slice tests you can actually run

@ApplicationModuleTest boots one module, so the order module's tests start in ~2 s instead of booting eight modules and Kafka. It does not stub the others for you — an unmocked bean reference across a module boundary fails the bootstrap, and you supply the mock yourself.

// modes: STANDALONE (default) · DIRECT_DEPENDENCIES · ALL_DEPENDENCIES
@ApplicationModuleTest                      // = STANDALONE: this module only
class OrderModuleTests {

    @MockitoBean PaymentService payments;   // YOU stub the neighbours

    @Test void placesOrder(Scenario scenario) {
        scenario.stimulate(() -> orders.place(cmd))
                .andWaitForEventOfType(OrderPlaced.class)
                .toArriveAndVerify(e -> assertThat(e.orderId()).isNotNull());
    }
}

What it does not do

  • It will not invent boundaries — you still do the domain work.
  • It does not stop cross-schema SQL; that needs a database-level rule or a migration review.
  • Adopting it on a tangled codebase means a long list of violations on day one. Baseline them, then ratchet down.

Pair it with the ArchUnit rules on the previous slide — Modulith owns module-to-module, ArchUnit owns inside-the-module.
