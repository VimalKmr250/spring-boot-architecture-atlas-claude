One schema per module, one owner per table

Code boundaries that are not matched by data boundaries are decorative. The shared table is what actually prevents extraction, and it is invisible in every architecture diagram.

Enforced by the database, not by agreement
CREATE SCHEMA order_mgmt;   CREATE SCHEMA payment;   CREATE SCHEMA inventory;

-- each module connects with its own role
CREATE ROLE app_order LOGIN;
GRANT USAGE ON SCHEMA order_mgmt TO app_order;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA order_mgmt TO app_order;
-- and is granted NOTHING on payment.* or inventory.*

-- a cross-schema join is now a runtime permission error in CI, not a review comment
SELECT o.id, p.status
  FROM order_mgmt.orders o JOIN payment.payments p ON p.order_id = o.id;
-- ERROR: permission denied for schema payment

One PostgreSQL cluster, one connection pool per module role. You keep operational simplicity — one backup, one failover, one upgrade — while the logical boundary is real.

"But I need order + payment data together"

  • For a screen: call both modules' APIs and compose in the application or the BFF.
  • For a list view: keep a denormalised read model, updated by events (next slide but one).
  • For reporting: that is not OLTP's job — replicate to a warehouse.

Each of these costs something. The join costs more, later, and all at once.

Duplication is not a smell hereThe inventory module storing a copy of the product name it needs is not a normalisation failure — it is a bounded context holding the view of the product that it cares about. Foreign keys across contexts are the actual smell.
Migration gateMake every migration touching a schema require review from that schema's owning team, via CODEOWNERS on db/migration/<module>/. It is the cheapest boundary control you will ever install.
