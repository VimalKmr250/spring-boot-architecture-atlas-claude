Configuration: typed, externalised, never in the jar

The same artifact must run in every environment. Anything that differs between environments is configuration; anything secret is a secret, and the two get handled differently.

Typed configuration — validated at startup, not at first use
@ConfigurationProperties("shop.payment")
@Validated
public record PaymentProperties(
        @NotNull URI gatewayBaseUrl,
        @NotBlank String merchantId,
        @DurationMin(millis = 100) @DurationMax(seconds = 5) Duration readTimeout,
        @Min(1) @Max(5) int maxRetries) { }

// A typo in the YAML fails the context at boot with a precise message,
// rather than a NullPointerException at 2 a.m. on the first live payment.
Layering — later wins, and the jar is the weakest
1. application.yaml in the jar          # safe defaults only
2. application-{profile}.yaml           # shape per environment, no secrets
3. ConfigMap / Config Server            # per-environment values
4. Vault / cloud secret manager         # credentials, injected at runtime
5. Environment variables                # final override, used by the platform
NeverSecrets in application.yaml, in the image, or in the repo — including "just the test one". Test credentials become production credentials somewhere, and a repo scan will find them years later.
Rotation is the real requirementA secret you cannot rotate without a deploy is not managed. Use short-lived, dynamically issued credentials (Vault database secrets, cloud IAM roles) so rotation is routine rather than an incident.

Feature flags belong here too

Flags decouple deploy from release: ship the new pricing engine dark, enable it for internal users, then 1%, then all. They are also your fastest rollback — faster than any redeploy.

Add an expiry date to every flag and a ticket to remove it. A four-year-old flag with three stale branches behind it is technical debt with a UI.
