The repository port, and the JPA adapter behind it

The domain gets an interface in its own vocabulary. Spring Data lives on the other side of it, where its magic cannot leak into business code.

internal/domain/OrderRepository.java — the port
public interface OrderRepository {
    void save(Order order);
    Optional<Order> findById(OrderId id);
    List<Order> findOpenFor(CustomerId customer);
}
internal/jpa/OrderRepositoryAdapter.java — the adapter
@Repository
class OrderRepositoryAdapter implements OrderRepository {

    private final OrderJpaRepository jpa;      // Spring Data, package-private
    private final OrderMapper mapper;          // MapStruct

    @Override public void save(Order order) {
        jpa.save(mapper.toEntity(order));
    }

    @Override public Optional<Order> findById(OrderId id) {
        return jpa.findWithLinesById(id.value()).map(mapper.toDomain());
    }
}

interface OrderJpaRepository extends JpaRepository<OrderJpaEntity, UUID> {
    @EntityGraph(attributePaths = "lines")     // kills the N+1 at the source
    Optional<OrderJpaEntity> findWithLinesById(UUID id);
}

When to skip the mapping

This costs one mapper per aggregate. It is worth it where the domain model and the table shape genuinely differ — which is most places where real rules live. For a lookup table, use the entity directly and move on; architecture that charges the same tax everywhere gets abandoned.

JPA

JdbcClient

jOOQ
