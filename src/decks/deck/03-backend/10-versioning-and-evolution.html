Evolve the API without a v2 rewrite

Spring Framework 7 made API versioning first-class on both server and client. But the version you never have to cut is cheaper than the one you route perfectly.

Spring 7 / Boot 4 — version-aware mappings
@Configuration
class ApiVersionConfig implements WebMvcConfigurer {
    @Override public void configureApiVersioning(ApiVersionConfigurer c) {
        c.useRequestHeader("X-API-Version")
         .addSupportedVersions("1", "2")
         .setDefaultVersion("1");
    }
}

@RestController
@RequestMapping("/api/orders")
class OrderController {

    @GetMapping(value = "/{id}", version = "1")
    OrderViewV1 getV1(@PathVariable UUID id) { ... }

    @GetMapping(value = "/{id}", version = "2")     // v2 splits address into a nested object
    OrderViewV2 getV2(@PathVariable UUID id) { ... }
}

The compatibility rules that avoid versions entirely

  • Additive only: new optional fields, never a removed or renamed one.
  • Never repurpose a field. status gaining a new enum value breaks every client with an exhaustive switch — add statusV2 or document the open set from day one.
  • Tolerant reader on every consumer: ignore unknown fields (FAIL_ON_UNKNOWN_PROPERTIES=false).
  • Expand / contract for breaking changes: add the new field, dual-write, migrate clients, then remove — three releases, zero downtime.
Version in the header or the path?Path (/v2/orders) is obvious in logs, gateways and curl, and is what most enterprises pick. Header is cleaner REST and what Spring 7 optimises for. Either works; having three schemes across eight teams does not. Decide once, in a standard.
Deprecation with teethShip Deprecation and Sunset headers, emit a metric tagged by client id and version, and mail the top consumers. Without usage data, no version is ever removed and you maintain v1 forever.
