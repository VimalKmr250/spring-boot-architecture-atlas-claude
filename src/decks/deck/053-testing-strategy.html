A test pyramid shaped like your architecture

The mistake is uniform testing: everything through @SpringBootTest, or everything mocked. Match the test type to the layer, and the suite stays fast and meaningful.

Testcontainers, shared and fast — Boot 4 service connections
import org.testcontainers.kafka.KafkaContainer;  // NOT ...containers.KafkaContainer

@TestConfiguration(proxyBeanMethods = false)
class ContainersConfig {
    @Bean @ServiceConnection            // wires spring.datasource.* automatically
    PostgreSQLContainer<?> postgres() {
        return new PostgreSQLContainer<>("postgres:17-alpine").withReuse(true);
    }
    @Bean @ServiceConnection
    KafkaContainer kafka() {
        return new KafkaContainer("apache/kafka:4.0.0").withReuse(true);
    }
}
// Two classes share the simple name KafkaContainer:
//   org.testcontainers.kafka.KafkaContainer      → apache/kafka (KRaft)
//   org.testcontainers.containers.KafkaContainer → confluentinc/cp-kafka
// Pair the wrong one with your image and startup hangs until it times out.

// src/test: one container per build, reused across every test class
@SpringBootTest
@Import(ContainersConfig.class)
class OrderFlowIT { ... }
H2 is not your databaseTesting against H2 while running PostgreSQL means your tests pass on SQL that production rejects — and silently skip the constraints, types and locking behaviour that matter. Testcontainers removed this excuse years ago.
Architecture tests are testsThe ArchUnit rules from slide 8 and modules.verify() from slide 9 run in the same suite. That is what makes the boundary real rather than aspirational.
