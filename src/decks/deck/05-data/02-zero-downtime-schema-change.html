Expand and contract: renaming a column with no outage

During a rolling deploy, old and new code run at the same time against one schema. Every migration must therefore be compatible with the version before it — which rules out the one-step rename entirely.

ReleaseMigrationApplication codeSafe because
R1 · expandALTER TABLE orders ADD COLUMN total_minor bigint NULL;Writes both total and total_minor; reads totalNew column is nullable; old pods ignore it
R1.5 · backfillBatched UPDATE ... WHERE total_minor IS NULL LIMIT 10000unchangedBatched, so no long lock on a 40M-row table
R2 · switch—Reads total_minor, still writes bothData is complete in both columns
R3 · contractALTER TABLE orders DROP COLUMN total;Writes and reads total_minor onlyNo running version references the old column

Flyway discipline that prevents 3am calls

  • Migrations are append-only and immutable once merged — validate-on-migrate on, always.
  • Never DROP in the same release that stops using something.
  • CREATE INDEX CONCURRENTLY on any table above a million rows — and it needs its own migration file with -- flyway:executeInTransaction=false, because Flyway wraps a migration in a transaction and Postgres refuses CONCURRENTLY inside one.
  • Adding a NOT NULL column with a default rewrites the table on old engines — add nullable, backfill, then constrain.
  • Set lock_timeout and statement_timeout on the migration role so a blocked DDL fails in seconds instead of queueing every query behind it.
V2026_09_03__add_total_minor.sql — transactional, as normal
SET lock_timeout = '3s';
ALTER TABLE order_mgmt.orders ADD COLUMN total_minor bigint;
V2026_09_04__index_orders_customer.sql — must NOT be in a transaction
-- flyway:executeInTransaction=false
CREATE INDEX CONCURRENTLY idx_orders_customer_placed
    ON order_mgmt.orders (customer_id, placed_at DESC);
-- CONCURRENTLY can leave an INVALID index if it fails; check
-- pg_index.indisvalid afterwards and DROP/recreate if needed.
The rollback questionInterviewers and incident reviews both ask it: you do not roll a migration back, you roll forward. Which is why expand/contract matters — at every intermediate point, the previous application version still works, so the deployment can be rolled back even though the schema cannot.
