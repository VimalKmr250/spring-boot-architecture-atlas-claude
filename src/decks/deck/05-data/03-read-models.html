CQRS without the ceremony

Full CQRS with event sourcing is rarely justified. Separating the read path from the write path almost always is — and it costs one class, not an architecture.

The read path: no entities, no mapping, one query
@Transactional(readOnly = true)
public List<OrderSummary> search(OrderSearch f, Pageable page) {
    return jdbc.sql("""
            SELECT o.id, o.placed_at, o.status, o.total_minor, o.currency,
                   o.line_count, o.customer_display_name
              FROM order_mgmt.order_summary o
             WHERE o.customer_id = :customer
               AND (:status::text IS NULL OR o.status = :status)
             ORDER BY o.placed_at DESC
             LIMIT :limit OFFSET :offset
            """)
        .param("customer", f.customerId()).param("status", f.status())
        .param("limit", page.getPageSize()).param("offset", page.getOffset())
        .query(OrderSummary.class)     // record, mapped by column name
        .list();                       // → List, not Page
}

// A Page needs a total, which is a SECOND query — so only ask for one
// when the UI actually renders "page 4 of 87":
public Page<OrderSummary> searchPaged(OrderSearch f, Pageable page) {
    var rows = search(f, page);
    return PageableExecutionUtils.getPage(rows, page, () -> countMatching(f));
}   // the supplier is skipped when the result obviously fits one page

Why order_summary exists

It is a denormalised table maintained by event listeners — it already contains the customer's display name and the line count, so the order-history screen is one index scan instead of three joins across two schemas that the boundaries forbid anyway.

Cost: eventual consistency of a second or two, and a rebuild job. Benefit: the p99 on your most-hit screen drops by an order of magnitude and stops depending on other modules.

Make rebuild a first-class featureEvery projection needs a documented, tested "replay from scratch" path. You will need it — after a bug, after a schema change, and the first time someone asks for a field you did not project.
Where the line isUse a read model when the query is hot, cross-module, or awkward. Do not project everything: each projection is a second source of truth that can drift, and drift is discovered by customers.
