Security: the filter chain, then the method, then the row

Three layers, each catching what the one above cannot. Authorisation at only one of them is how data leaks between customers.

Layer 1 · the filter chain — who are you, broadly what may you reach
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/api/**")
        .authorizeHttpRequests(a -> a
            .requestMatchers(GET, "/api/products/**").permitAll()
            .requestMatchers("/api/admin/**").hasRole("OPS")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(rolesConverter())))
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .csrf(CsrfConfigurer::disable)          // stateless bearer API; the BFF keeps CSRF ON
        .headers(h -> h.contentSecurityPolicy(c -> c.policyDirectives(
             "default-src 'self'; frame-ancestors 'none'")))
        .build();
}
Layer 2 · method security — may you do this to this thing
// CustomerId is a value type, so unwrap it — comparing the record
// itself to a String is always false, and fails OPEN-looking (denies
// everyone but the OPS role, so nobody notices until a customer calls).
@PreAuthorize("hasRole('OPS') or #command.customerId.value() == authentication.name")
public void cancel(CancelOrderCommand command) { ... }

@PostAuthorize("returnObject.customerId.value() == authentication.name")
public OrderView find(OrderId id) { ... }

// Past one `or`, move it into a bean you can unit-test:
@PreAuthorize("@orderAccess.mayCancel(#command, authentication)")
public void cancel(CancelOrderCommand command) { ... }

Layer 3 · the row

The layer most teams skip. A bug in a repository method that forgets WHERE customer_id = ? returns other customers' orders with a perfectly valid token.

// tenant/customer scoping applied centrally, not per query
@Entity
@FilterDef(name = "tenant", parameters = @ParamDef(name = "tenantId", type = String.class))
@Filter(name = "tenant", condition = "tenant_id = :tenantId")
class OrderJpaEntity { ... }

@Component
class TenantFilterActivator {
    @PersistenceContext EntityManager em;

    void activate() {   // called once per request, from an interceptor
        em.unwrap(Session.class)
          .enableFilter("tenant")
          .setParameter("tenantId", TenantContext.current());
    }
}

Or, for real isolation, PostgreSQL row-level security — the database enforces it even when the ORM is bypassed.

Multi-tenancy: pick deliberatelyShared schema + tenant column — cheapest, needs RLS discipline. Schema per tenant — good isolation, migrations across 500 schemas get slow. Database per tenant — strongest, viable only with tens of tenants. Enterprise default is shared schema with RLS; regulated customers buy the database.
Audit is a featureWho changed what, when, from where — with the trace id. Append-only, its own schema, read-only role for auditors. Retrofitting it after an incident or an audit finding is far more expensive than adding it in week two.
