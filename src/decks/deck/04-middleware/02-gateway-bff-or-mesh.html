Gateway, BFF, service mesh — three different jobs

These get conflated constantly. They solve non-overlapping problems and most enterprises eventually run all three, with clear rules about what may live in each.

API gatewayBFFService mesh
Traffic it handlesNorth–south (outside → in)North–south, one client typeEast–west (service → service)
Owned byPlatformThe frontend team that consumes itPlatform / infra
Legitimately containsAuth, rate limits, routing, TLS, request logging, CORSResponse shaping, aggregation, session cookies, client-specific cachingmTLS, retries, timeouts, traffic shifting, telemetry
Must never containBusiness rules or domain lookupsWrites to the database, domain invariantsAnything application-aware
Typical toolSpring Cloud Gateway, Kong, APIMA small Spring Boot or Node app per clientIstio, Linkerd
Skip it whenNever, past two servicesOne client, and the API already fits itYou have fewer than ~10 services
The BFF's real payoffOne mobile screen needing six calls over a 300 ms mobile RTT becomes one call with one round trip. The BFF also owns the cookie-based session, which is what keeps access tokens out of browser storage entirely — see the auth slide.
Gateway sprawlThe moment someone adds "if customer is gold tier, route to…" to gateway config, you have business logic in YAML with no tests, no local run and no code review culture. Push it back into the application, every time.
