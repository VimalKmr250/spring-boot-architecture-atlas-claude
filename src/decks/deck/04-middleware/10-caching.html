Two cache layers, and an invalidation story

Caching is easy; knowing when the cached value is wrong is the whole engineering problem. Decide the staleness budget per use case before choosing a mechanism.

Near cache (Caffeine) in front of a distributed cache (Redis)
@Service
class CatalogQueryService {

    @Cacheable(cacheNames = "product", key = "#sku", cacheManager = "twoLevel")
    public ProductView byKey(String sku) { return repo.load(sku); }

    // invalidation is an EVENT, not a scheduled job
    @ApplicationModuleListener
    void on(ProductUpdated e) {
        cache.evict("product", e.sku());                 // local
        redis.convertAndSend("cache.evict", e.sku());    // tell the other 11 instances
    }
}
# "twoLevel" is YOUR CacheManager bean (Caffeine in front of Redis).
# spring.cache.caffeine.spec configures Boot's AUTO-CONFIGURED manager,
# so a custom manager must read the spec itself — or keep the L1 spec
# in your own @ConfigurationProperties. They are not wired together.
shop.cache.l1.spec: maximumSize=10000,expireAfterWrite=60s
# L1 Caffeine: ~100 ns, per instance, may be 60 s stale
# L2 Redis:    ~1 ms, shared, TTL 10 min, invalidated by event

Three classic failuresStampede: a hot key expires and 500 threads hit the database — use @Cacheable(sync = true) or a short lock. Penetration: lookups for ids that do not exist bypass the cache every time — cache the negative result briefly. Avalanche: everything expires at the same second — add jitter to TTLs.
