Facade: one simple entry point in front of several collaborating services

Booking a ticket touches seat inventory, payments and email, in a set order, with a compensating step when payment fails. Callers should not have to know that sequence. A facade offers one method, book(user, seats), and keeps the choreography in one place. The subsystems stay public for callers who need more control.

FacadeDemo.java · hold, charge, then confirm or release
import java.util.*;

final class SeatInventory {
    private final Map<String, String> holds = new TreeMap<>();  // seat -> user
    private final Set<String> sold = new TreeSet<>();
    boolean hold(String user, List<String> seats) {
        for (String s : seats)
            if (sold.contains(s) || holds.containsKey(s)) return false;
        seats.forEach(s -> holds.put(s, user));
        return true;
    }
    void confirm(List<String> seats) {
        seats.forEach(s -> { holds.remove(s); sold.add(s); });
    }
    void release(List<String> seats) { seats.forEach(holds::remove); }
    String state() { return "sold " + sold + ", held " + holds.keySet(); }
}

final class Payments {
    boolean charge(String user, long amount) { return !user.equals("bob"); }
}

final class Mailer {
    final List<String> sent = new ArrayList<>();
    void ticket(String user, List<String> seats) { sent.add(user + " " + seats); }
}

final class BookingFacade {
    private static final long PRICE = 250;
    private final SeatInventory inventory;
    private final Payments payments;
    private final Mailer mailer;
    BookingFacade(SeatInventory i, Payments p, Mailer m) {
        inventory = i; payments = p; mailer = m;
    }

    String book(String user, List<String> seats) {
        if (!inventory.hold(user, seats))
            return user + ": seats unavailable";
        if (!payments.charge(user, PRICE * seats.size())) {
            inventory.release(seats);                 // compensate
            return user + ": payment declined, seats released";
        }
        inventory.confirm(seats);
        mailer.ticket(user, seats);
        return user + ": booked " + seats;
    }
}

public class FacadeDemo {
    public static void main(String[] args) {
        var inventory = new SeatInventory();
        var mailer = new Mailer();
        var booking = new BookingFacade(inventory, new Payments(), mailer);

        System.out.println(booking.book("ana", List.of("A1", "A2")));
        System.out.println(booking.book("bob", List.of("B1")));
        System.out.println(booking.book("cy", List.of("A2", "A3")));
        System.out.println(booking.book("cy", List.of("A3", "B1")));
        System.out.println(inventory.state());
        System.out.println("emails: " + mailer.sent);
    }
}

Facade or god class?A facade coordinates; it does not decide. Seat rules stay in SeatInventory and the charge in Payments. If the facade starts computing prices and checking seat adjacency, it has become the god class the pattern was meant to prevent.
It is the service layerIn LLD answers the facade is usually the application service (BookingService, ParkingLotService): the one class the demo's main talks to. Name it after the use case, not after the pattern.
