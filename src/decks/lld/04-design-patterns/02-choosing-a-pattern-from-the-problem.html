Start from the symptom in the requirements, never from the pattern

Interviewers mark down "I'll use the factory, strategy and observer patterns" said in the first minute, before any requirement justifies them. Mark them up for "pricing varies by lot and may change, so it goes behind an interface; that is the strategy pattern". The pattern name comes last, as a label for a decision you already made.

When the requirement says…Reach forSeen in
"The rule may differ", "pricing depends on…", "support several algorithms"StrategyParking fees, split types, elevator scheduling, seat pricing
"It behaves differently when it is…", a status field checked in every methodStateATM, vending machine, booking lifecycle, elevator
"Notify", "when X happens, update Y and Z"ObserverDisplays, reservation alerts, waiting lists
"Undo", "replay", "queue the request", "audit every action"CommandChess moves, editor, ATM transaction log
"Create the right kind of X from input"Factory method, or a static factoryVehicles, pieces, notifiers, splits
Many optional fields; an object that must be valid once builtBuilderSearch queries, bookings, test fixtures
"Integrate with the vendor's library"AdapterPayment gateways, SMS providers
Add-ons that stack: "plus a discount, plus logging, plus retry"DecoratorPricing rules, notifier retry, I/O streams
"Try each handler until one accepts", approval levelsChain of responsibilityATM note dispensing, request validation, expense approval
A part-whole tree that should be treated uniformlyCompositeFile systems, menus, group expenses
"One entry point for the client" over several servicesFacadeBooking service over seats, payments and notifications
Pattern-itisA VehicleFactoryFactory, an observer with one listener that will never have a second, a strategy interface with one implementation. Each adds a class and an indirection, and buys nothing. If you cannot name the second implementation, leave the interface out.
Lambdas are patterns tooIn modern Java a strategy with one method is often just a Function or a custom functional interface filled by a lambda. The same goes for commands (Runnable) and observers (Consumer). Give the interface a domain name when it carries domain meaning, such as PricingStrategy.
