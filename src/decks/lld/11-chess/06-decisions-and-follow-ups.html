Chess: the choices to defend, and where the missing rules would go

The chess follow-ups are almost all rules that depend on history (castling, en passant, repetition), which the stateless pieces cannot see. The answer is always the same: the game, which owns the history, adds those moves to the candidate list, and the check-by-simulation filter keeps working unchanged.

DecisionWhy, and the alternative
Pieces generate, the game filtersOne rule for check covers every piece and every pin. Encoding check in each piece duplicates it six times, and gets pins wrong.
Legality by apply-test-undoSimple and obviously correct. An engine would compute pins and attack maps instead, and be much faster.
Sealed Piece hierarchySix types fixed by the rules. Inheritance is right here: each piece really is a piece, and the loops really are shared.
Status derived, not storedRecomputed after every move and undo, so it cannot drift from the board.
Undo by reversalEach move stores the captured and placed piece. Cheaper than copying the board, but every new move type needs a correct undo.
Exceptions for illegal movesThe UI shows the reason. For an AI searching millions of moves, legalMoves is the API, and exceptions never occur.
Castling, the classic follow-upCastling needs four facts: the king and that rook have never moved, the squares between them are empty, the king is not in check, and it does not pass through or land on an attacked square. The first fact is history, so Game keeps a set of squares whose piece has moved (or checks history). legalMoves adds castling candidates when all four hold. A Castle move moves two pieces, so Move becomes a sealed interface with Simple, Castle and EnPassant records, each with its own apply and undo.
Follow-upWhat changes
En passantAllowed only immediately after an enemy pawn's two-square move, so Game reads the last move in history. An EnPassant move captures on a square other than its target, so it needs its own undo.
Choose the promotion piecemove(from, to, promoteTo); legalMoves generates four moves per promoting pawn.
Draw by threefold repetitionHash each position after a move (the board, the side to move, castling and en passant rights) and count repeats in a map. Undo decrements.
Players, clocks, resignationA Player with a Clock; the game switches clocks on each move. Resignation and timeout set a result without a board reason.
Save and loadMoves in standard notation (PGN) replay the game; a position string (FEN) restores a board. Board.fromRows is most of a FEN parser already.
Online playThe Game becomes the server's authority; clients send moves, the server validates and broadcasts. A version number on the game rejects moves made against a stale board.
A computer opponentA MoveChooser strategy: random, then minimax over legalMoves using apply and undo. The model needs no changes, which is the payoff for keeping the command's undo exact.
