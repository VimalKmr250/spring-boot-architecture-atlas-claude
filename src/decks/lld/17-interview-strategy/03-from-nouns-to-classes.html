From nouns to classes: underline the nouns, then throw half of them away

Noun extraction is the classic technique: the nouns in the requirements are candidate classes and the verbs are candidate methods. The skill is in the filtering. Some nouns are attributes, some are actors outside the system, some are the same thing under two names, and some are values that deserve a record rather than a class.

A noun that is…BecomesExample
A thing with identity and changing stateA class (an entity)ParkingSpot, Copy, Booking
A value, equal by its fieldsA recordPosition, Money, Ticket
A fixed set of options with dataAn enumVehicleType, Tier, SeatCategory
A rule that variesAn interface with implementationsPricingStrategy, Dispatcher
A property of something elseA fieldcolour, licence plate, due date
A person or system outsideA caller, not a classattendant, gate, librarian
A process, not a thingA method, or a service class"checkout", "settlement"

Then assign every verb to one class

  • Information expert: give the method to the class that holds the data it needs. "Does it fit?" goes on the spot.
  • Creator: the class that contains a thing creates it. The floor creates its spots.
  • Controller: each use case enters through a thin service method that coordinates.
  • If a verb needs data from three classes, it goes in the service, and the three classes each answer one question.
CRC cards, in your headFor each class, one line: its Class name, its Responsibilities, and its Collaborators. If a class has no responsibility beyond holding fields, merge it or make it a record. If it has more than three, split it. It takes thirty seconds per class and prevents the god class.
The anaemic modelClasses with only getters and setters, and a Manager that does everything with them, is the most common LLD failure. Interviewers read it as procedural code in class-shaped files. Behaviour belongs next to its data.
