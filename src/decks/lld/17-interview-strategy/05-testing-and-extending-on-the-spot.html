Testing and extending on the spot: prove it works, then show it bends

Before the interviewer asks, run your code or walk it through: the main flow, then the edges. Then the change request arrives. Treat it as the real test of the design. Say which classes change before touching the keyboard; if the answer is "one new class and one line in the factory", say that too, because it is the point of the whole exercise.

Edge cases worth one line each

  • Empty and full: no spots left; nothing to undo; an empty waiting list.
  • Twice: the same ticket redeemed twice; the same plate entering twice; a double click on "book".
  • Boundaries: exactly one hour; exactly at heldUntil; an amount of zero.
  • Rounding: ₹100 split three ways; a percentage that does not divide.
  • Order: cancel after confirm; return a copy that is not on loan.
  • Concurrency: two threads on the last spot or seat.
A concurrency test worth writing, in JUnit 5
@Test
void onlyOneOfManyUsersHoldsTheLastSeat() throws Exception {
    var service = new BookingService(pricing, fakeGateway, fixedClock);
    var winners = new AtomicInteger();
    try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < 100; i++) {
            String user = "u" + i;
            pool.submit(() -> service.hold(user, show, List.of("B1"))
                                     .ifPresent(b -> winners.incrementAndGet()));
        }
    }
    assertEquals(1, winners.get());          // an invariant, not a schedule
}
The change requestA good first sentence
"Add a new vehicle type""One enum constant; the allocation loop and pricing map already handle it."
"Weekend pricing""A new PricingStrategy, or a decorator around the hourly one. Nothing else changes."
"Make it thread-safe""The shared state is the free lists; the invariant is one vehicle per spot; I'll make claim atomic per floor."
"Notify users when…""The domain publishes an event; a notifier subscribes. The domain doesn't learn about email."
"Persist it""Maps become repositories behind interfaces; check-then-act becomes a conditional update."
"Add undo""Actions become command objects that know how to reverse themselves."
When the change does not fitSometimes the request cuts across your design. Say so plainly: "This touches three classes, because I modelled X as Y. With this requirement I'd restructure like this." Recognising a design limit calmly scores better than forcing the change in.
