Writing the code live: inside out, compiling as you go, talking the whole time

Write in the order things depend on each other: values and enums, then entities with their rules, then interfaces, then the service, then the demo. Each layer compiles on its own, so if time runs out you have a working model rather than a service that calls methods you never wrote.

Habits that score

  • Names from the domain. claim, release, heldUntil, not process, handle, data.
  • Fields private and final where possible; no setters for state with rules.
  • Validate at the boundary, in constructors and service entry points, then trust the data inside.
  • Small methods. A method longer than the screen is hiding a class.
  • Inject time and ids. Clock, id generators: tests and demos stay deterministic.
  • Exceptions with messages the caller could show a user: "A4 is held", not "error".
Narrate decisions, not keystrokes"I'm making the ticket a record because it never changes after issue." "This lock is per floor so gates on different floors don't wait." One sentence per decision. Silence reads as stuck; typing commentary ("now I'm writing a for loop") reads as filler.
Stubs are allowed; say soIf the payment gateway would take five minutes, write the interface and a one-line fake, and say "the real one is an adapter over the vendor's SDK". Interviewers want the seam, not the HTTP client.
