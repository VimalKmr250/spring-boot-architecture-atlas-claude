Three principle questions that open many LLD rounds

These twelve questions are the conceptual ones that come up around a design problem, before it or as follow-ups. Each has a 30-second answer to give first and a go deeper paragraph for the follow-up. The links go to the slides that cover the topic; the browser's Back button returns you here.

How to practise with theseRead the question, look away, and answer out loud for thirty seconds with an example from one of the seven problems. Then compare. An answer with a concrete class name in it ("the ticket keeps the pricing strategy") is worth more than a textbook definition.
Q1

Composition or inheritance: how do you choose?

30-second answerDefault to composition: hold the collaborator as a field behind an interface, so it can be swapped at runtime and tested with a fake. Use inheritance only for a genuine "is-a" inside code you control, where the parent was designed to be extended, such as chess pieces sharing a move-generation loop. Inheriting just to reuse code couples you to the parent's implementation.

Go deeper: Give the classic failure. A HashSet subclass that counts additions in both add and addAll double-counts, because addAll calls add internally, a detail the subclass never agreed to. A wrapper does not have the problem. Then say where inheritance is right: a sealed hierarchy where the loop is shared and only the data differs, as with sliding and stepping pieces.

Q2

What does the open/closed principle mean in practice?

30-second answerWhen a change you expected arrives, you add a class instead of editing working code. In practice that means an interface at each point the requirements say will vary: a new pricing rule is a new PricingStrategy, not another case in a switch. You cannot be closed against every change, so choose the seams from the requirements and say which ones you chose.

Go deeper: Be honest that one place still changes: whatever picks the strategy, whether a factory, configuration or main. OCP moves change to where it is cheap. Then give the other axis. If the types are fixed and the operations grow, a sealed type with an exhaustive switch is closed in a different way, because the compiler finds every switch that needs a new case.

Q3

Interface or abstract class, in modern Java?

30-second answerAn interface is the default for a point of variation: a class can implement several, and default methods cover small shared helpers. Choose an abstract class when subtypes share state or a fixed algorithm with steps to fill in, which is the template method pattern. Choose a sealed interface when the set of implementations is closed and you want exhaustive switches.

Go deeper: Name the constraints. Interfaces cannot hold instance state or constructors; abstract classes can, but a class extends only one. Since Java 8 the gap is smaller, so the question is really about state and about who may implement it. Records implement interfaces but cannot extend classes, which pushes value types towards interfaces.
