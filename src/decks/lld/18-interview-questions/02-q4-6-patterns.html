Three pattern questions, each really about telling two things apart

Pattern questions are rarely "define X". They are "how is X different from Y", or "should you use X at all". The answers turn on intent: who creates the object, who changes it, and why.

Q4

What is the difference between the strategy and state patterns?

30-second answerThey have the same structure: a context delegating to an interface. A strategy is chosen from outside and stays until someone swaps it; it answers "how do I do this job?" A state is replaced by the state itself as events arrive; each handler returns the next state, so the transitions are part of the design. Pricing is a strategy; the ATM's idle, card-inserted and authenticated are states.

Go deeper: Mention the smell each one removes. Strategy removes a switch on a configuration value; state removes a switch on a status field repeated in every method. Then say when not to bother: with three states and two events, an enum and one switch is clearer. State classes pay off when states carry their own data, like the ATM's PIN attempt counter, which lives and dies with CardInserted.

Q5

Write a thread-safe singleton. Should you use one?

30-second answerThe simplest safe singleton is an enum with one constant: thread-safe, lazy enough, and immune to reflection and serialization. If it must extend a class, use the holder idiom, where a static nested class holds the instance and the JVM initialises it once. Double-checked locking works only with volatile. But usually don't: create one instance in main or let Spring manage it, and pass it in, so it can be replaced in tests.

Go deeper: Explain why volatile matters: without it, another thread can see a non-null reference before the constructor's writes are visible. Then list the costs of singletons: hidden dependencies, state leaking between tests, and one instance per class loader rather than per JVM. A Spring bean is a singleton per container, reached by injection, which keeps the single instance without the global access.

Q6

Decorator, proxy and adapter all wrap an object. How do they differ?

30-second answerAn adapter changes the interface: it makes the vendor's SDK look like your PaymentGateway. A decorator keeps the interface and adds behaviour, and the client chooses and stacks the wrappers, as with pricing add-ons or BufferedReader. A proxy keeps the interface and controls access (caching, lazy loading, security, remoting), usually without the caller knowing, as Spring's @Transactional does.

Go deeper: Point out that decorator order is behaviour. Capping a fee before or after an EV discount gives different prices, so build the chain in one place. For proxies, name the self-invocation trap: a call from one method of a Spring bean to another on this skips the proxy, so the second method's @Transactional is ignored.
