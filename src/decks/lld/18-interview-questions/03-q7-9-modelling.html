Three modelling questions that test how you think, not what you remember

These come up at the start of a round ("how would you approach this?") or after it ("why is this an enum?"). Answer with the method, then one example from a problem you know well.

Q7

How do you get from a problem statement to classes?

30-second answerFirst pin down the use cases and assumptions. Then list the nouns and filter them: things with identity and changing state become classes, values become records, fixed options become enums, varying rules become interfaces, properties become fields, and outside actors become callers. Then give each verb to the class that has the data it needs, and keep a thin service per use case to coordinate.

Go deeper: Show a filtering decision that matters. In the library, "book" is two things: a Book you search and reserve, and a Copy you borrow. In the parking lot, "attendant" and "gate" are callers, not classes. Then mention the check against a god class: one line of responsibilities per class, split any class with more than three, and merge any with none.

Q8

Enum, class hierarchy or sealed interface: how do you choose?

30-second answerAn enum when the variants differ only in data: vehicle types that differ in spot size and rate. A sealed interface with records when the set is closed but each variant carries different data, and operations are added by switching over it. An open interface with classes when new variants keep arriving and each brings its own behaviour, such as pricing strategies.

Go deeper: Frame it as which axis changes. New types but fixed operations favours polymorphic methods on an interface. Fixed types but new operations favours a sealed type and switch, which the compiler checks for exhaustiveness. Say the migration path out loud: "an enum now; if trucks need their own rules, it becomes a sealed interface, and only the classes that switch on it change."

Q9

How do you handle money and time in a design?

30-second answerMoney is never a double. Use a long of minor units or BigDecimal with a fixed scale, inside a value object that validates and knows its currency, and make rounding an explicit rule that keeps totals exact. Time is never read from inside the logic. Inject a Clock, so fees, expiries and due dates can be tested by moving time rather than sleeping.

Go deeper: Give a rounding example: ₹100 three ways is 33.34, 33.33, 33.33, with the extra paisa assigned by a stated rule. Mention BigDecimal.equals comparing scale, so 10.5 and 10.50 differ unless you normalise. For time, name the distributed version: compare expiries against database time, because server clocks drift.
