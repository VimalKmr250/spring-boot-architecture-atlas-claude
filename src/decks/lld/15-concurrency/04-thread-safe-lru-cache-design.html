LRU cache: a hash map for O(1) lookup, a linked list for O(1) recency

"Design an LRU cache" is asked as a coding question and as an LLD question. Both want get and put in O(1), with the least recently used entry evicted when the cache is full. The LLD version adds "and make it thread-safe", which has a trap: in an LRU cache, get is a write.

HashMap<K, Node> finds a node in O(1) Doubly linked list orders nodes by recency head ⇄ [d] ⇄ [a] ⇄ [c] ⇄ tail most recent least recent get(a) index → node a; unlink; add after head put(e) full? unlink tail.prev (c), remove from index add [e] after head, put in index head and tail are sentinel nodes: no null checks at the ends, so unlink and add are four lines each
The two-minute version, when allowed
class LruMap<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruMap(int capacity) {
        super(16, 0.75f, true);            // accessOrder = true
        this.capacity = capacity;
    }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) {
        return size() > capacity;          // evict after each put
    }
}
// thread-safe: Collections.synchronizedMap(new LruMap<>(100))
Thread-safety optionTrade-off
One lock around every operationCorrect and simple. All threads contend on one lock; fine up to moderate load. The next slide builds this.
Read-write lockWrong. get moves the node, so two readers under a shared read lock corrupt the list.
Striped: N independent LRU segments by key hashN times less contention. Eviction is per segment, so it is only approximately LRU overall.
ConcurrentHashMap + buffered recencyRecord reads in a lock-free buffer and apply them to the order in batches. This is how Caffeine works; near-LRU at very high throughput.
Use a libraryIn production, Caffeine. Say so; then build the simple version, because that is the question.
The trap, stated onceIf an interviewer offers "use a read-write lock, since reads are common", the right answer is to decline and explain that an LRU read changes the order. It is one of the most reliable ways to show you understand what your lock protects.
Related variantsLFU (least frequently used) adds a frequency per node and a list per frequency, still O(1). TTL expiry adds a timestamp per node and a check in get. Both reuse this structure.
