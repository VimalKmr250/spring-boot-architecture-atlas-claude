The toolbox, and the check-then-act bug every tool exists to prevent

Almost every concurrency bug in an LLD answer is a check-then-act: read something, decide, then write, while another thread changes it in between. The demo forces that interleaving with two latches, so it goes wrong on every run. It then does the same withdrawals 10,000 times from virtual threads, safely.

RaceDemo.java · a forced lost update, then two fixes
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

final class Account {
    private int balance;
    Account(int balance) { this.balance = balance; }
    synchronized boolean withdraw(int amount) {    // check and act, one lock
        if (balance < amount) return false;
        balance -= amount;
        return true;
    }
    synchronized int balance() { return balance; }
}

public class RaceDemo {
    static int unsafeBalance = 100;

    static void await(CountDownLatch l) {
        try { l.await(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    public static void main(String[] args) throws Exception {
        var aChecked = new CountDownLatch(1);
        var bDone = new CountDownLatch(1);
        Thread a = Thread.ofPlatform().start(() -> {
            if (unsafeBalance >= 80) {              // A checks: 100 >= 80
                aChecked.countDown();
                await(bDone);                       // A is paused here...
                unsafeBalance -= 80;                // ...and acts on a stale check
            }
        });
        Thread b = Thread.ofPlatform().start(() -> {
            await(aChecked);
            if (unsafeBalance >= 80) unsafeBalance -= 80;   // B: 100 -> 20
            bDone.countDown();
        });
        a.join();
        b.join();
        System.out.println("check-then-act, no lock: balance " + unsafeBalance);

        var account = new Account(5_000);
        var ok = new AtomicInteger();
        try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 10_000; i++)
                pool.submit(() -> { if (account.withdraw(1)) ok.incrementAndGet(); });
        }
        System.out.println("synchronized: " + ok.get() + " withdrawals, balance " + account.balance());

        var counts = new ConcurrentHashMap<String, Integer>();
        try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 10_000; i++) {
                String key = i % 3 == 0 ? "fizz" : "other";
                pool.submit(() -> counts.merge(key, 1, Integer::sum));   // atomic per key
            }
        }
        System.out.println("ConcurrentHashMap.merge: " + new TreeMap<>(counts));
    }
}

ToolUse it for
synchronizedThe default. Short critical sections on one object. Re-entrant, released automatically.
ReentrantLockWhen you need tryLock with a timeout, interruptible waits, or several conditions.
ReadWriteLockMany readers, rare writers, and reads that really do not mutate. Not an LRU cache, where every read moves an entry.
AtomicInteger, AtomicReferenceA single variable updated with compare-and-set. LongAdder for hot counters.
ConcurrentHashMapMaps shared between threads. compute, merge, putIfAbsent are atomic per key; get then put is not.
CopyOnWriteArrayListListener lists: read constantly, changed rarely.
BlockingQueueHand-offs between producer and consumer threads, with back-pressure.
SemaphoreLimit how many threads do something at once, such as calls to a slow service.
