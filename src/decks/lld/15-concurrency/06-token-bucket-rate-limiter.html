Rate limiter: a token bucket per client, refilled from the clock, never by a timer

A bucket holds up to capacity tokens and gains rate tokens per second. Each request takes one token, or is refused if none are left. Bursts up to the capacity are allowed and the long-run average is the rate. Refill is computed from the elapsed time whenever a request arrives, so there is no background thread, and an injected clock makes it testable to the nanosecond.

RateLimiterDemo.java · integer arithmetic, a fake clock, one bucket per user
import java.util.Locale;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.LongSupplier;

final class TokenBucket {
    private static final long NANOS = 1_000_000_000L;
    private final long capacity, perSecond;
    private final LongSupplier nanoTime;
    private long tokens, lastRefill;

    TokenBucket(long capacity, long perSecond, LongSupplier nanoTime) {
        this.capacity = capacity;
        this.perSecond = perSecond;
        this.nanoTime = nanoTime;
        this.tokens = capacity;                    // start full: allow a burst
        this.lastRefill = nanoTime.getAsLong();
    }

    synchronized boolean tryAcquire() {
        refill();
        if (tokens == 0) return false;
        tokens--;
        return true;
    }

    private void refill() {                        // lazy: no timer thread
        long now = nanoTime.getAsLong();
        long earned = (now - lastRefill) * perSecond / NANOS;
        if (earned == 0) return;                   // keep the fraction for later
        tokens = Math.min(capacity, tokens + earned);
        lastRefill = tokens == capacity ? now : lastRefill + earned * NANOS / perSecond;
    }
}

final class RateLimiter {
    private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
    private final long capacity, perSecond;
    private final LongSupplier nanoTime;
    RateLimiter(long capacity, long perSecond, LongSupplier nanoTime) {
        this.capacity = capacity; this.perSecond = perSecond; this.nanoTime = nanoTime;
    }
    boolean allow(String client) {
        return buckets.computeIfAbsent(client,
                k -> new TokenBucket(capacity, perSecond, nanoTime)).tryAcquire();
    }
}

public class RateLimiterDemo {
    static long now = 0;                           // the fake clock, in nanos

    static void burst(RateLimiter limiter, String client, int requests) {
        StringBuilder s = new StringBuilder();
        for (int i = 0; i < requests; i++) s.append(limiter.allow(client) ? 'Y' : 'n');
        System.out.printf(Locale.ROOT, "t=%.2fs %-4s %s%n", now / 1e9, client, s);
    }

    public static void main(String[] args) {
        var limiter = new RateLimiter(5, 2, () -> now);   // burst 5, then 2 per second
        burst(limiter, "ana", 7);
        burst(limiter, "bo", 1);
        now += 500_000_000L;
        burst(limiter, "ana", 2);
        now += 250_000_000L;
        burst(limiter, "ana", 1);
        now += 250_000_000L;
        burst(limiter, "ana", 1);
        now += 3_000_000_000L;
        burst(limiter, "ana", 7);
    }
}

AlgorithmBehaviour
Fixed windowCount per calendar minute. Simple; allows 2× the limit across a window boundary.
Sliding logKeep every timestamp. Exact; memory grows with the limit.
Sliding window counterWeight this window and the last. Close to exact, two counters per client.
Token bucketBursts up to capacity, then a steady rate. Two numbers per client. The usual answer.
Leaky bucketA queue drained at a fixed rate. Smooths output; adds latency instead of refusing.
Why integer maths, and why the fraction is keptWith a double, 0.5 s × 2 tokens/s can come out as 0.999…, and a request that should pass is refused. Integer nanoseconds are exact. Advancing lastRefill only by the time actually converted into tokens keeps the leftover fraction, so at t = 0.75 s the half-token earned since 0.5 s is not lost.
Across many serversEach server has its own buckets, so ten servers allow ten times the rate. Keep the bucket in Redis and update it with one Lua script (read, refill, take, write), which runs atomically. Or give each server 1/n of the rate and accept the imprecision.
