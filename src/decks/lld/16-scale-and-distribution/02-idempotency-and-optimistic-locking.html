Idempotency keys make retries safe; version columns make concurrent edits safe

Across a network every call can time out without telling you whether it worked, so clients retry, and the server must treat a repeat as the same request. And two servers can read the same row and both write it back; the second write must fail rather than overwrite the first. These two techniques cover most of the correctness follow-ups in LLD.

Idempotency key · the client picks it, the server remembers it
-- client sends: POST /bookings/BK7/confirm   Idempotency-Key: 9f1c…
CREATE TABLE idempotency (
  key        VARCHAR(64) PRIMARY KEY,   -- unique: the second insert fails
  response   TEXT,
  created_at TIMESTAMP NOT NULL
);

-- in the same transaction as the real work:
INSERT INTO idempotency(key, created_at) VALUES (:key, now());
--   duplicate key?  return the stored response, do nothing else
UPDATE booking SET status = 'CONFIRMED' WHERE id = :id AND status = 'HELD';
UPDATE idempotency SET response = :json WHERE key = :key;
Where it goes in the problemsPayment charges and refunds (the ATM's debit request id), booking confirmation (a payment webhook delivered twice), Splitwise expenses uploaded twice from a phone on a bad network. The ATM's reverse already works this way: a second reversal of the same id does nothing.
Optimistic locking · read the version, write only if unchanged
SELECT id, vehicle, version FROM parking_spot WHERE id = 'F1-M1';
--   id=F1-M1 vehicle=NULL version=41

UPDATE parking_spot
   SET vehicle = 'CAR-A', version = version + 1
 WHERE id = 'F1-M1' AND version = 41;
--   1 row  → we won
--   0 rows → someone else changed it: re-read, retry or pick another spot
The same thing in JPA
@Entity
class ParkingSpot {
    @Id String id;
    String vehicle;
    @Version long version;   // Hibernate adds "AND version = ?" to every update,
}                            // and throws OptimisticLockException on 0 rows
