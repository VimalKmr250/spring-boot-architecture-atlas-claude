Distributed locks: prefer a conditional write, and if you must lock, use a lease with a fencing token

A lock across servers is harder than it looks. The holder can pause (a long GC, a network partition) past the lock's expiry, wake up, and write, not knowing another server now holds the lock. Most LLD scale questions do not need a lock at all, because a conditional write in the database already makes the decision atomic. When one is needed, it must expire, and the resource it guards must reject stale holders.

Why a lease alone is not enough t0 A gets lease, token 33 t1 A pauses (GC) lease expires t2 B gets lease, token 34 t3 B writes with token 34 accepted t4 A wakes, writes with token 33 storage: 33 < 34 seen rejected Fencing: every write carries the token, and the resource refuses any token lower than the highest it has already seen.

Seat holds

A hold is a lease: SET seat:S1:B1 BK7 NX PX 480000 claims with an expiry. The booking row is the source of truth, and confirmation checks it conditionally, so a late Redis key cannot sell a seat twice.

One sweeper job

Hold expiry and overdue reminders should run on one instance. Take a lease named after the job; the holder runs it and renews; if it dies, the lease lapses and another instance takes over.

What to say

"I'd avoid a distributed lock by making the write conditional. If I needed one, I'd use a lease with a fencing token checked by the database, not a bare Redis lock."
