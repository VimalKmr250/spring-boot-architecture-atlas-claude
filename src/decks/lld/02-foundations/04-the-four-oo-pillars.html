The four pillars, and how each one goes wrong

Interviewers rarely ask for the definitions. They check whether your design uses the pillars: state that only its owner can change, callers that depend on what an object does rather than how, and behaviour that varies by type without a switch on the type.

Encapsulation

An object guards its own state, and the only way to change it is through methods that keep it valid.

Goes wrong as a setBalance that lets any caller skip the overdraft rule.

Abstraction

Callers see what an object does and none of how. An interface is the cleanest form.

Goes wrong as a PaymentService whose callers must know which gateway sits behind it.

Inheritance

A subtype reuses and specialises a supertype. It is the strongest coupling Java has: the child depends on its parent's internals.

Goes wrong as Square extends Rectangle, or a hierarchy four levels deep.

Polymorphism

One call, many behaviours, chosen by the runtime type. It replaces conditionals on type.

Goes wrong as if (v instanceof Truck) … else if (v instanceof Car) repeated in five classes.

All four in one listing
interface Shape {                          // abstraction: what, not how
    double area();
}

final class Circle implements Shape {      // polymorphism: its own area()
    private final double r;                // encapsulation: private, final
    Circle(double r) {
        if (r <= 0) throw new IllegalArgumentException("radius");
        this.r = r;                        // valid from construction on
    }
    public double area() { return Math.PI * r * r; }
}

abstract class Account {                   // inheritance: shared rule
    private long balanceCents;             // no setter: change goes through
    void withdraw(long cents) {            // a method that keeps it valid
        if (cents > balanceCents + overdraftLimit())
            throw new IllegalStateException("insufficient funds");
        balanceCents -= cents;
    }
    abstract long overdraftLimit();        // the part subtypes specialise
}

double total = shapes.stream().mapToDouble(Shape::area).sum();
// no switch on type: a new Shape needs no change here
The test interviewers applyAdd a new type. If the new class is the only file you touch, polymorphism is doing its job. If you also have to edit a switch somewhere else, you have found the design's weak point, so say so before the interviewer does.
