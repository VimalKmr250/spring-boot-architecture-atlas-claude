Inherit from a class only when you control it and it was designed for it

A subclass depends on how its parent is implemented, not just on what it promises. In the classic example below, the parent's addAll calls add internally, so a subclass that counts in both methods counts every element twice. Wrapping the set instead of extending it removes that dependency.

CountingSet.java · extending against wrapping
import java.util.*;

@SuppressWarnings("serial")
class InstrumentedHashSet<E> extends HashSet<E> {   // inheritance
    private int addCount;
    @Override public boolean add(E e) {
        addCount++;
        return super.add(e);
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);     // HashSet inherits addAll, which calls add()
    }
    int addCount() { return addCount; }
}

final class WrappingSet<E> {                        // composition
    private final Set<E> inner;
    private int addCount;
    WrappingSet(Set<E> inner) { this.inner = inner; }
    boolean add(E e) { addCount++; return inner.add(e); }
    boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return inner.addAll(c);     // inner's add() is not ours: no double count
    }
    int addCount() { return addCount; }
}

public class CountingSet {
    public static void main(String[] args) {
        var inherited = new InstrumentedHashSet<String>();
        inherited.addAll(List.of("a", "b", "c"));
        var wrapped = new WrappingSet<String>(new HashSet<>());
        wrapped.addAll(List.of("a", "b", "c"));
        System.out.println("extends HashSet: " + inherited.addCount());
        System.out.println("wraps a Set:     " + wrapped.addCount());
    }
}
Output on JDK 21 · CountingSet.java
extends HashSet: 6
wraps a Set:     3
UseWhen
InterfaceThe default for a point of variation. A class can implement many. Default methods can share small helpers.
Abstract classSubtypes share state or a fixed algorithm with steps to fill in (template method). A class can extend only one.
Sealed interfaceThe set of subtypes is closed and known, and you want exhaustive switch. Records make good permitted types.
CompositionYou want to reuse behaviour from a class you do not own, or switch it at runtime.
The rule of thumbInheritance is fine for a genuine "is-a" inside one module you control: Bishop extends Piece. Across a boundary, or just to reuse code, compose. A good line to say in the interview: "I'd rather hold a PricingStrategy than be one, so it can change at runtime."
