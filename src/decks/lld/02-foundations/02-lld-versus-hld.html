High-level design draws the boxes; low-level design writes what is inside one

High-level design (HLD, or system design) picks the services, stores and channels, and the way data flows between them. LLD zooms into one of those boxes and designs its classes. The two rounds need different preparation and are scored on different things.

High-level designLow-level design
Typical promptDesign Twitter's timeline. Design a URL shortener for 100M users.Design a parking lot. Design Splitwise. Design an elevator controller.
Unit of designServices, databases, caches, queues, CDNsClasses, interfaces, enums, methods
What you drawBoxes and arrows for request and data flowA class diagram with relationships and multiplicities
What you writeAPIs, a data model, back-of-envelope numbersCompilable code for the core use cases
Key questionsHow many requests per second? What happens when this node dies? Where is the bottleneck?Who owns this state? What changes when a new vehicle type arrives? Is this method thread-safe?
Main trade-offsConsistency against availability, latency against cost, SQL against NoSQLInheritance against composition, flexibility against simplicity, lock granularity
Classic failureNo numbers; one database for everything; no failure handlingOne god class; a switch on type in five places; getters and setters and nothing else
Where they meetAn LLD question often ends with a scale follow-up: "the parking lot now spans 200 sites". The right answer is not to redraw everything. Say which object becomes a service, which in-memory map becomes a table, and which lock becomes a database constraint. Scale and distribution covers this.
