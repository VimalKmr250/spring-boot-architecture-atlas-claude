Low-level design turns a requirement into classes and the code inside them

Low-level design (LLD) decides which classes exist, what each one is responsible for, how they relate, and what their key methods do. Its output is code a teammate could extend without breaking: an interface where the behaviour varies, an enum where the values are fixed, and one owner for each piece of state.

Machine coding round

60 to 120 minutes to write a working program at your own machine, often with a console demo or unit tests. The interviewer then reads the code and asks for a change. Scored on correctness, structure and how easily it extends.

runnable code

Object-oriented design interview

45 to 60 minutes at a whiteboard or in a shared editor: requirements, a class diagram, and the code for the two or three methods that matter. Scored on the model and the reasoning, not on compiling.

diagram + key code

Design discussion in a coding round

A coding question with a design follow-up: "now support three pricing rules", "make it thread-safe". Scored on whether your first version bends or has to be rewritten.

extension

What you hand over by the end

  1. Requirements: the use cases in scope, the ones you left out, and the assumptions you made.
  2. Entities: the nouns that hold state, and the enums and value objects around them.
  3. Class diagram: the classes, their relationships and multiplicities, and the interfaces where behaviour varies.
  4. Code: the model, the service that runs the main use case, and a demo or test that proves it.
  5. Trade-offs: what you would change for concurrency, persistence, or the next requirement.

What it is not

  • Not system design. No load balancers, no sharding, no capacity estimates, unless you are asked how the design scales.
  • Not a pattern quiz. Patterns are a vocabulary for the choices you made. Using five of them where one would do costs marks.
  • Not a database schema. Tables may come up, but the model is objects and behaviour, not rows.
  • Not an algorithm puzzle. Each problem has one algorithmic core (the elevator scheduler, the debt simplifier), but most of the marks are for the structure around it.
One sentence to rememberA good low-level design puts each decision in exactly one place, so when the requirement changes, one class changes.
