ATM: a context, four states, a chain of note slots, and a bank behind an interface

The Atm holds the current state and forwards every button press to it; each state returns the next state. The cash dispenser is a chain of slots, one per note value. The bank is an interface, because the ATM must be testable without a real bank and will be connected to several.

Atm the context - state : AtmState - card : Card (0..1) - bank : Bank - dispenser : CashDispenser + insertCard(Card) + enterPin(String) + balance() + withdraw(int) + eject() ◆── 1 AtmState ──> 1 Bank ◆── 1 CashDispenser «interface» AtmState default: refuse politely + insertCard(Atm, Card) : AtmState + enterPin(Atm, String) : AtmState + balance(Atm) : AtmState + withdraw(Atm, int) : AtmState + eject(Atm) : AtmState ┄┄▷ Idle ┄┄▷ CardInserted ┄┄▷ Authenticated ┄┄▷ OutOfService CashDispenser + plan(amount) : Optional<Map<note, count>> + dispense(plan) may fail: hardware ◆── 1..* NoteSlot NoteSlot chain of responsibility - denomination - count ──> 0..1 NoteSlot next, smaller note «interface» Bank + verifyPin(Card, pin) : boolean + balance(Card) : long + debit(Card, amount) : txnId + reverse(txnId) ┄┄▷ InMemoryBank
State transitions Idle ──insertCard──> CardInserted CardInserted ──right PIN──> Authenticated CardInserted ──3rd wrong──> Idle card kept CardInserted ──eject──> Idle Authenticated ──withdraw──> Authenticated Authenticated ──last note──> OutOfService card returned Authenticated ──eject──> Idle OutOfService ──insertCard──> OutOfService refused
ClassOwns the decision
Each AtmStateWhich actions are allowed now, and what state comes next
CardInsertedThe PIN attempt count, which dies with the state
NoteSlotHow many of its notes to use
BankWhether the money exists, and whether a debit stands
Why the attempt counter lives in the stateA new CardInserted object is created for each card, so the count starts at 3 automatically and cannot leak to the next customer. A field on Atm would need resetting in every path back to Idle, and one path would be missed.
