Template method: fix the algorithm's skeleton, let subclasses fill in the steps

A base class defines the order of steps in a final method and leaves some steps abstract. Subclasses supply those steps but cannot reorder or skip the skeleton. Use it when several variants share the same sequence and differ in a few steps: importers, report generators, a game's turn loop, a chess piece's move generation.

TemplateDemo.java · two importers, one skeleton
import java.util.*;

abstract class Importer<T> {
    final String run(List<String> lines) {          // the template method
        List<T> good = new ArrayList<>();
        List<String> errors = new ArrayList<>();
        int start = hasHeader() ? 1 : 0;
        for (int i = start; i < lines.size(); i++) {
            try {
                T record = parse(lines.get(i).split(","));
                validate(record);                    // hook
                good.add(record);
            } catch (IllegalArgumentException | ArrayIndexOutOfBoundsException e) {
                errors.add("line " + (i + 1) + ": " + e.getMessage());
            }
        }
        save(good);
        return name() + ": " + good.size() + " saved, errors " + errors;
    }
    protected abstract String name();
    protected abstract T parse(String[] cells);      // required step
    protected abstract void save(List<T> records);   // required step
    protected void validate(T record) {}             // hook: optional
    protected boolean hasHeader() { return true; }   // hook: optional
}

record Member(String id, String email) {}
record Book(String isbn, int copies) {}

final class MemberImporter extends Importer<Member> {
    final List<Member> db = new ArrayList<>();
    protected String name() { return "members"; }
    protected Member parse(String[] c) { return new Member(c[0], c[1]); }
    protected void validate(Member m) {
        if (!m.email().contains("@")) throw new IllegalArgumentException("bad email " + m.email());
    }
    protected void save(List<Member> ms) { db.addAll(ms); }
}

final class BookImporter extends Importer<Book> {
    final List<Book> db = new ArrayList<>();
    protected String name() { return "books"; }
    protected boolean hasHeader() { return false; }
    protected Book parse(String[] c) { return new Book(c[0], Integer.parseInt(c[1])); }
    protected void save(List<Book> bs) { db.addAll(bs); }
}

public class TemplateDemo {
    public static void main(String[] args) {
        var members = new MemberImporter();
        System.out.println(members.run(List.of("id,email", "M1,ana@x.io", "M2,bo-at-x", "M3")));
        var books = new BookImporter();
        System.out.println(books.run(List.of("111,2", "222,two", "333,1")));
        System.out.println(members.db + " " + books.db);
    }
}

Abstract step

Every subclass must provide it: parse, save.

Hook

An optional step with a default that subclasses may override: validate, hasHeader.

Make the template finalOtherwise a subclass can override run and skip validation, and the guarantee is gone. The Hollywood principle ("don't call us, we'll call you") describes the flow: the base class calls the subclass, never the reverse.
The composition alternativeTemplate method is inheritance, with its coupling. If the steps vary independently (any parser with any store), pass them in as strategies instead: new Importer<>(parser, validator, store). Choose template method when the steps belong together.
