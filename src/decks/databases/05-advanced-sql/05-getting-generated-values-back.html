Ask the INSERT itself for the id it generated; a trigger can make @@IDENTITY return somebody else's

After inserting an order, the application needs its new id, to insert the lines and to return it to the caller. Reading it with a second query, "the highest id", is wrong as soon as two sessions insert at once. Both engines can return values from the insert itself: Oracle with RETURNING … INTO, SQL Server with the OUTPUT clause. JDBC's getGeneratedKeys() uses those underneath. SQL Server also keeps three "last identity" functions, and only one of them is safe.

returning.mss.sql · SQL Server 2025
BEGIN TRANSACTION;
-- 1  OUTPUT returns the generated values from the statement itself
INSERT INTO orders (customer_id, status, placed_at, total)
OUTPUT inserted.order_id, inserted.status
VALUES (2, 'PENDING', '2026-04-01 10:00:00', 89.00);
ROLLBACK;
GO

-- 2  add an audit table with its own identity, filled by a trigger on orders
CREATE TABLE order_audit (audit_id INT IDENTITY(500, 1) PRIMARY KEY, order_id INT, action VARCHAR(10));
GO
CREATE TRIGGER orders_audit_tr ON orders AFTER INSERT AS
  INSERT INTO order_audit (order_id, action) SELECT order_id, 'INSERT' FROM inserted;
GO

--    now the same INSERT ... OUTPUT is refused
BEGIN TRANSACTION;
INSERT INTO orders (customer_id, status, placed_at, total)
OUTPUT inserted.order_id, inserted.status
VALUES (2, 'PENDING', '2026-04-01 10:00:00', 89.00);
ROLLBACK;
GO

-- 3  OUTPUT INTO a table variable still works with the trigger in place
BEGIN TRANSACTION;
DECLARE @new TABLE (order_id INT);
INSERT INTO orders (customer_id, status, placed_at, total)
OUTPUT inserted.order_id INTO @new
VALUES (2, 'PENDING', '2026-04-01 10:00:00', 89.00);
SELECT order_id AS via_output_into FROM @new;

-- 4  SCOPE_IDENTITY is this scope's last identity; @@IDENTITY is the session's, trigger included
INSERT INTO orders (customer_id, status, placed_at, total)
VALUES (3, 'PENDING', '2026-04-01 10:05:00', 24.00);
SELECT SCOPE_IDENTITY() AS scope_identity, @@IDENTITY AS at_at_identity;
ROLLBACK;
GO

DROP TRIGGER orders_audit_tr;
DROP TABLE order_audit;

returning.ora.sql · Oracle 26ai
-- 1  RETURNING hands back generated values; SQL*Plus receives them into a bind variable
VARIABLE new_id NUMBER
INSERT INTO orders (customer_id, status, placed_at, total)
VALUES (2, 'PENDING', TIMESTAMP '2026-04-01 10:00:00', 89.00)
RETURNING order_id INTO :new_id;
PRINT new_id

-- 2  the same in PL/SQL, where application code usually does it
SET SERVEROUTPUT ON
DECLARE
  v_id    orders.order_id%TYPE;
  v_total orders.total%TYPE;
BEGIN
  INSERT INTO orders (customer_id, status, placed_at, total)
  VALUES (3, 'PENDING', TIMESTAMP '2026-04-01 10:05:00', 24.00)
  RETURNING order_id, total INTO v_id, v_total;
  DBMS_OUTPUT.PUT_LINE('new order ' || v_id || ' for ' || v_total);
END;
/
ROLLBACK;

SQL Server functionReturnsHere
SCOPE_IDENTITY()The last identity generated in this session and this scopeThe order's id
@@IDENTITYThe last identity generated in this session, in any scope, triggers included501: the audit row the trigger inserted
IDENT_CURRENT('orders')The last identity generated for the table, by any sessionWhatever another session inserted last; never use it for "my" row
OUTPUT inserted.colValues from the statement itself, for every row it insertedThe best option, but a table with a trigger needs OUTPUT … INTO
Error 334: OUTPUT and triggersAdding a trigger to orders broke every plain INSERT … OUTPUT against it. Some ORMs generate exactly that statement to read back keys; Entity Framework Core 7 switched to it and broke on tables with triggers. A DBA's audit trigger can take down an application that did not change. OUTPUT … INTO @table still works.
MAX(id) is not your idSELECT MAX(order_id) after an insert returns another session's row as soon as two inserts overlap. Sequences and identities are concurrency-safe precisely because each session gets its own number back.
Say it in the interview"I get keys back from the insert: RETURNING on Oracle, OUTPUT or SCOPE_IDENTITY() on SQL Server, getGeneratedKeys() in JDBC. In MongoDB the driver generates the ObjectId, so the id is known before the write." The JDBC side is on JDBC done right.
