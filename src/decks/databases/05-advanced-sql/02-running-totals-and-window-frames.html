A running total with ORDER BY alone uses a RANGE frame, so rows with the same timestamp share one total

Aggregate functions become window functions with OVER. Add ORDER BY and each row aggregates a frame: the rows from the start of the partition up to this one. The trap is the default frame, which the standard defines as RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE means "up to this row's value", so it includes every peer with the same sort value. In a wallet where two movements share a second, both rows show the balance after both. An explicit ROWS frame, with a unique tie-breaker in the sort, gives each row its own total.

frames.mss.sql · SQL Server 2025 (frames.ora.sql differs only in its DDL and timestamp literals)
-- a wallet's movements; two arrive in the same second
CREATE TABLE wallet_moves (move_id INT PRIMARY KEY, moved_at DATETIME2(0) NOT NULL, amount DECIMAL(10,2) NOT NULL);
INSERT INTO wallet_moves VALUES (1, '2026-03-01 09:00:00',  500.00),
                                (2, '2026-03-01 09:05:00', -120.00),
                                (3, '2026-03-01 09:05:00',  -30.00),
                                (4, '2026-03-01 09:20:00',  -45.50),
                                (5, '2026-03-01 10:00:00',  200.00);

SELECT move_id, moved_at, amount,
       SUM(amount) OVER (ORDER BY moved_at)                         AS default_frame,
       SUM(amount) OVER (ORDER BY moved_at, move_id
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       AVG(amount) OVER (ORDER BY moved_at, move_id
                         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)  AS moving_avg_3,
       SUM(amount) OVER ()                                           AS grand_total
FROM   wallet_moves
ORDER  BY moved_at, move_id;
DROP TABLE wallet_moves;

The default frameRows 2 and 3 both show 350.00 under default_frame. A statement printed from it would never show the 380.00 balance that existed between the two movements, and a "balance went negative" check could miss a real dip. Write the frame explicitly whenever you write ORDER BY inside OVER.
Same maths, different scaleSQL Server averaged DECIMAL(10,2) values to six decimal places, truncating: 116.666666. Oracle's NUMBER kept full precision, and the column format rounded it to 116.67 for display. Round explicitly when the result is shown to a person or compared.
Say it in the interview"SUM(amount) OVER (PARTITION BY account ORDER BY moved_at, move_id ROWS UNBOUNDED PRECEDING) is a running balance in one pass, with no self-join. ROWS counts rows; RANGE compares values." Oracle accepts RANGE BETWEEN INTERVAL '7' DAY PRECEDING AND CURRENT ROW for a true 7-day window; SQL Server allows RANGE only with UNBOUNDED and CURRENT ROW.
