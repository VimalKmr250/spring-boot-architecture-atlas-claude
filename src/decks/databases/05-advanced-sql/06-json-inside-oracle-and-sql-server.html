A JSON column lets a relational table hold a document, and SQL can still filter, explode, index and produce JSON

Not every attribute deserves a column. Event payloads, provider responses and per-product specifications vary in shape, and are mostly stored and returned whole. Both engines now have a native JSON type: Oracle 21c and SQL Server 2025, which replaces JSON kept in NVARCHAR. The database validates each value on insert and stores it in a binary form. SQL reaches inside with path expressions: JSON_VALUE for a scalar, JSON_TABLE (Oracle) or OPENJSON (SQL Server) to turn an array into rows, and an index on an extracted value. The same engines also build JSON from rows, which is often exactly what an API returns.

json.ora.sql · Oracle 26ai
-- 1  a native JSON column: the database parses and validates every value
CREATE TABLE order_events (event_id NUMBER PRIMARY KEY, payload JSON NOT NULL);
INSERT INTO order_events VALUES (1, '{"type":"ORDER_PLACED","orderId":1001,"channel":"web",
  "items":[{"sku":"LAP-14","qty":1},{"sku":"ACC-MSE","qty":1}]}');
INSERT INTO order_events VALUES (2, '{"type":"ORDER_PLACED","orderId":1003,"channel":"app",
  "items":[{"sku":"COF-GRD","qty":1},{"sku":"COF-BNS","qty":2}]}');
INSERT INTO order_events VALUES (3, '{"type":"ORDER_PLACED", "orderId": 1004');

-- 2  scalars with JSON_VALUE, arrays as rows with JSON_TABLE
SELECT e.event_id,
       JSON_VALUE(e.payload, '$.channel')                  AS channel,
       jt.sku, jt.qty
FROM   order_events e,
       JSON_TABLE(e.payload, '$.items[*]'
                  COLUMNS (sku VARCHAR2(20) PATH '$.sku', qty NUMBER PATH '$.qty')) jt
WHERE  JSON_EXISTS(e.payload, '$.items[*]?(@.qty >= 2)')
ORDER  BY e.event_id, jt.sku;

-- 3  index one field so lookups by it do not parse every document
CREATE INDEX order_events_order_ix ON order_events (JSON_VALUE(payload, '$.orderId' RETURNING NUMBER ERROR ON ERROR));

-- 4  and the other direction: rows to JSON, as an API would return them
SELECT JSON_OBJECT('orderId' VALUE o.order_id,
                   'lines'   VALUE JSON_ARRAYAGG(JSON_OBJECT('sku' VALUE p.sku, 'qty' VALUE i.qty) ORDER BY i.line_no)) AS order_json
FROM   orders o
JOIN   order_items i ON i.order_id = o.order_id
JOIN   products p    ON p.product_id = i.product_id
WHERE  o.order_id = 1001
GROUP  BY o.order_id;

DROP TABLE order_events PURGE;

json.mss.sql · SQL Server 2025
-- 1  the native json type (2025): values are parsed and validated on the way in
--    (a JSON parse error aborts the rest of its batch, hence the GO)
CREATE TABLE order_events (event_id INT PRIMARY KEY, payload JSON NOT NULL);
INSERT INTO order_events VALUES (1, '{"type":"ORDER_PLACED","orderId":1001,"channel":"web",
  "items":[{"sku":"LAP-14","qty":1},{"sku":"ACC-MSE","qty":1}]}');
INSERT INTO order_events VALUES (2, '{"type":"ORDER_PLACED","orderId":1003,"channel":"app",
  "items":[{"sku":"COF-GRD","qty":1},{"sku":"COF-BNS","qty":2}]}');
INSERT INTO order_events VALUES (3, '{"type":"ORDER_PLACED", "orderId": 1004');
GO

-- 2  scalars with JSON_VALUE, arrays as rows with OPENJSON
SELECT e.event_id,
       JSON_VALUE(e.payload, '$.channel') AS channel,
       j.sku, j.qty
FROM   order_events e
CROSS  APPLY OPENJSON(e.payload, '$.items') WITH (sku VARCHAR(20) '$.sku', qty INT '$.qty') j
WHERE  EXISTS (SELECT 1 FROM OPENJSON(e.payload, '$.items') WITH (qty INT '$.qty') x WHERE x.qty >= 2)
ORDER  BY e.event_id, j.sku;

-- 3  index one field through a computed column
ALTER TABLE order_events ADD order_id AS CAST(JSON_VALUE(payload, '$.orderId') AS INT);
CREATE INDEX order_events_order_ix ON order_events (order_id);

-- 4  and the other direction: rows to JSON, as an API would return them
SELECT o.order_id AS orderId,
       (SELECT p.sku, i.qty FROM order_items i JOIN products p ON p.product_id = i.product_id
        WHERE i.order_id = o.order_id ORDER BY i.line_no FOR JSON PATH) AS lines
FROM   orders o
WHERE  o.order_id = 1001
FOR    JSON PATH, WITHOUT_ARRAY_WRAPPER;

DROP TABLE order_events;

JSON is not a schema escape hatchFields inside JSON have no types, no NOT NULL and no foreign keys unless you add check constraints. If a field is filtered, joined or updated on its own, it wants to be a real column. Use JSON for payloads that are written once and read whole.
Errors stop more than the rowThe truncated document was rejected by both engines: ORA-40441 with the position, and SQL Server error 13609. In SQL Server that error aborted the rest of its batch, which is why the script needs a GO after it. Parse JSON in the application if bad input is expected.
Say it in the interview"For a mostly relational model with a few flexible attributes, I add a JSON column to the relational table and index the paths I query. When the whole aggregate is document-shaped and read as a unit, a document database fits better." See Embed or reference.
