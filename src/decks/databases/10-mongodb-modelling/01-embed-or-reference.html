Embed what is read and written together and stays bounded; reference what grows without limit or is shared

The central decision in document modelling is where each relationship lives. Embedding puts the child inside the parent: one read returns both, and one write changes both atomically. Referencing stores the child separately with the parent's id, as a foreign key would: the child can be queried on its own and can grow without limit, but reading both takes a second query or a $lookup, and changing both atomically takes a transaction. The questions below decide most cases. The script stores the running example's order lines both ways and measures each.

embed-reference.js · MongoDB 8.3, mongosh
// the same orders stored two ways: lines embedded in the order, or lines in their own collection
db.order_lines.drop();
db.orders.find().forEach(o => o.items.forEach((it, i) =>
  db.order_lines.insertOne({ orderId: o._id, lineNo: i + 1, productId: it.productId, qty: it.qty, unitPrice: it.unitPrice })));
db.order_lines.createIndex({ orderId: 1, lineNo: 1 });

// 1  reading order 1003 with its lines
const embedded = db.orders.find({ _id: 1003 }).explain('executionStats').executionStats;
print('embedded:   1 query,', embedded.totalDocsExamined, 'document examined');
const head = db.orders.find({ _id: 1003 }, { items: 0 }).explain('executionStats').executionStats;
const lines = db.order_lines.find({ orderId: 1003 }).explain('executionStats').executionStats;
print('referenced: 2 queries,', head.totalDocsExamined, '+', lines.totalDocsExamined, 'documents examined');

// 2  one more bag of beans: line quantity and order total must change together
show(db.orders.updateOne({ _id: 1003, 'items.productId': 110 },
  { $inc: { 'items.$.qty': 1, total: Decimal128('24.00') } }));          // one document: atomic
show(db.order_lines.updateOne({ orderId: 1003, productId: 110 }, { $inc: { qty: 1 } }));
print('referenced: the order total is a second write, to a second document: atomic only in a transaction');

db.orders.updateOne({ _id: 1003, 'items.productId': 110 }, { $inc: { 'items.$.qty': -1, total: Decimal128('-24.00') } });
db.order_lines.drop();

RelationshipUsually
Order → linesEmbed: bounded, read and written with the order
Customer → addressesEmbed: a handful, owned by the customer
Order → customerReference, plus a snapshot of the name: shared, changes on its own
Product → reviewsReference; embed the latest few (subset pattern)
Customer → eventsReference: unbounded
What embedding boughtReading order 1003 with its lines examined one document in one query, against three documents in two queries when referenced. Adding a bag of beans changed the line and the order total in one atomic updateOne. Referenced, that is two writes to two documents, consistent only inside a transaction.
What it costsAn embedded child cannot be queried as a top-level entity without $unwind, and everything embedded is loaded whenever the parent is, unless a projection excludes it. Embedding a shared entity, such as the full product in every order, means updating it everywhere when it changes.
Say it in the interview"I design from the access patterns. Data read together is stored together. One-to-few and owned: embed. One-to-many that grows without limit, or many-to-many: reference, and copy the few fields the read needs. Then I check the 16 MB limit and how often each piece changes."
