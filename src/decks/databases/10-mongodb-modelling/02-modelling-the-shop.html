Model the shop from its screens: each page should be one read, and each change one write where possible

List the application's reads and writes, then shape documents so the frequent ones are cheap. The order page needs the order, its lines and the customer's name, so lines are embedded and the name is copied. The product page needs the product, its breadcrumbs, a rating and the newest reviews. A review is written once and read mostly on that page, while the full review list grows without limit. So reviews get their own collection, and the product page carries a computed rating and a subset of the latest two, both maintained when a review is added.

shop-model.js · MongoDB 8.3, mongosh
// a product page needs the product, its category path and its latest reviews: one document
db.reviews.drop();
db.product_pages.drop();
const reviews = [
  { productId: 109, stars: 5, text: 'Consistent grind', at: ISODate('2026-02-01') },
  { productId: 109, stars: 4, text: 'Loud but fast',     at: ISODate('2026-02-20') },
  { productId: 109, stars: 2, text: 'Burrs wore out',    at: ISODate('2026-03-05') },
  { productId: 109, stars: 5, text: 'Great value',       at: ISODate('2026-03-18') }
];
db.reviews.insertMany(reviews);                                   // every review: its own collection
const p = db.products.findOne({ _id: 109 });
db.product_pages.insertOne({
  _id: p._id, sku: p.sku, name: p.name, price: p.price,
  categoryPath: p.categoryPath,                                    // copied: the page shows breadcrumbs
  rating: { count: 4, sum: 16 },                                   // computed pattern: kept by $inc
  latestReviews: reviews.slice(-2).reverse()                       // subset pattern: the newest two only
    .map(r => ({ stars: r.stars, text: r.text, at: r.at }))
});
show(db.product_pages.findOne({ _id: 109 }, { _id: 0, name: 1, categoryPath: 1, rating: 1, latestReviews: 1 }));

// a new review: insert it, and update the page's summary in the same breath
const r = { productId: 109, stars: 3, text: 'Fine for filter', at: ISODate('2026-04-02') };
db.reviews.insertOne(r);
show(db.product_pages.updateOne({ _id: 109 }, {
  $inc: { 'rating.count': 1, 'rating.sum': r.stars },
  $push: { latestReviews: { $each: [{ stars: r.stars, text: r.text, at: r.at }], $position: 0, $slice: 2 } }
}));
show(db.product_pages.findOne({ _id: 109 }, { _id: 0, rating: 1, 'latestReviews.text': 1 }));
db.reviews.drop();
db.product_pages.drop();

Every copy needs an ownerThe page's rating and latest reviews are copies of data in reviews. The code that inserts a review also updates the page, here with one $inc and one $push with $slice. If that second write can fail, recompute the summary from reviews periodically, or write both in a transaction.
The relational habitSplitting every entity into its own collection and joining with $lookup on every page gives MongoDB's costs without its benefit. If most screens join three collections, either the documents are shaped wrong or the data is relational.
Say it in the interview"I list the queries first: product page, order page, order history, admin search. Then I shape documents so each frequent query is one read on one index.
