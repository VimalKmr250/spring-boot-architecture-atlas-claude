For monitoring data, a time-series collection applies the bucket pattern for you, and a TTL index deletes old data on its own

A time-series collection (MongoDB 5.0 and later) accepts one document per measurement but stores them internally in compressed buckets, grouped by the metaField, here the host, and by time. Queries look like queries on ordinary documents. A TTL index on a date field tells a background task, which runs every 60 seconds, to delete documents older than expireAfterSeconds. That suits sessions, one-time tokens and raw metrics. Time-series collections take the same option, expireAfterSeconds, at creation.

timeseries.js · MongoDB 8.3, mongosh
// 1  the same 1,008,000 CPU samples: big_metrics is a time-series collection; copy them into plain documents
db.metrics_plain.drop();
db.big_metrics.aggregate([{ $project: { _id: 0, host: 1, ts: 1, cpu: 1 } }, { $out: 'metrics_plain' }]);
db.metrics_plain.createIndex({ host: 1, ts: 1 });
db.adminCommand({ fsync: 1 });                                   // flush to disk first, so both sizes are settled
const size = name => db.getCollection(name).aggregate([{ $collStats: { storageStats: {} } }]).next().storageStats;
const mb = b => (b / 1024 / 1024).toFixed(1) + ' MB';
const t = size('big_metrics'), p = size('metrics_plain');
print('time-series:', mb(t.storageSize), 'data +', mb(t.totalIndexSize), 'indexes');
print('plain:      ', mb(p.storageSize), 'data +', mb(p.totalIndexSize), 'indexes');

// 2  hourly averages for one host and one day
show(db.big_metrics.aggregate([
  { $match: { host: 'host-07', ts: { $gte: ISODate('2026-03-05T00:00:00Z'), $lt: ISODate('2026-03-05T03:00:00Z') } } },
  { $group: { _id: { $dateTrunc: { date: '$ts', unit: 'hour' } }, avgCpu: { $avg: '$cpu' }, samples: { $sum: 1 } } },
  { $sort: { _id: 1 } }
]));
db.metrics_plain.drop();

// 3  a TTL index: the server deletes documents once their date is older than expireAfterSeconds
db.sessions.drop();
db.sessions.createIndex({ lastSeen: 1 }, { expireAfterSeconds: 30 });
const now = Date.now();
db.sessions.insertMany([
  { _id: 'stale', lastSeen: new Date(now - 120 * 1000) },
  { _id: 'fresh', lastSeen: new Date(now + 600 * 1000) }
]);
print('right after insert:', db.sessions.countDocuments());
sleep(65 * 1000);                                                // the TTL monitor runs every 60 seconds
print('65 seconds later:  ', db.sessions.countDocuments(), JSON.stringify(db.sessions.find().toArray().map(d => d._id)));
db.sessions.drop();

OptionMeaning
timeFieldThe measurement's timestamp; required
metaFieldWhat identifies the series: host, sensor, account. Buckets never mix values
granularityseconds, minutes or hours: how far apart samples arrive, which sizes the buckets
expireAfterSecondsRetention: whole buckets are deleted once older
Twenty-five times smallerThe 1,008,000 samples took 0.8 MB of data as a time-series collection, against 20.1 MB as plain documents, and 0.4 MB of indexes against 38.9 MB. Synthetic samples this regular compress unusually well; with real metrics expect a smaller saving, but still several times.
TTL is approximateThe stale session vanished within the 65 seconds, not at the 30-second mark: the TTL monitor runs once a minute and may fall behind on a busy server. Never rely on TTL for security expiry: also check the timestamp in the query that uses the document.
Say it in the interview"For metrics I use a time-series collection with the source as the meta field and a retention period, and I keep rollups in a separate collection via $merge. A TTL index handles expiry for sessions and tokens." The SQL side of the same store is in the monitoring case study.
