MongoDB modelling questions start from the queries, which is the opposite of how relational design starts

A relational schema can be designed from the data alone; a document schema cannot. The best answers begin with "what does the application read together?" and end with a limit: how big a document can grow, and how often each copied field changes.

Q22

When do you embed, and when do you reference?

30-second answerEmbed what is read together and owned by the parent: an order's lines, a customer's few addresses. Reference when the child grows without limit, is shared by many parents, or changes on its own schedule: a customer's orders, a product used by many orders. When a referenced entity's fields are needed on every read, copy just those fields, such as the customer's name on the order. That is the extended reference pattern.

Go deeper: Embedding buys one read and atomic updates. Reading order 1003 with its lines took one document in one query, against three documents in two queries when referenced. Adding a line and updating the total was one atomic updateOne; referenced, it needs two writes, consistent only inside a transaction. The cost is duplication: every copied field needs an owner that updates it, or a decision that it is a snapshot, like the price paid. Many-to-many relations use arrays of ids on one side, never full copies on both.

Q23

What are the common MongoDB schema design patterns and anti-patterns?

30-second answerPatterns that move work from read time to write time. Bucket: one document per series per hour, for time series. Computed: keep a running total so reads do not recalculate it. Subset: embed the latest ten reviews, store the rest apart. Extended reference: copy the fields a read needs. Attribute: key-value pairs for sparse properties. Schema version: a field that tells readers which shape they hold. The classic anti-pattern is an unbounded array.

Go deeper: The unbounded array ends in a hard error. In this tab, $push in batches stopped at 15.1 MB with error 10334, "Resulting document after update is larger than 16777216" bytes. Long before that, every read and write of the parent moves the whole document. Events, logs and messages belong in their own collection, indexed by owner and time. Other anti-patterns: a $lookup on every read, which is a relational model in a document database, and too many collections or indexes, each with its own cost.

Q24

When would you choose MongoDB over Oracle or SQL Server, and when not?

30-second answerMongoDB fits self-contained aggregates read and written by key: a product catalogue with varied attributes, an order with its lines, user profiles, event and metrics data, and anything whose shape changes often. A relational database fits data with many relationships, invariants that span entities, and ad hoc reporting across them: a ledger, inventory, billing. Most systems are polyglot: orders in documents, the ledger in tables, each store with a clear owner.

Go deeper: The arguments that do not hold any more: "MongoDB has no transactions" (it has had multi-document ACID transactions since 4.0) and "relational databases cannot store JSON" (Oracle and SQL Server both query and index it). The real differences are the modelling approach, how easily the store scales out (sharding is built into MongoDB), the SQL tooling a team already has, and operational skills. Say which queries decide it, not which product is better.
