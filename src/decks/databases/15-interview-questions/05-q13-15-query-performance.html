Performance questions reward a method: measure, find the dominant cost, change one thing, measure again

"The page is slow, what do you do?" has no single right answer, but it has a wrong one: guessing an index before looking at anything. These three questions cover reading the plan, the plan cache with its parameter-sniffing side effect, and the application-side causes that no index fixes.

Q13

A query is slow. How do you find out why?

30-second answerGet the plan the query actually ran, with actual row counts, not the estimated one. On Oracle: the gather_plan_statistics hint and DBMS_XPLAN.DISPLAY_CURSOR. On SQL Server: the actual execution plan and SET STATISTICS IO ON. Then look for three things. Where most of the reads go. A full scan where I expected a seek. A big gap between estimated and actual rows. Logical reads are the number to compare between two versions; elapsed time moves with the cache.

Go deeper: An estimate a factor of 100 off means the optimiser chose blind: stale statistics, a skewed column without a histogram, or a predicate it cannot estimate. In this tab, Oracle estimated 100K FAILED rows against 2,500 actual. To find which query to look at, use Query Store on SQL Server, AWR or V$SQL on Oracle, and the slow-query log or profiler in MongoDB, sorted by total time, frequency multiplied by duration. A 50 ms query run a million times matters more than one 10-second report.

Q14

Why use bind variables? What is parameter sniffing?

30-second answerWith bind variables, the SQL text is the same for every value, so the database parses and optimises it once and reuses the cached plan, and input is always treated as a value, which prevents SQL injection. In Java that means PreparedStatement with ?, never string concatenation. The trade-off is parameter sniffing: the plan is built for the first value seen, and reused for values it does not suit.

Go deeper: In this tab, a plan compiled for a status matching 90 rows was reused for one matching 499,990. Its half a million key lookups cost 1,532,419 pages, against 2,639 for a scan, about 580 times more. Fixes, in order of preference: an index that suits both, OPTION (RECOMPILE) for rare report queries, OPTIMIZE FOR, or SQL Server 2022's parameter-sensitive plans. Oracle has adaptive cursor sharing for the same problem. The injection demo: x' OR '1'='1 concatenated matched all 10 customers; passed as a parameter it matched none.

Q15

The database looks healthy, but the endpoint is slow. What do you check in the application?

30-second answerRound trips. An N+1 pattern: one query for the list, then one per row, usually a lazy ORM relation. Single-row inserts with autocommit instead of batches. A small JDBC fetch size on a large read. And deep OFFSET pagination, which reads and throws away every skipped row. Each looks fine in the database's own statistics, because every single statement is fast. The fixes are a join or batch fetch, batching, a larger fetch size, and keyset pagination.

Go deeper: The numbers from this tab. 10,000 single inserts with autocommit took 27 seconds on Oracle and 74 on SQL Server; batched in one transaction, 78 and 212 milliseconds. Reading 20,001 rows took 2,002 round trips at fetch size 10, and 22 at 1,000. Page 20,000 with OFFSET read 1,789 pages against 6 with a keyset cursor. Then check connection pool waits: a pool that is too small queues requests in the application, where database monitoring never sees them.
