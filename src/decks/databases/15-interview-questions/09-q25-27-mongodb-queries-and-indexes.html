MongoDB query questions come down to the pipeline's order and the index that serves its first stage

An interviewer who asks about aggregation is checking that you can translate a SQL question into stages. The follow-up is always performance: which index, in which field order, and how explain proves it.

Q25

What is the aggregation pipeline, and how does it map to SQL?

30-second answerA sequence of stages, each transforming the stream of documents from the previous one. $match is WHERE; $group is GROUP BY, and a $match after it is HAVING; $project is the select list; $sort and $limit are ORDER BY and FETCH FIRST; $lookup is a left outer join; $unwind turns an array into rows. Put $match first, where it can use an index.

Go deeper: Only the stages at the start of the pipeline can use indexes; after a $group or $unwind, documents are in memory. $group and $sort use up to 100 MB per stage, then spill to disk, which has been the default since 6.0. $unwind drops documents with empty arrays unless told otherwise. For window functions, $setWindowFields brings ranking and running totals; for top N per group, $topN. $facet runs several pipelines over the same input, and $merge writes results to a collection.

Q26

How do you order the fields of a compound index? What is the ESR rule?

30-second answerEquality fields first, then the Sort field, then Range fields. Equality fields narrow the index to one contiguous slice; the sort field makes that slice already ordered, so the server can return the first N entries and stop; range conditions last filter within it. For "the newest 20 shipped orders over 400", that is { status: 1, placedAt: -1, total: 1 }.

Go deeper: In this tab, the ESR index returned the newest 20 matching orders after reading 20 index keys. The other field orders read 62,470 or 66,722 keys and sorted them in memory, just to return 20, and that cost grows with the data. Check with explain('executionStats'): no SORT stage, and totalKeysExamined close to nReturned. A compound index on an array field becomes multikey, and at most one array field per compound index is allowed. It is the same idea as SQL's equality-then-range column order.

Q27

How do you find and fix a slow MongoDB query?

30-second answerFind it with the slow-query log or the database profiler, ranked by total time. Then run explain('executionStats') and compare three numbers: nReturned, totalKeysExamined and totalDocsExamined. A COLLSCAN, or far more documents examined than returned, means a missing or wrong index. A SORT stage means the index order does not match the sort. Fix the index, and confirm with explain again.

Go deeper: In this tab, the profiler caught a query that examined 500,000 documents to return 520. A customer's 25 orders cost a scan of all 500,000 documents without an index, and 25 keys and 25 documents with one. A covered query, with every filtered and returned field in the index and _id: 0 in the projection, reads no documents at all. For paging, skip is MongoDB's OFFSET: page 20,001 read 400,020 keys, against 20 for a range on the last seen key. $indexStats finds indexes nobody uses.
