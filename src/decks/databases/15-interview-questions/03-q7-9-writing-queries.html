Query-writing questions are about choosing the right construct, and knowing its edge cases

These three come up as spoken questions as often as coding exercises. Each one has a version that sounds right and is wrong under ties, NULLs or concurrency, and the interviewer is checking whether you know the difference. The coding versions are in the SQL drills.

Q7

What is the difference between ROW_NUMBER, RANK and DENSE_RANK? Find the third highest salary.

30-second answerAll three number rows in a window's order. ROW_NUMBER gives unique numbers, breaking ties arbitrarily: 1, 2, 3, 4. RANK gives ties the same number and then skips: 1, 2, 2, 4. DENSE_RANK gives ties the same number without gaps: 1, 2, 2, 3. "Third highest salary" means the third distinct value, so DENSE_RANK() = 3 in an outer query, returning NULL when there is no third.

Go deeper: ROW_NUMBER is the trap answer: with two people on 150,000, it returned the second copy of the 6th value as the 7th highest salary, 150,000 instead of 140,000. Add PARTITION BY dept for "per department". Alternatives: SELECT DISTINCT salary … OFFSET 2 ROWS FETCH NEXT 1 ROW ONLY, or a correlated COUNT(DISTINCT), which is quadratic without an index. Give ROW_NUMBER a unique tie-breaker whenever you need exactly N rows, or the result changes between runs.

Q8

What is the difference between DELETE, TRUNCATE and DROP?

30-second answerDELETE is DML: it can filter, logs each row, fires triggers, and can be rolled back. TRUNCATE is DDL: it removes all rows by deallocating storage, with minimal logging and no triggers; SQL Server also resets the identity counter. DROP removes the table itself, with its indexes and grants. The engine difference interviewers like: TRUNCATE commits implicitly on Oracle but can be rolled back inside a transaction on SQL Server.

Go deeper: TRUNCATE is refused when another table's foreign key references this one (ORA-02266, Msg 4712), even if no child rows exist. Deleting millions of rows in one statement holds locks for its whole duration and floods the transaction log or undo. Delete in chunks of a few thousand, committing between them. For time-based data, partition by time and drop or truncate whole partitions: in this tab, dropping a month's partition wrote 8,120 bytes of redo against 2,323,700 for deleting the same rows.

Q9

How do you write an insert-or-update, and is MERGE safe under concurrency?

30-second answerMERGE is the standard upsert on both Oracle and SQL Server: match on the key, update when matched, insert when not. But it is not atomic under concurrency. Two sessions merging the same new key can both see "not matched", and the second insert fails on the unique constraint. The constraint is what guarantees one row; the code must catch the duplicate-key error and retry, which then updates.

Go deeper: In this tab's race test, a plain MERGE from many threads hit duplicate-key errors in every run on Oracle, and occasionally on SQL Server, whose locking read narrows the window without closing it; with the retry, nothing was lost. On SQL Server, MERGE … WITH (HOLDLOCK) takes a range lock, so the second session waits instead of failing. MongoDB's updateOne(…, { upsert: true }) has the same race, and the fix is the same: a unique index, plus a retry on E11000. Without a unique constraint, every one of these patterns can create duplicates.
