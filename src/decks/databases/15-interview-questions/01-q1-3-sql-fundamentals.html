Three questions that open almost every database interview for developers

Q1

In what order is a SELECT evaluated, and what is the difference between WHERE and HAVING?

30-second answerLogically: FROM and the joins, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, then the row limit. WHERE filters rows before grouping, so it cannot use aggregates. HAVING filters groups after aggregation, so it can. That order explains the classic errors: a select-list alias works in ORDER BY but not in WHERE, and a window function cannot be filtered in WHERE.

Go deeper: The order is logical, not physical. The optimiser moves predicates around freely, pushing a HAVING condition on a grouping column down into the scan, for instance. Put a row condition in WHERE rather than HAVING anyway, to make the intent clear. To filter on a window function, compute it in a subquery or CTE and filter outside. Oracle 26ai also accepts QUALIFY, while SQL Server does not. And "rows come back in insert order" is never true without an ORDER BY.

Q2

Explain the join types. What goes wrong when you filter the right-hand table of a LEFT JOIN?

30-second answerAn inner join keeps only matching pairs. A left join keeps every left row and fills the right side with NULLs when nothing matches; right is the mirror image, and full keeps both sides. A cross join pairs everything with everything. The trap: a condition on the right-hand table in WHERE removes the NULL-filled rows, so the left join silently becomes an inner join. Conditions on the optional table go in ON.

Go deeper: Two more traps follow. COUNT(*) after a left join counts 1 for a customer with no orders: count a column of the right table instead. And a join to a child table repeats the parent's columns once per child: in this tab, SUM(o.total) after joining order_items gave 12,748.60 instead of 8,190.70, because every two-line order was counted twice. Aggregate the child in a subquery first. The joins themselves are executed as nested loops, hash or merge joins; you see which in the plan.

Q3

How does NULL behave in SQL, and why can NOT IN return no rows?

30-second answerNULL means unknown, so any comparison with it, even NULL = NULL, is UNKNOWN, and WHERE keeps only TRUE rows. x NOT IN (1, NULL) means x <> 1 AND x <> NULL; the second part is never true, so the whole condition never is, and no rows come back. That is why I write anti-joins with NOT EXISTS, and test with IS NULL, never = NULL.

Go deeper: Aggregates skip NULLs: COUNT(col) counts non-null values, and AVG divides by them. A CHECK constraint passes on UNKNOWN. Engines differ in two places. Oracle treats '' as NULL, so a NOT NULL column rejects an empty string. A SQL Server unique constraint allows only one NULL, while Oracle allows many; a filtered index fixes that. Sorting differs too: Oracle puts NULLs last in ascending order, SQL Server first. MongoDB adds a third state: a missing field, which { f: null } also matches.
