Modelling questions test whether you know where each fact lives, and what happens when it changes

Expect these when the interviewer moves from "write a query" to "design the tables". The answers that score are concrete: name the anomaly that normalisation prevents, the cost of a random key, and the constraint that stops a duplicate payment. Abstract definitions alone do not score.

Q4

What is normalisation, and when would you denormalise?

30-second answerNormalisation gives each fact one home, so an update cannot leave two copies disagreeing. 1NF: one value per cell, no lists in a column. 2NF: every non-key column depends on the whole key, so a product's name does not sit on the order line keyed by order and product. 3NF: nothing depends on another non-key column, so the customer's email lives in customers, not on the order. I normalise to 3NF by default, then denormalise specific columns on purpose.

Go deeper: There are two legitimate reasons to denormalise. A snapshot: the unit price on the order line is the price paid, and must not change when the catalogue does; in this tab's data the laptop lines still show 1,299.00 against today's 1,199.00. And derived data for reads: an order total or a counter, with a named owner that keeps it correct and a reconciliation query that proves it. The cost is concurrency and drift: a counter updated on every order puts every order for that customer behind one row lock.

Q5

Surrogate or natural key? IDENTITY, SEQUENCE or UUID?

30-second answerA surrogate BIGINT primary key for internal tables, generated by an identity column or a sequence, with the natural key, such as email or SKU, protected by a unique constraint, because natural keys change and are often composite. A UUID when ids are created outside the database or exposed in URLs, preferably time-ordered, UUIDv7, so inserts stay at the end of the index. Generated keys are unique, never gapless.

Go deeper: A random UUID as a SQL Server clustered key decides where each row is stored, so every insert splits a random page. In this tab's test that left 2,082 pages at 67% full against 1,429 at 97%, with 99% fragmentation. Sequences skip values on rollback and on caching, so invoice numbers that must be gapless need a separate, serialised step. Hibernate's allocationSize reads a sequence ahead in blocks to avoid a round trip per insert. In MongoDB the driver generates the ObjectId, time-ordered to the second, before the write is sent.

Q6

How do you store money, and how would you model account balances in a payment system?

30-second answerIn an exact decimal type: NUMBER(12,2) in Oracle, DECIMAL(12,2) in SQL Server, Decimal128 in MongoDB, BigDecimal in Java. Never FLOAT, where 0.1 + 0.2 is 0.30000000000000004. For balances, a double-entry ledger: every movement is a journal of entries that sum to zero, appended and never updated. The balance is the sum of the entries, cached in a snapshot table if reads need it.

Go deeper: SQL Server's MONEY keeps four decimals at every step, so 100 / 3 × 3 came out as 99.9999. Integer division is another trap: 7 / 2 is 3 in SQL Server and 3.5 in Oracle. In the ledger, a unique constraint on the external event's idempotency key turns a redelivered webhook into a duplicate-key error (ORA-00001, Msg 2627) instead of a second capture, and the application treats that as "already done". A check query finds any journal that does not balance. Constraints are the last line of defence because the application is not the only writer.
