Locking and database-code questions ask what happens when two sessions collide, and where the logic should live

Deadlocks and job queues are the two locking problems a backend developer meets in production. Stored procedures and triggers raise a design question: how much logic belongs in the database? Interviewers want a reasoned position, not a slogan.

Q19

What causes a deadlock, how do the databases resolve it, and what should the application do?

30-second answerTwo transactions each hold a lock the other needs: transfer A locks wallet 1 then wants 2, while transfer B locks 2 then wants 1. Both engines detect the cycle within seconds and fail one side. SQL Server rolls back the victim's whole transaction with error 1205. Oracle raises ORA-00060 and rolls back only the statement that detected it. Prevent deadlocks by locking rows in a consistent order, for example by ascending id, and keeping transactions short. Handle the ones that still happen by retrying the whole transaction.

Go deeper: Oracle's partial rollback is the trap: after ORA-00060, the session still holds its earlier locks, and the other transaction stays blocked until the application rolls back. So the handler must roll back before retrying. In Spring both errors become DeadlockLoserDataAccessException, a PessimisticLockingFailureException that a retry policy can catch. Lock timeouts (ORA-00054, error 1222) become CannotAcquireLockException. SQL Server's DEADLOCK_PRIORITY chooses which session is the victim; the deadlock graph in Extended Events shows the cycle.

Q20

How would you build a job queue on a database table, with several workers?

30-second answerEach worker claims a few pending rows in a short transaction and locks them, skipping rows another worker has already locked: SELECT … FOR UPDATE SKIP LOCKED on Oracle, UPDLOCK, READPAST on SQL Server. Then it marks them in progress and commits. With a plain FOR UPDATE, the second worker would wait for the first, so only one would ever work. Add an index on the status column, and a lease or attempt count so a failing job cannot loop forever.

Go deeper: No job is claimed twice, no worker waits, and if a worker dies before committing, the database releases its claim. The table queue's advantage over a broker is transactionality: claiming a payment retry and updating the payment commit together. It does not give push delivery, fan-out or high throughput; for those, publish from the table through an outbox. MongoDB's equivalent is findOneAndUpdate from PENDING to CLAIMED, which is atomic on one document.

Q21

Should business logic go in stored procedures and triggers?

30-second answerMostly not. Business rules belong in the application, where they are versioned, tested and visible with the rest of the code. Procedures are good for set-based work close to the data and for cutting round trips in a chatty sequence of dependent statements. Triggers are code that runs on someone else's statement, invisible to the caller. I limit them to audit rows, and keep integrity in constraints.

Go deeper: Triggers have engine-specific failure modes. A SQL Server trigger fires once per statement, so one that reads a single id from inserted silently handles only one row of a multi-row insert. In this tab one order's total stayed at 59.00 against 83.00 in its lines. An Oracle row trigger that queries its own table fails with ORA-04091, the mutating-table error. Inside procedures, error handling differs too. On SQL Server a failed statement leaves the transaction open unless SET XACT_ABORT ON; use TRY…CATCH and THROW. Row-by-row cursors cost two to five times a set-based statement in most runs here.
