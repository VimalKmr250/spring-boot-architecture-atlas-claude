Consistency and scale questions test whether you know what MongoDB guarantees by default, and what you must ask for

"Is MongoDB ACID?" and "how would you shard this?" are senior-level questions with a trap in each: transactions that fail instead of waiting, a write reported as failed that actually happened, and a shard key that sends every insert to one machine. Each answer below names the trap.

Q28

Is MongoDB ACID? When do you need a multi-document transaction?

30-second answerYes. A single-document write is atomic and isolated, and since 4.0 (4.2 on sharded clusters) transactions span documents and collections with snapshot isolation. I design so that each invariant lives in one document, then enforce it with a conditional update that puts the check in the filter, such as { _id, stock: { $gte: 1 } } with $inc: { stock: -1 }. I use a transaction only when the invariant really spans documents, such as a transfer between two accounts.

Go deeper: In this tab's stock test, read-check-write in Java granted all 400 requests for 100 phones; the conditional update granted exactly 100. Transactions are optimistic: a second writer to the same document fails at once with WriteConflict, labelled TransientTransactionError, instead of waiting as in SQL. So always run them through the driver's withTransaction, which retries. They are limited to 60 seconds by default, add commit latency, and must not contain calls to other services. In Spring, MongoTransactionManager makes @Transactional work.

Q29

What are write concern, read concern and read preference?

30-second answerWrite concern is when the client is told "done": w: 1 once the primary has the write, w: 'majority' once most members have it, which survives a failover and has been the default since 5.0. Read concern is which data a read may see: local may include writes a failover could roll back, majority only those it cannot. Read preference is which members may serve a read: the primary by default, secondaries only for reads that tolerate staleness.

Go deeper: A write-concern timeout is not a rollback. In this tab, with one member down, w: 3 failed with "waiting for replication timed out", yet the writes were on the primary. Retrying blindly inserts twice, so business writes need an idempotency key. Reading from a secondary right after writing to the primary can miss the write; for read-your-own-writes there, use a causally consistent session with majority concerns, or read the primary. Replication lag grows under load, exactly when reporting traffic peaks.

Q30

How do you choose a shard key?

30-second answerFour properties. High cardinality, so the data can be split into many chunks. Low frequency, so no single value dominates. Non-monotonic inserts, so new documents do not all land on the shard holding the highest range. And presence in the main queries, so mongos can route each query to one shard instead of asking all of them. For orders, the customer id, or customer id plus date, so "my orders" stays on one shard.

Go deeper: On this tab's two-shard cluster, status was a bad key: 99.5% of documents had one value, making one huge chunk that cannot be split. placedAt was unique but monotonic, so it created a hot shard for inserts; hash it, or put another field in front of it. A query without the shard key became a scatter-gather SHARD_MERGE across all shards. Since 5.0 a collection can be resharded online, and analyzeShardKey (7.0) measures a candidate first, but both are heavy: choose carefully.
