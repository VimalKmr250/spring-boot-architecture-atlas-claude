Transaction questions separate developers who have seen concurrency bugs from those who have only read about ACID

Reciting what ACID stands for earns little. What earns marks is knowing what your engine's default isolation level actually allows, and how an update gets lost under it. The third question, where a transaction begins and ends, is where Oracle and SQL Server differ most.

Q16

What are the isolation levels, and what does READ COMMITTED mean on Oracle and on SQL Server?

30-second answerThe standard levels, from weakest: READ UNCOMMITTED (dirty reads), READ COMMITTED, REPEATABLE READ, SERIALIZABLE. Both engines default to READ COMMITTED, but implement it differently. Oracle reads a consistent snapshot from undo, so readers never block writers. SQL Server, by default, takes shared locks, so a reader waits for a writer to finish. With READ_COMMITTED_SNAPSHOT on, SQL Server reads versions like Oracle.

Go deeper: Oracle has only READ COMMITTED and SERIALIZABLE, which is really snapshot isolation. It raises ORA-08177 on a conflicting write, yet allows write skew: in this tab two withdrawals of 600 from different wallets against a shared total of 800 both committed, leaving −400. SQL Server adds SNAPSHOT, which fails with error 3960 instead of waiting. NOLOCK is READ UNCOMMITTED: in the demo it read a balance of 400 that was then rolled back. And asking Oracle's JDBC driver for REPEATABLE_READ, as @Transactional(isolation = …) would, fails with ORA-17030: Oracle has no such level.

Q17

What is a lost update, and how do you prevent it?

30-second answerTwo sessions read the same balance, each computes a new value in application code, and the second write overwrites the first. READ COMMITTED allows it on both engines, without an error. Three fixes. Do the arithmetic in one conditional statement: UPDATE … SET balance = balance - 100 WHERE id = ? AND balance >= 100, then check the row count. Optimistic locking: a version column in the WHERE clause, which is what JPA's @Version generates. Or pessimistic locking with SELECT … FOR UPDATE, for short, hot transactions.

Go deeper: Raising the isolation level is not a portable fix: Oracle's SERIALIZABLE rejects the second writer with ORA-08177, while SQL Server's REPEATABLE READ makes the two sessions deadlock. Pessimistic locks need a timeout: FOR UPDATE WAIT 1 or NOWAIT on Oracle (ORA-00054), UPDLOCK with LOCK_TIMEOUT on SQL Server (error 1222). MongoDB's equivalent of the conditional update is a filter that includes the check, with $inc; in this tab's stock test it granted exactly 100 of 400 requests, where read-check-write granted all 400.

Q18

Where does a transaction start and end? What happens to an uncommitted transaction when the connection closes?

30-second answerOracle starts a transaction implicitly with the first change, and every DDL statement commits whatever is open. SQL Server runs each statement in autocommit unless BEGIN TRANSACTION opens one, and DDL inside it can be rolled back. In JDBC, autocommit is on by default for both until the code, or Spring's @Transactional, turns it off. And on close() with work pending, Oracle's driver commits it, while SQL Server rolls it back.

Go deeper: The Oracle script in this tab inserted a customer, created a table and rolled back, and the customer was still there: the DDL had committed the insert. SQL Server's nested BEGIN TRANSACTION only increments @@TRANCOUNT: the inner COMMIT commits nothing, and any ROLLBACK rolls back everything. Keep transactions short: no remote calls and no user think time inside one. Spring's propagation settings decide whether a method joins the caller's transaction or starts its own.
