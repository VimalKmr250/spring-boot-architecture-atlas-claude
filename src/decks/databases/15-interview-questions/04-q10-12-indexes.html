Index questions check whether you can predict what the optimiser will do with a query

"What is an index?" is the warm-up. The real questions are why an index did or did not help a particular query. Strong answers talk in pages read and rows matched, and mention the plan that proves it.

Q10

What is the difference between a clustered and a non-clustered index? When is an index not used?

30-second answerA clustered index is the table: its leaf pages hold the rows, sorted by the key, so a table has at most one. A non-clustered index is a separate sorted structure whose entries point at rows, so a query needing other columns does a lookup per matching row. SQL Server tables are usually clustered on the primary key. Oracle's default is a heap, with an index-organised table as the clustered equivalent. A seek costs a few pages plus one lookup per row; when many rows match, a scan is cheaper.

Go deeper: Selectivity decides. In this tab, the 2,500 FAILED orders out of 500,000 needed a column the index lacked: 2,500 random lookups of about three pages each would have cost more than the 2,639 pages of a full scan, so the optimiser scanned. Forcing the index with a hint cost 7,678 pages. A covering index, with INCLUDE (total) on SQL Server or the column added to the key on Oracle, removed the lookups. A filtered index on just the failed rows is smaller still.

Q11

How do you choose the column order of a composite index?

30-second answerEquality columns first, then the range or sort column. An index on (customer_id, placed_at) answers "this customer's orders in March" with one contiguous range of the index, because within one customer the dates are sorted. It also serves filters on its left prefixes: a, or a, b, but not b alone. If the index order matches the ORDER BY after the equality columns, the sort disappears too.

Go deeper: In this tab, the Oracle plan for one customer's orders went from a full scan of 2,425 buffers to 11 once (customer_id, placed_at) existed; both conditions became access predicates. An index on (status, placed_at) asked only for a date had to scan 2,219 pages, because it is sorted by status first. Oracle can sometimes skip-scan a leading column with few values, but do not design for it. Every index slows every write, so extend an existing index before adding another. MongoDB names the same rule ESR.

Q12

The column is indexed but the query still scans. Why?

30-second answerUsually the predicate is not sargable: the column is wrapped in something, so the index's sort order cannot be used. A function, such as UPPER(email) or truncating a date. Arithmetic on the column. A leading wildcard, LIKE '%son'. Or an implicit conversion, when the parameter's type differs from the column's. The fix is to compare the bare column with a value of its own type, or to index the expression.

Go deeper: The conversion case hides in Java. The SQL Server JDBC driver sends strings as NVARCHAR by default, so a lookup on a VARCHAR email column converted the column and read 88 pages instead of 2; sendStringParametersAsUnicode=false fixed it. Truncating a date in SQL Server cost 1,012 pages against 9 for a half-open range. Other reasons: the optimiser estimates too many rows (stale statistics, skew, no histogram), the query needs columns the index lacks, or the table is so small a scan is cheaper. Read the predicate section of the plan first.
