A payment system never updates a balance in place: it appends entries that sum to zero, and derives balances from them

A balance column that is overwritten answers "how much?" but never "why?", and one lost update corrupts it for good. A ledger records every money movement as a journal: one business event, such as a capture, a fee or a refund. Each journal has two or more entries, signed so that debits are positive and credits negative. Every journal sums to zero, so the whole ledger sums to zero. Entries are inserted and never updated. A mistake is corrected with a reversing journal, and any balance is a SUM. An idempotency key on the journal makes "post the capture" safe to retry.

ledger.ora.sql · Oracle 26ai
-- accounts, journals (one per business event) and entries (debits positive, credits negative)
CREATE TABLE gl_accounts (
  code  VARCHAR2(30) PRIMARY KEY,
  kind  VARCHAR2(10) NOT NULL CHECK (kind IN ('ASSET', 'LIABILITY', 'REVENUE'))
);
CREATE TABLE journals (
  journal_id       NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  idempotency_key  VARCHAR2(64) NOT NULL CONSTRAINT journals_idem_uk UNIQUE,
  event            VARCHAR2(20) NOT NULL
);
CREATE TABLE entries (
  journal_id    NUMBER       NOT NULL REFERENCES journals,
  line_no       NUMBER(2)    NOT NULL,
  account_code  VARCHAR2(30) NOT NULL REFERENCES gl_accounts,
  amount        NUMBER(12,2) NOT NULL CHECK (amount <> 0),
  CONSTRAINT entries_pk PRIMARY KEY (journal_id, line_no)
);
INSERT INTO gl_accounts VALUES ('psp_receivable', 'ASSET');
INSERT INTO gl_accounts VALUES ('merchant_payable', 'LIABILITY');
INSERT INTO gl_accounts VALUES ('fee_revenue', 'REVENUE');

-- order 1001 is captured: the card processor owes us, we owe the merchant
INSERT INTO journals (idempotency_key, event) VALUES ('capture-pay-1001-1', 'CAPTURE');
INSERT INTO entries VALUES (1, 1, 'psp_receivable', 1328.90);
INSERT INTO entries VALUES (1, 2, 'merchant_payable', -1328.90);
-- our 2.9% fee comes out of what we owe the merchant
INSERT INTO journals (idempotency_key, event) VALUES ('fee-pay-1001-1', 'FEE');
INSERT INTO entries VALUES (2, 1, 'merchant_payable', 38.54);
INSERT INTO entries VALUES (2, 2, 'fee_revenue', -38.54);
COMMIT;

-- the capture message is delivered twice: the unique key makes the retry a no-op
INSERT INTO journals (idempotency_key, event) VALUES ('capture-pay-1001-1', 'CAPTURE');

-- a buggy posting with one leg only: no single-row constraint can catch it
INSERT INTO journals (idempotency_key, event) VALUES ('fee-pay-1002-1', 'FEE');
INSERT INTO entries VALUES (4, 1, 'merchant_payable', 20.27);
COMMIT;

-- so check that every journal balances, and that the books do
SELECT journal_id, SUM(amount) AS imbalance FROM entries GROUP BY journal_id HAVING SUM(amount) <> 0;
SELECT COALESCE(account_code, '(all: must be 0)') AS account, SUM(amount) AS balance
FROM   entries GROUP BY ROLLUP (account_code) ORDER BY GROUPING(account_code), account_code;

DROP TABLE entries PURGE;
DROP TABLE journals PURGE;
DROP TABLE gl_accounts PURGE;

SQL Server 2025 agreesledger.mss.sql (the same with INT IDENTITY, DECIMAL and BEGIN TRANSACTION) rejected the duplicate capture with error 2627 and found the same unbalanced journal 4.
What constraints cannot check"The entries of a journal sum to zero" is a rule across rows, and CHECK sees one row at a time. Journal 4 was accepted with one leg. Post journals only through one function that inserts all entries in one transaction and verifies the sum before committing, and run the imbalance query as a scheduled check.
Retries are normalPayment events arrive twice: a webhook is redelivered, a consumer restarts. The unique idempotency_key turned the second capture into ORA-00001 instead of a second 1328.90. The application treats that error as "already done". Journal 3 is missing for the same reason: the failed insert consumed its identity value.
Say it in the interview"Money is append-only: journals of balanced entries, exact decimals, an idempotency key per external event, and balances derived by summing, optionally cached in a snapshot table. I never overwrite a balance." How this fits a whole payment flow is in the payment case study.
