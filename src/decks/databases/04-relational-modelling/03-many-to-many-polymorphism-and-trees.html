Three shapes that do not fit one foreign key: many-to-many, "belongs to one of several", and hierarchies

A foreign key expresses "each row belongs to one parent row in one table". Three common relationships need more than that. Many-to-many, such as products and tags, needs a junction table keyed by the pair. A row that belongs to one of several parent types, such as a note on an order or on a product, is tempting to model as (target_type, target_id), but that cannot have a foreign key. Separate nullable keys with a check, an exclusive arc, keep referential integrity. Trees can be stored four ways; the right one depends on whether you mostly read subtrees or change the tree.

relationships.ora.sql · Oracle 26ai
-- 1  many-to-many: a junction table whose primary key is the pair
CREATE TABLE product_tags (
  product_id INT         NOT NULL REFERENCES products,
  tag        VARCHAR(20) NOT NULL,
  CONSTRAINT product_tags_pk PRIMARY KEY (product_id, tag)
);
INSERT INTO product_tags VALUES (101, 'gift'), (101, 'sale'), (103, 'gift'), (106, 'sale'),
                                (109, 'gift'), (109, 'sale'), (110, 'gift');

--    products carrying BOTH tags: group, then count the distinct matches
SELECT product_id
FROM   product_tags
WHERE  tag IN ('gift', 'sale')
GROUP  BY product_id
HAVING COUNT(DISTINCT tag) = 2
ORDER  BY product_id;

-- 2  a closure table: one row per ancestor-descendant pair, built once from parent_id
CREATE TABLE category_closure (
  ancestor_id   INT NOT NULL,
  descendant_id INT NOT NULL,
  depth         INT NOT NULL,
  CONSTRAINT category_closure_pk PRIMARY KEY (ancestor_id, descendant_id)
);
INSERT INTO category_closure (ancestor_id, descendant_id, depth)
WITH walk (ancestor_id, descendant_id, depth) AS (
  SELECT category_id, category_id, 0 FROM categories
  UNION ALL
  SELECT w.ancestor_id, c.category_id, w.depth + 1
  FROM   walk w JOIN categories c ON c.parent_id = w.descendant_id
)
SELECT ancestor_id, descendant_id, depth FROM walk;

--    every product anywhere under Electronics: a plain join, no recursion at read time
SELECT p.sku, cc.depth
FROM   category_closure cc
JOIN   products p ON p.category_id = cc.descendant_id
WHERE  cc.ancestor_id = 1
ORDER  BY cc.depth, p.sku;

-- 3  an exclusive arc: a note belongs to an order or to a product, never both
CREATE TABLE notes (
  note_id    INT PRIMARY KEY,
  order_id   INT REFERENCES orders,
  product_id INT REFERENCES products,
  body       VARCHAR(200) NOT NULL,
  CONSTRAINT notes_one_parent_ck CHECK (
    (CASE WHEN order_id IS NULL THEN 0 ELSE 1 END) + (CASE WHEN product_id IS NULL THEN 0 ELSE 1 END) = 1)
);
INSERT INTO notes VALUES (1, 1001, NULL, 'gift wrap requested');
INSERT INTO notes VALUES (2, 1001, 101, 'attached to both');

DROP TABLE notes;
DROP TABLE category_closure;
DROP TABLE product_tags;

The polymorphic keytarget_type = 'ORDER', target_id = 1001 is the pattern ORMs make easy, and the database cannot check it. Nothing stops a note pointing at an order that was deleted. The exclusive arc above has a real foreign key per parent, and a CHECK that rejected the note attached to both.
Entity-attribute-valueA table of (entity_id, attribute, value) rows looks flexible: products with arbitrary properties. Every query then needs a self-join per attribute, values lose their types, and constraints are impossible. For variable attributes, prefer a JSON column (JSON inside Oracle and SQL Server) or a document store.
Say it in the interview"Products with both tags is relational division: filter to the tags, group by product, and keep groups whose distinct count equals the number of tags. For trees I start with parent_id and a recursive CTE, and add a closure table when subtree reads dominate."
