Normalising means storing each fact once, so that changing it is one update and deleting one thing deletes nothing else

A first draft of an order system often looks like a spreadsheet: one wide row per order line, with the customer's email, the product's name and the category repeated on every row. It works until data changes. Each normal form removes one kind of repetition by moving a fact to the table whose key it depends on. 1NF: one value per cell, no lists. 2NF: no column depends on only part of a composite key. 3NF: no column depends on another non-key column. The script below builds the spreadsheet version from the running example and shows the three anomalies normalisation prevents.

flat-orders.ora.sql · Oracle 26ai
-- one row per order line, everything repeated: the spreadsheet a first draft often looks like
CREATE TABLE order_sheet AS
SELECT o.order_id, o.placed_at, c.customer_id, c.name AS customer, c.email,
       p.sku, p.name AS product, cat.name AS category, i.qty, i.unit_price
FROM   orders o
JOIN   customers c    ON c.customer_id = o.customer_id
JOIN   order_items i  ON i.order_id = o.order_id
JOIN   products p     ON p.product_id = i.product_id
JOIN   categories cat ON cat.category_id = p.category_id;

-- update anomaly: Asha changes her email, and the fix reaches one order
UPDATE order_sheet SET email = 'asha.rao@example.com' WHERE order_id = 1001;
SELECT DISTINCT customer_id, email FROM order_sheet WHERE customer_id = 1 ORDER BY email;

-- delete anomaly: deleting Gita's orders also deletes the only record of her email
SELECT COUNT(*) AS rows_about_gita FROM order_sheet WHERE customer_id = 7;
DELETE FROM order_sheet WHERE customer_id = 7;
SELECT COUNT(*) AS gita_left FROM order_sheet WHERE email = 'gita@example.com';

-- insert anomaly: a new product cannot be recorded until somebody orders it
INSERT INTO order_sheet (sku, product, category) VALUES ('KIT-PRS', 'French Press', 'Kitchen');

DROP TABLE order_sheet PURGE;

BCNF and beyondBoyce-Codd normal form tightens 3NF for tables with overlapping candidate keys. 4NF and 5NF deal with independent multi-valued facts. They come up rarely in application schemas. If every determinant in a table is a candidate key, you are in BCNF, and that answer is enough in an interview.
Where the repetition hidesComma-separated lists in a column ('gift,sale') break 1NF: they cannot be indexed, joined or constrained. Columns like phone1, phone2, phone3 are the same repeating group in disguise. Both want a child table.
Say it in the interview"I normalise to 3NF by default, so each fact has one home and constraints can protect it. Then I denormalise specific columns on purpose, for history or for read speed, and I write down how each copy is kept correct." That is the next slide.
