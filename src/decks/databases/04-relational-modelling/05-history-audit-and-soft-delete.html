"What was the price last Tuesday?" needs history the schema keeps on purpose; undo and backups are not an audit trail

Applications need three kinds of past data. Point-in-time reads answer "what did this row look like then?". An audit trail records who changed what, and when. A soft delete hides a row without destroying it. SQL Server's system-versioned temporal tables keep every past version in a history table, automatically, for as long as you like. Oracle's flashback query reads past versions from undo, which is kept for minutes or hours, not years. It is a developer's "oops" tool and a debugging aid, not a history. Soft delete is a column, plus an index that ignores deleted rows.

history.mss.sql · SQL Server 2025
-- 1  a system-versioned temporal table keeps every past version of each row
CREATE TABLE price_list (
  product_id  INT           PRIMARY KEY,
  price       DECIMAL(10,2) NOT NULL,
  valid_from  DATETIME2(0)  GENERATED ALWAYS AS ROW START NOT NULL,
  valid_to    DATETIME2(0)  GENERATED ALWAYS AS ROW END   NOT NULL,
  PERIOD FOR SYSTEM_TIME (valid_from, valid_to)
) WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.price_list_history));

INSERT INTO price_list (product_id, price) VALUES (101, 1299.00);
WAITFOR DELAY '00:00:02';
UPDATE price_list SET price = 1199.00 WHERE product_id = 101;
WAITFOR DELAY '00:00:02';
DECLARE @between_changes DATETIME2(0) = SYSUTCDATETIME();
WAITFOR DELAY '00:00:02';
UPDATE price_list SET price = 1249.00 WHERE product_id = 101;

--    the current row, and every version with the period it was valid for
SELECT product_id, price FROM price_list;
SELECT product_id, price,
       CASE WHEN valid_to = '9999-12-31 23:59:59' THEN 'current' ELSE 'superseded' END AS version
FROM   price_list FOR SYSTEM_TIME ALL
ORDER  BY valid_from;

--    "what was the price at that moment?"
SELECT product_id, price AS price_then FROM price_list FOR SYSTEM_TIME AS OF @between_changes;

ALTER TABLE price_list SET (SYSTEM_VERSIONING = OFF);
DROP TABLE price_list;
DROP TABLE price_list_history;

-- 2  soft delete: uniqueness applies to live rows only, through a filtered unique index
CREATE TABLE accounts_users (
  user_id     INT          PRIMARY KEY,
  email       VARCHAR(100) NOT NULL,
  deleted_at  DATETIME2(0) NULL
);
CREATE UNIQUE INDEX accounts_users_live_email_ux ON accounts_users (email) WHERE deleted_at IS NULL;

INSERT INTO accounts_users VALUES (3, 'kai@example.com', NULL);

history.ora.sql · Oracle 26ai
-- 1  flashback query reads a table as it was, from undo, with no history table
VARIABLE before_scn NUMBER
EXEC SELECT current_scn INTO :before_scn FROM v$database
UPDATE products SET price = 1199.00 WHERE product_id = 101;
COMMIT;
SELECT product_id, price FROM products WHERE product_id = 101;
SELECT product_id, price AS price_a_minute_ago
FROM   products AS OF TIMESTAMP (SYSTIMESTAMP - INTERVAL '1' MINUTE)
WHERE  product_id = 101;
--    and every version since that SCN, with the operation that created it
SELECT versions_operation AS op, price
FROM   products VERSIONS BETWEEN SCN :before_scn AND MAXVALUE
WHERE  product_id = 101
ORDER  BY versions_startscn NULLS FIRST;
UPDATE products SET price = 1299.00 WHERE product_id = 101;
COMMIT;

-- 2  soft delete: a unique index on an expression that is NULL for deleted rows
CREATE TABLE accounts_users (
  user_id     NUMBER        PRIMARY KEY,
  email       VARCHAR2(100) NOT NULL,
  deleted_at  TIMESTAMP(0)  NULL
);
CREATE UNIQUE INDEX accounts_users_live_email_ux
  ON accounts_users (CASE WHEN deleted_at IS NULL THEN email END);

Soft delete leaksEvery query must now remember WHERE deleted_at IS NULL, including the ones written next year. A plain unique index on email would stop a user who deleted their account from signing up again. Both partial indexes above accepted the second kai@example.com and rejected the third. Use a view of live rows, and consider whether "deleted" really means "archived".
Reading the errorOracle reported the duplicate on column SYS_NC00004$: the hidden virtual column behind the function-based index. The constraint name, ACCOUNTS_USERS_LIVE_EMAIL_UX, is the useful part, which is why it is worth naming indexes deliberately.
Say it in the interview"For audit I store history explicitly: a temporal table on SQL Server, or an append-only history table on Oracle, with who and why. Flashback query is for recovering from mistakes within the undo window. Soft delete gets a partial unique index and a view of live rows."
