An index that holds every column a query needs makes the table unnecessary, and one that holds only the rows you query stays tiny

The lookups on the previous slides exist because the index lacks a column the query needs, here total. A covering index includes it, so the query is answered from the index alone. SQL Server adds non-key columns to the leaf with INCLUDE; Oracle has no INCLUDE, so the column joins the key. A filtered or partial index holds only the rows that matter, such as the 0.5% of orders that FAILED. SQL Server writes it as WHERE status = 'FAILED'. Oracle gets the same effect from a function-based index that is NULL for every other row, because entirely-NULL keys are not indexed.

covering.mss.sql · SQL Server 2025
-- total revenue of the 2,500 FAILED orders, with three different indexes on status
CREATE INDEX ix_status          ON big_orders (status);
CREATE INDEX ix_status_covering ON big_orders (status) INCLUDE (total);
CREATE INDEX ix_failed_only     ON big_orders (order_id) INCLUDE (total) WHERE status = 'FAILED';
GO
SET STATISTICS IO ON;
-- 1  key only: SQL Server prefers to scan the table rather than do 2,500 lookups
SELECT SUM(total) AS failed_total FROM big_orders WITH (INDEX (ix_status)) WHERE status = 'FAILED';
-- 2  INCLUDE (total) puts the summed column in the index leaf: no lookups at all
SELECT SUM(total) AS failed_total FROM big_orders WITH (INDEX (ix_status_covering)) WHERE status = 'FAILED';
-- 3  a filtered index holds only the FAILED rows
SELECT SUM(total) AS failed_total FROM big_orders WITH (INDEX (ix_failed_only)) WHERE status = 'FAILED';
SET STATISTICS IO OFF;

-- how big each index is
SELECT i.name AS index_name, SUM(s.used_page_count) AS pages, SUM(s.row_count) AS index_rows
FROM   sys.dm_db_partition_stats s JOIN sys.indexes i ON i.object_id = s.object_id AND i.index_id = s.index_id
WHERE  s.object_id = OBJECT_ID('big_orders')
GROUP  BY i.name ORDER BY pages DESC;
DROP INDEX ix_status ON big_orders;
DROP INDEX ix_status_covering ON big_orders;
DROP INDEX ix_failed_only ON big_orders;

covering.ora.sql · Oracle 26ai
SET SERVEROUTPUT OFF
-- Oracle has no INCLUDE: add the column to the key. NULL keys are not indexed, which gives a partial index.
CREATE INDEX ix_status_total ON big_orders (status, total);
CREATE INDEX ix_failed_only  ON big_orders (CASE WHEN status = 'FAILED' THEN total END);

-- 1  everything the query needs is in the index, so the table is never visited
SELECT /*+ gather_plan_statistics INDEX(o ix_status_total) */ SUM(total) AS failed_total
FROM   big_orders o WHERE status = 'FAILED';
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'BASIC ROWS IOSTATS LAST'));

-- 2  the partial index: only the 2,500 FAILED rows have a non-NULL key; the query repeats the expression
SELECT /*+ gather_plan_statistics */ SUM(CASE WHEN status = 'FAILED' THEN total END) AS failed_total
FROM   big_orders o WHERE CASE WHEN status = 'FAILED' THEN total END IS NOT NULL;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'BASIC ROWS IOSTATS LAST'));

SELECT index_name, leaf_blocks, num_rows FROM user_indexes
WHERE  table_name = 'BIG_ORDERS' ORDER BY leaf_blocks DESC;
DROP INDEX ix_status_total;
DROP INDEX ix_failed_only;

Forcing the index made it worseHinting the plain status index cost 7,678 pages, three times the scan the optimiser had chosen. That is why the optimiser refused it. Fix a slow query by changing the index or the query, not by forcing a plan.
The estimate behind itOracle estimated 100K FAILED rows (E-Rows) against 2,500 actual: without a histogram it assumes the five statuses are equally common. Skewed columns need histograms, which Oracle's statistics job gathers for columns that appear in predicates. With such a bad estimate, plan choices go wrong.
Say it in the interview"For a hot query I build a covering index: filter columns as keys, returned columns in INCLUDE. For queries that only ever look at a small subset, such as unprocessed jobs or failed payments, a filtered index is small and cheap to maintain. Then I confirm in the plan that the key lookup is gone."
