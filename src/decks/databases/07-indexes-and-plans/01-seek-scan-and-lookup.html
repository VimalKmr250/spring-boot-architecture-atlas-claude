An index is a sorted copy of some columns plus a pointer to the row; every extra row it finds costs a lookup

A B-tree index keeps its keys sorted in pages: a root, a few levels of branches, then leaves. A seek walks from the root to the first matching leaf in three or four page reads, then reads along the leaves. A scan reads every page. In SQL Server, a table with a clustered index stores its rows in the clustered index's leaves, by default the primary key; a table without one is a heap. A non-clustered index leaf holds the key plus the clustered key, so each match costs a lookup into the clustered index for the other columns. Oracle tables are heaps by default, and the leaf holds a ROWID. Past a few thousand lookups, scanning the whole table is cheaper.

seek-scan.mss.sql · SQL Server 2025
-- big_orders: 500,000 rows, clustered on order_id
CREATE INDEX big_orders_customer_ix ON big_orders (customer_id);
CREATE INDEX big_orders_status_ix ON big_orders (status);
GO
-- STATISTICS IO reports the 8 KB pages each query read
SET STATISTICS IO ON;

-- 1  by the clustered key: a seek down the B-tree
SELECT order_id, status, total FROM big_orders WHERE order_id = 250000;

-- 2  one customer's 25 orders: seek the customer index, then look up each row
SELECT COUNT(*) AS orders, SUM(total) AS total FROM big_orders WHERE customer_id = 4242;

-- 3  2,500 FAILED orders: 0.5% of the table, and the index on status is not used
SELECT COUNT(*) AS orders, SUM(total) AS total FROM big_orders WHERE status = 'FAILED';

-- 4  the same count without SUM(total): every needed column is in the index
SELECT COUNT(*) AS orders FROM big_orders WHERE status = 'FAILED';
SET STATISTICS IO OFF;
GO
SET SHOWPLAN_TEXT ON;
GO
SELECT COUNT(*) AS orders, SUM(total) AS total FROM big_orders WHERE customer_id = 4242;
SELECT COUNT(*) AS orders, SUM(total) AS total FROM big_orders WHERE status = 'FAILED';
SELECT COUNT(*) AS orders FROM big_orders WHERE status = 'FAILED';
GO
SET SHOWPLAN_TEXT OFF;
GO
DROP INDEX big_orders_customer_ix ON big_orders;
DROP INDEX big_orders_status_ix ON big_orders;

"There is an index, why the scan?"Query 3 matches 0.5% of the table, and the optimiser still scanned. Each lookup is a random read of about three pages, so 2,500 lookups cost more than reading 2,639 pages in order. An index on a column alone helps only when few rows match, or when it covers the query: see covering indexes.
Heaps and clustered tablesOracle's default table is a heap, and an index entry points at the row's physical ROWID; an index-organised table (IOT) is Oracle's clustered equivalent. SQL Server tables are usually clustered on the primary key. A random clustered key, such as a GUID, scatters inserts: see Keys and generated ids.
Say it in the interview"A seek costs the tree height plus one lookup per matching row; a scan costs every page. The optimiser picks by estimated rows, so selectivity, the fraction of rows that match, decides whether an index is used." The B-tree structure itself is on HLD · Storage engines and indexes.
