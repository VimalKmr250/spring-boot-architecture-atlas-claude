Ask Oracle for the plan it actually ran, with real row counts, then compare estimates with actuals

EXPLAIN PLAN shows what the optimiser would do, with estimates only. For a slow query you want the plan it did run. Add the gather_plan_statistics hint, run the query, then call DBMS_XPLAN.DISPLAY_CURSOR in the same session. Every step then shows how many times it started, the rows estimated against the rows produced, and the blocks it read. Below, one customer's orders from the 500,000-row table, first without a suitable index and then with one.

oracle-plan.ora.sql · Oracle 26ai
-- SERVEROUTPUT off, or the "last cursor" is SQL*Plus fetching DBMS_OUTPUT
SET SERVEROUTPUT OFF

-- 1  one customer's recent orders, before any index on customer_id
SELECT /*+ gather_plan_statistics */ COUNT(*) AS orders, SUM(total) AS total
FROM   big_orders
WHERE  customer_id = 4242
AND    placed_at >= TIMESTAMP '2025-06-01 00:00:00';

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'ALLSTATS LAST'));

-- 2  the same query with an index that leads with the equality column
CREATE INDEX big_orders_cust_placed_ix ON big_orders (customer_id, placed_at);

SELECT /*+ gather_plan_statistics */ COUNT(*) AS orders, SUM(total) AS total
FROM   big_orders
WHERE  customer_id = 4242
AND    placed_at >= TIMESTAMP '2025-06-01 00:00:00';

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'ALLSTATS LAST'));

DROP INDEX big_orders_cust_placed_ix;

How to read it

Order
Indentation is the tree: a step feeds the step above it, one level less indented. Start reading at the most indented line.
*
That step has a predicate, listed under Predicate Information by Id.
access
The predicate decided which index entries to read: the index did the work.
filter
The rows were read first and the predicate was applied afterwards: the work was done and then discarded.
Starts
How many times the step ran. A large number under a nested loop is the classic hidden cost.
E-Rows / A-Rows
Estimated rows against actual rows. Within a factor of a few is fine; a factor of 100 means the optimiser chose blind, usually because of stale statistics or a predicate it cannot estimate.
Buffers
Logical reads: the number to compare between two versions of a query. A-Time moves with the cache and the machine.

Before: filter on a full scanStep 2 read every block of the table, 2,425 buffers, to return 8 rows. Both conditions appear as filter. Neither could narrow the read, because no index starts with customer_id.
After: access on a range scanWith (customer_id, placed_at), both conditions became access predicates: 3 index blocks, then 8 table rows, 11 buffers in total. The equality column leads and the range column follows; the column-order slide shows why that order matters.
Two gotchasSET SERVEROUTPUT OFF first: with it on, the last cursor is SQL*Plus fetching DBMS_OUTPUT, and you get that plan instead. And the same SQL_ID got a new plan once the index existed: creating an index invalidates the cached cursors that use the table.
