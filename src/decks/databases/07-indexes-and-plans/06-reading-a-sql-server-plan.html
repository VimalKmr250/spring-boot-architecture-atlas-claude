In a SQL Server plan, read from the most indented operator outwards, and compare estimated rows with actual rows at each step

SQL Server shows plans graphically in SSMS and VS Code; the same tree is available as text, and it is what tools and logs capture. SET SHOWPLAN_TEXT ON shows the estimated plan without running the query. SET STATISTICS PROFILE ON runs it and adds, for every operator, how many rows it really produced and how many times it ran. SET STATISTICS IO ON adds pages read per table, the most reliable number for comparing two versions of a query. Here, revenue per country from July's shipped orders: a seek on a covering date index, hash-joined to the customers.

mssql-plan.mss.sql · SQL Server 2025
-- revenue by country from July's shipped orders; the query lives in a view
CREATE INDEX big_orders_placed_ix ON big_orders (placed_at) INCLUDE (customer_id, status, total);
GO
CREATE VIEW july_shipped_revenue AS
SELECT c.country, COUNT(*) AS orders, SUM(o.total) AS revenue
FROM   big_orders o
JOIN   big_customers c ON c.customer_id = o.customer_id
WHERE  o.placed_at >= CAST('2025-07-01' AS DATETIME2(0))
AND    o.placed_at <  CAST('2025-08-01' AS DATETIME2(0))
AND    o.status = 'SHIPPED'
GROUP  BY c.country;
GO
-- run it with the actual plan: STATISTICS PROFILE adds Rows and Executes to every operator
SET STATISTICS IO ON;
SET STATISTICS PROFILE ON;
SELECT country, orders, revenue FROM july_shipped_revenue ORDER BY revenue DESC;
SET STATISTICS PROFILE OFF;
SET STATISTICS IO OFF;
GO
DROP VIEW july_shipped_revenue;
DROP INDEX big_orders_placed_ix ON big_orders;

How to read it

Shape
Each |-- feeds the operator above it, one level less indented. Data flows upwards; execution starts at the most indented lines.
Seek / Scan
Index Seek with a SEEK: range used the index's order. Index Scan or Clustered Index Scan read all of it. A WHERE: after either is a residual filter applied to every row read.
Lookup
Key Lookup, or a clustered seek marked LOOKUP, under a Nested Loops: one per row. Cover the query to remove it.
Joins
Nested Loops for few outer rows, Hash Match for large unsorted inputs, Merge Join for inputs already sorted on the key.
Rows / Executes
Actual rows and executions. Compare with EstimateRows: a large gap is where the plan went wrong.
Warnings
CONVERT_IMPLICIT in a predicate, spills to tempdb, missing statistics: in the graphical plan, a yellow triangle.

This plan is healthyThe date seek returned 43,072 rows, every shipped order in July, from a covering index in 362 pages; status was checked as a residual WHERE inside the seek. The hash join read all 20,000 customers once (145 pages). The estimate of 55,836 rows was within a third of the actual 43,072, close enough for the right join choice.
Where to look firstThe operator with the largest actual rows, an Executes count in the thousands under a Nested Loops, and any estimate wrong by 10× or more. Query Store keeps plans and their run-time statistics over time, so a sudden plan change can be found and compared with the previous plan.
Say it in the interview"I start with STATISTICS IO to see which table dominates, then the actual plan: scans where I expected seeks, lookups per row, and estimate-against-actual gaps." The Oracle equivalent is Reading an Oracle execution plan.
