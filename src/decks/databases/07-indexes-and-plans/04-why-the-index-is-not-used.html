An index on a column cannot help a predicate on an expression of that column, and an implicit type conversion is an expression

A predicate is sargable (search-argument-able) when the index can be searched for it directly: column = value, column >= value, column LIKE 'abc%'. Wrap the column in a function, such as TRUNC(placed_at), YEAR(placed_at) or UPPER(email), and the index's sort order no longer applies. The most common version is invisible in the code: comparing columns of different types makes the engine convert one side. When it converts the column, every row is converted and checked. Both engines show it in the plan's predicate.

sargable.ora.sql · Oracle 26ai
SET SERVEROUTPUT OFF
CREATE INDEX big_customers_phone_ix ON big_customers (phone);
CREATE INDEX big_orders_placed_ix   ON big_orders (placed_at);

-- 1  phone is VARCHAR2 but the literal is a number: Oracle converts the column, row by row
SELECT /*+ gather_plan_statistics */ customer_id FROM big_customers WHERE phone = 9000004242;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'BASIC ROWS IOSTATS LAST PREDICATE'));

-- 2  the same lookup with a string literal: an index range scan
SELECT /*+ gather_plan_statistics */ customer_id FROM big_customers WHERE phone = '9000004242';
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'BASIC ROWS IOSTATS LAST PREDICATE'));

-- 3  a function on the indexed column hides it; a range on the bare column does not
SELECT /*+ gather_plan_statistics */ COUNT(*) AS orders FROM big_orders WHERE TRUNC(placed_at) = DATE '2025-03-01';
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'BASIC ROWS IOSTATS LAST PREDICATE'));
SELECT /*+ gather_plan_statistics */ COUNT(*) AS orders FROM big_orders
WHERE  placed_at >= DATE '2025-03-01' AND placed_at < DATE '2025-03-02';
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'BASIC ROWS IOSTATS LAST PREDICATE'));

DROP INDEX big_customers_phone_ix;
DROP INDEX big_orders_placed_ix;

CREATE INDEX big_customers_email_ix ON big_customers (email);
GO
SET STATISTICS IO ON;
-- 1  email is VARCHAR; an NVARCHAR parameter makes SQL Server convert the column on every row
DECLARE @unicode NVARCHAR(255) = N'user4242@example.com';
SELECT customer_id FROM big_customers WHERE email = @unicode;

-- 2  the same lookup with a VARCHAR parameter: an index seek
DECLARE @plain VARCHAR(255) = 'user4242@example.com';
SELECT customer_id FROM big_customers WHERE email = @plain;
SET STATISTICS IO OFF;
GO

GO

SELECT customer_id FROM big_customers WHERE email = @unicode;
GO
SET SHOWPLAN_TEXT OFF;
GO

CREATE INDEX big_orders_placed_ix ON big_orders (placed_at);
GO

The Java version of the trapMicrosoft's JDBC driver sends every String parameter as NVARCHAR by default. Against VARCHAR columns, with a SQL collation like this database's, each lookup by email becomes an index scan, exactly as in query 1. Set sendStringParametersAsUnicode=false when the columns are VARCHAR; see Dialect traps.
Precedence decides which side convertsOracle converts the string column to a number, not the number to a string, because numbers rank higher. SQL Server converts VARCHAR to NVARCHAR for the same reason. Whenever the column's type ranks lower than the value's, the column is the side that gets converted, so the fix belongs to whoever sends the value: send it in the column's type.
Say it in the interview"When an indexed query scans, I read the predicate section of the plan. A function or a conversion on the column means the index cannot be sought. I rewrite the predicate so the bare column is compared with a value of its own type, or index the expression."
