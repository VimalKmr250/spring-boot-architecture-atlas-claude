In a composite index, equality columns go first and the range column last, because the index is sorted left to right

An index on (status, placed_at) is sorted by status, and by date within each status, like a phone book sorted by surname, then first name. "FAILED orders in July" is then one contiguous slice: jump to FAILED, then to 1 July, read to 31 July. Reverse the columns and all of July is contiguous, but the FAILED rows are scattered through it, so every July entry must be read and checked. And a query that does not constrain the leading column cannot seek at all. The script forces each index with a hint so the three can be compared on the same query.

column-order.mss.sql · SQL Server 2025
-- one query, three candidate indexes: FAILED orders placed in July 2025
-- (each index is created, measured and dropped in turn)
CREATE INDEX ix_status_placed ON big_orders (status, placed_at) INCLUDE (total);
GO
SET STATISTICS IO ON;
-- 1  equality column first, range column second: one contiguous slice of the index
SELECT COUNT(*) AS orders, SUM(total) AS total FROM big_orders WITH (INDEX (ix_status_placed))
WHERE  status = 'FAILED' AND placed_at >= '2025-07-01' AND placed_at < '2025-08-01';
SET STATISTICS IO OFF;
DROP INDEX ix_status_placed ON big_orders;
GO
CREATE INDEX ix_placed_status ON big_orders (placed_at, status) INCLUDE (total);
GO
SET STATISTICS IO ON;
-- 2  range column first: every July order is read, and status is checked on each
SELECT COUNT(*) AS orders, SUM(total) AS total FROM big_orders WITH (INDEX (ix_placed_status))
WHERE  status = 'FAILED' AND placed_at >= '2025-07-01' AND placed_at < '2025-08-01';
SET STATISTICS IO OFF;
DROP INDEX ix_placed_status ON big_orders;
GO
CREATE INDEX ix_status_placed ON big_orders (status, placed_at) INCLUDE (total);
GO
SET STATISTICS IO ON;
-- 3  the leading column is missing from the query: the index cannot be sought, only scanned
SELECT COUNT(*) AS orders FROM big_orders WITH (INDEX (ix_status_placed))
WHERE  placed_at >= '2025-07-01' AND placed_at < '2025-07-02';
SET STATISTICS IO OFF;
GO
SET SHOWPLAN_TEXT ON;
GO
SELECT COUNT(*) AS orders FROM big_orders WITH (INDEX (ix_status_placed))
WHERE  placed_at >= '2025-07-01' AND placed_at < '2025-07-02';
GO
SET SHOWPLAN_TEXT OFF;
GO
DROP INDEX ix_status_placed ON big_orders;

The missing leading columnQuery 3 asks only for a date, and (status, placed_at) is sorted by status first, so the plan shows an Index Scan with the date as a residual WHERE: 2,219 pages for one day's 2,335 orders. Oracle can sometimes "skip scan" such an index when the leading column has few distinct values, but do not design for it.
One index, several queriesAn index on (a, b, c) serves filters on a, on a, b and on a, b, c: the left prefixes. It does not serve b alone. Before adding an index, check whether an existing one can be extended instead; every index slows every write.
Say it in the interview"Equality columns first, then the range or sort column. If the query also sorts, an index whose order matches the ORDER BY after the equality columns avoids the sort." MongoDB's version of this rule has a name, ESR: see the ESR rule.
