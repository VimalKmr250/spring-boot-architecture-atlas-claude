OFFSET pages get slower the deeper you go; keyset pages cost the same on page 20,000 as on page 1

OFFSET n ROWS FETCH NEXT 20 must produce and discard n rows before returning 20, even with a perfect index, so the cost grows linearly with the page number. Keyset pagination, also called seek pagination, remembers where the previous page ended: the sort key and a unique tie-breaker of its last row. The next page then seeks straight to that point. Below, newest orders first, 20 per page, with an index whose order matches the sort.

paging.mss.sql · SQL Server 2025
-- newest orders first, 20 per page; the index matches the sort and covers the columns shown
CREATE INDEX big_orders_paging_ix ON big_orders (placed_at DESC, order_id DESC) INCLUDE (status, total);
GO
SET STATISTICS IO ON;
-- 1  page 1 with OFFSET
SELECT order_id, placed_at, total FROM big_orders
ORDER  BY placed_at DESC, order_id DESC
OFFSET 0 ROWS FETCH NEXT 20 ROWS ONLY;

-- 2  page 20,000 with OFFSET: 399,980 rows are read and thrown away first
SELECT order_id, placed_at, total FROM big_orders
ORDER  BY placed_at DESC, order_id DESC
OFFSET 399980 ROWS FETCH NEXT 20 ROWS ONLY;

-- 3  the same page by keyset: continue after the last row of page 19,999 (order 100021)
DECLARE @last_placed DATETIME2(0) = '2025-02-12 19:59:37', @last_id INT = 100021;
SELECT TOP (20) order_id, placed_at, total FROM big_orders
WHERE  placed_at < @last_placed OR (placed_at = @last_placed AND order_id < @last_id)
ORDER  BY placed_at DESC, order_id DESC;
SET STATISTICS IO OFF;
DROP INDEX big_orders_paging_ix ON big_orders;

Ties break pagesOrdering by placed_at alone, two orders in the same second could straddle a page boundary, and one of them would appear on both pages or on neither. The tie-breaker order_id makes the order total. The keyset filter needs both parts: placed_at < :p OR (placed_at = :p AND order_id < :id).
The total count"Page 3 of 25,000" needs a COUNT(*) over the whole result, often the most expensive query on the page. Spring Data's Page runs it on every request. Show "more results" instead, or cache an approximate count.
Say it in the interview"For infinite scroll and APIs I use keyset pagination: a unique sort key, an index in that order, and the last row's key as the cursor. OFFSET is fine for small result sets, or when users really need to jump to page N." The MongoDB version is on Covered queries and range pagination.
