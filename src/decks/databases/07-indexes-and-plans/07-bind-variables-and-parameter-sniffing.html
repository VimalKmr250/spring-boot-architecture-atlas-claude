Bind variables let one plan serve every value, which is fast, safe from injection, and occasionally wrong for a skewed value

Every distinct SQL text is parsed and optimised once, then cached. With values pasted into the text as literals, every customer id is a new statement: a parse and optimisation per call, and a shared pool or plan cache full of near-duplicates. With a bind variable (a ? in JDBC, :name in Oracle, @name in T-SQL), the text never changes, so the plan is reused. Reuse has one cost. The plan is optimised for the values seen at its first execution, and SQL Server calls that parameter sniffing. If the data is skewed, the plan for a rare value can be disastrous for a common one.

binds.ora.sql · Oracle 26ai, as a lab user allowed to flush the shared pool
-- lab only: start from an empty statement cache
ALTER SYSTEM FLUSH SHARED_POOL;

-- 1  three literal values: three different statements, each parsed and optimised from scratch
SELECT COUNT(*) AS orders FROM orders WHERE customer_id = 1;
SELECT COUNT(*) AS orders FROM orders WHERE customer_id = 2;
SELECT COUNT(*) AS orders FROM orders WHERE customer_id = 3;

-- 2  one statement with a bind variable, executed three times
VARIABLE cust NUMBER
EXEC :cust := 1
SELECT COUNT(*) AS orders FROM orders WHERE customer_id = :cust;
EXEC :cust := 2
SELECT COUNT(*) AS orders FROM orders WHERE customer_id = :cust;
EXEC :cust := 3
SELECT COUNT(*) AS orders FROM orders WHERE customer_id = :cust;

-- what the shared pool now holds
SELECT executions, sql_text FROM v$sql
WHERE  sql_text LIKE 'SELECT COUNT(*) AS orders FROM orders WHERE customer_id =%'
ORDER  BY sql_text;

binds.mss.sql · SQL Server 2025
CREATE INDEX big_orders_total_ix ON big_orders (total);
GO
CREATE OR ALTER PROCEDURE orders_above @min_total DECIMAL(12,2) AS
  SELECT COUNT(*) AS orders, MAX(placed_at) AS latest FROM big_orders WHERE total > @min_total;
GO
DBCC FREEPROCCACHE WITH NO_INFOMSGS;   -- lab only: start from an empty plan cache
SET STATISTICS IO ON;
-- 1  the first call compiles the plan for its value: very few rows, so seek and look up
EXEC orders_above @min_total = 504.90;
-- 2  the second call reuses that plan for a value that matches every row
EXEC orders_above @min_total = 5.00;
-- 3  the same call, compiled for its own value
EXEC orders_above @min_total = 5.00 WITH RECOMPILE;
SET STATISTICS IO OFF;
GO
DROP PROCEDURE orders_above;
DROP INDEX big_orders_total_ix ON big_orders;
GO
-- 4  SQL injection: input glued into the SQL text becomes code; a parameter stays data
DECLARE @email NVARCHAR(100) = N'x'' OR ''1''=''1';
EXEC (N'SELECT COUNT(*) AS matches FROM customers WHERE email = ''' + @email + N'''');
EXEC sp_executesql N'SELECT COUNT(*) AS matches FROM customers WHERE email = @email',
                   N'@email NVARCHAR(100)', @email = @email;

OPTION (RECOMPILE) / WITH RECOMPILEA fresh plan for every value: 2,639 pages instead of 1,532,419 hereA compilation per call; fine for reports, costly at thousands of calls a second
OPTIMIZE FOR (@p = typical) or UNKNOWNThe plan targets a chosen value, or the averageWrong for the other extreme

Parameter-sensitive plans 2022; Oracle adaptive cursor sharingThe engine keeps several plans for different value rangesAutomatic, but only for skew the statistics reveal
InjectionConcatenated into the SQL text, the input x' OR '1'='1 turned the filter into email = 'x' OR '1'='1' and matched all 10 customers. Passed as a parameter through sp_executesql, the same input was compared as a value and matched 0. In Java: always PreparedStatement with ?, never string concatenation, including in "internal" admin tools.
1.5 million pages for one callThe first call compiled a seek-plus-lookup plan for 90 rows (287 pages). Reused for a value matching 499,990 rows, it performed half a million lookups: 1,532,419 pages, about 580 times the cost of a scan. The same procedure can be fast in testing and slow in production, depending on which call came first after a restart.
Say it in the interview"Bind variables: one parse and one cached plan for all values, and immunity to SQL injection. The trade-off is sniffing on skewed data. I fix the hot case with RECOMPILE or a targeted hint, after confirming it in Query Store or the plan cache."
