NULL means "unknown", so every comparison with it is unknown, and WHERE keeps only rows that are true

SQL logic has three values: TRUE, FALSE and UNKNOWN. Any comparison with NULL, even NULL = NULL, yields UNKNOWN, and WHERE, ON and CHECK treat UNKNOWN differently: the first two drop the row, a CHECK lets it through. That is why referred_by <> 1 counted 3 customers rather than 8: the five with no referrer are neither equal nor unequal to 1. Aggregates skip NULLs, COUNT(*) counts rows, and the engines disagree about where NULLs sort and how many may share a unique column.

nulls.sql · runs on Oracle 26ai and SQL Server 2025
-- 1  "not referred by customer 1" quietly drops everyone with no referrer
SELECT COUNT(*)                                  AS all_customers,
       COUNT(referred_by)                        AS with_referrer,
       SUM(CASE WHEN referred_by <> 1 THEN 1 ELSE 0 END)                       AS not_equal_1,
       SUM(CASE WHEN referred_by <> 1 OR referred_by IS NULL THEN 1 ELSE 0 END) AS not_1_or_null
FROM   customers;

-- 2  NULL is not equal to NULL, and not unequal either
SELECT CASE WHEN NULL = NULL      THEN 'true' ELSE 'not true' END AS null_equals_null,
       CASE WHEN NULL IS NULL     THEN 'true' ELSE 'not true' END AS null_is_null;

-- 3  aggregates skip NULLs, so AVG is over 5 rows, not 10
SELECT AVG(referred_by)           AS avg_ignoring_nulls,
       AVG(COALESCE(referred_by, 0)) AS avg_nulls_as_zero
FROM   customers;

unique-null.mss.sql · SQL Server 2025
CREATE TABLE vouchers (voucher_id INT PRIMARY KEY, code VARCHAR(20) CONSTRAINT vouchers_code_uk UNIQUE);
INSERT INTO vouchers VALUES (1, NULL);
INSERT INTO vouchers VALUES (2, NULL);
GO
-- the fix: a filtered unique index ignores the NULLs
ALTER TABLE vouchers DROP CONSTRAINT vouchers_code_uk;
CREATE UNIQUE INDEX vouchers_code_ux ON vouchers (code) WHERE code IS NOT NULL;
INSERT INTO vouchers VALUES (2, NULL);
SELECT COUNT(*) AS rows_with_null_code FROM vouchers WHERE code IS NULL;
DROP TABLE vouchers;

nulls.js · MongoDB 8.3, mongosh
// null in a filter matches a field that is null and a field that is missing
db.n.drop();
db.n.insertMany([{ _id: 1, referredBy: 7 }, { _id: 2, referredBy: null }, { _id: 3 }]);
show(db.n.find({ referredBy: null }));
print('--');
show(db.n.find({ referredBy: { $exists: false } }));
print('--');
show(db.n.find({ referredBy: { $type: 'null' } }));
print('--');
// $ne: 7 includes the null and the missing ones, unlike SQL's <>
show(db.n.find({ referredBy: { $ne: 7 } }));
db.n.drop();

Integer AVGThe same AVG(referred_by) gave 2.4 on Oracle and 2 on SQL Server, because SQL Server averages an INT column in integer arithmetic. Write AVG(CAST(x AS DECIMAL(10,2))) or AVG(x * 1.0) when the column is an integer.
Sort order and uniqueness differAscending order puts NULLs last on Oracle and first on SQL Server. Oracle accepts NULLS FIRST and NULLS LAST; SQL Server does not, so sort by CASE WHEN x IS NULL THEN 1 ELSE 0 END, x. A SQL Server UNIQUE allows one NULL; a filtered unique index allows any number.
In MongoDB, null also means missing{ referredBy: null } matched the explicit null and the absent field. Use $exists or $type: 'null' to tell them apart. Unlike SQL's <>, $ne: 7 returns both of those documents.
