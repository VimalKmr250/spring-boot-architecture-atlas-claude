Validation in the application can be bypassed by a bug or a second service; a constraint cannot

Primary keys, unique keys, foreign keys, CHECK and NOT NULL are rules the database enforces on every write, whichever program makes it. They also make good error reports. Each statement below breaks one rule of the running example's schema, and each engine names the constraint it hit. With named constraints, an application can map the error to a precise message, for example "that email is already registered", instead of a generic 500. MongoDB has two equivalents: unique indexes, and $jsonSchema validation on a collection.

-- each statement breaks one rule of the running example's schema

-- duplicate email
INSERT INTO customers (customer_id, name, email, country, tier, created_at)
VALUES (11, 'Asha R.', 'asha@example.com', 'IN', 'GOLD', SYSTIMESTAMP);

-- no such customer
INSERT INTO orders (customer_id, status, placed_at, total)
VALUES (999, 'PENDING', SYSTIMESTAMP, 10);

-- qty must be > 0
INSERT INTO order_items (order_id, line_no, product_id, qty, unit_price)
VALUES (1001, 3, 103, 0, 29.90);

-- not an allowed status
UPDATE orders SET status = 'LOST' WHERE order_id = 1001;

-- name is required
INSERT INTO customers (customer_id, name, email, country, tier, created_at)
VALUES (12, NULL, 'x@example.com', 'IN', 'GOLD', SYSTIMESTAMP);

-- orders still point at it
DELETE FROM customers WHERE customer_id = 1;

constraints.js · MongoDB 8.3, mongosh
// a unique index is MongoDB's unique constraint
try { db.customers.insertOne({ _id: 11, name: 'Asha R.', email: 'asha@example.com' }); }
catch (e) { print(e.message); }

// $jsonSchema validation, added to an existing collection
db.runCommand({ collMod: 'payments', validationLevel: 'strict', validator: { $jsonSchema: {
  bsonType: 'object',
  required: ['orderId', 'idempotencyKey', 'status', 'amount'],
  properties: {
    status: { enum: ['AUTHORIZED', 'CAPTURED', 'FAILED', 'REFUNDED'] },
    amount: { bsonType: 'decimal', minimum: Decimal128('0') }
  } } } });
try { db.payments.insertOne({ _id: 99, orderId: 1001, idempotencyKey: 'pay-1001-9', status: 'LOST', amount: 10 }); }
catch (e) { print(e.message); printjson(e.errInfo.details.schemaRulesNotSatisfied); }

// put the collection back the way the other slides expect it
db.runCommand({ collMod: 'payments', validator: {}, validationLevel: 'off' });

Index your foreign keysA foreign key does not create an index on the child column. Without one, deleting a customer scans orders to look for children. On Oracle it is worse: deleting a parent row, or changing its key, briefly takes a table-level lock on the child table, which blocks other sessions writing orders. The running example indexes orders.customer_id for both reasons.
MongoDB enforces lessNothing checks that orderId in a payment matches a real order. References are the application's job, or a reason to embed. Schema validation is opt-in per collection, and validationAction: 'warn' only logs, which is useful while migrating old documents.
Say it in the interview"I validate in the application for good messages, and I keep constraints in the database for correctness, because the application is not the only writer. I name constraints so the error can be mapped, and I treat a unique-key violation as a normal outcome: it is how idempotent inserts work."
