Generated keys are unique, not gapless, and a random key scatters every insert across the index

A natural key is a real-world identifier, such as an email or a SKU. A surrogate key is a meaningless number the database generates. Most application tables use a surrogate primary key, and protect the natural key with a UNIQUE constraint, because natural keys change and are often composite. Oracle and SQL Server both offer identity columns and standalone sequences. Both hand out numbers outside the transaction, so a rollback leaves a gap. MongoDB's default _id is an ObjectId, generated by the driver, that starts with its creation time.

ids.ora.sql · Oracle 26ai
-- 1  an identity column is a sequence the table owns; a rolled-back insert still uses up its number
CREATE TABLE refunds (
  refund_id   NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payment_id  NUMBER NOT NULL,
  amount      NUMBER(12,2) NOT NULL
);
INSERT INTO refunds (payment_id, amount) VALUES (12, 449.00);
COMMIT;
INSERT INTO refunds (payment_id, amount) VALUES (16, 50.00);
ROLLBACK;
INSERT INTO refunds (payment_id, amount) VALUES (16, 50.00);
COMMIT;
SELECT refund_id, payment_id, amount FROM refunds ORDER BY refund_id;

-- 2  ALWAYS means the database chooses: supplying a value is an error
INSERT INTO refunds (refund_id, payment_id, amount) VALUES (99, 1, 1.00);
DROP TABLE refunds PURGE;

-- 3  a standalone sequence can be shared and read ahead of the insert
CREATE SEQUENCE ticket_seq START WITH 1000 INCREMENT BY 1 CACHE 20;
SELECT ticket_seq.NEXTVAL AS first_call, ticket_seq.NEXTVAL AS same_row FROM dual;
SELECT ticket_seq.NEXTVAL AS second_call FROM dual;
DROP SEQUENCE ticket_seq;

ids.mss.sql · SQL Server 2025
-- 1  IDENTITY: a rolled-back insert still uses up its number
CREATE TABLE refunds (
  refund_id   INT IDENTITY(1, 1) PRIMARY KEY,
  payment_id  INT NOT NULL,
  amount      DECIMAL(12,2) NOT NULL
);
INSERT INTO refunds (payment_id, amount) VALUES (12, 449.00);
BEGIN TRANSACTION;
INSERT INTO refunds (payment_id, amount) VALUES (16, 50.00);
ROLLBACK;
INSERT INTO refunds (payment_id, amount) VALUES (16, 50.00);
SELECT refund_id, payment_id, amount FROM refunds ORDER BY refund_id;

-- 2  supplying a value needs IDENTITY_INSERT
INSERT INTO refunds (refund_id, payment_id, amount) VALUES (99, 1, 1.00);
DROP TABLE refunds;

-- 3  a random GUID as the clustered key against a sequential one, 50,000 rows each
CREATE TABLE guid_random     (id UNIQUEIDENTIFIER NOT NULL DEFAULT NEWID() PRIMARY KEY CLUSTERED, pad CHAR(200) NOT NULL DEFAULT '');
CREATE TABLE guid_sequential (id UNIQUEIDENTIFIER NOT NULL DEFAULT NEWSEQUENTIALID() PRIMARY KEY CLUSTERED, pad CHAR(200) NOT NULL DEFAULT '');
SET NOCOUNT ON;
BEGIN TRANSACTION;
DECLARE @i INT = 0;
WHILE @i < 50000
BEGIN
  INSERT INTO guid_random DEFAULT VALUES;
  INSERT INTO guid_sequential DEFAULT VALUES;
  SET @i += 1;
END;
COMMIT;
SET NOCOUNT OFF;
SELECT OBJECT_NAME(s.object_id)                        AS table_name,
       s.page_count                                     AS pages,
       CAST(s.avg_page_space_used_in_percent AS DECIMAL(5,1)) AS page_fullness_pct,
       CAST(s.avg_fragmentation_in_percent AS DECIMAL(5,1))   AS fragmentation_pct
FROM   sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'DETAILED') s
WHERE  s.object_id IN (OBJECT_ID('guid_random'), OBJECT_ID('guid_sequential')) AND s.index_level = 0
ORDER  BY table_name DESC;
DROP TABLE guid_random;
DROP TABLE guid_sequential;

KeyGood atCosts
Identity or sequence (BIGINT)Small, ordered, cheap to index. Every insert lands at the right-hand end of the index.Guessable in URLs. Needs a database round trip, unless a sequence is read ahead in batches; that is what Hibernate's allocationSize does.
Random UUID (v4, NEWID())Generated anywhere, without coordination; safe to expose.16 bytes, and random inserts: 2,082 pages at 67% full against 1,429 at 97% above, with 99% fragmentation.
Time-ordered UUID (v7) or ObjectIdGenerated anywhere and roughly increasing, so inserts stay at the end of the index.Reveals the creation time. Ordering across machines is only approximate.
Natural key (email, SKU)No extra column; meaningful in joins.Changes, such as a new email, ripple into every referencing row. Enforce it with a UNIQUE constraint instead.
The gap is not a bugRefund 2 was used by the rolled-back insert, and it will never be reused. Sequences are non-transactional so that concurrent inserts never wait for each other. If the business needs gapless invoice numbers, assign them in a separate, serialised step, not from a sequence.
Random keys and clustered indexesIn SQL Server the primary key is the clustered index by default, so a random GUID key decides where each row is physically stored. Every insert lands on a random page and splits it, which explains the fragmentation above. Use NEWSEQUENTIALID(), a UUIDv7 generated by the application, or keep the GUID as a non-clustered unique column.
Say it in the interview"Surrogate BIGINT keys from a sequence for internal tables, with natural keys protected by unique constraints. Time-ordered UUIDs when ids are created outside the database or exposed publicly. Never promise gapless ids."
