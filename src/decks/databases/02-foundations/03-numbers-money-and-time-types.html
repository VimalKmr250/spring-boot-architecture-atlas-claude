Money needs an exact decimal type, and a date needs a range rather than an equals sign

Choosing a column type looks like a DBA decision, but the bugs it causes show up in application code. Totals come out a cent off. Integer division drops the fraction. A DATE that looks like midnight is not. A timestamp silently rounds to the next day. Each engine has its own version of each trap, so the scripts below are written per engine, and each ran as shown.

types.ora.sql · Oracle 26ai
-- 1  binary floating point against exact decimal
SELECT TO_CHAR(TO_BINARY_DOUBLE(0.1) + TO_BINARY_DOUBLE(0.2)) AS binary_double,
       TO_CHAR(0.1 + 0.2)                                     AS number_type
FROM   dual;

-- 2  dividing integers
SELECT 7 / 2 AS seven_halves FROM dual;

-- 3  a DATE always carries a time of day, even when the display hides it
SELECT CAST(placed_at AS DATE)                                AS placed_date,
       TO_CHAR(CAST(placed_at AS DATE), 'YYYY-MM-DD HH24:MI') AS really,
       CASE WHEN CAST(placed_at AS DATE) = DATE '2026-01-05'
            THEN 'equal' ELSE 'not equal' END                 AS same_as_jan_5
FROM   orders
WHERE  order_id = 1001;

-- 4  the half-open range that finds it
SELECT COUNT(*) AS orders_on_jan_5
FROM   orders
WHERE  placed_at >= DATE '2026-01-05' AND placed_at < DATE '2026-01-06';

types.mss.sql · SQL Server 2025
-- 1  binary floating point against exact decimal
SELECT CAST(0.1 AS FLOAT) + CAST(0.2 AS FLOAT)         AS float_type,
       CAST(0.1 AS DECIMAL(9,2)) + CAST(0.2 AS DECIMAL(9,2)) AS decimal_type;

-- 2  dividing integers
SELECT 7 / 2 AS seven_halves, 7 / 2.0 AS with_a_decimal;

-- 3  MONEY keeps four decimal places through every step
DECLARE @m MONEY = 100, @d DECIMAL(19,4) = 100;
SELECT @m / 3 * 3 AS money_type, @d / 3 * 3 AS decimal_type;

-- 4  DATETIME rounds to 1/300 of a second; DATETIME2 does not
SELECT CAST('2026-01-05 23:59:59.999' AS DATETIME)     AS datetime_type,
       CAST('2026-01-05 23:59:59.999' AS DATETIME2(3)) AS datetime2_type;

Four traps, all shown above0.1 + 0.2 in binary floating point is 0.30000000000000004 in every engine. 7 / 2 is 3 in SQL Server, because both operands are integers, and 3.5 in Oracle. MONEY keeps 4 decimals at every step, so 100 / 3 × 3 is 99.9999. And DATETIME turned 23:59:59.999 into the next day.
Oracle's DATE has a clockThe display showed 2026-01-05, yet the value was not equal to DATE '2026-01-05', because it also holds 09:12. Filter with a half-open range: >= day AND < day + 1. TRUNC(col) = day also works, but it cannot use a plain index on the column.
Say it in the interview"Money goes in an exact decimal type: NUMBER, DECIMAL or Decimal128, mapped to BigDecimal in Java. Instants go in UTC. I query time with half-open ranges so the boundary second belongs to exactly one day." Java's side of the same story is on Numbers that bite.
