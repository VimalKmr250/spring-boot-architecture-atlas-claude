On SQL Server, a failed statement inside a transaction does not end the transaction, unless XACT_ABORT says so

A transfer debits one wallet and credits another, and both must happen or neither. Here the debit breaks a CHECK (balance >= 0): wallet 2 holds 300 and is asked for 400. What happens next depends on the engine. SQL Server, by default, rolls back only the failing statement and carries on. The procedure then commits the credit alone, and money appears from nowhere. SET XACT_ABORT ON makes any runtime error roll back the whole transaction. Oracle treats a call from the client as a unit: an unhandled exception undoes everything the call did.

errors.mss.sql · SQL Server 2025
-- move 400 from wallet 2 (balance 300) to wallet 1; a CHECK forbids negative balances
UPDATE accounts SET balance = CASE account_id WHEN 1 THEN 500 ELSE 300 END WHERE account_id IN (1, 2);
ALTER TABLE accounts ADD CONSTRAINT accounts_balance_ck CHECK (balance >= 0);
GO
CREATE OR ALTER PROCEDURE transfer @from INT, @to INT, @amount DECIMAL(12,2)
AS
BEGIN
  BEGIN TRANSACTION;
  UPDATE accounts SET balance = balance + @amount WHERE account_id = @to;
  UPDATE accounts SET balance = balance - @amount WHERE account_id = @from;
  COMMIT;
END;
GO
-- 1  default settings: the failed UPDATE is rolled back, the transaction is not
EXEC transfer @from = 2, @to = 1, @amount = 400;
SELECT account_id, balance FROM accounts WHERE account_id IN (1, 2);
UPDATE accounts SET balance = 500 WHERE account_id = 1;
GO
-- 2  XACT_ABORT ON: any runtime error rolls back the whole transaction
SET XACT_ABORT ON;
EXEC transfer @from = 2, @to = 1, @amount = 400;
GO
SELECT account_id, balance FROM accounts WHERE account_id IN (1, 2);
GO
-- 3  TRY/CATCH: roll back if a transaction is open, then re-raise with THROW
CREATE OR ALTER PROCEDURE transfer @from INT, @to INT, @amount DECIMAL(12,2)
AS
BEGIN
  SET XACT_ABORT ON;
  BEGIN TRY
    BEGIN TRANSACTION;
    UPDATE accounts SET balance = balance + @amount WHERE account_id = @to;
    UPDATE accounts SET balance = balance - @amount WHERE account_id = @from;
    COMMIT;
  END TRY
  BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK;
    THROW;
  END CATCH;
END;
GO
EXEC transfer @from = 2, @to = 1, @amount = 400;
GO
SELECT account_id, balance FROM accounts WHERE account_id IN (1, 2);
DROP PROCEDURE transfer;
ALTER TABLE accounts DROP CONSTRAINT accounts_balance_ck;

errors.ora.sql · Oracle 26ai
-- move 400 from wallet 2 (balance 300) to wallet 1; a CHECK forbids negative balances
UPDATE accounts SET balance = CASE account_id WHEN 1 THEN 500 ELSE 300 END WHERE account_id IN (1, 2);
COMMIT;
ALTER TABLE accounts ADD CONSTRAINT accounts_balance_ck CHECK (balance >= 0);
CREATE TABLE error_log (logged_at TIMESTAMP DEFAULT SYSTIMESTAMP, message VARCHAR2(400));

-- an autonomous transaction commits on its own, whatever happens to the caller's
CREATE OR REPLACE PROCEDURE log_error(p_message VARCHAR2) IS
  PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
  INSERT INTO error_log (message) VALUES (p_message);
  COMMIT;
END;
/
CREATE OR REPLACE PROCEDURE transfer(p_from NUMBER, p_to NUMBER, p_amount NUMBER) IS
BEGIN
  UPDATE accounts SET balance = balance + p_amount WHERE account_id = p_to;
  UPDATE accounts SET balance = balance - p_amount WHERE account_id = p_from;
EXCEPTION
  WHEN OTHERS THEN
    log_error('transfer ' || p_from || '->' || p_to || ': ' || SQLERRM);
    RAISE;
END;
/
-- 1  the call fails: Oracle undoes everything the call did, not just the failing statement
EXEC transfer(2, 1, 400)
SELECT account_id, balance FROM accounts WHERE account_id IN (1, 2);
ROLLBACK;

-- 2  the caller rolled back, but the autonomous log entry survived
SELECT message FROM error_log;

DROP PROCEDURE transfer;
DROP PROCEDURE log_error;
DROP TABLE error_log PURGE;
ALTER TABLE accounts DROP CONSTRAINT accounts_balance_ck;

SQL Server, by defaultEffect of an error
Most runtime errors (constraint, conversion of a value)The statement is undone; the transaction stays open; the next statement runs
Some errors (deadlock 1205, certain conversions)The batch is aborted and the transaction rolled back
Compile errors (unknown column)Nothing in the batch runs
With SET XACT_ABORT ONAny runtime error rolls back the transaction and ends the batch
OracleEffect of an error
A failing SQL statementUndone; earlier statements in the transaction stay, uncommitted
A PL/SQL call that raises an unhandled exceptionEverything the call did is undone
An exception caught with WHEN OTHERS and not re-raisedThe call "succeeds": its partial work stays. A classic bug
PRAGMA AUTONOMOUS_TRANSACTIONIts own commit, independent of the caller: the error log survived the rollback
The half transferWithout XACT_ABORT, wallet 1 went from 500 to 900 while wallet 2 stayed at 300: the procedure's COMMIT ran after the failed debit. Put SET XACT_ABORT ON at the top of every T-SQL procedure that opens a transaction.
Swallowed exceptionsEXCEPTION WHEN OTHERS THEN NULL in PL/SQL, or a CATCH block without THROW in T-SQL, turns a failure into partial success. Log and re-raise, as both versions do here, unless the code can genuinely recover.
Say it in the interview"In T-SQL: SET XACT_ABORT ON, BEGIN TRY, and in CATCH roll back if @@TRANCOUNT > 0 and THROW. In PL/SQL: let exceptions propagate, and use an autonomous transaction only for logging. Commit in the caller that owns the unit of work." The Spring side is on Transactions.
