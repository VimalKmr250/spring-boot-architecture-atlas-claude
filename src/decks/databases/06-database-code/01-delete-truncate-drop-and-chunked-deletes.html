DELETE removes rows, TRUNCATE empties the table, DROP removes it, and only one of the engines can roll back a TRUNCATE

The question comes up in almost every SQL interview. The developer's answer is about consequences. DELETE is row-by-row DML: it can filter, it fires triggers, it is logged per row, and it is rolled back like any other change. TRUNCATE deallocates the table's storage in one step: no filter, no triggers, very fast. On Oracle it is DDL that commits, and on SQL Server it can be rolled back. DROP removes the table itself. Deleting millions of old rows is a fourth case: do it in chunks, each its own transaction.

truncate.ora.sql · Oracle 26ai
CREATE TABLE payments_copy AS SELECT * FROM payments;

-- 1  DELETE is ordinary DML: it can be rolled back
DELETE FROM payments_copy;
ROLLBACK;
SELECT COUNT(*) AS after_delete_rollback FROM payments_copy;

-- 2  TRUNCATE is DDL: it commits before and after, so ROLLBACK has nothing to undo
TRUNCATE TABLE payments_copy;
ROLLBACK;
SELECT COUNT(*) AS after_truncate_rollback FROM payments_copy;

-- 3  neither TRUNCATE nor DROP is allowed while a foreign key points at the table
TRUNCATE TABLE orders;
DROP TABLE payments_copy PURGE;

truncate.mss.sql · SQL Server 2025
SELECT * INTO payments_copy FROM payments;

-- 1  DELETE is ordinary DML: it can be rolled back
BEGIN TRANSACTION;
DELETE FROM payments_copy;
ROLLBACK;
SELECT COUNT(*) AS after_delete_rollback FROM payments_copy;

-- 2  TRUNCATE is logged and transactional in SQL Server: it can be rolled back too
BEGIN TRANSACTION;
TRUNCATE TABLE payments_copy;
ROLLBACK;
SELECT COUNT(*) AS after_truncate_rollback FROM payments_copy;

-- 3  neither TRUNCATE nor DROP is allowed while a foreign key points at the table
TRUNCATE TABLE orders;
GO
DROP TABLE payments_copy;

chunked-delete.mss.sql · SQL Server 2025
-- retention: remove samples older than 3 March from a 360,000-row copy, 50,000 rows per transaction
SELECT * INTO metrics_copy FROM big_metrics WHERE ts < '2026-03-06';
SET NOCOUNT ON;
DECLARE @deleted INT = 1, @batches INT = 0, @total INT = 0;
WHILE @deleted > 0
BEGIN
  DELETE TOP (50000) FROM metrics_copy WHERE ts < '2026-03-03';
  SET @deleted = @@ROWCOUNT;
  SET @total += @deleted;
  IF @deleted > 0 SET @batches += 1;
END;
SET NOCOUNT OFF;
SELECT @batches AS batches, @total AS rows_deleted, (SELECT COUNT(*) FROM metrics_copy) AS rows_left;
DROP TABLE metrics_copy;

The Oracle versionchunked-delete.ora.sql loops in PL/SQL with ROWNUM <= 50000 and a COMMIT per batch. It printed "3 batches, 144000 rows deleted" and left the same 216,000 rows.
One huge DELETEDeleting millions of rows in one statement holds locks on all of them until it ends; on SQL Server, past about 5,000 locks it escalates to a table lock. It writes undo or log for every row, and rolling it back after a failure takes as long again. Batches keep each transaction small, let other sessions in between, and can stop and resume.
Better than deletingFor time-based retention, partition the table by day or month and drop or truncate whole partitions: a metadata operation instead of a million row deletes. See the monitoring case study.
Say it in the interview"DELETE is DML: filtered, logged per row, fires triggers, can be rolled back. TRUNCATE is DDL: all rows, minimal logging, no triggers. It auto-commits on Oracle but can be rolled back on SQL Server, and it is blocked by incoming foreign keys. DROP removes the table."
