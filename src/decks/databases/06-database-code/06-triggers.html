A trigger is code that runs on someone else's statement: invisible to the caller, and easy to write for one row only

A trigger fires on INSERT, UPDATE or DELETE and runs inside the same transaction. That makes it a reliable place for audit rows and for derived values: nothing can bypass it. It is also code the application developer never sees. It adds work and locks to every write, and the two engines punish two different mistakes. Oracle row-level triggers may not query the table being changed (ORA-04091, the "mutating table"). SQL Server triggers fire once per statement, so a trigger that assumes one row silently mishandles a multi-row insert.

triggers.ora.sql · Oracle 26ai
-- keep orders.total in step with order_items, from a row-level trigger
CREATE OR REPLACE TRIGGER order_items_total_trg
AFTER INSERT OR UPDATE OR DELETE ON order_items
FOR EACH ROW
BEGIN
  UPDATE orders
  SET    total = (SELECT SUM(qty * unit_price) FROM order_items WHERE order_id = :NEW.order_id)
  WHERE  order_id = :NEW.order_id;
END;
/
-- a row trigger may not read the table whose change fired it
INSERT INTO order_items VALUES (1018, 2, 110, 1, 24.00);

-- a compound trigger collects the ids per row and recalculates once, after the statement
CREATE OR REPLACE TRIGGER order_items_total_trg
FOR INSERT OR UPDATE OR DELETE ON order_items
COMPOUND TRIGGER
  TYPE id_set IS TABLE OF BOOLEAN INDEX BY PLS_INTEGER;
  touched id_set;
  AFTER EACH ROW IS
  BEGIN
    touched(NVL(:NEW.order_id, :OLD.order_id)) := TRUE;
  END AFTER EACH ROW;
  AFTER STATEMENT IS
    id PLS_INTEGER := touched.FIRST;
  BEGIN
    WHILE id IS NOT NULL LOOP
      UPDATE orders SET total = (SELECT SUM(qty * unit_price) FROM order_items WHERE order_id = id)
      WHERE  order_id = id;
      id := touched.NEXT(id);
    END LOOP;
  END AFTER STATEMENT;
END order_items_total_trg;
/
INSERT INTO order_items VALUES (1018, 2, 110, 1, 24.00);
SELECT order_id, total FROM orders WHERE order_id = 1018;
ROLLBACK;
DROP TRIGGER order_items_total_trg;

triggers.mss.sql · SQL Server 2025
-- keep orders.total in step with order_items, written as if one row changes at a time
CREATE OR ALTER TRIGGER order_items_total_tr ON order_items AFTER INSERT AS
BEGIN
  DECLARE @order_id INT = (SELECT TOP (1) order_id FROM inserted);
  UPDATE orders
  SET    total = (SELECT SUM(qty * unit_price) FROM order_items WHERE order_id = @order_id)
  WHERE  order_id = @order_id;
END;
GO
-- one INSERT statement adds lines to two orders: only one total is updated
BEGIN TRANSACTION;
INSERT INTO order_items VALUES (1018, 2, 110, 1, 24.00), (1017, 2, 110, 1, 24.00);
SELECT o.order_id, o.total, SUM(i.qty * i.unit_price) AS from_lines
FROM   orders o JOIN order_items i ON i.order_id = o.order_id
WHERE  o.order_id IN (1017, 1018) GROUP BY o.order_id, o.total;
ROLLBACK;
GO
-- set-based: join to the inserted pseudo-table, so every affected order is recalculated
CREATE OR ALTER TRIGGER order_items_total_tr ON order_items AFTER INSERT AS
BEGIN
  UPDATE o
  SET    total = (SELECT SUM(qty * unit_price) FROM order_items WHERE order_id = o.order_id)
  FROM   orders o
  WHERE  o.order_id IN (SELECT order_id FROM inserted);
END;
GO
BEGIN TRANSACTION;
INSERT INTO order_items VALUES (1018, 2, 110, 1, 24.00), (1017, 2, 110, 1, 24.00);
SELECT o.order_id, o.total, SUM(i.qty * i.unit_price) AS from_lines
FROM   orders o JOIN order_items i ON i.order_id = o.order_id
WHERE  o.order_id IN (1017, 1018) GROUP BY o.order_id, o.total;
ROLLBACK;
GO
DROP TRIGGER order_items_total_tr;

The one-row triggerOne INSERT added a line to order 1017 and a line to 1018. The first trigger picked one order id from inserted, so order 1018's total stayed at 59.00 against 83.00 in its lines, with no error. The set-based version joins to inserted and fixes both. In Oracle, the compound trigger collects ids per row and recalculates once per statement.
Hidden costTriggers run for every write, including bulk loads and migrations. They hold the writer's locks longer, can cascade into other triggers, and disappear from the code the team reads. Avoid business logic in triggers; keep them for audit and simple derived columns, and document them where the application code lives.
Say it in the interview"The mutating-table error, ORA-04091, means a row-level trigger read the table it fires on. The fix is a compound trigger, or moving the logic out of the trigger. On SQL Server I always write triggers against the whole inserted and deleted sets, never a single variable."
