A view saves typing; a materialised view saves work, and the price is either staleness or slower writes

A plain view is a stored query: reading it runs the query, so it is always current and costs the same as the query. It is useful for hiding joins, restricting columns, or giving soft-deleted tables a "live rows" face. A materialised view stores the result. Oracle refreshes it on demand, on a schedule or on commit, so in between it can be stale. SQL Server's indexed view takes the other trade-off: it is updated inside every write to its base tables, never stale, and every write pays for it.

views.ora.sql · Oracle 26ai
-- 1  a view is a stored query: always current, computed on every read
CREATE OR REPLACE VIEW live_customers AS
  SELECT customer_id, name, tier FROM customers WHERE tier IN ('GOLD', 'SILVER');

-- 2  a materialised view stores the result; this one is refreshed on demand
CREATE MATERIALIZED VIEW revenue_by_product
  BUILD IMMEDIATE REFRESH COMPLETE ON DEMAND AS
  SELECT product_id, SUM(qty * unit_price) AS revenue, COUNT(*) AS lines
  FROM   order_items GROUP BY product_id;

INSERT INTO order_items VALUES (1018, 2, 110, 1, 24.00);
COMMIT;
SELECT revenue, lines FROM revenue_by_product WHERE product_id = 110;
EXEC DBMS_MVIEW.REFRESH('REVENUE_BY_PRODUCT')
SELECT revenue, lines FROM revenue_by_product WHERE product_id = 110;

DELETE FROM order_items WHERE order_id = 1018 AND line_no = 2;
COMMIT;
DROP MATERIALIZED VIEW revenue_by_product;
DROP VIEW live_customers;

views.mss.sql · SQL Server 2025
-- an indexed view: SCHEMABINDING, COUNT_BIG(*) and a unique clustered index make SQL Server store it
CREATE VIEW dbo.revenue_by_product WITH SCHEMABINDING AS
  SELECT product_id, SUM(qty * unit_price) AS revenue, COUNT_BIG(*) AS lines
  FROM   dbo.order_items GROUP BY product_id;
GO
CREATE UNIQUE CLUSTERED INDEX revenue_by_product_ux ON dbo.revenue_by_product (product_id);
GO
-- it is maintained inside the same transaction as the base table: never stale
BEGIN TRANSACTION;
SELECT revenue, lines FROM dbo.revenue_by_product WITH (NOEXPAND) WHERE product_id = 110;
INSERT INTO order_items VALUES (1018, 2, 110, 1, 24.00);
SELECT revenue, lines FROM dbo.revenue_by_product WITH (NOEXPAND) WHERE product_id = 110;
ROLLBACK;
DROP VIEW dbo.revenue_by_product;

Stale on purposeAfter the committed insert, the materialised view still said 192.00 and 4 lines until DBMS_MVIEW.REFRESH ran. A dashboard over it shows yesterday's numbers if nobody schedules the refresh, and a scheduled refresh can collide with peak load.
The write taxThe indexed view changed from 192.00 to 216.00 inside the inserting transaction. That is consistent, but every order line written now also updates the view's row for its product: a hot row if many orders contain the same product.
Say it in the interview"Views for encapsulation and security, materialised or indexed views for expensive aggregates read far more often than the data changes. I decide how stale the result may be, then pick refresh-on-demand, on-commit, or a synchronous indexed view." Read models outside the database are on Read models.
