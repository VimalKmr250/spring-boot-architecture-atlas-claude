Drill: "the two highest-paid people in each department", in one $group stage with $topN

Since MongoDB 5.2, $group has accumulators that keep only the best documents of each group: $top and $topN, with $bottom, $bottomN, $firstN and $lastN beside them. Each takes its own sortBy, so no earlier $sort is needed. For ties, $setWindowFields brings SQL's ranking functions, including $denseRank. The third query answers the e-commerce version: the best-selling product in each top-level category, computed from the order lines embedded in each order.

top-n.js · MongoDB 8.3, mongosh
// 1  the two highest-paid people in each department: $topN inside $group (MongoDB 5.2+)
show(db.employees.aggregate([
  { $group: { _id: '$dept',
              top2: { $topN: { n: 2, sortBy: { salary: -1 }, output: { name: '$name', salary: '$salary' } } } } },
  { $sort: { _id: 1 } }
]));

// 2  ties: the top three salary levels with $denseRank, so people on the same salary share a place
show(db.employees.aggregate([
  { $setWindowFields: { partitionBy: '$dept', sortBy: { salary: -1 }, output: { rnk: { $denseRank: {} } } } },
  { $match: { rnk: { $lte: 3 }, dept: { $in: ['Engineering', 'Payments'] } } },
  { $project: { _id: 0, dept: 1, name: 1, salary: 1, rnk: 1 } },
  { $sort: { dept: 1, rnk: 1, name: 1 } }
]));

// 3  the best-selling product per top-level category, from the embedded order lines
show(db.orders.aggregate([
  { $match: { status: { $in: ['PAID', 'SHIPPED'] } } },
  { $unwind: '$items' },
  { $lookup: { from: 'products', localField: 'items.productId', foreignField: '_id', as: 'p' } },
  { $group: { _id: { category: { $first: { $first: '$p.categoryPath' } }, sku: '$items.sku' },
              revenue: { $sum: { $multiply: ['$items.qty', '$items.unitPrice'] } } } },
  { $group: { _id: '$_id.category', best: { $top: { sortBy: { revenue: -1 }, output: { sku: '$_id.sku', revenue: '$revenue' } } } } },
  { $sort: { _id: 1 } }
]));

Complexity

$topN keeps at most N documents per group while it streams, so memory grows with the number of groups, not the size of the collection. The pre-5.2 $push then $slice builds the whole group in memory first. Query 3 runs a $lookup per order line, served by the index on products._id.

Follow-ups

"A department with one person?" Executive returns a one-element array, not an error. "Ties for second place?" $topN picks one arbitrarily, so use $denseRank as query 2 does: Ravi and Sara share third place. "Avoid the $lookup?" Copy the top-level category into each order line when the order is written: the extended reference pattern.

Say it in the interview"$group by the department with $topN, n: 2, sortBy salary descending. If ties must be kept, $setWindowFields with $denseRank and a $match on the rank. And a $match at the start so an index cuts the input."
