Drill: "sign-ups contain the same email in different cases: find them, keep the earliest, and stop it happening again"

The same three parts as the SQL drill, written as a pipeline. Find: $group on $toLower of the email, collect the ids with $push, keep groups with more than one. Sorting by sign-up time first means the first id in each list is the one to keep. Delete: every id after the first. Prevent: a unique index with a case-insensitive collation (strength 2), so CHEN@… and chen@… count as the same key.

duplicates.js · MongoDB 8.3, mongosh
db.signups.drop();
db.signups.insertMany([
  { _id: 1, email: 'asha@example.com', at: ISODate('2026-01-05') }, { _id: 2, email: 'ben@example.com', at: ISODate('2026-01-06') },
  { _id: 3, email: 'ASHA@example.com', at: ISODate('2026-02-01') }, { _id: 4, email: 'chen@example.com', at: ISODate('2026-02-03') },
  { _id: 5, email: 'asha@example.com', at: ISODate('2026-03-09') }, { _id: 6, email: 'Ben@Example.com', at: ISODate('2026-03-10') }
]);
// 1  group on the normalised email; keep groups with more than one document
const dups = db.signups.aggregate([
  { $sort: { at: 1 } },
  { $group: { _id: { $toLower: '$email' }, ids: { $push: '$_id' }, copies: { $sum: 1 } } },
  { $match: { copies: { $gt: 1 } } },
  { $sort: { _id: 1 } }
]).toArray();
show(dups);

// 2  delete every copy but the earliest
const extra = dups.flatMap(d => d.ids.slice(1));
show(db.signups.deleteMany({ _id: { $in: extra } }));

// 3  a unique index with a case-insensitive collation keeps them out
db.signups.createIndex({ email: 1 }, { unique: true, collation: { locale: 'en', strength: 2 } });
try { db.signups.insertOne({ _id: 7, email: 'CHEN@example.com', at: ISODate('2026-04-01') }); }
catch (e) { print(e.message.split(' collation')[0]); }
db.signups.drop();

The index only helps queries with the same collationA query uses a collated index only when it asks for the same collation, for example find({ email: 'ASHA@example.com' }).collation({ locale: 'en', strength: 2 }). Checked on 8.3: without it, that query ran a COLLSCAN and found nothing; with it, an index scan found Asha. Setting the collation as the collection's default avoids repeating it on every query.

Complexity

One pass to group, and memory for one entry per distinct email. On a large collection, the list of ids to delete may not fit in the client: write the duplicate groups to a collection with $merge or $out, then delete in batches with bulkWrite. Creating the unique index fails while any duplicates remain, so cleanup comes first.

Follow-ups

"Keep the latest?" Sort by at: -1. "Merge their data instead?" Use $group accumulators such as $max and $addToSet per field, then replace the survivor. "Unique on two fields?" A compound unique index. "Unique only for active users?" A partial index with partialFilterExpression.

Say it in the interview"$group on the normalised key with $push of the ids and a count, $match count above 1, delete all but the first id, then a unique index with a strength-2 collation so the database rejects the next one with E11000."
