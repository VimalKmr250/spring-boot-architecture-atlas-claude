A MongoDB query question is half about the pipeline and half about the shape of the documents

MongoDB interviews ask the same problems as SQL interviews: top N per group, rows without a match, totals per item, rollups by time, duplicates. The difference is that the data may already be joined, because order lines are embedded in the order, or may be missing, because a field can be absent instead of NULL. The drills that follow solve each problem with the aggregation pipeline on the running example, run on MongoDB 8.3, and point out the SQL drill that asks the same question.

Five steps, out loud

  1. Ask about the shape. "Are the lines embedded in the order? Can items be empty or missing? Is total a Decimal128 or a double?"
  2. Name the stages. "Filter, unwind the lines, group by product, sort, limit." That sentence is the pipeline.
  3. Filter first. Put $match, and $sort where it helps, at the start, where they can use an index. Later stages work on documents in memory.
  4. Build it stage by stage. Run the first stage, look at the documents, add the next. Say what each stage's output looks like.
  5. Discuss cost. Which index serves the first $match, whether $lookup has an index on its foreign field, and how big a group can grow.

The silent mistakes$unwind drops documents whose array is empty or missing. { field: null } also matches documents without the field. $sum of a missing field is 0, not null. A date stored as a string never equals an ISODate. Each one returns a plausible wrong answer with no error.
SQL habits that hurtA pipeline that starts with three $lookups is a relational schema stored in documents. Say so, and say which data you would embed so the query becomes a $match and a $group. The modelling side is on Embed or reference.
