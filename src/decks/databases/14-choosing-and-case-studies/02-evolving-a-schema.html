Schemas change in both worlds: SQL changes them with migrations, MongoDB with code that tolerates two shapes at once

A new attribute, here a sales channel on every order, has to reach 500,000 existing rows without downtime. In Oracle and SQL Server, adding a NOT NULL column with a constant default is a metadata-only change: existing rows get the default without being rewritten. In MongoDB there is no ALTER. New documents carry the field, readers treat a missing field as the default, and a batched backfill migrates the old documents at its own pace. In both worlds the safe sequence is the same: expand, migrate, then contract.

evolve.ora.sql · Oracle 26ai
SET TIMING ON
-- 1  expand: a new NOT NULL column with a default, on 500,000 rows, is a dictionary change only
ALTER TABLE big_orders ADD channel VARCHAR2(10) DEFAULT 'web' NOT NULL;
SELECT channel, COUNT(*) AS orders FROM big_orders GROUP BY channel;

-- 2  contract, later: drop it once no code reads it
ALTER TABLE big_orders DROP COLUMN channel;
SET TIMING OFF

evolve.js · MongoDB 8.3, mongosh
// 1  no ALTER: new documents simply carry the field; old ones lack it until migrated
db.big_orders.updateOne({ _id: 500001 }, { $setOnInsert: { customerId: 1, status: 'PENDING', channel: 'app', schemaVersion: 2,
  placedAt: ISODate('2026-04-01T10:00:00Z'), total: Decimal128('10.00') } }, { upsert: true });
print('without channel:', db.big_orders.countDocuments({ channel: { $exists: false } }));

// 2  readers treat a missing field as the old default...
show(db.big_orders.aggregate([{ $group: { _id: { $ifNull: ['$channel', 'web'] }, n: { $sum: 1 } } }, { $sort: { _id: 1 } }]));

// 3  ...while a backfill fills it in batches, so no single write is huge
let migrated = 0, res;
do {
  const ids = db.big_orders.find({ channel: { $exists: false } }, { _id: 1 }).limit(50000).toArray().map(d => d._id);
  res = db.big_orders.updateMany({ _id: { $in: ids } }, { $set: { channel: 'web', schemaVersion: 2 } });
  migrated += res.modifiedCount;
} while (res.modifiedCount > 0);
print('backfilled:', migrated, '| still without channel:', db.big_orders.countDocuments({ channel: { $exists: false } }));

// put the collection back for the other slides
db.big_orders.deleteOne({ _id: 500001 });
db.big_orders.updateMany({}, { $unset: { channel: '', schemaVersion: '' } });

What is not instantAdding a column with a default that is not a constant, changing a column's type, or adding a NOT NULL constraint to a populated column rewrites or scans the table, holding locks while it does. Those changes need the expand-and-contract sequence: a new column, a backfill in batches, a switch of readers and writers, and a drop at the end. Oracle's DDL also commits implicitly, so a failed migration cannot simply be rolled back.
Two shapes foreverMongoDB's lazy migration is easy to start and easy to never finish. Until the backfill reaches every document, every query, index and report must handle both shapes. Track the count of old-shape documents, as the script does, and finish the job.
Say it in the interview"Versioned migrations with Flyway or Liquibase for SQL, each backwards compatible with the running version of the application, and expand-and-contract for anything destructive. In MongoDB, a schema version field, tolerant readers and a batched backfill." The full procedure is on Zero-downtime schema change.
