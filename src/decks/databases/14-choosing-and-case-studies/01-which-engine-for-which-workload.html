Choose the data model first and the product second: relational for shared, constrained facts, documents for self-contained aggregates

"SQL or NoSQL?" is the wrong first question. Ask what the data looks like and how it is used. Is it a set of related facts that many features query in different ways, with invariants across entities, such as money and stock? Or is it a collection of self-contained aggregates, read and written whole by key, whose shape varies and grows? The first is relational, the second fits documents, and most real systems have both. Between Oracle and SQL Server the choice is rarely technical: it follows the organisation's licences, skills and platform.

Reasons that are not reasons"MongoDB scales and SQL doesn't" ignores that most applications never outgrow one well-indexed relational server. "SQL is old" ignores fifty years of tooling. "No schema means faster development" lasts until the third version of a document shape. Choose for the data and the queries.
Oracle against SQL ServerBoth handle any of these workloads. They differ in defaults: Oracle reads without blocking, SQL Server needs RCSI for that. They differ in procedural language, in licensing, and in the platform around them, such as Azure for SQL Server and Exadata or OCI for Oracle. Follow the organisation's existing estate.
Say it in the interview"I start from the data model and the queries. Strongly related data with cross-entity invariants goes relational; self-contained aggregates read by key go to documents. Polyglot persistence is normal, as long as each store has a clear owner." The broader trade-offs are on HLD · SQL or NoSQL.
