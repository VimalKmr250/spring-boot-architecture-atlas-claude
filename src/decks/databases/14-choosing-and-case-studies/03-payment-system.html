A payment system is a state machine over money: every transition is a guarded update, every event is idempotent, every cent is in a ledger

The database design of a payment service follows from three rules, each covered earlier in this tab. A payment moves through states (authorised, captured, refunded) only along allowed edges. An UPDATE … WHERE status = 'AUTHORIZED' enforces that atomically, so a retried capture changes nothing. Every external request carries an idempotency key with a unique constraint. Every movement of money is a balanced ledger journal. A reconciliation query then checks that order states and captured amounts agree.

payment-states.ora.sql · Oracle 26ai (the .mss.sql version adds BEGIN TRANSACTION)
-- payment 19 is AUTHORIZED; the capture request arrives twice (a client retry)
UPDATE payments SET status = 'CAPTURED' WHERE payment_id = 19 AND status = 'AUTHORIZED';
UPDATE payments SET status = 'CAPTURED' WHERE payment_id = 19 AND status = 'AUTHORIZED';

-- a refund is only valid for a captured payment, and only once
UPDATE payments SET status = 'REFUNDED' WHERE payment_id = 6 AND status = 'CAPTURED';

-- reconciliation: does every order's state agree with its money?
SELECT o.order_id, o.status, o.total,
       SUM(CASE WHEN p.status = 'CAPTURED' THEN p.amount ELSE 0 END) AS captured
FROM   orders o
LEFT   JOIN payments p ON p.order_id = o.order_id
GROUP  BY o.order_id, o.status, o.total
HAVING (o.status IN ('PAID', 'SHIPPED') AND SUM(CASE WHEN p.status = 'CAPTURED' THEN p.amount ELSE 0 END) <> o.total)
    OR (o.status IN ('PENDING', 'CANCELLED') AND SUM(CASE WHEN p.status = 'CAPTURED' THEN p.amount ELSE 0 END) > 0)
ORDER  BY o.order_id;
ROLLBACK;

What the run showedThe first capture updated 1 row; the retried capture updated 0, so the client can safely repeat the request. The refund of payment 6 updated 0 rows because that attempt had FAILED. Reconciliation then flagged order 1015: money captured while the order is still PENDING. The order service must be told.
Why relational herePayments need cross-row invariants, the ledger balancing, plus unique keys, foreign keys and auditing. Oracle and SQL Server give all of that declaratively. A document store can hold payments, but the guarantees move into application code.
