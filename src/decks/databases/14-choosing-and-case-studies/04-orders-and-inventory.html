Checkout must never sell stock it does not have: reserve with a conditional update inside the transaction that creates the order

Placing an order touches three things: the order, its lines and the stock. They must succeed or fail together, and under concurrency the stock check must not be separate from the stock change. In a relational database that is one transaction: insert the order and its lines, then reserve each product with UPDATE … SET reserved = reserved + :qty WHERE on_hand - reserved >= :qty. Zero rows updated means out of stock, so roll back. Below, two checkouts against the running example's inventory: two grinders are available, the last phone is already reserved.

checkout.ora.sql · Oracle 26ai
-- checkout: create the order, its lines and the stock reservations in one transaction
CREATE OR REPLACE PROCEDURE checkout(p_customer NUMBER, p_product NUMBER, p_qty NUMBER, p_order OUT NUMBER) AS
  v_price products.price%TYPE;
BEGIN
  SELECT price INTO v_price FROM products WHERE product_id = p_product;
  INSERT INTO orders (customer_id, status, placed_at, total)
  VALUES (p_customer, 'PENDING', SYSTIMESTAMP, v_price * p_qty)
  RETURNING order_id INTO p_order;
  INSERT INTO order_items VALUES (p_order, 1, p_product, p_qty, v_price);
  UPDATE inventory SET reserved = reserved + p_qty
  WHERE  product_id = p_product AND on_hand - reserved >= p_qty;
  IF SQL%ROWCOUNT = 0 THEN
    RAISE_APPLICATION_ERROR(-20001, 'out of stock: product ' || p_product);
  END IF;
END;
/
VARIABLE order_id NUMBER
-- two grinders: in stock
EXEC checkout(2, 109, 2, :order_id)
-- one Clam C2 phone: on_hand 1, already reserved 1
EXEC checkout(2, 107, 1, :order_id)

SELECT product_id, on_hand, reserved FROM inventory WHERE product_id IN (107, 109) ORDER BY product_id;
SELECT COUNT(*) AS pending_orders_for_customer_2 FROM orders WHERE customer_id = 2 AND status = 'PENDING';
ROLLBACK;
DROP PROCEDURE checkout;

What the run showedThe grinder checkout committed its order, line and reservation (reserved went from 1 to 3). The phone checkout raised ORA-20001. Because the call failed, Oracle undid everything it had done, including the order row it had already inserted: customer 2 has exactly one pending order.
Hot rowsA flash sale on one product makes its inventory row the most contended row in the system, and every checkout queues on its lock. Keep the transaction short, reserve last, or split stock into several rows ("buckets") and reserve from any one that has enough.
Say it in the interview"Check and decrement in one conditional statement, inside the same transaction as the order, with a CHECK constraint as the backstop. Reservations expire if payment does not follow. Across services, it becomes a saga." The system-design view is HLD · inventory without overselling.
