A query answered from the index alone examines zero documents; a page found by range skips nothing

A query is covered when the filter, the sort and every projected field are in one index, so MongoDB never loads the documents. The common miss is _id: it is returned unless excluded, and it is not in a secondary index, so including it forces a FETCH per result. Pagination has the same shape as in SQL. skip(n) still walks n index entries and throws them away, while a range on the sort key, "after the last value I saw", starts at the right place.

covered.js · MongoDB 8.3, mongosh
db.big_orders.createIndex({ customerId: 1, placedAt: -1, total: 1 });
const report = (label, ex) => print(label.padEnd(24), stages(ex).padEnd(54),
  'keys', String(ex.executionStats.totalKeysExamined).padStart(6), '| docs', String(ex.executionStats.totalDocsExamined).padStart(6));

// 1  covered: the filter, the sort and every returned field are in the index, and _id is excluded
report('projection with _id', db.big_orders.find({ customerId: 4242 }, { placedAt: 1, total: 1 }).sort({ placedAt: -1 }).explain('executionStats'));
report('covered', db.big_orders.find({ customerId: 4242 }, { _id: 0, placedAt: 1, total: 1 }).sort({ placedAt: -1 }).explain('executionStats'));
db.big_orders.dropIndex({ customerId: 1, placedAt: -1, total: 1 });

// 2  paging the whole collection by _id: skip walks past every earlier key, a range starts where the last page ended
report('skip(400000).limit(20)', db.big_orders.find().sort({ _id: 1 }).skip(400000).limit(20).explain('executionStats'));
report('_id > 400000, limit(20)', db.big_orders.find({ _id: { $gt: 400000 } }).sort({ _id: 1 }).limit(20).explain('executionStats'));

skip is not freePage 20,001 by skip read 400,020 index keys to return 20 documents. The cost grows with the page number, exactly like SQL's OFFSET. Spring Data's PageRequest.of(n, size) becomes skip(n * size).
Range pages need a unique sortPaging by placedAt alone breaks when two orders share a timestamp. Sort by { placedAt: -1, _id: -1 }, and continue with $or: [{ placedAt: { $lt: t } }, { placedAt: t, _id: { $lt: id } }], the same tie-breaker logic as keyset pagination in SQL.
Say it in the interview"For hot list endpoints I build an index that covers the filter, the sort and the returned fields, and exclude _id if it is not needed. For paging I use the last seen sort key as a cursor instead of skip."
