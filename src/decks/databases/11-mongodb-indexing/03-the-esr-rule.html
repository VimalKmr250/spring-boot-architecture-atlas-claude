Order compound index fields as Equality, Sort, Range, and the newest 20 orders cost 20 index keys instead of 62,470

MongoDB's guideline for compound indexes has a name: ESR. Fields tested for equality come first, because each value is one contiguous slice of the index. The sort field comes next, so that within the slice the index is already in the requested order. Range conditions come last, filtering entries as they are read. With that order, limit(20) stops after 20 matching entries. Put the range before the sort, and every entry in the range must be read and sorted in memory before the first 20 are known. It is the same reasoning as SQL's column order, extended to sorting.

esr.js · MongoDB 8.3, mongosh
// newest 20 SHIPPED orders over 400: an Equality, a Sort and a Range in one query
const query = () => db.big_orders.find({ status: 'SHIPPED', total: { $gt: Decimal128('400') } })
                                 .sort({ placedAt: -1 }).limit(20);
const report = (label, ex) => print(label.padEnd(26), stages(ex).padEnd(56),
  'keys', String(ex.executionStats.totalKeysExamined).padStart(6), '| docs', String(ex.executionStats.totalDocsExamined).padStart(6));
const indexes = [
  ['E, S, R  status, placedAt, total', { status: 1, placedAt: -1, total: 1 }],
  ['E, R, S  status, total, placedAt', { status: 1, total: 1, placedAt: -1 }],
  ['R, E, S  total, status, placedAt', { total: 1, status: 1, placedAt: -1 }]
];
for (const [label, keys] of indexes) {
  db.big_orders.createIndex(keys, { name: 'esr_test' });
  report(label.slice(0, 8), query().hint('esr_test').explain('executionStats'));
  db.big_orders.dropIndex('esr_test');
}
Output on MongoDB 8.3 · esr.js
E, S, R                    LIMIT > FETCH > IXSCAN esr_test                          keys     20 | docs     20
E, R, S                    FETCH > SORT > IXSCAN esr_test                           keys  62470 | docs     20
R, E, S                    FETCH > SORT > IXSCAN esr_test                           keys  66722 | docs     20
The in-memory SORTBoth other orders produced a SORT stage: every matching key was read, 62,470 or 66,722, and sorted, all to return 20 documents. A blocking sort is limited to 100 MB of memory before it spills to disk, and it grows with the data, so a page that is fast at launch slows down every month.
Equality on arrays and $in$in with a few values behaves like several equalities: the planner can merge the sorted slices. With many values it acts more like a range. Check with explain whether a SORT stage appears.
Say it in the interview"ESR: equality fields first, then the sort field, then ranges. It lets a limited, sorted query stop after N index keys with no in-memory sort. I verify with explain: no SORT stage, and keys examined close to the limit."
