In MongoDB explain output, compare three numbers: documents returned, index keys examined, documents examined

cursor.explain('executionStats') runs the query and reports the winning plan as a tree of stages, plus counters. The ideal is nReturned ≈ totalKeysExamined ≈ totalDocsExamined: every key read led to a document that was returned. A COLLSCAN, or many more documents examined than returned, means the index is missing or does not match the query. To find slow queries in the first place, the profiler records operations slower than a threshold, and $indexStats shows which indexes are actually used.

explain.js · MongoDB 8.3, mongosh
// the numbers that matter in explain('executionStats')
const report = (label, ex) => print(label.padEnd(18), stages(ex).padEnd(42),
  'returned', String(ex.executionStats.nReturned).padStart(3),
  '| keys', String(ex.executionStats.totalKeysExamined).padStart(6),
  '| docs', String(ex.executionStats.totalDocsExamined).padStart(6));

// 1  one customer's orders, before and after an index
const q = { customerId: 4242 };
report('no index', db.big_orders.find(q).explain('executionStats'));
db.big_orders.createIndex({ customerId: 1 });
report('{ customerId: 1 }', db.big_orders.find(q).explain('executionStats'));

// 2  the profiler records operations slower than slowms, with their plan summary
db.setProfilingLevel(1, { slowms: 20 });
db.big_orders.find({ status: 'FAILED', total: { $gt: 400 } }).batchSize(1000).toArray();   // no index on status
db.setProfilingLevel(0);
show(db.system.profile.find({ ns: 'shop.big_orders', op: 'query' }, { _id: 0, planSummary: 1, docsExamined: 1, nreturned: 1 })
  .sort({ ts: -1 }).limit(1));
db.system.profile.drop();

// 3  $indexStats: how often each index has been used since it was created (explain does not count)
db.big_orders.find(q).toArray();
show(db.big_orders.aggregate([{ $indexStats: {} }, { $project: { _id: 0, name: 1, ops: '$accesses.ops' } }, { $sort: { name: 1 } }]));
db.big_orders.dropIndex({ customerId: 1 });

500,000 examined for 25Without an index the customer's 25 orders cost a scan of all 500,000 documents; with one, 25 keys and 25 documents. The profiler caught the other query: 500,000 documents examined to return 520, with plan summary COLLSCAN. That ratio is the first thing to look for.
Profiler and index statistics in productionProfiling level 1 writes every operation slower than slowms to system.profile, a small capped collection. Turn it on briefly, or rely on the slow-query log, which records the same operations. $indexStats counts real uses since the index was created; explain does not count. An index at zero after a full business cycle is a candidate to drop.
