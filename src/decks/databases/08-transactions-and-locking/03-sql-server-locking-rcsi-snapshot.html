By default SQL Server's readers wait for writers; one database setting gives it Oracle-style versioned reads

SQL Server's default READ COMMITTED is implemented with locks: a reader takes a shared lock on each row it reads, and must wait while a writer holds an exclusive lock on that row. That is why a long update can stall every report touching the same rows, and why WITH (NOLOCK) is sprinkled through so many codebases. Row versioning is the real fix. READ_COMMITTED_SNAPSHOT (RCSI) makes READ COMMITTED read the last committed version, kept in the version store, instead of waiting. ALLOW_SNAPSHOT_ISOLATION adds a SNAPSHOT level that reads one snapshot for the whole transaction.

SqlServerReads.java · mssql-jdbc 13.4.0
import java.sql.*;

/** SQL Server's default locking reads, NOLOCK, and the two row-versioning alternatives. */
public class SqlServerReads {
    static final String URL = "jdbc:sqlserver://localhost:1433;databaseName=shop;encrypt=false";

    public static void main(String[] args) throws Exception {
        try (Connection a = open(); Connection b = open()) {
            reset(a);
            update(b, "SET LOCK_TIMEOUT 1000");                       // B gives up on a lock after 1 second

            // 1  default READ COMMITTED takes shared locks: B's read waits for A's uncommitted write
            update(a, "UPDATE accounts SET balance = 400 WHERE account_id = 1");
            try {
                balance(b, "");
            } catch (SQLException e) {
                System.out.println("1 locking READ COMMITTED: B's read failed: " + e.getMessage());
            }

            // 2  NOLOCK reads uncommitted data, which A then rolls back
            long dirty = balance(b, " WITH (NOLOCK)");
            a.rollback();
            System.out.printf("2 NOLOCK: B read %d; A rolled back, so the balance is %d%n", dirty, balance(b, ""));
            b.commit();
        }

        // switch on row versioning (needs a moment with no other open transactions)
        admin("ALTER DATABASE shop SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE");
        admin("ALTER DATABASE shop SET ALLOW_SNAPSHOT_ISOLATION ON");
        try (Connection a = open(); Connection b = open()) {
            // 3  READ_COMMITTED_SNAPSHOT: the same read returns the last committed version, without waiting
            update(a, "UPDATE accounts SET balance = 400 WHERE account_id = 1");
            System.out.printf("3 RCSI: A wrote 400, not committed; B reads %d without waiting%n", balance(b, ""));
            a.commit();
            b.commit();

            // 4  SNAPSHOT: a transaction-wide snapshot, and an error if B updates a row A changed meanwhile
            b.setTransactionIsolation(SQLServerSnapshot.LEVEL);
            long first = balance(b, "");
            update(a, "UPDATE accounts SET balance = 300 WHERE account_id = 1"); a.commit();
            System.out.printf("4 SNAPSHOT: B reads %d, A commits 300, B reads %d%n", first, balance(b, ""));
            try {
                update(b, "UPDATE accounts SET balance = balance - 50 WHERE account_id = 1");
            } catch (SQLException e) {
                System.out.println("  B updates the row A changed: " + e.getErrorCode() + " " + e.getMessage().lines().findFirst().orElse(""));
            }
            b.rollback();
            reset(a);
        }
        admin("ALTER DATABASE shop SET ALLOW_SNAPSHOT_ISOLATION OFF");
        admin("ALTER DATABASE shop SET READ_COMMITTED_SNAPSHOT OFF WITH ROLLBACK IMMEDIATE");
    }

    /** The JDBC constant for SQL Server's SNAPSHOT level is driver-specific. */
    static final class SQLServerSnapshot { static final int LEVEL = 4096; }

    static Connection open() throws SQLException {
        Connection c = DriverManager.getConnection(URL, "sa", "Atlas_pw1!");
        c.setAutoCommit(false);
        return c;
    }

    static void admin(String sql) throws SQLException {
        try (Connection c = DriverManager.getConnection(URL, "sa", "Atlas_pw1!"); Statement s = c.createStatement()) {
            s.execute(sql);
        }
    }

    static void reset(Connection c) throws SQLException {
        update(c, "UPDATE accounts SET balance = CASE account_id WHEN 1 THEN 500 ELSE 300 END WHERE account_id IN (1, 2)");
        c.commit();
    }

    static long balance(Connection c, String hint) throws SQLException {
        try (Statement s = c.createStatement();
             ResultSet rs = s.executeQuery("SELECT balance FROM accounts" + hint + " WHERE account_id = 1")) {
            rs.next();
            return rs.getLong(1);
        }
    }

    static void update(Connection c, String sql) throws SQLException {
        try (Statement s = c.createStatement()) { s.executeUpdate(sql); }
    }
}

NOLOCK is not a performance hintIt reads uncommitted data: step 2 saw a balance that never existed. During page splits it can also skip rows or read them twice. Reports built on NOLOCK are occasionally wrong in ways nobody can reproduce. If readers wait on writers, enable RCSI.
What RCSI costsVersions live in tempdb, or in the database itself with accelerated database recovery, and each changed row carries 14 bytes of versioning information. Code that relied on blocking to serialise work, such as reading a value and then updating it, loses that protection. Use UPDLOCK, as on Preventing lost updates. SQL Server 2025's optimized locking, which holds fewer row locks per transaction, builds on the same versioning.
Say it in the interview"Default SQL Server READ COMMITTED blocks readers behind writers. I would enable READ_COMMITTED_SNAPSHOT, as Azure SQL Database does by default, and use SNAPSHOT for long consistent reports, handling error 3960 as a retry. I would not use NOLOCK for anything that must be correct."
