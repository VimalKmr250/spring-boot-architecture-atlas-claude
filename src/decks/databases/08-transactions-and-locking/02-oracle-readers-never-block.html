Oracle keeps the previous version of every changed row, so a query reads a consistent snapshot instead of waiting for locks

When session A updates a row, Oracle writes the old version to undo and locks only the row, against other writers. When session B reads the row, it reads the last committed version: from the table if no change is pending, rebuilt from undo if one is. Readers take no locks, so they never wait for writers, and writers never wait for readers. Writers still wait for writers on the same row. Each statement reads as of its start under READ COMMITTED, Oracle's default. Under SERIALIZABLE, which is really snapshot isolation, the whole transaction reads as of its first statement.

OracleReads.java · ojdbc17 23.26.3
import java.sql.*;

/** Oracle's multi-version reads, shown with two sessions taking turns: A writes, B reads. */
public class OracleReads {
    static final String URL = "jdbc:oracle:thin:@//localhost:1521/FREEPDB1";

    public static void main(String[] args) throws Exception {
        try (Connection a = open(); Connection b = open()) {
            reset(a);

            // 1  a reader never waits for a writer: B sees the last committed value at once
            update(a, "UPDATE accounts SET balance = 400 WHERE account_id = 1");
            long t0 = System.nanoTime();
            long seen = balance(b, 1);
            System.out.printf("1 A changed 500 to 400, not committed; B reads %d, waited %s%n",
                    seen, (System.nanoTime() - t0) / 1_000_000 < 500 ? "no" : "yes");

            // 2  a writer does wait for a writer: B's locking read gives up after 1 second
            try {
                query(b, "SELECT balance FROM accounts WHERE account_id = 1 FOR UPDATE WAIT 1");
            } catch (SQLException e) {
                System.out.println("2 B's FOR UPDATE WAIT 1: " + firstLine(e));
            }
            a.commit();
            b.rollback();

            // 3  READ COMMITTED: each statement sees the latest commit, so a repeated read can change
            long first = balance(b, 1);
            update(a, "UPDATE accounts SET balance = 300 WHERE account_id = 1"); a.commit();
            System.out.printf("3 READ COMMITTED: B reads %d, A commits 300, B reads %d%n", first, balance(b, 1));
            b.commit();

            // 4  SERIALIZABLE: the whole transaction reads one snapshot, taken at its first statement
            b.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
            first = balance(b, 1);
            update(a, "UPDATE accounts SET balance = 200 WHERE account_id = 1"); a.commit();
            System.out.printf("4 SERIALIZABLE:   B reads %d, A commits 200, B reads %d%n", first, balance(b, 1));

            // 5  ... and B may not overwrite a row changed since that snapshot
            try {
                update(b, "UPDATE accounts SET balance = balance - 50 WHERE account_id = 1");
            } catch (SQLException e) {
                System.out.println("5 B updates the row A changed: " + firstLine(e));
            }
            b.rollback();

            // 6  write skew: SERIALIZABLE here is snapshot isolation, which does not stop it
            reset(a);
            a.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
            long totalA = total(a), totalB = total(b);            // both see 800 across the two wallets
            if (totalA - 600 >= 0) update(a, "UPDATE accounts SET balance = balance - 600 WHERE account_id = 1");
            if (totalB - 600 >= 0) update(b, "UPDATE accounts SET balance = balance - 600 WHERE account_id = 2");
            a.commit();
            b.commit();
            System.out.printf("6 write skew: both saw %d and withdrew 600 from different wallets; total now %d%n",
                    totalA, total(a));
            a.commit();
            reset(a);
        }
    }

    static Connection open() throws SQLException {
        Connection c = DriverManager.getConnection(URL, "shop", "Atlas_pw1");
        c.setAutoCommit(false);
        return c;
    }

    static void reset(Connection c) throws SQLException {
        update(c, "UPDATE accounts SET balance = CASE account_id WHEN 1 THEN 500 ELSE 300 END WHERE account_id IN (1, 2)");
        c.commit();
    }

    static long balance(Connection c, int id) throws SQLException {
        return query(c, "SELECT balance FROM accounts WHERE account_id = ?", id);
    }

    static long total(Connection c) throws SQLException {
        return query(c, "SELECT SUM(balance) FROM accounts WHERE account_id IN (1, 2)");
    }

    static long query(Connection c, String sql, Object... params) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            for (int i = 0; i < params.length; i++) ps.setObject(i + 1, params[i]);
            try (ResultSet rs = ps.executeQuery()) {
                rs.next();
                return rs.getLong(1);
            }
        }
    }

    static void update(Connection c, String sql) throws SQLException {
        try (Statement s = c.createStatement()) { s.executeUpdate(sql); }
    }

    static String firstLine(SQLException e) { return e.getMessage().lines().findFirst().orElse(""); }
}

Snapshot is not serializableBoth transactions read a total of 800 and each withdrew 600 from a different wallet. Neither wrote a row the other wrote, so neither got ORA-08177, and the combined result, −400, could not happen in any serial order. Guard such invariants with a lock on a shared row (SELECT … FOR UPDATE on the customer) or a constraint.
The price of versionsLong queries need old versions to stay in undo. If they are overwritten first, the query fails with ORA-01555, "snapshot too old". In 26ai, a FOR UPDATE WAIT 1 that times out reports ORA-00054 with the lock described, as step 2 shows; older releases reported ORA-30006.
Say it in the interview"Oracle uses multi-version concurrency: readers see a consistent snapshot from undo and take no locks, so reads never block writes. READ COMMITTED snapshots per statement, SERIALIZABLE per transaction and raises ORA-08177 on a conflicting write. Neither prevents write skew."
