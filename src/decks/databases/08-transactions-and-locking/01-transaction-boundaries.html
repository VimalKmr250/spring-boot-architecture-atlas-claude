Know where your transaction starts and ends: autocommit, implicit commits and nested BEGINs all move the boundary

A transaction is the unit that commits or rolls back as a whole. Where it begins differs by engine. Oracle starts one implicitly with the first change and ends it with COMMIT or ROLLBACK, and every DDL statement commits first. SQL Server runs each statement in autocommit unless BEGIN TRANSACTION opens an explicit one, and DDL inside it can be rolled back. JDBC drivers start in autocommit mode on both, which is why frameworks switch it off for a @Transactional method. A savepoint lets part of a transaction be undone without ending it.

boundaries.ora.sql · Oracle 26ai
-- 1  DDL commits: the CREATE TABLE silently commits the INSERT before it
INSERT INTO customers (customer_id, name, email, country, tier, created_at)
VALUES (11, 'Kai Tanaka', 'kai@example.com', 'JP', 'BRONZE', TIMESTAMP '2026-04-01 10:00:00');
CREATE TABLE scratch (id NUMBER);
ROLLBACK;
SELECT COUNT(*) AS customer_11_rows FROM customers WHERE customer_id = 11;
DELETE FROM customers WHERE customer_id = 11;
DROP TABLE scratch PURGE;
COMMIT;

-- 2  a savepoint undoes part of a transaction
INSERT INTO payments (order_id, idempotency_key, method, status, amount, created_at)
VALUES (1018, 'pay-1018-1', 'CARD', 'FAILED', 59.00, TIMESTAMP '2026-03-29 20:01:00');
SAVEPOINT after_first_attempt;
INSERT INTO payments (order_id, idempotency_key, method, status, amount, created_at)
VALUES (1018, 'pay-1018-2', 'CARD', 'CAPTURED', 59.00, TIMESTAMP '2026-03-29 20:03:00');
ROLLBACK TO SAVEPOINT after_first_attempt;
SELECT idempotency_key, status FROM payments WHERE order_id = 1018;
ROLLBACK;

boundaries.mss.sql · SQL Server 2025
-- 1  DDL is transactional: ROLLBACK undoes the CREATE TABLE and the INSERT
BEGIN TRANSACTION;
INSERT INTO customers (customer_id, name, email, country, tier, created_at)
VALUES (11, N'Kai Tanaka', 'kai@example.com', 'JP', 'BRONZE', '2026-04-01 10:00:00');
CREATE TABLE scratch (id INT);
ROLLBACK;
SELECT COUNT(*) AS customer_11_rows, OBJECT_ID('scratch') AS scratch_table FROM customers WHERE customer_id = 11;

-- 2  a savepoint undoes part of a transaction
BEGIN TRANSACTION;
INSERT INTO payments (order_id, idempotency_key, method, status, amount, created_at)
VALUES (1018, 'pay-1018-1', 'CARD', 'FAILED', 59.00, '2026-03-29 20:01:00');
SAVE TRANSACTION after_first_attempt;
INSERT INTO payments (order_id, idempotency_key, method, status, amount, created_at)
VALUES (1018, 'pay-1018-2', 'CARD', 'CAPTURED', 59.00, '2026-03-29 20:03:00');
ROLLBACK TRANSACTION after_first_attempt;
SELECT idempotency_key, status, @@TRANCOUNT AS open_transactions FROM payments WHERE order_id = 1018;
ROLLBACK;

-- 3  nested BEGIN TRANSACTION only counts; the inner COMMIT commits nothing
BEGIN TRANSACTION;
BEGIN TRANSACTION;
SELECT @@TRANCOUNT AS depth_after_two_begins;
COMMIT;
SELECT @@TRANCOUNT AS depth_after_inner_commit;
ROLLBACK;
SELECT @@TRANCOUNT AS depth_after_rollback;

The CREATE TABLE that committedThe Oracle script inserted customer 11, created a table, and rolled back, yet customer 11 was still there: the DDL had committed the insert. Migration scripts that mix DML and DDL on Oracle cannot be undone by a rollback; plan them to be re-runnable instead. See Zero-downtime schema change.
Nested transactions are not nestedIn SQL Server the inner COMMIT only decremented @@TRANCOUNT from 2 to 1; nothing was committed, and the final ROLLBACK undid it all. A procedure that commits "its own" work inside a caller's transaction commits nothing. Spring's REQUIRES_NEW opens a second connection for this reason; see Transaction propagation.
Say it in the interview"A transaction should cover one business operation and nothing slow: no remote calls, no user think time inside it. In application code I let the framework open and close it, and I know that Oracle DDL commits implicitly while SQL Server DDL is transactional."
