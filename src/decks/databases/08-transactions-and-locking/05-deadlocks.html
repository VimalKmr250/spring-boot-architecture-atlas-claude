Two transactions that lock the same rows in opposite orders will eventually wait for each other forever, until the database breaks the cycle

Transfer A debits wallet 1 then wallet 2; transfer B debits wallet 2 then wallet 1. Each takes its first row lock, then waits for the row the other holds. Neither can proceed, which is a deadlock. Both engines detect the cycle within seconds and break it by failing one participant, and they differ in what they roll back. Oracle rolls back only the statement that detected the deadlock and raises ORA-00060; that session still holds its earlier locks until it commits or rolls back. SQL Server picks a victim and rolls back its whole transaction with error 1205. The fix is the same everywhere: take locks in one consistent order.

Deadlock.java · ojdbc17 23.26.3, mssql-jdbc 13.4.0
import java.sql.*;
import java.util.List;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

/** Two transfers between the same two wallets, locking them in opposite orders, on Oracle and SQL Server. */
public class Deadlock {
    record Db(String name, String url, String user, String password, String blocked, String setup) {}

    static final List<Db> DBS = List.of(
        new Db("Oracle 26ai", "jdbc:oracle:thin:@//localhost:1521/FREEPDB1", "shop", "Atlas_pw1",
               "SELECT COUNT(*) FROM v$session WHERE username = 'SHOP' AND blocking_session IS NOT NULL", null),
        new Db("SQL Server 2025", "jdbc:sqlserver://localhost:1433;databaseName=shop;encrypt=false", "sa", "Atlas_pw1!",
               "SELECT COUNT(*) FROM sys.dm_exec_requests WHERE blocking_session_id <> 0",
               "SET DEADLOCK_PRIORITY LOW"));                       // make B the victim, so the run is repeatable

    static final String DEBIT = "UPDATE accounts SET balance = balance - 10 WHERE account_id = ?";

    public static void main(String[] args) throws Exception {
        for (Db db : DBS) {
            System.out.println("== " + db.name());
            transfer(db, new int[] {1, 2}, new int[] {2, 1});        // opposite orders
            transfer(db, new int[] {1, 2}, new int[] {1, 2});        // the same order
        }
    }

    static void transfer(Db db, int[] orderA, int[] orderB) throws Exception {
        try (Connection a = open(db, null); Connection b = open(db, db.setup()); Connection monitor = open(db, null);
             var threads = Executors.newVirtualThreadPerTaskExecutor()) {
            reset(a);
            System.out.printf("  A locks %d then %d, B locks %d then %d%n", orderA[0], orderA[1], orderB[0], orderB[1]);
            debit(a, orderA[0]);
            Future<String> resultB;
            if (orderA[0] == orderB[0]) {                             // same order: B queues behind A at once
                resultB = threads.submit(() -> finish(b, db, orderB[0], orderB[1]));
                waitUntilBlocked(monitor, db);
                debit(a, orderA[1]);
                a.commit();
                System.out.println("  A committed; B: " + resultB.get());
                return;
            }
            debit(b, orderB[0]);
            Future<String> resultA = threads.submit(() -> finish(a, db, orderA[1]));
            waitUntilBlocked(monitor, db);                            // A now waits for B
            resultB = threads.submit(() -> finish(b, db, orderB[1])); // and B for A: a cycle
            System.out.println("  A: " + resultA.get());
            System.out.println("  B: " + resultB.get());
        }
    }

    // run the remaining debits and commit; on an error, report it, look at the other session, then roll back
    static String finish(Connection c, Db db, int... ids) throws SQLException {
        try {
            for (int id : ids) debit(c, id);
            c.commit();
            return "committed";
        } catch (SQLException e) {
            String other = blockedNow(db) ? "the other session is still blocked" : "the other session is running";
            c.rollback();
            return "error " + e.getErrorCode() + ": " + e.getMessage().lines().findFirst().orElse("")
                    + "\n     before this side rolled back, " + other;
        }
    }

    static boolean blockedNow(Db db) throws SQLException {
        try (Connection c = open(db, null); Statement s = c.createStatement(); ResultSet rs = s.executeQuery(db.blocked())) {
            return rs.next() && rs.getInt(1) > 0;
        }
    }

    static void debit(Connection c, int id) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement(DEBIT)) {
            ps.setInt(1, id);
            ps.executeUpdate();
        }
    }

    static Connection open(Db db, String setup) throws SQLException {
        Connection c = DriverManager.getConnection(db.url(), db.user(), db.password());
        c.setAutoCommit(false);
        if (setup != null) try (Statement s = c.createStatement()) { s.execute(setup); }
        return c;
    }

    static void reset(Connection c) throws SQLException {
        try (Statement s = c.createStatement()) {
            s.executeUpdate("UPDATE accounts SET balance = CASE account_id WHEN 1 THEN 500 ELSE 300 END WHERE account_id IN (1, 2)");
        }
        c.commit();
    }

    static void waitUntilBlocked(Connection monitor, Db db) throws Exception {
        for (int i = 0; i < 400; i++) {
            try (Statement s = monitor.createStatement(); ResultSet rs = s.executeQuery(db.blocked())) {
                if (rs.next() && rs.getInt(1) > 0) return;
            }
            monitor.commit();
            Thread.sleep(25);
        }
        throw new IllegalStateException("nobody blocked");
    }
}

Oracle: the half-failed transactionAfter ORA-00060, session A still held its lock on wallet 1, and B stayed blocked until A's code rolled back. An application that catches the error and carries on, or does nothing, leaves B waiting. Treat ORA-00060 as "roll back the transaction and retry", exactly like SQL Server's 1205.
Where deadlocks hideUpdating rows in the order a request lists them, foreign key checks against unindexed child tables, MERGE … HOLDLOCK key ranges, and lock escalation to a whole table on SQL Server. Sorting the keys before updating, as the second run did, removes the most common case.
Say it in the interview"Deadlocks come from inconsistent lock order. I lock rows in a fixed order, such as ascending id, keep transactions short, and retry the whole transaction on ORA-00060 or 1205; in Spring both arrive as a PessimisticLockingFailureException subtype, which a retry policy can catch."
