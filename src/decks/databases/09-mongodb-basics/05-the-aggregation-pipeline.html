An aggregation pipeline is a list of stages, each transforming the documents the previous stage produced

Where SQL describes the result and lets the optimiser order the work, a pipeline lists the steps in order: $match filters, $group aggregates, $sort, $limit and $project shape the output. Each SQL clause has a stage, and the comments in the pipeline below name them. The order is yours to choose, and it matters: a $match placed first can use an index and shrinks everything after it. The SQL version ran on both Oracle and SQL Server and returned the same five customers and totals.

pipeline.js · MongoDB 8.3, mongosh
// revenue per customer from paid and shipped orders, top 5: the SQL beside each stage
show(db.orders.aggregate([
  { $match: { status: { $in: ['PAID', 'SHIPPED'] } } },            // WHERE status IN ('PAID', 'SHIPPED')
  { $group: { _id: '$customer.id',                                  // GROUP BY customer_id
              name:    { $first: '$customer.name' },
              orders:  { $sum: 1 },                                 // COUNT(*)
              revenue: { $sum: '$total' } } },                      // SUM(total)
  { $match: { orders: { $gte: 2 } } },                              // HAVING COUNT(*) >= 2
  { $sort: { revenue: -1 } },                                       // ORDER BY revenue DESC
  { $limit: 5 },                                                    // FETCH FIRST 5 ROWS ONLY
  { $project: { _id: 0, customerId: '$_id', name: 1, orders: 1, revenue: 1 } }  // SELECT list
]));

pipeline.sql · runs on Oracle 26ai and SQL Server 2025
SELECT o.customer_id, c.name, COUNT(*) AS orders, SUM(o.total) AS revenue
FROM   orders o JOIN customers c ON c.customer_id = o.customer_id
WHERE  o.status IN ('PAID', 'SHIPPED')
GROUP  BY o.customer_id, c.name
HAVING COUNT(*) >= 2
ORDER  BY revenue DESC
OFFSET 0 ROWS FETCH NEXT 5 ROWS ONLY;

Stage order is plan orderA pipeline that groups first and matches afterwards groups every document in the collection. The optimiser moves some stages, such as a $match that only uses fields from before a $project, but do not rely on it: filter first, and project away large fields early.
Memory$group and $sort work in memory up to 100 MB per stage, then spill to disk; allowDiskUse is the default since 6.0. A $group on a high-cardinality key over millions of documents is the usual cause of a slow pipeline.
Say it in the interview"$match is WHERE, $group is GROUP BY, the second $match is HAVING, $sort and $limit are ORDER BY and FETCH. I put $match first so it can use an index, and I check the pipeline with explain like a SQL plan."
