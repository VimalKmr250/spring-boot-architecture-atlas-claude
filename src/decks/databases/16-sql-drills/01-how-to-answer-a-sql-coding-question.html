A SQL coding question is graded on the edge cases you ask about, not only on the query you write

Interviewers reuse a small set of SQL problems: the Nth highest value, duplicates, top N per group, rows with no match, running totals, consecutive runs, hierarchies and pivots. Each has a standard answer, and each has edge cases the interviewer is waiting for: ties, NULLs, empty groups, dates at boundaries. The drills that follow solve each problem on the running example, run on both Oracle and SQL Server, with the follow-up questions that usually come next.

Five steps, out loud

  1. Restate and clarify. "Highest salary: distinct values, or people? If two people tie, are they both second? What if there is no third?"
  2. Name the shape. "This is top N per group, so a ranking window partitioned by department."
  3. Write it in steps. A CTE per step: filter, aggregate, rank, then select. Easier to read and to fix while talking.
  4. Check with data. Run it in your head on a tie, a NULL and an empty group. Say what each returns.
  5. Discuss cost. Which index supports it, how it scales, and the engine-specific alternative such as QUALIFY, CROSS APPLY or PIVOT.

The silent mistakesNOT IN over a nullable column, COUNT(*) after a LEFT JOIN, BETWEEN on timestamps, ROW_NUMBER where ties matter, integer division in SQL Server. Each returns a plausible wrong answer with no error, which is why interviewers ask about them.
Dialect on a whiteboardWrite standard SQL (OFFSET … FETCH, CASE, window functions) and mention the dialect form: "on SQL Server I'd use TOP, on old Oracle ROWNUM in a subquery". Interviewers care that you know the difference, not that you remember every function name.
