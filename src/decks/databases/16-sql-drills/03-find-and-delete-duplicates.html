Drill: "the table has duplicate emails: find them, delete all but one, and make sure it never happens again"

Three parts, and each one has a trap. Find: duplicates are defined by a normalised key, here the lower-cased email, not the raw column. Delete: number the copies with ROW_NUMBER partitioned by that key, ordered by which one to keep, here the earliest sign-up, and delete those numbered above 1. Prevent: a unique index on the same normalised key. Without that third step the cleanup has to be repeated forever.

duplicates.ora.sql · Oracle 26ai
-- newsletter sign-ups imported twice from two systems, emails in mixed case
CREATE TABLE signups (signup_id NUMBER PRIMARY KEY, email VARCHAR2(100) NOT NULL, signed_up DATE NOT NULL);
INSERT INTO signups VALUES (1, 'asha@example.com', DATE '2026-01-05');
INSERT INTO signups VALUES (2, 'ben@example.com',  DATE '2026-01-06');
INSERT INTO signups VALUES (3, 'ASHA@example.com', DATE '2026-02-01');
INSERT INTO signups VALUES (4, 'chen@example.com', DATE '2026-02-03');
INSERT INTO signups VALUES (5, 'asha@example.com', DATE '2026-03-09');
INSERT INTO signups VALUES (6, 'Ben@Example.com',  DATE '2026-03-10');

-- 1  find them: group on the normalised key, keep groups with more than one row
SELECT LOWER(email) AS email, COUNT(*) AS copies, MIN(signup_id) AS keep_id
FROM   signups GROUP BY LOWER(email) HAVING COUNT(*) > 1 ORDER BY email;

-- 2  delete all but the earliest copy of each
DELETE FROM signups
WHERE  signup_id IN (SELECT signup_id
                     FROM  (SELECT signup_id,
                                   ROW_NUMBER() OVER (PARTITION BY LOWER(email) ORDER BY signed_up, signup_id) AS rn
                            FROM   signups)
                     WHERE  rn > 1);
SELECT signup_id, email FROM signups ORDER BY signup_id;

-- 3  and stop them coming back
CREATE UNIQUE INDEX signups_email_ux ON signups (LOWER(email));
INSERT INTO signups VALUES (7, 'CHEN@example.com', DATE '2026-04-01');
DROP TABLE signups PURGE;

duplicates.mss.sql · SQL Server 2025
-- newsletter sign-ups imported twice from two systems, emails in mixed case
CREATE TABLE signups (signup_id INT PRIMARY KEY, email VARCHAR(100) NOT NULL, signed_up DATE NOT NULL);
INSERT INTO signups VALUES (1, 'asha@example.com', '2026-01-05'), (2, 'ben@example.com', '2026-01-06'),
                           (3, 'ASHA@example.com', '2026-02-01'), (4, 'chen@example.com', '2026-02-03'),
                           (5, 'asha@example.com', '2026-03-09'), (6, 'Ben@Example.com', '2026-03-10');

-- 1  find them; the case-insensitive collation already treats 'ASHA@…' and 'asha@…' as equal
SELECT email, COUNT(*) AS copies, MIN(signup_id) AS keep_id
FROM   signups GROUP BY email HAVING COUNT(*) > 1 ORDER BY email;

-- 2  delete all but the earliest copy of each: SQL Server can delete through a CTE
WITH ranked AS (
  SELECT signup_id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY signed_up, signup_id) AS rn FROM signups
)
DELETE FROM ranked WHERE rn > 1;
SELECT signup_id, email FROM signups ORDER BY signup_id;

-- 3  and stop them coming back
ALTER TABLE signups ADD CONSTRAINT signups_email_uk UNIQUE (email);
INSERT INTO signups VALUES (7, 'CHEN@example.com', '2026-04-01');
DROP TABLE signups;

Engine differences

Oracle needed LOWER(email) in the grouping and a function-based unique index. SQL Server's case-insensitive collation grouped the variants by itself, and a plain unique constraint rejected CHEN@…. The group's displayed value, Ben@Example.com, is an arbitrary member of the group. SQL Server can also delete straight through a CTE; Oracle deletes by key with IN, or by ROWID.

Follow-ups

"Keep the latest instead?" Order the window by signed_up DESC. "Millions of rows?" Delete in batches. "The duplicates have different data, so which wins?" That is a merge, not a delete: decide per column. "No unique id at all?" Oracle has ROWID; in SQL Server, the CTE delete works anyway.

Say it in the interview"Group by the normalised key with HAVING COUNT(*) > 1 to find them; ROW_NUMBER partitioned by that key, delete rn > 1; then a unique index on the same expression so the database prevents it next time."
