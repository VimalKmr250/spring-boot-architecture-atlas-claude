Drill: "flag orders whose payment failed three or more times in a row", the islands question for rows with no regular interval

The minute-based trick on LAG, LEAD, gaps and islands subtracts a row number from a timestamp, so it needs evenly spaced rows. Payment attempts have no fixed spacing, so the general form uses two row numbers. One counts every attempt on the order. The other counts the attempts with the same status. While the status stays the same, both go up by one, so their difference stays constant. Grouping by order, status and that difference turns each run into one row.

streaks.sql · runs unchanged on Oracle 26ai and SQL Server 2025
-- 1  the two numbers side by side: their difference stays constant within a run of one status
SELECT order_id, payment_id, status,
       ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY created_at)          AS attempt_no,
       ROW_NUMBER() OVER (PARTITION BY order_id, status ORDER BY created_at)  AS status_no,
       ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY created_at)
     - ROW_NUMBER() OVER (PARTITION BY order_id, status ORDER BY created_at)  AS run_key
FROM   payments
WHERE  order_id IN (1003, 1005, 1011)
ORDER  BY order_id, created_at;

-- 2  payment attempts that failed three or more times in a row on the same order
WITH attempts AS (
  SELECT order_id, payment_id, status,
         ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY created_at)          AS attempt_no,
         ROW_NUMBER() OVER (PARTITION BY order_id, status ORDER BY created_at)  AS status_no
  FROM   payments
),
runs AS (
  SELECT order_id, status, attempt_no - status_no AS run_key, COUNT(*) AS run_length,
         MIN(payment_id) AS first_payment, MAX(payment_id) AS last_payment
  FROM   attempts
  GROUP  BY order_id, status, attempt_no - status_no
)
SELECT order_id, run_length, first_payment, last_payment
FROM   runs
WHERE  status = 'FAILED' AND run_length >= 3
ORDER  BY order_id;

SQL Server 2025 agreesThe same file returns the same seven rows and the same run: order 1005, payments 6 to 8.
Why the key worksTake an order with attempts F, F, C, F, F, F. Attempt numbers are 1 to 6. The FAILED rows are numbered 1, 2, then 3, 4, 5 within their status, so the differences are 0, 0, then 1, 1, 1: two runs of failures with different keys. The CAPTURED row gets 3 − 1 = 2, in its own group because status is part of the key.

Follow-ups

"Longest streak per order?" MAX(run_length) over the runs, grouped by order. "Ongoing streaks only?" Keep runs whose last attempt is the order's last attempt. "Where did the run start and end in time?" MIN and MAX of created_at in the same GROUP BY. "Ties on created_at?" Add payment_id to both ORDER BYs, or the numbering is not deterministic.

Say it in the interview"Two ROW_NUMBERs: one over the entity, one over entity and status. Their difference is constant inside a run, so I group by it and filter on the count. One sort per window, no self-join." The same trick finds consecutive login days or a run of failed health checks.
