Every write to one document is atomic, so put the check inside the update and 400 requests for 100 units grant exactly 100

MongoDB guarantees that a single-document write is all-or-nothing and isolated: no reader sees half of it, and two writers to the same document are applied one after the other. That is enough for most invariants, as long as the condition is part of the update. The program below has 8 threads each asking 50 times to reserve one phone, with 100 in stock. The first version reads the document, checks in Java and writes back the new count, which is the document-database version of the lost update. The second puts the check in the filter: "where reserved is below onHand, increment reserved".

StockReservations.java · MongoDB Java driver 5.8.1
import com.mongodb.client.MongoClient;
import com.mongodb.client.MongoClients;
import com.mongodb.client.MongoCollection;
import com.mongodb.client.model.Filters;
import com.mongodb.client.model.Updates;
import org.bson.Document;

import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

/** 8 threads each try to reserve 1 unit 50 times: 400 requests for 100 units in stock. */
public class StockReservations {
    public static void main(String[] args) throws Exception {
        try (MongoClient client = MongoClients.create("mongodb://localhost:27017/?directConnection=true")) {
            MongoCollection<Document> stock = client.getDatabase("shop").getCollection("stock_demo");
            run(stock, "read, check, then $set", StockReservations::readCheckWrite);
            run(stock, "one conditional $inc", StockReservations::conditionalInc);
            stock.drop();
        }
    }

    interface Reservation { boolean reserve(MongoCollection<Document> stock); }

    static void run(MongoCollection<Document> stock, String label, Reservation reservation) throws Exception {
        stock.drop();
        stock.insertOne(new Document("_id", "PHN-C2").append("onHand", 100).append("reserved", 0));
        AtomicInteger granted = new AtomicInteger();
        try (var pool = Executors.newFixedThreadPool(8)) {
            for (int t = 0; t < 8; t++) {
                pool.submit(() -> {
                    for (int i = 0; i < 50; i++) if (reservation.reserve(stock)) granted.incrementAndGet();
                });
            }
        }
        Document after = stock.find().first();
        System.out.printf("%-24s granted %3d, stored reserved = %3d, onHand = %d%n",
                label, granted.get(), after.getInteger("reserved"), after.getInteger("onHand"));
    }

    // the application reads, decides, and writes back the number it computed
    static boolean readCheckWrite(MongoCollection<Document> stock) {
        Document d = stock.find(Filters.eq("_id", "PHN-C2")).first();
        int reserved = d.getInteger("reserved");
        if (reserved >= d.getInteger("onHand")) return false;
        stock.updateOne(Filters.eq("_id", "PHN-C2"), Updates.set("reserved", reserved + 1));
        return true;
    }

    // the server checks and increments in one atomic step on one document
    static boolean conditionalInc(MongoCollection<Document> stock) {
        return stock.updateOne(
                Filters.and(Filters.eq("_id", "PHN-C2"),
                            Filters.expr(new Document("$lt", java.util.List.of("$reserved", "$onHand")))),
                Updates.inc("reserved", 1)).getModifiedCount() == 1;
    }
}

400 granted, 52 recordedThe read-check-write version told all 400 requests "yes", and the document records only 52 reservations: the threads read the same count and overwrote each other's increments. Four runs recorded 66, 50, 50 and 52, the last shown above. This is the same bug as the SQL lost update, and the same fix: let the database do the check and the change in one step.
The conditional incrementExactly 100 reservations were granted and recorded, and the other 300 saw modifiedCount 0, which the code reports as "out of stock". It needs no transaction and no lock held across round trips, because the condition and the change are one atomic operation on one document.
Say it in the interview"Single-document writes are atomic, and I design so that each business invariant lives in one document. Then a conditional update, with the check in the filter, is a compare-and-set. I use multi-document transactions only when an invariant really spans documents."
