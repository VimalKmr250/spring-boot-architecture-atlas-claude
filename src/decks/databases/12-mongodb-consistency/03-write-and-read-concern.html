Durability and freshness in MongoDB are per-operation settings: how many members must have a write, and which data a read may see

A replica set copies every write from the primary to the secondaries. The write concern says when the client is told "done": w: 1 after the primary has it, w: 'majority' after most members have it, w: 3 after all three. A read concern says which data a read may return: local may include writes that a failover could still roll back, majority only data that cannot be. A read preference says which members may serve the read. These scripts ran against a three-node replica set: first with every member up, then with one stopped.

wc-up.js · MongoDB 8.3, three-member replica set rs1
// all three members up: each write concern is acknowledged
db.payments_log.drop();
for (const w of [1, 'majority', 3]) {
  const res = db.payments_log.insertOne({ event: 'captured', w: String(w) }, { writeConcern: { w, wtimeout: 2000 } });
  print('w:', String(w).padEnd(8), 'acknowledged:', res.acknowledged);
}
print('members:', rs.status().members.map(m => m.name.split(':')[0] + ' ' + m.stateStr).join(', '));

wc-down.js · run after docker stop rs1c
// rs1c is stopped: two of three members up
print('members:', rs.status().members.map(m => m.name.split(':')[0] + ' ' + m.stateStr).join(', '));
for (const w of ['majority', 3]) {
  try {
    db.payments_log.insertOne({ event: 'refunded', w: String(w) }, { writeConcern: { w, wtimeout: 2000 } });
    print('w:', String(w).padEnd(8), 'acknowledged');
  } catch (e) {
    print('w:', String(w).padEnd(8), e.name + ':', e.message);
  }
}
// the w: 3 write timed out, yet it was not rolled back: the primary has it
print('refund events on the primary:', db.payments_log.countDocuments({ event: 'refunded' }));

A timeout is not a rollbackWith rs1c down, w: 3 failed with "waiting for replication timed out", yet both refund events were on the primary. The client only learns that the write was not confirmed in time. Retrying such a write without an idempotency key inserts it twice.
Stale secondariesA read from a secondary right after a write to the primary can miss the write. For read-your-writes on secondaries, use a causally consistent session with majority read and write concerns, or read from the primary. Replication lag grows under load, exactly when the dashboard is most in demand.
Say it in the interview"w: 'majority' for business writes, so a failover cannot lose them; read concern majority when I act on what I read; primary reads by default and secondaries only for staleness-tolerant reports." The theory behind it is HLD · Leader-follower replication.
