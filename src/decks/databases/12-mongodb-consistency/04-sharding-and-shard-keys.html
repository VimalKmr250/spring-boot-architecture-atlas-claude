The shard key decides where every document lives and which queries touch one shard or all of them; it is the hardest choice to undo

A sharded cluster splits a collection across shards, each itself a replica set, by ranges of a shard key. Applications connect to mongos routers, which send each operation to the shards that can hold the matching documents. A good key has many distinct values, spreads writes evenly, and appears in most queries. A monotonic key, such as a timestamp or an ObjectId, sends every new insert to the shard holding the highest range. Hashing the key spreads inserts but loses range queries. These scripts ran on a two-shard cluster with 100,000 orders loaded under two different keys.

sharding.js · MongoDB 8.3, two shards behind mongos
// 100,000 orders loaded twice: once sharded on a hashed customerId, once on placedAt
db.by_customer.drop(); db.by_time.drop();
const orders = Array.from({ length: 100000 }, (_, i) => {
  const n = i + 1;
  return { _id: n, customerId: 1 + (n * 7919) % 20000, status: n % 200 === 0 ? 'FAILED' : 'SHIPPED',
           placedAt: new Date(Date.UTC(2025, 0, 1) + n * 37 * 1000) };
});
sh.shardCollection('shop.by_customer', { customerId: 'hashed' });
sh.shardCollection('shop.by_time', { placedAt: 1 });
for (const name of ['by_customer', 'by_time']) {
  for (let i = 0; i < orders.length; i += 10000) db.getCollection(name).insertMany(orders.slice(i, i + 10000));
}

// 1  where the documents went
for (const name of ['by_customer', 'by_time']) {
  const perShard = db.getCollection(name).aggregate([{ $collStats: { count: {} } }]).toArray()
    .map(s => s.shard + ' ' + s.count).sort().join(', ');
  print(name.padEnd(12), perShard);
}

// 2  a query with the shard key goes to one shard; one without it goes to all of them
const route = ex => ex.queryPlanner.winningPlan.stage + ' (' + ex.queryPlanner.winningPlan.shards.length + ' shard' +
  (ex.queryPlanner.winningPlan.shards.length > 1 ? 's' : '') + ')';
print('by customerId:', route(db.by_customer.find({ customerId: 4242 }).explain()));
print('by status:    ', route(db.by_customer.find({ status: 'FAILED' }).explain()));

// 3  analyzeShardKey measures a candidate key before you commit to it; each needs a supporting index
for (const key of [{ customerId: 1 }, { status: 1 }, { placedAt: 1 }]) db.by_customer.createIndex(key);
for (const key of [{ customerId: 1 }, { status: 1 }, { placedAt: 1 }]) {
  const k = db.adminCommand({ analyzeShardKey: 'shop.by_customer', key, readWriteDistribution: false }).keyCharacteristics;
  print(JSON.stringify(key).padEnd(18), 'distinct values', String(k.numDistinctValues).padStart(6),
        '| most common share', (100 * k.mostCommonValues[0].frequency / k.numDocsTotal).toFixed(3) + '%',
        '| monotonic:', k.monotonicity.type);
}

Candidate keyVerdict
customerId20,000 values, none dominant; "my orders" queries hit one shard. Good
status2 values, one holding 99.5%: one huge, unsplittable chunk. Bad
placedAtUnique values but monotonic: a hot shard for inserts. Hash it, or prefix it
Scatter-gatherThe query by status could not be routed: SHARD_MERGE across both shards, merging the results in mongos. With 20 shards, every such query asks all 20. Queries without the shard key are the hidden cost of a key chosen for even writes alone.
Changing your mindSince 5.0 a collection can be resharded online, and since 4.4 a key can be refined by adding a suffix field. Both are heavy operations on a large collection. analyzeShardKey 7.0 measures cardinality, frequency and monotonicity of a candidate before you commit; it judged status monotonic here only because of how this synthetic data was generated.
Say it in the interview"A shard key needs high cardinality, low frequency, non-monotonic inserts, and must match the main query's filter. For orders I would use the customer id, or a compound key of customer and date, so each customer's queries stay on one shard." Partitioning in general is on HLD · Partitioning strategies.
