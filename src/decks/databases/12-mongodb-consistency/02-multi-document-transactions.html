MongoDB has ACID transactions across documents, but a conflict aborts at once instead of waiting, so every transaction needs a retry

Since 4.0 on replica sets, and 4.2 on sharded clusters, a session can run a transaction that spans documents and collections. It reads from one snapshot, writes atomically on commit, and is invisible to others until then. Concurrency control is optimistic. When two transactions write the same document, the second gets a WriteConflict immediately, labelled TransientTransactionError, and must restart from the beginning. The drivers' withTransaction helper retries those automatically. A transfer between two wallets is the textbook case.

transactions.js · MongoDB 8.3, mongosh, one-node replica set
db.accounts.updateOne({ _id: 1 }, { $set: { balance: Decimal128('500.00') } });
db.accounts.updateOne({ _id: 2 }, { $set: { balance: Decimal128('300.00') } });

// 1  a transfer across two documents: both writes commit together or not at all
const s1 = db.getMongo().startSession();
const acc1 = s1.getDatabase('shop').accounts;
s1.startTransaction({ readConcern: { level: 'snapshot' }, writeConcern: { w: 'majority' } });
acc1.updateOne({ _id: 1 }, { $inc: { balance: Decimal128('-100') } });
acc1.updateOne({ _id: 2 }, { $inc: { balance: Decimal128('100') } });
print('inside the transaction, others still see:', db.accounts.findOne({ _id: 1 }).balance.toString());
s1.commitTransaction();
print('after commit:', db.accounts.findOne({ _id: 1 }).balance.toString(), db.accounts.findOne({ _id: 2 }).balance.toString());

// 2  two transactions write the same document: the second fails at once with a write conflict
const a = db.getMongo().startSession(), b = db.getMongo().startSession();
a.startTransaction(); b.startTransaction();
a.getDatabase('shop').accounts.updateOne({ _id: 1 }, { $inc: { balance: Decimal128('-50') } });
try {
  b.getDatabase('shop').accounts.updateOne({ _id: 1 }, { $inc: { balance: Decimal128('-70') } });
} catch (e) {
  print(e.codeName, '| labels:', JSON.stringify(e.errorLabels));
  b.abortTransaction();
}
a.commitTransaction();

// 3  withTransaction runs the callback again when the error is labelled TransientTransactionError
const c = db.getMongo().startSession();
let attempts = 0;
c.withTransaction(() => {
  attempts++;
  c.getDatabase('shop').accounts.updateOne({ _id: 2 }, { $inc: { balance: Decimal128('-10') } });
});
print('withTransaction committed after', attempts, 'attempt(s); balances',
      db.accounts.find({ _id: { $in: [1, 2] } }).toArray().map(d => d.balance.toString()).join(' / '));

Not like SQL lockingTransaction B did not wait for A to commit; it failed at once with WriteConflict. Code written for a relational database, which expects to block and then proceed, sees an exception instead. Always use the driver's withTransaction or an equivalent retry loop.
Limits and costsTransactions are limited to 60 seconds by default (transactionLifetimeLimitSeconds). They hold resources on the server while open and add commit latency, especially across shards. Keep them short, touch few documents, and do not call other services inside them.
Say it in the interview"MongoDB transactions give snapshot isolation across documents, with optimistic conflicts: a TransientTransactionError means retry the whole transaction. I prefer a model where one document holds the invariant, and use transactions for the rare cross-document case such as a transfer."
