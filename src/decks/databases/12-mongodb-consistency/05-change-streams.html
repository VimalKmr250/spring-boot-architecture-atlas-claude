A change stream delivers every committed change as an event, and a resume token lets a consumer continue exactly where it stopped

A change stream is a cursor on the replica set's operation log, filtered and shaped with an aggregation pipeline. An application can react to inserts, updates and deletes: publish an event when an order's status changes, refresh a cache, feed a search index. Each event carries a resume token. A consumer that stores the token of the last event it handled can restart with resumeAfter and receive everything since, as long as the oplog still holds it. It is change data capture without a separate tool.

change-streams.js · MongoDB 8.3, mongosh
// open a change stream on orders, for status changes only, then make some changes
const stream = db.orders.watch(
  [{ $match: { operationType: 'update', 'updateDescription.updatedFields.status': { $exists: true } } }],
  { fullDocument: 'updateLookup' });

db.orders.updateOne({ _id: 1015 }, { $set: { status: 'PAID' } });
db.orders.updateOne({ _id: 1015 }, { $set: { note: 'gift wrap' } });          // not a status change: filtered out
db.orders.updateOne({ _id: 1018 }, { $set: { status: 'CANCELLED' } });

let event, resumeToken;
while ((event = stream.tryNext()) !== null) {
  print(event.operationType, event.documentKey._id, '->', event.updateDescription.updatedFields.status,
        '| customer', event.fullDocument.customer.name);
  resumeToken = event._id;
}
stream.close();

// a consumer that restarts resumes after the last event it processed: nothing is lost in between
db.orders.updateOne({ _id: 1015 }, { $set: { status: 'SHIPPED' } });
const resumed = db.orders.watch([{ $match: { operationType: 'update' } }], { resumeAfter: resumeToken });
print('after resume:', resumed.tryNext().updateDescription.updatedFields.status);
resumed.close();

// put the orders back for the other slides
db.orders.updateOne({ _id: 1015 }, { $set: { status: 'PENDING' }, $unset: { note: '' } });
db.orders.updateOne({ _id: 1018 }, { $set: { status: 'PENDING' } });

OptionEffect
A $match stageOnly the events you want: the note-only update was filtered out
fullDocument: 'updateLookup'Adds the current document, here for the customer's name
resumeAfter / startAfterContinue after a stored token
fullDocumentBeforeChange 6.0The document as it was before the change, if the collection keeps pre-images
Store the token after the workA consumer that saves the resume token before processing the event loses that event if it crashes in between. One that saves it after may process the event twice. So make the handler idempotent, and save the token after each event or each batch.
The oplog is a windowThe oplog is capped by size or retention time. A consumer that is down for longer than that window cannot resume and must rebuild from a full read. Size the oplog for your longest expected outage, and monitor the consumer's lag.
Say it in the interview"Change streams give ordered, resumable change events from the oplog, filtered with a pipeline. I use them as an outbox: write the order, and a consumer publishes the event, with the resume token stored after each event so a restart neither loses nor skips anything." Compare Outbox and CDC.
