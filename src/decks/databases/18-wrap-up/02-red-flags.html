Mistakes that corrupt data in production, and phrases that sink database interviews

The left column lists what goes wrong in real systems; each item has a slide in this tab, with the output that shows it happening. The right column lists what interviewers hear as a red flag, with what to say instead. Most red flags have the same root: trusting the application, or the default settings, to keep the data correct.

In production code

  • Read, check in Java, write back. Lost updates under READ COMMITTED, and overselling: 400 of 100 phones granted.
  • No unique constraint behind an upsert or an idempotency check. Two concurrent requests both insert.
  • FLOAT or MONEY for money. Rounding errors in totals, 99.9999 instead of 100.
  • NOT IN over a nullable column. An empty result, with no error.
  • Functions or conversions on indexed columns. 88 pages per lookup instead of 2, from a driver default.
  • One insert per round trip, with autocommit. Seconds where milliseconds would do.
  • OFFSET paging over large tables. Page 20,000 reads 1,789 pages instead of 6.
  • NOLOCK for speed. Reports showing values that were rolled back.
  • Single-row triggers on SQL Server. Multi-row inserts leave totals silently wrong.
  • Unbounded arrays in MongoDB. A write that fails at 16 MB, for the most active customer.
  • Retrying a timed-out write without an idempotency key. The write had succeeded; now it exists twice.
Red flag in an interviewSay instead
"The application validates it, so we don't need constraints.""Validation gives good messages; constraints keep the data correct, because the application is not the only writer, nor the only instance."
"Just add an index.""I'd read the plan first: which predicate, how many rows, and whether the index can be used for it."
"We use NOLOCK because it is faster.""If readers wait for writers, I enable read committed snapshot; NOLOCK reads uncommitted data."
"@Transactional makes it thread-safe.""A transaction at READ COMMITTED still loses updates; I use a conditional update, a version column or a lock."
"MongoDB has no transactions / no schema.""It has multi-document transactions with retries, and $jsonSchema validation; I design so most invariants live in one document."
"NoSQL scales, SQL doesn't.""It depends on the access pattern; most systems need a well-indexed relational database long before they need sharding."
"We test against H2.""Repository tests run on the production engine and version in Testcontainers, because dialect differences are where bugs hide."
"The id sequence gives us invoice numbers.""Sequences have gaps by design; gapless numbering needs its own serialised step."
