Three memory-model questions that separate senior candidates from the rest

Most candidates can say "volatile means visible". These questions ask why visibility is not automatic, what exactly volatile promises, and why one famous idiom was broken for years. The demos in this tab give you a concrete story for each.

Q16

What is the Java Memory Model, and what does happens-before mean?

30-second answerThe JMM, chapter 17 of the language specification, defines when a write in one thread is guaranteed to be visible to a read in another. Without synchronisation the compiler, the JIT and the CPU may keep values in registers, reorder instructions and buffer stores, so another thread can see stale or out-of-order values. Happens-before is the guarantee: if A happens-before B, B sees A and everything before it. A program with no data races behaves as if it ran in one sequential order.

Go deeper: List the edges: unlocking a monitor before a later lock of it, a volatile write before a later read of it, Thread.start, join, the end of a constructor for final fields, and the java.util.concurrent hand-offs. Then tell the demo: with plain fields, a store-buffering test saw both threads read 0 in tens of thousands of 200,000 trials, a result no interleaving allows; with volatile, never. x86 reorders only a store with a later load; ARM reorders more.

Q17

What does volatile guarantee, and when is it not enough?

30-second answerA read of a volatile field sees the latest write to it, and everything the writing thread did before that write. It also stops the compiler and CPU reordering around it, and makes 64-bit long and double reads and writes atomic. It does not make a compound action atomic: count++ on a volatile still loses updates. Use it for flags and for publishing immutable snapshots; use an atomic or a lock for read-modify-write and for invariants across fields.

Go deeper: In the demo, four threads each incremented a volatile counter a million times and it ended below 4,000,000, while AtomicInteger and synchronized were exact. Making an array reference volatile does not make its elements volatile: use AtomicIntegerArray. A volatile write costs a memory fence; reads are almost free on x86. The plain flag in the visibility demo never stopped its reader, because the JIT read it once, outside the loop.

Q18

Why does double-checked locking need volatile?

30-second answerinstance = new Config() is three steps: allocate, run the constructor, publish the reference. Without volatile, the publication can become visible to another thread before the constructor's writes, so a thread taking the unsynchronised fast path sees a non-null reference to a half-built object. volatile adds the happens-before edge from the constructor to every reader. Simpler still: the holder idiom, or an enum.

Go deeper: The first null check sits outside the lock so that, once initialised, readers never take it; the second, inside, stops two threads both creating one. Copy the field into a local to avoid a second volatile read. The holder idiom works because the JVM initialises a class lazily, exactly once, under a lock, and class initialisation is itself a happens-before edge. If every field of the object is final, a racy reader still sees those fields fully set, but relying on that is fragile.
