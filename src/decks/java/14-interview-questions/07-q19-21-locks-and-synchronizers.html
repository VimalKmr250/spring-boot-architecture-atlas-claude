Three questions about choosing the right waiting tool

Interviewers ask these to see whether you reach for the simplest correct tool. The strong answer names the default, then the specific feature that would justify something heavier, and one failure mode of each.

Q19

synchronized or ReentrantLock?

30-second answerBoth are re-entrant mutual-exclusion locks with the same memory semantics. synchronized is part of the language: it releases itself, even on an exception, and each object has one wait set. ReentrantLock is a class you must unlock in finally, and in return it offers tryLock with a timeout, lockInterruptibly, optional fairness, several Conditions and introspection. Default to synchronized; use ReentrantLock when you need one of those features.

Go deeper: On JDK 21 to 23, blocking inside synchronized pinned a virtual thread to its carrier: in this tab's demo, ten sleeps on one carrier took over a second with synchronized and about 100 ms with ReentrantLock. JDK 24 removed that difference. tryLock with a timeout is also a deadlock escape hatch. For read-mostly data there are ReadWriteLock and StampedLock. Lock a private final object, never this in a public class.

Q20

What is the difference between wait and sleep, and why must wait be called in a loop?

30-second answersleep pauses the thread for a time and keeps every lock it holds. wait releases the monitor of the object it is called on, blocks until notify, notifyAll, a timeout or an interrupt, then takes the monitor back before returning, and must be called while holding that monitor. Always wait in a while loop that rechecks the condition: wakeups can be spurious, notifyAll wakes every waiter, and another thread may change the state before you run.

Go deeper: Calling wait without the monitor throws IllegalMonitorStateException: current thread is not owner. notify wakes one arbitrary waiter, possibly one that cannot proceed, so prefer notifyAll, or Conditions with separate wait sets. In real code, a BlockingQueue or a latch does all of this for you. Both sleep and wait respond to interrupts by throwing InterruptedException.

Q21

CountDownLatch, CyclicBarrier or Semaphore?

30-second answerA CountDownLatch is one-shot: threads wait until a count reaches zero, as a start gate or to wait for N tasks. A CyclicBarrier makes a fixed group of threads wait for each other, round after round, with an optional action each time. A Semaphore hands out N permits, limiting how many threads proceed at once, with no owner per permit. A Phaser generalises the first two for groups whose size changes.

Go deeper: If one party at a barrier is interrupted or times out, the others get BrokenBarrierException until reset(). A latch cannot count up again. A semaphore is the natural way to bound a slow dependency from virtual threads: in the demo, 50 tasks behind Semaphore(3) never had more than three inside. Often a simpler tool fits: invokeAll, CompletableFuture.allOf or join.
