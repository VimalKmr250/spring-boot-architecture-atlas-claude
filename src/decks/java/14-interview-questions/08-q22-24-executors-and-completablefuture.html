Three questions about running work in the background, and the defaults that hurt

Every service runs background work, and these questions check that you know what the convenient defaults do under load. The answers that score name the trap in the default: an unbounded queue, a shared common pool, a carrier thread that cannot be released.

Q22

How does a ThreadPoolExecutor decide to queue, grow or reject, and why is newFixedThreadPool risky?

30-second answerOn each execute: if fewer than the core number of threads are running, start a core thread; otherwise offer the task to the queue; if the queue is full and there are fewer than the maximum threads, start an extra one; otherwise call the rejection handler, which throws by default. Extra threads appear only when the queue is full. newFixedThreadPool uses an unbounded queue, so it never grows and never rejects: under overload the queue, the latency and the heap grow until something fails.

Go deeper: Build pools explicitly: a bounded queue, named threads, and a deliberate policy. CallerRunsPolicy makes the submitting thread run the task, which slows producers down for free. newCachedThreadPool has the opposite problem: no queue and no thread limit. Size CPU-bound pools near the core count and I/O-bound ones by cores × (1 + wait/compute), then cap by what they call, such as the database pool. Monitor queue length, not just thread count.

Q23

Future or CompletableFuture, and what is the difference between thenApply and thenCompose?

30-second answerA Future can only be blocked on, polled or cancelled. A CompletableFuture can also be completed by hand and composed: attach steps that run when it completes, combine several, recover from errors and add timeouts, all without blocking a thread. thenApply maps the result with a plain function, T -> U. thenCompose takes a function that returns another future, T -> CompletableFuture<U>, and flattens it, like flatMap.

Go deeper: thenCombine joins two futures running at once, and allOf waits for many: five 200 ms calls took 200 ms in the demo because all were started before anything waited. Failures arrive wrapped in CompletionException; exceptionally and handle recover, whenComplete only observes. Without an executor, async stages run in the shared common pool, so never put blocking I/O there. cancel(true) does not interrupt the running task.

Q24

What are virtual threads, and when do they not help?

30-second answerVirtual threads, final in Java 21, are ordinary Thread objects that the JDK schedules onto a small pool of carrier threads, one per core by default. When a virtual thread blocks on I/O, a sleep or a lock, it is unmounted and its carrier runs another, so blocking thread-per-request code scales to hundreds of thousands of concurrent tasks. They do not speed up CPU-bound work, should never be pooled, and need explicit limits on the resources they call.

Go deeper: In the demo, 100,000 virtual threads each sleeping one second finished in about two seconds on 20 carriers. Pinning: on JDK 21 to 23 a virtual thread blocked inside synchronized held its carrier; JDK 24 fixed that, and native calls still pin. A million threads means a million ThreadLocal copies, which is why ScopedValue became final in 25. In Spring Boot 3.2 and later, spring.threads.virtual.enabled=true switches request handling to them.
