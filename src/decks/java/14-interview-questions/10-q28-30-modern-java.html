Three questions about the Java that came after 8

These test whether you have kept up, and whether you use new features with judgement. A good answer is specific: the release, what the feature replaces, and a case where you would not use it.

Q28

What has changed in Java since 8 that you actually use?

30-second answerBy 11: var, the List.of factories, HttpClient and the new String helpers. By 17: records, text blocks, switch expressions, instanceof patterns, sealed classes and helpful NullPointerException messages. By 21: virtual threads, pattern matching in switch with record patterns, and sequenced collections. In 25: scoped values, flexible constructor bodies, compact source files and compact object headers. Plus the runtime: G1 by default, container awareness, and JFR included free.

Go deeper: Say what broke on an upgrade you did: reflection into JDK internals closed in 16 and 17, the Java EE modules removed in 11, libraries built for a newer class file version. Explain the cadence: a feature release every six months and an LTS every two years, with previews behind --enable-preview until they are final. Structured concurrency is still a preview in 25.

Q29

When would you not use a record?

30-second answerA record is a transparent, shallowly immutable carrier: a final class whose private final fields are its components, with a canonical constructor, accessors and value-based equals, hashCode and toString, built into the language. Do not use one when you need mutable state, inheritance from a class, hidden or derived state stored in fields, or framework contracts such as JPA entities, which need a no-argument constructor and proxies. Use it for DTOs, events, keys, projections and value objects.

Go deeper: Validate and copy in the compact constructor, because a record holding a caller's List is not immutable. An array component makes equals compare identity. Records deserialize through their canonical constructor, so validation runs there too, unlike ordinary classes. Lombok's @Value gives similar classes through an annotation processor, with more knobs and a build-time dependency.

Q30

What problem do sealed classes and pattern matching solve together?

30-second answerA sealed type lists exactly which classes may extend it, so the compiler knows the complete set. A switch over it, matching types and deconstructing records, can then be checked for exhaustiveness: no default is needed, and adding a new subtype breaks every switch that does not handle it, at compile time. Together they give Java algebraic data types: a closed hierarchy of records, handled by one switch per operation instead of a visitor.

Go deeper: Permitted subclasses must be final, sealed or non-sealed. Guards use when, case null handles null, and a case that can never match is a dominance error. If a new subtype arrives without recompiling the switch, it throws MatchException. The design trade-off: sealed types and switches when the set of types is fixed and operations keep coming; an interface method when new types keep coming.
