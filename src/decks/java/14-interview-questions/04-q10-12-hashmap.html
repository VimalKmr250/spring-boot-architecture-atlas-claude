The HashMap questions, asked in every Java interview at every level

"How does HashMap work?" is the most common core-Java question there is. A junior answer describes buckets. A strong answer adds the hash spreading, the resize rule, Java 8's tree bins and what goes wrong with mutable keys, which is what the next two questions probe.

Q10

How does HashMap work internally?

30-second answerIt is an array of buckets whose length is a power of two, 16 by default. put calls hashCode, mixes the high 16 bits into the low ones, and masks with length - 1 to choose a bucket. It walks that bucket comparing the stored hash, then equals, and replaces the value or appends a node. When the size passes capacity × 0.75 the table doubles. get repeats the same lookup. Both are O(1) on average.

Go deeper: A power of two lets the index be one AND instead of a division, and spreading the hash keeps keys that differ only in high bits from colliding. On resize each node stays at index i or moves to i + oldCapacity, decided by one bit of the stored hash, so hashCode is never called again. The null key lives in bucket 0. Iteration follows bucket order, which changes on resize. new HashMap<>(1000) still resizes at 769 entries; HashMap.newHashMap(1000) (19) does not.

Q11

What happens when keys collide, and what did Java 8 change?

30-second answerColliding keys share a bucket as a linked list, so a lookup there is linear in the number of colliding keys. Since Java 8, adding to a bucket that already holds 8 nodes converts it into a red-black tree, making it O(log n), but only once the table has at least 64 slots; a smaller table resizes instead. A tree bin that shrinks to 6 nodes or fewer on a resize becomes a list again. Java 8 also switched to appending new nodes at the tail.

Go deeper: The change (JEP 180) defends against hash-flooding attacks, where crafted keys all collide. In this tab's demo, with every key hashing to 42, the 9th and 10th keys doubled the table to 32 and then 64, and the 11th made the tree. Tree bins order by hash, then compareTo if the keys are Comparable. A TreeNode is about twice the size of a Node. A bad hashCode is a performance cliff, never a correctness bug.

Q12

Why should HashMap keys be immutable?

30-second answerThe map files each entry under its key's hash at the moment of insertion. If a field that hashCode uses changes later, the key now hashes to a different bucket: get and remove look in the wrong place and fail, while the entry stays in the map, unreachable. That is a wrong answer and a memory leak at once. String, records of immutable types and Instant cannot drift.

Go deeper: The demo in this tab mutates a Date key: get returns null while the map still reports size 1. The same holds for HashSet elements and for the fields a TreeMap comparator reads. If a key must change, remove it, change it, then put it back. A record is only a safe key if its components are immutable too: a List component reopens the problem.
