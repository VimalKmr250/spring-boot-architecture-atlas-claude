Three questions about what the JVM is doing underneath your code

JVM questions come up most in senior and production-focused rounds, often as "tell me about an OutOfMemoryError you fixed". Answer with the model first, then the evidence you would collect: the error message, a heap dump, a GC log, a thread dump.

Q25

What are the JVM's memory areas, and how do StackOverflowError and OutOfMemoryError differ?

30-second answerEach thread has a program counter and a stack of frames holding locals and operands. Shared areas are the heap, split into young (Eden and two survivor spaces) and old generations; Metaspace for class metadata; the code cache for compiled code; and native memory for direct buffers, thread stacks and the GC's own structures. StackOverflowError means one thread's stack is full, usually from runaway recursion. OutOfMemoryError means an area could not satisfy an allocation, and its message names the area.

Go deeper: Know the messages: Java heap space, Metaspace, Cannot reserve … direct buffer memory, unable to create native thread, Requested array size exceeds VM limit. Each points at a different cause and flag: -Xmx, MaxMetaspaceSize, MaxDirectMemorySize, OS limits, a size bug. In a container the process needs the heap plus everything else, so a limit equal to -Xmx gets the process killed. Always run with -XX:+HeapDumpOnOutOfMemoryError.

Q26

How does the garbage collector decide what is garbage, and why are heaps generational?

30-second answerBy tracing, not by counting references. Starting from the GC roots (every thread's locals, static fields, JNI references and held monitors), the collector marks everything reachable and reclaims the rest, including cycles that point only at each other. Most objects die young, so new objects go into a young generation that is collected often and cheaply by copying the few survivors; long-lived ones are promoted to the old generation and collected rarely. G1 is the default collector; ZGC targets sub-millisecond pauses.

Go deeper: A Java memory leak is an object that is still reachable by mistake: a static map, a listener, a ThreadLocal. Soft references are cleared before any OutOfMemoryError, weak ones at the next collection, and phantom ones drive Cleaner. System.gc() is only a request. finalize is deprecated for removal. Choosing between G1, ZGC and Parallel depends on the latency and throughput goals, and is measured from GC logs.

Q27

What happens between "java -jar" and your first line of main, and why are the first requests slow?

30-second answerThe launcher starts the JVM, which sets up the runtime and the collector, then loads the main class through the application class loader, which delegates to the platform and bootstrap loaders. The class is linked (verified, prepared, resolved) and initialised (its static initialisers run), and main starts in the interpreter. Other classes load lazily when first used, and hot code is compiled by C1 and then C2. Early requests pay for class loading, initialisation and interpretation: that is warm-up.

Go deeper: In the demo the first call of a method took milliseconds and the two-thousandth tens of microseconds. A class built for a newer JDK fails here with UnsupportedClassVersionError. Class data sharing and Leyden's AOT cache (JDK 24 and 25) store loaded classes and method profiles from a training run to start warmer; GraalVM native image compiles ahead of time. In Kubernetes, only report ready after warm-up traffic.
