Three collections questions that test whether you have measured anything

Each of these has a textbook answer and a real one. The textbook says linked lists are good at inserts and fail-fast iterators catch concurrent changes. The real answers, backed by this tab's measurements, are what interviewers hope to hear.

Q13

ArrayList or LinkedList: when would you choose LinkedList?

30-second answerAlmost never. ArrayList is a resizable array: O(1) get, amortised O(1) appends, O(n) inserts in the middle by shifting, and 4 bytes per reference. LinkedList is a doubly linked list: O(1) at the ends or at an iterator's position, but O(n) get with a cache miss per node, and 24 bytes per node. For a queue or a stack, ArrayDeque beats both. LinkedList only wins for many middle inserts through an iterator you already hold.

Go deeper: ArrayList grows by half when full and allocates its first 10 slots lazily; presize it when you know the size. In this tab's measurement, 1,000 calls to get(n/2) on a million elements took a fraction of a millisecond on ArrayList and over a second on LinkedList. Even middle inserts are usually faster on the array, because System.arraycopy moves memory faster than the list can walk to the node.

Q14

What is a ConcurrentModificationException, and how do you avoid it?

30-second answerNon-concurrent collections count their structural changes, and an iterator checks that count on each next(). If anything other than the iterator itself changed the collection, it throws, even in a single thread, for example list.remove(x) inside a for-each loop. Avoid it with Iterator.remove, removeIf, a ListIterator, collecting the changes and applying them after the loop, or a concurrent collection.

Go deeper: The check is best-effort, not a guarantee. Removing the second-to-last element of an ArrayList during a for-each ends the loop silently and skips the last element, because hasNext() only compares the cursor with the size. Concurrent collections never throw: ConcurrentHashMap's iterators are weakly consistent, and CopyOnWriteArrayList's iterate a snapshot. For maps, use entrySet().removeIf.

Q15

HashMap, Hashtable, synchronizedMap or ConcurrentHashMap?

30-second answerHashMap is not thread-safe and allows a null key and null values. Hashtable is legacy: every method locks one shared lock, and it rejects nulls. Collections.synchronizedMap wraps any map in one lock, but iteration and compound actions still need your own locking. ConcurrentHashMap reads without locking, locks one bin per write, offers atomic compute, merge and putIfAbsent, and rejects nulls. For a shared map, it is the default.

Go deeper: Nulls are banned because a null from get must mean absent: in a concurrent map you cannot follow up with containsKey safely. Even on a ConcurrentHashMap, get then put is a race; the demo lost increments that merge did not. A plain HashMap shared by eight writers lost a large share of 400,000 keys with no exception. Java 7's version used segments; Java 8 rewrote it around bins.
