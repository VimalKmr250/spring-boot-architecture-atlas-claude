Q1

Is Java pass-by-value or pass-by-reference?

30-second answerAlways pass-by-value. For a primitive, the value copied is the number; for an object, the value copied is the reference. So a method can change the object the caller passed in, because both references point at it, but assigning a new object to the parameter only moves the method's own copy. That is why you cannot write a swap(a, b) in Java.

Go deeper: Draw the two stack frames and the one heap object. "Objects are passed by reference" is the answer interviewers are listening for as a mistake: in a pass-by-reference language the callee could rebind the caller's variable, and Java cannot. Strings and wrappers look as if they were copied because they are immutable, so no method can change them at all. To return two values, return a record.

Q2

Why is String immutable, and what is the string pool?

30-second answerEvery method that seems to modify a String returns a new one. That makes strings safe to share between threads, safe as hash keys (the hash is cached), and safe for security checks, because a path or class name cannot change after it was checked. It also lets the JVM pool them: identical literals and compile-time constants share one instance. new String(…) always makes a new object, and intern() returns the pooled one.

Go deeper: The pool has been in the heap since Java 7. "ord" + "er" is folded by javac into the literal, so it is the pooled instance; part + "er" is built at run time and is not. Hence == on strings passes tests and fails on input. Since Java 9 a Latin-1 string uses one byte per character (compact strings). And += in a loop copies everything each time: 57.8 MB against 98 KB for StringBuilder in this tab's demo.

Q3

What is the difference between == and equals, and why must hashCode be overridden with equals?

30-second answer== compares primitives by value and objects by identity: is it the same object? equals compares meaning, as each class defines it; Object's default is identity. Hash collections pick a bucket by hashCode and call equals only inside it. If two equal objects have different hash codes they land in different buckets, so a HashSet holds both "duplicates" and contains fails. Equal objects must have equal hash codes.

Go deeper: Name the contract: reflexive, symmetric, transitive, consistent, false for null. Then the traps: a hash code built from a mutable field loses the entry when the field changes; instanceof equality across a subclass that adds fields breaks symmetry; equals(Order) is an overload, not an override, which @Override catches. javac's -Xlint:overrides warns about equals without hashCode. A record generates both correctly.
