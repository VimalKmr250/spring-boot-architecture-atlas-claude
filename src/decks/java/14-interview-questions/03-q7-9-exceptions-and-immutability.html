Three questions about failing safely and staying unchanged

Exception questions test judgement as much as rules: when to make a caller deal with something, and how to keep the cause when you translate. The immutability question is a checklist question, and a missing item is easy to spot.

Q7

Checked or unchecked exceptions: what is the difference, and when do you use each?

30-second answerChecked exceptions, subclasses of Exception but not of RuntimeException, must be caught or declared, and javac enforces it. Use them for recoverable conditions at a boundary the caller can act on, such as I/O or a timeout. Unchecked ones, RuntimeException and Error, need no declaration: programming errors and failures no caller can fix. Modern code, and Spring, favour unchecked domain exceptions, translated from checked ones at the boundary, keeping the cause.

Go deeper: Checked-ness exists only in the compiler; the JVM never checks it. Checked exceptions do not mix with lambdas, because the standard functional interfaces declare none. Never catch Error except to log at the top of a thread. A static initialiser that throws gives ExceptionInInitializerError once, then NoClassDefFoundError forever. Catching InterruptedException must restore the interrupt flag.

Q8

What does try-with-resources do that a finally block does not?

30-second answerIt closes every AutoCloseable it declares, in reverse order, however the body exits. If the body throws and close() throws too, the body's exception propagates and the close failure is attached to it with addSuppressed. A hand-written finally that calls close() lets the close failure replace the original, so the log shows the symptom and loses the cause. It also skips a resource that is null.

Go deeper: A return inside finally discards any exception in flight, and javac's [finally] lint is the only warning. finally does not run on System.exit or a killed process. Since Java 9 an effectively final variable can be the resource. Make close() idempotent, because wrappers often close what they wrap. ExecutorService (19) and HttpClient (21) are AutoCloseable too.

Q9

How do you make a class immutable?

30-second answerMake the class final, or give it a private constructor and factories. Make every field private and final, with no setters; a change returns a new instance. Copy every mutable input in the constructor, for example with List.copyOf, and prefer immutable types such as Instant over Date. Never return mutable internals. A record does most of this, but you still copy mutable components in its compact constructor.

Go deeper: The payoffs: no locks needed, safe sharing and caching, stable hash keys, and final fields mean other threads see the object fully built. The traps: Collections.unmodifiableList is a view the owner can still change; List.copyOf is shallow, so the elements must be immutable too; and a non-final class can be subclassed into something mutable. String and the wrappers are the textbook examples.
