Every object pays a header and rounds up to 8 bytes, so a boxed int costs four times an int

On a 64-bit HotSpot with a heap under 32 GB, an object starts with a 12-byte header: an 8-byte mark word for the hash, locking and GC age, and a 4-byte compressed class pointer. Fields follow, and the total rounds up to a multiple of 8. References are 4 bytes. JDK 25 can shrink the header to 8 bytes with compact object headers (JEP 519), an opt-in product flag. The per-object rows below count allocated bytes; the map line measures heap in use after a full GC.

ObjectSize.java · bytes per object, then a map against an array
import java.lang.management.ManagementFactory;
import java.util.*;
import java.util.function.IntFunction;

public class ObjectSize {
    static final com.sun.management.ThreadMXBean MX =
            (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();

    record Money(long cents) { }
    record Line(int qty, long cents) { }

    // Average bytes per object over many allocations, so the measurement itself is noise.
    static long each(IntFunction<Object> make) {
        int n = 100_000;
        Object[] keep = new Object[n];                     // allocated first: not counted
        long before = MX.getCurrentThreadAllocatedBytes();
        for (int i = 0; i < n; i++) keep[i] = make.apply(i);
        long bytes = MX.getCurrentThreadAllocatedBytes() - before;
        return Math.round(bytes / (double) n);
    }

    static long liveHeap() {
        System.gc();
        return ManagementFactory.getMemoryMXBean().getHeapMemoryUsage().getUsed();
    }

    public static void main(String[] args) {
        System.out.println("compact object headers: " + ManagementFactory.getRuntimeMXBean().getInputArguments()
                .contains("-XX:+UseCompactObjectHeaders"));
        System.out.printf("%-26s %3d bytes%n", "new Object()", each(i -> new Object()));
        System.out.printf("%-26s %3d bytes%n", "Integer (not cached)", each(i -> Integer.valueOf(1_000 + i)));
        System.out.printf("%-26s %3d bytes%n", "Long", each(i -> Long.valueOf(1_000 + i)));
        System.out.printf("%-26s %3d bytes%n", "record Money(long)", each(i -> new Money(i)));
        System.out.printf("%-26s %3d bytes%n", "record Line(int, long)", each(i -> new Line(i, i)));
        System.out.printf("%-26s %3d bytes%n", "new int[0]", each(i -> new int[0]));
        System.out.printf("%-26s %3d bytes%n", "new int[10]", each(i -> new int[10]));
        System.out.printf("%-26s %3d bytes%n", "new Object[10]", each(i -> new Object[10]));
        System.out.printf("%-26s %3d bytes%n", "String.valueOf(10_000 + i)", each(i -> String.valueOf(10_000 + i)));

        int n = 1_000_000;                                 // retained size, measured after a full GC
        long base = liveHeap();
        Map<Integer, Integer> boxed = HashMap.newHashMap(n);
        for (int i = 0; i < n; i++) boxed.put(i + 1_000, i + 1_000);
        long mapBytes = liveHeap() - base;
        base = liveHeap();
        int[] plain = new int[n];
        for (int i = 0; i < n; i++) plain[i] = i;
        long arrayBytes = liveHeap() - base;
        System.out.printf("1M int->int entries kept alive: HashMap %d bytes each, int[] %d bytes each (%d, %d)%n",
                mapBytes / n, arrayBytes / n, boxed.size(), plain.length);
    }
}

RowWhy
new Object() 16 → 8A header and nothing else, rounded to 8. Compact headers halve it.
Long 24 → 1612 bytes of header leave the 8-byte field misaligned, so 4 bytes are wasted. An 8-byte header fixes both.
int[10] 56An array header holds its length too (16 bytes here), plus 4 bytes per element.
String of 5 digits: 48A 24-byte String plus a 24-byte byte[5]. Latin-1 text stores one byte per character.
HashMap, about 70 per entryA 32-byte node, two 16-byte Integers and table slots: over 16 times the int[].
Big numeric dataA million boxed entries cost about 70 MB, where two int[] arrays cost 8 MB. For large sets of numbers use primitive arrays, IntStream, or a primitive collection library such as fastutil or Eclipse Collections.
The 32 GB cliffCompressed references work up to about 32 GB of heap. Above that every reference doubles to 8 bytes, so a 33 GB heap can hold less than a 31 GB one. Stay below 32 GB, or go well above it.
Measuring your own objectsJOL (Java Object Layout) prints the exact field layout of any class. jcmd <pid> GC.class_histogram shows which classes fill a live heap, and a heap dump shows who holds them: see memory leaks.
