Each thread has its own stack; everything else is shared, and each area fails with its own error

The JVM's memory is not just the heap. Each thread has a stack of frames holding its locals and operands. The heap holds every object. Metaspace holds class metadata, the code cache holds JIT-compiled code, and direct buffers, thread stacks and the GC's own structures live outside the heap altogether. When one area runs out, the error message names it, and the message tells you where to look.

MemoryAreas.java · the pools, then four of the ways to run out
// Run with: java -Xmx64m -XX:MaxDirectMemorySize=1m MemoryAreas.java
import java.lang.management.*;
import java.nio.ByteBuffer;
import java.util.*;

public class MemoryAreas {
    static int depth;
    static void recurse() { depth++; recurse(); }

    public static void main(String[] args) {
        for (MemoryPoolMXBean pool : ManagementFactory.getMemoryPoolMXBeans())
            System.out.printf("%-8s %s%n", pool.getType() == MemoryType.HEAP ? "heap" : "non-heap", pool.getName());

        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("StackOverflowError after about " + (depth / 1_000) * 1_000 + " frames (varies with -Xss and the JIT)");
        }

        List<long[]> hoard = new ArrayList<>();
        try {
            while (true) hoard.add(new long[1_000_000]);          // 8 MB each, all kept reachable
        } catch (OutOfMemoryError e) {
            int held = hoard.size();
            hoard = null;                                         // release it so the program can go on
            System.out.println("OutOfMemoryError: " + e.getMessage() + " (after " + held + " x 8 MB)");
        }
        try {
            long[] huge = new long[Integer.MAX_VALUE];
            System.out.println(huge.length);
        } catch (OutOfMemoryError e) {
            System.out.println("OutOfMemoryError: " + e.getMessage());
        }
        try {
            ByteBuffer.allocateDirect(2 * 1024 * 1024);           // off-heap, capped by MaxDirectMemorySize
        } catch (OutOfMemoryError e) {
            System.out.println("OutOfMemoryError: " + e.getMessage());
        }
        MemoryUsage heap = ManagementFactory.getMemoryMXBean().getHeapMemoryUsage();
        System.out.println("heap max " + heap.getMax() / (1024 * 1024) + " MB, set by -Xmx64m");
    }
}

The message saysLook at
Java heap spaceA leak or an undersized heap: take a heap dump (-XX:+HeapDumpOnOutOfMemoryError)
GC overhead limit exceededParallel GC spent nearly all its time collecting and recovered almost nothing: the same causes
MetaspaceToo many classes: generated proxies, or a class loader leak after redeploys
Requested array size exceeds VM limitAn array near Integer.MAX_VALUE elements, usually a bug in a size calculation
Cannot reserve … direct buffer memoryOff-heap buffers from Netty, NIO or a driver, past MaxDirectMemorySize
unable to create native threadOS or container limits on threads or memory, not the heap
StackOverflowErrorRecursion without a base case, or a very deep but valid one: raise -Xss
In a container, heap is not the whole billThe process uses the heap plus Metaspace, code cache, thread stacks, direct buffers and the GC's own structures. A container sized to exactly -Xmx gets killed by the kernel with no Java error at all. The Spring Boot tab works through the sizing: JVM memory.
