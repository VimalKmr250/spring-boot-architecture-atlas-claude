The JIT compiles what runs hot, optimises it with what it has seen, and undoes it when it was wrong

HotSpot starts every method in the interpreter and counts calls and loop iterations. Hot methods are compiled by C1, which also records which types and branches actually occur, and then by C2, which uses that profile to inline, unroll loops and remove allocations. The first call below took milliseconds; the two-thousandth took tens of microseconds. That gap is why a freshly started service is slow, and why naive benchmarks lie.

Jit.java · warm-up, and an allocation the JIT removes
import java.lang.management.ManagementFactory;

public class Jit {
    record Point(double x, double y) {
        double length() { return Math.sqrt(x * x + y * y); }
    }

    static double walk(int steps) {                 // one Point per step, and none escapes it
        double total = 0;
        for (int i = 0; i < steps; i++) {
            Point p = new Point(i, i + 1);
            total += p.length();
        }
        return total;
    }

    static final com.sun.management.ThreadMXBean MX =
            (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();

    public static void main(String[] args) {
        long[] nanos = new long[5];
        double sink = 0;
        for (int round = 0; round < 2_000; round++) {
            long t0 = System.nanoTime();
            sink += walk(10_000);
            long ns = System.nanoTime() - t0;
            if (round == 0) nanos[0] = ns;
            if (round == 1) nanos[1] = ns;
            if (round == 10) nanos[2] = ns;
            if (round == 100) nanos[3] = ns;
            if (round == 1_999) nanos[4] = ns;
        }
        System.out.printf("walk(10,000) took %d, %d, %d, %d, %d microseconds on runs 1, 2, 11, 101, 2000%n",
                nanos[0] / 1_000, nanos[1] / 1_000, nanos[2] / 1_000, nanos[3] / 1_000, nanos[4] / 1_000);

        long before = MX.getCurrentThreadAllocatedBytes();
        sink += walk(1_000_000);
        long bytes = MX.getCurrentThreadAllocatedBytes() - before;
        System.out.printf("walk(1,000,000) once warm allocated %,d bytes for 1,000,000 Points (sink %.0f)%n", bytes, Math.floor(sink));
    }
}

In the PrintCompilation linesMeans
First two columnsMilliseconds since start, then the compile task's id
Tier 3, then 4C1 with profiling, then C2. Tier 0 is the interpreter; tiers 1 and 2 are rarely used C1 variants.
% and @ 4On-stack replacement: the loop at bytecode index 4 was compiled while walk was still running, and the frame switched over mid-loop.
made not entrantThat compiled version is retired: replaced by a better tier, or invalidated because an assumption stopped holding (deoptimisation).
OptimisationHere
InliningPoint.length() and the constructor were compiled into walk, which is what lets the next one work.
Escape analysisNo Point leaves its iteration, so C2 kept its fields in registers: 0 bytes allocated, against 32 MB with the analysis switched off.
SpeculationCalls are inlined for the classes seen so far, behind a cheap check; a new class arriving triggers deoptimisation.
Why naive benchmarks lieA loop timed with System.nanoTime measures the interpreter, then a compile, then code that may have removed the work entirely because its result is unused. Use JMH, which forks JVMs, warms up, and consumes results with a Blackhole.
Warm-up in productionThe first requests after a deploy run interpreted and trigger compiles that compete for CPU. Send synthetic traffic before marking an instance ready, or keep enough capacity that slow instances do not matter.
