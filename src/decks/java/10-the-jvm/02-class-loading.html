A class is loaded on demand by a chain of loaders, and its identity includes the loader that defined it

Classes are loaded lazily, the first time code needs them. Each loader asks its parent first and defines the class itself only if the parent cannot, so java.lang.String always comes from the bootstrap loader and cannot be replaced from the classpath. A loaded class is then linked, and initialised (its static initialiser run) only on its first active use. At run time a class is its name plus its loader.

ClassLoading.java · the chain, lazy initialisation, two loaders and one name
import java.net.URL;
import java.net.URLClassLoader;

public class ClassLoading {
    public static class Tariffs {                           // public: see the last part
        static { System.out.println("  Tariffs static initialiser runs, in " + Tariffs.class.getClassLoader().getName()); }
        public Tariffs() { }
        static final int VAT_PERCENT = 20;                          // a constant: no initialisation
        static int lookups = 0;
    }

    static String loader(Class<?> c) {
        ClassLoader l = c.getClassLoader();
        return c.getName() + " -> " + (l == null ? "bootstrap (null)" : l.getName());
    }

    public static void main(String[] args) throws Exception {
        System.out.println(loader(String.class));
        System.out.println(loader(java.sql.Connection.class));
        System.out.println(loader(ClassLoading.class));
        System.out.println("parent chain: app -> " + ClassLoader.getSystemClassLoader().getParent().getName()
                + " -> " + ClassLoader.getSystemClassLoader().getParent().getParent());

        System.out.println("reading the constant VAT_PERCENT = " + Tariffs.VAT_PERCENT);
        Class<?> loadedOnly = Class.forName("ClassLoading$Tariffs", false, ClassLoading.class.getClassLoader());
        System.out.println("forName(name, false, loader) loaded " + loadedOnly.getSimpleName() + " without initialising it");
        System.out.println("now touching a non-constant static field:");
        Tariffs.lookups++;
        System.out.println("  lookups = " + Tariffs.lookups);

        // Two loaders that do not delegate to each other each define their own class with the same name.
        URL classes = ClassLoading.class.getProtectionDomain().getCodeSource().getLocation();
        try (var first = new URLClassLoader("first", new URL[] {classes}, null);
             var second = new URLClassLoader("second", new URL[] {classes}, null)) {
            Class<?> a = first.loadClass("ClassLoading$Tariffs"), b = second.loadClass("ClassLoading$Tariffs");
            Object instance = a.getDeclaredConstructor().newInstance();
            System.out.println("same name, two loaders: a == b " + (a == b) + ", b.isInstance(object of a) " + b.isInstance(instance)
                    + ", a == Tariffs.class " + (a == Tariffs.class));
        }
    }
}

X cannot be cast to XThe same class file defined by two loaders gives two unrelated classes: a == b is false and casting between them throws ClassCastException with both names identical. It happens when a library is both in an app server and in the web app, or in plugin systems and test frameworks.
Class loader leaksA class keeps its loader alive, and the loader keeps every class it defined, with their static fields. One ThreadLocal or JDBC driver registration that outlives a redeployed web app keeps the whole old app in Metaspace. After a few redeploys: OutOfMemoryError: Metaspace.
Each loader, its own staticsThe first loader's copy of Tariffs ran its static initialiser again, with its own lookups. Lazy initialisation is also what makes the holder idiom thread-safe: the JVM runs a class's initialiser exactly once, under a lock.
