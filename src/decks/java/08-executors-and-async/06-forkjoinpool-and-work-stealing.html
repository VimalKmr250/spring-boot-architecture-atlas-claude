ForkJoinPool splits work recursively and lets idle threads steal it, so every core stays busy

A fork/join task splits itself in two until the pieces are small, forks one half and computes the other. Each worker keeps its forked tasks in its own deque and works from the top. A worker with nothing to do steals from the bottom of someone else's deque, where the oldest and largest pieces are. Parallel streams and CompletableFuture's default executor both run on this machinery, in the common pool.

ForkJoin.java · a RecursiveTask, and the pool that parallel streams use
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.LongAdder;
import java.util.stream.LongStream;

public class ForkJoin {
    static final LongAdder TASKS = new LongAdder();

    static final class Sum extends RecursiveTask<Long> {
        private static final long serialVersionUID = 1L;
        static final int THRESHOLD = 10_000;
        private final long[] data;
        private final int from, to;
        Sum(long[] data, int from, int to) { this.data = data; this.from = from; this.to = to; }

        @Override protected Long compute() {
            TASKS.increment();
            if (to - from <= THRESHOLD) {                     // small enough: just do it
                long s = 0;
                for (int i = from; i < to; i++) s += data[i];
                return s;
            }
            int mid = (from + to) >>> 1;
            Sum left = new Sum(data, from, mid), right = new Sum(data, mid, to);
            left.fork();                                      // push onto this worker's deque
            long r = right.compute();                         // work on the other half ourselves
            return left.join() + r;                           // often run by us, sometimes stolen
        }
    }

    public static void main(String[] args) {
        long[] data = LongStream.rangeClosed(1, 10_000_000).toArray();
        ForkJoinPool pool = new ForkJoinPool(8);
        long total = pool.invoke(new Sum(data, 0, data.length));
        System.out.printf("sum %,d from %,d tasks; steals: %,d (varies by run)%n", total, TASKS.sum(), pool.getStealCount());
        pool.close();

        Set<String> threads = new ConcurrentSkipListSet<>();
        long parallel = LongStream.rangeClosed(1, 2_000_000).parallel()
                .peek(i -> threads.add(Thread.currentThread().getName().replaceAll("\\d+$", "N")))
                .sum();
        System.out.println("parallel stream sum " + parallel + " ran on " + threads);
        System.out.println("common pool parallelism " + ForkJoinPool.getCommonPoolParallelism()
                + " (cores - 1; the caller thread joins in)");
    }
}

Writing a fork/join task

  • Fork one half, compute the other. Forking both and joining both leaves the current worker idle.
  • Pick a threshold. Too small and task overhead dominates; too large and cores sit idle at the end. 10,000 elements gave 2,047 tasks here.
  • Join in reverse order of forking, so the worker usually pops its own task instead of waiting.
  • RecursiveTask<V> returns a value; RecursiveAction does not.
Do not block in itFork/join assumes tasks compute. A task that waits on I/O or a lock holds a worker, and the common pool has only cores − 1 of them for the whole JVM. If blocking is unavoidable, wrap it in ForkJoinPool.managedBlock so the pool can add a thread meanwhile.
Parallel streamsThe output shows a parallel stream running on common-pool workers and on main: the calling thread joins in, which is why the pool is sized to cores − 1. When that helps and when it hurts is on how a parallel stream runs.
