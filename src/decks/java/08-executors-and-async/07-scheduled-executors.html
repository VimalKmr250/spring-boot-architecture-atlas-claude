Fixed rate keeps a timetable, fixed delay keeps a gap, and either one stops for good after an exception

ScheduledExecutorService runs tasks after a delay or periodically, on a small thread pool. The two periodic methods differ only when a run takes longer than the period, which in production is exactly when it matters. And both share one dangerous rule: if a run throws, the task is never scheduled again, and nothing is logged.

Scheduling.java · rate against delay, a task that throws, java.util.Timer
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class Scheduling {
    static long t0;
    static long at() { return Math.round((System.nanoTime() - t0) / 5e7) * 50; }   // to 50 ms

    static void work(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    public static void main(String[] args) throws Exception {
        try (ScheduledExecutorService ses = Executors.newScheduledThreadPool(2)) {
            List<Long> rate = new CopyOnWriteArrayList<>(), delay = new CopyOnWriteArrayList<>();
            t0 = System.nanoTime();
            ScheduledFuture<?> r = ses.scheduleAtFixedRate(() -> { rate.add(at()); work(150); }, 0, 100, TimeUnit.MILLISECONDS);
            ScheduledFuture<?> d = ses.scheduleWithFixedDelay(() -> { delay.add(at()); work(150); }, 0, 100, TimeUnit.MILLISECONDS);
            Thread.sleep(1_000);
            r.cancel(false);
            d.cancel(false);
            System.out.println("150 ms task, period 100 ms, start times in ms:");
            System.out.println("  scheduleAtFixedRate     " + rate);
            System.out.println("  scheduleWithFixedDelay  " + delay);

            AtomicInteger runs = new AtomicInteger();
            ScheduledFuture<?> fragile = ses.scheduleAtFixedRate(() -> {
                if (runs.incrementAndGet() == 3) throw new IllegalStateException("feed unavailable");
            }, 0, 20, TimeUnit.MILLISECONDS);
            Thread.sleep(300);
            System.out.println("a periodic task that threw on run 3 ran " + runs.get() + " times in 300 ms; done=" + fragile.isDone());
            try {
                fragile.get();
            } catch (ExecutionException e) {
                System.out.println("  the exception was kept in the future: " + e.getCause().getMessage());
            }
        }

        Timer timer = new Timer("legacy-timer", true);
        timer.schedule(new TimerTask() {
            @Override public void run() { throw new IllegalStateException("one bad task"); }
        }, 0);
        Thread.sleep(100);
        try {
            timer.schedule(new TimerTask() { @Override public void run() { } }, 0);
        } catch (IllegalStateException e) {
            System.out.println("java.util.Timer after one task threw: " + e.getMessage());
        }
    }
}

One exception ends the scheduleThe task that threw on its third run never ran again: its future is done, and the exception waits inside it for a get nobody calls. Wrap every periodic body in try / catch (Exception e) that logs, so one bad run does not stop the feed for good.
java.util.Timer is worseOne thread runs every task, so a slow task delays all the others, and one exception kills that thread: every later schedule fails with Timer already cancelled. It also follows the wall clock, so a clock change shifts its timetable. The scheduled executor uses System.nanoTime.
In a clusterEvery instance runs its own schedule, so a nightly job on four pods runs four times. Use a lock such as ShedLock, or a scheduler with a shared store. Spring's @Scheduled uses a single thread by default. See batch and scheduling.
