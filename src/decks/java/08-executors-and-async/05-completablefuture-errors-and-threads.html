Failures travel down the chain wrapped in CompletionException, and each step runs on whatever thread is at hand

When a stage throws, every dependent stage completes exceptionally too, until one of them handles it. Three methods do the handling, and they differ in whether they can change the outcome. The other half of the story is threads: a non-async step runs on the thread that completed the previous one, or on the caller if that had already happened, and an async step with no executor runs in the common ForkJoinPool.

CfErrors.java · recovering, timing out, and which thread runs what
import java.util.concurrent.*;

public class CfErrors {
    static String thread() { return Thread.currentThread().getName(); }

    static CompletableFuture<Integer> failing() {
        return CompletableFuture.supplyAsync(() -> { throw new IllegalStateException("inventory down"); });
    }

    public static void main(String[] args) throws Exception {
        int recovered = failing().exceptionally(ex -> {
            System.out.println("exceptionally sees " + ex.getClass().getSimpleName() + " wrapping " + ex.getCause().getMessage());
            return 0;                                                   // a fallback value
        }).join();
        System.out.println("recovered to " + recovered);

        String handled = failing().handle((value, ex) -> ex == null ? "stock " + value : "fallback").join();
        System.out.println("handle -> " + handled);

        try {
            failing().whenComplete((v, ex) -> System.out.println("whenComplete sees the failure but cannot fix it")).join();
        } catch (CompletionException e) {
            System.out.println("join() throws CompletionException, cause " + e.getCause().getMessage());
        }
        try {
            failing().get();
        } catch (ExecutionException e) {
            System.out.println("get() throws ExecutionException, cause " + e.getCause().getMessage());
        }

        CompletableFuture<String> never = new CompletableFuture<>();
        try {
            never.orTimeout(100, TimeUnit.MILLISECONDS).join();         // Java 9
        } catch (CompletionException e) {
            System.out.println("orTimeout: " + e.getCause().getClass().getSimpleName());
        }
        System.out.println("completeOnTimeout: " + new CompletableFuture<String>()
                .completeOnTimeout("cached price", 100, TimeUnit.MILLISECONDS).join());

        System.out.println("supplyAsync with no executor runs on: " + CompletableFuture.supplyAsync(CfErrors::thread).join());
        CompletableFuture<String> done = CompletableFuture.completedFuture("x");
        System.out.println("thenApply on a completed future runs on: " + done.thenApply(v -> thread()).join());
        CompletableFuture<String> later = CompletableFuture.supplyAsync(() -> {
            try { Thread.sleep(100); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            return "y";
        });
        CompletableFuture<String> after = later.thenApply(v -> thread());
        System.out.println("thenApply registered before completion runs on: " + after.join());
        System.out.println("thenApplyAsync runs on: " + done.thenApplyAsync(v -> thread()).join());
        System.out.println("common pool parallelism: " + ForkJoinPool.commonPool().getParallelism()
                + " on " + Runtime.getRuntime().availableProcessors() + " cores");
    }
}

Unwrap before you inspectA failure from an async stage arrives wrapped: exceptionally saw a CompletionException whose cause was the real IllegalStateException. join throws that unchecked wrapper, get a checked ExecutionException. Test ex.getCause(), not ex.
Blocking work in the common poolWith no executor, supplyAsync uses the common pool: 19 threads on this 20-core machine, shared with every parallel stream in the JVM. Twenty slow HTTP calls there stall everything else. Pass an executor for anything that blocks, as CfCompose does with IO.
cancel does not interruptCompletableFuture.cancel(true) completes the future with a CancellationException but does not interrupt the thread running the task, which carries on. If the work must stop, check a flag or use a Future from an ExecutorService.
