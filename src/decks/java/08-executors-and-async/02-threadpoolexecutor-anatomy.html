A pool fills its core threads, then its queue, then its extra threads, and then it rejects

The order surprises almost everyone: a ThreadPoolExecutor adds threads beyond the core size only when the queue is full. With an unbounded queue the queue is never full, so the maximum pool size is never used and a fixed pool can only queue. The demo blocks every task so each decision stays visible.

PoolAnatomy.java · seven blocked tasks into core 2, queue 2, max 4
import java.util.concurrent.*;

public class PoolAnatomy {
    public static void main(String[] args) throws Exception {
        CountDownLatch release = new CountDownLatch(1);
        Runnable blocker = () -> {
            try { release.await(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };

        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2, 4,                                   // core and maximum threads
                30, TimeUnit.SECONDS,                   // idle time before extra threads die
                new ArrayBlockingQueue<>(2),            // a bounded queue
                Thread.ofPlatform().name("pool-", 1).factory(),
                new ThreadPoolExecutor.AbortPolicy());  // the default: throw

        for (int task = 1; task <= 7; task++) {
            int threads = pool.getPoolSize();
            String outcome;
            try {
                pool.execute(blocker);
                outcome = pool.getPoolSize() > threads
                        ? (threads < pool.getCorePoolSize() ? "new core thread" : "queue full, so an extra thread")
                        : "queued";
            } catch (RejectedExecutionException e) {
                outcome = "REJECTED: " + e.getClass().getSimpleName();
            }
            System.out.printf("task %d: %-37s threads %d, queued %d%n", task, outcome, pool.getPoolSize(), pool.getQueue().size());
        }
        release.countDown();
        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
        System.out.println("completed " + pool.getCompletedTaskCount() + ", largest pool " + pool.getLargestPoolSize());

        // CallerRunsPolicy: when full, the submitting thread runs the task itself (back-pressure).
        CountDownLatch release2 = new CountDownLatch(1);
        ThreadPoolExecutor polite = new ThreadPoolExecutor(1, 1, 0, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(1), new ThreadPoolExecutor.CallerRunsPolicy());
        polite.execute(() -> { try { release2.await(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } });
        polite.execute(() -> { });                                       // fills the queue
        polite.execute(() -> System.out.println("third task ran on: " + Thread.currentThread().getName()));
        release2.countDown();
        polite.shutdown();
        polite.awaitTermination(5, TimeUnit.SECONDS);

        int cores = Runtime.getRuntime().availableProcessors();
        double waitMs = 90, computeMs = 10;
        System.out.printf("sizing on %d cores: CPU-bound about %d threads; 90 ms waiting per 10 ms computing about %d%n",
                cores, cores, (int) (cores * (1 + waitMs / computeMs)));
    }
}

Rejection policyWhen the pool is full
AbortPolicy (default)Throws RejectedExecutionException to the submitter
CallerRunsPolicyThe submitting thread runs the task itself, so it slows down: back-pressure for free
DiscardPolicyDrops the task silently. Almost never what you want
DiscardOldestPolicyDrops the oldest queued task and retries; for latest-value-wins work only

Sizing

  • CPU-bound: about one thread per core. More threads only add switching.
  • Blocking I/O: cores × (1 + wait time / compute time), from Goetz: 200 for the example above.
  • Little's law checks it: threads busy = arrival rate × time per task. 400 requests/s at 250 ms each keep 100 threads busy.
  • Then cap it by what the pool calls: 200 threads sharing a 20-connection database pool means 180 of them wait.
