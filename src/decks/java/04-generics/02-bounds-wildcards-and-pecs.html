Producer extends, consumer super: wildcards make generic methods accept what they should

Generic types are invariant: a List<Integer> is not a List<Number>, because otherwise you could add a Double to a list of integers. Wildcards win the flexibility back safely. ? extends T means you can read Ts out; ? super T means you can put Ts in. Arrays chose covariance instead, and pay for it at run time.

Pecs.java · extends to read, super to write, and why arrays differ
import java.util.*;

public class Pecs {
    // Producer: we only read from it, so accept any list of a Number subtype.
    static double total(Collection<? extends Number> amounts) {
        double sum = 0;
        for (Number n : amounts) sum += n.doubleValue();
        return sum;
    }

    // Consumer: we only write Integers into it, so accept a list of any supertype.
    static void fillIds(List<? super Integer> sink, int count) {
        for (int i = 1; i <= count; i++) sink.add(i);
    }

    // The JDK's shape: read from src (extends), write to dest (super).
    static <T> void copyInto(List<? super T> dest, List<? extends T> src) {
        for (T item : src) dest.add(item);
    }

    // Comparable<? super T>: works when the comparison is inherited from a superclass.
    static <T extends Comparable<? super T>> T largest(List<? extends T> items) {
        T best = items.get(0);
        for (T item : items) if (item.compareTo(best) > 0) best = item;
        return best;
    }

    static class Amount implements Comparable<Amount> {
        final long cents;
        Amount(long cents) { this.cents = cents; }
        @Override public int compareTo(Amount o) { return Long.compare(cents, o.cents); }
        @Override public String toString() { return getClass().getSimpleName() + "(" + cents + ")"; }
    }
    static class Refund extends Amount {               // a Comparable<Amount>, not Comparable<Refund>
        Refund(long cents) { super(cents); }
    }

    public static void main(String[] args) {
        List<Integer> ints = List.of(1, 2, 3);
        List<Double> doubles = List.of(0.5, 1.5);
        System.out.println("total ints " + total(ints) + ", total doubles " + total(doubles));

        List<Number> numbers = new ArrayList<>();
        List<Object> objects = new ArrayList<>();
        fillIds(numbers, 3);
        fillIds(objects, 2);
        copyInto(objects, doubles);
        System.out.println("numbers " + numbers + ", objects " + objects);

        List<Refund> refunds = List.of(new Refund(500), new Refund(1200), new Refund(90));
        System.out.println("largest refund " + largest(refunds));

        // List<Number> wide = ints;                  // does not compile: generics are invariant
        Object[] slots = new String[2];               // arrays are covariant, so this compiles
        try {
            slots[0] = 42;                            // and fails at run time
        } catch (ArrayStoreException e) {
            System.out.println("ArrayStoreException: " + e.getMessage());
        }
    }
}

PECS in the JDK

Collections.copy(List<? super T> dest, List<? extends T> src). addAll(Collection<? extends E>). forEach(Consumer<? super T>). Stream.map(Function<? super T, ? extends R>). Parameters get wildcards; return types should not, or every caller inherits them.

Why Comparable<? super T>

Refund inherits compareTo from Amount, so it is a Comparable<Amount>, not a Comparable<Refund>. With <T extends Comparable<T>>, largest(refunds) would not compile. That is why Collections.max is declared with ? super T.

Covariant arraysObject[] slots = new String[2] compiles, so every store into an array of references is checked at run time, and the wrong one throws ArrayStoreException. Generics moved that check to compile time. It is also why generic arrays are not allowed.
