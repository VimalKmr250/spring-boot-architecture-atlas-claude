Core-Java coding questions test whether your code survives two threads, a null and a follow-up

The drills in this section are the ones Java interviews set over and over: an immutable class, a hash map from scratch, two threads in turn, parallel calls with timeouts, a concurrent counter, and a bug hunt. The code matters less than the way you get there. Interviewers score the questions you ask, the invariant you state, whether you test your own code, and how you answer "and now make it thread-safe".

The five steps, out loud

  1. Pin the contract. Inputs, nulls, sizes, ordering, and above all: is it used by one thread or many? Each answer changes the design.
  2. State the invariant. "Each key lives in exactly one bucket, chosen by its hash." "Exactly one thread prints at a time, odd first." Code is easier to check against a sentence.
  3. Write compilable Java. Real types, real imports, generics where they belong. A record or a final class with private final fields is a quick signal of care.
  4. Test it in front of them. A main with the normal case, an edge case and a failing input. For concurrency, repeat the run, and say why the code cannot race.
  5. Name the cost and the next step. Time and space, then the follow-up you would expect: resize, thread safety, back-pressure, timeouts.
