Seven equality bugs that compile cleanly, pass the tests, and return null in production

Each of these has appeared earlier in the tab as a mechanism. Here they are as a reviewer meets them: one line of code, the wrong answer it gives, and the fix. All seven come from the same two facts: == compares identity, and hash-based collections trust equals and hashCode to agree and to stay fixed.

EqualityBugs.java · each bug in a line or two
import java.math.BigDecimal;
import java.util.*;

public class EqualityBugs {
    static final class Order {
        final String id;
        Order(String id) { this.id = id; }
        public boolean equals(Order other) { return other != null && id.equals(other.id); }   // an overload!
        @Override public int hashCode() { return id.hashCode(); }
    }

    record Batch(int[] quantities) { }

    public static void main(String[] args) {
        Map<String, Integer> stock = Map.of("tea", 500, "milk", 500);
        System.out.println("1 same stock?             " + (stock.get("tea") == stock.get("milk"))
                + "  -> equals: " + stock.get("tea").equals(stock.get("milk")));

        String typed = new Scanner("ACTIVE").next();                          // as if read from input
        System.out.println("2 status == \"ACTIVE\"      " + (typed == "ACTIVE") + "  -> equals: " + "ACTIVE".equals(typed));

        Set<Order> orders = new HashSet<>(List.of(new Order("ORD-1")));
        System.out.println("3 contains(ORD-1)         " + orders.contains(new Order("ORD-1"))
                + "  (equals(Order) never overrides equals(Object))");

        Map<BigDecimal, String> priceBands = new HashMap<>(Map.of(new BigDecimal("10.00"), "standard"));
        System.out.println("4 band for 10.0           " + priceBands.get(new BigDecimal("10.0"))
                + "  -> TreeMap: " + new TreeMap<>(priceBands).get(new BigDecimal("10.0")));

        Map<Batch, String> labels = new HashMap<>(Map.of(new Batch(new int[] {1, 2}), "small"));
        System.out.println("5 label for equal batch   " + labels.get(new Batch(new int[] {1, 2})) + "  (arrays compare by identity)");

        List<Integer> ids = new ArrayList<>(List.of(5, Integer.MIN_VALUE, 3, Integer.MAX_VALUE, -7));
        ids.sort((a, b) -> a - b);                                            // subtraction overflows
        System.out.println("6 sorted with a - b       " + ids);
        ids.sort(Integer::compare);
        System.out.println("  sorted with compare     " + ids);

        Date start = new Date(0);
        Map<Date, String> shifts = new HashMap<>(Map.of(start, "night"));
        start.setTime(3_600_000);                                             // a mutable key, changed
        System.out.println("7 shift after the key changed: " + shifts.get(start) + ", map still holds " + shifts.size());
    }
}

The review questionFor every type used as a map key or set element, ask: is equals overridden, does hashCode use the same fields, and can any of those fields change? A record of immutable types answers all three. The rules themselves are on the Object contract.
