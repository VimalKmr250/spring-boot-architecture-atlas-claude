A thread is always in one of six states, and an interrupt is a request it must choose to honour

getState() reports one of six values. RUNNABLE covers running on a CPU, waiting for one, and blocking inside most native I/O. Interrupting a thread only sets a flag: blocking methods notice it, throw InterruptedException and clear it, and computing code must check it itself. Nothing can stop a thread from outside. Thread.stop() has thrown UnsupportedOperationException since JDK 20.

ThreadStates.java · each state on cue, then two ways to answer an interrupt
import java.util.concurrent.CountDownLatch;

public class ThreadStates {
    static void waitFor(Thread t, Thread.State s) throws InterruptedException {
        while (t.getState() != s) Thread.sleep(1);
    }

    public static void main(String[] args) throws Exception {
        Object lock = new Object();
        CountDownLatch release = new CountDownLatch(1);
        Thread worker = new Thread(() -> {
            System.out.println("inside run()        " + Thread.currentThread().getState());
            try {
                Thread.sleep(200);                           // TIMED_WAITING
                synchronized (lock) { }                      // BLOCKED while main holds the lock
                release.await();                             // WAITING
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "worker");

        System.out.println("after new           " + worker.getState());
        synchronized (lock) {
            worker.start();
            waitFor(worker, Thread.State.TIMED_WAITING);
            System.out.println("in sleep(200)       " + worker.getState());
            waitFor(worker, Thread.State.BLOCKED);
            System.out.println("at synchronized     " + worker.getState());
        }
        waitFor(worker, Thread.State.WAITING);
        System.out.println("in await()          " + worker.getState());
        release.countDown();
        worker.join();
        System.out.println("after run() returns " + worker.getState());

        Thread sleeper = new Thread(() -> {
            try {
                Thread.sleep(60_000);
            } catch (InterruptedException e) {
                System.out.println("sleeper woke with InterruptedException; flag is now "
                        + Thread.currentThread().isInterrupted());
                Thread.currentThread().interrupt();          // restore it for whoever runs next
                System.out.println("sleeper restored the flag: " + Thread.currentThread().isInterrupted());
            }
        });
        sleeper.start();
        waitFor(sleeper, Thread.State.TIMED_WAITING);
        sleeper.interrupt();
        sleeper.join();

        Thread spinner = new Thread(() -> {
            long spins = 0;
            while (!Thread.currentThread().isInterrupted()) spins++;   // CPU work must poll the flag
            System.out.println("spinner saw the flag and stopped: " + (spins > 0));
        });
        spinner.start();
        Thread.sleep(50);
        spinner.interrupt();
        spinner.join();

        Thread virtual = Thread.ofVirtual().name("vt-", 1).start(() -> { });
        virtual.join();
        Thread heartbeat = Thread.ofPlatform().name("heartbeat").daemon().unstarted(() -> { });
        System.out.println(virtual.getName() + " virtual=" + virtual.isVirtual() + " daemon=" + virtual.isDaemon()
                + "; " + heartbeat.getName() + " daemon=" + heartbeat.isDaemon());
    }
}

Never swallow an interruptA method that throws InterruptedException clears the flag first, as line 7 of the output shows. An empty catch means a shutdown request, or a Future.cancel(true), is lost, and the thread runs on. Either rethrow it or call Thread.currentThread().interrupt() before returning.
RUNNABLE does not mean busyA thread blocked in a socket read or a JDBC call shows as RUNNABLE in a thread dump, because the JVM cannot see inside native code. Two hundred RUNNABLE threads in SocketInputStream.read usually means a slow dependency, not a CPU problem.
Daemon threadsThe JVM exits when only daemon threads are left, without running their finally blocks. Virtual threads are always daemon threads. The builders 21 Thread.ofPlatform() and Thread.ofVirtual() set names, daemon status and handlers in one place.
