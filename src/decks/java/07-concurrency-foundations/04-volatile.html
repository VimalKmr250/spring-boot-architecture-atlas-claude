volatile gives visibility and ordering for one variable, never atomicity for a sequence of steps

Every read of a volatile field sees the most recent write to it, and everything written before that write. That makes it right for a stop flag, or for a reference to an immutable snapshot that one thread replaces and many read. It does nothing for count++, which is a read, an add and a write: two threads can both read 41 and both write 42.

VolatileDemo.java · lost updates, then two lazy singletons done right
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class VolatileDemo {
    static volatile int volatileCount;
    static int lockedCount;
    static final AtomicInteger atomicCount = new AtomicInteger();
    static final Object lock = new Object();

    // Double-checked locking: correct only because the field is volatile.
    static final class Config {
        private static volatile Config instance;
        final String region;
        private Config() { region = "eu-west"; }
        static Config get() {
            Config c = instance;                     // one volatile read on the fast path
            if (c == null) {
                synchronized (Config.class) {
                    c = instance;
                    if (c == null) instance = c = new Config();
                }
            }
            return c;
        }
    }

    // The holder idiom: lazy and thread-safe, with no volatile and no lock.
    static final class Rates {
        private Rates() { }
        private static final class Holder { static final Rates INSTANCE = new Rates(); }
        static Rates get() { return Holder.INSTANCE; }
    }

    public static void main(String[] args) throws Exception {
        int threads = 4, each = 1_000_000;
        try (ExecutorService pool = Executors.newFixedThreadPool(threads)) {
            for (int t = 0; t < threads; t++)
                pool.submit(() -> {
                    for (int i = 0; i < each; i++) {
                        volatileCount++;                  // read, add, write: three steps
                        atomicCount.incrementAndGet();    // one atomic step
                        synchronized (lock) { lockedCount++; }
                    }
                });
        }
        System.out.printf("expected      %,d%n", threads * each);
        System.out.printf("volatile ++   %,d%n", volatileCount);
        System.out.printf("AtomicInteger %,d%n", atomicCount.get());
        System.out.printf("synchronized  %,d%n", lockedCount);

        var configs = ConcurrentHashMap.<Config>newKeySet();
        var rates = ConcurrentHashMap.<Rates>newKeySet();
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1_000; i++) pool.submit(() -> { configs.add(Config.get()); rates.add(Rates.get()); });
        }
        System.out.println("1,000 concurrent callers saw " + configs.size() + " Config and " + rates.size() + " Rates instance");
    }
}

Why double-checked locking needs itinstance = new Config() is three steps: allocate, construct, assign. Without volatile, the assignment may become visible before the constructor's writes, so a thread on the fast path sees a non-null Config whose region is still null. The local c saves a second volatile read.
The holder idiom needs nothingThe JVM initialises Holder on first use, exactly once, under its own lock, and class initialisation creates a happens-before edge. Lazy, thread-safe and free after the first call. An enum is simpler still: singleton, the safe ways.
Good usesA volatile boolean running checked by a worker loop. A volatile reference to an immutable config, replaced whole on reload. Counters belong in AtomicLong or LongAdder, on atomics and CAS.
