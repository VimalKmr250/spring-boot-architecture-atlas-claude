Happens-before is the only ordering promise between threads, and it is created at specific points

If action A happens-before action B, then B sees A's effects and everything that happened before A. The JLS defines a small set of these edges, java.util.concurrent documents more, and the relation is transitive. Without an edge, any outcome the hardware can produce is legal, including one that no interleaving of the source lines could produce: both reads below returning 0.

Reordering.java · the store-buffering test, plain fields against volatile ones
import java.util.concurrent.atomic.AtomicInteger;

// The store-buffering test: each thread writes one variable, then reads the other.
// If every thread's actions happened in program order, at least one read would see a 1.
public class Reordering {
    static int x, y, r1, r2;                       // plain fields
    static volatile int vx, vy;                    // volatile fields
    static int vr1, vr2;
    static final AtomicInteger round = new AtomicInteger(), finished = new AtomicInteger();

    static Thread side(int trials, Runnable body) {
        return new Thread(() -> {
            for (int i = 1; i <= trials; i++) {
                while (round.get() != i) Thread.onSpinWait();   // start each trial together
                body.run();
                finished.incrementAndGet();
            }
        });
    }

    static int run(boolean useVolatile, int trials) throws InterruptedException {
        round.set(0);
        Thread a = useVolatile ? side(trials, () -> { vx = 1; vr1 = vy; }) : side(trials, () -> { x = 1; r1 = y; });
        Thread b = useVolatile ? side(trials, () -> { vy = 1; vr2 = vx; }) : side(trials, () -> { y = 1; r2 = x; });
        a.start();
        b.start();
        int bothZero = 0;
        for (int i = 1; i <= trials; i++) {
            x = y = vx = vy = 0;
            finished.set(0);
            round.set(i);                          // release both threads
            while (finished.get() != 2) Thread.onSpinWait();
            if (useVolatile ? vr1 == 0 && vr2 == 0 : r1 == 0 && r2 == 0) bothZero++;
        }
        a.join();
        b.join();
        return bothZero;
    }

    public static void main(String[] args) throws InterruptedException {
        int trials = 200_000;
        System.out.printf("plain fields:    both reads saw 0 in %,d of %,d trials%n", run(false, trials), trials);
        System.out.printf("volatile fields: both reads saw 0 in %,d of %,d trials%n", run(true, trials), trials);
    }
}

Reading the resultIf each thread's write came before its read, the second read to run would have to see a 1. Yet with plain fields both saw 0 in tens of thousands of trials: each write sat in a store buffer while the next read went ahead. With volatile, the JVM puts a fence after each write, and the impossible result never appeared in 200,000 trials. x86 reorders only a store with a later load; ARM servers such as Graviton reorder more, so racy code that works on a laptop can fail in production.

Piggybacking on transitivityWrite the data in plain fields, then write a volatile flag. A reader that sees the flag also sees the data: write data → write flag (program order) → read flag (volatile) → read data (program order). This is how BlockingQueue, Future and safe publication work, and it is why you rarely need volatile on every field.
