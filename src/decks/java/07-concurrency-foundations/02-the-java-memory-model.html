Without a happens-before edge, another thread may never see your write

The Java Memory Model (JLS chapter 17) defines when a write in one thread must be visible to a read in another. In between, the compiler, the JIT and the CPU may keep values in registers, reorder instructions and buffer stores, as long as no single thread can tell. Two threads can tell. The promise in return: a program with no data races behaves as if its actions ran in one sequential order.

Visibility.java · a flag that one thread sets and another never sees
public class Visibility {
    static boolean plainStop;                      // no happens-before between writer and reader
    static volatile boolean volatileStop;

    public static void main(String[] args) throws InterruptedException {
        Thread plain = new Thread(() -> {
            long spins = 0;
            while (!plainStop) spins++;            // the JIT may read plainStop once, outside the loop
            System.out.println("plain reader stopped after " + spins + " spins");
        });
        plain.setDaemon(true);                     // so the JVM can still exit
        plain.start();
        Thread.sleep(500);                         // long enough for the loop to be compiled
        plainStop = true;
        plain.join(2_000);
        System.out.println("plain flag: reader still running 2 s after the write? " + plain.isAlive());

        Thread reader = new Thread(() -> {
            long spins = 0;
            while (!volatileStop) spins++;         // a volatile read on every iteration
            System.out.println("volatile reader stopped" + (spins > 0 ? "" : " at once"));
        });
        reader.start();
        Thread.sleep(500);
        volatileStop = true;
        reader.join(2_000);
        System.out.println("volatile flag: reader still running? " + reader.isAlive());
    }
}

What goes wrongExample
VisibilityThe JIT compiled while (!plainStop) into a loop that reads the field once. Legal: nothing in the loop synchronises, so no other thread's write has to be seen.
ReorderingWrites and reads swap places, in the compiler or the CPU. The next slide catches it happening tens of thousands of times.
Atomicitycount++ is a read, an add and a write; a thread can lose the race between them. On 32-bit JVMs a non-volatile long or double can even tear into two halves (JLS 17.7).
Fixed by accident is not fixedPut a System.out.println in the plain loop and it usually stops, because PrintStream synchronises internally. Remove the logging and the bug returns. The definition to remember: a data race is two accesses to one variable, at least one a write, not ordered by happens-before.
