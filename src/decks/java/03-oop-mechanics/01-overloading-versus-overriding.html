The compiler picks an overload from static types; the JVM picks an override from the object

Overloading means several methods with one name and different parameters; javac chooses one at compile time from the declared types of the arguments. Overriding means a subclass replacing an inherited method; the JVM chooses at run time from the actual class of the receiver. Mixing the two up explains most "why did it call that one?" questions.

Overloads.java · overload resolution, overrides, hiding, covariant returns
public class Overloads {
    static String pay(Object o)  { return "pay(Object)"; }
    static String pay(Number n)  { return "pay(Number)"; }
    static String pay(Integer i) { return "pay(Integer)"; }
    static String pay(long l)    { return "pay(long)"; }
    static String pay(int... xs) { return "pay(int...)"; }

    static class Shape {
        String name = "shape";
        String area() { return "Shape.area"; }
        Shape copy() { return new Shape(); }
        static String kind() { return "Shape.kind"; }
    }
    static class Circle extends Shape {
        String name = "circle";                       // hides the field: no override
        @Override String area() { return "Circle.area"; }
        @Override Circle copy() { return new Circle(); }   // covariant return type
        static String kind() { return "Circle.kind"; }     // hides the static method
    }

    public static void main(String[] args) {
        int i = 5;
        short s = 5;
        Object boxed = 5;
        System.out.println("pay(int 5)     -> " + pay(i));        // widening beats boxing
        System.out.println("pay(short 5)   -> " + pay(s));
        System.out.println("pay(Integer 5) -> " + pay(Integer.valueOf(5)));
        System.out.println("pay(Object 5)  -> " + pay(boxed));    // the static type decides
        System.out.println("pay()          -> " + pay());

        Shape shape = new Circle();
        System.out.println("shape.area()   -> " + shape.area());  // runtime type decides
        System.out.println("shape.name     -> " + shape.name);    // fields: static type
        System.out.println("shape.copy()   -> " + shape.copy().getClass().getSimpleName());
        System.out.println("Shape.kind()   -> " + Shape.kind() + ", Circle.kind() -> " + Circle.kind());
    }
}

pay(Object 5)  -> pay(Object)

shape.name     -> shape
shape.copy()   -> Circle

How javac picks an overload

  1. Phase 1: methods applicable by subtyping or widening alone. No boxing, no varargs.
  2. Phase 2: only if phase 1 found nothing, allow boxing and unboxing.
  3. Phase 3: only then, allow varargs.

Within a phase the most specific method wins, and a tie is a compile error. That is why pay(5) calls pay(long): widening is phase 1 and boxing to Integer is phase 2. And pay(boxed) calls pay(Object) although the object is an Integer: overload choice never looks at the runtime class.

Always write @OverrideMistype the parameter, as in equals(Order other), and you have written an overload. It compiles, and HashSet keeps calling Object.equals(Object). With @Override the same mistake is a compile error. Equality and hashing bugs shows it failing.
