Strings never change, so the JVM can share them, pool the literals and cache the hash

Every method that seems to modify a String returns a new one. That one rule makes strings safe to share between threads, safe as map keys, and safe to pass to security checks. It also explains the two classic traps: == that works only for literals, and += in a loop that copies the whole string on every pass.

Strings.java · identity, the pool, compact strings, concatenation cost
import java.lang.management.ManagementFactory;

public class Strings {
    static final com.sun.management.ThreadMXBean MX =
            (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
    static long allocated() { return MX.getCurrentThreadAllocatedBytes(); }

    public static void main(String[] args) {
        String a = "order";
        String b = "order";
        String c = new String("order");
        String d = "ord" + "er";                 // folded by javac into "order"
        final String prefix = "ord";
        String e = prefix + "er";                // a constant too: prefix is final
        String part = "ord";
        String f = part + "er";                  // built at run time
        System.out.println("a == b            " + (a == b));
        System.out.println("a == new String   " + (a == c));
        System.out.println("a == \"ord\"+\"er\"   " + (a == d));
        System.out.println("a == final+\"er\"   " + (a == e));
        System.out.println("a == part+\"er\"    " + (a == f));
        System.out.println("a == f.intern()   " + (a == f.intern()));
        System.out.println("a.equals(c)       " + a.equals(c));

        String s = "total";
        s.concat("!");                           // returns a new string, discarded
        s.toUpperCase();
        System.out.println("still             " + s);

        System.out.println("\"Aa\".hashCode()   " + "Aa".hashCode() + ", \"BB\".hashCode() " + "BB".hashCode());

        long before = allocated();
        String latin = "a".repeat(1_000);
        long latinBytes = allocated() - before;
        before = allocated();
        String euro = "€".repeat(1_000);
        long euroBytes = allocated() - before;
        System.out.println("1000 x 'a' allocates " + latinBytes + " bytes, 1000 x '€' " + euroBytes
                + " (lengths " + latin.length() + ", " + euro.length() + ")");

        before = allocated();
        String joined = "";
        for (int i = 0; i < 5_000; i++) joined += i + ",";
        long plusBytes = allocated() - before;
        before = allocated();
        var builder = new StringBuilder();
        for (int i = 0; i < 5_000; i++) builder.append(i).append(',');
        String built = builder.toString();
        long builderBytes = allocated() - before;
        System.out.printf("+= in a loop: %,d bytes; StringBuilder: %,d bytes; same result: %b%n",
                plusBytes, builderBytes, joined.equals(built));
    }
}

a == bBoth literals resolve to the one pooled instance.
new StringAlways a new object, never the pooled one.
"ord" + "er", finalConstant expressions: javac folds them into the literal "order".
part + "er"Built at run time, so a new object. intern() returns the pooled copy.
1,040 vs 2,088 bytesCompact strings since 9: a Latin-1 string stores one byte per character, anything else two.
57.8 MB vs 98 KBEach += copies everything so far: O(n²) bytes for n appends.

== on stringsLiterals are pooled, so == passes tests that compare literals. A string from a request, a file or a database is a new object, and the same comparison fails. Use equals, or "ACTIVE".equals(status) when status may be null.
Where the pool livesIn the heap since Java 7, so pooled strings are collected like anything else. Calling intern() yourself is rarely worth it; G1's -XX:+UseStringDeduplication shares duplicate backing arrays without code changes.
