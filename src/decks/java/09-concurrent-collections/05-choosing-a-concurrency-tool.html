Name the problem first; the tool follows from it

Most concurrency questions, in interviews and in code review, reduce to a handful of needs. Each need has one tool that fits it and one tool people reach for instead, which is usually where the bug comes from. Read the right-hand column as the list of things to look for in a review.

Stop a worker loop from another threadvolatile boolean, or interrupt itA plain field, which the loop may never re-read
Count events from many threadsLongAdder; AtomicLong if read oftenvolatile long and ++

Wait for a lock, but not foreverReentrantLock.tryLock(timeout)synchronized, which cannot time out
Share a map between threadsConcurrentHashMap with merge and computeHashMap, or get then put
Load a cache entry once per keycomputeIfAbsentcontainsKey, then put

Hand work from producers to consumersA bounded BlockingQueueA list and wait / notify
Limit concurrent calls to a dependencySemaphore, or a sized connection poolA small thread pool used as a limiter

Handle many blocking I/O tasks at onceVirtual threads 21A platform pool of hundreds of threads
Split CPU-bound work across coresForkJoinPool, or a parallel streamMore threads than cores

The order to think inCan it be unshared? Can it be immutable? Is there a thread-safe class that already does this? Only then: which lock, and what exactly does it protect. Write that last answer in a comment beside the lock.
