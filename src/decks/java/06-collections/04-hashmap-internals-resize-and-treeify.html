The table doubles at 75% full, and a crowded bucket turns into a red-black tree

When the size passes capacity × 0.75, the table doubles and every node moves to either its old index or old index + old capacity, decided by one bit of the stored hash. When one bucket collects too many keys, Java 8 and later convert it from a linked list into a red-black tree, so even a flood of colliding keys costs O(log n) per lookup instead of O(n). The demo watches both happen.

HashMapResize.java · normal growth, then eleven keys with one hash code
// Run with: java --add-opens java.base/java.util=ALL-UNNAMED HashMapResize.java
import java.lang.reflect.Field;
import java.util.*;

public class HashMapResize {
    static Field table;

    static int length(HashMap<?, ?> map) throws IllegalAccessException {
        Object[] tab = (Object[]) table.get(map);
        return tab == null ? 0 : tab.length;
    }

    // Every key collides: the worst case that treeification exists for.
    record BadKey(int id) implements Comparable<BadKey> {
        @Override public int hashCode() { return 42; }
        @Override public int compareTo(BadKey o) { return Integer.compare(id, o.id); }
    }

    public static void main(String[] args) throws Exception {
        table = HashMap.class.getDeclaredField("table");
        table.setAccessible(true);

        var map = new HashMap<String, Integer>();
        System.out.println("new HashMap: table length " + length(map) + " (allocated on first put)");
        List<String> orderAt12 = null;
        for (int i = 1; i <= 25; i++) {
            int before = length(map);
            map.put("order-" + i, i);
            if (i == 12) orderAt12 = new ArrayList<>(map.keySet()).subList(0, 6);
            if (length(map) != before) System.out.println("put #" + i + ": table " + before + " -> " + length(map));
        }
        System.out.println("first keys at size 12: " + orderAt12);
        System.out.println("first keys at size 25: " + new ArrayList<>(map.keySet()).subList(0, 6));

        var bad = new HashMap<BadKey, Integer>();
        for (int i = 1; i <= 11; i++) {
            int before = length(bad);
            bad.put(new BadKey(i), i);
            Object[] tab = (Object[]) table.get(bad);
            Object bin = tab[42 & (tab.length - 1)];
            System.out.println("colliding key " + String.format("%2d", i) + ": table " + before + " -> " + tab.length
                    + ", bin is a " + bin.getClass().getSimpleName());
        }
        var sized = new HashMap<String, Integer>(1_000);
        sized.put("x", 1);
        System.out.println("new HashMap<>(1_000): table length " + length(sized)
                + "; HashMap.newHashMap(1_000): " + length(put(HashMap.newHashMap(1_000))));
    }

    static HashMap<String, Integer> put(HashMap<String, Integer> m) { m.put("x", 1); return m; }
}

The capacity argument is not a sizenew HashMap<>(1_000) makes 1,024 slots with a threshold of 768, so it still resizes at the 769th entry. HashMap.newHashMap(1_000) 19 sizes the table for 1,000 entries. Before 19, pass (int) (n / 0.75f) + 1.
Why trees, and their limitsTreeification arrived in Java 8 (JEP 180) to blunt hash-flooding attacks, where crafted keys all collide. Tree bins order nodes by hash, then by compareTo if the keys are Comparable. Colliding keys that are not comparable can still need a search of both subtrees. A TreeNode is about twice the size of a Node.
Resizes are cheap, but not freeEach resize allocates a new table and walks every node, but never calls hashCode again: the stored hash decides the new index. Under concurrent writes a plain HashMap resize can lose entries. Java 7's head insertion could even create a cycle that spun a CPU forever. Use ConcurrentHashMap.
