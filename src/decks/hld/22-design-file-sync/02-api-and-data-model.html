A file is a list of block hashes; a change is an append to a per-namespace journal

The client splits a file into blocks (about 4 MB) and hashes each one. It first asks which hashes the server lacks, uploads only those, then commits the new block list against the revision it started from. Every commit appends a row to an ordered journal for that namespace, a user's root or a shared folder. Other devices sync by reading the journal from their last cursor.

API
POST /v1/blocks/check  { "hashes": ["a1f3…", "9c0e…", "77ab…"] }
→ 200 { "missing": ["9c0e…"] }             # upload only what's new
PUT  /v1/blocks/9c0e…   <4 MB>            # content-addressed, idempotent

POST /v1/files/commit
{ "ns": "ns_42", "path": "/docs/plan.key", "parentRev": 17,
  "blocks": ["a1f3…", "9c0e…", "77ab…"], "size": 11534336 }
→ 200 { "rev": 18 }
→ 409 { "latestRev": 18 }                 # someone committed first

GET  /v1/changes?ns=ns_42&cursor=c_9912   → entries since cursor
GET  /v1/notify?cursors=…                 # long-poll: "something changed"

Content addressing

A block's name is its hash, so uploads are idempotent (the same bytes give the same name), deduplication is automatic, and every read can be verified end to end. A version is just a new block list. Unchanged blocks are shared with the previous version at no cost.

Blocks before commit

Upload blocks first, then commit metadata. A commit that references a missing block is rejected. The journal therefore never points at bytes that don't exist, even when a client crashes halfway through an upload.

Shard by namespace

All journal rows for a namespace live on one shard, so a commit is a single-shard transaction and the sequence numbers are gap-free. Very large shared team folders are the hot keys to watch, and may need a dedicated shard.
