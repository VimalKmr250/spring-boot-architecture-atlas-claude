Shape the data for the read before the read arrives

Three data-management patterns that sharding and caching don't cover. Materialized views precompute expensive query results. Index tables add secondary lookups to stores that only index a primary key. Static content hosting takes whole categories of requests off your compute entirely.

Materialized view

Use it for dashboards, leaderboards and "top N" lists, anywhere the same heavy aggregation is read far more often than its inputs change. Maintain it by scheduled refresh, incrementally from change events, or natively (REFRESH MATERIALIZED VIEW CONCURRENTLY).

Index table

The do-it-yourself secondary index for KV and sharded stores (DynamoDB GSIs are the managed version). It's a second write per change, and it's consistent only if both writes are in one transaction or the index is rebuilt from a change stream.

Static content hosting

Use it for single-page apps, docs sites, images and downloads. Version the file names so CDN caching is safe. Pair it with a valet key (presigned URLs) for private files, and never proxy big downloads through app servers.
