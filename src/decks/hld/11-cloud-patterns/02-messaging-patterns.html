Four messaging patterns that turn up in almost every async design

Beyond "put it on a queue", four named patterns cover most async needs. They scale consumers, prioritise urgent work, compose processing steps, and keep large payloads off the broker. A fifth, the sequential convoy, keeps order within a group while still processing in parallel across groups.

Sequential convoy

Some messages must be processed in order, but only relative to their group: all of order 17's events, but not order 17 against order 42. Route by group key to a partition or session (Kafka keys, SQS FIFO message groups, Service Bus sessions). Each group is then sequential, and different groups run in parallel.

Trade-offs to mention

Competing consumers break global ordering, so combine them with a convoy if order matters. Priority queues need separate worker pools, or urgent work still waits behind bulk work. Pipes and filters add a hop per step: great for throughput, not for low latency. With a claim check, delete the blob when the message is done (use lifecycle rules).
