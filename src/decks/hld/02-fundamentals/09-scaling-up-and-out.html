Scale the database up, scale the stateless tier out

Vertical scaling buys a bigger machine. It needs no code change, but it has a ceiling, a single point of failure, and a price that grows faster than the capacity. Horizontal scaling adds more machines, which only works once the machines are interchangeable. So the real work of scaling out is moving state out of the application servers.

Where state hides

In-memory sessions, local file uploads, in-process caches that must be coherent, scheduled jobs that run "on the server", WebSocket connections. Each one needs a home outside the box, or the box can't be replaced freely.

Sticky sessions are a smell

Pinning a user to one server works until that server dies or the load becomes uneven. Prefer a shared session store, or signed tokens (JWT) that carry the state. Keep stickiness for connection-oriented protocols such as WebSockets, where it is inherent.

Autoscaling needs headroom

New instances take 1–5 minutes to boot and warm up. Scale on a leading signal (request rate, queue depth) with a target around 60% utilisation. For known events, pre-scale rather than waiting for the autoscaler to react.
