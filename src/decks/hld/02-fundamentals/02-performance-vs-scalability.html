Slow for one user is a performance problem; slow for many is a scalability problem

A service is scalable if adding resources adds capacity in roughly the same proportion. The two problems need different fixes, so diagnose which one you have before reaching for more servers. More servers won't fix a slow query, and faster code won't fix a single shared lock.

Diagnose performance

Measure one request: trace it, profile it, look at EXPLAIN. The fixes are an index, a batched call, less serialisation, a cache in front of an expensive computation, or a better algorithm.

Diagnose scalability

Load-test at rising load and watch where latency turns upward. Find the resource that saturates first: CPU, connection pool, a DB row lock, one hot partition, or a single-threaded consumer.

Why scaling is never perfectly linear

The Universal Scalability Law names the two taxes. Contention is waiting for shared resources. Coherency is the work of keeping nodes in agreement. The second grows with the square of the node count, which is why "just add nodes" eventually stops helping.

Interviewers probe"What happens at 10× load?" Name the first thing that saturates and what you'd do about it: "The primary database's write throughput. I'd first check whether writes can be batched or queued, then shard by user id." A vague "add more servers" is not an answer.
