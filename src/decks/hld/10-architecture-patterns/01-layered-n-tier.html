Layers separate concerns in the code; tiers separate them onto machines

The oldest and still the most common style. A layer is a logical grouping in the codebase: presentation, business logic, data access. Each layer depends only on the one below it. A tier is a physical deployment boundary: browser, application servers, database. Nearly every system in this deck is a 3-tier system at heart, whatever else it adds.

Why it lasts

It's easy to understand, easy to staff and easy to test layer by layer, and each tier scales independently: stateless app servers out, the database up. Most CRUD-heavy business applications never need anything more.

Where it hurts

Layers slice by technical concern, so a single feature touches every layer. In a large codebase every team edits the same layers, which becomes a "big ball of mud" without module boundaries inside each layer. The database becomes the integration point.

The modern refinement

Keep the tiers, but slice the code by business capability first (modules) and by layer within each module. Put the domain at the centre with ports and adapters, so the database and frameworks are details. That becomes the modular monolith on the next slide.
