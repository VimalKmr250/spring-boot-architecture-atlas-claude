CQRS: one model for changing data, others shaped for reading it

Command Query Responsibility Segregation splits the write side (commands that enforce rules on a normalised model) from the read side (queries served by denormalised views built for each screen or API). The views are updated from change events, so each side scales and evolves on its own, at the cost of reads that lag writes slightly.

Use it when

Reads and writes are very different in shape or volume (a 100:1 ratio, complex screens over simple writes). You need several views of the same data (search, reporting, per-customer history). Or the read side must scale independently, possibly in another store.

Don't use it for

Simple CRUD, where a single model and a couple of indexes are enough. CQRS doubles the moving parts, and the replication lag forces UX changes ("your order will appear shortly") or read-your-writes workarounds.

Make projections rebuildable

A projection is derived data. Version it, make its handlers idempotent, and be able to drop it and replay the event stream or CDC log to rebuild it. That is also how you add a new read model next quarter.
