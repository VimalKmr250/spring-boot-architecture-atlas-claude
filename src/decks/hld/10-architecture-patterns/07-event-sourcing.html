Store what happened, and derive the current state from it

Instead of overwriting a row with the latest state, event sourcing appends every change as an immutable event to a stream per entity. Current state is a fold over the stream. You get a perfect audit log, the ability to answer "what was true on March 1st", and the freedom to build new read models from history. The price is real complexity.

Where it earns its keep

Domains where history is the product or the regulation: ledgers and accounting, banking, trading, insurance claims, audit-heavy workflows. Also when you'll need read models nobody has thought of yet.

What gets hard

Event schemas are forever, so you need upcasters or versioned events. Queries across entities need projections. The right to erasure needs crypto-shredding. Long streams need snapshots. And the team has to think in events.

Not the same as event-driven

Event-driven means publishing events between services. Event sourcing means using events as a service's own storage. You can have either without the other, and most event-driven systems store state in ordinary tables.
