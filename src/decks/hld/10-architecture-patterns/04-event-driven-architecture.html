Components react to facts instead of calling each other

In an event-driven architecture, a component announces that something happened ("OrderPlaced") and doesn't know or care who listens. Other components react on their own schedule. It comes in two topologies: a broker topology, where processors chain off each other's events, and a mediator topology, where a central coordinator decides the steps.

Three kinds of event

Event notification: "order 17 placed". Thin, so consumers call back for details. Event-carried state transfer: the event carries the data consumers need, so they keep their own copy and never call back. Event sourcing: events are the database (see two slides on).

Where it shines

Many consumers of the same fact. Fan-out to analytics, search and notifications. Integrating systems owned by different teams. Absorbing bursts. Building new features off an existing stream without touching its producer.

What it costs

Eventual consistency everywhere, and flows that are hard to see without tracing. Duplicates and reordering. Schema evolution across teams, which needs a schema registry and compatibility rules. And the temptation to model a synchronous question as two events.
