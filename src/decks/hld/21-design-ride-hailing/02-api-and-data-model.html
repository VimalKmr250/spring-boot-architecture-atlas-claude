Locations stream in over a persistent connection; trips are guarded rows

Drivers push a location every few seconds, so use a long-lived connection (WebSocket or MQTT) rather than a new HTTPS request each time. Riders create a trip with one idempotent POST and then receive updates by push. The data splits along the ephemeral/durable line: locations are latest-value-wins data with a TTL, and trips are transactional rows with a status and a version.

API
# driver app: one persistent connection, a message every ~4 s
WS  /v1/driver/stream   → { "lat": 37.7749, "lng": -122.4194,
                            "heading": 90, "seq": 1841, "ts": … }
                        ← { "type": "offer", "offerId": "of_3", "ttl": 10 }

POST /v1/rides   Idempotency-Key: 5d1e…
{ "pickup": {…}, "dropoff": {…}, "product": "standard" }
→ 202 { "rideId": "r_77", "status": "MATCHING" }

POST /v1/offers/of_3/accept         # driver, within 10 s
GET  /v1/rides/r_77  → status, driver, car, ETA   (+ push updates)

Sequence numbers, not trust

Mobile networks deliver updates late and out of order. Each update carries a per-driver seq, and the server drops anything older than the last one applied. Clients buffer points while offline and send them in a batch for the route history, but only the newest point updates the live index.

Update less often, when you can

Four seconds is for moving drivers. A parked, available driver can report every 15–30 s, and the app can skip updates that moved less than about 20 m. That cuts the write rate a lot during quiet periods at no cost in matching quality.

Offers expire

An offer is a short-lived record (Redis, TTL 10 s) linking a trip and a driver. The driver's accept is valid only while it exists and only if the trip is still MATCHING, which the database checks, not the app.
