How the balancer picks a server decides whether load actually evens out

If requests cost roughly the same and the servers are identical, the simplest algorithm is fine. Once request costs vary (one search takes 5 ms, another 2 s) or servers differ, you want an algorithm that looks at current load. If a server holds state for a key, such as a cache shard or a WebSocket, you want one that sends that key to the same place every time.

AlgorithmUse whenWeakness
Round robinIdentical servers, uniform short requestsBlind to slow requests and slow servers
Least connections / least requestVariable request cost, long-lived connectionsNeeds per-server state; a fresh server gets flooded (use slow-start)
Weighted (RR or LC)Mixed instance sizes; shifting 5% of traffic to a canaryWeights must be maintained by hand or automation
IP / key hash, consistent hashCache shards, session affinity, stateful connectionsHot keys overload one server; client IPs behind NAT cluster together
Power of two choicesLarge fleets, many independent balancersSlightly worse than a perfect global view, which doesn't exist anyway
