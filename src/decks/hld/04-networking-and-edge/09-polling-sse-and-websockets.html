Four ways for the server to tell the client something changed

HTTP is request-response: the server can only speak when it's asked. Real-time features (chat, live scores, notifications, collaborative editing) need a way round that. The four options trade simplicity against latency and the number of connections you must keep open.

Use forRare updates, simplest clientsFallback; legacy clientsNotifications, feeds, dashboards, token streamingChat, multiplayer, collaborative editing, trading
The scaling consequencePersistent connections make the connection tier stateful. A million online users is a million open sockets spread over, say, 20 gateway servers. The system needs a registry of which user is on which gateway, so a message can be routed to the right box. The chat design (§14) builds exactly that.
