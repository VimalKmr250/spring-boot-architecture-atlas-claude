Three calls, and a hidden context that makes conflicts detectable

The API is deliberately tiny. The subtle part is the context: a version (a vector clock) returned by get and passed back on put, so the store knows which version a write was based on. Placement is pure computation. Hash the key to a token, and the next N distinct nodes clockwise on the ring are its replicas. No lookup service is needed.

API
get(key, consistency=QUORUM)
    -> [(value, context), ...]      # >1 entry = concurrent siblings
put(key, value, context=None, consistency=QUORUM, ttl=None)
    -> context'                     # context from a prior get
delete(key, context)                # writes a tombstone, not a hole

# per request: ONE | QUORUM | ALL   (N fixed per keyspace, e.g. 3)
placement
token = murmur3(key)                # 64-bit position on the ring
replicas = walk_clockwise(token, n=3, distinct_racks=True)

Virtual nodes

Each physical node owns many small token ranges (vnodes, e.g. 16–256) scattered around the ring rather than one big arc. Load evens out, a joining node takes small slices from everyone, and a failed node's load spreads across the cluster instead of landing on one neighbour.

Rack- and zone-aware replicas

Walking clockwise, skip nodes in a rack or zone that already holds a replica. Three replicas in three availability zones means a whole zone can go down and every key still has two live copies, enough for QUORUM.

Deletes are writes

A delete writes a tombstone that replicates like any value. If replicas simply dropped the key, a replica that missed the delete would "resurrect" it during repair. Tombstones are purged after a grace period (for example 10 days) longer than any repair cycle.
