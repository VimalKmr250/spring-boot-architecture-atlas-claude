Deep dive 1: overlapping quorums, writes that survive a down replica, and versions that expose conflicts

Three mechanisms define how the store behaves under failure. Quorum overlap (W + R > N) makes a read see the latest acknowledged write. A sloppy quorum with hinted handoff keeps writes available when a replica is down. Vector clocks tell "newer" apart from "concurrent", so the store never silently throws away one side of a conflict.

Quorums aren't linearizability

Even with W + R > N, edge cases remain: sloppy quorums, a write that failed after reaching one replica, and clock-based LWW. Don't promise strong consistency from quorums alone. If you truly need it for a key (a lock or a counter), use consensus (Raft or Paxos) or a lightweight transaction.

Read repair

When the replicas queried for a read disagree, the coordinator returns the newest version and writes it back to the stale replicas, synchronously or asynchronously. Frequently read keys stay consistent without any background job. Rarely read keys need anti-entropy.

LWW or siblings?

Cassandra chose last-writer-wins with timestamps: simple, but concurrent writes lose data and clock skew decides the winner. Dynamo and Riak chose vector clocks and siblings: nothing is lost, but clients must merge. CRDTs (counters, sets) merge automatically where the data type allows it.
