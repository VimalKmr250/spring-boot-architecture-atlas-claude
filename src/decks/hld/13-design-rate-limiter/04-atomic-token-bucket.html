Deep dive 1: the check must be one atomic operation

"Read the counter, decide, write it back" from 50 gateways is a textbook race. Two gateways read "1 token left", both allow, and the limit leaks under exactly the concurrent load it exists for. Make the whole refill-check-take step atomic on the shard that owns the key. In Redis that means a Lua script.

token_bucket.lua (runs inside Redis)
-- KEYS[1] = bucket key   ARGV = rate/s, burst, now_ms, cost
local rate, burst, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]),
                               tonumber(ARGV[3]), tonumber(ARGV[4])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or burst
local ts     = tonumber(b[2]) or now
tokens = math.min(burst, tokens + (now - ts) / 1000 * rate)   -- refill
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(burst / rate * 1000) * 2)
local wait = allowed and 0 or math.ceil((cost - tokens) / rate * 1000)
return { allowed and 1 or 0, math.floor(tokens), wait }

Details that come up

  • Whose clock? Pass now from the gateway (NTP-synced), or read Redis TIME inside the script so every caller shares one clock.
  • Cost: weight expensive endpoints (cost = 10 for an export), so a limit reflects load, not just request count.
  • One round trip: load the script once (EVALSHA). Check several rules in one call when their keys share a hash tag, so they land on the same shard.
  • The TTL lets idle keys vanish, so memory tracks active clients, not every client ever seen.
