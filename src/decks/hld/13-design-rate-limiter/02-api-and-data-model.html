Rules are configuration, counters are tiny keys with a TTL

A rate limiter has two kinds of data with opposite profiles. Rules are small, rarely change, and are read on every request, so they're cached in every gateway. Counters are one small record per (rule, client), updated on every request, and expired when idle.

rules (config store, pushed to gateways)
- id: free-tier-default
  match: { tier: free }
  key: api_key
  algorithm: token_bucket
  rate: 10/s
  burst: 20
- id: pro-search
  match: { tier: pro, route: "GET /v1/search" }
  key: api_key
  algorithm: token_bucket
  rate: 100/s
  burst: 200
- id: login-per-ip
  match: { route: "POST /v1/login" }
  key: client_ip
  algorithm: sliding_window
  limit: 10/min
response on rejection
HTTP/1.1 429 Too Many Requests
Retry-After: 2
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 2

Rule evaluation is local

Matching a request to its rules must not need a network call. Gateways hold the full rule set in memory, subscribe to changes, and stamp every decision with the rule version it used. That makes audits and debugging possible.

Multiple rules per request

A request can hit several rules at once: per key, per org, per endpoint, and global. Check them all in one round trip (a single Lua call over several keys, or a pipeline). Reject if any rule rejects, and report the tightest one in the headers.

Shadow mode

New or tightened rules first run in "log only" mode: count what would have been rejected, without rejecting. Promote a rule to enforcement once you've seen whom it would hit. This single feature prevents most rate-limit incidents.
