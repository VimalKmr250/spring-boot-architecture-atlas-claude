Design a distributed rate limiter for a public API

Every request to the API must be checked against its caller's allowance, across dozens of gateway instances, adding almost no latency. The limiter must not become the outage it was meant to prevent. The core difficulties are shared, contended counters across machines, and deciding what happens when the counter store itself is unavailable.

Functional

  • Limit by API key, user, IP and endpoint, e.g. "100 req/s, bursts to 200" and "10k/day".
  • Return 429 with Retry-After and remaining-quota headers.
  • Change rules without a deploy, and per customer tier.

Non-functional

  • Adds < 2 ms p99. Must not reduce API availability.
  • Accurate to within a few percent. Briefly exceeding a limit by 5% is fine.
  • Scales linearly with gateways and keys.

Ask about the purpose

  • Protective (keep us up) → fail open if the limiter breaks.
  • Contractual (billing tiers) → accuracy matters, and you may fail closed.
  • This one decision drives the failure design (deep dive 2).
