Producers send intents; the platform decides channel, content and timing

A producer says "tell user 42 their order shipped" with a template and parameters. It doesn't choose between push and email, and it doesn't render text. That keeps preferences, localisation, caps and provider details in one place, and lets you change them without touching fifty services.

API
POST /v1/notifications
Idempotency-Key: order-881-shipped            # same key → same notification
{ "recipients": { "user_ids": ["u-42"] },     # or { "segment": "lapsed-30d" }
  "template": "order_shipped", "category": "transactional",
  "priority": "normal",                       # critical | normal | bulk
  "params": { "order_id": "881", "eta": "Thu" },
  "send_at": null }                           # or a timestamp
→ 202 { "notification_id": "n-5f2…" }

GET  /v1/notifications/n-5f2…     → per-channel status timeline
POST /v1/devices    { "token": "…", "platform": "ios" }
PUT  /v1/users/u-42/preferences   { "marketing": { "push": false } }

202, not 200

Sending is asynchronous. The API validates the request, checks idempotency, persists it (or enqueues it durably) and returns a notification id immediately. Producers must never block on an SMS provider's latency.

Segments are expanded later

"Send to segment lapsed-30d" (8 M users) is stored as one job. A campaign worker expands it in pages, at a controlled rate, instead of the API call enqueueing 8 M messages synchronously.

Two different stores

Preferences, devices and templates are small, read constantly and change rarely, so keep them in a relational DB behind a cache. The log is write-heavy, time-ordered and huge, so use a wide-column store with a TTL, and aggregate to analytics for open and click rates.
