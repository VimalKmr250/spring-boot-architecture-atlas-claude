Full-text search inverts the data: from each word to the documents that contain it

LIKE '%shoe%' scans every row and knows nothing about relevance. A search engine (Elasticsearch/OpenSearch, Solr, or Lucene underneath) builds an inverted index at write time, so a query becomes a few list lookups and a merge. Search is a derived view, fed from your system of record.

Not a source of truth

Write to the database first and index asynchronously, from CDC or events. Search clusters can lose data or need reindexing after a mapping change, so rebuilding from the source must be a routine job, not a crisis.

Scaling a search cluster

Shard by document, so each query fans out to all shards and merges the top-k. Add replicas for query throughput. Keep shards around 10–50 GB. Time-based indexes (logs-2026.09.30) make retention a matter of dropping old indexes.

Where it shows up

Product and content search, typo tolerance and synonyms, faceted filtering ("brand: X, price < 50"), log analytics, geo queries, and autocomplete. For simple prefix autocomplete, a dedicated trie service can be cheaper (§17).
