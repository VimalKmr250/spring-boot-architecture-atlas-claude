Split the database by function, and copy data where reads need it

Two cheaper moves often come before sharding. Federation (functional partitioning) splits one database into several by domain, so users, products and orders each get their own, with separate load and separate failures. Denormalization stores data redundantly in the shape the read needs, trading write complexity for join-free reads.

Federation is service ownership

In microservices, federation is the norm: each service owns its data and nobody else touches its tables (database per service, §10). The same split works inside a modular monolith, as schema per module. Cross-domain questions are then answered through APIs or read models, never joins.

Some copies are features

Copying the product title and price into the order line isn't really denormalization. It records what the customer actually bought, even if the catalogue changes tomorrow. Separate snapshots, which must never update, from caches of truth, which must.

Materialized views

A denormalized read model maintained automatically, either by the database (a materialized view) or by a consumer of change events (a projection). This is the read side of CQRS (§10). Accept that it lags the source by milliseconds to seconds.
