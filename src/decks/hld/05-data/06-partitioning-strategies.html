Sharding splits the data so each node holds, and writes, only a part

Partitioning (sharding) is how you scale writes and storage past one machine. Each record lives on exactly one shard, chosen by its partition key. The strategy decides three things: whether load spreads evenly, whether range queries stay on one shard, and how hard it is to add shards later.

Choosing the partition key

Choose a key with high cardinality (many distinct values), even load (no key far hotter than the rest), and that matches the main query, so the common request touches one shard. user_id for user data, conversation_id for messages, tenant_id for SaaS. Never a boolean, a country, or a raw timestamp.

Secondary indexes

Local index: each shard indexes its own rows. Writes stay cheap, but a query by the indexed field must ask every shard. Global index: the index is itself partitioned by the indexed value. Reads go to one place, but each write updates another shard, usually asynchronously.

What you give up

Cross-shard joins, transactions and unique constraints. Design so the common operation stays inside one shard. For the rare cross-shard operation, use a saga or an async job, and denormalise the data a query needs onto the shard that serves it.
