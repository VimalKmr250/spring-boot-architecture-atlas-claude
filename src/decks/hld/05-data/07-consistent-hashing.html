Consistent hashing: adding a node moves only its share of keys

With hash(key) % N, going from 3 to 4 nodes changes the answer for about 75% of keys. For a cache that means a sudden wave of misses; for a database it means a massive data migration. Consistent hashing places nodes and keys on the same ring and gives each key to the next node clockwise, so a new node only takes keys from its immediate neighbour.

Virtual nodes fix the lumps

Three random points on a ring give very uneven arcs. Each physical node therefore takes 100–256 virtual nodes spread around the ring, which evens out the load. A new node takes a little from everyone rather than a lot from one neighbour, and a bigger machine can simply own more vnodes.

Replication falls out of it

To keep N copies, store the key on the next N distinct physical nodes clockwise. That list is the key's preference list. It is how Cassandra and DynamoDB place replicas without a central directory.

Alternatives worth naming

Rendezvous (HRW) hashing: each key goes to the node with the highest hash(key, node). It's simple and needs no ring. Jump hash: fast, but nodes must be numbered. Fixed hash slots (Redis Cluster uses 16,384) make rebalancing a matter of moving whole slots.
