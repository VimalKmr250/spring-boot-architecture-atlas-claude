Transactions are only as safe as their isolation level

ACID means Atomic (all or nothing), Consistent (invariants hold), Isolated (concurrent transactions don't interfere) and Durable (committed means kept). The "I" is a spectrum, and most databases default to a weak level for speed. The two anomalies below cause real incidents in money and booking systems.

The fixes, from cheapest

  • Atomic update: SET balance = balance - 30 WHERE id = 1 AND balance >= 30. There is no read-modify-write left to race.
  • Optimistic lock: a version column, … WHERE version = 7. Zero rows updated means someone else won, so retry.
  • Pessimistic lock: SELECT … FOR UPDATE on the rows you check. Correct, but it serialises contention.
  • Serializable isolation with automatic retry on a serialization failure. Simplest to reason about, with some throughput cost.

* PostgreSQL's repeatable read aborts one of two conflicting updates. MySQL InnoDB's does not, and a plain read-then-write there still loses an update.
