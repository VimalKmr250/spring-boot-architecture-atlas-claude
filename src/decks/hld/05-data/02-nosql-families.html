Four data shapes, each optimised for a different question

"NoSQL" covers very different systems. What they share is that you design the data around the queries you will run, often duplicating it, rather than normalising it and letting the query planner work it out. Picture the shape of the data first, then pick the family whose shape matches.

Design rule for wide-column and KV storesOne table per query. Write the list of queries first, and give each one a table whose partition key is what the query filters on and whose clustering key is what it sorts by. Duplicate the data across tables at write time. Storage is cheap; a scatter-gather query across every node is not.
