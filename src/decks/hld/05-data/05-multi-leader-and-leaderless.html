More than one node accepts writes, so conflicts become your problem

A single leader is a bottleneck and a single point of failure for writes. Multi-leader puts a leader in each region, so writes stay local. Leaderless (Dynamo-style) lets any replica accept a write and uses quorums. Both buy write availability and latency, and both need a rule for what happens when two writes to the same key collide.

Setting (N = 3)Behaviour
W=2, R=2Balanced; tolerates 1 node down for reads and writes
W=3, R=1Fast reads, but any node down blocks writes
W=1, R=3Fast, available writes; slow reads
W=1, R=1Fastest; eventual consistency only (W + R ≤ N)
Quorums are not magicEven with W + R > N you can see anomalies. Sloppy quorums during failures, concurrent writes resolved by clocks, and a write that failed on some replicas but succeeded on others can all break the overlap guarantee. For real linearizability (unique usernames, balances), use consensus-backed single-leader writes. Cassandra's lightweight transactions and DynamoDB's conditional writes exist for exactly this.
