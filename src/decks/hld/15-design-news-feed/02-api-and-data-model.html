Posts are the truth; a feed is just a list of post ids

Keep post content in one place, and keep feeds as lightweight lists of ids per user, fetched and then hydrated in a batch. A feed entry never copies the post body. That's what makes edits and deletes tractable, and it keeps the feed cache small enough to hold for every active user.

API
POST /v1/posts                      { "text": "…", "media_ids": ["m-1"] }
→ 201 { "post_id": "18446…", "created_at": … }

GET  /v1/feed?cursor=eyJzIjo…&limit=20
→ 200 { "items": [ { "post": {…}, "author": {…},
                     "likes": 1204, "liked_by_me": false } ],
        "next_cursor": "eyJzIjo…" }      # opaque: (score, post_id)

PUT    /v1/users/{id}/follow
DELETE /v1/users/{id}/follow
POST   /v1/posts/{id}/like              # idempotent per user

Why the graph is stored twice

Fan-out asks "who follows X?" and the profile page asks "whom does Y follow?". Each question needs its own partition key. Write both rows on follow (async repair keeps them in sync), or use a graph service such as Facebook's TAO.

Cursor, not offset

Feeds change while you scroll. Offsets skip and duplicate items. An opaque cursor, (score, post_id) of the last item, resumes exactly, and lets the server change the ranking without breaking pages already loaded.

Counters live apart

A viral post takes 100k likes a minute. Incrementing a column on the post row makes it a hot row. Use sharded counters (N sub-keys summed on read), plus a per-user "liked" set so the like button is idempotent.
