Design a web crawler: a billion pages a month, without hammering anyone's server

Start from seed URLs, then fetch pages, extract links and repeat, feeding a search index or an archive. Raw throughput is the easy part. The hard parts are politeness (never overload a host), deduplication (most links point to pages you've already seen) and robustness against a web that is malformed, slow and sometimes adversarial.

Functional

  • From seed URLs, fetch pages, extract links, and crawl the new ones.
  • Store raw content for downstream consumers (indexer, archive).
  • Recrawl pages so changes show up; faster for pages that change often.

Non-functional

  • Polite: obey robots.txt; at most one connection and about one request per few seconds per host.
  • Robust: survive bad HTML, slow servers, redirect loops and crawler traps.
  • Scalable and extensible: add nodes and new content types (PDF, images) without a redesign.

Clarify

  • Purpose: search index, archive or data set? It sets priority and freshness.
  • HTML only, or render JavaScript too? Rendering costs 10–100× more per page.
  • Whole web or a list of domains? Keep old versions or only the latest?
