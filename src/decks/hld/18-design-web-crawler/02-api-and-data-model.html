No public API: the contracts are internal, and the URL table is the crawler's memory

A crawler is a pipeline, so its "API" is a set of stage contracts: enqueue, next, fetch, store, emit. The data model is small but huge in volume. It holds per-URL state (when you last fetched it, whether it changed, when to come back), per-host state (robots.txt, crawl delay, errors), the raw pages, and the link graph that drives priority.

stage contracts
frontier.add(url, priority, found_on)    # only after the seen-check
frontier.next(worker) -> url             # blocks until a host is ready
fetch(url, etag, last_modified)
    -> 200 body | 304 unchanged | 3xx | 4xx | 5xx | timeout
store.append(warc_record) -> (warc_file, offset)
emit("pages.fetched", {url_hash, warc_file, offset, sha256})
robots.txt (fetched per host, cached ~24 h)
User-agent: *
Disallow: /cart/
Disallow: /search?
Crawl-delay: 5
Sitemap: https://ex.com/sitemap.xml

Normalise before you hash

Lowercase the scheme and host, drop default ports and #fragments, resolve ../, sort query parameters and strip tracking ones (utm_*, session ids). Without this, one page has dozens of "different" URLs and you crawl it dozens of times.

Two different "seen" questions

URL seen? is checked before fetching and saves bandwidth. Content seen? is checked after fetching, because mirrors and syndicated copies have different URLs but the same body. It saves parsing, storage and index pollution.

Store pages as WARC

Append many fetched responses (headers and body) into large WARC files, around 1 GB each, in object storage. Small objects per page would mean billions of tiny writes. The URL table keeps a pointer (file and offset) to each record.
