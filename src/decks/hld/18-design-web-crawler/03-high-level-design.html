A loop: frontier, fetch, parse, dedupe, filter, and back to the frontier

Every crawler is the same cycle. Take the next URL the frontier allows, fetch it, parse out text and links, drop duplicate content, filter and normalise the links, keep only URLs never seen before, and feed those back in. Everything else, such as indexing, archiving and analytics, hangs off a stream of fetched pages.

Fetchers are I/O-bound

Most time is spent waiting on remote servers, so use asynchronous I/O with thousands of concurrent connections per node rather than a thread per request. Set strict limits: 10 s timeouts, a 10 MB maximum body, at most 5 redirects, and accepted content types only.

DNS becomes a bottleneck

Resolving each host through a public resolver adds 10–100 ms and can get you rate-limited. Run a local caching resolver per node and cache host → IP in host_state, respecting TTLs. Politeness is often enforced per IP too, since one server can host thousands of domains.

Downstream is decoupled

The crawler's output is a durable stream of pages. The indexer, a link-graph job that feeds priorities back, and an archive can each consume it independently, and a slow indexer never slows the crawl.
