Upload in resumable chunks; play back as plain files that any CDN can cache

The upload API hands out a signed, resumable upload URL, so large files go straight to object storage in chunks and a failed chunk is retried on its own. Playback isn't an API call per frame. The video becomes a manifest listing renditions, and each rendition is a list of short segments. Both are ordinary HTTP files, which is exactly what a CDN is good at.

API
POST /v1/uploads   { "filename": "trip.mov", "size": 2147483648 }
→ 201 { "videoId": "v_8Kq", "chunkSize": 8388608,
        "uploadUrl": "https://upload…/v_8Kq?sig=…" }

PUT  {uploadUrl}   Content-Range: bytes 0-8388607/2147483648
                   # resumable: retry only the failed chunk
POST /v1/videos/v_8Kq/complete   → 202 { "status": "PROCESSING" }

GET  /v1/videos/v_8Kq
→ { "status": "READY", "duration": 312,
    "manifest": "https://cdn…/v_8Kq/master.m3u8?token=…" }

Upload straight to storage

API servers never proxy gigabytes. They issue a signed resumable URL (S3 multipart, GCS resumable) and the client uploads directly in 8 MB chunks. The complete call, or the storage event, triggers processing. Keep the original forever, in a colder storage tier.

HLS and DASH, one set of segments

HLS (Apple) and DASH (everyone else) differ mainly in the manifest. With CMAF-packaged fMP4 segments, both manifests point at the same segment files, halving storage and CDN cache footprint compared with packaging each format separately.

Metadata is small

Videos and renditions are ordinary rows: tens of millions of videos, a few KB each, in a sharded SQL or wide-column store, heavily cached. View counts are events aggregated asynchronously, never a row update per view.
