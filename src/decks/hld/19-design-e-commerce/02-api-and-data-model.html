Checkout is one idempotent POST; stock and money live in separate, strongly consistent tables

Browse endpoints are plain cacheable GETs. The single write that matters is POST /checkout. It carries an idempotency key and returns 202 with an order id, because the work behind it (reserve, pay, confirm) is a multi-step workflow. The data model makes the invariants explicit: an order line records the price paid, and a reservation is a row with an expiry.

API
GET  /v1/search?q=running+shoes&size=10&page=2
GET  /v1/products/{sku}            # catalog + price + stock badge
PUT  /v1/carts/{cartId}/items/{sku}   { "qty": 2 }

POST /v1/checkout
Idempotency-Key: 7f3c9a…
{ "cartId": "c_91", "addressId": "a_4", "paymentMethod": "pm_tok_…" }
→ 202 { "orderId": "o_5521", "status": "PENDING" }

GET  /v1/orders/o_5521   → PENDING | CONFIRMED | CANCELLED | SHIPPED
domain events (via the outbox)
OrderPlaced → StockReserved → PaymentAuthorized → OrderConfirmed
                    └→ ReservationExpired / PaymentFailed → OrderCancelled

Snapshot the price

The order line stores the unit price the customer agreed to. Prices change, and the catalog is not the record of what someone paid. Re-validate price and stock at checkout and show the customer any difference before charging.

Reservations are rows

A reservation is a row with an expiry, not just a decremented counter. That gives you an audit trail, lets a sweeper release expired holds, and lets a reconciliation job compare reserved with the sum of active reservations.

A store per service

Catalog: a document store plus a search index. Carts: a KV store (DynamoDB or Redis) with a TTL. Orders, inventory and payments: PostgreSQL, sharded by order id and by SKU when needed. Each service owns its data and publishes events through an outbox.
