Deep dive 2: checkout is a saga, with reversible steps first and an idempotency key on every hop

Stock, orders and payments live in different services, and one of them is an external provider, so there is no single transaction to wrap it all in. The order service runs a persisted state machine. It reserves, authorises and confirms, and each step has a compensation if a later one fails. Retries are safe because every call carries a key the receiver deduplicates on.

Orchestrate this one

Checkout has a strict order, compensations and a customer waiting on the result, which suits an explicit orchestrator (the order service, or a workflow engine such as Temporal). Persist the saga state after every step so a crashed instance resumes where it stopped instead of starting over.

Authorise, then capture

At checkout, only authorise: the funds are held, not taken. Capture when the order ships. Cancelling before shipment then means voiding an authorisation rather than refunding a charge, which is cheaper, instant, and has no fees.

Trust, but reconcile

Providers also report outcomes by webhook, and webhooks can arrive late, twice or out of order. Handle them idempotently by provider reference. A daily job compares your payments table with the provider's settlement report and flags any mismatch.
