Deep dive 1: build the top-k lists bottom-up, and keep the trie small

The trie is built offline, so you can afford to do the work there. Insert every kept query with its score, then compute each node's top-k by merging its children's lists from the leaves up. At query time nothing is searched, only read. The remaining problem is memory, which you control with thresholds, depth limits and path compression.

Query cost

O(len(prefix)) pointer hops to reach the node, then return a precomputed list, no matter how many queries sit below it. That flat cost is the property that lets a million requests a second fit on a modest fleet.

Scoring

Score = decayed frequency plus a small freshness boost, capped so a single viral day can't dominate for weeks. Normalise queries at build time (lowercase, trim, Unicode NFKC) so "Car " and "car" count as one.

Why not just a database

WHERE query LIKE 'car%' ORDER BY count DESC LIMIT 8 works with a prefix index at low volume, but at 1 M/s each call is a range scan and a sort. A search engine's completion suggester is fine at moderate scale. At this scale, precompute.
