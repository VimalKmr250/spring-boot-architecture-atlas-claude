A fast in-memory serving path fed by a slow, careful build path

Split the system in two. Serving is stateless apart from a read-only trie in memory: every request is a few pointer hops, heavily cached at the edge. Building is a data pipeline that turns search logs into ranked, filtered snapshots every hour or so and ships them to the servers.

Caching does most of the work

One- and two-character prefixes are few (about 1,000) and account for a large share of requests. The CDN and browser cache them for minutes. The server sees mostly longer, rarer prefixes, and each of those is still a microsecond trie walk.

Sharding the trie

Shard by prefix range so each lookup hits exactly one shard. The ranges are cut by measured traffic, not the alphabet ("s" and "c" are huge, "x" is tiny). Replicate each shard three or more times for throughput and availability.

Safe deploys of data

Load the new snapshot alongside the old one, run canary queries (sizes, blocklist hits, top results for known prefixes), then swap an atomic pointer. Keep the previous version for an instant rollback, since a bad snapshot is a data outage.
