One tiny GET, and a trie that stores its answers at every node

The API is a single cacheable GET. The interesting data structure is a trie (prefix tree) in which every node also stores the top-k completions below it. A lookup becomes "walk down one node per character, then return the list stored there". There is no subtree search at query time.

API
GET /v1/suggest?q=car&lang=en&limit=8
Cache-Control: public, max-age=300           # short prefixes are very cacheable
→ 200 { "prefix": "car",
        "suggestions": [ "car insurance", "cars for sale", "cartoon",
                         "car rental", "cardi b", … ],
        "version": "trie-2026-09-30T10" }
client behaviour (half the design)
// debounce 50–100 ms; cancel stale requests; cache per prefix
// "car" then "cart" → if "car" results are complete (< 8 hits), filter locally
// never block typing on the network

Where the counts come from

A query_counts table (query → decayed score), built from search logs by a batch or streaming job. Scores decay exponentially (half-life of about a week), so yesterday's spike fades and evergreen queries stay.

The trie is a build artefact

It isn't a database. It's an immutable snapshot built offline, versioned, stored in object storage and loaded into memory by the serving nodes. Updates arrive as new snapshots, never as in-place writes on the hot path.

Or a KV of prefixes

A flat alternative: precompute prefix → top-8 list for every prefix up to 20 characters and serve it from a KV store or a CDN. It's simpler to shard and cache, and bigger on disk. It's often the pragmatic interview answer after explaining the trie.
