Monitor from the user inward: journeys first, machines last

A design isn't finished until you can tell whether it's working. Monitoring works in layers. At the top are the signals users feel, which page a human. Below them are the signals that explain why, which go on dashboards. Alongside sit security and usage monitoring, which answer "who is doing what" rather than "is it up".

Three kinds of health check

Liveness: is the process stuck? Restart it. Readiness: can it take traffic now? Remove it from the load balancer. Deep checks of dependencies belong on dashboards, not in liveness probes. Otherwise a database blip restarts your whole fleet at once.

Measure where the user is

Server metrics miss DNS failures, CDN errors and slow clients. Add synthetic probes (scripted journeys from several regions every minute) and real user monitoring (timings reported by the browser or app).

Instrument once, everywhere

OpenTelemetry SDKs emit metrics, logs and traces with shared resource attributes (service, version, region) and a shared trace id. Put that into platform libraries, so every new service is observable by default.
