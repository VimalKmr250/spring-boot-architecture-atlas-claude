Long work gets a job id now and a result later

Anything slower than a couple of seconds, such as generating a report, transcoding a video or bulk-importing a CSV, shouldn't hold an HTTP request open. Accept the request, put a job on a queue, return 202 Accepted with a URL to check, and let a worker do the work. The client polls, or gets a push when the job finishes.

Event-driven jobs

Triggered by something that happened: an upload finished, an order was placed. Consumers pick them up from a queue or topic. Latency is seconds, and throughput scales with the number of workers.

Schedule-driven jobs

Nightly reports, cleanups, reminders. Don't run cron on every app instance, or it fires N times. Use a single scheduler service, a lock (ShedLock, a DB advisory lock, a Redis lock with a lease), or leader election. Make each run idempotent and resumable.

What a job system needs

Retries with backoff and a dead-letter queue for poison jobs, visibility timeouts so a crashed worker's job reappears, priorities or separate queues so bulk work can't starve urgent work, status and progress tracking, and a limit on how long a job may run.
