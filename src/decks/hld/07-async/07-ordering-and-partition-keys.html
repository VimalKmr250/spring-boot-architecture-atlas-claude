Order is guaranteed per partition, so key by the thing whose order matters

A log scales by splitting a topic into partitions that are read in parallel. Order holds within a partition, not across them. Messages with the same key always land in the same partition, so choose the key as the entity whose events must stay in sequence, usually the aggregate id.

Choosing the key

Key by the entity whose history must be sequential: order_id, account_id, conversation_id. Avoid keys with a few huge values (a tenant with half the traffic), which create a hot partition, and don't key randomly if anything downstream depends on order.

How order still breaks

Producer retries without idempotence enabled, a consumer that processes one partition with a thread pool, retry topics that re-queue a failed message behind newer ones, and replicas in other regions. Carry a version or sequence number and reject stale updates at the consumer.

Global order is expensive

Total order over everything means one partition, and so the throughput of one consumer. Almost nothing needs it. When something seems to, it usually needs per-entity order plus a timestamp for display.
