Messages arrive at least once, so processing must happen effectively once

A consumer can crash after doing the work but before acknowledging it, and the broker cannot tell that apart from never having done it. So it redelivers. Reliable messaging is therefore at-least-once. "Exactly once" in practice means at-least-once delivery plus an idempotent consumer that recognises repeats.

SemanticsHowFailure outcomeUse for
At-most-onceAck (or auto-commit) before processingMessages can be lost, never duplicatedMetrics samples, telemetry, anything where a gap is cheaper than a duplicate
At-least-onceProcess, then ackNever lost; duplicates on crash or retryThe default for business events, paired with idempotent consumers
Effectively-onceAt-least-once + dedupe, or Kafka transactions for read-process-write within KafkaNeither lost nor applied twicePayments, balances, inventory, billing
Idempotency keys at the API edge tooThe same problem appears when a client retries POST /payments after a timeout. The client sends an Idempotency-Key header. The server stores the key with the response, and on a repeat key returns the stored response instead of charging again. That is how Stripe's API works, and interviewers expect it on any money-moving endpoint.
