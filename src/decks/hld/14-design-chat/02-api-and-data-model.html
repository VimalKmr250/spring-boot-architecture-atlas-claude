A WebSocket protocol for live traffic, REST for history, and messages partitioned by conversation

Live messages, receipts and presence flow over one persistent WebSocket per device. Fetching history, the conversation list and media uploads are ordinary REST calls that can be cached and retried. The store is modelled around the two hottest queries: "latest messages in conversation X" and "my conversations, newest first".

WebSocket frames (JSON or protobuf)
// client → server
{ "t": "send", "client_msg_id": "c-9f1…", "conv": "g-77", "body": "…" }
{ "t": "ack",  "conv": "g-77", "seq": 1042 }        // delivered up to 1042
{ "t": "read", "conv": "g-77", "seq": 1042 }

// server → client
{ "t": "sent", "client_msg_id": "c-9f1…", "seq": 1043 }  // persisted ✓
{ "t": "msg",  "conv": "g-77", "seq": 1043, "from": "u-5", "body": "…", "ts": … }
{ "t": "receipt", "conv": "g-77", "seq": 1043, "user": "u-9", "state": "read" }
REST
GET  /v1/conversations?cursor=…                # my inbox, by last activity
GET  /v1/conversations/g-77/messages?before=1043&limit=50
POST /v1/media/upload-url                      # presigned PUT for images

Why a wide-column store

The workload is write-heavy (700k/s), almost all reads are "latest N in one conversation", and there is a lot of data. That's exactly a partition-per-conversation, clustered-by-sequence table. The month bucket keeps very long-lived chats from growing one partition forever.

Sequence numbers, not timestamps

Each conversation gets a monotonically increasing seq, assigned by the server when the message is persisted. It orders messages, drives "give me everything after 1042" sync, and makes receipts one number: "read up to 1042".

client_msg_id for idempotency

Phones retry on flaky networks. The client generates an id per message, and the server dedupes on (conv, client_msg_id), returning the existing seq. A resend never produces a duplicate bubble.
