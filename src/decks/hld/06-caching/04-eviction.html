A full cache must forget something; the policy decides what

Memory is finite, so a cache evicts entries to make room. The policy is a bet about the future. LRU bets that recently used items will be used again, LFU that frequently used ones will, and TTL expiry that data goes bad after a while regardless. The best policy depends on the access pattern, which is why it's measured, not guessed.

PolicyEvictsGood whenFails when
LRULeast recently usedRecency predicts reuse (sessions, feeds, most web traffic)A one-off scan (a batch job, a crawler) flushes the hot set
LFULeast frequently usedStable popularity (top products, reference data)Popularity shifts and old counts linger, unless counters decay
FIFOOldest insertedSimplicity; data that ages uniformlyHot old keys get evicted anyway
TTL expiryAnything past its time to liveFreshness bounds ("prices at most 60 s old")Used as the only policy: memory still fills
RandomA random keyHuge caches where bookkeeping costs more than precisionSmall caches with a clear hot set
In Redis termsSet maxmemory and a policy. allkeys-lru or allkeys-lfu for a pure cache. volatile-lru or volatile-ttl when the same instance also holds keys that must not be evicted (it then evicts only keys with a TTL). And never noeviction for a cache: once memory is full, writes start failing. Watch evicted_keys and the hit ratio together.
