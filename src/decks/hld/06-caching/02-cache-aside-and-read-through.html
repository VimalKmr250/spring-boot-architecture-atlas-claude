On a miss, someone has to load from the database: your code or the cache

Cache-aside (lazy loading) is the default. The application checks the cache, reads the database on a miss, and fills the cache itself. Read-through moves that loading logic into the cache layer, so the application only ever talks to the cache. Both load only what is actually requested, so the cache fills with the hot set.

cache-aside, the whole pattern
def get_profile(user_id):
    key = f"profile:{user_id}"
    cached = redis.get(key)
    if cached is not None:
        return deserialize(cached)            # hit
    row = db.query("SELECT … FROM profiles WHERE id = %s", user_id)
    if row is None:
        redis.set(key, NOT_FOUND, ex=60)      # cache the miss too
        return None
    redis.set(key, serialize(row), ex=300 + random.randint(0, 60))
    return row

def update_profile(user_id, changes):
    db.update(user_id, changes)               # 1. write the truth
    redis.delete(f"profile:{user_id}")        # 2. then invalidate, don't update

Trade-offs to state

  • Resilient: if the cache dies, reads fall through to the database. That is slower but still correct, provided the database can take it.
  • First request is slow: every miss costs a cache round trip plus a database read. Warm critical keys at deploy time.
  • Stale window: data can be stale until the TTL expires or an invalidation lands. Pick the TTL from how stale the business can tolerate.
  • The random extra TTL (jitter) stops thousands of keys set together from expiring together.
