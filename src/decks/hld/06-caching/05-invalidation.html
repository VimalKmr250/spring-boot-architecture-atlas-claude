Invalidation fails through races, not through forgetting to delete

"Update the database, then delete the key" is correct most of the time. The dangerous case is a slow reader overlapping a writer. The reader loaded the old value before the write, and puts it in the cache after the writer deleted the key. The stale value then stays cached until its TTL expires, and may never be corrected if there is no TTL.

① TTL as the safety net

Choose the TTL from the staleness the business can accept (30 s for prices, 10 min for a profile), and add jitter. Every other technique reduces how often staleness happens. The TTL limits how long it lasts.

② Leases (the Facebook memcache fix)

A miss hands the reader a lease token, and the cache accepts the later SET only with a valid token. A DEL in between invalidates the token, so the late write of v1 is rejected. Leases also throttle stampedes on the same key.

③ Versioned values

Store (version, value) and set conditionally, e.g. with a Lua script that writes only if the incoming version is newer. Because versions come from the database (a row version or LSN), an old value can never overwrite a newer one.

④ Invalidate from the change stream

Instead of every code path remembering to delete, a CDC consumer (for example, Debezium reading the WAL) deletes keys for every committed change, and can delete again a second later to catch late sets. This covers writes made outside your service as well.
