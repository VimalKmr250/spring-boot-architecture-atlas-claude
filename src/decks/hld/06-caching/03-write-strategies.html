What happens to the cache when data changes is the real design choice

Reads are straightforward. The bugs live in writes. Four strategies decide whether a write goes through the cache, around it, or is buffered in it, and each one fixes the write latency, the freshness of reads, and what you lose if the cache node dies.

Delete, don't updateOn a write, delete the cache key rather than setting it to the new value. Two concurrent writers that each update the cache can finish in the opposite order to their database commits, leaving the older value cached indefinitely. A delete is idempotent, and the next read reloads the truth.
