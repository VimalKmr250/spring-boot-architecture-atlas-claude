Three endpoints and one hot table keyed by code

Every redirect is a lookup by exact key, and links never change once created. That is a key-value access pattern with no joins on the hot path, so the store choice is easy. Click data is append-only and analytical, so it goes to a different store entirely.

API
POST /v1/urls
Idempotency-Key: 7c1e…            # retries can't create duplicates
{ "long_url": "https://…", "alias": "spring-sale", "expires_at": "2027-01-01" }
→ 201 { "code": "Ab3xK9q", "short_url": "https://short.ly/Ab3xK9q" }

GET /{code}
→ 302 Location: https://…          # or 404 / 410 Gone if expired

GET /v1/urls/{code}/stats?from=…&to=…
→ 200 { "clicks": 18234, "by_day": […], "top_countries": […] }

DELETE /v1/urls/{code}             # owner only; tombstones the code

302, not 301 (by default)

A 301 Moved Permanently is cached by browsers, so repeat clicks never reach you. That means less load, but no analytics and no way to expire the link. Use 302 when stats or expiry matter. Offer 301 for "permanent, no stats" links.

Why a KV store fits

Lookup by exact key, no joins, immutable values, 3 TB growing steadily. Any of DynamoDB, Cassandra or sharded PostgreSQL works. Say which and why: "PostgreSQL until a few TB, because the team knows it. The schema is already shard-friendly."

Idempotent creates

A mobile client that retries a timed-out create shouldn't get two codes. The Idempotency-Key maps to the first response for 24 hours. Custom aliases use a conditional insert (INSERT … IF NOT EXISTS), so a collision returns 409.
