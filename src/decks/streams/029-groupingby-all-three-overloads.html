groupingBy: the GROUP BY of streams

groupingBy sorts elements into buckets by a key, then reduces each bucket with a downstream collector, which defaults to toList(). Most interview coding questions about employees and departments come down to one groupingBy with the right downstream.

The three overloads, then nesting and composite keys
// 1 · key → list of elements                     (a HashMap of ArrayLists today)
Map<String, List<Order>> byStatus = orders.stream()
        .collect(Collectors.groupingBy(Order::status));

// 2 · key → a reduced value
Map<String, Double> revenueByCustomer = orders.stream()
        .collect(Collectors.groupingBy(Order::customer,
                 Collectors.summingDouble(Order::total)));

// 3 · you choose the map
TreeMap<String, Long> countByStatus = orders.stream()
        .collect(Collectors.groupingBy(Order::status, TreeMap::new,
                 Collectors.counting()));

// Two levels: customer → status → orders
Map<String, Map<String, List<Order>>> nested = orders.stream()
        .collect(Collectors.groupingBy(Order::customer,
                 Collectors.groupingBy(Order::status)));

// A composite key is a record, not a concatenated string
record CustomerStatus(String customer, String status) {}
Map<CustomerStatus, Long> pairs = orders.stream()
        .collect(Collectors.groupingBy(
                 o -> new CustomerStatus(o.customer(), o.status()),
                 Collectors.counting()));

The null keyA classifier that returns null throws NullPointerException: element cannot be mapped to a null key. It is the groupingBy version of the toMap surprise: the test data had a status on every order. Map missing keys to a real value, for example o -> Objects.requireNonNullElse(o.status(), "UNKNOWN").
Key order and missing groupsThe default map is a HashMap, so printing it gives no particular order: pass TreeMap::new or LinkedHashMap::new when order matters. And a group exists only for keys that occur. A status with no orders is absent, not an empty list.
