Split, work, combine: streams on fork/join

parallelStream() or .parallel() asks the library to split the source with its spliterator's trySplit, process the pieces as fork/join tasks, and combine the partial results. The tasks run on ForkJoinPool.commonPool(), which is shared by the whole JVM, helped by the thread that called the terminal operation.

Who does the work, on a 20-core machine running JDK 25
ForkJoinPool.commonPool().getParallelism();     // 19: cores − 1
Runtime.getRuntime().availableProcessors();     // 20

IntStream.range(0, 10_000).parallel()
         .mapToObj(i -> Thread.currentThread().getName())
         .collect(Collectors.toSet());
// [main, ForkJoinPool.commonPool-worker-1, … -worker-19]: the caller helps

// Sized once for the whole JVM, at startup:
// -Djava.util.concurrent.ForkJoinPool.common.parallelism=8
SourceSplitsWhy
ArrayList, arrays, IntStream.rangeWellExact halves by index, sizes known (SUBSIZED)
HashSet, HashMap viewsWell enoughBy bucket ranges; sizes only estimated
TreeSet, TreeMap viewsAdequatelyBy subtree, which may be unbalanced
LinkedListBadlyMust walk the list to find a split point
Stream.iterate, BufferedReader.linesBadlyEach element depends on the previous, or on reading in order
One pool for the whole JVMCompletableFuture.supplyAsync without an executor also runs on the common pool. So does every other library's parallel stream. A slow parallel stream in one endpoint therefore delays unrelated work across the service. Running a parallel stream from inside your own ForkJoinPool (pool.submit(() -> list.parallelStream()…).get()) makes it use that pool instead. That behaviour is an implementation detail rather than a documented contract, and many teams rely on it anyway.
