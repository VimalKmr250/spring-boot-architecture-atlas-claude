Writing a gatherer: state, integrate, push

Most custom gatherers need three decisions: what state to keep, what to push for each element, and whether to stop. The factories on Gatherer take exactly those pieces. The examples compile and run on JDK 25.

distinctBy: the first element for each key
static <T, K> Gatherer<T, ?, T> distinctBy(Function<? super T, ? extends K> key) {
    return Gatherer.ofSequential(
        () -> new HashSet<K>(),                       // state: keys seen so far
        Gatherer.Integrator.ofGreedy((seen, t, down) -> {
            if (seen.add(key.apply(t))) return down.push(t);
            return true;                               // a repeat: skip it, keep going
        }));
}

List<Order> firstPerCustomer = orders.stream()
        .gather(distinctBy(Order::customer))
        .toList();
withinBudget: stateful short-circuit
// Pass orders until the running total would exceed the budget, then stop
static Gatherer<Order, ?, Order> withinBudget(double budget) {
    return Gatherer.ofSequential(
        () -> new double[1],                           // state: amount spent
        (spent, order, down) -> {
            if (spent[0] + order.total() > budget) return false;  // stop pulling
            spent[0] += order.total();
            return down.push(order);
        });
}

orders.stream().gather(withinBudget(1_000)).toList();

State belongs in the initializerA gatherer that keeps its HashSet in a field, or captures one from the enclosing method, shares that state across every stream that uses it, and across threads. The second run then starts with the first run's keys. The initializer exists so that each evaluation gets fresh state; always keep mutable state there.
