A stream is a recipe, not a container

A collection holds elements. A stream holds none. It describes work: where the elements come from, what happens to each one, and what to produce at the end. Nothing runs until a terminal operation asks for a result, and then it runs exactly once.

The running example on every API slide
record Line(String sku, int qty, double price) {}
record Order(String id, String customer, String status,
             double total, List<Line> lines) {}

List<String> bigSpenders = orders.stream()   // source: nothing copied
        .filter(o -> o.total() > 500)        // recorded, not run
        .map(Order::customer)                // recorded, not run
        .distinct()                          // recorded, not run
        .sorted()                            // recorded, not run
        .toList();                           // runs all of the above, once
CollectionStream
Holds elementsYes, in memoryNo. Elements flow through it
Work happensWhen you call a methodOnly when a terminal op runs
IterationExternal: you write the loopInternal: the library drives it
ReusableAs often as you likeOnce
SizeFiniteCan be infinite
Changes the sourceadd, remove doNever. It builds a new result
Where the one-shot rule bitesStoring a Stream in a field or passing it to two methods. The second consumer throws. Store the collection, or a Supplier<Stream<T>>, and call .stream() each time you need one: a fresh pipeline costs a few small objects.
