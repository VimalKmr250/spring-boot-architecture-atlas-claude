Adapters that reshape what each group becomes

A downstream collector decides what each group of a groupingBy or partitioningBy turns into. Five adapters reshape it without leaving the collector: transform the elements, filter them, flatten them, finish with a function, or reduce them.

AdapterWhat it does to each groupSince
mapping(f, downstream)Transforms each element, then collects: the ids of each customer's orders8
filtering(p, downstream)Keeps matching elements, but keeps the group even when nothing matches9
flatMapping(f, downstream)Expands each element into a stream: every SKU each customer bought9
collectingAndThen(downstream, finisher)Applies a function to the finished result: unwrap an Optional, freeze a list8
reducing(identity, mapper, op) · reducing(identity, op) · reducing(op)A reduce per group; the one-argument form returns an Optional8
Four adapters on the order data
// mapping: customer → the ids of their orders
Map<String, List<String>> idsByCustomer = orders.stream()
        .collect(Collectors.groupingBy(Order::customer,
                 Collectors.mapping(Order::id, Collectors.toList())));

// filtering: large orders per customer, and customers with none stay in the map
Map<String, List<Order>> largeByCustomer = orders.stream()
        .collect(Collectors.groupingBy(Order::customer,
                 Collectors.filtering(o -> o.total() > 500, Collectors.toList())));

// flatMapping: customer → every SKU they bought
Map<String, Set<String>> skusByCustomer = orders.stream()
        .collect(Collectors.groupingBy(Order::customer,
                 Collectors.flatMapping(o -> o.lines().stream().map(Line::sku),
                                        Collectors.toSet())));

// collectingAndThen: the biggest order per customer, without the Optional
Map<String, Order> biggest = orders.stream()
        .collect(Collectors.groupingBy(Order::customer,
                 Collectors.collectingAndThen(
                     Collectors.maxBy(Comparator.comparingDouble(Order::total)),
                     Optional::get)));
filtering versus filter-then-group, on JDK 25Two employees, one in ops earning 10 and one in dev earning 50, grouped by department after keeping salaries above 20:
filtering inside the grouping gives {dev=[…], ops=[]}.
filter before the grouping gives {dev=[…]}.
A report of "large orders per customer" usually wants every customer listed, which is exactly why filtering was added in Java 9.
Why Optional::get is safe here, and only hereA group exists only because at least one element produced its key, so maxBy inside groupingBy can never be empty. The same result in one step, with no Optional at all: toMap(Order::customer, o -> o, BinaryOperator.maxBy(Comparator.comparingDouble(Order::total))).
