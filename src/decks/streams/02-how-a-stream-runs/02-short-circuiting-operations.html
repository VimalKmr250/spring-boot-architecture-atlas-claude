Some operations can stop early, and only they can handle infinity

A short-circuiting operation can finish without reading the whole source. It is the only kind that can make a pipeline over an infinite stream terminate, and it is what lets a search over a million orders stop at the first match. When a short-circuit fires anywhere downstream, the source stops being pulled.

Infinite source, finite answer, and the one that never returns
// Terminates: iterate never ends, but findFirst stops at a match
int first = Stream.iterate(1, n -> n * 2)
        .filter(n -> n > 1_000)
        .findFirst()
        .orElseThrow();                       // 1024

// Terminates: limit caps an infinite generator
List<Double> samples = Stream.generate(Math::random)
        .limit(3)
        .toList();

// Never returns: every element passes, so allMatch
// has to keep looking for one that fails
Stream.generate(() -> 1).allMatch(n -> n > 0);

Short-circuit is not the same as cheap

anyMatch over orders stops at the first match. If there is no match it still reads every order, so the worst case is the whole source. In a database-backed stream that is a full table read. Push the condition into the query when it can be pushed.

flatMap honours it since Java 10

In Java 8 and 9, flatMap pushed each inner stream through in full, even when the step downstream had already stopped. So Stream.of(1).flatMap(i -> Stream.iterate(0, x -> x + 1)).findFirst() never returned. JDK 10 fixed it (JDK-8075939), and on 25 it returns Optional[0]. The fix still catches out anyone reading Java 8 advice.
