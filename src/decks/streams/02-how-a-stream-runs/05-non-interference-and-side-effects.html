Two rules the compiler cannot check

The Javadoc asks two things of every lambda you pass to a stream. Non-interference: do not modify the source while the pipeline runs. Statelessness: do not depend on, or change, shared mutable state. Break either and the code may still pass a test, then fail under load or in parallel.

Interference: modifying the source mid-stream, on JDK 25
List<String> names = new ArrayList<>(List.of("ana", "bo", "cy", "dee"));
// Each example below starts again from this list
names.stream()
     .filter(n -> n.length() == 2)
     .forEach(names::remove);
// NullPointerException: Cannot invoke "String.length()"
//   because "<parameter1>" is null

names.stream()
     .filter(n -> n.length() == 2)
     .forEach(n -> names.add(n + "!"));
// ConcurrentModificationException, after the loop has finished

names.removeIf(n -> n.length() == 2);   // what was meant
Why two different failuresAn ArrayList spliterator walks its backing array by index and checks for modification only once, at the end. Removing bo shifts the array under the walk, so cy is skipped and the filter is handed the empty slot at the end: the NullPointerException. Adding lets the walk finish, then the final check throws. The Javadoc promises neither, only that the result is undefined. Modifying the source before the terminal operation starts is fine: the stream reads it only once that operation begins.
Side effects: building a result by hand
// Wrong: the pipeline mutates a list it does not own
List<String> ids = new ArrayList<>();
orders.parallelStream()
      .filter(o -> o.total() > 500)
      .forEach(o -> ids.add(o.id()));    // lost updates, or
                                         // ArrayIndexOutOfBoundsException

// Right: let the stream build what it returns
List<String> bigIds = orders.parallelStream()
        .filter(o -> o.total() > 500)
        .map(Order::id)
        .toList();
Measured, not hypotheticalIn one run on JDK 25, IntStream.range(0, 100_000).parallel().forEach(list::add) into a plain ArrayList left 14,084 elements in the list and threw nothing. The same code run sequentially is correct, which is why this bug survives code review.
Side effects that are fineOnes the result does not depend on: logging from peek while debugging, or incrementing a thread-safe metric such as a LongAdder. And forEach at the end of a pipeline exists precisely to cause a side effect. The rule is about producing the result through side effects.
