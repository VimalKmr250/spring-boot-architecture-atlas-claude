Stateful operations remember, and memory costs

A stateless operation decides about each element on its own: filter, map, flatMap, peek. A stateful one has to remember what it has already seen. distinct keeps a set of every element so far, sorted keeps every element, and limit and skip keep a count. The difference shows up in memory, in parallel speed, and on infinite streams.

A stateful operation over a database stream
// Every row is read into memory before the first one comes out of
// sorted(): the limit(10) cannot help, because it runs after the barrier
try (Stream<Order> all = jdbc.queryForStream("select * from orders", ORDER_ROW)) {
    all.sorted(Comparator.comparingDouble(Order::total).reversed())
       .limit(10)
       .forEach(this::report);
}

// Sort where the index is, and read ten rows
jdbc.query("select * from orders order by total desc limit 10", ORDER_ROW)
    .forEach(this::report);
Stateful lambdas are a different thing, and a bugA stateful operation is the library's business. A stateful lambda is yours, and it breaks things. The classic example deduplicates by key with filter(seen::add), where seen is a HashSet. That works sequentially. In parallel, several threads write to an unsynchronised set, and which duplicate survives depends on thread timing. The Javadoc asks for lambdas whose result does not depend on state that changes while the pipeline runs. For "distinct by key", group or toMap by the key instead, or write a gatherer.
