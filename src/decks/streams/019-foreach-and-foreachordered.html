forEach is for side effects, and only for side effects

forEach runs an action on every element and returns nothing. It is the right ending when the point is an effect: sending, writing, printing. It is the wrong ending for building a result. And in parallel it ignores encounter order unless you ask for forEachOrdered.

Right uses, and the ones that need no stream
orders.stream()
      .filter(o -> "PAID".equals(o.status()))
      .forEach(mailer::sendReceipt);               // an effect: exactly right

orders.parallelStream()
      .map(Order::id)
      .forEachOrdered(System.out::println);        // encounter order, in parallel

// No pipeline needed? Collection.forEach and Map.forEach are enough
orders.forEach(this::audit);
stockBySku.forEach((sku, qty) -> log.info("{} = {}", sku, qty));
MethodOrderWatch for
forEach(action)Encounter order sequentially; none in parallelThe action may run on several threads at once, so it must be thread-safe
forEachOrdered(action)Always encounter orderActions run one at a time, in order, which gives up much of the parallel speed-up
Iterable.forEach · Map.forEachThe collection's ownNo stream is built. On a synchronized collection it runs under the collection's lock; a stream does not

Not for building results

forEach(list::add) is the parallel lost-update bug from the side-effects slide. When the goal is a collection, a map or a number, end with toList, collect or reduce.

No break

A lambda cannot break out of the loop that calls it. To stop early, make the condition part of the pipeline with takeWhile, anyMatch or findFirst. If the stopping logic is complex, a plain for loop is clearer.

No checked exceptions

Consumer.accept declares none, so forEach(this::writeToDisk) does not compile if writeToDisk throws IOException. The options are on Checked exceptions and debugging.
