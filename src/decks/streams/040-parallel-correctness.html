Code that is right sequentially and wrong in parallel

A pipeline that keeps the rules gives the same answer sequentially and in parallel. The bugs come from breaking them: shared mutable state, a reduce with a false identity or a non-associative operation, and code that assumes an order or a thread. Every "parallel" result below was measured on JDK 25 on a 20-core machine.

The Spring version of the ThreadLocal rowSpring binds the transaction, the persistence context, the security context and the logging MDC to the calling thread. Inside parallelStream() the worker threads have none of them. A repository call in the lambda runs outside the caller's @Transactional, lazy loading throws LazyInitializationException, and log lines lose their trace id. Load the data first, then go parallel over plain objects, if at all.
The checklist that makes parallel safeLambdas that are stateless and do not touch shared mutable data. reduce with a true identity and an associative operation. Results produced by collectors, never by side effects. No assumptions about order or thread. Code written this way can switch between sequential and parallel with no change in its result, which is exactly the property the Stream API was designed around.
