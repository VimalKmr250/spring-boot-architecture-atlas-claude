Parallel pays only when there is enough work to split

Splitting, scheduling and combining all cost something. Parallel wins when there is a lot of CPU work in total, a source that splits cleanly, and a cheap combine step. Most request-handling code has none of the three.

The N × Q rule of thumb

N is the number of elements and Q the work per element. The heuristic often quoted by the JDK's own stream authors is that N × Q needs to be in the order of 10,000 simple operations or more before parallelism has a chance. Summing a thousand integers (Q ≈ 1) is far below it. Rendering a thousand PDF pages is far above it. Everything in between: measure it.

Measure with JMH, not a System.nanoTime() loop: JIT warm-up, dead-code elimination and GC pauses make hand-rolled timings misleading in both directions.

Blocking I/O in a parallel streamids.parallelStream().map(restClient::fetch).toList() parks common-pool threads on network calls. With 19 of them, 19 slow calls stall every parallel stream and default CompletableFuture in the JVM. For I/O fan-out, use Gatherers.mapConcurrent (Java 24) or an executor of virtual threads, both of which bound concurrency explicitly and leave the common pool alone.
Say this in the interview"Parallel streams are for CPU-bound work over large, easily split data. I'd prove the gain with JMH first, because in a web service the requests already keep the cores busy. And I'd never put blocking calls in one: the common pool is shared by the whole JVM."
