map, flatMap, mapMulti, and infinite sources

map versus flatMap is the single most asked stream question. The other two here are how interviewers check whether your knowledge stopped at Java 8.

Q7

What is the difference between map and flatMap?

30-second answermap turns each element into exactly one element: orders.stream().map(Order::lines) gives a Stream<List<Line>>. flatMap turns each element into a stream and splices those streams together: flatMap(o -> o.lines().stream()) gives a Stream<Line>. Use flatMap to flatten nested collections, split text into words, or turn Optionals into zero or one element.

Go deeper: The telltale bug is map(o -> o.lines().stream()), which produces a Stream<Stream<Line>> that prints as ReferencePipeline$Head@…. There are primitive versions, flatMapToInt and friends, and Optional.flatMap is the same idea for optionals. A flatMap function that returns null is treated as an empty stream. Historical detail: until Java 10, flatMap ignored short-circuiting and consumed each inner stream fully (JDK-8075939).

Q8

When would you use mapMulti instead of flatMap?

30-second answermapMulti (Java 16) replaces each element with zero or more elements by pushing them into a consumer instead of returning a stream. It is the better choice when each element yields only a few results, often zero or one, because it avoids creating a stream per element, and when the logic is easier to write imperatively, such as an instanceof test.

Go deeper: Show the shape: .<Line>mapMulti((order, sink) -> { for (Line l : order.lines()) if (l.qty() >= 10) sink.accept(l); }). Point out the type witness: without <Line> the compiler infers Stream<Object>, and the assignment to List<Line> fails. There are primitive versions, mapMultiToInt and friends. When each element already is a collection, flatMap(List::stream) is still the clearer choice.

Q9

How do you create an infinite stream, and how do you stop it?

30-second answerStream.iterate(seed, f) produces seed, f(seed), f(f(seed)) and so on; Stream.generate(supplier) produces independent values. Both are infinite, so something downstream must short-circuit: limit, takeWhile, findFirst, anyMatch. Since Java 9, iterate(seed, hasNext, next) is finite on its own: the for loop as a stream.

Go deeper: Give the two traps. Stream.iterate(1, n -> n * 3).filter(n -> n <= 100).toList() never ends, because filter does not short-circuit and does not know the values only grow; takeWhile is the fix. And a stateful operation before the short-circuit defeats it: iterate(…).sorted().limit(3) made about 46 million pulls in two seconds on JDK 25 without producing anything, and ends in OutOfMemoryError. iterate is ordered; generate is not.
