Parallel streams: when, how, and what breaks

Interviewers ask about parallel streams to hear judgement, not enthusiasm. The strongest answers to the first question start with "rarely".

Q16

When should you use a parallel stream?

30-second answerRarely, and only after measuring. It pays for CPU-bound work over large data that splits well — arrays, ArrayList, ranges — with stateless operations and a cheap combine step. It rarely pays for small collections, for I/O, for order-bound stateful operations, or inside a web server whose request threads already keep every core busy. Rule of thumb: elements times work per element well above 10,000 simple operations.

Go deeper: Say why it hurts. There is splitting and merging overhead; LinkedList and iterate split badly; boxing makes the work memory-bound; sorted, distinct, limit and findFirst must preserve order. Then the operational risk: every parallel stream in the JVM shares ForkJoinPool.commonPool(), which has one thread fewer than there are cores, so blocking calls in one stream starve the others, including default CompletableFutures. For I/O fan-out, use Gatherers.mapConcurrent or virtual threads.

Q17

How does a parallel stream work internally?

30-second answerThe source's Spliterator is split recursively with trySplit. Each chunk runs as a fork/join task on ForkJoinPool.commonPool(), with the calling thread helping. The partial results are then combined pairwise, by merging collector containers or applying the reduce combiner, in encounter order when the stream is ordered.

Go deeper: The common pool's parallelism is availableProcessors() − 1: 19 on a 20-core machine. It is set for the whole JVM with -Djava.util.concurrent.ForkJoinPool.common.parallelism. Spliterator characteristics drive the behaviour: SUBSIZED sources split into exact halves, and ORDERED forces order-preserving merges. Running the stream inside your own ForkJoinPool makes it use that pool, which many teams rely on although it is an implementation detail. parallel() and sequential() are flags for the whole pipeline, and the last call wins.

Q18

What is wrong with list.parallelStream().forEach(result::add)?

30-second answerresult is usually an ArrayList, which is not thread-safe, so concurrent adds lose elements or throw ArrayIndexOutOfBoundsException. In one run on JDK 25, 100,000 parallel adds left 14,084 elements, with no error. The stream should produce the result: map, then toList() or a collector. Synchronising the list "fixes" it by serialising the work, which makes it slower than sequential.

Go deeper: State the general rule: lambdas passed to a stream should be stateless and free of side effects. Side effects in forEach are fine for output, such as sending or logging, but not for building results. The same family of bugs includes a HashMap used as a cache inside a lambda, ThreadLocals (null on worker threads), and Spring's transaction and security context, which are bound to the calling thread and so absent in the common pool. Collect first, then perform the effects.
