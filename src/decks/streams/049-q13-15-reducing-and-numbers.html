reduce, collect, and the numbers they return

The reduce questions test whether you know the rules that make parallel correct. The numeric question tests whether you know which types come back, because every one of the traps is a type.

Q13

Explain the three forms of reduce.

30-second answerreduce(identity, op) returns a T, and the identity for an empty stream. reduce(op) returns an Optional<T>, empty for an empty stream. reduce(identity, accumulator, combiner) lets the result type differ from the element type, and the combiner merges partial results in parallel. All three need an associative operation, and the identity must be a true identity.

Go deeper: Show the failure. reduce(1, Integer::sum) over 1 to 4 gives 11 sequentially and 14 in parallel on JDK 25, because the false identity is added once per chunk; subtraction gives −10 and 0. The three-argument form: Stream.of("a", "bb", "ccc").reduce(0, (acc, s) -> acc + s.length(), Integer::sum) is 6. In practice prefer sum(), count(), max() and the collectors. reduce is right for immutable values combined by an associative operation.

Q14

What is the difference between reduce and collect?

30-second answerreduce is an immutable reduction: each step combines two values into a new value, which suits numbers. collect is a mutable reduction: it accumulates elements into a container — a list, a map, a StringBuilder — that it creates with a supplier. For collections and strings use collect. reduce would copy the container at every step, which is O(n²), or, if you mutate the identity, race in parallel.

Go deeper: In parallel, collect gives each chunk its own container from the supplier and merges them with the combiner, so no locking is needed. Concurrent collectors such as groupingByConcurrent share one thread-safe container instead. Show the three-argument form, collect(StringBuilder::new, StringBuilder::append, StringBuilder::append), and say that a Collector is just that supplier, accumulator and combiner, plus a finisher, packaged for reuse.

Q15

How do you count, sum and average with streams, and what types come back?

30-second answercount() returns a long, but Collectors.counting() returns a Long. On primitive streams, sum() returns an int, long or double, average() returns an OptionalDouble, and summaryStatistics() gives count, sum, min, average and max in one pass. summingInt returns an Integer, averagingInt a Double, and summarizingInt an IntSummaryStatistics. Those are mostly used downstream of groupingBy.

Go deeper: The traps are all about types. IntStream.sum() and summingInt overflow silently (Integer.MAX_VALUE + 1 gives -2147483648), so sum money as long. averagingInt over nothing returns 0.0, while average() returns an empty OptionalDouble. An empty IntSummaryStatistics reports a min of Integer.MAX_VALUE. And Map<String, Integer> from counting() does not compile, because the count is a Long.
