Three questions that open almost every streams interview

These are the stream questions interviewers ask most, gathered from the question lists that keep recurring in 2025 and 2026 Java interviews. Each has a 30-second answer to say first and a go deeper paragraph for the follow-up, and each links back to the slides that cover it.

How to practise with theseRead the question, look away, and answer out loud for thirty seconds. Then compare with the 30-second answer. Whatever you left out is your study list, and the links under each answer open the slide that covers it. The browser's Back button returns you here.
Q1

What is a stream, and how is it different from a collection?

30-second answerA collection stores elements; a stream stores none. A stream describes a computation — a source, some intermediate operations, one terminal operation — that runs once, on demand. It is lazy, can be consumed only once, can be infinite, never modifies its source, and uses internal iteration, which is what lets the library skip work, stop early and run in parallel.

Go deeper: The one-liner that shows you understand it is "a collection is about data, a stream is about computation". Then give the consequences. Laziness means no intermediate collections, and work skipped when a short-circuit fires. One-shot means a second terminal operation throws IllegalStateException. Internal iteration is why .parallel() can exist at all. If the interviewer says "stream", check they do not mean InputStream, which is unrelated.

Q2

What is the difference between intermediate and terminal operations?

30-second answerIntermediate operations — filter, map, sorted — return a new Stream and do nothing yet: each one only records a stage. Terminal operations — collect, toList, forEach, reduce, count, findFirst — produce a result or a side effect, run the whole pipeline, and consume the stream. A pipeline has exactly one terminal operation, at the end.

Go deeper: Split the intermediate operations further. Stateless ones (filter, map, flatMap, peek) look at one element at a time. Stateful ones (distinct, sorted, limit, skip) must remember what they have seen. Short-circuiting ones (limit, takeWhile) can make an infinite stream finite. Terminal operations can short-circuit too: anyMatch, allMatch, noneMatch, findFirst, findAny. iterator() and spliterator() are also terminal: escape hatches for pulling elements yourself.

Q3

Why can't you reuse a stream?

30-second answerBecause it is a one-shot traversal, not a data structure. Its stages are linked objects that are marked as used the moment you chain another operation or start a terminal one. A second use throws IllegalStateException: stream has already been operated upon or closed. Keep the collection and call stream() again, or hold a Supplier<Stream<T>>.

Go deeper: Explain why the design is right. Some sources can be read only once — a file, a socket, a database cursor, an iterator — and the API treats every source the same way. The rule covers intermediate calls too: calling s.filter(…) twice on the same s throws the same exception, because a stage can be linked only once. The real-world bug is a Stream stored in a field, or returned from a getter that two callers use.
