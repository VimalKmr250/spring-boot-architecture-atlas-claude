Optional, functional interfaces and method references

These are not stream questions strictly speaking, but they arrive in the same round, usually straight after findFirst comes up.

Q19

orElse or orElseGet? And how should Optional be used?

30-second answerorElse(x) always evaluates x, even when a value is present; orElseGet(supplier) calls the supplier only when the Optional is empty. So orElse(repository.loadDefault()) hits the database on every call. Use orElse for constants, orElseGet for anything computed, and orElseThrow with a meaningful exception rather than get().

Go deeper: Optional is designed as a return type for "maybe no result", which is why findFirst, min, max and reduce(op) return one. Avoid it for fields, parameters and collection elements: it is not Serializable, and it adds a third state, null, besides present and empty. The useful methods are map, flatMap, filter, and from Java 9 ifPresentOrElse, or, and stream for flattening a Stream<Optional<T>>. Optional.of(null) throws; ofNullable is the null-safe factory. Never return null from a method declared to return Optional.

Q20

What is a functional interface, and which ones do streams use?

30-second answerAn interface with exactly one abstract method, so a lambda or method reference can implement it; @FunctionalInterface asks the compiler to check that. Streams use Predicate (filter), Function (map), Consumer (forEach), Supplier (generate, collect), UnaryOperator (iterate), BinaryOperator (reduce), BiFunction, BiConsumer and Comparator, plus primitive variants such as ToIntFunction and IntPredicate that avoid boxing.

Go deeper: Default and static methods do not count towards the single abstract method, and neither do public methods of Object such as equals, which is why Comparator qualifies. Mention the composition helpers: Predicate.and, or, negate and not (Java 11), and Function.andThen, compose and identity. None of these interfaces declares a checked exception, and captured local variables must be effectively final. Those two facts are behind the two most common lambda compile errors.

Q21

What are the four kinds of method reference?

30-second answerA static method: Integer::parseInt. An instance method of a particular object: System.out::println, mailer::send. An instance method of an arbitrary object of a type, where the first argument becomes the receiver: String::toUpperCase, Order::customer. And a constructor: ArrayList::new, String[]::new. Each is shorthand for a lambda that only calls that one method.

Go deeper: The third kind is the one people misread. String::compareToIgnoreCase used as a Comparator<String> takes two arguments, and the first becomes the receiver. Method references also help type inference: Comparator.comparing(Order::total).reversed() compiles, while comparing(o -> o.total()).reversed() fails, because the lambda's parameter is inferred as Object. And a named method gives a readable stack trace where a lambda gives lambda$process$3.
