The collector questions, and the exceptions behind them

Collectors are where most stream bugs in production come from, so these questions are usually followed by "and what happens when…". Have the exception names ready.

Q10

What is the difference between Stream.toList() and Collectors.toList()?

30-second answerStream.toList() (Java 16) returns an unmodifiable list: add, remove, set and sort throw UnsupportedOperationException. It does allow null elements. Collectors.toList() returns a list whose type and mutability are unspecified; in practice an ArrayList. Collectors.toUnmodifiableList() (Java 10) is unmodifiable and rejects nulls.

Go deeper: The production risk is the IDE quick fix that swaps collect(Collectors.toList()) for toList(). It compiles, and a caller that mutates the list then fails at run time. If a mutable list is needed, say so with toCollection(ArrayList::new). And Collectors.toList() is still needed as a downstream collector inside groupingBy, because Stream.toList() is a terminal operation, not a collector.

Q11

What can go wrong with Collectors.toMap?

30-second answerTwo run-time failures. A duplicate key throws IllegalStateException — "Duplicate key a (attempted merging values 5 and 7)" — unless you pass a merge function. A null value throws NullPointerException, even though HashMap allows nulls. Neither shows up with tidy test data, which is why toMap is such a common cause of production errors.

Go deeper: Walk the overloads. toMap(k, v, merge) resolves collisions: Double::sum, (a, b) -> a, BinaryOperator.maxBy(cmp). toMap(k, v, merge, mapFactory) chooses the map: LinkedHashMap::new, TreeMap::new. If one key can have several values, the answer was groupingBy. For legitimate null values, filter them out or use the three-argument collect with HashMap::put. toUnmodifiableMap and toConcurrentMap behave the same on duplicates.

Q12

What is the difference between groupingBy and partitioningBy?

30-second answergroupingBy(classifier) builds a Map<K, List<T>> with one entry per key that actually occurs. partitioningBy(predicate) builds a Map<Boolean, List<T>> that always has both true and false, even for empty input. Both take a downstream collector — counting(), mapping(…), summingDouble(…) — to reduce each group.

Go deeper: Show the practical difference. With groupingBy(o -> o.total() > 500), get(true) is null when no order is large; partitioningBy never returns null there. groupingBy also has a map-factory overload (TreeMap::new for sorted keys) and a concurrent variant, and a null key throws "element cannot be mapped to a null key". Mention filtering (Java 9) for keeping empty groups, and nested grouping such as customer, then status, then orders.
