The two operations that have to remember

distinct drops repeats using equals and hashCode. sorted orders by natural order or a comparator. Both are stateful, and both lean on contracts in your own classes that the compiler never checks.

Outputs on JDK 25
Stream.of("b", "a", "b", "c", "a").distinct().toList();
// [b, a, c]: the first occurrence of each, in order

orders.stream()
      .sorted(Comparator.comparing(Order::customer)
                        .thenComparing(Order::total, Comparator.reverseOrder()))
      .toList();                   // by customer, then biggest order first

Stream.of("bb", "a", "cc", "d")
      .sorted(Comparator.comparingInt(String::length))
      .toList();
// [a, d, bb, cc]: stable, so ties keep their input order

// There is no distinctBy. Keep the first order per customer:
Collection<Order> firstPerCustomer = orders.stream()
        .collect(Collectors.toMap(Order::customer, o -> o,
                                  (first, later) -> first, LinkedHashMap::new))
        .values();
MistakeWhat happens
sorted() on a class that is not ComparableClassCastException at run time, when the terminal operation runs: "cannot be cast to class java.lang.Comparable"
distinct() on a class without equals/hashCodeNothing is removed: identity equality treats every object as distinct. Records get this right by construction
sorted(c).findFirst()O(n log n) and O(n) memory for what min(c) does in one pass with no buffer
(a, b) -> a.qty() - b.qty()Overflows for large or mixed-sign values and mis-sorts silently
Mutating fields that hashCode reads, mid-streamdistinct misses duplicates; results are undefined
sorted() then parallel forEachThe sort is correct and then ignored: forEach does not respect order
Comparators are their own slidecomparing, thenComparing, reversed, nullsFirst and the reversed() type-inference trap are on Method references and Comparator combinators.
