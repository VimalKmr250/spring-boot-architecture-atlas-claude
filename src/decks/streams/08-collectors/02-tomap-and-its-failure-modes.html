toMap builds a map, and throws on data you did not expect

toMap(keyMapper, valueMapper) looks like the simplest collector and causes more production exceptions than any other. It fails on a duplicate key and on a null value, and clean test data triggers neither.

Every form, and the exact exception on JDK 25
// Two words with the same first letter: the key collides
Stream.of("apple", "avocado")
      .collect(Collectors.toMap(w -> w.charAt(0), String::length));
// IllegalStateException: Duplicate key a (attempted merging values 5 and 7)

// Decide what a duplicate means: here, add the totals
Map<String, Double> spendByCustomer = orders.stream()
        .collect(Collectors.toMap(Order::customer, Order::total, Double::sum));

// Keep the latest order per customer, in a sorted map
TreeMap<String, Order> latest = orders.stream()
        .collect(Collectors.toMap(Order::customer, o -> o,
                                  (older, newer) -> newer, TreeMap::new));

// Null values fail in every form, although HashMap accepts them
orders.stream().collect(Collectors.toMap(Order::id, Order::status));
// NullPointerException, on the first order whose status is null

// If null values are legitimate, collect by hand
Map<String, String> statusById = orders.stream()
        .collect(HashMap::new, (m, o) -> m.put(o.id(), o.status()), HashMap::putAll);

Why it passes every testTest fixtures have one order per customer, so the key is unique. Production has a customer who ordered twice, and the endpoint returns a 500. Whenever the key comes from data rather than from a primary key, write the merge function, even if it is only (a, b) -> a, because writing it forces you to decide.
Often it was a grouping all alongIf one key can legitimately have several values, the target type is a Map<K, List<V>>, and the collector is groupingBy, on the next slides. A merge function that concatenates lists is a hand-written groupingBy.
