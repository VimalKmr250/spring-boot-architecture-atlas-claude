Elements travel down the pipeline one at a time

The obvious mental model is wrong. A stream does not filter the whole list, then map the whole list, then collect. It takes one element and pushes it through every stage as far as it goes, then takes the next. That one fact explains laziness and short-circuiting, and it is why sorted() costs what it does. Vertical, not horizontal

In pipeline 2, filter and map take turns: fig is dropped before kiwi is even read. No list of filtered elements exists at any point, which is why a stream over a million rows needs no more memory than a stream over ten.

Pulled by the terminal operation

Nothing runs until the terminal operation starts asking for elements. In pipeline 1, apple, plum and cherry are never read, because findFirst() had its answer after two pulls. Pipeline 4 does the same with an infinite source.

A barrier breaks the flow

sorted() cannot release anything until it has seen everything. In pipeline 3, filter runs on all five words before map runs once. After the barrier, laziness resumes: limit(2) stops map after two calls. Pipeline 5 shows what a barrier does to an infinite stream.

Pipeline 1 with print statements, on JDK 25
Stream.of("fig", "kiwi", "apple", "plum", "cherry")
      .filter(s -> { System.out.println("filter " + s); return s.length() > 3; })
      .map(s -> { System.out.println("map " + s); return s.toUpperCase(); })
      .findFirst();

"Why didn't my peek print?"Usually because nothing pulled. Without a terminal operation a pipeline is only a description, so list.stream().peek(System.out::println) prints nothing at all. Since Java 9 even a terminal operation can skip it. count() on a source whose size is known, such as a List (and still known after map), returns the size without reading a single element, so a peek in front of it never runs. Put a filter in between and the size becomes unknown, so every element flows again.
