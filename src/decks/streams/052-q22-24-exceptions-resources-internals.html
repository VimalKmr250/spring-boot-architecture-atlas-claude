Exceptions, resources, and the machinery underneath

Senior rounds reach these. Each is a question about what the API does not do for you: handle checked exceptions, close resources, or explain itself.

Q22

How do you handle checked exceptions inside a stream?

30-second answerThe functional interfaces declare no checked exceptions, so a lambda that calls a method throwing IOException does not compile. The options: catch it inside the lambda and rethrow an unchecked exception such as UncheckedIOException, ideally in a named helper method; return failures as data, such as a result record, and partition them afterwards; or use a plain loop, which is often the clearest.

Go deeper: Discuss the trade-offs. Wrapping aborts the pipeline at the first failure, and callers must know to catch the unchecked type. Failures as data keep going and report every failure. "Sneaky throw" tricks hide the checked exception from the compiler, so nobody is forced to handle it: avoid them. An exception thrown in any stage surfaces from the terminal operation, on the caller's thread, even for parallel streams.

Q23

Do streams need to be closed?

30-second answerMost do not: streams over collections, arrays and generators hold no resources. Streams backed by I/O do: Files.lines, Files.list, Files.walk, and anything built over a reader or a database cursor. Stream is AutoCloseable, and terminal operations do not close it, so use try-with-resources, or the service leaks file handles until it fails with "Too many open files".

Go deeper: close() runs the handlers registered with onClose, in order. All of them run even if one throws; the first exception propagates and the rest are attached as suppressed. Closing a concat-ed stream closes both inputs. The same rule applies to Spring's JdbcTemplate.queryForStream and to repository methods that return a Stream: they hold a connection and a cursor. Using a stream after close() throws IllegalStateException.

Q24

How do streams work internally? What is a Spliterator?

30-second answerEach intermediate call creates a pipeline stage linked to the previous one, and nothing runs. The terminal operation wraps the stages into a chain of Sinks and pushes elements through that chain one at a time, from the source's Spliterator. A spliterator is a "splittable iterator", with tryAdvance, forEachRemaining, trySplit and characteristics. When the pipeline can short-circuit, the loop checks for cancellation before each element.

Go deeper: The characteristics let the library optimise. SIZED lets count() skip traversal. SORTED makes a later natural-order sorted() do nothing, and DISTINCT does the same for distinct(). SUBSIZED gives even parallel splits. Stateful stages buffer inside their sink until end() is called. To stream a custom data structure, write a Spliterator and pass it to StreamSupport.stream(spliterator, parallel).
