Offsets: when you commit decides what you lose

Four strategies. The dangerous one is the raw client's default — Spring's container quietly saves you from it, which is worth knowing precisely, because the answer to "what happens if I crash mid-batch?" depends on which of these you are actually running.

Auto-commit — raw client default

enable.auto.commit: true
auto.commit.interval.ms: 5000

Commits on a timer, during poll(), regardless of whether your handler succeeded. A crash after the commit but before processing loses those records permanently.

Acceptable only for telemetry where loss is cheaper than complexity — and you will not get this by accident in Spring: since spring-kafka 2.3 the listener container sets it to false unless you explicitly ask for true.

BATCH — what Spring actually gives you

# nothing to configure — this is the container default
ack-mode: BATCH

Offsets for the whole poll are committed after every record in it has been handled. No timer, so nothing is acknowledged before it was processed.

Fine for most consumers. The gap: fail on record 400 of 500 and the poll's offsets are not committed, so all 500 are redelivered — which is correct, and is why the handler must be idempotent.

RECORD — commit per message

ack-mode: RECORD

The container commits after each record returns. Narrowest redelivery window, and the most commit traffic — at volume it can dominate your processing time.

Use when each message is expensive and irreplaceable, so the commit cost is noise.

MANUAL_IMMEDIATE — you decide

enable.auto.commit: false
ack-mode: MANUAL_IMMEDIATE

You take an Acknowledgment and call it once the work has committed. Same guarantee as RECORD, but you choose the moment — which is what lets you ack a duplicate early and skip the work.

The choice for anything that matters, because the acknowledgement point becomes explicit in the code rather than implicit in a property.

Order of operations — the part that actually provides the guarantee
@KafkaListener(topics = "orders.order.placed.v1", groupId = "inventory")
public void on(OrderPlaced e, Acknowledgment ack) {
    inventory.reserve(e);       // 1. do the work; its transaction commits
    ack.acknowledge();          // 2. only then record that we handled it
}
// Crash between 1 and 2 → the record is redelivered → the idempotency
// guard makes the second attempt a no-op. That is the whole contract.

// Reset a group deliberately (offline, group must be inactive):
// kafka-consumer-groups.sh --reset-offsets --group inventory \
//   --topic orders.order.placed.v1 --to-datetime 2026-09-15T00:00:00.000 --execute
auto.offset.reset is only used when there is no committed offsetA brand-new group, or one whose offsets expired. latest (the default) silently skips everything already on the topic — which is why a newly deployed consumer can appear to work while processing nothing. earliest replays all history, which can be a stampede. Choose it deliberately per consumer, and know which you have.
Offsets are not a bookmark you ownThey live in __consumer_offsets with their own retention (offsets.retention.minutes, seven days by default). A group that is down longer than that loses its position and falls back to auto.offset.reset — a genuinely nasty surprise after a long outage or a holiday shutdown.
