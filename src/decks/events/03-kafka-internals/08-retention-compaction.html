Retention, compaction and tiered storage

How long data lives is a design decision per topic, not an infrastructure default. Compaction in particular turns a topic into something quite different — a changelog you can rebuild state from.

Deletion by time or size — the normal case
cleanup.policy: delete
retention.ms: 604800000        # 7 days
retention.bytes: -1            # unlimited, or cap per partition
segment.ms: 86400000           # roll a new segment daily
# Retention is enforced per SEGMENT, and the active segment is never deleted —
# so actual retention is always a little longer than configured.
Compaction — keep the latest value per key, forever
cleanup.policy: compact
min.cleanable.dirty.ratio: 0.5
delete.retention.ms: 86400000  # how long tombstones survive
# The log becomes a snapshot: every key's most recent value is retained.
# Publishing a null value is a TOMBSTONE — it marks the key deleted.

cleanup.policy: compact,delete  # both: compact, and also drop very old records

What compaction is for

Reference data
A products topic where the latest record per SKU is the current product. A new consumer reads from the start and has the full catalogue.
Changelogs
Kafka Streams state stores back themselves with a compacted topic — that is how a stateful processor rebuilds after a restart.
Materialising state
Any "current state per entity" feed where history is not needed.

Compacted topics must be keyed. An unkeyed compacted topic retains everything and quietly does nothing.

Compaction is not immediate and not a guaranteeThe cleaner runs in the background on non-active segments, so duplicates for a key exist for a while. A consumer reading from the start may see two versions of a key — it must apply them in order and end at the right value, which it will, since order within a partition holds.
Tiered storage changes the retention conversationGA since Kafka 3.9: older segments move to object storage, so months of retention no longer means months of expensive broker disk. It makes long replay windows affordable, but reading cold data is slower — plan a backfill to take longer than a recent replay.
