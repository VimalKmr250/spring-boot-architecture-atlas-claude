Relaying the outbox: polling or CDC

Two implementations of the same pattern with very different operational profiles. Most teams should start with polling and move to CDC when volume or latency justifies a Kafka Connect cluster.

Polling relay — simple, no extra infrastructure
CREATE TABLE outbox (
  id            bigserial PRIMARY KEY,
  aggregate_type text NOT NULL,          -- 'order'
  aggregate_id   text NOT NULL,          -- '88421'  → becomes the Kafka key
  event_type     text NOT NULL,          -- 'OrderPlaced'
  payload        jsonb NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now(),
  sent_at        timestamptz             -- null = not yet published
);
CREATE INDEX ON outbox (created_at) WHERE sent_at IS NULL;   -- partial: stays tiny
@Scheduled(fixedDelay = 200)
@Transactional
void relay() {
    // LIMIT comes BEFORE the locking clause — Postgres rejects the
    // other order. FOR UPDATE SKIP LOCKED makes this safe on N pods.
    var batch = jdbc.sql("""
        SELECT * FROM outbox WHERE sent_at IS NULL
        ORDER BY id
        LIMIT 200
        FOR UPDATE SKIP LOCKED
        """).query(OutboxRow.class).list();

    for (var row : batch) {
        kafka.send(topicFor(row), row.aggregateId(), row.payload());
    }
    kafka.flush();                              // confirm before marking
    jdbc.sql("UPDATE outbox SET sent_at = now() WHERE id = ANY(?)")
        .param(batch.stream().map(OutboxRow::id).toArray(Long[]::new))
        .update();                              // ANY(?) needs an ARRAY, not a List
}
Yes, this holds a transaction across a network callEverywhere else in this atlas the rule is "never call an external system inside @Transactional". The relay is the deliberate exception: the rows are locked with SKIP LOCKED so no other pod blocks on them, the batch is bounded, and the send has a delivery.timeout.ms that caps how long the transaction can live. Keep the batch small, keep the timeout short, and size the relay's pool separately from the request pool — then one slow broker delays events instead of exhausting the connections checkout needs.

The CDC failure everyone learns onceA replication slot that stops being consumed prevents PostgreSQL from recycling WAL segments. The disk fills, and the primary stops accepting writes. Alert on replication slot lag from the first day you create one, and have a documented decision about when to drop the slot to save the database.
Either way, watch the age of the oldest unsent rowOne metric — max(now() - created_at) where sent_at is null — tells you the whole health of your event pipeline. It is the best early warning in an event-driven system, and it costs one query.
