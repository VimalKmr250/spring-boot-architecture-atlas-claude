Eventual consistency is a product decision

The moment a write becomes asynchronous, a user can act on a screen that is out of date. That is not a bug to be engineered away — it is a behaviour the product must define, and engineering alone cannot decide it.

SituationWhat the user should see
Order placed, payment pending"Order received — we'll confirm payment shortly", with the order visible in their history immediately
Address changed, projection laggingThe new address, read from the write model for this user for a short window
Stock shown while browsing"12 in stock" with an as-of tolerance; never a promise
Stock at checkoutStrongly consistent — read and reserve, no cache, no projection
Refund issued"Refund issued — 3–5 days to appear" — the delay is real and the user already expects it
Search index behindAcceptable silently; users do not know what was indexed a second ago

Three techniques that absorb the lag

Read-your-writes
After a write, pin that user's reads to the write model for a few seconds (a flag in the session or a Redis key). Removes an entire category of support ticket for about five lines of code.
Optimistic UI
Show the result immediately, reconcile when the event lands, and have a defined behaviour for when it does not.
Explicit pending state
Model it in the domain — PAYMENT_PENDING is a real state with real rules, not a gap between two states.
The conversation to have earlyAsk the product owner: "if this is thirty seconds out of date, what does the customer do?" Sometimes the answer is "nothing, they wouldn't notice". Sometimes it is "they order the same thing twice and we lose money". The second answer is a requirement for synchronous handling, and it is far cheaper to hear it in design than in a post-incident review.
Bound the lag, then alert on it"Eventually" is not a specification. "The order-history projection is within 5 seconds at p99" is — it can be measured, alerted on, and put in a contract. Every projection in a serious system should have a stated staleness budget.
