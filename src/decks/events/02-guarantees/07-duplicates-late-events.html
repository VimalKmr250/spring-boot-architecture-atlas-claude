Duplicates, out-of-order and late events

Three distinct problems that get conflated. Each has a different fix, and a consumer that handles all three is what "robust" actually means in an event-driven system.

Duplicate

Same event, twice. Caused by producer retries, consumer rebalances, redeploys mid-batch, replay.

Fix: idempotent handler, keyed on a business key or the event id. Covered two slides back.

Frequency: constant. Design for it always.

Out-of-order

Event B applied before event A. Caused by no key, repartitioning, a retry topic, or concurrent handlers.

Fix: carry a monotonic version or business timestamp; ignore anything not newer than what you have applied.

Frequency: occasional, and always at the worst moment.

Late

Correctly ordered, but hours behind — a consumer was down, a DLT was replayed, an upstream backlog cleared.

Fix: decide the business rule. Apply it anyway? Ignore beyond a window? Route to manual review?

Frequency: after every incident.

A consumer that survives all three
@KafkaListener(topics = "orders.order.statuschanged.v1", groupId = "projection")
@Transactional
public void on(OrderStatusChanged e, Acknowledgment ack) {

    var view = projections.findById(e.orderId()).orElseGet(() -> OrderView.empty(e.orderId()));

    // out-of-order + duplicate in one guard
    if (e.aggregateVersion() <= view.appliedVersion()) {
        meters.counter("events.stale", "type", e.type()).increment();
        ack.acknowledge();
        return;
    }

    // late: a business decision, not a technical one
    if (Duration.between(e.occurredAt(), Instant.now()).toHours() > 24) {
        lateEvents.quarantine(e);            // human review, do not silently apply
        ack.acknowledge();
        return;
    }

    view.apply(e);
    view.setAppliedVersion(e.aggregateVersion());
    projections.save(view);
    ack.acknowledge();
}
Measure staleness, not just lagConsumer lag counts messages. The number that matters is now() - event.occurredAt at the point of processing — actual end-to-end latency, including time spent in retries and upstream queues. Publish it as a histogram; it is the SLI your product owner would recognise.
Gaps are the fourth problemNot a missing duplicate but a genuinely missing event — dropped before the outbox, or lost in a mis-handled DLT. No consumer-side pattern detects this. Only reconciliation does: a periodic job comparing source-of-truth counts and totals against each projection. Every serious event-driven system has one.
