Shipping a breaking schema change

Sooner or later a change is genuinely incompatible. The playbook is expand/contract again — the same shape as a database migration, run across consumers you may not control.

PhaseProducerConsumersDuration
0 · MeasureList every consumer group on the topic; contact the owners—Before anything else
1 · ExpandAdd the new field alongside the old; populate bothUnchanged — the schema is still compatibleOne release
2 · MigrateUnchangedEach consumer switches to the new field on its own scheduleWeeks — the long pole
3 · VerifyMetric: is anyone still reading the old field?—Until the metric is zero
4 · ContractStop populating the old field, then remove itUnaffected — nobody reads itOne release

When expand/contract is impossible

A change to the meaning of the topic itself — different granularity, a different key, a fundamentally different shape. Then it is a new topic:

  1. Create orders.order.placed.v2.
  2. Dual-publish to v1 and v2 from the same transaction.
  3. Consumers migrate one at a time and confirm.
  4. Monitor v1 consumer groups until none remain active.
  5. Announce a sunset date, stop publishing v1, delete it later.

The version in the topic name is what makes this routine instead of a coordinated outage.

What not to doChange the schema, tell people in a chat channel, deploy on Friday. The consumers you know about will cope; the batch job that runs monthly and the partner integration nobody documented will fail silently, and you will hear about it in three weeks from a finance reconciliation.
The metric that makes step 3 possibleMonitor active consumer groups per topic and per schema version. Without it, "has everyone migrated?" is answered by asking around, which means v1 is never retired and you maintain both forever.
Dual-publish from one transactionBoth records go into the same outbox transaction, so v1 and v2 can never diverge. Publishing v2 from a separate job that reads v1 introduces lag and a second failure mode at exactly the moment you need confidence.
