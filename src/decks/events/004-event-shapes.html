Three event shapes — thin, fat, and delta

The single most consequential design choice per topic. It decides whether consumers can work independently, how much your payloads cost, and how badly a schema change hurts.

1 · Notification (thin) — "something happened, go look"
{ "eventId": "9c1f…", "type": "OrderPlaced", "orderId": "88421",
  "occurredAt": "2026-09-16T01:12:04Z" }
2 · Event-carried state transfer (fat) — "here is what it looks like now"
{ "eventId": "9c1f…", "type": "OrderPlaced", "version": 1,
  "orderId": "88421", "customerId": "c-4410",
  "lines": [ { "sku": "SKU-8842", "qty": 2, "unitMinor": 1999 } ],
  "totalMinor": 3998, "currency": "GBP",
  "shipTo": { "country": "GB", "postcode": "EC2…" },
  "occurredAt": "2026-09-16T01:12:04Z" }
3 · Delta — "this is what changed"
{ "eventId": "a71b…", "type": "OrderAddressChanged", "orderId": "88421",
  "changed": { "shipTo.postcode": { "from": "EC2A 1AA", "to": "EC1V 9BW" } } }

Which to choose

Thin
Small, stable, leaks nothing. But every consumer calls back to the producer — so the producer's availability and rate limits become everyone's problem, and you have reinvented request-response with extra steps.
Fat
The enterprise default. Consumers are genuinely independent and can be replayed. Costs payload size, and the schema is now a contract with people you cannot name.
Delta
Compact and precise, but consumers must have seen every prior event to make sense of it — ordering and completeness become mandatory rather than desirable.
The fat-event taxEverything in the payload is now a published contract. Put a field in because one consumer asked, and you can never remove it. Publish only what the event means, not a database row dump — and never include fields a consumer should not see: a fat event is a data-sharing decision as much as a technical one.
The hybrid that worksFat event with the fields consumers actually need, plus a self link for the full resource. Common consumers stay independent; the rare one that needs everything can fetch it.
