When a consumer throws: retry, then get out of the way

The default behaviour of a Kafka consumer that keeps failing is to block its partition forever. Everything in this slide exists to stop that.

The error handler every consumer application needs
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {

    // Where a record goes when retries are exhausted: the .DLT suffix.
    // Partition -1 lets the producer choose. Pinning record.partition()
    // (the tempting version, and Spring's own default) throws the moment
    // the DLT has fewer partitions than the source topic — which is the
    // normal case, because nobody provisions a DLT with 24 partitions.
    var recoverer = new DeadLetterPublishingRecoverer(template,
        (record, ex) -> new TopicPartition(record.topic() + ".DLT", -1));

    var handler = new DefaultErrorHandler(recoverer,
        new ExponentialBackOffWithMaxRetries(3));      // 3 attempts, then DLT

    // A poison pill never gets better — do not waste three attempts on it
    handler.addNotRetryableExceptions(
        DeserializationException.class,
        MethodArgumentNotValidException.class,
        IllegalArgumentException.class);

    // Transient problems that deserve every retry
    handler.addRetryableExceptions(
        TransientDataAccessException.class,
        ResourceAccessException.class);

    handler.setRetryListeners((record, ex, attempt) ->
        meters.counter("consumer.retry", "topic", record.topic(),
                       "attempt", String.valueOf(attempt)).increment());
    return handler;
}

What the DLT record carries

Spring adds headers to every dead-lettered record: original topic, partition, offset and timestamp, the exception class, message and stack trace, and the attempt count.

That is what makes a DLT actionable rather than a graveyard — you can see why each record failed without reproducing it.

kafka_dlt-original-topic       orders.order.placed.v1
kafka_dlt-original-partition   3
kafka_dlt-original-offset      918224
kafka_dlt-exception-fqcn       com.retailco…InsufficientStock
kafka_dlt-exception-message    Only 2 left of SKU-8842
Blocking retries block the partitionThe default handler retries in place, pausing the consumer. Three attempts with exponential backoff on a record that will never succeed stalls every record behind it on that partition — a head-of-line block that looks like a dead consumer. This is why bounded retries plus a DLT is non-negotiable, and why the next slide exists.
A DLT with no owner is data loss with extra stepsAlert on DLT depth greater than zero. Route it to the team that owns the consumer, not to the platform team. And have a documented, tested replay path — a DLT nobody drains is a queue of business events quietly not happening.
Classify errors deliberatelyTransient (network, deadlock, 503) → retry. Poison (malformed, schema mismatch) → straight to DLT. Business (insufficient stock) → often not an error at all: emit a compensating event and acknowledge. Treating the third as a technical failure is how DLTs fill with perfectly normal outcomes.
