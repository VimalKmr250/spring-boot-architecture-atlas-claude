Producing from Spring, with the failure handled

send() returns a future. Ignoring it is the single most common way to lose events in a Spring application, because nothing fails visibly — the code looks correct and the record never arrives.

order/internal/kafka/OrderEventPublisher.java
@Component
class OrderEventPublisher {

    private final KafkaTemplate<String, OrderPlaced> kafka;
    private final MeterRegistry meters;

    void publish(OrderPlaced event) {
        var record = new ProducerRecord<>(
                "orders.order.placed.v1",
                null,                                   // let the partitioner decide
                event.orderId(),                        // KEY — gives per-order ordering
                event);
        record.headers()
              .add("eventId",   event.eventId().getBytes(UTF_8))
              .add("eventType", "OrderPlaced".getBytes(UTF_8))
              .add("version",   "1".getBytes(UTF_8));   // routing and dedupe without
                                                        // deserialising the payload
        kafka.send(record).whenComplete((result, ex) -> {
            if (ex != null) {
                meters.counter("events.publish.failed", "topic", record.topic()).increment();
                log.error("publish failed for order {}", event.orderId(), ex);
                outbox.markUnsent(event.eventId());     // it stays in the outbox, retried
            } else {
                var md = result.getRecordMetadata();
                log.debug("published {} to {}-{}@{}", event.eventId(),
                          md.topic(), md.partition(), md.offset());
            }
        });
    }
}
The silent losskafka.send(topic, key, event); with no callback. The broker is down, the buffer fills, the send eventually times out — and your code has long since returned 201 to the customer. Nothing in the logs says an order was never published.
Headers earn their keepPut eventId, eventType, version and the tracing context in headers. A consumer can then route, dedupe and filter without deserialising the payload — which matters when it is a 4 KB Avro record it may not even want.
Do not publish inside a database transactionA send from within @Transactional either happens before the commit (publishing something that may roll back) or blocks the transaction on a network call. This is the dual-write problem — use the outbox, and let this publisher be the relay rather than the business code.
