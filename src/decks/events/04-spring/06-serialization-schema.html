Serialization and the schema registry

The payload format is a contract with consumers you cannot name. A registry turns "please don't break it" into a rule the deploy enforces.

Avro with a registry, in Spring
spring.kafka:
  producer:
    value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
    properties:
      schema.registry.url: https://schema-registry.internal
      auto.register.schemas: false      # register via CI, not from production code
      use.latest.version: true
  consumer:
    value-deserializer: io.confluent.kafka.serializers.KafkaAvroDeserializer
    properties:
      specific.avro.reader: true

Compatibility modes — pick per topic

BACKWARD
New schema reads old data. The usual choice: consumers upgrade first, producers follow.
FORWARD
Old schema reads new data. Producers upgrade first — right when you cannot coordinate consumer upgrades.
FULL
Both. Safest, most restrictive: only optional fields with defaults may be added or removed.
NONE
No checks. Equivalent to having no registry, with the operational cost of having one.
auto.register.schemas must be false in productionOtherwise the first producer to start quietly registers whatever schema it happens to have — including a broken one from a bad build — and the compatibility gate never fires. Register schemas from the pipeline, where a failed check blocks the deploy.
The rule that makes evolution painlessEvery new field is optional with a default. Never remove or rename a required field; never change a type. Both are then compatible in both directions, and you will almost never need a v2 topic.
