Kafka transactions: read-process-write, atomically

The genuine exactly-once story, and its exact boundary. Worth knowing precisely because it is asked constantly and answered loosely.

In Spring: it is the property, not an annotation
spring.kafka:
  producer.transaction-id-prefix: order-enricher-   # ← this is the switch
  consumer.isolation-level: read_committed
// Setting the prefix auto-configures a KafkaTransactionManager AND hands
// it to the listener container. The CONTAINER then opens the transaction
// around the poll and calls sendOffsetsToTransaction() at the end — which
// is the part that makes consume+produce+commit atomic.
//
// So no @Transactional here. Adding it starts a SECOND, nested Kafka
// transaction around the container's one and buys nothing.
@KafkaListener(topics = "orders.order.placed.v1", groupId = "enricher")
public void enrich(OrderPlaced in) {
    kafka.send("orders.order.enriched.v1", in.orderId(), enrich(in));
}

// @Transactional on a listener is for the OTHER resource — a JPA write —
// and that is a different transaction manager, with the caveat opposite.
The "chained transaction" temptationSpring can chain a Kafka transaction and a JPA transaction so they commit together. It is not atomic — it is two commits in sequence, and a crash between them leaves them inconsistent. It narrows the window; it does not close it.

For a database write plus an event, the honest answer remains the outbox. Reach for Kafka transactions when both sides are Kafka.
