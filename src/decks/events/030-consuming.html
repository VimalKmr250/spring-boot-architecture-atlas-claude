@KafkaListener in depth

The annotation is small; the container behind it has about thirty settings that matter. These are the ones that change behaviour rather than performance.

Three listener shapes, and what each is for
// 1. Record listener — the default. One message, one method call.
@KafkaListener(topics = "orders.order.placed.v1", groupId = "inventory",
               concurrency = "6")                 // 6 threads, ≤ partition count
public void onOrder(@Payload OrderPlaced event,
                    @Header(KafkaHeaders.RECEIVED_KEY) String key,
                    @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                    @Header(KafkaHeaders.OFFSET) long offset,
                    @Header(name = "eventId", required = false) String eventId,
                    Acknowledgment ack) {
    inventory.reserve(event);
    ack.acknowledge();
}

// 2. Batch listener — for bulk database writes; far higher throughput
@KafkaListener(topics = "orders.order.placed.v1", groupId = "projection",
               containerFactory = "batchFactory")
public void onBatch(List<OrderPlaced> events, Acknowledgment ack) {
    projections.upsertAll(events);                // ONE round trip instead of 500
    ack.acknowledge();                            // commits the whole batch
}

// 3. Explicit partition assignment — no group, no rebalancing
@KafkaListener(topicPartitions = @TopicPartition(topic = "orders.order.placed.v1",
                partitionOffsets = @PartitionOffset(partition = "0", initialOffset = "0")))
public void replayPartitionZero(OrderPlaced event) { ... }

concurrency is per listener

It creates that many consumers in the group from this application. Six pods × concurrency 6 = 36 consumers; with 12 partitions, 24 of them idle. Set it to partitions / expected pods, not to a number that feels fast.

Batch listeners change error handling

A failure in the middle of a batch means the whole batch is retried, so every handler must be idempotent at batch granularity. BatchListenerFailedException lets you tell the error handler which record failed so only that one goes to the DLT.

Do not fan out to a thread pool

Handing records to an executor inside the listener destroys ordering and breaks the offset contract — you acknowledge work that has not happened. Use concurrency, which parallelises by partition and keeps both properties.
