The order saga, fully specified

The architecture deck introduced sagas; this is what the implementation actually needs. Four things turn a saga from a diagram into something operable: persisted state, timeouts, compensation, and a way to see where it is stuck.

Every state has a timeout and a terminal path. A saga with a state that can be entered and never left is how orders sit in limbo for eleven days.

The saga as a persisted entity, driven by events
@Entity
class OrderSaga {
    @Id UUID orderId;
    @Enumerated(STRING) SagaState state;
    Instant enteredStateAt;
    Instant timeoutAt;                 // set on every transition
    String  failureReason;
    @Version long version;             // concurrent events on one saga
}

@Component
class OrderSagaHandler {

    @KafkaListener(topics = "inventory.stock.reserved.v1", groupId = "order-saga")
    @Transactional
    void onStockReserved(StockReserved e, Acknowledgment ack) {
        var saga = sagas.findById(e.orderId()).orElseThrow();
        if (saga.state() != AWAITING_STOCK) { ack.acknowledge(); return; }  // idempotent
        saga.transitionTo(AWAITING_PAYMENT, Duration.ofSeconds(60));
        commands.send(new AuthorisePayment(e.orderId(), saga.totalMinor()));
        ack.acknowledge();
    }

    @Scheduled(fixedDelay = 5000)      // the timeout sweeper — the piece people omit
    @Transactional
    void sweepTimeouts() {
        sagas.findExpired(Instant.now()).forEach(saga -> {
            meters.counter("saga.timeout", "state", saga.state().name()).increment();
            saga.compensate();          // or escalate to MANUAL_REVIEW
        });
    }
}
Three things that make a saga operableA query: "show me every saga not in a terminal state older than an hour" — that is your daily operations report. A metric per state, so a rising AWAITING_PAYMENT count alerts before customers call. A manual path: some sagas will need a human, and designing MANUAL_REVIEW as a real state beats discovering that stuck orders have nowhere to go.
