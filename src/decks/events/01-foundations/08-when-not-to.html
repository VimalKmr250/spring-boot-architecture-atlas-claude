When not to go event-driven

The honest version of this list is what separates someone who has run an event-driven system from someone who has read about one.

Do not use events when…

  • The caller needs the answer now. "Is this card authorised?" is a synchronous question. Making it async means inventing a pending state the whole product must handle.
  • You need a strong read-your-own-writes guarantee and the UI cannot express "processing".
  • There is exactly one consumer, forever, and it is owned by the same team. You have added a broker and gained decoupling from yourself.
  • The team has no operational capacity for a broker — Kafka is a distributed system that needs owners, upgrades and on-call.
  • Ordering across entities is a business requirement. Kafka orders within a partition only; global ordering means one partition, which means no parallelism.
  • You are using it to avoid fixing a boundary. Events between two modules that share a database is decoupling theatre.

The costs, stated plainly

Debugging
A bug spans four services and a queue. Without end-to-end tracing you are reading four log files by timestamp.
Testing
You cannot unit-test a topology. You need contract tests, Testcontainers, and discipline about what each level proves.
Consistency
Every screen must handle "not yet". Product and design have to be part of this decision, not told afterwards.
Operations
Lag, DLTs, rebalances, disk, retention, schema compatibility, replay. All new work that did not exist before.
Cognitive load
New joiners must learn the topology, not just the codebase.
The proportionate defaultSynchronous calls inside the request path for what must succeed now; events for everything that reacts. That is the rule from the architecture deck, and for most enterprise systems it is the whole of the event-driven architecture they need. Reach for the full toolkit — streams, projections, event mesh — when you have a specific problem it solves.
