State stores, joins and windows

The three capabilities that justify Streams, and the operational consequences each one brings.

The state store, and how it survives

Each task keeps a local RocksDB store on disk. Every write also goes to a compacted changelog topic in Kafka.

On restart or reassignment, the task rebuilds its store by replaying that changelog — which for a large store can take minutes. num.standby.replicas: 1 keeps a warm copy on another instance so failover is fast instead of slow.

This is the operational cost people underestimate: a stateful Streams app needs disk, and a rebalance is not free.

Enrich orders with customer data — no service call
KTable<String, Customer> customers =
    builder.table("customers.customer.snapshot.v1");      // compacted topic

KStream<String, OrderPlaced> orders = builder.stream("orders.order.placed.v1");

orders.selectKey((k, o) -> o.customerId())
      .join(customers, OrderEnricher::withCustomer)       // local lookup, microseconds
      .to("orders.order.enriched.v1");

// Windowed: 5 failed payments from one card in 10 minutes
payments.filter((k, p) -> p.declined())
        .groupBy((k, p) -> p.cardFingerprint())
        .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(10), Duration.ofMinutes(2)))
        .count()
        .filter((windowedKey, count) -> count >= 5)
        .toStream()
        .to("risk.card.velocity.v1");
Event time, not wall-clock timeWindows are driven by the record's timestamp, so a replay produces the same results as the original run — which is the property that makes Streams reproducible. Set timestampExtractor to read your business occurredAt, not the broker's ingestion time, or a backlog will land everything in one window.
Grace period and late recordsA window closes after its grace period; records arriving later are dropped and counted in dropped-records. Pick the grace from real observed lateness and alert on that metric — silently dropped records in a risk calculation is exactly the failure nobody notices.
Co-partitioning is a hard requirementA KStream–KTable join needs both topics keyed the same way with the same partition count, or Streams fails at startup. A GlobalKTable avoids this by replicating everything to every instance — fine for a few hundred thousand reference rows, not for a customer table with fifty million.
