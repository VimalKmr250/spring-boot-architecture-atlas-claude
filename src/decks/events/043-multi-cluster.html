More than one cluster: why, and how they connect

A second cluster is never free — it doubles the operational surface and introduces offsets that do not translate. There are four reasons that justify it, and "we have a lot of topics" is not one.

What MirrorMaker 2 actually does

Runs on Kafka Connect. Copies records, topic configuration and ACLs from source to target, and — critically — maintains a checkpoint topic that maps source offsets to target offsets per consumer group.

By default it prefixes replicated topics with the source cluster alias (eu.orders.order.placed.v1), which is how it avoids replication cycles in an active-active setup. IdentityReplicationPolicy keeps the original names for a simple DR topology.

Replication is asynchronous. There is no cross-cluster ordering guarantee and no exactly-once across the bridge.

Offsets do not transferOffset 918,224 on the source is a different record on the target. Failing over means translating offsets from the checkpoint topic — and the translation is approximate, so a consumer restarted on the DR cluster will reprocess some records. Idempotent consumers are what make failover survivable, which is one more reason they are not optional.
Stretch cluster as the alternativeOne logical cluster spanning three availability zones in the same region, with rack-aware replica placement. You get automatic failover and no offset translation, at the cost of cross-AZ latency on every replicated write. Within one region this is usually better than two clusters; across regions the latency makes it impractical.
Test the failoverThe same rule as database DR: a replication topology that has never been failed over is a diagram. Run the drill, measure how long consumers take to resume, and publish the number.
