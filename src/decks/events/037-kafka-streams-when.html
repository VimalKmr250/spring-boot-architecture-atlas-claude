Kafka Streams: when it beats a plain consumer

A library, not a cluster — it runs inside your Spring Boot app. It earns its place when you need state or time; for stateless work a @KafkaListener is simpler and easier to operate.

Use Streams when you need…

  • Aggregation over a stream — orders per customer per hour, running totals.
  • Joins — enrich an order event with customer data from another topic, without calling a service.
  • Windowing — "more than 5 failed payments from one card in 10 minutes".
  • Deduplication at scale with a state store rather than a database table.
  • Repartitioning — re-key a stream so downstream processing has the ordering it needs.

All of these need to remember something between messages. That memory is what Streams manages for you.

Stay with a plain consumer when…

  • Each message is handled independently — reserve stock, send an email, update a row.
  • The work is a database write; Streams' state store adds nothing.
  • You need arbitrary access to other systems mid-processing.
  • The team has no appetite for a second operational model — Streams brings state stores, changelog topics, standby replicas and rebalance-triggered state restoration.

Most enterprise consumers are in this column, and should stay there.

The DSL, in the shapes you will actually use
@Bean
KStream<String, OrderPlaced> topology(StreamsBuilder builder) {

    KStream<String, OrderPlaced> orders = builder.stream("orders.order.placed.v1");

    orders
        .filter((key, order) -> order.totalMinor() > 100_00)        // stateless
        .mapValues(OrderEnricher::toHighValue)                      // stateless
        .to("orders.order.highvalue.v1");

    orders
        .selectKey((key, order) -> order.customerId())               // re-key…
        .groupByKey()                                               // …triggers a repartition
        .count(Materialized.as("orders-per-customer"))              // STATEFUL
        .toStream()
        .to("analytics.customer.ordercount.v1");

    orders
        .flatMapValues(order -> order.lines())                      // one event → many
        .groupBy((key, line) -> line.sku(), Grouped.with(Serdes.String(), lineSerde))
        .aggregate(() -> 0,                                         // units per SKU
                   (sku, line, total) -> total + line.qty(),
                   Materialized.with(Serdes.String(), Serdes.Integer()));
    // reduce() needs (V, V) -> V, so the values must already BE the number.
    // Here they are OrderLines, so aggregate() with an initialiser is the
    // right operator — or mapValues(OrderLine::qty) first, then reduce.

    return orders;
}
Every re-key is a round trip through KafkaselectKey followed by an aggregation writes the whole stream to an internal repartition topic and reads it back, because the new key must land on the right partition. It is correct and it doubles your traffic for that stage — so re-key once, as early as possible, not repeatedly through the topology.
