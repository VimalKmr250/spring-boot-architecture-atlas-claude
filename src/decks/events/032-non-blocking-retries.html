@RetryableTopic: retry without blocking the partition

The answer to the head-of-line problem. Failed records are forwarded to timed retry topics and re-consumed later, so the main partition keeps flowing at full speed.

Four lines to enable it
@RetryableTopic(
    attempts = "4",
    backoff = @Backoff(delay = 1000, multiplier = 4.0, maxDelay = 60000),
    exclude = { DeserializationException.class, IllegalArgumentException.class },
    dltStrategy = DltStrategy.FAIL_ON_ERROR,
    topicSuffixingStrategy = SUFFIX_WITH_INDEX_VALUE)
@KafkaListener(topics = "orders.order.placed.v1", groupId = "inventory")
public void on(OrderPlaced event) { inventory.reserve(event); }

@DltHandler
void dlt(OrderPlaced event,
         // DLT_-prefixed constants — these are the headers the
         // DeadLetterPublishingRecoverer writes (kafka_dlt-*). The
         // un-prefixed ORIGINAL_TOPIC / EXCEPTION_MESSAGE are for
         // records republished to an ordinary topic, and bind to null here.
         @Header(KafkaHeaders.DLT_ORIGINAL_TOPIC) String topic,
         @Header(KafkaHeaders.DLT_EXCEPTION_FQCN) String type,
         @Header(KafkaHeaders.DLT_EXCEPTION_MESSAGE) String reason) {
    support.raiseTicket(event.orderId(), type + ": " + reason);   // a human owns it
}
When to use whichBlocking retry (DefaultErrorHandler) when ordering matters and failures are rare and brief — a deadlock, a momentary network blip. Non-blocking retry topics when a downstream dependency can be down for minutes and you cannot stall the whole partition behind it. Most order-processing consumers want the first; most integration consumers calling third parties want the second.
