At-most-once, at-least-once, and the exactly-once conversation

The most common interview question in this area, and the one most often answered wrongly with confidence. The precise answer is short and the reasoning behind it is what is being tested.

SemanticHow you get itYou may loseYou may duplicateUse for
At-most-onceCommit the offset before processing; acks=0yesnoMetrics, telemetry, anything where loss is cheaper than a duplicate
At-least-onceCommit the offset after processing; acks=allnoyesAlmost everything. The default you should design for
Exactly-once (within Kafka)Transactional producer + isolation.level=read_committednono*Kafka-to-Kafka processing: Streams, read-process-write
Exactly-once effectsAt-least-once delivery into an idempotent handlernono observable effectAny external side effect: a database write, a payment, an email
Where "exactly-once" stopsKafka's EOS covers Kafka to Kafka — consume, transform, produce, commit offsets, all in one transaction. The moment your handler writes to PostgreSQL or calls a payment gateway, that external system is outside the transaction and the guarantee ends there.

So the correct sentence is: "exactly-once processing within Kafka, and exactly-once effects elsewhere by making the handler idempotent."

The settings behind each guarantee
# Producer — do not lose writes
acks: all                       # client default SINCE KAFKA 3.0 (was 1 before).
                                # Pin it: acks=1 acknowledges on the leader alone,
                                # so a failover before replication loses the write.
enable.idempotence: true        # nominally default true in 3.0, but a config-validation
                                # bug (KAFKA-13598) meant it only took effect from
                                # 3.0.1/3.1.1/3.2.0 — so pin it. Requires acks=all,
                                # and de-duplicates producer retries in a session
min.insync.replicas: 2          # TOPIC setting; with acks=all and RF=3 this is
                                # what actually makes the durability promise real

# Consumer — do not lose messages
enable.auto.commit: false       # RAW-CLIENT default is true, committing on a timer
                                # regardless of success. Spring's container already
                                # forces false — set it anyway so it is visible.
isolation.level: read_committed # skip records from aborted transactions
acks=all alone is not enoughWith replication factor 3 and min.insync.replicas=1, "all" can mean "the leader only" when the followers are lagging. The pair that makes a real durability promise is RF=3 and min.insync.replicas=2: the write survives losing one broker, and the partition goes read-only rather than silently accepting unsafe writes when two are down.
