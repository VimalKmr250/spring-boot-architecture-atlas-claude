Consumer lag is climbing — the diagnostic order

Six checks, cheapest first. The mistake is scaling consumers before knowing which of these it is, which usually makes the problem worse by triggering a rebalance.

#CheckIf yes
1Is lag on all partitions or one?One → hot key or a stuck consumer. Do not scale; find that partition
2Did producer volume jump?A legitimate spike — scale out, or let the buffer absorb it if time-to-drain is acceptable
3Is the rebalance rate elevated?The group is thrashing. Look at max.poll.interval vs handler duration, and pod restarts
4Has handler latency risen?A downstream dependency slowed. Fix there; the consumer is a symptom
5Are consumers at the partition count already?You cannot scale further without adding partitions — make handling cheaper instead
6Are errors and retries up?Retries multiply effective processing time. Check the DLT and the retry topics
The commands to run first
# Lag per partition — the single most useful command
kafka-consumer-groups.sh --bootstrap-server $B --describe --group inventory
#  TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG   CONSUMER-ID
#  orders  0          918224          918230          6     consumer-1-a3f…
#  orders  7          901003          962847          61844 consumer-4-9cd…   ← here

# Is anything consuming at all?
kafka-consumer-groups.sh --bootstrap-server $B --describe --group inventory --members

# What is that consumer's thread actually doing?
curl -s localhost:8081/actuator/threaddump | jq '.threads[]
  | select(.threadName | contains("KafkaConsumer")) | {threadName, threadState}'
A consumer with no member idIf --describe shows lag but the CONSUMER-ID column is empty, nothing is consuming that partition — the group has no live member for it. That is a dead or unstarted consumer, not a slow one, and scaling will not help.
The fastest real fix, usuallySwitch to a batch listener with a bulk write. Five hundred individual inserts become one statement, and a consumer that handled 2,000/s handles 20,000/s with no new infrastructure and no partition change. Check this before adding pods.
Do not raise max.poll.interval.ms to stop rebalancesIt hides a slow handler and delays detection of genuinely dead consumers. Reduce max.poll.records so a poll's work finishes quickly instead.
