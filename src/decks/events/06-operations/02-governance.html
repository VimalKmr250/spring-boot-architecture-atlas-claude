Platform governance: topics, quotas and self-service

A shared Kafka cluster with no rules becomes unusable at around a hundred topics. With the wrong rules it becomes a ticket queue. The paved-road model from the architecture deck applies directly.

Topic provisioning as code

# topics/orders.yaml — in the owning team's repo, applied by CI
- name: orders.order.placed.v1
  owner: checkout-team
  partitions: 24
  replication: 3
  config:
    min.insync.replicas: 2
    retention.ms: 604800000
    cleanup.policy: delete
  schema: schemas/order-placed-v1.avsc
  compatibility: BACKWARD
  consumers: [inventory, payment, search, notification]

Reviewed in a pull request, applied by a pipeline, and the same file generates the catalogue entry. No ticket, no console clicking, and every topic has an owner by construction.

Quotas: stop one client taking the cluster

kafka-configs --alter --entity-type clients --entity-name analytics-backfill \
  --add-config 'producer_byte_rate=10485760,consumer_byte_rate=52428800'

A backfill job replaying six months of history will saturate the cluster and degrade every production consumer. A quota makes it slow instead of making everyone else slow.

The standards worth setting centrallyNaming convention · envelope fields · default partition count and replication · compatibility mode · required ACL model · mandatory DLT per consumer · trace propagation on. Six or seven rules, enforced by the pipeline that provisions topics, cover almost everything that goes wrong.
Orphan topicsTeams reorganise; topics do not. Run a quarterly report of topics with no producer traffic, no active consumer group, or an owner who no longer exists. Deleting them is usually blocked on nobody being willing to confirm they are unused — which is what the consumer-group metric is for.
