Twelve event-driven anti-patterns

Each of these is common, was reasonable when it was introduced, and is expensive to unwind. Recognising them by symptom is more useful than knowing the names.

Anti-patternWhat you seeWhat it costs
Commands disguised as eventsSendEmail on a topic, one consumer, producer knows the outcomeCoupling with no owner for failures. Fan-out you can never use
Database change feed as a "domain event"CDC straight off tables into a shared topicThirty teams coupled to your schema; you can never refactor
Dual writesave(); kafka.send();Silent loss on crash. Found weeks later by reconciliation
Non-idempotent consumerA counter increment in a handlerEvery rebalance, retry and replay corrupts data a little
Unbounded retriesRetry forever, no DLTOne bad record blocks its partition and everything behind it
Event chains as workflowSix services each reacting to the last, no coordinatorNobody can answer "where is order 88421 stuck"
Event sourcing by accidentRebuilding current state by replaying a topic on every readAll the cost of event sourcing, none of the tooling
Shared consumer groupTwo applications, one group idEach sees half the events. Nobody notices for weeks
No schema governanceJSON, no registry, "we'll be careful"A breaking change reaches production and fails asynchronously
Fat events as data dumpsEvery column of the row in the payloadA published contract you can never shrink, plus a PII exposure
Synchronous call inside a consumerHandler calls three services and waitsConsumer throughput now equals the slowest dependency's latency
Events for everythingThe whole request path made asyncEvery screen must model "not yet"; debugging cost with no availability gain
The pattern behind themNine of the twelve come from treating the broker as the architecture. Kafka does not make a system event-driven any more than a database makes it well-modelled. The architecture is the event design — what is a fact, who owns it, what it means — and the broker is how it travels.
