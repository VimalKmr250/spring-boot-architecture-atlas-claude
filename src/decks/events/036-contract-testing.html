Contract testing for events

OpenAPI protects your HTTP consumers. Nothing protects your event consumers unless you build it — and the failure mode is worse, because it is asynchronous and silent.

Three layers of protection

1 · Registry gate
Schema compatibility checked in CI against the registered version. Catches removed fields, changed types, missing defaults. Cheapest and highest value — do this first.
2 · Producer contract test
The producer asserts it emits a payload matching the published schema, with the fields consumers rely on actually populated. A schema says a field may exist; a contract test says it is filled.
3 · Consumer-driven contract
Each consumer publishes what it needs; the producer's build verifies it still provides all of them. Spring Cloud Contract or Pact. Real coordination cost, real protection.
Registry compatibility check in the pipeline
- name: Check schema compatibility
  run: |
    curl -sf -X POST \
      "$REGISTRY/compatibility/subjects/orders.order.placed.v1-value/versions/latest" \
      -H "Content-Type: application/vnd.schemaregistry.v1+json" \
      -d @build/schema-payload.json \
    | jq -e '.is_compatible == true'
# Fails the build on a breaking change — no meeting, no judgement call.
Semantic breakage passes every schema checkChanging totalMinor from "total excluding tax" to "total including tax" is fully compatible structurally and catastrophic in practice. No tool catches it.

Defences: document the semantics of every field in the catalogue, and treat a meaning change as a new field (totalInclTaxMinor) rather than a redefinition — exactly the expand/contract discipline you use for a database column.

Proportionate choiceLayer 1 for every topic. Layer 2 for topics with external or cross-department consumers. Layer 3 only where a broken contract would be an incident and the consumers are known and few — its coordination cost is what makes teams abandon it.
