The ordering is the data structure — use it or you have a plain tree

A binary search tree guarantees that everything in the left subtree is smaller and everything on the right is larger. Two consequences follow, and every problem here is one of them: you can discard half the tree at each step, and an in-order traversal emits sorted values.

Consequence one — halving

Comparing a target against node.val tells you which side it must be on, so the other side is discarded outright. Searching, inserting, deleting and finding a lowest common ancestor are all O(h) rather than O(n).

On a balanced tree h is log n. On a degenerate one — values inserted in sorted order — it is n, and every operation degrades to a linear scan. Say that when asked about complexity.

Written iteratively, these are O(1) space, which is usually worth preferring.

Consequence two — in-order is sorted

Visit left, then the node, then right, and the values come out in ascending order. That single fact solves most of this family:

  • Validation — the sequence must be strictly increasing.
  • The k-th smallest — stop after k emissions.
  • Recovery — exactly two elements are out of order in a sorted sequence.

When a BST problem looks hard, ask what the in-order sequence would look like. The answer is usually the algorithm.

Applies when

The tree is stated to be a BST. That word is the licence to use ordering — without it you have an ordinary binary tree and must visit every node.

Does not apply when

The tree is unbalanced in a way that matters and you need guaranteed logarithmic bounds — that is an AVL or red-black tree. Also when duplicates are allowed, since the problem must then define which side they go on.

Complexity

O(h) for search, insert, delete and lowest common ancestor — log n balanced, n degenerate. O(n) for anything requiring a full in-order pass. Space is O(1) iteratively, O(h) recursively.

The phrase "without changing its structure" in LC 99 is what forces the in-order approach rather than a rebuild.
