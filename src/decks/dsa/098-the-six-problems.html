Anchor 1 · LC 98 — the path to the solution

The wrong first attempt
Check left.val < node.val < right.val at every node. This is the single most common wrong answer in the whole BST family, and it passes the problem's own first example.
Why it fails
The BST property is about entire subtrees, not immediate children. A node can satisfy its parent while violating an ancestor several levels up, exactly as in the traced tree.
Solution one — the range
Carry (lo, hi) down. Descending left tightens hi to the current value; descending right tightens lo. Every node must lie strictly inside its inherited interval.
Solution two — in-order
A valid BST emits a strictly increasing in-order sequence, so keep a prev pointer and fail the moment prev.val >= node.val. Same complexity, and it generalises to LC 99.
The overflow trap
Use long bounds. A tree consisting of one node holding Integer.MIN_VALUE is valid, but val > Integer.MIN_VALUE rejects it — and that case is in the test set.
Duplicates
Invalid by LeetCode's definition, so the comparisons are strict on both sides.
LC 98 · O(n) time, O(h) space
class Solution {
    public boolean isValidBST(TreeNode root) {
        // long bounds: a node may legitimately hold Integer.MIN_VALUE
        // or Integer.MAX_VALUE, which int sentinels would reject.
        return valid(root, Long.MIN_VALUE, Long.MAX_VALUE);
    }

    private boolean valid(TreeNode node, long lo, long hi) {
        if (node == null) return true;

        // Strict on both sides — duplicates are not allowed.
        if (node.val <= lo || node.val >= hi) return false;

        // Descending LEFT tightens the upper bound to this value;
        // descending RIGHT tightens the lower bound. That inherited
        // bound is what a parent-only comparison cannot see.
        return valid(node.left,  lo, node.val)
            && valid(node.right, node.val, hi);
    }
}

Anchor 2 · LC 99 — the path to the solution

Brute force
Collect the in-order values, sort a copy, compare position by position, and swap back the two that differ. O(n log n) time and O(n) space — correct, and worth stating first.
The reframing
The in-order sequence should be sorted. Swapping two elements of a sorted sequence creates a very specific defect, so you do not need to sort anything — just find it.
The two cases
If the swapped nodes are non-adjacent in the sequence, there are exactly two inversions: take the first element of the first and the second element of the last. If they are adjacent, there is exactly one inversion, and both culprits are in it.
Handling both uniformly
On the first inversion, record first = prev and second = node. On any later inversion, overwrite second = node only. That single rule covers both cases with no branching.
The final step
Swap the two values. The statement forbids changing the structure, so moving nodes is not allowed.
Edge cases
Exactly two nodes are swapped, as guaranteed. The O(1)-space follow-up is Morris traversal — mention it, but the stack version is what to write.
LC 99 · O(n) time, O(h) space
class Solution {
    private TreeNode first, second, prev;

    public void recoverTree(TreeNode root) {
        inorder(root);
        // Swap VALUES — the structure must not change.
        int tmp = first.val;
        first.val = second.val;
        second.val = tmp;
    }

    private void inorder(TreeNode node) {
        if (node == null) return;

        inorder(node.left);

        // In-order should be strictly increasing. An inversion here
        // means one of the two swapped nodes is involved.
        if (prev != null && prev.val > node.val) {
            // First inversion: BOTH candidates come from it.
            if (first == null) first = prev;
            // Every inversion updates `second`. If the nodes were
            // adjacent there is only one inversion, and this line
            // still captures the right node.
            second = node;
        }
        prev = node;

        inorder(node.right);
    }
}

700 · Search in a BST engine A

Path: scanning the whole tree is O(n) and ignores the ordering. One comparison per level discards half the remaining tree.

Delta: a three-line while loop. Prefer the iterative form — it is O(1) space, and the recursive version buys nothing here.

Watch for: return the node, not a boolean. The subtree rooted there is the expected answer, and returning null when absent is correct rather than an error.

235 · Lowest Common Ancestor of a BST engine A

Path: the general-tree algorithm is O(n) and works, but ignores the ordering entirely. The BST version is O(h) and much shorter.

Delta: while both targets are on the same side of the current node, walk that way. The first node where they split — or that equals one of them — is the answer.

Watch for: a node is permitted to be its own ancestor, so stop when cur.val equals either target. Forgetting that descends past the correct answer.

230 · Kth Smallest Element in a BST engine B

Path: a full in-order into a list then index k−1 is O(n) time and space. The observation is that you can stop as soon as k values have been emitted.

Delta: the iterative in-order with an explicit stack, decrementing k on each pop and returning at zero. That is O(h + k), which matters when k is small and the tree is large.

Watch for: the follow-up asks what changes if the tree is modified often. The answer is to store a subtree size in each node, making selection O(h) — worth naming even without coding it.

450 · Delete Node in a BST engine A

Path: descend to the node using the ordering, then handle the removal. The descent is easy; the removal has three cases.

Delta: zero or one child means returning that child upward — the parent's assignment splices it in. Two children means overwriting the value with the in-order successor, then deleting that successor from the right subtree.

Watch for: the successor is the leftmost node of the right subtree, not simply root.right. It is the unique smallest value greater than the deleted one, which is what keeps both subtrees ordered.

If you only drill twoDo 98 and 99. 98 corrects the parent-comparison instinct, which is the error that quietly breaks more BST solutions than anything else. 99 then forces you to reason about what a swap does to the in-order sequence — and that habit of asking "what would the sorted order look like?" is what makes the rest of this family straightforward.
