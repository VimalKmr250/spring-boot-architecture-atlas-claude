Anchor 1 · LC 102 — the path to the solution

First attempt
A plain queue traversal visits nodes in the right order but produces one flat list — the level boundaries are gone.
The failed fix
Tracking depth per node and grouping afterwards works, but it needs a parallel structure and is more code than the real solution.
The observation
At the moment the queue holds a complete level, its size is that level's width. Everything enqueued afterwards belongs to the next level, so the boundary is already in the data.
The one line
int size = q.size() before the inner loop. Draining exactly size nodes consumes one level and leaves the next in place — the invariant restores itself.
The DFS alternative
Recurse with a depth parameter and append to out.get(depth), creating the list when the depth is first reached. Also O(n), and worth mentioning — it uses O(h) space instead of O(w).
Edge cases
A null root returns an empty list. Filter null children on enqueue so the snapshot stays accurate.
LC 102 · O(n) time, O(w) space
class Solution {
    public List<List<Integer>> levelOrder(TreeNode root) {
        List<List<Integer>> out = new ArrayList<>();
        if (root == null) return out;

        Queue<TreeNode> q = new ArrayDeque<>();
        q.offer(root);

        while (!q.isEmpty()) {
            // SNAPSHOT: the queue currently holds exactly one level.
            // Reading q.size() inside the loop would swallow the next.
            int size = q.size();
            List<Integer> level = new ArrayList<>(size);

            for (int i = 0; i < size; i++) {
                TreeNode node = q.poll();
                level.add(node.val);

                // Filter nulls on ENQUEUE so the snapshot stays exact.
                if (node.left  != null) q.offer(node.left);
                if (node.right != null) q.offer(node.right);
            }
            out.add(level);
        }
        return out;
    }
}

Anchor 2 · LC 116 — the path to the solution

Brute force
Level-order with the template, linking each node to the next in its level. O(n) time but O(w) space — and the follow-up demands O(1).
The observation
Once level k's next pointers are set, that level is itself a linked list. So you can traverse it without a queue — the structure you just built is the queue.
The two links per node
Walking a node on level k, you can set two pointers on level k+1: left.next = right within the node, and right.next = next.left across to the neighbour's subtree. The second is what needs the current level's own links.
Why perfection matters
The tree is stated to be perfect, so every node has either two children or none, and head.left and head.right always exist together. That is what makes the two-link step unconditional.
Descending
After wiring a level, drop to leftmost.left — the leftmost node of the next level, which is where the next sweep begins.
The general case
LC 117 removes the perfection guarantee, and then you must scan for the next non-null child. Mention it as the natural follow-up.
LC 116 · O(n) time, O(1) space
class Solution {
    public Node connect(Node root) {
        Node leftmost = root;

        // Stop at the last level — it has no children to wire.
        while (leftmost != null && leftmost.left != null) {

            // Walk this level using the next pointers ALREADY set.
            // The level is its own linked list, so no queue is needed.
            for (Node head = leftmost; head != null; head = head.next) {

                // 1 · within this node
                head.left.next = head.right;

                // 2 · across to the neighbour's subtree. This is the
                //     step that consumes the current level's links.
                if (head.next != null) {
                    head.right.next = head.next.left;
                }
            }
            leftmost = leftmost.left;    // descend one level
        }
        return root;
    }
}

199 · Binary Tree Right Side View template

Path: "what you see from the right" is the last node of each level — restating it that way turns the problem into the template.

Delta: one line. Inside the inner loop, if (i == size - 1) out.add(node.val).

Watch for: a DFS that visits right before left and records the first node at each new depth also works, in O(h) space. Worth offering when the tree is deep and narrow.

515 · Find Largest Value in Each Tree Row template

Path: a fold over each level rather than a collection.

Delta: replace the list with an int max, seeded to Integer.MIN_VALUE at the start of each level.

Watch for: seeding with 0 fails on a tree of all-negative values — a mistake that passes every example in the problem statement and fails the hidden tests.

637 · Average of Levels template

Path: another fold, this time summing and dividing by the snapshot — which is exactly the level's width, already at hand.

Delta: accumulate into a long, then out.add((double) sum / size).

Watch for: the overflow is real, not theoretical — a level of 2000 nodes each near Integer.MAX_VALUE is in the test set. Cast before dividing, or integer division truncates the result.

103 · Zigzag Level Order template + flag

Path: the instinct is to alternate the order in which children are enqueued. That does not work — it corrupts the ordering two levels down.

Delta: traverse normally and change only how the level list is built. Use a LinkedList with addFirst on right-to-left levels, or collect normally and Collections.reverse the odd ones.

Watch for: flip the flag once per level, outside the inner loop. Flipping per node produces an interleaving rather than a reversal.

If you only drill twoDo 102 and 116. 102 fixes the size snapshot, after which 199, 515, 637 and 103 are each a one-line edit. 116 is the one worth real thought: it asks you to notice that the structure you are building can replace the auxiliary structure you were using, which is a move that appears again in graph and matrix problems.
