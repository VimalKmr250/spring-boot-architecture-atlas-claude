Anchor 1 · LC 56 — the path to the solution

Brute force
Repeatedly scan for any overlapping pair and fuse them, until a full pass changes nothing. O(n³) and awkward to write correctly.
The observation
Sorting by start makes overlap local: if an interval does not overlap the one immediately before it, it cannot overlap anything earlier either, because every earlier interval starts no later and has already been absorbed.
What that buys
Only the last emitted interval ever needs checking — so one pass with one comparison per element.
The two cases
cur.start <= last.end means extend; otherwise append. There is no third case, which is a useful thing to notice out loud.
The detail
last.end = max(last.end, cur.end). A contained interval such as [2,3] inside [1,10] would otherwise truncate the merge.
Edge cases
Touching intervals do merge here, so the test is <=. Copy each interval into the output rather than storing the input reference, or later mutation corrupts the source array.
LC 56 · O(n log n) time, O(n) space
class Solution {
    public int[][] merge(int[][] intervals) {
        // Sorting by start makes overlap local: only the previously
        // emitted interval can possibly overlap the current one.
        Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));

        List<int[]> out = new ArrayList<>();

        for (int[] cur : intervals) {
            int[] last = out.isEmpty() ? null : out.get(out.size() - 1);

            if (last != null && cur[0] <= last[1]) {
                // Overlapping (touching counts here, hence <=).
                // max() because cur may be fully CONTAINED in last.
                last[1] = Math.max(last[1], cur[1]);
            } else {
                // Disjoint — copy, never alias the input row.
                out.add(new int[]{ cur[0], cur[1] });
            }
        }
        return out.toArray(new int[0][]);
    }
}

Anchor 2 · LC 253 — the path to the solution

Restating it
The number of rooms needed is the maximum number of meetings running at the same instant. Once phrased that way, the problem stops being about rooms.
Brute force
For each meeting, count how many others overlap it. O(n²).
Solution one — the heap
Sort by start. Keep a min-heap of end times: the root is the room freeing up soonest. For each meeting, reuse that room if it has already finished, otherwise open a new one. The heap size is the room count.
Solution two — the sweep
Split every meeting into a +1 at its start and a −1 at its end, sort all events by time, and track the running maximum. Same O(n log n), and often easier to explain.
The ordering detail
At equal timestamps, process the end before the start — a room genuinely frees at that instant. In the heap version this is the <= in the reuse test.
Why the heap is never bigger than needed
A room is only opened when every existing one is still busy, so the size never exceeds true peak concurrency.
LC 253 · O(n log n) time, O(n) space
class Solution {
    public int minMeetingRooms(int[][] intervals) {
        if (intervals.length == 0) return 0;

        // Process meetings in the order they begin.
        Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));

        // Min-heap of END times: the root is the room that
        // becomes free soonest.
        PriorityQueue<Integer> rooms = new PriorityQueue<>();

        for (int[] m : intervals) {
            // <= because a room frees AT the end instant: a meeting
            // ending at 10 does not conflict with one starting at 10.
            if (!rooms.isEmpty() && rooms.peek() <= m[0]) {
                rooms.poll();          // reuse that room
            }
            rooms.offer(m[1]);         // occupy a room until m ends
        }
        // A room was only ever added when all others were busy,
        // so the size is exactly the peak concurrency.
        return rooms.size();
    }
}

57 · Insert Interval skeleton A

Path: appending and re-running LC 56 is O(n log n) and correct — say it. But the input is already sorted, so the sort is pure waste.

Delta: three phases in one pass. Copy everything ending before the new interval starts; absorb everything overlapping it by taking min of starts and max of ends; copy the rest.

Watch for: the new interval may overlap nothing, or everything. Both fall out of the three phases with no special case — which is why this structure is worth writing rather than branching.

252 · Meeting Rooms skeleton A Premium

Path: checking all pairs is O(n²). Sorting by start makes conflict local, exactly as in LC 56.

Delta: sort by start and return false the moment intervals[i][0] < intervals[i-1][1]. Strict < here: a meeting starting when another ends is fine.

Premium: paywalled. LC 56 covers the same reasoning, and 253 below is the strictly harder version — solving that one subsumes this entirely.

435 · Non-overlapping Intervals skeleton C

Path: "remove the minimum" is the same as "keep the maximum", which is classic activity selection. That restatement is the whole problem.

Delta: sort by end, then greedily accept any interval starting at or after the last accepted end. The answer is n − kept.

Watch for: sorting by start is the trap — it picks a long early interval and loses several short ones. Be ready to give the exchange argument for why earliest-finish-first is safe; that is the follow-up question.

452 · Minimum Arrows to Burst Balloons skeleton C

Path: identical to 435 with the count inverted — instead of removals, you are counting the groups that survive.

Delta: sort by end; fire an arrow at the end of the first balloon, and skip every balloon whose start is at or before that point. The arrow count is the number of groups.

Watch for: coordinates span the full int range, so a[1] - b[1] in the comparator overflows and produces a wrong sort order. Use Integer.compare — LeetCode tests this case specifically.

If you only drill twoDo 56 and 435. Together they force the central decision: 56 sorts by start because it is building merged intervals, 435 sorts by end because it is keeping as many as possible. Once you can state why each is right, 57, 252, 253 and 452 are all short variations — and picking the wrong end is the only way this family goes wrong.
