Anchor 1 · LC 875 — the path to the solution

Brute force
Try every speed from 1 upwards and stop at the first that fits. O(max · n) — with piles to 10⁹ that is 10¹⁴ operations.
The constraint tell
n ≤ 10⁴ but piles[i] ≤ 10⁹. A tiny array with gigantic values means the search is over the value range, not the array.
The observation
Eating faster never takes more hours. So feasibility is monotone in speed, and the brute-force scan is a linear search over a sorted-by-feasibility axis — exactly what binary search replaces.
The check
sum(ceil(pile / k)) ≤ h. She never moves on mid-pile, which is why it is a ceiling — that sentence in the statement is the whole modelling step.
Edge cases
Use long for the hour total. Round up with integer arithmetic, never Math.ceil on doubles — at 10⁹ the division loses precision.
LC 875 · O(n log maxPile) time, O(1) space
class Solution {
    public int minEatingSpeed(int[] piles, int h) {
        int lo = 1, hi = 0;
        for (int p : piles) hi = Math.max(hi, p);   // fastest useful speed

        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;

            if (canFinish(piles, mid, h)) hi = mid;      // maybe the answer
            else                          lo = mid + 1;  // definitely too slow
        }
        return lo;
    }

    private boolean canFinish(int[] piles, int speed, int h) {
        long hours = 0;
        for (int p : piles) {
            hours += (p + speed - 1) / speed;   // ceil(p / speed), integer only
            if (hours > h) return false;        // early exit
        }
        return true;
    }
}

Anchor 2 · LC 410 — the path to the solution

The DP solution
dp[i][j] = best split of the first i elements into j parts. O(n²k) time, O(nk) space. It is the textbook answer and it passes — mention it, then beat it.
The inversion
Stop asking "what is the smallest possible largest sum" and ask "with a cap of M, how many parts do I need?" That second question is a single greedy pass.
Why greedy is optimal here
Fill each part as full as the cap allows before starting the next. Closing a part early can never reduce the total count, so the greedy count is the minimum. Say this — it is the step interviewers push on.
Monotonicity
A larger cap never needs more parts, so partsNeeded(M) ≤ k reads F F F T T T in M.
Bounds
lo = max(nums) — no part can be smaller than its largest element. hi = sum(nums) — one part holds everything. Starting lo at 0 or 1 is the classic error.
Same problem
LC 1011 is this with "parts" renamed "days" and "cap" renamed "capacity". Identical code.
LC 410 · O(n log sum) time, O(1) space
class Solution {
    public int splitArray(int[] nums, int k) {
        long lo = 0, hi = 0;
        for (int v : nums) {
            lo = Math.max(lo, v);   // a part can never be smaller than one element
            hi += v;                // one part holding everything always works
        }

        while (lo < hi) {
            long mid = lo + (hi - lo) / 2;

            if (partsNeeded(nums, mid) <= k) hi = mid;
            else                             lo = mid + 1;
        }
        return (int) lo;
    }

    /** Greedy: fill each part to the cap before opening the next. */
    private int partsNeeded(int[] nums, long cap) {
        int parts = 1;
        long cur = 0;

        for (int v : nums) {
            if (cur + v > cap) { parts++; cur = v; }   // open a new part
            else                 cur += v;
        }
        return parts;
    }
}

1011 · Capacity To Ship Packages greedy packing

Path: identical to 410 in every respect — only the vocabulary differs. Recognising that equivalence out loud is itself worth points.

Delta: lo = max(weights) (a package must fit on one ship), hi = sum(weights). feasible(cap) counts days by the same greedy fill.

Watch for: packages must ship in order, which is what makes the greedy valid. If reordering were allowed this would be bin packing, and NP-hard.

1283 · Smallest Divisor Given a Threshold count units

Path: the same shape as 875 with "hours" renamed "sum of quotients". If you solved Koko, you can write this in two minutes.

Delta: lo = 1, hi = max(nums) — at that divisor every term is 1, so the sum is n, and the statement guarantees threshold ≥ n. feasible(d) is sum(ceil(v/d)) ≤ threshold.

Watch for: the ceiling again. Math.ceil((double) v / d) works here but integer arithmetic is faster and exact — build the habit.

1482 · Min Days to Make m Bouquets count runs

Path: the answer is a day, not a size — the first cue that the answer space is a time axis. By day x, the bloomed flowers form fixed runs, and each run of length L yields L / k bouquets.

Delta: feasible(x) scans once, tracking the current run of flowers with bloomDay ≤ x and resetting it at every unbloomed flower.

Watch for: check (long) m * k > n up front and return −1 — the multiplication overflows int at the stated limits, and it is the only impossible case.

774 · Minimize Max Distance to Gas Station real-valued

Path: a heap-based greedy that repeatedly splits the widest gap looks natural but is wrong — it is locally greedy and misses the optimum. Binary searching the distance is both simpler and correct.

Delta: the answer is a double, so there is no integer grid to converge onto. Run a fixed 100 iterations instead of comparing against an epsilon. feasible(d) sums (int)(gap / d) extra stations per gap and tests against k.

Watch for: while (hi - lo > 1e-6) can spin forever when the two doubles become adjacent representable values. The fixed count cannot.

Premium: this one is behind LeetCode's paywall. LC 1552 is a free substitute: the same "maximise the minimum distance" shape, and it drills the mirrored template.
