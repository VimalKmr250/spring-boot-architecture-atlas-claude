Write lowerBound once; derive the rest

One function, eight lines, no post-loop fixups. Everything else in this family is either a call to it with a different target, or the same loop with a different way of deciding which half to keep.

The one template worth memorising
/**
 * The first index in [0, n] at which the predicate becomes true.
 * Requires monotonicity:  F F F T T T  — it must flip exactly once.
 *
 * Invariant, maintained by every iteration:
 *     everything <  l  is FALSE
 *     everything >= r  is TRUE
 * so when l == r, that index IS the boundary.
 *
 * Returns n when no index satisfies the predicate — which is
 * exactly the insert position, not an error case.
 */
int lowerBound(int[] a, int target) {
    int l = 0, r = a.length;          // r = n, NOT n - 1

    while (l < r) {                   // strict <, so it ends with l == r
        int mid = l + (r - l) / 2;    // NOT (l + r) / 2 — that overflows near Integer.MAX_VALUE

        if (a[mid] >= target) r = mid;     // mid may be the boundary: keep it
        else                  l = mid + 1; // mid is definitely not: drop it
    }
    return l;
}

// Everything else falls out of that one function:
int firstOccurrence(int[] a, int t) { int i = lowerBound(a, t);
                                      return (i < a.length && a[i] == t) ? i : -1; }
int lastOccurrence (int[] a, int t) { return lowerBound(a, t + 1) - 1; }
int countOf        (int[] a, int t) { return lowerBound(a, t + 1) - lowerBound(a, t); }
int insertPosition (int[] a, int t) { return lowerBound(a, t); }          // LC 35, verbatim
boolean contains   (int[] a, int t) { int i = lowerBound(a, t);
                                      return i < a.length && a[i] == t; } // LC 704
Variant · rotated array, target search (LC 33)
// A rotated sorted array is not monotone, so no single predicate
// works. But at ANY midpoint, at least one half is still sorted —
// and in a sorted half you can decide containment in O(1).
int search(int[] a, int target) {
    int l = 0, r = a.length - 1;      // closed range here: we want an exact hit

    while (l <= r) {
        int mid = l + (r - l) / 2;
        if (a[mid] == target) return mid;

        if (a[l] <= a[mid]) {                     // LEFT half is sorted
            if (a[l] <= target && target < a[mid]) r = mid - 1;   // it must be in there
            else                                   l = mid + 1;
        } else {                                  // RIGHT half is sorted
            if (a[mid] < target && target <= a[r]) l = mid + 1;
            else                                   r = mid - 1;
        }
    }
    return -1;
}
Variant · compare against a neighbour, not a target (LC 153, 162)
// When there is no target, compare a[mid] with something that
// tells you which side the answer lies on.

// LC 153 — minimum of a rotated array. Compare with a[r], never a[l]:
// on an unrotated array a[mid] > a[l] is true yet the min is at 0.
int findMin(int[] a) {
    int l = 0, r = a.length - 1;
    while (l < r) {
        int mid = l + (r - l) / 2;
        if (a[mid] > a[r]) l = mid + 1;   // min is strictly right of mid
        else               r = mid;       // mid could BE the min
    }
    return a[l];
}

// LC 162 — any peak. Walk uphill; the edges count as -infinity,
// so an uphill step can never run off the end.
int findPeakElement(int[] a) {
    int l = 0, r = a.length - 1;
    while (l < r) {
        int mid = l + (r - l) / 2;
        if (a[mid] < a[mid + 1]) l = mid + 1;   // ascending: a peak lies right
        else                     r = mid;       // descending: mid could be it
    }
    return l;
}

The knobs

Range
[0, n) half-open for boundary questions; [0, n−1] closed only when you need an exact hit and will return from inside the loop, as in LC 33.
Predicate
The only genuinely problem-specific line. Say it in words first, then check it reads F…F T…T left to right.
Comparator
Against a target (34, 35, 704), against the right end (153), or against a neighbour (162). Choosing the wrong comparison partner is the classic LC 153 failure.
Return
l for a boundary, a[l] for a value, l − 1 for the last element below the boundary. Never adjust after the loop for any other reason.
The three bugs that actually happenmid = (l + r) / 2 — overflows once l + r exceeds Integer.MAX_VALUE. This is the famous bug that sat in the JDK's own Arrays.binarySearch for nine years; always write l + (r - l) / 2. r = mid - 1 in the half-open template — discards the very index you were looking for, and the result is silently off by one. Mixing the two range conventions — while (l < r) with r = n - 1 never examines the last element; while (l <= r) with r = mid loops forever. Pick one convention per function and never blend them.
