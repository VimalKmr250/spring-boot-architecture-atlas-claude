Six searches, one template and two rotations

704 and 35 are the template unmodified. 34 is two calls to it. 153 and 162 change what mid is compared against. 33 is the one that needs real thought — and it is the one that gets asked.

Anchor 1 · LC 34 — the path to the solution

Brute force
Linear scan for the first and last hit. O(n) — and the problem explicitly demands O(log n), so it is rejected by the statement itself.
The tempting wrong turn
One binary search for any occurrence, then linear expansion outwards. On [8,8,8,…,8] that expansion is O(n), so the whole thing is O(n). Interviewers reach for exactly that input.
The observation
Both endpoints are boundaries, not values. The first 8 is the boundary of "≥ 8"; the position after the last 8 is the boundary of "≥ 9".
The result
Two calls to one function. Nothing is duplicated, and there is no descending variant to get wrong.
Edge case
Target absent: both calls return the same index, so check a[first] == target before returning and emit [−1,−1] otherwise. Also guard first == a.length.
LC 34 · O(log n) time, O(1) space
class Solution {
    public int[] searchRange(int[] nums, int target) {
        int first = lowerBound(nums, target);

        // Absent if we ran off the end, or landed on a different value.
        if (first == nums.length || nums[first] != target)
            return new int[]{ -1, -1 };

        // The first index past the run of `target`, minus one.
        int last = lowerBound(nums, target + 1) - 1;

        return new int[]{ first, last };
    }

    /** First index with nums[i] >= target; nums.length if there is none. */
    private int lowerBound(int[] nums, int target) {
        int l = 0, r = nums.length;

        while (l < r) {
            int mid = l + (r - l) / 2;
            if (nums[mid] >= target) r = mid;
            else                     l = mid + 1;
        }
        return l;
    }
}

Anchor 2 · LC 33 — the path to the solution

Brute force
Linear scan, O(n). The statement demands O(log n).
Two-pass idea
Binary search for the rotation point (that is LC 153), then binary search the correct half. Two passes, both O(log n), and completely acceptable — say it, because it decomposes into a problem you have already solved.
The observation
You do not need the pivot. Split at any mid and at least one half is guaranteed sorted — a rotation can only break the order in one place.
Deciding the half
a[l] <= a[mid] means the left half is sorted. Inside a sorted half, "is the target here?" is a single range check; if it is not, it must be in the other half.
Why <= and not <
When l == mid — a two-element range — the left half is trivially sorted. Writing < misclassifies it and drops the answer. This is the single most common LC 33 failure.
LC 33 · O(log n) time, O(1) space
class Solution {
    public int search(int[] nums, int target) {
        int l = 0, r = nums.length - 1;   // closed range: we return on an exact hit

        while (l <= r) {
            int mid = l + (r - l) / 2;
            if (nums[mid] == target) return mid;

            // A rotation breaks the order in exactly one place,
            // so at least one half is always properly sorted.
            if (nums[l] <= nums[mid]) {              // LEFT half sorted
                // Inside a sorted half, containment is one range test.
                if (nums[l] <= target && target < nums[mid]) r = mid - 1;
                else                                          l = mid + 1;

            } else {                                 // RIGHT half sorted
                if (nums[mid] < target && target <= nums[r]) l = mid + 1;
                else                                          r = mid - 1;
            }
        }
        return -1;
    }
}

704 · Binary Search template

Path: there is no path — this is the baseline. Its value is as a memory test: you should be able to type the template correctly with no compile-and-fix cycle.

Delta: lowerBound, then i < n && a[i] == target. Many people write the closed-range version here instead; either is fine, but pick one and use it everywhere.

Watch for: if you cannot write this from memory, do not move on. Every later pattern in this deck assumes it.

35 · Search Insert Position template

Path: the problem asks where the target "would be if inserted in order" — which is the definition of a lower bound. No adaptation at all.

Delta: none. return lowerBound(nums, target); is the entire solution, and the n return case handles "larger than everything" without a branch.

Watch for: this is the clearest demonstration that "not found" is a legitimate answer rather than an error — the mental shift the whole pattern depends on.

153 · Find Minimum in Rotated Sorted Array neighbour

Path: a linear scan is O(n); the rotation means there is exactly one place where a[i] < a[i-1], and that is the minimum.

Delta: compare a[mid] against a[r]. If a[mid] > a[r] the break lies strictly right, so l = mid + 1; otherwise r = mid, because mid may itself be the minimum.

Watch for: comparing against a[l] instead fails on an unrotated array such as [1,2,3,4], where a[mid] > a[l] yet the minimum is at index 0.

162 · Find Peak Element neighbour

Path: the input is not sorted, which makes O(log n) look impossible. It is not: the predicate "a peak exists at or left of mid" is monotone even though the array is not.

Delta: compare a[mid] with a[mid + 1]. Ascending means a peak lies to the right; descending means mid itself could be one. The stated a[-1] = a[n] = −∞ guarantees the uphill walk always terminates on a peak.

Watch for: this is the clearest proof in the family that binary search needs a monotone predicate, and never a sorted array.

If you only drill twoDo 34 and 33. 34 forces you to internalise the boundary formulation that makes every other variant free; 33 is the most-asked binary search in real interviews and the one where the <= versus < detail separates a working solution from a nearly-working one.
