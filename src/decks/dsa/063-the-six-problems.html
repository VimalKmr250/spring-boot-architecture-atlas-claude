Anchor 1 · LC 239 — the path to the solution

Brute force
Scan each window for its maximum. O(n·k), which at n = 10⁵ and k = 10⁵ is 10¹⁰.
The heap attempt
A max-heap of (value, index) pairs, discarding stale entries lazily from the top. O(n log n) time, O(n) space, and completely correct — offer this first, because it shows you can reach a working answer before optimising.
What the heap wastes
It keeps elements that can never win again. If a[j] ≥ a[i] and j > i, then i is dominated on both value and lifetime — yet the heap still stores it and pays log n to skip it later.
The observation
Delete those elements outright. What remains is automatically sorted, so the maximum is simply the front — no comparisons at all.
Why a deque and not a stack
Two different eviction rules operate at opposite ends: stale-by-age at the front, dominated-by-value at the back. A stack has only one end.
Edge cases
k == 1 returns the input unchanged. Guard the read with i >= k - 1. Output length is n − k + 1.
LC 239 · O(n) time, O(k) space
class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {
        int n = nums.length;
        int[] out = new int[n - k + 1];

        // Indices; their values decrease from front to back,
        // so the front is always the window maximum.
        Deque<Integer> dq = new ArrayDeque<>();

        for (int i = 0; i < n; i++) {

            // 1 · expire by AGE. The window covering i begins at
            //     i - k + 1, so anything <= i - k has slid out.
            while (!dq.isEmpty() && dq.peekFirst() <= i - k) {
                dq.pollFirst();
            }

            // 2 · evict by DOMINATION. nums[i] is larger and
            //     outlives them, so they can never win again.
            while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i]) {
                dq.pollLast();
            }
            dq.offerLast(i);

            // 3 · read, but only once a full window exists.
            if (i >= k - 1) {
                out[i - k + 1] = nums[dq.peekFirst()];
            }
        }
        return out;
    }
}

Anchor 2 · LC 862 — the path to the solution

Why the obvious window fails
With all-positive values this would be a shrink-while-valid window. Negatives destroy that: extending a subarray can lower its sum, so there is no monotone shrink rule. State this first — it is the reason the problem is Hard rather than Medium.
The reformulation
Work on prefix sums P. A subarray (j, i] qualifies when P[i] − P[j] ≥ K, and you want the largest such j to make it short.
First discard rule
Once P[i] − P[front] ≥ K, that front is answered — and no later i can do better with it, since any later window using it is longer. Record the length and remove it permanently.
Second discard rule
If P[i] ≤ P[back], that back is useless: i gives a sum at least as large from a nearer starting point. Remove it.
The result
Those two rules are exactly the deque's two evictions — but keyed on prefix values rather than on age. The deque stays increasing in P.
Edge cases
Seed with index 0 representing the empty prefix. Use long for P: 10⁵ values of 10⁵ overflows int.
LC 862 · O(n) time, O(n) space
class Solution {
    public int shortestSubarray(int[] nums, int k) {
        int n = nums.length;

        long[] P = new long[n + 1];             // long: sums reach 1e10
        for (int i = 0; i < n; i++) P[i + 1] = P[i] + nums[i];

        // Indices into P; their prefix values INCREASE front to back.
        Deque<Integer> dq = new ArrayDeque<>();
        int best = Integer.MAX_VALUE;

        for (int i = 0; i <= n; i++) {

            // 1 · this front is satisfied — record it and drop it.
            //     No later i can use it to make a SHORTER subarray.
            while (!dq.isEmpty() && P[i] - P[dq.peekFirst()] >= k) {
                best = Math.min(best, i - dq.pollFirst());
            }

            // 2 · a back with a bigger prefix is useless: i is both
            //     smaller and closer, so it dominates on both counts.
            while (!dq.isEmpty() && P[dq.peekLast()] >= P[i]) {
                dq.pollLast();
            }
            dq.offerLast(i);
        }
        return best == Integer.MAX_VALUE ? -1 : best;
    }
}

1438 · Longest Subarray With Absolute Diff ≤ Limit max + min

Path: a TreeMap of window counts gives max and min in O(log n) each, for O(n log n) overall — a clean, correct first answer worth stating.

Delta: two deques, one decreasing and one increasing. The condition max − min > limit drives the left edge, so expiry is by validity rather than age.

Watch for: when l advances, remove from a deque only if its front is the departing value — comparing with == on the value, not unconditionally.

1696 · Jump Game VI DP accelerator

Path: the plain DP is dp[i] = nums[i] + max(dp[i-k..i-1]), which is O(n·k) and times out. The inner max over a moving band is the deque's whole purpose.

Delta: the template with dp values in place of nums, expiring by index < i - k. dp[dq.peekFirst()] is the best reachable predecessor.

Watch for: push index 0 before the loop starts, or the first read finds an empty deque.

1425 · Constrained Subsequence Sum DP accelerator

Path: nearly identical to 1696, with one extra decision: elements may be skipped entirely, so a negative running best should be abandoned.

Delta: dp[i] = nums[i] + Math.max(0, dp[dq.peekFirst()]). The max(0, …) is the whole difference — it says "starting fresh here beats carrying a negative forward".

Watch for: the answer is max(dp), not dp[n-1] — the best subsequence need not reach the end.

1499 · Max Value of Equation algebra + deque

Path: the difficulty is algebraic, not structural. Maximise y_i + y_j + |x_i − x_j| with x_j − x_i ≤ k; since points are sorted by x, for j > i the expression is (y_j + x_j) + (y_i − x_i).

Delta: the first bracket is fixed at the current point, so you only need the maximum y_i − x_i over points within distance k — a max over a moving range, which is the template.

Watch for: expire by x-distance, not by index count: x[i] − x[front] > k. Using index age instead is the most common wrong answer here.

If you only drill twoDo 239 and 862. 239 establishes the three moves and the domination argument that justifies deleting elements outright. 862 shows the pattern applied where no window is visible at all — the deque runs over prefix sums, and both eviction rules are re-derived from the problem rather than copied. That transfer is what makes the rest of this family tractable.
