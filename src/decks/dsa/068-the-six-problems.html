Six selections, and two worth beating

215, 973 and 703 are the bounded heap with different comparators. 347 and 692 add a counting step first — and 347 can then be solved in O(n) without a heap at all. 1046 uses a heap for repeated extraction rather than selection.

Anchor 1 · LC 215 — the path to the solution

Brute force
Sort descending and read index k − 1. O(n log n), two lines, and it passes. Say it — then explain why you would do better.
The observation
Sorting orders all n elements when you only care about k of them. The other n − k comparisons are wasted.
The bounded heap
Keep the best k seen so far in a min-heap. The root is the weakest of those, so it doubles as the admission threshold and as the running answer.
Why min and not max
Because the root must be the element you would drop first. Holding the k largest, that is the smallest of them — which is also, by definition, the k-th largest.
The O(n) follow-up
Quickselect. Partition around a random pivot; if the pivot lands at index n − k you are done, otherwise recurse into one side only. Average O(n), worst case O(n²) — mention that it mutates the input.
Edge case
Duplicates count separately: the 2nd largest of [5,5] is 5, not an error. Never de-duplicate.
LC 215 · O(n log k) time, O(k) space
class Solution {
    public int findKthLargest(int[] nums, int k) {
        // MIN-heap: the root is the smallest of the k largest,
        // which is exactly the k-th largest overall.
        PriorityQueue<Integer> heap = new PriorityQueue<>();

        for (int v : nums) {
            if (heap.size() < k) {
                heap.offer(v);
            } else if (v > heap.peek()) {
                // v beats the weakest one we hold — swap them.
                heap.poll();
                heap.offer(v);
            }
            // otherwise v cannot make the top k: discard in O(1)
        }
        return heap.peek();
    }
}

Anchor 2 · LC 692 — the path to the solution

Brute force
Count with a map, sort all entries by (count desc, word asc), take k. O(n log n) and completely correct — the expected baseline.
Why it is the interesting one
Two sort keys pointing in opposite directions: frequency descending, but ties broken alphabetically ascending.
The reversal
In a bounded min-heap the root holds the item to evict — the worst candidate. So the comparator must sort worst-first: lowest count first, and among equal counts the alphabetically largest word first, because that is the one that loses.
Why that reads backwards
The heap order is the inverse of the output order. Writing the comparator as if it were the output order is the standard failure, and it produces answers that are right on counts and wrong on ties.
The final step
Draining a min-heap yields worst-first, so the result must be reversed before returning.
Edge case
Use compareTo on the strings, not == or equals alone — you need an ordering, not equality.
LC 692 · O(n log k) time, O(n) space
class Solution {
    public List<String> topKFrequent(String[] words, int k) {
        Map<String, Integer> freq = new HashMap<>();
        for (String w : words) freq.merge(w, 1, Integer::sum);

        // The ROOT must hold the WORST candidate, so this comparator
        // is the reverse of the output order:
        //   lower count first, and among equal counts the
        //   alphabetically LARGER word first — it loses ties.
        PriorityQueue<Map.Entry<String, Integer>> heap =
            new PriorityQueue<>((x, y) ->
                x.getValue().equals(y.getValue())
                    ? y.getKey().compareTo(x.getKey())
                    : x.getValue() - y.getValue());

        for (Map.Entry<String, Integer> e : freq.entrySet()) {
            heap.offer(e);
            if (heap.size() > k) heap.poll();     // drops the worst
        }

        // Draining gives worst-first, so reverse for the answer.
        LinkedList<String> out = new LinkedList<>();
        while (!heap.isEmpty()) out.addFirst(heap.poll().getKey());
        return out;
    }
}

703 · Kth Largest Element in a Stream min, size k

Path: storing every value and sorting on each add is O(n log n) per call. The stream has no known end, so O(k) memory is the actual requirement.

Delta: the same bounded min-heap, but as an instance field. Seed it from the constructor's array, then add is offer-then-trim-then-peek.

Watch for: the initial array may be shorter than k, so guard peek() until the heap has filled. This is the design question the problem is really asking.

973 · K Closest Points to Origin max, size k

Path: sort by distance and take k — O(n log n). The heap brings it to O(n log k), and quickselect on distance averages O(n).

Delta: you want the k smallest distances, so the heap flips to max: the farthest point sits at the root ready to be evicted.

Watch for: compare x² + y² directly. Math.sqrt is slower and introduces floating-point comparisons for no gain, since squaring preserves order on non-negative values.

347 · Top K Frequent Elements min on count

Path: count with a map, then a bounded min-heap keyed on the count gives O(n log k) — the expected answer.

Delta: then beat it. A frequency can never exceed n, so it can index an array directly: bucket the values by count and read downwards from n. That is O(n) with no comparator at all.

Watch for: new List[n + 1] raises an unchecked-generic-array warning. It is correct and idiomatic here — say so rather than working around it.

1046 · Last Stone Weight max, unbounded

Path: re-sorting after every smash is O(n² log n). The heap gives extract-max in O(log n), which is what the simulation needs.

Delta: this is not a top-k problem. The heap is unbounded and the loop repeatedly pulls the two largest, pushing back the difference when it is non-zero.

Watch for: loop while size > 1, and return 0 when the heap empties. Use Comparator.reverseOrder() for the max-heap — and with values bounded at 1000, a counting approach also works.

If you only drill twoDo 215 and 692. 215 fixes the direction rule — k largest means a min-heap — which is the error that costs people this whole family. 692 is the one that forces you to reason about why the comparator reads backwards, and once that clicks, writing a correct comparator for any two-key selection becomes mechanical.
