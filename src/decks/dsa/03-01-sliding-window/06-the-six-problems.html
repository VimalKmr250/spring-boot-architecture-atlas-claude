Anchor 1 · LC 3 — the path to the solution

Brute force
Try every pair (l, r) and test the substring for duplicates. O(n³), or O(n²) if you carry a set as r grows.
The observation
If [l, r] contains a duplicate, then so does [l, r'] for every r' > r. So once l has been pushed past a duplicate, it never has any reason to go back.
The optimisation
Keep l monotone and maintain a count array instead of rebuilding a set. Each index is touched twice.
Edge cases
Empty string returns 0; a single repeated character returns 1; the count array must cover the full ASCII range the problem allows.
LC 3 · O(n) time, O(1) space
class Solution {
    public int lengthOfLongestSubstring(String s) {
        int[] count = new int[128];       // KNOB 1 · ASCII counts beat a HashMap here
        int l = 0, best = 0;

        for (int r = 0; r < s.length(); r++) {
            char in = s.charAt(r);
            count[in]++;                  // KNOB 2 · admit

            // KNOB 3 · the ONLY char that can now exceed 1 is the one
            // we just admitted, so this single test is the full invariant.
            while (count[in] > 1) {
                count[s.charAt(l++)]--;   // KNOB 4 · evict, mirroring KNOB 2
            }

            best = Math.max(best, r - l + 1);   // KNOB 5 · record
        }
        return best;
    }
}

Anchor 2 · LC 76 — the path to the solution

Brute force
Every substring, each checked against t's frequency map. O(n²·m) and hopeless at n = 10⁵.
First idea
A shortest-form window that compares the window's map to t's map. Correct, but the comparison is O(52) per step and easy to get wrong.
The observation
You never need the whole comparison — only how many characters are still missing, counted with multiplicity. That collapses to a single int.
The trick
Let need[c] go negative for surplus characters. Then need[c] > 0 before admitting means "this one actually helped", and need[c] == 0 before evicting means "losing this one actually hurts". Both tests are one line.
LC 76 · O(n + m) time, O(1) space
class Solution {
    public String minWindow(String s, String t) {
        if (s.length() < t.length()) return "";

        int[] need = new int[128];
        for (char c : t.toCharArray()) need[c]++;

        int missing = t.length();   // chars still uncovered, WITH multiplicity
        int bestL = 0, bestLen = Integer.MAX_VALUE, l = 0;

        for (int r = 0; r < s.length(); r++) {
            // admit: only a char we still needed reduces `missing`.
            // Surplus chars push need[c] negative, which is intentional.
            if (need[s.charAt(r)]-- > 0) missing--;

            while (missing == 0) {            // valid → shrink and record
                if (r - l + 1 < bestLen) { bestLen = r - l + 1; bestL = l; }

                // evict: giving back a char whose need was exactly 0
                // is the one that breaks coverage.
                if (need[s.charAt(l++)]++ == 0) missing++;
            }
        }
        return bestLen == Integer.MAX_VALUE
                ? "" : s.substring(bestL, bestL + bestLen);
    }
}

209 · Minimum Size Subarray Sum variant B

Path: brute force is every (l, r) with prefix sums, O(n²). The observation is that all values are positive, so the window sum rises strictly with width — validity is monotone, so a window works.

Delta: state is a single int sum; invalid test becomes while (sum >= target), and the record moves inside that loop. Return 0, not MAX_VALUE, when nothing qualifies.

Watch for: the follow-up asks for O(n log n). That variant builds a running-sum array and binary searches it for each r — worth naming even if you do not write it.

424 · Longest Repeating Character Replacement variant A

Path: brute force fixes a target letter and windows 26 times, O(26n) — already fast enough, and worth mentioning aloud. The single-pass version is the interesting one.

Delta: only knob 3 changes, to while (len - maxFreq > k) — the count of characters you would have to replace. Keep maxFreq as a running maximum and do not recompute it when shrinking: a stale-high maxFreq can only suppress a window that could not have beaten the recorded best anyway.

Watch for: that non-recomputation is the part interviewers probe. Be ready to justify it.

904 · Fruit Into Baskets variant A

Path: the story about baskets is a disguise. Two baskets, each holding one fruit type, means "longest subarray with at most 2 distinct values" — read past the narrative to the constraint.

Delta: none. This is the skeleton from the previous slide with win.size() > 2 exactly as written. Generalise the 2 to a parameter and the same code answers "at most K distinct" for any K.

Watch for: the win.remove(out) when a count hits zero — without it size() over-reports and the answer is too small.

567 · Permutation in String variant C

Path: brute force sorts every window of width |s1|, O(n·k log k). The observation: a permutation is defined entirely by its character counts, and adjacent windows differ in only two positions — so the count vector updates in O(1).

Delta: fixed size, so the shrink is an if. Rather than comparing 26 counters per step, keep a matches integer of how many letters have the right count, and adjust it by ±1 as each admit or evict crosses the target.

Watch for: the matches counter is the part worth practising. Recomputing all 26 counts each step is O(26n) and still passes, but the incremental update is what the problem is testing.
