Three skeletons, split by what the question wants

Merge (sort by start, extend or append), count simultaneous (sort by start, evict finished with a heap), and keep-the-most (sort by end, greedily accept). Each is under fifteen lines once the sort is chosen.

Skeleton A · merge overlapping (LC 56, 57)
// Sort by START. Then exactly two cases arise per interval.
int[][] merge(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));

    List<int[]> out = new ArrayList<>();

    for (int[] cur : intervals) {
        int[] last = out.isEmpty() ? null : out.get(out.size() - 1);

        if (last != null && cur[0] <= last[1]) {
            // Overlap: extend. max() matters — cur may be CONTAINED
            // in last, and then cur[1] is smaller.
            last[1] = Math.max(last[1], cur[1]);
        } else {
            // Disjoint: start a new interval. Copy it — never alias
            // the input array, or a later merge mutates the source.
            out.add(new int[]{ cur[0], cur[1] });
        }
    }
    return out.toArray(new int[0][]);
}
Skeleton B · count simultaneous (LC 253)
// Sort by START; a min-heap of END times holds the rooms in use.
// The heap root is the meeting that frees up soonest.
int minMeetingRooms(int[][] meetings) {
    Arrays.sort(meetings, (a, b) -> Integer.compare(a[0], b[0]));

    PriorityQueue<Integer> endTimes = new PriorityQueue<>();

    for (int[] m : meetings) {
        // A room whose meeting ENDED by the time this one starts
        // can be reused. Note <= : a room frees AT its end time.
        if (!endTimes.isEmpty() && endTimes.peek() <= m[0]) {
            endTimes.poll();
        }
        endTimes.offer(m[1]);
    }
    return endTimes.size();       // peak concurrency
}
Skeleton C · keep the most / remove the fewest (LC 435, 452)
// Sort by END. The greedy: always take the interval that finishes
// earliest, because it leaves the most room for everything after.
//
// Exchange argument: any optimal set can have its first interval
// swapped for the earliest finisher without creating a conflict,
// so the greedy choice is never worse.
int maxNonOverlapping(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));

    int kept = 0;
    long lastEnd = Long.MIN_VALUE;

    for (int[] iv : intervals) {
        if (iv[0] >= lastEnd) {   // no conflict with what we kept
            kept++;
            lastEnd = iv[1];
        }
    }
    return kept;                  // removals = intervals.length - kept
}

Choosing the skeleton

"merge", "insert"
A. Sort by start; extend or append.
"how many rooms / how many at once"
B. Sort by start, heap of ends. Equivalently, sweep +1/−1 events — same answer, and worth naming as the alternative.
"remove the fewest", "the minimum arrows"
C. Sort by end, greedy accept. Both phrasings are the same problem.
"can one person attend all"
A, reduced: sort by start and return false at the first overlap.
The < versus <= decisionIn LC 56, [1,2] and [2,3] do merge — so the test is cur[0] <= last[1]. In LC 253, a meeting ending at 2 and another starting at 2 do not conflict, because the room frees at the end instant — so the reuse test is peek() <= start. In LC 452, an arrow at a shared endpoint does burst both balloons. Each of these is stated or implied by the examples; read them rather than guessing.
The three bugs that actually happenForgetting Math.max when extending — a contained interval shortens the merged end, and the failure only appears on inputs with nesting. Integer overflow in the comparator — a[0] - b[0] overflows when coordinates span the int range, which LC 452 tests directly; use Integer.compare. Sorting by the wrong end — sorting by start in an activity-selection problem picks a long early interval and loses several short ones, which passes the first example and fails the rest.
