Anchor 1 · LC 208 — the path to the solution

Why not a hash set
insert and search would be O(1), but startsWith would have to scan every stored word. The prefix operation is what forces the structure.
The shape
A 26-way tree where the edges carry letters. Spelling a word walks a path; a shared prefix walks shared nodes.
The flag
isWord distinguishes "a word ends here" from "this is merely on the way to one". Without it, search("app") returns true after inserting only "apple".
Why search and startsWith share a walk
Both follow the same path; they differ only in what they check at the end. startsWith asks whether the node exists, search asks whether it is flagged.
Array over map
Input is lowercase only, so TrieNode[26] avoids hashing entirely and the null check is the membership test.
Edge case
The empty string is a valid prefix of everything and returns true from startsWith — the walk simply makes no steps.
LC 208 · O(L) per operation, O(total chars × 26) space
class Trie {
    private static class Node {
        Node[] children = new Node[26];
        boolean isWord;
    }

    private final Node root = new Node();

    public void insert(String word) {
        Node cur = root;
        for (char c : word.toCharArray()) {
            int i = c - 'a';
            if (cur.children[i] == null) cur.children[i] = new Node();
            cur = cur.children[i];
        }
        // Without this flag, "app" would appear present merely
        // because "apple" laid down the path.
        cur.isWord = true;
    }

    public boolean search(String word) {
        Node n = walk(word);
        return n != null && n.isWord;       // the path AND the flag
    }

    public boolean startsWith(String prefix) {
        return walk(prefix) != null;        // the path alone
    }

    private Node walk(String s) {
        Node cur = root;
        for (char c : s.toCharArray()) {
            cur = cur.children[c - 'a'];
            if (cur == null) return null;   // check BEFORE the next step
        }
        return cur;
    }
}

Anchor 2 · LC 212 — the path to the solution

Brute force
Run a single-word grid search once per dictionary word. With 3×10⁴ words that is 3×10⁴ full board traversals — far too slow.
What is wasted
Every one of those searches re-walks the same board cells. Words sharing a prefix repeat identical work.
The inversion
Traverse the board once, carrying a trie pointer alongside the position. The trie answers "does any word continue this way?" with a single null check.
Why that prunes so well
A path dies as soon as no dictionary word shares its prefix — often at depth 1. Most of the board is rejected almost immediately.
Store the word, not a flag
Keeping the whole string at its terminal node means you can emit it directly, with no need to reconstruct the path.
Two optimisations
Null the stored word after collecting it, so duplicates are impossible. And null out exhausted child links so the trie shrinks as the search proceeds — that is what makes the large tests pass.
LC 212 · O(mn·4^L) worst case, O(total chars) space
class Solution {
    private static final int[][] DIRS = {{1,0},{-1,0},{0,1},{0,-1}};

    private static class Node {
        Node[] children = new Node[26];
        String word;                 // the whole word, not just a flag
    }

    public List<String> findWords(char[][] board, String[] words) {
        Node root = new Node();
        for (String w : words) {     // build the trie
            Node cur = root;
            for (char c : w.toCharArray()) {
                int i = c - 'a';
                if (cur.children[i] == null) cur.children[i] = new Node();
                cur = cur.children[i];
            }
            cur.word = w;
        }

        List<String> out = new ArrayList<>();
        for (int r = 0; r < board.length; r++)
            for (int c = 0; c < board[0].length; c++)
                dfs(board, r, c, root, out);
        return out;
    }

    private void dfs(char[][] b, int r, int c, Node node, List<String> out) {
        if (r < 0 || r >= b.length || c < 0 || c >= b[0].length) return;

        char ch = b[r][c];
        if (ch == '#') return;                  // already on this path

        Node next = node.children[ch - 'a'];
        if (next == null) return;               // no word continues — PRUNE

        if (next.word != null) {
            out.add(next.word);
            next.word = null;                   // collect exactly once
        }

        b[r][c] = '#';
        for (int[] d : DIRS) dfs(b, r + d[0], c + d[1], next, out);
        b[r][c] = ch;                           // restore

        // Dead branch: no words left below it. Cutting it shrinks the
        // trie as the search runs, which is what makes this fast.
        boolean empty = true;
        for (Node child : next.children) if (child != null) { empty = false; break; }
        if (empty && next.word == null) node.children[ch - 'a'] = null;
    }
}

211 · Add and Search Words wildcard

Path: ordinary insert; the search is what changes, because . matches any letter.

Delta: the walk becomes a recursion. On a concrete letter, follow that one child. On a dot, try all 26 and return true if any succeeds.

Watch for: the recursion must check node == null at entry, since a dot branch will hand it null children. A word of all dots costs O(26^L), which the constraints bound at length 3 — worth saying aloud.

648 · Replace Words shortest root

Path: for each word in the sentence, find the shortest dictionary root that prefixes it.

Delta: walk the word letter by letter and stop at the first node with isWord set — because you walk in increasing length, the first hit is the shortest root. If the walk breaks or no flag is found, keep the original word.

Watch for: returning at the first flag is what makes it the shortest. Walking to the end and taking the last flag gives the longest root, which is the wrong answer.

677 · Map Sum Pairs values

Path: store an integer per key, and sum the values of every key sharing a prefix.

Delta: nodes hold an int value. sum(prefix) walks to the prefix node and then totals its whole subtree with a DFS.

Watch for: inserting an existing key replaces its value rather than adding. If you instead keep a running sum on each node for speed, you must propagate the delta — new value minus old — or repeated inserts inflate the totals.

1268 · Search Suggestions System ordered children

Path: after each typed character, suggest up to three matching products in lexicographic order.

Delta: walk to the prefix node, then DFS its subtree visiting children from index 0 to 25 — that order is alphabetical, so the first three words found are the answer with no sorting.

Watch for: sorting the product list and binary searching for the prefix range is an equally valid O(n log n) solution and is shorter to write. Offer both; the trie is the better answer when queries are repeated.

If you only drill twoDo 208 and 212. 208 fixes the node shape and the isWord distinction that every other problem here depends on. 212 teaches the inversion that defines the pattern — traversing the search space once while the trie tells you when to stop — plus the two pruning tricks that turn a correct solution into a fast one.
