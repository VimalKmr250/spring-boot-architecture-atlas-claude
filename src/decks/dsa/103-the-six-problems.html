Six enumerations, one skeleton

78 and 77 differ by where you record. 39 changes the start index to allow reuse. 46 switches to a used array. 90 and 47 add the two dedup rules — which are different from each other, and that difference is the point.

Anchor 1 · LC 78 — the path to the solution

The bitmask alternative
For n ≤ 20, loop a mask from 0 to 2ⁿ − 1 and include element j when bit j is set. Iterative, no recursion, and a genuinely good answer — offer it.
The recursive view
At each element there are two choices: include it or not. That binary tree has 2ⁿ leaves, one per subset.
The loop formulation
Rather than an explicit include/exclude branch, loop over the remaining candidates. Each iteration is the include branch; moving to the next iteration is the exclude branch.
Why every node counts
Each partial path is itself a valid subset, so record on entry rather than at leaves. That is what makes subsets simpler than combinations.
Why order is not duplicated
start = i + 1 means the sweep only ever moves right, so [2,1] is unreachable. No sorting or set is needed for distinct input.
Edge case
The empty subset is included automatically — it is the very first recorded value, at the root.
LC 78 · O(n·2ⁿ) time, O(n) space beyond the output
class Solution {
    public List<List<Integer>> subsets(int[] nums) {
        List<List<Integer>> out = new ArrayList<>();
        backtrack(nums, 0, new ArrayList<>(), out);
        return out;
    }

    private void backtrack(int[] nums, int start,
                           List<Integer> path, List<List<Integer>> out) {
        // EVERY node is a valid subset, including the empty one,
        // so record on entry with no filter at all.
        out.add(new ArrayList<>(path));    // COPY, not the live list

        for (int i = start; i < nums.length; i++) {

            path.add(nums[i]);                          // choose

            // i + 1: the sweep only moves right, so [2,1] can never
            // be generated and no de-duplication is needed.
            backtrack(nums, i + 1, path, out);          // explore

            path.remove(path.size() - 1);               // un-choose
        }
    }
}

Anchor 2 · LC 47 — the path to the solution

The lazy fix
Generate all n! permutations and push them through a HashSet. Correct, but it does the full exponential work and then discards most of it. Say it, then do better.
The right approach
Prune duplicate branches before exploring them, so the identical work is never done.
The rule
Sort first so equal values are adjacent. Then at each depth, among a run of equal values, allow only the leftmost unused copy to be chosen.
Why !used[i-1]
If the previous equal copy is currently in use, we are deeper in a branch that already took it — so this copy is a legitimate second occurrence. If it is not in use, it was already tried and undone at this depth, so choosing this copy would repeat an identical branch.
Why the other rule does not work here
The combination rule i > start relies on a left-to-right sweep. Permutations revisit every index at every depth, so there is no start to compare against — hence a different test.
Edge case
The sort is mandatory. Without it, equal values are not adjacent and the rule silently does nothing.
LC 47 · O(n·n!) worst case, O(n) space beyond the output
class Solution {
    public List<List<Integer>> permuteUnique(int[] nums) {
        Arrays.sort(nums);                 // MANDATORY: equal values adjacent

        List<List<Integer>> out = new ArrayList<>();
        backtrack(nums, new boolean[nums.length], new ArrayList<>(), out);
        return out;
    }

    private void backtrack(int[] nums, boolean[] used,
                           List<Integer> path, List<List<Integer>> out) {
        if (path.size() == nums.length) {
            out.add(new ArrayList<>(path));
            return;
        }

        for (int i = 0; i < nums.length; i++) {
            if (used[i]) continue;

            // Among equal values, only the LEFTMOST unused copy may be
            // chosen at this depth. If nums[i-1] is not used, it was
            // already tried and undone here — taking nums[i] now would
            // repeat an identical branch.
            if (i > 0 && nums[i] == nums[i - 1] && !used[i - 1]) continue;

            used[i] = true;
            path.add(nums[i]);

            backtrack(nums, used, path, out);

            path.remove(path.size() - 1);      // undo BOTH mutations
            used[i] = false;
        }
    }
}

77 · Combinations record at depth k

Path: the same tree as subsets, but only nodes at depth k are answers.

Delta: move the record into a base case — if (path.size() == k) { collect; return; }.

Watch for: the pruning is worth adding. If fewer than k − path.size() candidates remain, the branch cannot complete, so bound the loop at n - (k - path.size()) + 1. It converts a slow solution into a fast one on the larger inputs.

39 · Combination Sum start = i

Path: candidates are distinct but each may be reused without limit, and the target bounds the depth.

Delta: recurse with i instead of i + 1, which permits reuse while still forbidding reorderings. Record when the remaining target reaches exactly 0, and abandon the branch when it goes negative.

Watch for: sorting first lets you break rather than continue once a candidate exceeds the remainder — every later candidate is larger, so the whole rest of the loop is dead.

46 · Permutations used[]

Path: order matters, so the left-to-right sweep no longer applies — every unused index is a candidate at every depth.

Delta: drop start entirely, loop from 0, and guard with a boolean[] used. Record at depth n.

Watch for: there are now two mutations to undo — the path entry and the used flag. Restoring only one is the classic failure, and it produces too few permutations rather than an obvious crash.

90 · Subsets II i > start

Path: subsets of an input with repeats. Collecting into a set works but does the full work first.

Delta: sort, then if (i > start && nums[i] == nums[i-1]) continue;. This lets the first copy at a given depth through and blocks the rest.

Watch for: i > start, not i > 0. With i > 0 the second copy is blocked even one level deeper, so [1,1] never appears — and the answer is missing entries rather than having extra ones.

If you only drill twoDo 78 and 47. 78 fixes the skeleton and the copy-on-record habit that every problem here depends on. 47 is where the two dedup rules become distinguishable — being able to explain why combinations use i > start while permutations use !used[i-1] is the difference between remembering two lines and understanding them.
