Pay once up front, answer every range for free

Build an array where P[i] is the sum of everything before index i. Then the sum of any range [l, r] is P[r+1] − P[l] — one subtraction, O(1), no matter how wide the range. That single identity is the whole pattern.

The invariant

P[0] = 0, and P[i] = a[0] + … + a[i−1]. The leading zero is not decoration: it is what makes ranges starting at index 0 need no special case.

So P has length n + 1. Sizing it n is the most common implementation error here, and it forces an if (l == 0) branch that then gets the boundary wrong.

Build is O(n) once; every subsequent range query is O(1). The trade is O(n) extra memory, which is almost always worth it the moment there is more than one query.

The second move — counting with a map

Range lookup is only half the pattern. The other half answers "how many subarrays sum to K?" without examining any range at all.

A subarray (l, r] sums to K exactly when P[r] − P[l] = K, that is when P[l] = P[r] − K. So as you sweep r, ask a hash map how many earlier prefixes equalled P[r] − K and add that count.

This works with negative numbers, which is exactly the case a sliding window cannot handle — there the window has no valid shrink rule, because extending it may raise or lower the sum.

Applies when

Repeated range sum queries on a static array, or any "count the subarrays whose sum has property X" question — including sums that are negative, where a window has no valid shrink rule.

Does not apply when

The array is updated between queries — that needs a Fenwick or segment tree, since every update would rebuild O(n) of the prefix array. Also when the question is about a longest run rather than a count and all values are positive; a window is cheaper there.

Complexity

O(n) to build, O(1) per range query. The counting variant is O(n) total with O(n) map space. Always accumulate in long: 10⁵ values of 10⁹ overflows int.
