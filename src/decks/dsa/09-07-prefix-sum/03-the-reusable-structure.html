Two skeletons: build-and-query, and sweep-and-count

The first materialises the prefix array because there will be many queries. The second never stores it at all — it keeps one running sum and a map, because it only ever needs to compare the current prefix against earlier ones.

Skeleton A · build once, query O(1) (LC 303, 724)
// P has length n + 1 and P[0] = 0. That leading zero is what
// removes every "does the range start at index 0?" special case.
class PrefixSum {
    private final long[] P;

    PrefixSum(int[] a) {
        P = new long[a.length + 1];          // n + 1, never n
        for (int i = 0; i < a.length; i++) {
            P[i + 1] = P[i] + a[i];          // long: 1e5 * 1e9 overflows int
        }
    }

    /** Inclusive on both ends. */
    long range(int l, int r) {
        return P[r + 1] - P[l];              // one subtraction, any width
    }
}
Skeleton B · sweep and count (LC 560, 930, 974, 523)
// No prefix ARRAY is built. One running sum, one map of
// "how many times has this prefix value occurred so far".
int countSubarraysSummingTo(int[] a, int k) {
    Map<Long, Integer> seen = new HashMap<>();
    seen.put(0L, 1);                    // the empty prefix — never omit this

    long sum = 0;
    int count = 0;

    for (int v : a) {
        sum += v;

        // LOOK UP FIRST. With k == 0 the key equals `sum`,
        // so inserting first would let a prefix match itself.
        count += seen.getOrDefault(sum - k, 0);

        seen.merge(sum, 1, Integer::sum);
    }
    return count;
}
The modular variant — when the question is "divisible by k" (LC 974, 523)
/**
 * A subarray sum is divisible by k exactly when its two end
 * prefixes have the SAME remainder mod k:
 *     (P[r] - P[l]) % k == 0   is the same as   P[r] % k == P[l] % k
 *
 * So the map is keyed on the remainder, not on the sum itself,
 * and it never grows beyond k entries.
 */
int subarraysDivByK(int[] a, int k) {
    int[] seen = new int[k];        // remainders are 0..k-1, so an array beats a map
    seen[0] = 1;                    // the empty prefix again

    int sum = 0, count = 0;

    for (int v : a) {
        sum += v;

        // Java's % returns a NEGATIVE remainder for negative operands,
        // so -1 % 5 is -1, not 4. This normalisation is mandatory,
        // and forgetting it is the single most common failure here.
        int r = ((sum % k) + k) % k;

        count += seen[r];
        seen[r]++;
    }
    return count;
}

Choosing the skeleton

Many range queries
Skeleton A. Build the array once in the constructor; the whole point is that the queries are then free.
Count subarrays
Skeleton B. Do not build the array — you only ever need the current prefix and a tally of earlier ones.
Divisible by k
The modular variant, keyed on the normalised remainder. An int[k] beats a HashMap.
A multiple of k, length ≥ 2
Store the first index at which each remainder appeared rather than a count, so you can enforce the minimum length.
Balance point
Compare left against total − left − a[i] as you sweep. No map and no array at all.
The three bugs that actually happenOmitting the {0:1} seed — every subarray that starts at index 0 goes uncounted, and the answer is quietly too low on exactly the inputs where the prefix first equals k. Negative remainders — Java's % can return a negative value, so seen[sum % k] throws or silently mis-buckets; always normalise with ((x % k) + k) % k. int accumulation — 10⁵ elements of 10⁹ overflows long before anything looks wrong, and the count comes back plausible but incorrect.
