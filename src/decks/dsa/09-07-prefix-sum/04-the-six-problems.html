Anchor 1 · LC 560 — the path to the solution

Brute force
Every pair (l, r) with a fresh inner sum. O(n³), or O(n²) if the inner loop accumulates as it goes.
Why not a window
Because nums[i] may be negative. Extending the window can raise or lower the sum, so "shrink while too large" is not a valid rule. Say this out loud — it is the step that shows you chose the pattern rather than guessed it.
The reformulation
A subarray ending at r sums to k exactly when an earlier prefix equalled P[r] − k. That turns a search over ranges into a lookup on a single number.
Why counts, not positions
Several earlier prefixes may share a value, and each one yields a distinct subarray. Step 5 of the trace adds two at once for exactly this reason.
Edge cases
Seed {0:1}. Look up before inserting, which matters when k = 0. Accumulate in long.
LC 560 · O(n) time, O(n) space
class Solution {
    public int subarraySum(int[] nums, int k) {
        // prefix value -> how many times it has occurred
        Map<Long, Integer> seen = new HashMap<>();
        seen.put(0L, 1);            // the empty prefix

        long sum = 0;
        int count = 0;

        for (int v : nums) {
            sum += v;

            // Every earlier prefix equal to (sum - k) marks the
            // start of a distinct subarray ending here.
            count += seen.getOrDefault(sum - k, 0);

            // Insert AFTER the lookup: with k == 0 the keys coincide.
            seen.merge(sum, 1, Integer::sum);
        }
        return count;
    }
}

Anchor 2 · LC 974 — the path to the solution

Brute force
All O(n²) subarrays, testing each sum for divisibility. Too slow at n = 3×10⁴.
The observation
(P[r] − P[l]) % k == 0 is the same statement as P[r] % k == P[l] % k. So the question becomes "how many earlier prefixes share my remainder?" — the counting skeleton with the key changed.
Why an array beats a map
There are only k possible remainders, so int[k] is exact, faster, and needs no boxing.
The real difficulty
Java defines % to take the sign of the dividend, so -1 % 5 is -1, not 4. Indexing an array with that throws; using it as a map key silently splits one remainder class into two and returns a wrong count.
The fix
((sum % k) + k) % k. Write it every time, even when the input looks non-negative — the running sum can still go negative.
LC 974 · O(n) time, O(k) space
class Solution {
    public int subarraysDivByK(int[] nums, int k) {
        // There are only k possible remainders, so index them directly.
        int[] seen = new int[k];
        seen[0] = 1;                // the empty prefix

        int sum = 0, count = 0;

        for (int v : nums) {
            sum += v;

            // Java's % takes the sign of the dividend: -1 % 5 == -1.
            // Normalise into [0, k) or this indexes out of bounds.
            int r = ((sum % k) + k) % k;

            // Every earlier prefix with the same remainder gives a
            // subarray whose sum is divisible by k.
            count += seen[r];
            seen[r]++;
        }
        return count;
    }
}

303 · Range Sum Query — Immutable skeleton A

Path: summing the range per call is O(n) each, and the problem says sumRange is called up to 10⁴ times. The word immutable in the title is the hint: the array never changes, so precomputing is safe.

Delta: skeleton A verbatim. Build P in the constructor, return P[r+1] − P[l].

Watch for: sizing P at n instead of n+1. It compiles, and then l = 0 needs a branch that is easy to get wrong.

724 · Find Pivot Index skeleton A, streamed

Path: computing both sides for every candidate is O(n²). One total plus a running left sum makes it O(n) with no array.

Delta: take total first, then sweep keeping left. The right side is total − left − nums[i]; return i the first time the two match.

Watch for: index 0 is a legal pivot with an empty left side summing to 0 — so test before adding nums[i] to left, not after.

930 · Binary Subarrays With Sum skeleton B

Path: the values are only 0 and 1, so the prefix sum is non-decreasing and bounded by n. That means the map can be a plain array.

Delta: skeleton B with int[n + 1] in place of the HashMap, indexed by the prefix sum itself. Everything else is unchanged.

Watch for: goal may be 0, which makes the lookup key equal the current sum — the look-up-before-insert ordering is what keeps that correct.

523 · Continuous Subarray Sum skeleton B, modular

Path: same remainder reformulation, but the problem demands a subarray of length at least two, so a raw count is not enough.

Delta: store the first index at which each remainder appeared, not a count. On a repeat, return true only when i − firstIndex ≥ 2. Seed with remainder 0 at index −1 so a qualifying prefix from the start still works.

Watch for: record the index only when the remainder is new — overwriting it destroys the earliest occurrence and loses valid answers.

If you only drill twoDo 560 and 974. 560 is the counting reformulation in its plainest form, and the look-up-before-insert ordering it teaches applies to every problem on this slide. 974 adds the one piece of Java-specific knowledge in this pattern — that % can return a negative remainder — which is the difference between a correct submission and a runtime exception.
