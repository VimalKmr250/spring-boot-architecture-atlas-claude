A double loop, and where the base cases go

The body is one line. The engineering is in handling the first row and column — either explicitly, or by padding the table so they stop being special.

Path counting, with padding (LC 62, 63)
// PADDING: an extra row and column of zeros means every real cell
// has both neighbours, so the main loop needs no boundary checks.
int uniquePaths(int rows, int cols) {
    // dp[r][c] corresponds to grid cell (r-1, c-1)
    int[][] dp = new int[rows + 1][cols + 1];

    // One seed to start the accumulation. Placing it here makes
    // dp[1][1] come out as 1, which is correct for the start cell.
    dp[0][1] = 1;

    for (int r = 1; r <= rows; r++)
        for (int c = 1; c <= cols; c++)
            dp[r][c] = dp[r - 1][c] + dp[r][c - 1];

    return dp[rows][cols];
}

// With OBSTACLES (LC 63), a blocked cell is simply unreachable:
// set it to 0 and everything downstream adjusts automatically.
if (grid[r - 1][c - 1] == 1) dp[r][c] = 0;
else                         dp[r][c] = dp[r - 1][c] + dp[r][c - 1];
Minimum cost, with explicit base cases (LC 64)
// Without padding, fill the first row and column first — there is
// no choice to make there, only accumulation.
int minPathSum(int[][] grid) {
    int rows = grid.length, cols = grid[0].length;
    int[][] dp = new int[rows][cols];

    dp[0][0] = grid[0][0];

    // Top row: reachable only from the left.
    for (int c = 1; c < cols; c++) dp[0][c] = dp[0][c - 1] + grid[0][c];

    // Left column: reachable only from above.
    for (int r = 1; r < rows; r++) dp[r][0] = dp[r - 1][0] + grid[r][0];

    for (int r = 1; r < rows; r++)
        for (int c = 1; c < cols; c++)
            dp[r][c] = grid[r][c] + Math.min(dp[r - 1][c], dp[r][c - 1]);

    return dp[rows - 1][cols - 1];
}

// several cells below, so the transition widens rather than changes.
// Working BOTTOM-UP removes the need to scan the last row at the end.

The knobs

Combining operation
+ to count paths, min for a cheapest path, 1 + min(three) for the largest square.
Base cases
Pad when the sentinel is natural — 0 for counting or summing. Fill explicitly when it is not, as with a minimum where 0 would win incorrectly.
Direction
Top-down for start-to-end problems; bottom-up when the destination is any cell of the last row, which avoids a final scan.
Answer cell
dp[rows−1][cols−1] for paths, max(dp) for the largest square, dp[0] after a bottom-up fill.
Space
One rolling row of width cols, or overwrite the input grid when mutation is allowed — say so before doing it.
The three bugs that actually happenPadding a minimisation with zeros — the sentinel then wins every min and every path costs nothing. Pad with a large value, or fill the base cases explicitly. Reading dp[r][c−1] after overwriting it in the rolling form — the two reads must happen before the write, which is why order matters there. Returning the side length in LC 221 — the question asks for the area, so square it.
