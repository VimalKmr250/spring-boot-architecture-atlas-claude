One bounded heap, and the comparators that configure it

The loop is five lines. Everything problem-specific lives in the comparator and in which direction the heap runs — so getting those two right is the whole job.

The template — the k largest, with a bounded min-heap
/**
 * Keep at most k items. MIN-heap, so the root is the weakest
 * of the current best k — the one to evict when something better
 * arrives.  O(n log k) time, O(k) space.
 */
int kthLargest(int[] a, int k) {
    // Java's PriorityQueue is a MIN-heap by default, which is
    // exactly what "k largest" wants. No comparator needed.
    PriorityQueue<Integer> heap = new PriorityQueue<>();

    for (int v : a) {
        heap.offer(v);

        // Never let it exceed k. Evicting the root drops the
        // smallest, which is always the right one to lose.
        if (heap.size() > k) heap.poll();
    }
    return heap.peek();     // smallest of the top k == the k-th largest
}

// The one-comparison variant: cheaper, because most arrivals
// fail the test and never touch the heap structure at all.
for (int v : a) {
    if (heap.size() < k)        heap.offer(v);
    else if (v > heap.peek()) { heap.poll(); heap.offer(v); }
    // else: discard in O(1)
}
Comparators — the part that is actually problem-specific
// k LARGEST values  -> min-heap (the default)
new PriorityQueue<Integer>();

// k SMALLEST values -> max-heap
new PriorityQueue<Integer>(Comparator.reverseOrder());

// k CLOSEST points  -> max-heap on squared distance, so the
// FARTHEST sits at the root ready to be evicted.
// Compare squared distances: no sqrt, no floating point.
new PriorityQueue<int[]>((p, q) ->
        (q[0]*q[0] + q[1]*q[1]) - (p[0]*p[0] + p[1]*p[1]));

// k MOST FREQUENT  -> min-heap on the count
new PriorityQueue<Map.Entry<Integer,Integer>>(
        Map.Entry.comparingByValue());

// MIXED KEYS — least frequent first, and among equal counts the
// LEXICOGRAPHICALLY LARGEST first, so the worst candidate is
// always at the root and gets evicted.
new PriorityQueue<Map.Entry<String,Integer>>((x, y) ->
        x.getValue().equals(y.getValue())
            ? y.getKey().compareTo(x.getKey())     // reversed!
            : x.getValue() - y.getValue());
Quickselect — O(n) average for a single k-th query
// Beats the heap on average, but is O(n^2) worst case and
// REORDERS the input. Offer the heap first, then this.
int quickselect(int[] a, int k) {
    int target = a.length - k;        // k-th largest == index n-k when sorted
    int lo = 0, hi = a.length - 1;
    Random rnd = new Random();        // randomise or sorted input is O(n^2)

    while (true) {
        int p = lo + rnd.nextInt(hi - lo + 1);
        int pos = partition(a, lo, hi, p);

        if (pos == target) return a[pos];
        if (pos < target) lo = pos + 1;   // discard the left half entirely
        else              hi = pos - 1;
    }
}

private int partition(int[] a, int lo, int hi, int p) {
    int pivot = a[p];
    swap(a, p, hi);
    int store = lo;
    for (int i = lo; i < hi; i++) {
        if (a[i] < pivot) swap(a, store++, i);
    }
    swap(a, store, hi);
    return store;
}

The knobs

Direction
The root must hold the item you would sacrifice first. k largest → min-heap; k smallest → max-heap.
Bound
Poll whenever size exceeds k. Skipping this makes it O(n log n) with O(n) memory, which defeats the point on a stream.
Comparator
The only genuinely problem-specific code. When two keys are involved, the tie-break is usually reversed relative to intuition, because the root is the loser.
When to beat it
If frequencies bound the values, bucket by count for O(n). If a single k-th query is wanted and mutating the input is allowed, quickselect averages O(n).
Streaming
Make the heap a field and keep it bounded. That is the whole design for a k-th-largest-so-far class.
The three bugs that actually happenThe heap pointing the wrong way — a max-heap for "k largest" evicts your best element every time, and the result looks plausible on small inputs. Integer overflow in a comparator — a - b overflows when the values span the int range; use Integer.compare(a, b). Forgetting to reverse the tie-break — in LC 692 the root must hold the worst candidate, so among equal counts the lexicographically largest word sorts first, which reads backwards until you remember what the root is for.
