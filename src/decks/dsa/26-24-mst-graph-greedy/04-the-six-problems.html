Anchor 1 · LC 1584 — the path to the solution

The restatement
Every pair of points can be joined at a cost equal to their Manhattan distance, and you must connect them all as cheaply as possible. That is a minimum spanning tree on a complete graph.
Kruskal's cost here
The graph is complete, so there are n(n−1)/2 edges — about 500,000 at n = 1000. Building and sorting them is O(n² log n) and does pass.
Why Prim is better
Prim never materialises the edge list. It keeps, for each node outside the tree, the cheapest edge into the tree — an array of n values that is refreshed after each addition.
Linear scan instead of a heap
With n ≤ 1000, scanning for the minimum is O(n) and the whole algorithm is O(n²) — simpler than a heap and no lazy deletion to get right.
The one distinction
Prim's key is the edge weight alone, not an accumulated distance. Adding best[u] to it turns this into Dijkstra and builds the wrong tree.
Edge case
A single point needs no edges and costs 0, which the loop handles because best[0] starts at 0.
LC 1584 · O(n²) time, O(n) space
class Solution {
    public int minCostConnectPoints(int[][] points) {
        int n = points.length;

        boolean[] inTree = new boolean[n];
        int[] best = new int[n];              // cheapest edge INTO the tree
        Arrays.fill(best, Integer.MAX_VALUE);
        best[0] = 0;                          // start anywhere

        int total = 0;

        for (int iter = 0; iter < n; iter++) {
            // Cheapest node not yet attached. O(n) scan beats a heap
            // here, because the graph is complete anyway.
            int u = -1;
            for (int v = 0; v < n; v++)
                if (!inTree[v] && (u == -1 || best[v] < best[u])) u = v;

            inTree[u] = true;
            total += best[u];

            for (int v = 0; v < n; v++) {
                if (inTree[v]) continue;

                int d = Math.abs(points[u][0] - points[v][0])
                      + Math.abs(points[u][1] - points[v][1]);

                // The key is the EDGE weight alone. Writing
                // best[u] + d would make this Dijkstra.
                if (d < best[v]) best[v] = d;
            }
        }
        return total;
    }
}

Anchor 2 · LC 778 — the path to the solution

The restatement
You may swim between adjacent cells once the water level reaches both. The answer is the smallest level at which the top-left and bottom-right become connected — a bottleneck, not a sum.
Why not Dijkstra on sums
The cost of a path is its maximum cell, so adding cell values is meaningless. Dijkstra still applies with max in place of +, and that is one good solution.
The union-find view
Sort the cells by height. Raise the water level one cell at a time, unioning each newly submerged cell with its already-submerged neighbours. The first moment the two corners share a component is the answer.
Why that is correct
Adding cells in increasing height means the level when they connect is exactly the largest cell either path must cross — which is the definition of the bottleneck.
The third solution
Binary search the answer and run a flood fill to test connectivity. O(n² log n) as well, and worth naming.
Edge case
The answer is at least max(grid[0][0], grid[n-1][n-1]) — both corners must be submerged before any swim is possible.
LC 778 · O(n² log n) time, O(n²) space
class Solution {
    public int swimInWater(int[][] grid) {
        int n = grid.length;

        // Where each height lives — heights are a permutation of 0..n*n-1.
        int[] cellOfHeight = new int[n * n];
        for (int r = 0; r < n; r++)
            for (int c = 0; c < n; c++)
                cellOfHeight[grid[r][c]] = r * n + c;

        DSU dsu = new DSU(n * n);
        boolean[] submerged = new boolean[n * n];
        int[][] DIRS = {{1,0},{-1,0},{0,1},{0,-1}};

        // Raise the water one height at a time.
        for (int t = 0; t < n * n; t++) {
            int cell = cellOfHeight[t];
            int r = cell / n, c = cell % n;
            submerged[cell] = true;

            // Join to any neighbour already under water.
            for (int[] d : DIRS) {
                int nr = r + d[0], nc = c + d[1];
                if (nr < 0 || nr >= n || nc < 0 || nc >= n) continue;
                if (submerged[nr * n + nc]) dsu.union(cell, nr * n + nc);
            }

            // Because cells are added in increasing height, the moment
            // the corners connect, t IS the smallest sufficient level.
            if (dsu.connected(0, n * n - 1)) return t;
        }
        return -1;   // unreachable: every cell is eventually submerged
    }
}

1135 · Connecting Cities With Minimum Cost Kruskal Premium

Path: the textbook statement — an edge list with weights, connect everything as cheaply as possible.

Delta: Kruskal verbatim. Sort, union, accumulate, and return −1 if fewer than n − 1 edges were accepted.

Premium: paywalled. LC 1584 above is the same algorithm on an implicit graph, and 1584 plus 1168's virtual-node idea covers everything this problem teaches.

1168 · Optimize Water Distribution virtual node Premium

Path: two different cost types — a well at a house, or a pipe between houses — which looks like it is not an MST at all.

Delta: invent node 0 as "the water source" and turn each well into an edge from 0 to that house. Every cost is now an edge, and an ordinary MST over n + 1 nodes gives the answer.

Premium: paywalled, but the trick is the most transferable idea in this pattern — whenever one cost is per-node rather than per-edge, look for the virtual node that converts it.

1489 · Critical and Pseudo-Critical Edges Kruskal × E

Path: compute the MST weight once as a baseline. Then classify each edge by forcing it out and forcing it in.

Delta: an edge is critical if excluding it raises the MST weight or disconnects the graph. It is pseudo-critical if including it first still yields the baseline weight. Everything else matters not at all.

Watch for: tag each edge with its original index before sorting, or you cannot report which edges you classified. With E ≤ 200, running Kruskal 2E times is comfortably fast.

1102 · Path With Maximum Minimum Value sorted union-find Premium

Path: the exact mirror of 778 — maximise the smallest cell on a path instead of minimising the largest.

Delta: add cells in decreasing value, unioning with already-added neighbours. The value at which the two corners connect is the answer. A max-heap Dijkstra with min in place of + works equally well.

Premium: paywalled. 778 above is the same problem mirrored, and solving it gives you this one for free — flip the sort direction and the comparison.

If you only drill twoDo 1584 and 778. 1584 fixes both MST algorithms and the distinction between Prim's edge-weight key and Dijkstra's accumulated distance. 778 teaches the bottleneck reframing — that "minimise the maximum along a path" is a connectivity question in disguise, answered by adding edges in sorted order and watching for the moment two nodes join.
