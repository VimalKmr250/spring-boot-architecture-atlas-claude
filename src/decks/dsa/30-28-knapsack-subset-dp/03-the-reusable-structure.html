One array, and two loop decisions

The body barely changes between problems. What changes is the direction of the capacity loop and, when counting, which loop sits outside — and those two choices define four different problems.

0/1 knapsack — each item at most once
/**
 * dp[c] = the best value achievable with capacity exactly c
 *         (or "is c reachable", for the boolean form).
 *
 * The capacity loop runs BACKWARDS. Reading dp[c - w] before it is
 * overwritten means reading the PREVIOUS row — so this item has not
 * yet been used, and cannot be used twice.
 */
boolean canPartition(int[] nums) {
    int total = 0;
    for (int v : nums) total += v;

    // Two equal halves need an even total. Cheap impossibility test.
    if (total % 2 != 0) return false;
    int target = total / 2;

    boolean[] dp = new boolean[target + 1];
    dp[0] = true;                       // the empty subset sums to 0

    for (int v : nums) {
        // BACKWARDS. Forwards would let one item be counted repeatedly.
        for (int c = target; c >= v; c--) {
            dp[c] |= dp[c - v];
        }
    }
    return dp[target];
}
Unbounded, and the counting loop order (LC 518)
// UNBOUNDED: capacity FORWARDS, so dp[c - coin] may already
// include this coin — which is exactly reuse.
//
// COMBINATIONS vs PERMUTATIONS is a SEPARATE decision, made by
// which loop is on the outside:

// items OUTER  ->  COMBINATIONS. Each coin is fully considered
// before the next, so 1+2 and 2+1 are the same single way.
int change(int amount, int[] coins) {
    int[] dp = new int[amount + 1];
    dp[0] = 1;                          // one way to make zero: take nothing

    for (int coin : coins) {            // items outside
        for (int c = coin; c <= amount; c++) {   // capacity forwards
            dp[c] += dp[c - coin];
        }
    }
    return dp[amount];
}

// capacity OUTER  ->  PERMUTATIONS. Every coin is reconsidered at
// every amount, so 1+2 and 2+1 count separately. That is LC 377,
// a different problem with almost identical code.
// for (int c = 1; c <= amount; c++)
//     for (int coin : coins)
//         if (coin <= c) dp[c] += dp[c - coin];
Reframing a problem into a knapsack (LC 494, 1049)
// LC 494 — assign + or - to every number so the total is `target`.
// Let P be the positives and N the negatives:
//     P - N = target   and   P + N = total
//  => P = (total + target) / 2
// So it becomes: COUNT the subsets summing to that value.
int findTargetSumWays(int[] nums, int target) {
    int total = 0;
    for (int v : nums) total += v;

    // Impossible if out of range, or if the split is not an integer.
    if (Math.abs(target) > total || (total + target) % 2 != 0) return 0;
    int subsetSum = (total + target) / 2;

    int[] dp = new int[subsetSum + 1];
    dp[0] = 1;

    for (int v : nums)
        for (int c = subsetSum; c >= v; c--)   // 0/1, so BACKWARDS
            dp[c] += dp[c - v];

    return dp[subsetSum];
}

// The result is |P - N| where P + N = total, so minimising it
// means getting P as close to total/2 as possible: a 0/1 knapsack

The three bugs that actually happenCapacity loop forwards in a 0/1 problem — items get reused and the answer is too large. On [1,1] with target 2 it reports true from a single 1. Loop order wrong when counting — combinations become permutations, so LC 518 returns a much larger number that still looks plausible. dp[0] left at zero — the empty subset is a genuine way to make 0, and omitting it makes every count zero.
