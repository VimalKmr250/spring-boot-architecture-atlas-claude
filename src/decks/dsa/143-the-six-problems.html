Anchor 1 · LC 136 — the path to the solution

Brute force
A HashMap of counts, or a HashSet toggled by add and remove. O(n) time but O(n) space — and the problem explicitly demands constant space.
Sorting
Sort and scan for the element without a neighbour. O(n log n) time, O(1) space, and it mutates the input. A reasonable second answer.
The observation
You need an operation that makes identical values annihilate each other while leaving a lone value intact. XOR is exactly that: x ^ x = 0 and x ^ 0 = x.
Why order does not matter
XOR is commutative and associative, so the pairs cancel wherever they sit. No grouping, no sorting, one pass.
Seeding with 0
Zero is XOR's identity, so it is the correct accumulator start — the same reason you seed a sum with 0 and a product with 1.
The generalisation
If two values were unique instead of one, XOR everything, isolate a set bit of the result with x & (-x), and partition the array on that bit. Each half then has exactly one unique value. Worth mentioning.
LC 136 · O(n) time, O(1) space
class Solution {
    public int singleNumber(int[] nums) {
        // x ^ x == 0 makes pairs annihilate.
        // x ^ 0 == x leaves the lone value untouched.
        // XOR is commutative and associative, so order is irrelevant.
        int unique = 0;
        for (int v : nums) unique ^= v;
        return unique;
    }
}

Anchor 2 · LC 137 — the path to the solution

Why XOR fails
Three copies of a value XOR down to one copy of it, not zero. The cancellation property is specific to pairs, so the fold leaves noise behind.
The reframing
Stop thinking about values and think about bit lanes. Each of the 32 positions is an independent counter, and XOR is really a per-lane count modulo 2.
The generalisation
If values appear three times, count each lane modulo 3. Triplicated values contribute a multiple of 3 to every lane and vanish; the unique value's bits are exactly the non-zero remainders.
The implementation
Two nested loops — 32 bit positions by n values. O(32n), which is linear in n and uses O(1) space.
The compressed form
Two integers, ones and twos, acting as a modulo-3 state machine. Same computation, far less readable. Present the counting version first, then offer this.
Negative numbers
Use >>> for the extraction and the two's-complement representation handles negatives correctly — bit 31 is simply another lane.
LC 137 · O(32n) time, O(1) space
class Solution {
    public int singleNumber(int[] nums) {
        int result = 0;

        // Each bit position is an INDEPENDENT counter. Values that
        // appear three times add a multiple of 3 to every lane, so
        // the remainder isolates the unique value's bits.
        for (int bit = 0; bit < 32; bit++) {
            int count = 0;
            for (int v : nums) {
                count += (v >>> bit) & 1;    // >>> so bit 31 works for negatives
            }
            if (count % 3 != 0) result |= (1 << bit);
        }
        return result;
    }
}

268 · Missing Number parity

Path: summing 0..n and subtracting the array total is the obvious O(n) answer — mention that it can overflow for large n, which is why XOR is preferred.

Delta: XOR every index 0..n together with every value. Each present number appears exactly twice — once as an index, once as a value — and cancels. The missing one appears once and survives.

Watch for: the loop must cover indices 0 through n inclusive, which is one more than the array length. Missing that leaves the wrong survivor.

191 · Number of 1 Bits counting

Path: checking all 32 positions works and is O(1) by any practical measure. n & (n − 1) is faster when the value is sparse.

Delta: that expression clears the lowest set bit, so looping until n == 0 runs exactly once per set bit — 3 iterations for a value with 3 ones, not 32.

Watch for: the input is treated as unsigned, so the loop must use n != 0 rather than n > 0. A negative input has bit 31 set and n > 0 exits immediately.

338 · Counting Bits DP on bits

Path: calling the LC 191 routine for every value is O(32n) and passes. The follow-up asks for a single linear pass without a built-in.

Delta: dp[i] = dp[i >> 1] + (i & 1). Dropping the last bit gives a strictly smaller index whose answer is already computed; add back the bit you dropped.

Watch for: dp[i] = dp[i & (i-1)] + 1 is an equally valid recurrence using the clearing trick instead. Both are one line; knowing why each works is the point.

190 · Reverse Bits rearranging

Path: shift bits out of the bottom of the input and into the bottom of the result, which builds the reversal automatically over 32 steps.

Delta: result = (result << 1) | (n & 1) then n >>>= 1. All 32 iterations must run even after n reaches zero, or the remaining shifts are skipped and the answer is misaligned.

Watch for: >>> is mandatory — >> on a negative input copies the sign bit forever. The repeated-call follow-up is a 256-entry byte lookup table, which is the expected answer there.

If you only drill twoDo 136 and 137. 136 establishes the XOR fold and the O(1)-space habit. 137 is where the pattern becomes understanding rather than recall: seeing XOR as a per-lane parity counter, and therefore seeing modulo-3 counting as the natural generalisation, is what lets you handle a variant you have never met.
