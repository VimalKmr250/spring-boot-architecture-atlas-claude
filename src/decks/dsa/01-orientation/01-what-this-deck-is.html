Thirty patterns, not one hundred and eighty problems

Nobody solves an interview problem by recalling the problem. You recognise the shape, reach for the structure that fits it, and adapt three lines. This deck takes the thirty patterns one at a time, teaches each as a reusable Java structure, and drills it on the six LeetCode problems that stress a different corner of that one idea.

30

patterns, each a self-contained topic. Nothing in one topic depends on having read another.

180

LeetCode problems, linked. Two per pattern are solved in full; the other four are shown as a delta against that pattern's own structure.

4

slides per pattern — mechanics, a dry run, the reusable structure, the six problems. Every line of code is Java 17+.

The four slides, every time

Mechanics
The invariant that holds on every iteration, and the argument for why the work is bounded. This is the part that transfers to problems not on the list.
Dry run
One concrete input traced step by step, as a diagram and a table. If you cannot trace it by hand, you do not know it yet.
Structure
The generic Java skeleton, its variants, and the exact knobs you turn per problem.
Problems
The six, each with the path from brute force to optimal — not just the finished answer.

How to use it

  • Arrow keys move through slides; C opens contents, where each pattern is its own section.
  • New to pointer patterns? Sliding window opens with two extra slides that build the idea from zero, including a step-through you can type your own input into.
  • Work one pattern to the end before starting the next. They are deliberately independent.
  • Read the mechanics slide, then cover the dry-run table and trace the input yourself. Compare after.
  • Type the structure from memory before reading the problems. The structure is the unit of recall.
  • Copper marks the pointer or value that moved this step; teal marks auxiliary state changing.
  • Complexity is always stated as time / space, excluding the space taken by the output. The Complexity analysis section, straight after these orientation slides, shows how every one of those figures is derived.
The one habit worth buildingBefore writing anything, say out loud which pattern you are using and what its invariant is. If you cannot name the invariant, you are about to write a loop you will then debug for ten minutes. Interviewers score that naming almost as highly as the code.
