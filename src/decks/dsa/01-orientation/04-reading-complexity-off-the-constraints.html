The constraints tell you the intended complexity

Judges run on the order of 108 simple operations per second. Every problem's constraint section is therefore a direct hint at the algorithm the setter had in mind — read it before you design, not after your first submission times out.

Worked example

The constraints read 1 <= piles.length <= 10⁴ and 1 <= piles[i] <= 10⁹.

The array is small but the values are enormous. A small n paired with a huge value range means the search is over the value range, not the array: the search space is the values, and each feasibility check costs one O(n) pass. Total O(n log maxV) ≈ 10⁴ × 30 = 3×10⁵ operations, comfortably inside budget. That problem is LC 875.

Two more tells worth memorising"Return the answer modulo 10⁹+7" means the count is astronomically large, so it is a counting DP and never an enumeration. "You may return the answer in any order" means the grader sorts for you, so do not spend time ordering the output.
Say this in the interview"The constraints put n at 10⁵, so I need O(n log n) or better — which rules out the pairwise approach I'd otherwise reach for." In one sentence you have demonstrated that you design against a budget rather than guessing. It reliably scores, and it costs five seconds.
