Anchor 1 · LC 1 — the path to the solution

Brute force
Two nested loops over all pairs, O(n²). It passes on small inputs, which is why this is rated Easy and still worth getting exactly right.
Why not two pointers
Sorting would give O(n log n) — but the answer is the original indices, and sorting destroys them. You would have to carry index pairs alongside the values. The hash keeps them for free.
The inversion
Do not search forward for a partner. Remember what you have passed, and at each element ask whether its required partner target − a[i] is already behind you.
The ordering detail
Probe before inserting. On [3,3] with target 6, inserting first lets index 0 match itself and returns [0,0]. Probing first returns the correct [0,1].
Why it is still one pass
If i < j form the answer, then when the loop reaches j the value at i is already stored. Every pair is discovered at its second element.
LC 1 · O(n) time, O(n) space
class Solution {
    public int[] twoSum(int[] nums, int target) {
        // value -> the index where we saw it
        Map<Integer, Integer> seen = new HashMap<>();

        for (int i = 0; i < nums.length; i++) {
            // PROBE FIRST. Inserting first would let nums[i]
            // pair with itself when 2 * nums[i] == target.
            Integer j = seen.get(target - nums[i]);
            if (j != null) return new int[]{ j, i };

            seen.put(nums[i], i);
        }
        return new int[]{};   // the statement guarantees this is unreachable
    }
}

Anchor 2 · LC 128 — the path to the solution

Brute force
For each value, walk upwards checking membership with a linear scan. O(n³) — or O(n²) with a set.
The obvious fix
Sort, then scan for the longest adjacent run. O(n log n), genuinely correct, and easy to write. Say this first — the follow-up asking for O(n) is what rules it out.
First O(n) attempt
Put everything in a set and walk upwards from every value. Still O(n²): on [1,2,…,n] the walk from 1 covers n, from 2 covers n−1, and so on.
The observation
A walk starting mid-run recomputes a suffix of a walk that another start already covers. So only walk from a head — a value v with v − 1 absent. Every run has exactly one.
The result
Each element is walked over exactly once across the whole algorithm, so the nested loop is O(n) in total. One continue is the entire optimisation.
Edge case
Duplicates are absorbed by the set. The empty array must return 0, so initialise best at 0 rather than 1.
LC 128 · O(n) time, O(n) space
class Solution {
    public int longestConsecutive(int[] nums) {
        Set<Integer> set = new HashSet<>();
        for (int v : nums) set.add(v);      // duplicates collapse here

        int best = 0;

        for (int v : set) {
            // THE ONE LINE THAT MATTERS.
            // If v-1 exists, v is mid-run and the head will cover it.
            if (set.contains(v - 1)) continue;

            // v begins a run: walk it once.
            int len = 1;
            while (set.contains(v + len)) len++;

            best = Math.max(best, len);
        }
        return best;   // 0 for an empty array
    }
}

217 · Contains Duplicate membership

Path: nested loops are O(n²); sorting and scanning neighbours is O(n log n) with O(1) extra space. The set is O(n) time for O(n) space — name that trade, because it is the entire point of the problem.

Delta: if (!seen.add(v)) return true;. Set.add already reports whether the element was new, so a separate contains call is redundant work.

Watch for: if the interviewer adds "O(1) space", the answer becomes sort-then-scan, and you must say you are mutating the input.

242 · Valid Anagram counting

Path: sorting both strings and comparing is O(n log n) and perfectly acceptable. Counting is O(n) and strictly better.

Delta: one int[26]. Increment for s, decrement for t, then confirm every slot is zero — or bail early if any goes negative. Compare lengths first and return immediately if they differ.

Watch for: the Unicode follow-up. int[26] no longer works; switch to a HashMap<Integer, Integer> keyed on code points, since a Java char cannot hold one.

49 · Group Anagrams grouping

Path: comparing every pair for anagram-hood is O(n²·L). Replacing the comparison with a computed key makes it one pass.

Delta: the key. Sorting each word is O(L log L); a 26-slot count vector rendered via Arrays.toString is O(L) and better. Build the map with computeIfAbsent, then return new ArrayList<>(map.values()).

Watch for: do not concatenate raw counts into a string — "1,11" and "11,1" would collide. Keep the separators that Arrays.toString supplies.

347 · Top K Frequent Elements buckets

Path: count, then sort by frequency — O(n log n). A size-k min-heap improves that to O(n log k), which is the expected answer and worth presenting.

Delta: then beat it. A frequency is at most n, so it can index an array directly: bucket the values by count and read downwards from n. That is O(n), with no comparator.

Watch for: new List[n + 1] raises an unchecked-generic-array warning. It is correct and conventional here; say so rather than working around it.
