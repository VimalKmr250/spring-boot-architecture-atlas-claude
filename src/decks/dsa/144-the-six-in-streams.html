Bitwise folds work in any order, so all six are clean

Most reductions in this deck need a caveat. Bitwise ones do not. XOR and OR are associative, and 0 is a true identity for both, so reduce(0, (a, b) -> a ^ b) is exactly what the reduce contract asks for, and it stays correct in parallel. 137 and 190 split the work over the 32 bits instead of over the numbers. 191 walks down to zero with IntStream.iterate, one step per set bit. 338 builds its table by doubling, so it needs neither Integer.bitCount nor a table that reads its own earlier entries.

LC 136 · Single Number · clean
class Solution {
    public int singleNumber(int[] nums) {
        // x ^ x == 0 and x ^ 0 == x, in any order: the pairs
        // cancel, and the single number is all that is left.
        return Arrays.stream(nums).reduce(0, (a, b) -> a ^ b);
    }
}
LC 268 · Missing Number · clean
class Solution {
    public int missingNumber(int[] nums) {
        // XOR 0..n with every number present. Each present one
        // appears twice and cancels; the missing one is left.
        int n = nums.length;
        return IntStream.concat(IntStream.rangeClosed(0, n),
                                Arrays.stream(nums))
                .reduce(0, (a, b) -> a ^ b);
    }
}
LC 137 · Single Number II · clean
class Solution {
    public int singleNumber(int[] nums) {
        // Sum each of the 32 bits over all the numbers. The
        // triples add a multiple of 3 to every bit, so the sum
        // mod 3 is that bit of the single number.
        IntUnaryOperator bitSum = b -> Arrays.stream(nums)
                .map(x -> x >>> b & 1).sum();
        return IntStream.range(0, 32)
                .map(b -> bitSum.applyAsInt(b) % 3 << b)
                .reduce(0, (a, c) -> a | c);
    }
}
LC 191 · Number of 1 Bits · clean
class Solution {
    public int hammingWeight(int n) {
        // x & (x - 1) clears the lowest set bit, so the walk
        // down to zero takes one step per set bit.
        return (int) IntStream
                .iterate(n, x -> x != 0, x -> x & (x - 1))
                .count();
    }
}
LC 338 · Counting Bits · clean
class Solution {
    public int[] countBits(int n) {
        // Doubling: the counts for 2^k .. 2^(k+1) - 1 are those
        // for 0 .. 2^k - 1, plus one for the new top bit.
        UnaryOperator<int[]> doubled = a -> IntStream
                .concat(Arrays.stream(a),
                        Arrays.stream(a).map(c -> c + 1))
                .toArray();
        int[] bits = Stream.iterate(new int[] {0}, doubled)
                .filter(a -> a.length > n)
                .findFirst().get();
        return Arrays.copyOf(bits, n + 1);
    }
}
LC 190 · Reverse Bits · clean
class Solution {
    public int reverseBits(int n) {
        // Bit b moves to bit 31 - b. The moved bits never
        // overlap, so OR-ing them in any order is safe.
        return IntStream.range(0, 32)
                .map(b -> (n >>> b & 1) << (31 - b))
                .reduce(0, (a, c) -> a | c);
    }
}
Why this reduce needs no caveatStream.reduce asks for two things: an associative operation, and an identity that really is one. XOR meets both, with 0 as the identity, so adding .parallel() to 136 or 268 would still give the right answer. That is the answer to "is this reduce safe?", and it is the test to apply to every other reduce in this deck. A fold that fails it, like the trie walk in pattern 25, is only correct sequentially.
The library already has theseIn production code, use Integer.bitCount for 191 and Integer.reverse for 190. bitCount is a JIT intrinsic, a single POPCNT instruction on modern x86. If the interviewer allows library calls, IntStream.rangeClosed(0, n).map(Integer::bitCount).toArray() is all of 338. The doubling version answers the follow-up that rules those calls out, and it still runs in O(n).
