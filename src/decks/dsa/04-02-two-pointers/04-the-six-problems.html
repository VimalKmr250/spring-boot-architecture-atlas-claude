Anchor 1 · LC 15 — the path to the solution

Brute force
Three nested loops, O(n³), plus a Set of sorted triples to kill duplicates. Correct and far too slow at n = 3000.
The observation
Fix the first element. What remains is exactly 2Sum with target −a[i] — a solved problem. Sorting first costs O(n log n) once and buys the O(n) core at every anchor.
The real difficulty
Not the search, the duplicates. Sorting puts equal values adjacent, which makes de-duplication a skip rather than a hash set: skip repeated anchors, and after recording a hit skip repeated values on both sides.
Early exit
Once a[i] > 0 the smallest possible triple already exceeds zero, so break. Cheap, and it shows you are thinking about the sorted order.
LC 15 · O(n²) time, O(1) space beyond the output
class Solution {
    public List<List<Integer>> threeSum(int[] nums) {
        Arrays.sort(nums);                       // creates the ordering the discard needs
        List<List<Integer>> out = new ArrayList<>();

        for (int i = 0; i + 2 < nums.length; i++) {
            if (nums[i] > 0) break;              // sorted: nothing ahead can reach 0
            if (i > 0 && nums[i] == nums[i - 1]) continue;   // duplicate ANCHOR

            int l = i + 1, r = nums.length - 1;
            while (l < r) {
                int sum = nums[i] + nums[l] + nums[r];

                if (sum < 0)      l++;           // too small: a[l] is finished
                else if (sum > 0) r--;           // too large: a[r] is finished
                else {
                    out.add(List.of(nums[i], nums[l], nums[r]));

                    // duplicate HITS — distinct from the anchor skip above
                    while (l < r && nums[l] == nums[l + 1]) l++;
                    while (l < r && nums[r] == nums[r - 1]) r--;

                    l++; r--;                    // both, or we re-find this pair
                }
            }
        }
        return out;
    }
}

Anchor 2 · LC 42 — the path to the solution

The right question
Do not ask "how much water sits in this valley". Ask, for each column independently: how high does the water stand here? The answer is min(maxLeft, maxRight) − h[i].
First solution
Precompute maxLeft[] and maxRight[] in two passes, then sum. O(n) time but O(n) space — a perfectly good answer, and worth stating before optimising.
The observation
You never need both maxima at once. If h[l] < h[r], then rightMax ≥ h[r] > h[l], so the water at l is fixed by leftMax alone — the right side cannot be the binding constraint.
The result
Two running maxima and two pointers: O(n) time, O(1) space. Always mention the O(n)-space version first, then this.
LC 42 · O(n) time, O(1) space
class Solution {
    public int trap(int[] h) {
        int l = 0, r = h.length - 1;
        int leftMax = 0, rightMax = 0, water = 0;

        while (l < r) {
            // Whichever side is SHORTER is the binding constraint,
            // so that side's water is already fully determined.
            if (h[l] < h[r]) {
                leftMax = Math.max(leftMax, h[l]);
                water  += leftMax - h[l];   // never negative: leftMax >= h[l]
                l++;
            } else {
                rightMax = Math.max(rightMax, h[r]);
                water   += rightMax - h[r];
                r--;
            }
        }
        return water;
    }
}

167 · Two Sum II skeleton A

Path: the array is handed to you sorted, which is the problem telling you the intended pattern. A hash map also works in O(n) but uses O(n) space and ignores the gift.

Delta: skeleton A verbatim. The only trap is the 1-indexed return: {l + 1, r + 1}.

Watch for: if asked for an O(n log n) alternative, fix each l and binary search the remainder for its complement. Slower here, but it is the version that survives when the two pointers cannot both move.

16 · 3Sum Closest skeleton C

Path: identical scaffold to 15, but there may be no exact hit, so "found it" is replaced by "is this the closest so far".

Delta: keep bestDiff and update it before the comparison branch. The move rule is unchanged — sum < target still means l++, because closeness is still monotone along the sorted array. Return immediately on an exact hit; nothing can beat zero.

Watch for: initialise with the first valid triple, not Integer.MAX_VALUE, or the difference computation overflows.

18 · 4Sum skeleton C

Path: exactly 15 with one more nesting level. Writing the generic kSum from the previous slide once is cheaper than writing 3Sum and 4Sum separately.

Delta: two anchors, both with their own duplicate skip. Use long for the running sum and target — four values near 10⁹ overflow int, and LeetCode's test set includes exactly that case.

Watch for: the pruning if ((long) a[i] * k > target) break; turns a borderline solution into a comfortable one.

11 · Container With Most Water skeleton B

Path: brute force is all O(n²) pairs. The discard argument traced on the previous slide reduces it to one pass.

Delta: skeleton B verbatim. The instinct to sort is the single biggest trap in this problem — the width is the index distance, so sorting destroys the thing being measured.

Watch for: on a tie, move either pointer; both choices are safe because the measured area is already recorded.
