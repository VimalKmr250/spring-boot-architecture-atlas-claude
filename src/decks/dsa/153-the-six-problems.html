Anchor 1 · LC 416 — the path to the solution

Brute force
Enumerate all 2ⁿ subsets and check each sum. At n = 200 that is impossible.
The reframing
If the two halves are equal, each is total / 2. So the question collapses to: is there a subset summing to exactly total/2? — classic subset-sum.
The free rejection
An odd total cannot split, so return false immediately. One line, and it eliminates the whole computation on half the inputs.
The state
dp[c] = "is sum c reachable using the items seen so far?" Boolean, because the question is existence rather than an optimum.
The transition
dp[c] |= dp[c − v]. Sum c becomes reachable if c − v already was and you now add item v.
The direction
Backwards. Reading dp[c − v] from the previous row keeps each item to one use. Forwards would let a single 1 build 1, 2, 3, … and report true for impossible inputs.
LC 416 · O(n·sum) time, O(sum) space
class Solution {
    public boolean canPartition(int[] nums) {
        int total = 0;
        for (int v : nums) total += v;

        // Equal halves require an even total — reject for free.
        if (total % 2 != 0) return false;
        int target = total / 2;

        // dp[c] = "can the items seen so far sum to exactly c?"
        boolean[] dp = new boolean[target + 1];
        dp[0] = true;                      // the empty subset makes 0

        for (int v : nums) {
            // BACKWARDS: dp[c - v] is still the PREVIOUS row, so this
            // item cannot be used twice. Forwards would allow reuse
            // and report true for [1,1] with target 2 from one 1.
            for (int c = target; c >= v; c--) {
                dp[c] |= dp[c - v];
            }
        }
        return dp[target];
    }
}

Anchor 2 · LC 518 — the path to the solution

The question
How many distinct combinations of coins make the amount, with unlimited supply. Order does not matter: 1+2 and 2+1 are one way.
Two decisions, not one
Coins are reusable, so the capacity loop runs forwards. And combinations rather than permutations means the items loop is outside. These are independent choices and both must be right.
Why items outside gives combinations
Each coin is fully processed before the next is considered, so a combination is only ever built in non-decreasing coin order. There is exactly one such ordering per multiset, so each is counted once.
Why capacity outside gives permutations
Every coin is reconsidered at every amount, so 1-then-2 and 2-then-1 are built along different paths and counted separately. That is LC 377 — same code, loops swapped, different problem.
The base case
dp[0] = 1. There is exactly one way to make zero: take nothing. Leaving it at 0 makes every count zero.
Edge case
amount = 0 returns 1, not 0 — which falls out of the base case with no special handling.
LC 518 · O(coins·amount) time, O(amount) space
class Solution {
    public int change(int amount, int[] coins) {
        // dp[c] = the number of COMBINATIONS making amount c.
        int[] dp = new int[amount + 1];
        dp[0] = 1;                 // exactly one way to make 0: take nothing

        // ITEMS OUTER -> combinations. Each coin is fully considered
        // before the next, so every combination is built in
        // non-decreasing coin order and counted exactly once.
        //
        // Swapping these two loops would count 1+2 and 2+1 separately,
        // which is LC 377 — a different problem with the same body.
        for (int coin : coins) {

            // CAPACITY FORWARDS -> unbounded. dp[c - coin] may already
            // include this coin, which is exactly what reuse means.
            for (int c = coin; c <= amount; c++) {
                dp[c] += dp[c - coin];
            }
        }
        return dp[amount];
    }
}

494 · Target Sum 0/1 counting

Path: assigning + or − to every element looks like enumeration, and the 2ⁿ backtracking solution does pass at n = 20. The algebra is better.

Delta: with positives P and negatives N, P − N = target and P + N = total, so P = (total + target) / 2. Count the subsets summing to that — a 0/1 knapsack with +=.

Watch for: two impossibility checks first — |target| > total, and (total + target) odd. Without them the array size goes negative or the answer is silently wrong.

1049 · Last Stone Weight II 0/1 optimisation

Path: simulating smashes greedily with a heap is a different problem and gives the wrong answer. The insight is that every smash sequence amounts to assigning each stone a + or a −.

Delta: the remainder is |P − N|, minimised by making P as close to total/2 as possible. So find the largest reachable sum at or below total/2, and the answer is total − 2·best.

Watch for: the table only needs to reach total/2 — the symmetric half is redundant, which halves both the memory and the time.

474 · Ones and Zeroes two capacities

Path: each string consumes two budgets at once — a number of zeros and a number of ones — so a single capacity cannot express the constraint.

Delta: dp[zeros][ones] = the largest subset fitting those budgets. Iterate both dimensions backwards, for the same reason the 1D version does.

Watch for: count the zeros and ones of each string once, before the DP loops. Recounting inside the inner loop multiplies the running time by the string length for nothing.

879 · Profitable Schemes saturating dimension

Path: two dimensions again — members used, and profit earned. But profit behaves differently from a capacity.

Delta: profit saturates: once you have met minProfit, more profit does not create a new state. So the index is min(p + profit[i], minProfit), which keeps the table bounded regardless of how large the profits are.

Watch for: that clamp is the whole trick. Without it the table would need a dimension the size of the total profit. Take the count modulo 10⁹+7 at every addition.

If you only drill twoDo 416 and 518. 416 fixes the backwards-capacity rule that governs every 0/1 problem here. 518 is the one that forces you to hold two independent loop decisions at once — direction for reuse, order for combinations — and being able to state why each is right is what makes the rest of this family mechanical.
