Prune early, and make the feasibility test O(1)

Plain enumeration explores the whole tree. Constrained backtracking kills a branch the moment it becomes impossible — and the difference between a solution that finishes and one that times out is almost always how cheaply you can ask "is this still legal?".

Two kinds of pruning

Feasibility
This branch violates a rule now — a queen attacks another, a cell is already on the path, the remaining sum went negative. Cut immediately.
Bound
This branch cannot possibly reach a solution even if everything goes well — not enough candidates remain, or the smallest remaining value already exceeds the target. Cut on arithmetic rather than on a rule.

Both belong at the top of the loop body, before the choose step. Pruning after recursing does the work you were trying to avoid.

Make the test O(1)

A feasibility check that scans the partial solution turns an already exponential search into something far worse. Maintain incremental state instead, updated on choose and restored on un-choose.

For N-Queens, three boolean arrays — column, and the two diagonals keyed by r + c and r − c + n — turn an O(n) scan into three array reads. For a grid walk, mutating the board itself records the visited set with no extra memory at all.

Identifying that state is the real work in this pattern. The recursion is unchanged.

Applies when

Enumeration plus rules: a grid path that cannot revisit cells, a partition where every piece must satisfy a predicate, placements that must not conflict. Constraints are what keep the exponential search tractable.

Does not apply when

Only a count or an optimum is wanted and subproblems repeat — that is dynamic programming. Backtracking re-explores overlapping states; DP solves each once.

Complexity

Worst case still exponential — O(m·n·4^L) for a grid word search, O(n!) for N-Queens — but pruning makes the practical running time far smaller. State the worst case, then say what the pruning buys.
