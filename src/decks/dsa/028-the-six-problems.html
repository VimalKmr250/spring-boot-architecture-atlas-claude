Six lists, four skeletons, one shared constraint

Every one of these has an easy O(n)-space solution with a HashSet or an ArrayList. Say that solution out loud first — it shows you see the trade-off — then give the O(1)-space pointer version, which is what the problem is actually testing.

Anchor 1 · LC 142 — the path to the solution

Brute force
Walk the list putting every node into a HashSet; the first node already present is the entrance. O(n) time, O(n) space, and completely correct — offer it first.
The constraint
The follow-up asks for O(1) space, which rules the set out and forces the pointer argument.
Phase 1
Two speeds guarantee a meeting somewhere inside the cycle. That point depends on L and C and is not the entrance.
Phase 2
From 2(L + k) = L + k + nC you get L = nC − k: the head-to-entrance distance equals the meeting-point-to-entrance distance. Walk both at speed one and they collide there.
LC 142 · O(n) time, O(1) space
class Solution {
    public ListNode detectCycle(ListNode head) {
        ListNode slow = head, fast = head;

        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;

            if (slow == fast) {          // PHASE 1 · a meeting exists
                ListNode p = head;

                // PHASE 2 · L = nC - k, so both walk L steps
                // and land together on the entrance.
                while (p != slow) {
                    p = p.next;
                    slow = slow.next;
                }
                return p;
            }
        }
        return null;                     // fast ran off the end: no cycle
    }
}

Anchor 2 · LC 234 — the path to the solution

Brute force
Copy the values into an ArrayList and check it with two pointers. O(n) time, O(n) space, three lines. Always say this first.
The constraint
O(1) space. You cannot index a list, and you cannot walk it backwards — so make a piece of it point backwards.
The decomposition
Three known sub-procedures, in order: find the middle (skeleton A), reverse from the middle (skeleton D), then walk the two halves in step. Naming the three parts before coding is what makes this tractable under pressure.
Why the odd case is free
With an odd length the middle node ends up in both halves, and comparing it against itself always succeeds. No special case is needed — which surprises most people.
The professional touch
Mention that this mutates the input, and that a production version would reverse the second half back before returning. Interviewers notice.
LC 234 · O(n) time, O(1) space
class Solution {
    public boolean isPalindrome(ListNode head) {
        // 1 · middle — skeleton A
        ListNode slow = head, fast = head;
        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;
        }

        // 2 · reverse from the middle onwards — skeleton D
        ListNode prev = null;
        while (slow != null) {
            ListNode next = slow.next;
            slow.next = prev;
            prev = slow;
            slow = next;
        }

        // 3 · walk both halves. `prev` heads the reversed tail,
        //     which is the SHORTER half, so it controls the loop.
        ListNode a = head, b = prev;
        while (b != null) {
            if (a.val != b.val) return false;
            a = a.next;
            b = b.next;
        }
        return true;
    }
}

876 · Middle of the Linked List skeleton A

Path: the obvious solution counts the length, then walks half of it — two passes. The two-speed loop does it in one without ever knowing the length.

Delta: skeleton A verbatim, returning slow. The problem asks for the second middle on even lengths, which is exactly what fast = head gives; starting fast = head.next would give the first.

Watch for: this is the sub-procedure inside 234, and inside any routine that has to split a list in half. Make it automatic.

141 · Linked List Cycle skeleton A

Path: a HashSet of visited nodes is the natural first answer, O(n) space. The follow-up forces O(1).

Delta: skeleton A with an identity comparison after each move. Compare with == on references, not .val — two distinct nodes can hold the same value.

Watch for: the loop guard must test fast before fast.next. Reversing those two terms throws on any list of even length with no cycle.

19 · Remove Nth Node From End skeleton B

Path: the two-pass version measures the length, then walks len − n nodes. Perfectly correct; the follow-up asks for one pass, which is the fixed-gap idea.

Delta: gap, not speed. Advance fast by n, then move both until fast.next == null, leaving slow on the node before the target.

Watch for: without the dummy, removing the head needs its own branch. With it, the code is uniform — and you must return dummy.next, not head.

160 · Intersection of Two Linked Lists skeleton C

Path: the explicit version measures both lengths, advances the longer list by the difference, then walks in step. Correct, and worth describing — the head-swap is just that idea written in four lines.

Delta: when a pointer runs off its list, send it to the other head. Both then cover lenA + lenB and arrive together.

Watch for: the no-intersection case terminates because both hit null on the same step and null == null ends the loop. Do not add a guard for it — the guard is what breaks it.

If you only drill twoDo 142 and 234. 142 is the one piece of algebra here, and phase 2 is the half people get backwards; 234 is the composite that proves you can chain three list procedures without losing a pointer.
