Take the locally best option — and be able to prove it is safe

A greedy algorithm commits to a choice and never reconsiders. That makes it fast and simple, and wrong far more often than people expect. The pattern is not "take the biggest"; it is finding the ordering under which the obvious choice is provably optimal, then saying why.

The exchange argument

Every correct greedy has the same proof shape. Take any optimal solution that differs from yours at the first choice. Show you can swap its choice for yours without making it worse. Repeat, and the optimal solution has been transformed into the greedy one — so the greedy is optimal too.

If you cannot construct that swap, the greedy is probably wrong. That failure is the signal to reach for dynamic programming instead.

Interviewers ask "why does that work?" on every greedy problem. The exchange argument is the answer, and it is usually two sentences.

The three shapes greedy takes here

Furthest reach
Track how far you can get, and commit only when forced. Jump problems.
Sort, then place
Find an order in which each item's position is forced once its predecessors are fixed. Reconstruction problems.
Bound then construct
Prove a lower bound on the answer from the most constrained element, then show it is achievable. Scheduling with cooldowns.

All three are O(n) or O(n log n), and all three are short — the difficulty is entirely in the justification.

Applies when

A locally optimal choice is provably safe: taking it never rules out an optimal completion. Usually visible after sorting, or when one element is so constrained that it dictates the answer.

Does not apply when

Choices interact — taking the biggest coin now may strand you later. That is the coin-change trap, and it is what dynamic programming exists for. If you cannot write the exchange argument, assume greedy is wrong.

Complexity

O(n) when no sort is needed, O(n log n) when there is one. Space is usually O(1). These are among the cheapest solutions in the deck — the cost is all in the reasoning.

The tell is an optimisation with no obvious subproblem structure — if a DP state is hard to define, look for a greedy and its proof.
