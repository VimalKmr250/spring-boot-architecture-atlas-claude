One template, three blanks to fill

The loop is an ordinary boundary search; the array comparison becomes feasible(mid) and you are done. All the thinking moves into feasible, which should be a direct transcription of the problem statement — deliberately dull code.

The template — fill in three blanks
/**
 * Smallest x in [lo, hi] for which feasible(x) holds.
 * Requires monotone feasibility:  F F F T T T over the answer range.
 *
 * BLANK 1 · lo   — a value that fails, or the smallest legal one
 * BLANK 2 · hi   — a value that obviously works
 * BLANK 3 · feasible(x) — an O(n) simulation, as literal as possible
 */
int solve(int[] a, int limit) {
    int lo = 1, hi = 0;
    for (int v : a) hi = Math.max(hi, v);        // BLANKS 1 and 2

    while (lo < hi) {                            // an ordinary boundary search
        int mid = lo + (hi - lo) / 2;

        if (feasible(a, mid, limit)) hi = mid;   // mid might be the answer: keep it
        else                         lo = mid + 1;
    }
    return lo;                                   // lo == hi == the smallest feasible x
}

/** BLANK 3 · read this straight off the problem statement. */
private boolean feasible(int[] a, int speed, int limit) {
    long hours = 0;
    for (int pile : a) {
        hours += (pile + speed - 1) / speed;     // ceil without floating point
        if (hours > limit) return false;         // early exit: cheap and avoids overflow
    }
    return hours <= limit;
}

Choosing the bounds

Capacity / speed
lo = max(a) when every element must fit somewhere on its own (LC 410, 1011); lo = 1 when elements may be consumed over several steps (LC 875, 1283).
Upper
hi = sum(a) for packing — one group holds everything. hi = max(a) for rates. Too generous costs a few iterations; too tight returns a wrong answer.
Time-style answers
[min(day), max(day)], and check feasibility at hi first — LC 1482 can be impossible outright, and returns −1.
Overflow
Accumulate in long. With n = 10⁵ and values to 10⁹ the sum reaches 10¹⁴, which overflows int long before the search goes wrong.
The three bugs that actually happenlo set below the largest element in a packing problem — capacity 3 can never hold an item of size 7, and the greedy check loops or reports nonsense. Forgetting to round up — pile / speed is floor division, so a pile of 7 at speed 6 reports one hour instead of two; use (v + x - 1) / x. The maximising mirror without rounding mid up — with lo = mid and a floor midpoint, a two-element range never shrinks and the loop hangs.
