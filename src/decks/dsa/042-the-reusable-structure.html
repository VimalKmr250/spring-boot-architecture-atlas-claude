Four idioms, and the Java methods worth knowing

The code is short, so the leverage is in fluency: merge, computeIfAbsent and getOrDefault remove the null-checking that makes hash solutions look clumsy under time pressure.

The four idioms
// 1 · MEMBERSHIP — "have I seen it?"
//     Set.add returns false when the element was already there,
//     so the check and the insert are a single operation.
boolean containsDuplicate(int[] a) {
    Set<Integer> seen = new HashSet<>();
    for (int v : a) if (!seen.add(v)) return true;
    return false;
}

// 2 · COUNTING — merge is the whole idiom
Map<Integer, Integer> freq = new HashMap<>();
for (int v : a) freq.merge(v, 1, Integer::sum);       // no getOrDefault dance
freq.merge(v, -1, Integer::sum);                      // and to decrement
if (freq.get(v) == 0) freq.remove(v);                 // keep size() honest

//     For a known small alphabet, an array beats a map outright —
//     no boxing, no hashing, and it is what a window state should use.
int[] count = new int[26];
count[c - 'a']++;

// 3 · GROUPING — computeIfAbsent creates the bucket on first use
Map<String, List<String>> groups = new HashMap<>();
groups.computeIfAbsent(key, k -> new ArrayList<>()).add(value);

// 4 · COMPLEMENT — store as you go, ask for the partner you need
Map<Integer, Integer> seen = new HashMap<>();
for (int i = 0; i < a.length; i++) {
    Integer j = seen.get(target - a[i]);
    if (j != null) return new int[]{ j, i };
    seen.put(a[i], i);        // AFTER the lookup — see the note below
}
Bucket sort by frequency — top-K in O(n), no heap (LC 347)
// A heap gives O(n log k). But a frequency can never exceed n,
// so index an array BY the frequency and read it from the top:
// O(n), and simpler than the heap version once you have seen it.
int[] topKFrequent(int[] nums, int k) {
    Map<Integer, Integer> freq = new HashMap<>();
    for (int v : nums) freq.merge(v, 1, Integer::sum);

    // bucket[f] = every value occurring exactly f times
    List<Integer>[] bucket = new List[nums.length + 1];
    for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
        int f = e.getValue();
        if (bucket[f] == null) bucket[f] = new ArrayList<>();
        bucket[f].add(e.getKey());
    }

    int[] out = new int[k];
    int idx = 0;
    for (int f = nums.length; f >= 1 && idx < k; f--) {
        if (bucket[f] == null) continue;
        for (int v : bucket[f]) {
            out[idx++] = v;
            if (idx == k) break;
        }
    }
    return out;
}

Picking the container

int[26]
Lowercase letters. Fastest, and no boxing at all. Reach for it before a map whenever the alphabet is fixed.
int[128]
ASCII. Covers mixed case and punctuation without thought.
HashMap
Arbitrary or unbounded keys. The default when values are ints up to 10⁹.
HashSet
Membership only. Say !set.add(v) rather than contains then add.
TreeMap
Only when you need order or range queries — floorKey, ceilingKey, subMap. O(log n), so do not reach for it by default.
The three bugs that actually happenInserting before looking up in LC 1 — on [3,3] with target 6, the element finds itself and you return [0,0]. Always probe first, then insert. Leaving zero counts in the map — size() then over-reports distinct keys, which silently breaks every "at most K distinct" window. Using == on boxed Integer — it compares references, and Java only caches −128 to 127, so the comparison works on small tests and fails at 1000. Use .equals, or unbox to int first.
