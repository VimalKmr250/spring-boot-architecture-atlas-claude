Security

Security questions in a backend loop are rarely about cryptography. They check whether you know where each check happens, and which one teams most often forget.

Q54

Walk me through what Spring Security does with a request carrying a JWT.

30-second answerThe request passes through the SecurityFilterChain. BearerTokenAuthenticationFilter extracts the token, and a JwtDecoder checks the signature against the issuer's JWKS keys (cached, and refetched for an unknown kid), then the issuer, the expiry and the not-before time. A converter maps scopes and role claims to authorities, and the resulting Authentication goes into the SecurityContext. Only then do the URL rules in authorizeHttpRequests and any @PreAuthorize methods run.

Go deeper: Name the check most answers miss: the audience is validated only if you configure it. Without audiences: [order-api], a valid token minted for the marketing API is accepted by the payments API, because both trust the same issuer. One line of YAML closes that lateral-movement path. Then the choices for a bearer-token API: stateless sessions and CSRF protection off, while a cookie-based BFF keeps CSRF on. And authorisation at three layers, URL, method and row, because a URL rule cannot know who owns order 88421.

Q55

JWT or opaque tokens? And how do you revoke a JWT?

30-second answerYou cannot revoke a JWT directly. A signed JWT stays valid until it expires, and that is the price of validating it locally without a network call. So keep access tokens short-lived, five to fifteen minutes, and keep refresh tokens on the server. Where instant revocation genuinely matters, use opaque tokens with introspection: a call to the identity provider per request, which you can cache for a few seconds, in exchange for real revocation and no readable claims.

Go deeper: Say where each fits. JWTs suit internal service-to-service traffic and high request rates. Opaque tokens suit external-facing APIs and regulated work, and many banks mandate them. A middle ground is a short-lived JWT plus a deny-list checked only on sensitive operations, such as payouts or password changes. Mention that a JWT is signed, not encrypted: anyone holding it can decode the claims, so it must not carry personal data.

Q56

How do you stop one customer reading another customer's order?

30-second answerCheck ownership on every object access, not only authentication at the door. A valid token plus GET /orders/88421 with someone else's id is broken object-level authorisation, first on the OWASP API Security Top 10. URL rules cannot catch it, because the URL is legitimate. Enforce it in three layers: the filter chain for who you are, method security for whether you may act on this object, and scoping at the data layer, so a query that forgets WHERE customer_id = ? still cannot return other customers' rows.

Go deeper: Make it concrete. Write @PreAuthorize("@orderAccess.mayView(#id, authentication)"), with the check in a bean you can unit-test, rather than SpEL that grows a third or. At the row level, use a Hibernate @Filter enabled per request, or PostgreSQL row-level security, which still holds when someone bypasses the ORM with native SQL. Return 404 rather than 403 for objects the caller may not see, so ids cannot be probed. For multi-tenant systems, say which isolation model you would pick: a shared schema with row-level security by default, and a schema or database per tenant for customers who pay for it.

Q57

How should one service authenticate to another?

30-second answerThere are two parts: proving which service is calling, and deciding whose authority the call carries. For the first, use OAuth2 client credentials, a token for the calling service whose audience is the service being called, or mTLS, ideally issued and rotated by a service mesh. For the second, either relay the user's token, or exchange it for a narrower one, so the downstream service can enforce user-level rules and audit a person. Or call as a service account and pass the user id as data.

Go deeper: Give the trade-off. Token relay couples you more tightly to the identity provider and carries tokens further, but the audit trail names a person, which is what regulated, customer-affecting flows need. Service accounts are simpler and faster, but the downstream service must trust the caller, which is why they are paired with mTLS. In Spring, OAuth2ClientHttpRequestInterceptor on a RestClient handles the client side. And the operational point: hand-managed truststores expire at 3 a.m. on a bank holiday, so let the platform issue and rotate workload certificates.

Q58

Where do secrets live, and how do they get rotated?

30-second answerNever in the repo, the image or application.yaml, not even test credentials. Secrets come from a secret manager, such as Vault or the cloud provider's, injected at runtime. The real requirement is rotation. Short-lived, dynamically issued credentials, such as Vault database secrets or cloud IAM roles for workloads, make rotation routine rather than an incident.

Go deeper: Separate configuration from secrets. Environment-specific values come from config maps or a config server, and are validated at startup with @ConfigurationProperties and @Validated, so a typo fails the boot rather than the first payment. Secrets take a separate, access-logged path. Add secret scanning on every commit, and accept the uncomfortable rule that a secret that has ever been in git history is compromised: rotate it rather than rewriting history. Actuator's /env and /configprops mask values by default, but they belong on an internal port anyway.
