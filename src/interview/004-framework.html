Six steps for any design question

Say the step names out loud as you go. It makes your reasoning legible and stops you spiralling on one part.

1 · Clarify (3–5 min)

Functional scope — what is explicitly out. Scale: DAU, peak RPS, data volume, growth. Consistency needs per operation. Latency budget. Team size and timeline. Write the numbers where you both can see them.

2 · Contract first

The 4–6 API operations, and the core entities with their key fields. This anchors everything after it and costs two minutes.

3 · Boxes and arrows

Client → edge → API → services/modules → data. Say which arrows are synchronous and which are events, and why, as you draw them.

4 · Data model and storage

Which store for which data and why. Partition/shard key. Indexes for the top three queries. Where the read model is, if any.

5 · Scale the bottleneck

Name the bottleneck first — usually the database or a single hot partition — then fix that: caching, read replicas, async offload, partitioning. Do not scale everything.

6 · Failure and operations

What happens when each dependency is down. Idempotency and retries. Monitoring and the SLO. This is the section most candidates run out of time for — budget for it deliberately.

Time disciplineIn a 45-minute round: 5 clarify, 5 contract, 10 high-level, 10 deep-dive on whatever they steer you to, 10 failure and scale, 5 spare. If you are still on step 3 at minute 25, summarise and move.
