Five scripts for the long questions

Rehearse these out loud. Not to recite — to have the shape of the answer available so your attention goes to the interviewer's constraints instead of to structure.

W1

"Design an order management system for a large retailer"

Clarify (say these out loud): Order volume and peak — say 1.2M/month, peaking at 40× on a sale day. Read/write ratio: order reads outnumber writes ~20:1. Consistency: stock at checkout must be strongly consistent; stock shown while browsing may be 30 s stale. Latency budget for place-order: 1.5 s p99. Team: 40 engineers, five teams.

Contract: POST /orders (idempotency key), GET /orders/{id}, GET /orders?customer&status (cursor paged), POST /orders/{id}/cancel. Entities: Order (id, customer, lines, status, total, version), OrderLine, Payment, Reservation.

Shape: Modular monolith with eight modules, one artifact, three deployments. "I'd start here rather than microservices because the boundaries are still being learned, and at five teams the coordination cost doesn't yet justify the distribution cost. Here's what would make me split…"

The flow: place order → reserve stock (sync, must fail the order) → authorise payment (sync) → commit → OrderPlaced via outbox → fulfilment, notification, search index, loyalty (all async). Draw the sync hops in one colour and the async in another, and say why each is which.

Data: PostgreSQL, schema per module, no cross-schema joins. order_summary read model for history, maintained by events. Redis for the price cache and rate limits. OpenSearch for search, fed by events. Partition the orders table by month once it passes tens of millions of rows.

Scale the bottleneck: "The bottleneck at 40× is the orders write path and the inventory hot rows." Queue the non-critical work; optimistic locking plus reservation TTL on inventory; scale workers separately from web; pre-warm and raise the cache TTL for the sale window; shed load at the gateway before the database gets there.

Failure and ops: Payment gateway down → circuit breaker, order accepted as PAYMENT_PENDING with a retry job, customer told honestly. WMS down → events queue, fulfilment lags, nothing lost. Kafka down → outbox rows accumulate, the database still serves checkout. SLO 99.9% on place-order with burn-rate alerts; trace id end to end; DLT depth and consumer lag alerted.

W2

"We have a five-year-old monolith with 400 tables. Modernise it."

First, refuse the rewrite. "A big-bang rewrite of a system with five years of encoded business rules has a well-known failure rate. I'd strangle it instead — and the first six weeks are measurement, not code."

Measure: which endpoints carry traffic, which tables are written by more than one area, where the change requests actually land, and what the current failure modes are. Most of the 400 tables are cold; the architecture problem is in maybe forty of them.

Stabilise: add tracing and structured logs, characterisation tests on the highest-traffic flows, a CI pipeline that people trust, and timeouts on every outbound call. You cannot safely change a system you cannot observe.

Modularise in place: draw the boundaries, move packages to match, add ArchUnit rules with today's violations baselined, then ratchet down every sprint. This is unglamorous and it is where most of the value is — it delivers the decoupling without the distribution risk.

Split the data: schema per module, one role per module, cross-schema joins replaced by API calls or read models. Run this way for a while. "If I can't split the data, I definitely can't split the service."

Then extract, one module, on evidence: pick the one with a named trigger — usually the one with a different scaling profile or a compliance boundary. Interface stays, adapter swaps, feature flag, cut over, delete. Measure whether it helped before doing a second one.

Close with the business framing: "Each phase ships value on its own — the tracing pays for itself in incident time, the modularisation in change lead time. Nothing here requires a two-year programme with no deliverable until the end." That sentence is often what the question was really probing.

W3

"Design rate limiting for our public partner API"

Clarify: Limit by what: API key, partner, endpoint, or all three? What shape: "100 requests a second sustained, bursts to 200" is the usual contract. Is the limit contractual, so billing and fairness depend on it, or protective, to keep us up? How exact must it be across 50 gateway instances; is going 5% over for a second acceptable? Total traffic: say 20k requests a second.

Algorithm: A token bucket per key: a refill rate and a capacity, two numbers of state. It expresses "sustained rate plus burst", which is what partner contracts usually say. Name the alternatives and why not. A fixed window is simplest but lets through double the limit across a window boundary. A sliding log is exact but stores every request. A sliding-window counter is a good approximation using two counters, and a fine second choice.

Where: At the edge, in the gateway, before a request costs anything. Spring Cloud Gateway's RedisRateLimiter is a token bucket implemented in a Lua script. Add a second, service-level concurrency limit on the expensive endpoints, because rate and concurrency protect against different things: a hundred cheap requests are fine, and ten report exports are not.

State: Redis, one key per partner holding tokens and a timestamp, updated atomically by a Lua script so the read-modify-write cannot race across 50 instances. Keys carry a TTL, so idle partners cost nothing. That is about a millisecond per check, and a single Redis node handles on the order of 100k simple operations a second.

Response: 429 Too Many Requests with Retry-After, plus remaining-quota headers (the common X-RateLimit-* convention, or the IETF RateLimit header fields draft), so well-behaved clients slow down before they hit the wall.

Failure: Decide deliberately what happens when Redis is down. For a protective limit, fail open to a coarse in-memory limiter on each instance (the limit divided by the instance count), so the limiter's store failing does not take the API down with it. For a contractual limit, you might fail closed. Across regions, give each region its share of the budget rather than making a synchronous cross-region check on every request.

Operate it: Keep limits in configuration, changeable without a deploy. Graph 429s per partner and alert when a top partner starts being limited, because that is often an incident on their side, or a bug on ours. Close with: "Partners should be able to see their own limits and usage. A rate limiter is part of the product, not only a defence."

W4

"Design a flash sale: 10,000 units, 500,000 people, starting at noon"

Clarify: How many SKUs? A limit per customer? How long is a unit held in the basket? Is overselling ever acceptable? It is not: it is a legal and trust problem. Is fairness first come, first served? Traffic: most of the 500,000 arrive in the first minute, so tens of thousands of page loads a second, and thousands of purchase attempts a second.

Reframe it out loud: "Ninety-eight per cent of these people will be told no. The design is about telling them no quickly and cheaply, and serving the two per cent well." That sentence usually changes the conversation.

Shape: The sale page is static and served from the CDN; it never reaches the origin. A waiting room at the edge admits users at the rate checkout can handle. Web and worker deployments are scaled up before noon, not by an autoscaler reacting at 12:00:30.

Inventory, the hard part: Do not let 500,000 requests update one row. Put a gatekeeper counter in Redis and DECR it atomically. A result below zero means sold out, answered in a millisecond. Only the winners write a durable reservation to PostgreSQL, with a TTL of about ten minutes, so the database sees around 10,000 writes rather than 500,000. An expired reservation returns its unit to the counter. Redis is the gate and PostgreSQL is the truth, and a reconciliation job compares them. If you cannot use Redis, split the stock across several rows so the writes spread out; optimistic retries on a single hot row collapse under this much contention.

Idempotency and abuse: A unique constraint on (customer, sale) and an idempotency key on the purchase request, so double clicks and retries cannot take two units. Limits per account and per device at the edge. Optionally, allow only accounts created before the sale was announced.

Payment and failure: Payment follows the reservation. If it fails or times out, the reservation is released back to the pool. When stock runs out, flip one flag that the CDN serves, so the sold-out page never touches the origin. Shed load at the gateway with a queue page rather than letting the database become the queue. Load-test at twice the forecast the week before, and have a kill switch.

Close with the invariant: "Every 'no' comes from the edge or from Redis in milliseconds. Only the ten thousand winners ever touch the database."

W5

"Checkout errors spiked ten minutes ago. You're on call. Talk me through it."

Acknowledge and size it (first two minutes): Acknowledge the page so others know it is owned. Open the SLO dashboard: how many customers, which journeys, and since when. If customers are affected, declare an incident. Severity follows impact, not cause.

Look for the change: What happened at that time? A deploy, a flag, a migration, a config change, a dependency's status page, a traffic spike? Most incidents follow a change, and the timeline is the fastest diagnostic you have.

Mitigate before you diagnose: Roll back the deploy, turn off the flag, fail over, or shed load. "Restoring service comes first. The root cause can wait for the postmortem, and a rollback is cheaper than being right." This is the sentence the round is listening for.

Communicate: Open an incident channel. Name an incident commander once more than two people are involved, so the people debugging are not also writing updates. Post updates on a fixed cadence, every fifteen to thirty minutes, even when nothing has changed. Update the customer status page if customers can see the problem.

Diagnose, if no change explains it or the rollback did not help: The RED dashboard shows which endpoint and which status codes. Are they 5xx errors or timeouts? Trace one failing request. Check the dependency dashboard: is a breaker open, has the gateway's latency jumped? Check pool saturation, then the logs filtered by trace id.

Confirm recovery: The error rate is back inside the SLO, consumer lag is draining, and nothing is stuck. Orders left in PAYMENT_PENDING get retried, and a reconciliation run finds anything that needs repair, such as duplicates or half-processed orders.

Postmortem: Blameless, with a timeline, contributing factors (usually several, not one root cause), what slowed detection and mitigation, and action items with owners. The permanent change is the part interviewers want to hear.
