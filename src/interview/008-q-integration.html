Integration, messaging and resilience

Q24

A downstream service is slow. How do you stop it taking you down?

30-second answerFour layers in order. Timeout first — without a bounded call, nothing else can work. Then bounded retries with exponential backoff and jitter, only on idempotent operations. Then a circuit breaker so you stop calling a dead system. Then a bulkhead capping concurrency to that dependency, so it cannot consume every thread you have.

Go deeper: Explain why jitter matters — without it every client retries at the same millisecond and keeps the recovering dependency down. Explain retry amplification: three services each retrying three times turns one request into twenty-seven, exactly when the dependency is struggling. And say that every breaker state needs a defined fallback: a cached value, a queued write, or an honest 503 with Retry-After.

Q25

Synchronous call or event — how do you choose?

30-second answerOne question: if this step fails, should the user's action fail? Yes — synchronous, in the same transaction (taking payment). No — publish an event (confirmation email, loyalty points, search reindex). That single rule keeps checkout availability high while five downstream systems average far less.

Go deeper: Name the cost of the event path honestly — the order now exists in a state where payment has not happened yet, and both the domain model and the UI have to admit that state. Then availability multiplication: five synchronous dependencies at 99.9% each give you 99.5% before you have written a line of your own code.

Q26

How do you guarantee event ordering?

30-second answerOnly within a partition, and only by keying on the entity. All events for one order go to one partition because the key is the order id, so they arrive in order for that order. There is no global ordering across partitions, and you should not design as if there were.

Go deeper: Mention the consequences: partition count caps consumer parallelism, and a hot key creates a hot partition. If a consumer needs to tolerate out-of-order arrival anyway, carry a version or timestamp in the event and ignore anything older than what you have already applied — which is more robust than depending on ordering at all.

Q27

A consumer hits a message it can never process. What happens?

30-second answerBounded retries — three, with backoff — then publish to a dead-letter topic, alert, and move on. Infinite retry blocks the partition and everything behind it. Non-retryable exceptions like deserialization failures skip the retries entirely, because a poison pill never gets better.

Go deeper: Add the two operational pieces: a documented replay path from the DLT after the bug is fixed, and alerting on DLT depth greater than zero plus consumer lag — those two are your real SLIs for the async side, not CPU. Also mention where the offset is committed relative to the work — and get the default right, because interviewers who run Kafka will know it: the raw client auto-commits on a timer, but Spring's listener container disables that and acks per poll (AckMode.BATCH), so the real question is whether a mid-batch failure should redeliver 500 records or one. MANUAL_IMMEDIATE is how you make that choice explicit.

Q28

How do you make an API safe to retry?

30-second answerAn Idempotency-Key header the client generates per logical operation. Insert it with a unique constraint before doing the work; on a duplicate key with the same request fingerprint, return the stored response; with a different fingerprint, return 422 because the client reused a key for a different request.

Go deeper: Mention storing the response body and status against the key with a TTL, so the retry gets an identical answer rather than a second order. Then the layering rule: no retry anywhere — client, gateway, or @Retryable — without idempotency. Gateways should retry GETs only. Retrying a POST without a key is how customers get charged twice.

Q29

How do you debug a request that crossed four components and a queue?

30-second answerOne trace id, propagated end to end — including through the Kafka message headers, which is the hop teams forget. Every log line carries it, every span carries it, and the customer's error page shows it. Support quotes the id, you get the whole journey in one query.

Go deeper: In Spring terms: Micrometer Tracing with W3C traceparent, OTLP export, and observation-enabled: true on both the Kafka template and the listener container. Mention structured JSON logs with the correlation pattern, sampling at 10% with errors always sampled, and the cardinality rule — never tag a metric with an order id, that belongs in logs and traces.

Q30

What does acks=all actually guarantee?

30-second answerThat the write reached every replica currently in the in-sync set, and that set can shrink to just the leader. On its own that is weaker than it sounds. The durable combination is replication factor 3, min.insync.replicas=2 and acks=all. An acknowledged write then exists on at least two brokers, and if two brokers are lost the partition refuses writes rather than quietly accepting them on one.

Go deeper: Explain the ISR. A follower that falls further behind than replica.lag.time.max.ms is dropped from it, and acks=all then means "all the replicas still keeping up". Keep unclean.leader.election.enable false for anything involving money: setting it true restores availability by electing an out-of-sync replica, and discards writes that were acknowledged. On the producer, acks=all and idempotence have been the defaults since Kafka 3.0, although idempotence only took effect from 3.0.1, 3.1.1 and 3.2.0 onwards. The real bound on delivery is delivery.timeout.ms, not retries. And followers do not serve reads for throughput; read scaling comes from partitions.

Q31

Consumer lag is climbing. What do you do?

30-second answerDiagnose before you scale. Adding consumers triggers a rebalance and often makes things worse. First question: is the lag on every partition, or on one? One partition means a hot key or a stuck consumer. Every partition means producer volume jumped, the handler slowed down because a dependency did, or the group is stuck in a rebalance loop. Each cause has a different fix, and only the first is "scale out".

Go deeper: Name the command. kafka-consumer-groups.sh --describe --group … shows lag per partition and which member owns it. An empty consumer id means nothing is consuming that partition at all. Then check whether the consumer count already equals the partition count, because beyond that extra pods sit idle. The fix that usually wins is a cheaper handler: a batch listener with one bulk write turns 500 inserts into one statement, and can raise throughput by an order of magnitude with no new infrastructure. Do not raise max.poll.interval.ms to stop rebalances. Lower max.poll.records, so one poll's work finishes in time.

Q32

What is a consumer-group rebalance, and how do you stop it hurting?

30-second answerWhen group membership changes, partitions are reassigned. Under the old eager protocol every consumer stops and gives up all its partitions first, so each rolling deploy pauses the whole group several times. Cooperative sticky assignment moves only the partitions that must move. Static membership, with a group.instance.id per pod, means a restart within the session timeout triggers no rebalance at all. On Kafka 4, the new consumer protocol (KIP-848) removes the group-wide pause entirely.

Go deeper: The failure interviewers want you to recognise is the rebalance loop. A batch takes longer than max.poll.interval.ms, the broker decides the consumer is dead, the partition moves, and the new owner reprocesses the same slow batch. Lag climbs while the logs show rebalances rather than errors. The fix is a lower max.poll.records. Also commit offsets in onPartitionsRevoked so the new owner does not redo work, and keep the instance id stable: a StatefulSet pod name works, while a random UUID defeats the point.

Q33

How do you change an event's schema without breaking consumers?

30-second answerMake every change additive. New fields are optional with defaults, and nothing required is removed, renamed or given a new type. Enforce it with a schema registry set to BACKWARD compatibility, with schemas registered from CI, so an incompatible producer fails its own deploy instead of breaking a consumer nobody knew about. Consumers are tolerant readers that ignore fields they do not recognise.

Go deeper: For a genuinely breaking change, run expand and contract across the consumers. Add the new field alongside the old one, let each consumer migrate, watch a metric until nobody reads the old field, then remove it. If the meaning of the topic changes, such as a different key or granularity, publish a .v2 topic, write both versions from the same outbox transaction, and retire v1 once its consumer groups have gone. Mention auto.register.schemas: false in production. Otherwise the first producer to start registers whatever schema it has, and the compatibility gate never fires.

Q34

Kafka or RabbitMQ?

30-second answerThey do different jobs. Kafka is a partitioned, replayable log with high throughput, many independent consumers, and retention and replay as features: an event backbone. RabbitMQ is a broker of queues with flexible routing, per-message TTL and priorities, and messages that are gone once consumed: a work queue. Many large organisations run both, plus an MQ estate for systems that already speak it, with a written rule for what goes where.

Go deeper: Give the deciding questions. Will anyone need to replay history, or add a consumer next year that reads from the beginning? Kafka. Do you need per-message routing, priorities or delays at modest volume? RabbitMQ. Would you rather not run a broker at all? SQS and SNS, or a managed event bus. Then add the current detail. Kafka's historical gap as a queue, per-record acknowledgement and more consumers than partitions, is closing with KIP-932 share groups, GA in Kafka 4.2. That does not give Kafka RabbitMQ's routing, but it removes one common reason for running both.
