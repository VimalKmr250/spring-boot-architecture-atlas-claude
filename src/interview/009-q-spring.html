Q35

Why doesn't @Transactional work when I call the method from the same class?

30-second answerBecause it is implemented with a proxy. An internal this.method() call never goes through the proxy, so the advice never runs. Fix by moving the method to another bean, or by using TransactionTemplate explicitly. There is no warning in any version — the reference manual says the annotation "may be silently ignored", and the code appears to work until someone tests a rollback.

Go deeper: Same mechanism explains why @Cacheable, @Async and @Retryable also do nothing on self-invocation, and why final or private methods cannot be advised with CGLIB proxies. This question is really testing whether you know Spring is a proxy container rather than magic.

Q36

What rolls a Spring transaction back?

30-second answerBy default, RuntimeException and Error — not checked exceptions. So a checked PaymentDeclinedException commits the half-written order. Either set rollbackFor = Exception.class, or adopt the convention that all domain exceptions are unchecked, which is what I would do.

Go deeper: Cover propagation while you are there: REQUIRED joins the caller's transaction (the default), REQUIRES_NEW suspends it and takes a second connection from the pool — nest that in a loop and you deadlock your own pool. Legitimate uses are audit rows that must survive a rollback, and post-commit event listeners.

Q37

What is an N+1 and how would you catch it before production?

30-second answerOne query for a list, then one per row for a lazy association — 501 queries for 500 orders. Fix with @EntityGraph or join fetch. Catch it by asserting the query count on the hot endpoints in an integration test, so a regression six months later fails the build rather than a dashboard.

Go deeper: Mention open-in-view: false — the default is true and it hides N+1s behind a request-scoped session until production load exposes them. Then the adjacent traps: two join fetches on collections give a cartesian explosion, and pagination combined with join fetch makes Hibernate log "applying in memory" and then run out of heap.

Q38

How do you size a connection pool?

30-second answerLittle's law: concurrency = throughput × hold time. Ten orders a second, 40 ms of database work each, is 0.4 connections on average; times five for peak is about two, so set it to 10–20 for headroom. Then check the total across all pods against the database's max_connections.

Go deeper: Explain why bigger is worse: PostgreSQL context-switches between hundreds of backends, latency rises, each request holds its connection longer, which needs more connections. Pools are queues, and oversizing just moves the queue somewhere less observable. Forty pods at 20 each is 800 connections, which is how a healthy service takes down a shared cluster.

Q39

Do virtual threads change your architecture?

30-second answerThey remove the thread-per-request ceiling for IO-bound work, so you can handle far more concurrent blocked requests without going reactive. They do not create capacity downstream — if your throughput is limited by the database or a third party, ten thousand virtual threads queue on twenty connections instead of on a thread pool.

Go deeper: In Boot it is spring.threads.virtual.enabled: true. Note that pinning on synchronized blocks is largely resolved in modern JDKs but legacy libraries can still pin, and that the honest framing is: virtual threads make the simple blocking programming model scale, which removes most of the reason to adopt WebFlux.

Q40

How do you test a Spring Boot application properly?

30-second answerMatch the test to the layer. Domain rules in plain JUnit with no context, microseconds. Slices — @WebMvcTest, @DataJpaTest — for serialization, validation and SQL. Testcontainers with the real PostgreSQL and Kafka for integration. A handful of end-to-end journeys, no more. Plus architecture tests, which are tests like any other.

Go deeper: Say explicitly that H2 is not your database — it passes SQL that production rejects and skips the constraints and locking behaviour that matter. Mention @ServiceConnection and container reuse to keep the suite fast, and that three reliable E2E tests beat forty flaky ones, because a suite people re-run "because it's probably flaky" has stopped being a gate.

Q41

What's new in Spring Boot 4 that matters architecturally?

30-second answerFour things I would actually use: first-class API versioning on server and client; declarative HTTP interface clients via @ImportHttpServices; resilience in the core framework — @Retryable and @ConcurrencyLimit without an extra library; and null safety through JSpecify with @NullMarked packages. Java 17 is still the baseline, 25 recommended.

Go deeper: Add the migration realities: the framework is split into finer modules, which is the most common upgrade surprise; Jackson 3 changes defaults (ISO-8601 dates, unchecked exceptions); and Spring Data AOT generates repository queries at build time for a meaningful startup improvement. 4.1 (June 2026) added gRPC support, InetAddressFilter for SSRF mitigation on the HTTP clients, lazy JDBC connection acquisition and @RedisListener. Knowing the version cadence — a major or minor every six months — is a cheap credibility signal.

The detail that separates "I read the release notes" from "I did the upgrade": core @Retryable is not a rename of Spring Retry's. It needs @EnableResilientMethods, the attribute is maxRetries and it counts retries rather than attempts, and there is no @Recover — so a copied annotation compiles, runs one extra time, and loses its fallback silently.

Q42

How does Spring Boot auto-configuration actually work?

30-second answer@SpringBootApplication turns on component scanning and @EnableAutoConfiguration, which reads every AutoConfiguration.imports file on the classpath, about 150 classes from Boot itself. Each class is guarded by conditions: @ConditionalOnClass (is the library present?), @ConditionalOnProperty, and above all @ConditionalOnMissingBean, which makes Boot back off whenever you declare the bean yourself. Your own configuration is registered first, which is how that back-off can see it.

Go deeper: The diagnostic answers half the follow-ups. Run with --debug, or call /actuator/conditions, and the condition evaluation report says exactly why each auto-configuration did or did not apply. Then give the four ways to take control, weakest first. Set a property. Declare a *Customizer bean, which changes one setting and keeps Boot's defaults. Declare your own bean, which makes you own every default: define your own ObjectMapper and you lose the modules Boot had registered. Or exclude the auto-configuration, the blunt instrument. The legacy trap: before Boot 2.7 the list lived in spring.factories, and Boot 3.0 removed that route. An in-house starter that never migrated contributes nothing, and nothing reports an error.

Q43

Constructor or field injection, and what happens with a circular dependency?

30-second answerConstructor injection. The dependencies are explicit and final, the object is complete once constructed, and a test can build it with new. A cycle of constructor-injected beans fails at startup, which is the right outcome because a cycle is a design smell, and Boot has refused circular references by default since 2.6. Fix the design, usually by extracting the shared piece into a third bean or turning one direction into an event. @Lazy on one side is a stopgap.

Go deeper: Scopes are the usual next question. Singleton is the default. A prototype injected into a singleton is created once, at injection time, so it behaves like a singleton; inject an ObjectProvider<T> to get a fresh instance per call. Request and session scopes are injected as scoped proxies. Prototype beans never get a destroy callback. Finally, constructors should wire, not work: a constructor that calls the database makes startup depend on that system, and a brief outage there becomes a crash loop here.

Q44

What goes wrong with @Async and @Scheduled?

30-second answerFour things. Self-invocation bypasses the proxy, so the method runs synchronously. Boot's auto-configured executor has 8 core threads and an unbounded queue, so max-size never takes effect and a backlog grows in memory instead of being rejected. Exceptions from a void async method go to an uncaught-exception handler, which logs them and nothing else. And thread-bound context, such as the MDC, the trace and the security context, does not follow the task unless you propagate it.

Go deeper: Give the fixes. Name a bounded executor per workload, @Async("notificationExecutor"), with a queue capacity and a rejection policy you chose. Return CompletableFuture when the caller needs the outcome. Add a TaskDecorator (Framework 6.1 ships ContextPropagatingTaskDecorator) so logs and traces stay correlated. For @Scheduled, the default scheduler has one thread, so one slow job delays all the others. In a multi-pod deployment every pod runs every job unless you add a lock, such as ShedLock, or run schedulers only in the worker deployment. With virtual threads enabled, Boot switches both to virtual-thread executors and the pool settings stop applying.

Q45

What does a HashMap need from its keys, and why is that awkward for a JPA entity?

30-second answerConsistent equals and hashCode. Equal objects must have equal hash codes, and neither may change while the object is in the map. Change a field that hashCode reads and the entry is stranded in the wrong bucket: get and remove miss it, although iteration still finds it. Records and other immutable value objects get this right by construction.

Go deeper: The JPA twist is that a generated id is null until the entity is persisted, so an id-based hashCode changes the moment you save. An entity added to a HashSet before saving can no longer be found in it. There are three sound options: an immutable business key; an id assigned at construction, such as a client-generated UUIDv7; or equality on the id with a hashCode that is constant for the class, trading bucket speed for correctness. Never use Lombok's @Data on an entity, because it hashes every field, including lazy associations, which triggers loads. For the internals follow-up: an array of buckets with a default capacity of 16 and a load factor of 0.75, doubling on resize. Since Java 8, a bucket that grows past 8 entries becomes a red-black tree once the table has at least 64 buckets, which limits the damage from poor hash codes to O(log n).

Q46

volatile, synchronized, atomics, ConcurrentHashMap: when do you need which?

30-second answervolatile gives visibility and ordering for a single variable. It is right for a stop flag or a safely published reference, and wrong for count++, which is a read, an add and a write that can interleave. synchronized or a Lock gives mutual exclusion for compound actions. Atomics give lock-free updates to one variable, with LongAdder for heavily contended counters. ConcurrentHashMap gives thread-safe map operations, and compute, merge and computeIfAbsent make check-then-act atomic.

Go deeper: The bug interviewers plant is check-then-act on a concurrent map. if (!map.containsKey(k)) map.put(k, v) is two operations and it races; putIfAbsent or computeIfAbsent is one. Keep the function passed to compute* short, and never modify the same map from inside it. ConcurrentHashMap rejects null keys and values, and its iterators are weakly consistent rather than fail-fast. Then the enterprise framing: in a Spring service, most shared mutable state is a bug. Singletons should be stateless, and state belongs in the database, where transactions and version columns handle concurrency. On virtual threads, a synchronized block around blocking IO used to pin the carrier thread. JDK 24 largely fixed that, but ReentrantLock is still the safe choice for code that must run on older JDKs.

Q47

Do records and sealed types change how you model a domain?

30-second answerYes. They make illegal states harder to write. Records are immutable value objects with correct equals and hashCode, plus a compact constructor for validation, which is exactly what Money, OrderId or Address should be. Sealed interfaces close a hierarchy, so a payment result becomes a fixed set of types, and since Java 21 the compiler checks a pattern-matching switch over them for exhaustiveness.

Go deeper: Show the payoff with sealed interface PaymentResult permits Authorised, Declined, Pending, where each is a record carrying only the data that state has. A declined result cannot accidentally carry an authorisation code. Add a new state and every switch without a default stops compiling, which is exactly the reminder you want. Know the limits too. Records are not JPA entities, because they are final and immutable while entities need a no-argument constructor and mutable state. They work well as embeddables from Hibernate 6.2, as query projections and as DTOs, and Jackson handles them natively.
