Data and consistency

Q12

How do you keep data consistent across services without 2PC?

30-second answerSaga: a sequence of local transactions, each with a compensating action. Reserve stock, authorise payment, capture, ship — and if authorisation fails, release the stock. Compensation is not a rollback; it is a new business fact with its own audit trail. Order the irreversible steps last.

Go deeper: Contrast orchestration (a saga state machine you can query — "where is order 88421 stuck") with choreography (lower coupling, but the flow exists only in traces). For enterprise work, orchestration is the default past three steps. Then the operational requirements: persist saga state, make every step idempotent, and put a timeout on every step — a saga without timeouts produces orders sitting in AWAITING_PAYMENT for eleven days.

Q13

How do you write to the database and publish to Kafka atomically?

30-second answerYou don't — you use the transactional outbox. Write the event into an outbox table in the same local transaction as the data, and let a separate relay publish it and mark it sent. Crash anywhere and the row is still there, so it gets published again. That gives at-least-once, which is why every consumer is idempotent.

Go deeper: Name both failure modes of the naive approach: send-then-commit publishes an event for an order that rolls back; commit-then-send loses the event on a crash. Then the two relay options — a polling relay (FOR UPDATE SKIP LOCKED, simple, ~200 ms–1 s latency) versus Debezium CDC reading the WAL (millisecond latency, ordering from the log, costs a Connect cluster). Bonus: Spring Modulith's event publication registry is exactly this pattern, built in.

Q14

Two customers order the last item at the same moment. What happens?

30-second answerOptimistic locking with a version column. The update is WHERE sku = ? AND version = ?; the loser gets zero rows updated, an OptimisticLockingFailureException, and a bounded retry on fresh state — where it sees stock is zero and gets a clean "out of stock". No locks held across the request.

Go deeper: Explain why not pessimistic: SELECT FOR UPDATE is correct but serialises the hot row, which is fatal for a flash-sale SKU while being fine for a rarely-contended ledger. Mention the reservation model for real e-commerce — reserve with a TTL at checkout, confirm on payment, release on expiry — so you are not holding stock indefinitely for abandoned carts.

Q15

Can you guarantee exactly-once processing?

30-second answerNot over a network — you get at-most-once or at-least-once. What you can achieve is exactly-once effects: at-least-once delivery into an idempotent handler. Deduplicate on a business key, not on an offset.

Go deeper: Show the concrete handler: check whether a reservation already exists for that orderId, and if so acknowledge and return — a duplicate is not an error. Mention Kafka's transactional producer and read_committed as exactly-once within Kafka, and be clear that it does not extend to your database or a third-party API. Getting this distinction right is one of the strongest signals in a mid-to-senior interview.

Q16

How do you change a database schema with zero downtime?

30-second answerExpand and contract, across three releases. Add the new nullable column; dual-write and backfill in batches; switch reads; then drop the old column once no running version references it. During a rolling deploy old and new pods share one schema, so every migration must be compatible with the previous release.

Go deeper: Add the operational details — CREATE INDEX CONCURRENTLY on large tables, a lock_timeout so blocked DDL fails fast instead of queueing every query behind it, batched backfills, and migrations as immutable append-only files with Flyway validation on. Answer the rollback question before they ask it: you roll forward, and expand/contract is what makes the deployment rollback-safe even though the schema is not.

Q17

The order history page is slow. Walk me through fixing it.

30-second answerMeasure first — is it the database, the serialization, or the network? Then in order of cost: check for an N+1, add the covering index, replace offset pagination with a keyset cursor, project a denormalised read model maintained by events, and only then cache. Each step is cheaper than the next one.

Go deeper: Be concrete: 501 queries in the trace means N+1 — fix with @EntityGraph and assert the query count in a test so it cannot come back. OFFSET 100000 makes Postgres walk 100k rows — switch to WHERE (placed_at, id) < (?, ?) ORDER BY ... LIMIT 20. Caching last is deliberate: caching a bad query hides the problem until the cache misses at peak.

Q18

When would you use CQRS or event sourcing?

30-second answerCQRS-lite — a separate read path with projections instead of aggregates — almost always pays for itself, and costs one class. Full event sourcing is justified when the audit trail is the requirement (ledgers, regulated workflows) or when you genuinely need to reconstruct past state. Otherwise it buys a large amount of complexity for a temporal query nobody asked for.

Go deeper: Name the real costs of event sourcing: schema evolution of events you can never delete, snapshotting for long streams, the difficulty of ad-hoc queries, and a steep onboarding curve for every new engineer. Then the middle ground you would actually ship: normal state storage plus a durable domain-event log, which gives most of the audit value at a fraction of the cost.

Q19

What isolation level do you use, and what does it actually prevent?

30-second answerThe database default: READ COMMITTED on PostgreSQL and Oracle, REPEATABLE READ on MySQL. I handle concurrency with optimistic locking rather than by raising the level. READ COMMITTED prevents dirty reads but still allows non-repeatable reads and phantoms. That is usually fine, because a version check catches the conflicts that actually matter.

Go deeper: Show that you know engines go further than the standard requires. PostgreSQL's REPEATABLE READ is snapshot isolation and prevents phantoms, and InnoDB prevents them with gap locks. Snapshot isolation still allows write skew, where two transactions each check a condition, both write, and together they break it. That is the case SERIALIZABLE exists for. On PostgreSQL it aborts transactions with serialization failures under contention, so switching it on without a retry around the whole unit of work turns a correctness problem into an availability problem. Also mention @Transactional(timeout = 5), in seconds, to bound how long long-running work holds its locks and its connection. The follow-up is nearly always Q14, and the answer there is a version column, not an isolation level.

Q20

How would you add caching, and how do you know when a cached value is wrong?

30-second answerStart from a staleness budget for each use case, not from a technology. Product copy can be minutes stale, a price seconds stale, and stock at checkout never, so checkout is not cached at all. Then use cache-aside with two layers: Caffeine in-process (about 100 ns, per instance) in front of Redis (about 1 ms, shared). Invalidate on domain events, and keep a TTL as the safety net.

Go deeper: Name the three classic failures and their fixes. In a stampede, a hot key expires and 500 threads hit the database at once: use @Cacheable(sync = true) or a short lock. In penetration, lookups for ids that do not exist skip the cache every time: cache the negative result briefly. In an avalanche, everything expires in the same second: add jitter to the TTLs. Then the multi-instance problem. Evicting locally on one pod leaves eleven others serving the old value, so the eviction has to be broadcast, through a Redis channel or an event. Close with the ordering point: fix the query first, because a cache in front of a bad query hides it until the cache misses at peak.

Q21

The orders table has 500 million rows and keeps growing. What do you do?

30-second answerPartition before you shard. Range-partition by month on placed_at, so the queries that matter, such as recent orders or one customer's latest page, touch one or two partitions. Retention then means dropping a partition instead of running a multi-hour DELETE. Keep the hot data small, move cold data to cheaper storage, and shard only when a single primary genuinely cannot take the write rate.

Go deeper: Give the PostgreSQL details that show you have done it. The primary key must include the partition key, so it becomes (id, placed_at). Partition pruning only works when the query filters on the partition key, so a lookup by id alone probes every partition: keep a narrow id-to-date lookup table, or use a time-ordered id that the date can be read from. Old partitions can be detached (DETACH PARTITION ... CONCURRENTLY from PostgreSQL 14) and archived without blocking queries on the parent table. Before any of this, check whether the pressure is really from reads, because a read model or a replica is far cheaper. If you do shard, key on the entity whose queries must stay local, usually the customer, and move cross-shard reporting to the warehouse.

Q22

How do you serve search and reporting without hurting the transactional database?

30-second answerGive each workload its own store, fed by events or replication, with the staleness it can tolerate. Full-text search and facets go to OpenSearch, a few seconds behind. Internal screens and exports read from a replica, milliseconds behind. Analytics go to a warehouse through CDC, minutes to hours behind. The primary serves transactions only, and nobody points a dashboard at it.

Go deeper: Name the replica trap, read-your-own-writes. The customer places an order, the confirmation page reads from the replica, and the order is not there yet. The fix is about five lines: after a write, send that user's reads to the primary for a short window, using a flag keyed on their id. For search, say out loud that results may miss the newest item for a second or two, and that the UI is designed for it. The interviewer is checking that you accept eventual consistency deliberately rather than by accident.

Q23

UUID or database sequence for primary keys?

30-second answerA sequence on PostgreSQL or Oracle, with Hibernate's allocationSize matching the sequence's INCREMENT BY, so ids arrive in blocks and inserts can batch. If ids must exist before persisting, or be generated across services, use a time-ordered UUIDv7, not a random v4. Avoid IDENTITY if you need batch inserts, because Hibernate cannot batch them.

Go deeper: Give the reason for each. With IDENTITY the id is known only after the INSERT, so Hibernate round-trips per row and silently turns off JDBC batching. A mismatched allocationSize produces duplicate-key errors that only appear under concurrency. A random v4 key sends every insert to a random leaf page of the B-tree, which costs write throughput and bloats the index on a large table. A v7 key starts with a timestamp, so inserts land almost in order. Hibernate 7.0 added UuidGenerator.Style.VERSION_7; its older TIME style is a different, version-1-like layout. And always use a surrogate key: "the order number will never change" describes today's process, not the data.
