Red flags, and how to say the right thing instead

What sinks the answerSay this instead
"I'd use microservices.""I'd start modular in one deployable, and split when I can point at scaling, SLA, team or compliance pressure."
"Kafka guarantees exactly-once.""At-least-once delivery into an idempotent handler gives exactly-once effects. Kafka's transactions are exactly-once within Kafka."
"We'd just add a cache.""I'd fix the query first; caching a bad query hides it until the cache misses at peak. Then cache, with an invalidation story."
"It scales horizontally.""The app layer scales horizontally; the bottleneck is the database write path, and here's how I'd relieve it."
"We use Spring Boot and Kubernetes."Describe behaviour and boundaries. Tools are the last five percent of the answer.
"I'd make the connection pool bigger.""I'd check pool wait time first. If the database is the constraint, a bigger pool just moves the queue. I'd size it from throughput × hold time."
"We'd add more consumers.""Consumers stop helping at the partition count, and scaling triggers a rebalance. I'd check whether the lag is on one partition or all of them first."
"I'd give it more heap.""Is there an OutOfMemoryError, or an exit 137? The second is native memory, and a bigger heap makes it worse."
"The payment call goes inside the transaction.""I'd never hold a database transaction open across a remote call. It holds a connection and its locks for the gateway's 800 ms."
"We validate the JWT, so it's secure.""The token says who you are. It doesn't say you own order 88421, so the ownership check happens on every access."
Silence while thinking."Let me think about the consistency requirement here — I'm weighing a saga against keeping it in one transaction." Narrate; they are grading reasoning.
Defending the first idea."That constraint changes it — with a hard 200 ms budget I'd drop the synchronous tax call and use a cached estimate."
No failure discussion.Volunteer it: "The obvious failure mode here is the payment gateway, so…" Bring it up before they have to ask.
The last minuteWhen they ask if you have questions, ask something that only someone who would have to live in the system would ask: "What's your deployment frequency, and what usually blocks it?" · "Where do your boundaries currently hurt most?" · "How do you decide when to extract a service?" The answers tell you more about the job than any job description, and asking them is itself a signal.
