Production and operations

The questions that tell an interviewer whether you have been on call for what you built. Mitigation before diagnosis, measurement before guessing, and a precise vocabulary for what the JVM does inside a container.

Q59

What does "production ready" mean to you?

30-second answerThat the team can run the service at 3 a.m. without the person who wrote it. Concretely: one artifact promoted through every environment, with no secrets inside. Timeouts on every outbound call. Liveness and readiness probes that mean different things. Graceful shutdown. A trace id end to end. SLOs with burn-rate alerts and a runbook for each alert. Idempotent consumers with a dead-letter topic. Expand-and-contract migrations. And a backup that has actually been restored.

Go deeper: Pick the two that most teams skip and say why they matter. Restoring a backup: most teams have never tried, and find out at the worst moment that the restore takes nine hours or leaves out a schema. And killing a pod in production, deliberately, during business hours: if that feels frightening, the graceful-shutdown and retry story is not real yet. Presenting this as a go-live checklist, rather than a list of technologies, is what the question is looking for.

Q60

What goes in the liveness probe, and what goes in readiness?

30-second answerLiveness asks "is this JVM wedged, and should it be restarted?", so it checks nothing external. Readiness asks "can this instance serve right now?", so it includes the dependencies the service cannot work without, such as its own database. Put the database in liveness and a thirty-second database blip fails liveness on every pod at once. Kubernetes restarts the whole fleet, and the restart storm turns a blip into a ten-minute outage.

Go deeper: Then the second-order rule: third-party dependencies belong in neither. If the payment gateway is in readiness, a gateway outage pulls every pod out of the load balancer, and customers get a connection error instead of "payments are temporarily unavailable, your basket is saved". Report it as a custom DEGRADED status that still maps to HTTP 200, and alert on it. In Boot these are the /actuator/health/liveness and /readiness groups. Add a startupProbe for slow starts so liveness can stay aggressive, and give every custom health check a timeout, because probes run every few seconds on every pod.

Q61

How do you deploy without dropping requests?

30-second answerThree things have to line up. Graceful shutdown, so on SIGTERM the server stops accepting new requests and finishes in-flight ones within a bounded timeout; this is Boot's default since 3.4. A preStop sleep of a few seconds, so the pod leaves the Service endpoints before it stops accepting, otherwise the last requests are routed to a closed connector. And a readiness probe that stays down until the new pod is warm, so it does not receive traffic early.

Go deeper: Then the parts that concern data rather than pods. During a rolling deploy two versions run against one schema, so migrations must be expand-only and backward compatible, run once as a job before the rollout rather than from every pod. Kafka consumers stop during shutdown, and any uncommitted batch is redelivered to the next owner, which is fine because the consumers are idempotent. Add a PodDisruptionBudget so a node drain cannot take every replica at once. And check that terminationGracePeriodSeconds, 30 seconds by default, is longer than the preStop sleep plus the shutdown timeout, or Kubernetes kills the JVM halfway through draining.

Q62

p99 latency doubled right after a deploy. Walk me through it.

30-second answerMitigate first, then diagnose. If the deploy is the obvious suspect and the SLO is burning, roll back; the diagnosis can use the data you already have and a canary. Then work from the cheapest check. Is it every request or only the tail? A trace of one slow request finds the hop. Then the query count and time on that hop, the pool wait time, and thread dumps. A CPU profile comes last, because CPU-bound application code is the rarest cause in an enterprise service.

Go deeper: Name the usual suspects, roughly in order of likelihood: a new N+1 or a missing index in the change, an unbounded result set, a new downstream call without a timeout, connection-pool starvation (where the time shows up as waiting to acquire rather than working), and a huge response being serialised. Mention the three-thread-dump trick: take three dumps ten seconds apart, and any thread stuck on the same frame in all three is the problem. Mention JFR too, which is safe to run in production at around 1% overhead. And compare before and after on the same dashboard under comparable load, because "it feels faster" is not a result.

Q63

Pods are being OOMKilled, but the heap graph looks fine. Why?

30-second answerBecause the process is killed for memory that is not heap. Exit code 137 with no OutOfMemoryError in the logs means the container went over its limit. Metaspace, thread stacks (up to about 1 MB for each platform thread), the code cache, and the direct buffers used by Netty and the Kafka client all live outside -Xmx. Raising the heap makes it worse.

Go deeper: The fix is headroom, set as a percentage: -XX:MaxRAMPercentage=75 rather than a hard-coded -Xmx, which crash-loops the day someone shrinks the container. Diagnose with Native Memory Tracking: start with -XX:NativeMemoryTracking=summary, then run jcmd <pid> VM.native_memory summary. Check the thread count, since hundreds of platform threads can reserve hundreds of megabytes of stack. Then contrast the other case: an actual OutOfMemoryError in the logs is a heap problem, usually a leak or an unbounded query, and it needs a heap dump rather than a bigger heap.

Q64

The heap climbs until the pod restarts. How do you find the leak?

30-second answerFirst confirm that it is a leak. A healthy heap is a sawtooth with a flat baseline; a leak is a sawtooth whose low points keep rising after full collections. Then take a class histogram with jcmd <pid> GC.class_histogram, which is often enough on its own. If it is not, take a heap dump from a pod already out of rotation and open it in Eclipse MAT: the dominator tree, then the path to GC roots. That path is the bug.

Go deeper: List the leaks that actually happen in Spring services: a ConcurrentHashMap used as a cache with no eviction (use Caffeine with a maximum size), a ThreadLocal set on a pooled thread and never removed, listeners registered and never unregistered, a list field on a singleton that only grows, and large objects in long-lived HTTP sessions. Then the handling point that shows experience in regulated work: a heap dump contains every string in memory, including names, addresses and tokens. It is production data, so it goes to restricted storage and is deleted afterwards, never onto a laptop. Also note that frequent deploys hide leaks: if pods restart as often as you release, a leak can stay invisible for years.

Q65

Which garbage collector would you use?

30-second answerG1, the default, for almost every enterprise service, and then fix allocation rather than tuning flags. Generational ZGC (JDK 21+) when the heap is large or there is a hard p99 target, because its pauses stay under a millisecond whatever the heap size, at a small cost in throughput. Parallel for batch jobs where only total throughput matters. The collector is rarely the real problem: an endpoint that loads 50,000 entities to return 20 rows is a query problem showing up as GC.

Go deeper: Volunteer the container trap. The JVM sizes itself from the processors it can see, and a CPU limit of 500m makes it see one. With one processor it picks SerialGC and sizes the common ForkJoinPool to a single thread. Give the container at least two full cores, or set -XX:ActiveProcessorCount. Then read symptoms before touching flags. Frequent young collections are normal. An old generation that grows after each full GC is a leak. Long full GCs mean the heap is too small for the live data, or leaking. G1 humongous allocations come from huge arrays, so page the query. Turn on GC logging with -Xlog:gc* so the evidence exists before you need it, and remember that MaxGCPauseMillis is a target, not a guarantee.

Q66

How do you decide what to alert on?

30-second answerOn symptoms the customer feels, derived from SLOs, not on CPU. Pick an SLI for each journey, such as the share of POST /orders that succeed within 1.5 s. Set an objective, such as 99.9% over 28 days. Then alert on how fast the error budget is burning: a fast window that pages (about 14× the sustainable rate over an hour) and a slow window that opens a ticket (about 6× over six hours). That catches both the outage and the slow bleed without paging on a blip.

Go deeper: Explain the budget. 99.9% allows about 43 minutes a month, and that figure turns "can we ship this risky change?" into arithmetic. Every paging alert has a runbook. Below the SLOs, dashboards follow RED for endpoints (rate, errors, duration) and USE for resources (utilisation, saturation, errors) such as pools, heap and disk. On the asynchronous side, consumer lag and dead-letter depth are the SLIs. And keep metric tags low-cardinality: an order id belongs in logs and traces, never on a metric.
